Topic and objective

TOPIC: Processes, threads and inter-process communication — the opening clause of GATE 2027 Section 8, Operating Systems, which reads "System calls, processes, threads, inter-process communication, concurrency and synchronization." This lesson takes the first four items. Concurrency and synchronisation get their own lesson, and deadlock, scheduling, memory and file systems follow.

LEARNING OBJECTIVE: Given a question, decide which of three things it is asking: which state transition is legal, how many processes or prints a fork sequence produces, or which resources a thread or process owns. Then answer it from a diagram rather than from memory — the edge list, the process tree, or the shared and private columns. Given a switch cost and a time slice, compute the fraction of CPU time lost. Given an IPC mechanism, say what it can carry and who may use it.

I read this topic as one question asked three times: what does this thing own, and what does it share? A process owns an address space and an execution context. A thread owns an execution context and shares the address space. Two things that share nothing need a kernel mechanism to talk. Every definition, count and mechanism below is that sentence at a different scale.

Prerequisites

  • What a function call does to the stack. A call pushes a frame and a return address; returning pops it. Built in Recursion.
  • What a variable in memory is. A named location whose address can be taken and printed. Built in Pointers in C.
  • Address spaces and page tables, at the level of "an address is translated". Introduced in Memory Hierarchy and Cache and taken further in the virtual-memory lesson still to come.
  • Counting by doubling. The fork count is 2 to the power n. Built in Counting and Combinatorics.

Nothing from the COA lessons is assumed beyond "a register holds a value" and "a page table translates an address". Where a fact needs the C standard — what fork returns — the POSIX specification is quoted, not remembered.

The five ideas to leave with

  1. A process is an address space, an execution context and a PCB. A program is none of those; it is a file.
  2. Ready waits for the CPU; blocked waits for an event. A woken process always joins the ready queue, which is why blocked to running does not exist.
  3. fork copies the caller, so every process alive executes it: n sequential forks give 2n processes and 2n − 1 children.
  4. Threads share everything except the program counter, the registers and the stack, so a thread switch need not touch the page table.
  5. Shared memory maps once and then needs synchronisation; message passing copies every message and can block instead.

Intuition: the recipe, the cook, and the kitchen

A recipe is a piece of paper. It does nothing on its own. A cook following it is a different kind of thing: the cook is standing somewhere, holding a spoon, halfway through step three. Two cooks following the same recipe are two cooks, each with their own spoon and their own place in the method, and if one adds salt to their pot the other pot does not get saltier.

That is the whole difference between a program and a process. The paper is the program; the cook at work is the process. The cook's hands and their place in the recipe are the execution context; the pots and ingredients are the address space; and the note the kitchen keeps on the wall saying who is on which station is the process control block.

Educational interpretation The analogy fixes one thing and only one thing: a process is an active thing with a position, not a passive list of steps. It is not a model of the scheduler, and it says nothing about memory.

Formal vocabulary, every symbol glossed

Program. A file of instructions and initial data on secondary storage.

Process. A program in execution, identified by a process identifier (pid), owning an address space and an execution context.

Address space. The set of addresses the process may name, holding code, global data, the heap and the stack.

Execution context. The program counter, the stack pointer and the general registers — what must be saved to resume exactly here.

PCB (process control block). The kernel's record for one process: its state, its saved context, its pid, its accounting and its open resources.

Thread. One execution context inside a process. A process has at least one thread; with more than one, the address space is shared and the contexts are not.

What the PCB actually holds

  • State — new, ready, running, blocked or terminated.
  • Saved context — program counter, stack pointer, registers.
  • Identity and accounting — pid, parent pid, owner, CPU time used.
  • Scheduling information — priority, queue pointers.
  • Memory information — a pointer to the page table or base and limit registers.
  • Open resources — the file descriptor table.

Notice what is missing: the code and the variables. Those live in the address space. The PCB holds what the kernel needs in order to resume the process, not the process's data.

Three checks that catch most slips

Check one. Ask whether the thing you are counting is a process, a child process, a print, or a byte. Each of the four appears in a real previous-year question, and three of them differ from each other.

Check two. For any state transition, ask what the process is waiting for. Waiting for the CPU means ready; waiting for anything else means blocked.

Check three. For any sharing question, ask whether the item belongs to the execution or to the process. The execution column is private; the process column is shared.

The five states, and why two edges are missing

Every state question is answered from this list and nothing else. Learn the six edges; the missing ones follow.

The six legal edges

  • new → ready — admitted by the long-term scheduler.
  • ready → running — dispatched by the short-term scheduler.
  • running → ready — preempted, typically by a timer interrupt.
  • running → blocked — the process itself asks for something not yet available.
  • blocked → ready — the awaited event has happened.
  • running → terminated — it exits, by returning or by exit().

Two edges that do not exist, and why

blocked → running. The event happening does not hand over the CPU. The CPU may be busy, and the scheduler must still choose. So the process moves to ready and waits its turn. This is the statement GATE 2020 Q12 marks false.

ready → blocked. Blocking is something a process does by executing a request, and executing requires the CPU. A process that is not running cannot ask for anything. This is one of the two transitions GATE 2024 Set 1 Q15 asks you to reject.

Ready is not "almost running"

The two words sound interchangeable and are not. A ready process is fully able to run: if the scheduler chose it this instant, it would execute. A blocked process is unable to run at all, no matter what the scheduler wants, because the thing it needs has not happened.

So "how many processes can run right now" is the ready queue plus the one running. A blocked process is never in that count.

Where the 2n comes from

A fork call is executed by every process that is alive when the call is reached. After the first call there are two processes, and both reach the second call, so each creates one child and the population doubles. After n sequential calls the population is 2n.

processes = 2n    children = 2n − 1

Mathematical derivation By induction on n. With n = 0 there is one process, and 20 = 1. If after k calls there are 2k, then every one of them reaches call k+1 and creates one child, giving 2·2k = 2k+1.

fork, exec, wait, exit — the four calls that make a process

These are the system calls the syllabus means by "system calls". Each one changes the state of a process in a way you can name.

What each call does

fork(). Creates a copy of the calling process. Returns 0 in the child, the child's pid in the parent, and a negative value on failure. Both copies continue after the call.

exec(). Replaces the calling process's address space and code with a new program. The pid is unchanged and the call does not return on success. This is how a child stops being a copy and becomes a different program.

wait(). Blocks the parent until one of its children terminates, and collects the child's exit status. Without it, a terminated child stays in the process table as a zombie.

exit(). Terminates the calling process, releasing its address space and keeping a status for the parent to collect.

Why the return value is the only difference

Both copies leave the call at the same instruction, with the same variables and the same open files. Nothing in their state differs except the value the call produced. So the value is the only way the code can know which copy it is, which is why the convention is a value that cannot be confused: zero for the child, a positive pid for the parent.

Verified fact The POSIX specification of fork() states that it returns 0 to the child process and the process ID of the child to the parent, and −1 on failure.

Copy on write does not break the rule

A real kernel does not copy the whole address space at the fork. It marks the pages copy-on-write, and copies a page only when one side writes to it. That is an optimisation, and it changes nothing you can observe: after the fork, the two address spaces behave as independent copies.

The one thing it explains is why a child can print the same address as its parent. The address printed is virtual, and the child's virtual layout is a copy of the parent's. Equal virtual addresses, different physical frames.

Threads: the same split, one level down

If a process is an address space plus a context, a thread is a context that borrows the address space. So the shared and private columns are not a list to memorise; they are the definition read off.

Private, because it belongs to an execution: program counter, registers, stack, thread id and state.

Shared, because it belongs to the process: code, global and static data, heap, open files, address space and page table.

Three sequential forks

fork(); fork(); fork(); — how many child processes are created?

After the first call: 2 processes. Both reach the second call, so 4. All four reach the third, so 8 processes. Children are processes minus the original: 8 − 1 = 7.

This is GATE CSE 2012, and the answer recorded there is 7. The trap is answering 8, which is the number of processes. The question said children.

The parent's value and the child's value

Take a = 10 before the call, and let the child do a = a + 5 while the parent does a = a − 5, each printing a and &a. The child prints 15, the parent prints 5, and both print the same address.

So if u, v are the parent's two numbers and x, y the child's, then u + 10 = x and v = y. That is the answer to the GATE CSE 2005 question.

Mathematical derivation The values differ by exactly the 10 that separates the two assignments. The addresses agree because the child's virtual layout is a copy of the parent's, so the same variable has the same virtual address in both.

A fork inside a loop that waits

int x = 3; while (x > 0) { fork(); printf("hello"); wait(NULL); x--; }

Iteration 1: one process forks, so two processes print — 2 prints. Iteration 2: both of those fork, so four print — 4. Iteration 3: all four fork, so eight print — 8. Total 14.

This is GATE CSE 2024 Set 1, and the recorded answer is 14. Note the two different counts: 14 prints, but only 8 distinct processes. The paper asks for prints.

What wait does to the count

A common guess is that wait(NULL) halves the count, because the parent pauses. It does not. Waiting changes when things happen and how many processes are alive at a given moment; it does not change how many processes eventually exist, nor how many times each of them executes the printing statement.

Mathematical derivation The count is a sum over iterations of the number alive in that iteration: 2 + 4 + 8. That sum is 2x+1 − 2, which for x = 3 is 16 − 2 = 14.

Worked examples, page 2 of 2

Three numerical shapes: the switch fraction, the thread switch, and a message channel's capacity.

The switch fraction

A time slice of 10 ms and a context switch of 0.1 ms. What fraction of CPU time goes to switching?

fraction = s / (q + s)

With s = 0.1 and q = 10: 0.1 / 10.1 = 0.00990, which is 0.99 per cent. With q = 1 ms: 0.1 / 1.1 = 0.0909, which is 9.09 per cent.

The denominator is the whole cycle, slice plus switch. Dividing by the slice alone gives 1 per cent and 10 per cent — close, and wrong in a way a NAT question can mark.

Why a thread switch is cheaper

Suppose saving and restoring the registers costs 0.5 µs, and changing the address space — flushing the cached translations and starting cold — costs 2 µs.

A thread switch pays only the first: 0.5 µs. A process switch pays both: 2.5 µs. The ratio is 5.

Educational interpretation The two numbers are a plausible model, not a measurement of any particular machine. The ratio is what the argument needs, and the argument holds for any pair where the address-space term dominates.

A pipe against a message queue

Two bytes are written to a channel, then three more. A reader asks for five bytes.

From a pipe: the reader receives 5 bytes in one read, spanning two separate writes, because a pipe has no boundaries. From a message queue: the reader receives 2 bytes — one whole message — because a queue keeps boundaries, and a second read is needed for the remaining 3.

Same bytes, different structure. Any question that says "one write, one read" is a message question; any question that says "a stream of bytes" is a pipe question.

The capacity is the parameter

A message channel with capacity 0 is a rendezvous: the sender blocks until the receiver actually receives. Capacity k lets the sender run k messages ahead and then blocks on the next. Capacity "unbounded" never blocks, and is a modelling assumption, never a real buffer.

So a question that asks whether the sender blocks is answerable only after you name the capacity. Without it, both answers are defensible, and the question is under-specified.

Boundary cases and counterexamples

The rules above are correct; these are the places where a careless reading of them breaks.

Zombie and orphan

A child that has terminated but whose parent has not called wait keeps its entry in the process table: that entry is a zombie. It holds no address space and cannot run, but it holds a pid, so a program that forks in a loop without waiting can exhaust the pid table.

A child whose parent terminated first is an orphan. It is re-parented, conventionally to the init process, which will reap it. So neither state breaks the state machine: both are terminated processes, and the difference is who collects the status.

When fork fails

fork returns a negative value when the process table or the memory is exhausted. So the count 2n is the count when every call succeeds — an assumption the papers state, and one a real program must check.

This is also why a "fork bomb" halts a machine: the tree grows until a call fails, and the failing process has no child to wait for.

exec does not create a process

exec replaces the calling process's program. The pid is unchanged, the address space is discarded and rebuilt, and the open files survive unless marked close-on-exec. So fork followed by exec in the child is the standard way to start a new program: the fork makes the copy that isolates the new program, and the exec fills it.

The distinction to keep: fork increases the process count, exec does not.

A pipe blocks in both directions

A pipe has a finite kernel buffer. A writer that fills it blocks until a reader drains some; a reader that finds it empty blocks until a writer adds something or closes the writing end. Reading after every writer has closed returns end of file, which is zero bytes — not an error and not a block.

So "the reader blocks forever" is only true while some writer still holds the pipe open. This is the edge case that decides whether a two-process pipeline terminates.

A signal is not a message

A signal carries a number and nothing else. Several occurrences of the same signal raised while it is pending may be delivered once, because the pending set records the signal, not a count. So signals cannot be used to count events reliably.

That is a genuine edge: an implementation detail with a visible consequence, and the reason a queue rather than a signal is the tool when every message matters.

The two-edge counterexample, stated minimally

One process is running; a second is blocked on a disk read. The read completes. What is the second process's state now?

It becomes ready, and only then may it be dispatched. The minimal counterexample to "blocked goes to running" is therefore any moment when the CPU is occupied by someone else — which is the normal case, not the exceptional one.

By contrast, if the CPU is idle and the second process is the only candidate, the scheduler dispatches it immediately. The transitions are still two: blocked to ready, then ready to running. Simultaneous in time, distinct in the model.

Eight beliefs that cost marks, and the sentence that repairs each

Each entry gives the wrong belief, the correction, and where the exam has used it.

1. "A blocked process can start running when its I/O completes."

Correction: it moves to ready. The scheduler still has to choose it, and the CPU may be busy. Used in: GATE CSE 2020 Q12, which marks exactly this statement false.

Why the belief survives: on an idle machine the two transitions happen so close together that they look like one.

2. "n forks create n children."

Correction: every process alive executes the call, so the population doubles: 2n processes and 2n − 1 children. Used in: GATE CSE 2012.

Why the belief survives: the first fork does create exactly one child, so the pattern looks linear for one step.

3. "The PCB contains the process's data."

Correction: it contains the state needed to resume — saved context, state, pid, accounting, resource pointers. The variables live in the address space.

Why the belief survives: both are "the process's stuff", and the PCB does hold a pointer to the page table, which sounds like memory.

4. "Each thread has its own heap."

Correction: the heap belongs to the process and is shared. A thread has its own stack, not its own heap. Used in: GATE CSE 2017 Set 2 Q7, whose only shared item in the list is the address space.

Why the belief survives: "thread-local storage" exists, but it is an allocation mechanism, not a per-thread heap.

5. "User-level threads can run on two cores."

Correction: the kernel sees one schedulable entity, so it cannot place two of them on two cores. Only kernel-level threads give true parallelism.

Why the belief survives: two user threads do appear to run "at the same time" — but that is interleaving inside one core, not parallelism.

6. "One write to a pipe is one read."

Correction: a pipe is a byte stream with no boundaries. Two writes can be read as one read, and one write can be read in pieces.

Why the belief survives: in small tests the timing usually makes it true, so the code appears to work until it is loaded.

7. "A context switch is part of the work."

Correction: no user instruction retires during a switch. It is overhead, and it is why utilisation is below one hundred per cent.

Why the belief survives: a switch is triggered by real work — a timer, a blocking call — so it feels like part of the computation.

8. "The parent gets 0 from fork."

Correction: the child gets 0, the parent gets the child's pid. A negative value means the call failed and there is no child at all. Used in: GATE CSE 2005, where reading the branches backwards flips the answer.

Why the belief survives: "0 means success" is a habit from other system calls, and here it means something else.

Two pairs that are easily confused

Preemption against blocking. Both take a process off the CPU, and only one of them is the process's own doing. Preemption is running to ready: the timer takes the CPU away and the process remains runnable. Blocking is running to blocked: the process asks for something unavailable and cannot run even if given the CPU. A question that asks which transitions are possible is usually testing this pair.

Process against thread. A process owns an address space; a thread borrows one. Everything else follows: isolation, the cost of a switch, the need for IPC, and the need for synchronisation. If you can say which of the two a sentence is about, the sentence is usually already answered.

Four question families, and the procedure for each

Every previous-year item I could verify in this topic falls into one of these four. The procedure is the same each time, and it is a page of work rather than a page of memory.

Family 1 — state transitions

Shape: a list of transitions, asked to pick the possible or the impossible ones. Sometimes with a diagram to interpret.

Procedure: write the six legal edges. Test each offered transition against them. Answer the question actually asked — possible or impossible — and check whether it is single or multiple select.

Seen in: GATE CSE 2009 Q32 (read a diagram), 2020 Q12 (which are true), 2024 Set 1 Q15 (which are not possible), 2024 Set 2 Q15 (which events force a switch).

Family 2 — counting processes

Shape: a short C program with one or more forks, asking for a count of processes, children or prints.

Procedure: draw the tree. Each fork doubles the number of nodes below it. Mark the printing statement at each node and count marks separately from nodes. If a branch is guarded by if (fork() == 0), follow the branch in the copy that takes it.

Seen in: GATE CSE 2005 (branch and address), 2012 (child count), 2024 Set 1 Q47 (prints in a loop with wait).

Family 3 — threads and what is shared

Shape: a list of resources, asking which are shared by threads or which must be saved on a switch.

Procedure: sort each item into the execution column or the process column. Then answer. For a switch question, ask whether the address space changes: if not, the page table base register is not saved.

Seen in: GATE CSE 2014 Set 1 Q20 (which statement is false), 2017 Set 2 Q7 (which are shared), 2023 Q12 (what is saved on a thread switch).

Family 4 — switch cost arithmetic

Shape: a time slice, a switch cost, and a question about the fraction of time, the number of switches, or utilisation.

Procedure: the cycle is slice plus switch, so the fraction is s / (q + s). Convert both to the same unit before dividing. If the question asks for a count of switches, count the boundaries in the schedule, not the processes.

This family borders on the scheduling lesson, which owns the full schedule arithmetic. Here it is only the cost of one switch.

Practice, page 1 of 2 — the previous-year set

MCQEasyPYQ — GATE CSE 2012

A process executes the code fork(); fork(); fork();. The total number of child processes created is

(A) 3    (B) 4    (C) 7    (D) 8

Answer: (C) 7

Three sequential calls give 23 = 8 processes, and the original is not a child, so 8 − 1 = 7.

(D) is the count of processes. (A) is one child per call, which ignores that every process executes the next call. (B) is 22, one call short.

MCQMediumPYQ — GATE CSE 2020, Q12

Consider these statements about process state transitions for a system using preemptive scheduling. I. A running process can move to ready state. II. A ready process can move to running state. III. A blocked process can move to running state. IV. A blocked process can move to ready state. Which are TRUE?

(A) I, II and III only    (B) II and III only    (C) I, II and IV only    (D) I, II, III and IV

Answer: (C) I, II and IV only

III is the only false statement. A blocked process must pass through ready before it can run, because the scheduler, not the event, decides who gets the CPU.

I is true because of preemption: the timer can take the CPU away. II is the dispatch edge. IV is the wake-up edge.

MSQMediumPYQ — GATE CSE 2024 Set 1, Q15

Which of the following process state transitions is/are NOT possible?

(A) Running to Ready    (B) Waiting to Running    (C) Ready to Waiting    (D) Running to Terminated

Answer: (B) and (C)

(B) fails because a woken process joins the ready queue. (C) fails because blocking requires executing a request, and only a running process executes anything.

(A) is possible by preemption and (D) is an ordinary exit, so neither can be the answer to a question that asks for the impossible ones.

MCQMediumPYQ — GATE CSE 2017 Set 2, Q7

Which of the following is/are shared by all the threads in a process? I. Program counter   II. Stack   III. Address space   IV. Registers

(A) I and II only    (B) III only    (C) I, II and IV    (D) All four

Answer: (B) III only

A thread is an execution context, so it needs its own program counter, registers and stack. Everything that belongs to the process — including the address space — is shared.

The trap is reading "stack" as part of the process. The process has a stack area, and each thread gets its own stack inside it.

Practice, page 2 of 2 — previous-year items and original variations

MSQMediumPYQ — GATE CSE 2023, Q12

Which one or more of the following need to be saved on a context switch from one thread T1 of a process to another thread T2 of the same process?

(A) Page table base register    (B) Stack pointer    (C) Program counter    (D) General purpose registers

Answer: (B), (C) and (D)

The page table base register holds the base of the page table for the current address space. Both threads share one page table, so the register already holds the right value and is not saved.

The stack pointer, program counter and general registers are per-thread execution state, so all three are saved. This is the same shared/private split, applied to a switch instead of a list.

NATHardPYQ — GATE CSE 2024 Set 1, Q47

Consider int x = 3; while (x > 0) { fork(); printf("hello"); wait(NULL); x--; }. The code compiles and runs correctly and no system call fails. The total number of times the printf statement is executed is ______.

Answer: 14

Iteration 1 has one process, which forks, so two processes print: 2. Iteration 2 has two, which fork, so four print: 4. Iteration 3 has four, which fork, so eight print: 8. Total 2 + 4 + 8 = 14.

The closed form is 2x+1 − 2 = 16 − 2 = 14. Note that the number of distinct processes is 8; the question asks for prints.

MSQMediumPYQ — GATE CSE 2024 Set 2, Q15

Process P is running. Which of these events will always trigger a context switch that moves P to a non-running state? (A) P makes a blocking system call to read a block from disk. (B) P accesses a page in swap, causing a page fault. (C) A disk interrupt is raised to deliver data requested by another process. (D) A timer interrupt is raised.

Answer: (A) and (B)

(A) blocks P until the read completes, so it leaves the CPU. (B) blocks P while the page is fetched from swap, which is the same situation with a different cause.

(C) does not touch P: the interrupt is served, and P resumes. (D) does not necessarily: a timer interrupt only preempts when the quantum has expired, and a non-preemptive policy ignores it.

MCQMediumPYQ — GATE CSE 2014 Set 1, Q20

Which one of the following is FALSE?

(A) User level threads are not scheduled by the kernel. (B) When a user level thread is blocked, all other threads of its process are blocked. (C) Context switching between user level threads is faster than between kernel level threads. (D) Kernel level threads cannot share the code segment.

Answer: (D)

Threads of one process share its code segment at either implementation level, because the code belongs to the process. So (D) is false.

(A) is true by definition, (B) is true because the kernel sees one execution unit, and (C) is true because a library switch needs no kernel entry.

MCQHardOriginal practice — counterexample

Two processes share a pipe. Process A writes 2 bytes, then 3 bytes. Process B then issues one read of 5 bytes, and the buffer holds all 5 bytes. Which statement is correct?

(A) The read returns 2 bytes, because a read returns at most one write.
(B) The read returns 5 bytes, spanning two writes.
(C) The read blocks until A writes 5 bytes in one call.
(D) The read returns 0, because message boundaries were lost.

Answer: (B)

A pipe is a byte stream with no boundaries. A read of 5 with 5 bytes buffered returns all 5, however they were written.

(A) is the message-queue behaviour, which is exactly the confusion this question tests. (C) invents a constraint that does not exist. (D) misreads "no boundaries" as "data loss" — nothing is lost, only the grouping.

NATMediumOriginal practice

A round-robin scheduler uses a time slice of 4 ms and a context switch costs 0.2 ms. What percentage of the CPU's time is spent on context switching, to two decimal places?

Answer: 4.76

The cycle is 4 + 0.2 = 4.2 ms, of which 0.2 ms is switching: 0.2 / 4.2 = 0.047619, which is 4.76 per cent.

Dividing by the slice alone gives 5 per cent. The two answers differ, and only the first is licensed by the model, because the cycle includes the switch.

MCQMediumOriginal practice — closely confused pair

A message channel between two processes has capacity 0. Process S sends one message; process R has not yet called receive. What happens?

(A) S blocks until R receives.   (B) The message is buffered and S continues.   (C) The send fails and returns an error.   (D) S continues, and the message is lost.

Answer: (A)

Capacity 0 means there is no buffer, so the sender and receiver must meet: the send cannot complete until a receive is in progress. That is a rendezvous.

(B) describes capacity 1 or more. (C) and (D) confuse "blocks" with "fails" — blocking is not failure, and the message is not lost, it is simply not yet handed over.

Revision sheet

Definitions, the edge list, the formulas and the traps, in the order a question uses them.

Definitions, one line each

  • Program — a file of instructions on secondary storage.
  • Process — a program in execution, with an address space and an execution context.
  • Address space — code, global data, heap and stack, as the process sees them.
  • Execution context — program counter, stack pointer and general registers.
  • PCB — the kernel's record of state, saved context, identity and resources.
  • Ready — runnable, waiting for the CPU. Blocked — waiting for an event.
  • Context switch — save one context, load another; no user work happens.
  • Thread — an execution context sharing its process's address space.
  • IPC — a kernel-provided mechanism for processes that share no address space.
  • Rendezvous — a zero-capacity channel, where sender and receiver must meet.

Formulas, with their licences

processes = 2n

Licence: n sequential forks, every one of them succeeding.

children = 2n − 1

Licence: the original process is not a child.

prints = 2x+1 − 2

Licence: the loop fork(); print; wait; x-- with every process inheriting x.

switch fraction = s / (q + s)

Licence: one switch per cycle, and the cycle is the slice plus the switch.

process switch = registers + address space

Licence: the two processes have different page tables. A thread switch omits the second term.

Decision procedure for any question

  1. Name the kind: states, copies, sharing, or switch cost.
  2. Draw the matching object: edge list, process tree, column split, or Gantt bar.
  3. Read the answer off the object.
  4. Check the unit: processes, children, prints, bytes, or a percentage.
  5. Check the licence of any formula you used.

Traps, one line each

  • Blocked never goes straight to running.
  • Ready never goes straight to blocked.
  • Children are 2n − 1, not 2n.
  • Prints are not processes.
  • The child's fork return value is 0; the parent's is positive.
  • The heap is shared; the stack is not.
  • A thread switch does not save the page table base register.
  • A pipe keeps bytes, not messages.
  • Capacity 0 blocks the sender.
  • The switch fraction's denominator includes the switch.

The one sentence

What does this thing own, and what does it share? A process owns an address space and an execution context; a thread owns a context and shares the space; two things that share nothing need the kernel to carry their words. Every state, count, cost and mechanism in this lesson is that sentence read at a different scale.
