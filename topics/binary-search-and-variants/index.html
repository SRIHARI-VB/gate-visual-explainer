Topic and objective

TOPIC: Binary search and its variants — the loop and its invariant, the exact comparison count, the two loop shapes and their faults, first and last occurrence, rotated arrays, bitonic arrays, search on a monotone predicate, and the decision-tree lower bound that explains why log n cannot be beaten.

LEARNING OBJECTIVE: Given a sorted array and a target, trace the loop and say how many comparisons it makes, including the last one. Given a piece of binary-search code, say whether it terminates and whether it can return a wrong index. Given a search problem that is not "find x in a sorted array" — duplicates, a rotation, a peak, a yes/no predicate — reduce it to the same loop with a changed test. Given a claim about the best possible search cost, justify it with a decision tree rather than an appeal to the algorithm.

I read this topic as one loop plus six different tests. Sorting and the Ω(n log n) bound for sorting live in the next lesson of this unit; hashing in the one after it. This lesson uses the complexity language of Asymptotic Complexity rather than re-teaching it.

GATE relevance

Verified fact Class A — explicitly in the syllabus.

Section 5 of the official GATE 2027 CS syllabus (IIT Madras) opens: "Searching, sorting, hashing. Asymptotic worst case time and space complexity. Algorithm design techniques: greedy, dynamic programming and divide-and-conquer. Graph traversals, minimum spanning trees, shortest paths."

Searching is the first word of the Algorithms section, and binary search is the standard example used to test the asymptotic vocabulary of the second sentence. Class A means a question is inside the declared boundary; it does not mean one is guaranteed, and it says nothing about marks.

Prerequisites

  • Arrays, Stacks and Queues — zero-based indexing and O(1) access to any cell. Every index here is a cell number, and the arithmetic only works because access is free.
  • Asymptotic Complexity — Θ and Ω notation. This lesson uses that language and does not re-derive it.
  • Recurrence Relations — unrolling F(n) = F(⌊n/2⌋) + 1. Scene 4 does it in full, so the lesson stands alone.
  • Counting and Combinatorics — the leaf count of a binary tree of a given height, which is all of scene 10.

Beyond that, only the logarithm is assumed: log base 2 of n is the number of times you can halve n before reaching 1. ⌊x⌋ rounds down and ⌈x⌉ rounds up; every use is spelled out the first time.

Afterwards

Answer any search question in this order: sorted or monotone?, which quantity?, which loop shape?, present or absent?, which assumption?

The costliest mistake is a count that is off by one because the final comparison was dropped. The second costliest is trusting a bound without checking that the array was sorted — binary search on unsorted data is not slow, it is wrong.

Estimates for planning, not measurements.

Level 1 — Intuition: the dictionary, not the phone book

A sorted array is a licence to skip. Open a dictionary in the middle and see "mango": every word before that page is smaller and every word after it is larger. You have not learned where your word is, but half the book cannot contain it. That single fact is the whole algorithm.

The trick is throwing away, not looking. A scan gains one position per comparison; a halving search gains half the remaining book. After ten comparisons a scan has looked at ten words, a halving search has eliminated all but one word in a thousand.

Educational interpretation The picture is good for the mechanism and poor for the cost — a real dictionary has a thumb index, which is direct addressing, not binary search. Keep it for the discarding; use the trace table in Level 4 for the counting.

Level 2 — The formal statement, symbol by symbol

Given an array A of n cells indexed 0 to n − 1 with A[0] ≤ A[1] ≤ … ≤ A[n − 1], and a value x, find an index i with A[i] = x, or report that none exists.

Keep two indices, lo and hi, meaning "the answer, if it exists, has an index between lo and hi inclusive". Then compute mid = ⌊(lo + hi) / 2⌋; compare A[mid] with x, which costs one unit; if equal return mid, if A[mid] < x set lo = mid + 1, otherwise set hi = mid − 1; repeat while lo ≤ hi. When lo > hi the range is empty and the answer is "absent".

Two conditions are assumed, and both matter. The array is sorted — otherwise the discarding is unjustified. The cells are directly addressable — otherwise reaching A[mid] costs something and the bound changes.

Level 3 — The invariant, and why it is the whole proof

An invariant is a sentence true before the loop, true after every pass, and strong enough at the end to give the answer:

If x occurs in A at all, it occurs at some index i with lo ≤ i ≤ hi.Everything strictly outside [lo, hi] has been proved not to hold x.

Before the loop it holds trivially, since lo = 0 and hi = n − 1 cover everything. Each pass preserves it: the cell mid is compared, and the updates throw away exactly the cells the comparison proved wrong. At the end, either A[mid] = x, or lo > hi and the range is empty — so x is absent, a proof rather than a guess.

Mathematical derivation The invariant makes the updates forced rather than remembered: mid must be excluded from both new ranges because it has just been tested, which is why they are mid + 1 and mid − 1 and never mid.

The one sentence to memorise

"Sorted, so the comparison at the middle eliminates one whole side." Every variant here — first occurrence, rotated, bitonic, predicate — is a different answer to which side does this comparison eliminate?

Faced with an unfamiliar search problem, do not look for an array to binary-search. Ask what one probe tells you, and whether the answer is then confined to a region you can halve.

Level 5 — The bound, derived rather than quoted

Let F(n) be the worst-case comparison count on n cells. The first comparison is spent on the middle cell; the two remaining pieces have ⌊(n − 1)/2⌋ and ⌈(n − 1)/2⌉ cells, so the larger has ⌊n/2⌋, and the adversary may put the target there. Hence

F(n) = F(⌊n/2⌋) + 1, with F(0) = 0.One comparison, then the same problem on at most half the cells.

Unrolling gives one per halving, ⌊log₂ n⌋ of them, plus the final comparison on the last surviving cell: F(n) = ⌊log₂ n⌋ + 1. Check: n = 16 gives 5, n = 15 gives 4, n = 1 gives 1, n = 2 gives 2.

Verified fact This page checks the form exhaustively: for every array of up to eight cells over a small alphabet and every target, the observed worst case equals ⌊log₂ n⌋ + 1, and the same expression equals ⌈log₂(n + 1)⌉ for every n up to one million.

Level 5 — The two conditions, and what breaks when one fails

Sortedness. On A = [5, 1, 9, 3] searching for 3, the first probe is index 1 holding 1. Since 1 < 3 the code sets lo = 2 and never looks at index 3. The answer is wrong, and no care in the loop body fixes it.

Direct access. In a linked list the middle cell cannot be reached in constant time; walking to it costs O(n) per probe and destroys the bound. That is why balanced search trees exist: they buy the halving while keeping insertion cheap.

The bound is on comparisons. A question asking for time, array accesses or iterations is asking something else: iterations can be one fewer than comparisons, and accesses are often two per comparison.

Level 6 — Edge cases a real implementation must survive

n = 0. lo = 0, hi = −1, the loop never runs, answer −1. Code that computes a[mid] before testing crashes here.

n = 1. One comparison decides everything — the only size where a miss and a hit cost the same in the worst case.

All cells equal. The first probe returns ⌊(n−1)/2⌋, which is a correct index and not the first one.

Target outside the values. Both ends cost ⌈log₂(n + 1)⌉ comparisons, the full worst case.

32-bit indices. lo + hi can overflow before the halving; compute lo + (hi − lo)/2 instead, which never exceeds hi.

A counterexample to "binary search is faster"

Take n = 8 and a target at A[0]. Linear search finds it in one comparison; binary search probes indices 3, then 1, then 0 — three.

So O(log n) describes how the cost grows, not that the algorithm is quicker on every input. For small n and favourable positions the scan wins; the crossover for a uniform target is around n ≈ 10 in practice.

Educational interpretation This is the growth-rate versus measurement distinction. An option saying "binary search always uses fewer comparisons" is false, and n = 8 refutes it in one line.

Level 7 — How GATE tests this, in four shapes

The count. "Maximum number of comparisons…" A formula, and the mark is lost by an off-by-one. Quote the convention.

The recurrence. The options are recurrences; the trap is a coefficient of 2, which describes searching both halves.

The code. A loop is printed; read the exit condition and the two updates together, because the faults live in their pairing.

The unfamiliar structure. Rotated, bitonic, a matrix, a predicate — asking for the best achievable bound. The answer is almost always Θ(log n), argued in two stages.

Example 1 — First occurrence among duplicates

A = [4, 8, 8, 8, 12, 16], find the first index holding 8. A plain binary search returns index 2 — a correct answer to the wrong question.

Change the test from "is A[mid] equal" to "is A[mid] < 8". If yes the first 8 is right, so lo = mid + 1; if no it is at mid or left, so hi = mid. Loop while lo < hi.

lo, himidA[mid]A[mid] < 8update
0, 638falsehi = 3
0, 318falsehi = 1
0, 104truelo = 1

lo = hi = 1, so the first 8 is at index 1, in three comparisons. hi started at n, not n − 1, because "one past the end" is a legal answer.

Example 2 — Counting the copies

upper_bound of 8 uses the test A[mid] ≤ 8 and returns index 4, the first index whose value is greater than 8. So upper_bound − lower_bound = 4 − 1 = 3 copies, in two logarithmic searches.

The safe recipe. Compute lb = lower_bound(x). If lb = n or A[lb] ≠ x the value is absent, count 0. Otherwise the first occurrence is lb and the last is ub − 1.

Mathematical derivation The two loops differ in one character: < against ≤. That decides whether the boundary sits before or after the run of equal values, which is why the difference counts them.

Example 3 — A rotated sorted array

A = [43, 47, 51, 3, 7, 11, 14], target 7. At each step exactly one half around mid is sorted, and that is the fact to exploit.

Example 4 — Reading a buggy loop

while (lo < hi) { mid = (lo + hi) / 2; if (A[mid] < x) lo = mid; else hi = mid; }Integer division, so mid is the floor.

Take A = [1, 3, 5, 7], x = 7. lo = 0, hi = 3, mid = 1 (3 < 7) so lo = 1; then mid = 2 (5 < 7) so lo = 2; then mid = 2 again, so lo = 2 again. The state (2, 3) repeats for ever.

The diagnosis. When hi = lo + 1 the floor of the average is lo itself, so lo = mid is a no-op. The repair is lo = mid + 1, valid because A[mid] < x already proved mid cannot be the answer. Verified fact The page's model reproduces the stall.

Example 5 — Bitonic array, the GATE 2025 Set 2 shape

A = [2, 5, 9, 14, 20, 17, 11, 6, 3] rises to 20 at index 4 and falls. Target 11.

Stage 1. Compare A[mid] with A[mid+1]: if the middle is smaller the array is still climbing, so lo = mid + 1, else hi = mid. Here lo = 0, hi = 8, mid = 4, A[4] = 20 > A[5] = 17, so hi = 4; mid = 2, 9 < 14, so lo = 3; mid = 3, 14 < 20, so lo = 4. Peak at index 4 in three comparisons.

Stage 2. Binary-search A[0..4] for 11 — not found, three comparisons. Then search A[5..8] = [17, 11, 6, 3] with the inequality reversed — found at index 6, two comparisons.

Total 3 + 3 + 2 = 8, which is also the worst case over all targets on nine cells. The bound is Θ(log n) because the stages add.

Example 7 — Three different counts

For n = 1000 the worst-case comparison count is ⌊log₂ 1000⌋ + 1 = 10. Other counts differ: iterations can be one fewer, because the last pass may exit without a further test; array accesses are usually two per comparison in a naive three-way test and one if the value is cached; time is comparisons times the cost of one comparison, which is not constant for strings or large records.

This is the commonest source of lost marks — the stem says "comparisons" and the options tempt you with iterations. Educational interpretation Comparing two 64-bit integers and two 1 KB strings are both "one comparison" asymptotically and differ by three orders of magnitude in practice.

Example 8 — The lower bound, met exactly

For n = 7 cells any comparison search needs at least ⌈log₂ 8⌉ = 3 comparisons in the worst case, because a tree of height 3 holds at most 2³ − 1 = 7 internal nodes and one node per answer is needed. Binary search on 7 cells uses exactly 3, so the bound is tight.

What the bound does not say. It does not apply to hashing, which reaches Θ(1) expected time by not comparing at all. A lower bound is always relative to a model, and the model here is "the only thing you may do is compare".

Empty and single-cell arrays

n = 0. lo = 0, hi = −1, the condition lo ≤ hi is false at once: zero comparisons, answer −1. Code that computes mid before testing indexes cell 0 of an empty array.

n = 1. One comparison — the only size where a hit and a miss cost the same in the worst case.

Two cells: where every off-by-one lives

With lo = 0 and hi = 1 the floor of the average is 0, so the probe is the first cell. Every fault in this topic appears here: lo = mid stalls, hi = mid with a ceiling stalls, and hi = mid − 1 with a floor terminates in one step.

Test with n = 2. A suite of odd sizes only will pass a buggy loop, because the stall needs a final window of exactly two cells.

All cells equal, and the meaning of "found"

A = [8, 8, 8, 8, 8], x = 8. The first probe is index 2, which equals 8, so the loop returns 2 — a correct index and not the first one.

Asked for the first occurrence the answer is 0, and only the lower_bound loop finds it; asked for the count it is 5, and only the difference of two boundary searches finds it. An option list containing 2 is testing whether you read the stem.

Target outside the range of values

A target below A[0] or above A[n − 1] is a miss costing ⌈log₂(n + 1)⌉ comparisons — the full worst case. The loop cannot know the target is outside until the range empties.

A one-line guard (if (x < A[0] || x > A[n−1]) return −1;) changes the constant and not the class.

The two loop shapes, side by side

Closed. while (lo <= hi) with hi = mid − 1 and lo = mid + 1; hi starts at n − 1; the loop exits with lo = hi + 1 and both pointers may leave the array.

Half-open. while (lo < hi) with hi = mid and lo = mid + 1; hi starts at n, a legal answer ("insert at the end"); on exit lo = hi is the answer index.

Both are correct. The error is borrowing the condition from one and the updates from the other.

Nearly the same problem, not the same problem

Search a sorted matrix — rows and columns sorted is not a sorted array. The staircase walk from the top-right corner is Θ(m + n), not Θ(log(mn)).

Find a peak in an arbitrary array — one probe against a neighbour eliminates a half, so Θ(log n), and the array need not be sorted at all.

Median of two sorted arrays — Θ(log(min(m, n))) by partitioning; a merge answer is Θ(m + n) and is the trap option.

1 — "Binary search works on any array"

Minimal counterexample. A = [5, 1, 9, 3], x = 3. The probe at index 1 is 1, and 1 < 3 sets lo = 2, so index 3 is never examined. It reports "absent".

Repair. Sort first — Θ(n log n) — which often makes a linear scan the better answer for a single query.

2 — "It uses ⌈log₂ n⌉ comparisons"

Minimal counterexample. n = 8: ⌈log₂ 8⌉ = 3, but searching for the largest element probes indices 3, 5, 6, 7 — four comparisons. The count is ⌊log₂ n⌋ + 1 = 4.

Why it survives. ⌈log₂ n⌉ is the number of halvings to reduce n to 1, one fewer than the number of comparisons. Both appear in textbooks, describing different quantities.

3 — "A miss is cheaper than a hit"

Minimal counterexample. On 16 cells, target 25 (absent) takes four comparisons and target 43 (present) also takes four. The worst miss equals the worst hit at ⌈log₂ 17⌉ = 5.

General fact. Every root-to-leaf path has length within one of every other, so all outcomes cost about the same — which is what makes the algorithm predictable.

4 — "More comparisons per step means a better class"

Minimal counterexample. At n = 100,000 binary search needs at most 17 comparisons; ternary needs 22. The ratio tends to 2 / log₂ 3 ≈ 1.262 — about 26% worse, with the same Θ(log n) class.

General fact. A k-way search costs (k − 1)/log₂ k per level, minimised at k = 2. Binary is optimal in this family.

5 — "lo = mid and hi = mid are always safe"

Minimal counterexample. while (lo < hi) { mid = (lo+hi)/2; if (A[mid] < x) lo = mid; else hi = mid; } on [1, 3, 5, 7] with x = 7 enters lo = 2, hi = 3 and repeats for ever, because mid = 2 = lo.

General fact. Every iteration must strictly shrink the range. A branch that can leave both pointers unchanged is a bug.

6 — "A lower bound is the answer"

Minimal counterexample. A bitonic array is not sorted, yet Θ(log n) is achievable because it is two monotone runs. Conversely, one query on a general unsorted array has no better strategy than a scan, so there the answer is Θ(n) even though Ω(log n) is still true.

General fact. A lower bound says nothing can be faster; it never says something is achievable. "Best possible" wants both bounds.

7 — "Binary search is always better than a scan"

Minimal counterexample. n = 8 with the target at index 0: the scan uses 1 comparison, binary search uses 3.

General fact. Asymptotics compare growth, not measurements — and for one query on a small array a scan also avoids the cost of sorting.

8 — "Rotation makes it Θ(n)"

Minimal counterexample. [43, 47, 51, 3, 7, 11, 14] with target 7 is found in three comparisons. Every rotation of every array up to seven cells is checked in this page's model, with no wrong answer and the worst case still ⌊log₂ n⌋ + 1.

General fact. What binary search needs is not global sortedness but a probe that eliminates a constant fraction. One sorted half per step is enough.

Pattern 1 — the count, asked directly

"What is the maximum number of comparisons made by binary search on a sorted array of n elements?" Decide the convention from the options: ⌊log₂ n⌋ + 1 counts the final equality test, ⌈log₂ n⌉ counts only the halvings. At n = 1000 both give 10; at n = 1024 they are 11 against 10, so the convention matters exactly at powers of two.

Shortcut and its assumption. ⌊log₂ n⌋ + 1 holds for the standard mid = ⌊(lo+hi)/2⌋ loop with lo ≤ hi. A different mid rule shifts the count by at most one.

Pattern 2 — the recurrence, as options

PYQ GATE CSE 2021, Set 2, Question 8. "What is the worst-case number of arithmetic operations performed by recursive binary search on a sorted array of size n?" Options Θ(√n), Θ(log₂ n), Θ(n²), Θ(n); answer Θ(log₂ n).

PYQ GATE 2024, Data Science & AI paper, Question 40. With F(n) the maximum comparisons on n cells, the true option is F(n) = F(⌊n/2⌋) + 1; the others were F(⌊n/2⌋) + F(⌈n/2⌉), F(⌊n/2⌋) and F(n − 1) + 1.

Same question in different clothes: the coefficient is 1 because one half is searched, and the +1 is the comparison at the middle.

Pattern 3 — reading a printed loop

PYQ GATE CSE 2014, Set 3, Question 42. A function ProcessArray over a sorted array had a loop whose body held two independent tests: if (x <= listA[k]) j = k − 1; and if (listA[k] <= x) i = k + 1;, with k = (i + j)/2 while i ≤ j.

The reasoning. When listA[k] equals x both tests fire at once, so i moves past j and the loop exits with k at the match; a smaller value fires only the second test, a larger one only the first. That is a binary search, and the answer was the option saying so.

The lesson. Two independent ifs are not an if/else chain, and here the overlap is deliberate — it is how the loop terminates on equality.

Pattern 4 — a structure that is not sorted

PYQ GATE CSE 2025, Set 2, Question 31. A bitonic array has A[1..i] non-decreasing and A[i+1..n] non-increasing; the question asked for the best possible bound on the worst-case comparison count. Answer: Θ(log n).

Two stages. Find the peak with a modified binary search — Θ(log n) — then binary-search the two monotone runs — Θ(log n) each. Sequential stages add.

The trap option. Θ(log² n), from multiplying the stages as if one were nested in the other. The answer is Θ(log n) whenever one probe can still eliminate a constant fraction.

The four traps that cost marks

Off by one. Forgetting the final comparison: at n = 16 the answer is 5, not 4.

Wrong ceiling. Writing ⌈log₂ n⌉ where ⌊log₂ n⌋ + 1 is meant; they differ at every power of two.

Wrong quantity. Iterations when comparisons were asked for, or comparisons when accesses were.

Wrong model. Applying the comparison bound to hashing, or assuming a lower bound implies an achievable algorithm.

What "best possible" is really asking

Two claims, and both are needed. An upper bound: here is an algorithm that achieves it. A lower bound: no comparison algorithm can do better, argued from the number of possible answers.

With only one of the two the answer is one-sided. That is why Θ(log n) for the bitonic array needs both the two-stage algorithm and the decision-tree argument.

MCQEasyPYQ: GATE CSE 2021 Set 2

What is the worst-case number of arithmetic operations performed by recursive binary search on a sorted array of size n?

  1. Θ(√n)
  2. Θ(log₂ n)
  3. Θ(n²)
  4. Θ(n)

Answer: B — Θ(log₂ n)

The recursion makes one comparison and calls itself on half the cells: T(n) = T(n/2) + Θ(1), which unrolls to Θ(log n). The base 2 is a constant factor and does not change the class. A would need each step to shrink n by a square root; C and D examine a linear number of cells.

The page's model confirms the exact count is ⌊log₂ n⌋ + 1.

A sorted array holds 1000 elements. With the standard loop while (lo <= hi), mid = ⌊(lo + hi)/2⌋, and the equality test counted, what is the maximum number of comparisons for one search?

Answer: 10

MCQMediumPYQ: GATE 2024 DA, Q40

Let F(n) be the maximum number of comparisons made while searching for an entry in a sorted array of size n using binary search. Which ONE is TRUE?

  1. F(n) = F(⌊n/2⌋) + 1
  2. F(n) = F(⌊n/2⌋) + F(⌈n/2⌉)
  3. F(n) = F(⌊n/2⌋)
  4. F(n) = F(n − 1) + 1

Answer: A

One comparison removes the middle cell; the two pieces have sizes ⌊(n−1)/2⌋ and ⌈(n−1)/2⌉, the larger is ⌊n/2⌋, and the adversary puts the target there. With F(1) = 1 this solves to ⌊log₂ n⌋ + 1. B gives F(4) = 4 against the true 3; C predicts 1 at n = 2 where 2 can be needed; D is linear search.

From the GATE 2024 Data Science & AI paper, not the CS paper; it is labelled with its own paper for that reason.

MCQMediumOriginal GATE-style

A = [4, 8, 8, 8, 12, 16]. Using the half-open loop with the test A[mid] < 8, what does the function return?

  1. 2 — some index holding 8
  2. 1 — the first index holding 8
  3. 3 — the last index holding 8
  4. 6 — the value is absent

Answer: B — index 1

Trace: (0, 6) → mid 3, 8 is not < 8, hi = 3; (0, 3) → mid 1, 8 is not < 8, hi = 1; (0, 1) → mid 0, 4 < 8, lo = 1. Now lo = hi = 1.

A is what the closed loop with an equality test returns — correct, but not the first. C needs the test A[mid] ≤ 8. D is wrong because 8 is present.

NATMediumOriginal GATE-style

A = [4, 8, 8, 8, 12, 16]. Using lower_bound and upper_bound, how many times does 8 occur?

Answer: 3

lower_bound = 1 and upper_bound = 4, so the count is 4 − 1 = 3. The count is upper − lower, not last − first: 3 − 1 = 2 would be one short, because a difference of positions counts the gaps.

Both searches are Θ(log n), so this beats a scan when the array is large and many queries arrive.

MCQMediumOriginal GATE-style

A = [43, 47, 51, 3, 7, 11, 14], a sorted array rotated left by three. Searching for 7 with the rotated-array search, how many element comparisons are made and what is returned?

  1. 2 comparisons, index 4
  2. 3 comparisons, index 4
  3. 4 comparisons, index 4
  4. Cannot be applied, the array is not sorted

Answer: B — 3 comparisons, index 4

(0, 6) mid 3: A[lo] = 43 > A[3] = 3, so the right half is sorted and 7 lies in [3, 14] → lo = 4. (4, 6) mid 5: A[4] = 7 ≤ A[5] = 11, left sorted, 7 in [7, 11] → hi = 4. (4, 4) mid 4: A[4] = 7, equal.

A comes from setting lo to the start of the sorted run (3) instead of mid + 1 (4) — the algorithm does not know where the run starts. D is the misconception: one half is always sorted.

MCQMediumPYQ: GATE CSE 2025 Set 2

An array A of length n with distinct elements is bitonic if A[1..i] is non-decreasing and A[i+1..n] is non-increasing. Which ONE is the best possible asymptotic bound on the worst-case number of comparisons to search it?

  1. Θ(n)
  2. Θ(1)
  3. Θ(log² n)
  4. Θ(log n)

Answer: D — Θ(log n)

Upper. Find the peak by comparing A[mid] with A[mid+1] and halving, then binary-search the ascending run and, if needed, the descending run with the inequality reversed — three sequential logarithmic stages, so Θ(log n). Lower. Any comparison search among n distinct values has n + 1 outcomes, so its tree needs height ⌈log₂(n + 1)⌉.

A is a scan, B cannot separate n answers, C is the designed trap from multiplying the stages.

MSQMediumOriginal GATE-style

Which statements about binary search on a sorted array of n cells are TRUE?

  1. Every iteration of a correct loop strictly shrinks the range.
  2. The worst case for a miss is at most the worst case for a hit.
  3. ⌈log₂ n⌉ and ⌊log₂ n⌋ + 1 are equal for every n.
  4. A miss costs fewer comparisons when the target is below A[0].

Answer: A and B

A is the termination argument: a branch that leaves both pointers unchanged repeats its state for ever, which is what lo = mid does when hi = lo + 1. B holds because every root-to-leaf path is within one level of every other.

C fails at n = 8 (3 against 4). D fails because a target below A[0] is found absent only after the range empties — the full ⌈log₂(n + 1)⌉.

MCQMediumOriginal GATE-style

An array of 2³¹ − 1 cells is searched with 32-bit signed int indices, lo = 1,500,000,000 and hi = 1,600,000,000. Which expression computes the correct middle index?

  1. (lo + hi) / 2
  2. lo + (hi − lo) / 2
  3. (lo + hi) >> 1 with an overflow check afterwards
  4. hi − (lo + hi) / 2

Answer: B

lo + hi = 3,100,000,000 exceeds 2,147,483,647 and wraps to −1,194,967,296, so halving gives a negative index. Computing hi − lo first keeps every intermediate inside the range: 100,000,000 halved is 50,000,000, plus lo gives 1,550,000,000.

C shifts an already-wrapped value — a shift does not undo the wrap. D gives 50,000,000, which is not the middle. The page computes both numbers as part of its model checks.

NATHardOriginal GATE-style

Using binary search on the answer with P(x) = (x³ ≥ 1,000,000) over the integer range 0 to 1023, what is the smallest x with P(x) true?

Answer: 100

100³ = 1,000,000, and 99³ = 970,299, so the boundary is 100. The predicate is monotone on non-negative integers, so the boundary is well defined.

The cost. 1024 values means ⌈log₂ 1024⌉ = 10 predicate calls; if each call scanned n items the total would be 10n, not 10.

MCQHardOriginal GATE-style

Which of these is NOT solvable in Θ(log n) comparisons by a binary-search-style algorithm?

  1. Search a sorted array of n cells
  2. Find the peak of an array whose entries first increase and then decrease
  3. Verify that an m × n matrix is sorted in every row and every column, given that it is
  4. Search a sorted array rotated by an unknown amount, all entries distinct

Answer: C

Verifying sortedness requires reading all mn entries in the worst case, because one out-of-place cell anywhere makes the answer "no". That is Θ(mn), and no halving argument reaches it.

A, B and D are all Θ(log n) — plain search, peak plus two monotone searches, and testing which half is sorted at each step. Searching a sorted matrix for a value is Θ(m + n) by the staircase walk, which is a different problem from verifying sortedness.

MSQHardOriginal GATE-style

Which statements about the comparison lower bound for searching are correct?

  1. Any comparison-based search among n distinct values needs at least ⌈log₂(n + 1)⌉ comparisons in the worst case.
  2. Binary search meets this bound exactly, so it is optimal among comparison searches.
  3. Because the bound is Ω(log n), every search problem on n items has a Θ(log n) algorithm.
  4. Hashing is not bound by it, because it does not locate the value by comparing.

Answer: A, B and D

A by counting: the tree needs n + 1 leaves and height h gives at most 2^h, so 2^h ≥ n + 1. B: binary search's tree is as balanced as n allows, so its height is exactly ⌈log₂(n + 1)⌉ — meeting a lower bound is what optimality means.

C fails: one query on an unsorted array still needs Θ(n), which is above the bound — a lower bound says nothing can be faster, not that something is this fast. D holds because the argument assumes the only operation is a comparison.

The five formulas

Worst case: F(n) = ⌊log₂ n⌋ + 1Equivalently ⌈log₂(n + 1)⌉; they agree for every n ≥ 1.

Recurrence: F(n) = F(⌊n/2⌋) + 1, F(0) = 0Coefficient 1, because only one half is searched.

Decision tree: h ≥ ⌈log₂(n + 1)⌉Height h holds at most 2^h − 1 internal nodes, one per comparison.

Occurrences: upper_bound(x) − lower_bound(x)Each is Θ(log n); the difference counts the copies.

k-way search: (k − 1)/log₂ k · log₂ nMinimised at k = 2; ternary is about 1.262 times worse.

The two loop shapes, with their faults

Closed. while (lo <= hi), hi = mid − 1, lo = mid + 1, hi from n − 1. Use it for any matching index with an equality test inside the loop.

Half-open. while (lo < hi), hi = mid, lo = mid + 1, hi from n. Use it for a boundary — first occurrence, insertion point, predicate flip.

Fault 1. lo = mid in the half-open loop: at hi = lo + 1 the state repeats. Fix: lo = mid + 1.

Fault 2. mid = ⌈(lo+hi)/2⌉ with hi = mid: at lo = 0, hi = 1 the state repeats. Fix: use the floor.

Fault 3. (lo + hi) / 2 in 32-bit arithmetic. Fix: lo + (hi − lo) / 2.

The five questions, in order

  1. Sorted, or a monotone predicate? Neither means Θ(n) for one query.
  2. Which quantity? Comparisons, iterations, array accesses or time — different numbers.
  3. Which loop shape? Read the exit condition and the two updates as a pair.
  4. Present, or possibly absent? A miss costs the same, not less.
  5. Which assumption? Distinct values, a distribution, a bound on the answer.

Run these five before reading the options. Almost every wrong option fails one of them.

Numbers worth remembering

n = 1 → 1. n = 8 → 4. n = 16 → 5. n = 1000 → 10. n = 1024 → 11. n = 10⁶ → 20. n = 2³¹ − 1 → 32.

Average for a uniform target: 3.27 at n = 15, 4.16 at n = 31 — close to the worst case, which is why binary search is predictable.

Doubling n adds exactly one comparison. That sentence is the practical meaning of log n, and it is what "how does the count grow when the array doubles" is looking for.

Six traps in one place

Forgetting the final equality comparison. Writing ⌈log₂ n⌉ instead of ⌊log₂ n⌋ + 1. Assuming a miss is cheaper than a hit. Assuming binary search is faster on every input. Assuming rotation or bitonicity makes it Θ(n). Treating a lower bound as an achievable algorithm.

Each has a one-line counterexample in the Misconceptions tab. If you can produce the counterexample, you cannot be caught by the trap.

Where this leads next

Sorting — the same decision-tree argument applied to permutations gives Ω(n log n), and mergesort meets it. The next lesson in this unit.

Hashing — the escape from the comparison model, and the reason a lower bound is always relative to a model.

Balanced trees — keeping the halving while allowing insertion; already in Trees, BSTs and Heaps.

Greedy and DP — binary search on the answer is the bridge: a monotone predicate turns an optimisation problem into a search, and the search is the cheap part.
