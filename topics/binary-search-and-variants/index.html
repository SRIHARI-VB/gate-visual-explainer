Topic and objective

TOPIC: Binary search and its variants — the loop and its invariant, the exact comparison count, the two loop shapes and their faults, first and last occurrence, rotated arrays, bitonic arrays, search on a monotone predicate, and the decision-tree lower bound that explains why log n cannot be beaten.

LEARNING OBJECTIVE: Given a sorted array and a target, trace the loop correctly and say how many comparisons it makes, including the last one. Given a piece of binary-search code, say whether it terminates and whether it can return a wrong index. Given a search problem that is not "find x in a sorted array" — duplicates, a rotation, a peak, a yes/no predicate — reduce it to the same loop with a changed test. Given a claim about the best possible search cost, justify it with a decision tree rather than with an appeal to the algorithm.

I read this topic as one loop plus six different tests. Sorting, and the Ω(n log n) lower bound for sorting, live in the next lesson of this unit; hashing lives in the one after it. This lesson is only about searching, and it uses the complexity language of the Asymptotic Complexity lesson rather than re-teaching it.

GATE relevance

Verified fact Class A — explicitly in the syllabus.

Section 5 of the official GATE 2027 CS syllabus (IIT Madras) opens with: "Searching, sorting, hashing. Asymptotic worst case time and space complexity. Algorithm design techniques: greedy, dynamic programming and divide-and-conquer. Graph traversals, minimum spanning trees, shortest paths."

Searching is the first word of the Algorithms section. Binary search is also the standard example used to test the asymptotic vocabulary of the second sentence, so one question can carry both.

Class A means a question here is inside the declared boundary. It does not mean one is guaranteed, and it says nothing about the number of marks. The previous-year questions quoted in this lesson are observations about old papers, not a forecast.

Prerequisites

Four published lessons carry what this one uses:

  • Arrays, Stacks and Queues — zero-based indexing, and why an array gives O(1) access to any cell. Every index in this lesson is a cell number, and the arithmetic only works because access is free.
  • Asymptotic Complexity — Θ and Ω notation, and the fact that a recurrence with one recursive call is unrolled by division. This lesson uses that language and does not re-derive it.
  • Recurrence Relations — solving F(n) = F(⌊n/2⌋) + 1 by unrolling. Scene 4 does the unrolling in full, so the lesson stands alone, but the method is taught there.
  • Counting and Combinatorics — the count of leaves in a binary tree of a given height, which is the whole of scene 10.

The only mathematics assumed beyond that is the logarithm: log base 2 of n is the number of times you can halve n before reaching 1. Floor and ceiling are used constantly — ⌊x⌋ is x rounded down, ⌈x⌉ is x rounded up — and every use is spelled out in words the first time.

What you should be able to do afterwards

Answer any search question in this order: is the structure sorted or is a predicate monotone?, which quantity is being counted?, which loop shape is this?, is the target guaranteed present?, which assumption did the stem give?

The most expensive mistake in this topic is a count that is off by one because the final comparison was dropped. The second most expensive is trusting a bound without checking whether the array was actually sorted — binary search on unsorted data is not slow, it is wrong.

Level 1 — Intuition: the dictionary, not the phone book

A sorted array is a licence to skip. If you open a dictionary in the middle and see the word "mango", then every word before that page is smaller than "mango" and every word after it is larger. You have not learned where your word is, but you have learned that half the book cannot contain it. That single fact is the whole algorithm.

The trick is throwing away, not looking. A linear scan gains one position per comparison. A halving search gains half the remaining book per comparison. After ten comparisons a linear scan has looked at ten words; a halving search has eliminated all but one word in a thousand.

Educational interpretation The dictionary picture is good for the mechanism and poor for the cost. A real dictionary has a thumb index, which is closer to direct addressing than to binary search. Keep the picture for the discarding, and use the trace table in Level 4 for the counting.

Level 2 — The formal statement, symbol by symbol

Given an array A of n cells, indexed from 0 to n − 1, with A[0] ≤ A[1] ≤ … ≤ A[n − 1], and a value x, find an index i with A[i] = x, or report that none exists.

The algorithm keeps two indices, lo and hi, meaning "the answer, if it exists, has an index between lo and hi inclusive". Then:

  • Compute the middle index mid = ⌊(lo + hi) / 2⌋, the floor of the average, so mid is an integer cell number.
  • Compare A[mid] with x. That comparison costs one unit.
  • If they are equal, return mid. If A[mid] < x, the answer cannot be at mid or to its left, so set lo = mid + 1. Otherwise set hi = mid − 1.
  • Repeat while lo ≤ hi. When lo > hi the range is empty, and the answer is "absent".

Two conditions are being assumed, and both matter. The array is sorted — otherwise the discarding is unjustified. The cells are directly addressable — otherwise reaching A[mid] would itself cost something, and the bound would change.

Level 3 — The invariant, and why it is the whole proof

An invariant is a sentence that is true before the loop, true after every pass, and strong enough at the end to give the answer. Here it is:

If x occurs in A at all, then it occurs at some index i with lo ≤ i ≤ hi.Everything strictly outside [lo, hi] has already been proved not to hold x.

Before the loop it holds trivially, because lo = 0 and hi = n − 1 cover the whole array. Each pass preserves it: the cell mid is compared, and the two possible updates throw away exactly the cells that the comparison proved wrong. At the end, if the loop stopped because A[mid] = x, we have the answer; if it stopped because lo > hi, the range is empty, and an empty range cannot contain x, so x is absent — a proof, not a guess.

Mathematical derivation The invariant is what makes the two updates forced rather than remembered. mid must be excluded from both new ranges because it has just been tested; that is why the updates are mid + 1 and mid − 1 and never mid.

The one sentence to memorise

"Sorted, so the comparison at the middle eliminates one whole side." Every variant in this lesson — first occurrence, rotated, bitonic, predicate — is a different answer to the question which side does this comparison eliminate?

When you meet an unfamiliar search problem, do not look for an array to binary-search. Ask what a single probe tells you, and whether the answer is then confined to a region you can halve.

Four comparisons. The count is the number of rows, and the last row counts, because the equality test is itself a comparison. For n = 16 the formula gives ⌊log₂ 16⌋ + 1 = 4 + 1 = 5, and this particular target was luckier than the worst case.

Four comparisons again, and the answer is −1. Note the shape of the failure: the range became empty because lo moved past hi, not because anything was found. Mathematical derivation A miss never costs more than the worst hit, because both walk a root-to-leaf path in the same comparison tree and all such paths are within one level of each other.

Level 5 — The bound, derived rather than quoted

Let F(n) be the worst-case number of comparisons on n cells. The first comparison is spent on the middle cell. The two remaining pieces have ⌊(n − 1)/2⌋ and ⌈(n − 1)/2⌉ cells, so the larger has ⌊n/2⌋ cells, and the adversary may put the target there. Hence

F(n) = F(⌊n/2⌋) + 1, with F(0) = 0.One comparison, then the same problem on at most half the cells.

Unrolling: F(n) = 1 + 1 + … + 1 over as many halvings as n survives, which is ⌊log₂ n⌋, and then one final comparison on the last surviving cell. So F(n) = ⌊log₂ n⌋ + 1. Check it: n = 16 gives 5, n = 15 gives 4, n = 1 gives 1, n = 2 gives 2.

Verified fact The closed form is checked exhaustively in this page's model: for every array of up to nine cells over a small alphabet and every target, the observed worst case equals ⌊log₂ n⌋ + 1, and the same expression equals ⌈log₂(n + 1)⌉ for every n up to one million.

Level 5 — The two conditions, and what breaks when one fails

Sortedness. On A = [5, 1, 9, 3] searching for 3, the first probe is index 1 holding 1. Since 1 < 3 the code sets lo = 2 and never looks at index 3. The answer is wrong, and no amount of care in the loop body fixes it.

Direct access. In a linked list you cannot reach the middle cell in constant time; you must walk to it, which costs O(n) per probe and destroys the bound. Binary search is a statement about arrays, and it is why balanced search trees exist: they buy the halving while keeping insertion cheap.

The bound is on comparisons. A question that asks for time, for array accesses, or for iterations is asking a different question. Iterations of the loop can be one fewer than comparisons, and array accesses are often two per comparison.

Level 6 — Edge cases that a real implementation must survive

n = 0. lo = 0, hi = −1, the loop never runs, and the answer is −1. Any code that computes a[mid] before the first test crashes here.

n = 1. One comparison decides everything. A miss and a hit cost the same, which is the only size where that is true for the worst case.

All cells equal. Every comparison returns "equal" at the first probe, so the answer is index ⌊(n−1)/2⌋. That is a correct index, not the first one — the difference matters when the question says "first occurrence".

Target below every cell, or above every cell. Both take ⌈log₂(n + 1)⌉ comparisons, the same as the worst hit. A miss at an end is not cheaper than a miss in the middle.

n = 2³¹ − 1 with 32-bit indices. The sum lo + hi can overflow before the halving, producing a negative index. The fix is to compute lo + (hi − lo)/2, which never exceeds hi.

A counterexample to "binary search is faster"

Take n = 8 and a target that sits at A[0]. Linear search finds it in one comparison. Binary search on the same input probes index 3, then index 1, then index 0: three comparisons.

So the O(log n) claim is a statement about how the cost grows, not a statement that the algorithm is quicker on every input. For small n and favourable positions, the scan wins. The crossover for n cells, assuming a uniform target, is around n ≈ 10 in practice.

Educational interpretation This is exactly the distinction the asymptotic lesson draws between a growth rate and a measurement. An exam option that says "binary search always uses fewer comparisons" is false, and the n = 8 example refutes it in one line.

Level 7 — How GATE tests this, in three shapes

Shape 1, the count. "What is the maximum number of comparisons…" The answer is a formula, and the mark is lost by an off-by-one. Quote the convention: comparisons including the final equality test.

Shape 2, the recurrence. "Let F(n) be the maximum number of comparisons… which of the following is true?" Here the options are recurrences, and the trap is a coefficient of 2, which describes searching both halves.

Shape 3, the code. A loop is printed and you must say whether it terminates, whether it is binary search, or what it returns for a given input. Read the exit condition and the two updates together — the faults live in their pairing.

A fourth shape has become common since 2020: a structure that is not a sorted array — rotated, bitonic, a matrix, a predicate — and a question asking for the best achievable bound. The answer is almost always Θ(log n) with a two-stage argument.

Example 1 — First occurrence among duplicates

A = [4, 8, 8, 8, 12, 16], find the first index holding 8. A plain binary search returns index 2 (the middle of the whole array), which is a correct answer to the wrong question.

Change the test. Instead of "is A[mid] equal", ask "is A[mid] < 8". If yes, the first 8 is to the right, so lo = mid + 1. If no, the first 8 is at mid or to its left, so hi = mid. Loop while lo < hi.

lo, himidA[mid]test A[mid] < 8update
0, 638falsehi = 3
0, 318falsehi = 1
0, 104truelo = 1

lo = hi = 1, so the first 8 is at index 1. Three comparisons. Note hi started at n, not n − 1: the answer may be "one past the end", and the half-open window allows that.

Example 2 — Counting the copies

On the same array, upper_bound of 8 uses the test A[mid] ≤ 8 and returns index 4, the first index whose value is greater than 8.

upper_bound − lower_bound = 4 − 1 = 3, the number of copies of 8. Two logarithmic searches answer "how many times does x occur" in Θ(log n), which no scan can beat asymptotically.

The safe recipe. Compute lb = lower_bound(x). If lb = n or A[lb] ≠ x, the value is absent — count 0. Otherwise the first occurrence is lb and the last is ub − 1.

Mathematical derivation The two loops differ in exactly one character: < against ≤. That character decides whether the boundary is placed before or after the run of equal values, which is why the difference counts them.

Example 3 — A rotated sorted array

A = [43, 47, 51, 3, 7, 11, 14], n = 7, target 7. At each step exactly one of the two halves around mid is sorted, and that is the fact to exploit.

Three comparisons. The test "is the left half sorted" is A[lo] ≤ A[mid]; when it fails, the right half is the sorted one. Mathematical derivation With distinct values the two cases are exhaustive, because a rotation point inside the left half leaves the right half untouched.

Example 4 — Reading a buggy loop

Here is a loop printed as an exam question:

while (lo < hi) { mid = (lo + hi) / 2; if (A[mid] < x) lo = mid; else hi = mid; }Integer division, so mid is the floor.

Take A = [1, 3, 5, 7] and x = 7. Start lo = 0, hi = 3, mid = 1 (value 3 < 7) so lo = 1. Next mid = 2 (value 5 < 7) so lo = 2. Next mid = 2 again, so lo = 2 again. The state (2, 3) repeats for ever.

The diagnosis. When hi = lo + 1, the floor of the average is lo itself, so lo = mid is a no-op. The repair is lo = mid + 1, which is valid here because A[mid] < x already proved that mid cannot be the answer. Verified fact The page's model reproduces the stall: it enters the state (2, 3) and never leaves.

Example 5 — Bitonic array, the GATE 2025 Set 2 shape

A = [2, 5, 9, 14, 20, 17, 11, 6, 3] rises to 20 at index 4 and then falls. Target 11.

Stage 1, find the peak. Compare A[mid] with A[mid+1]. If A[mid] < A[mid+1] the array is still climbing, so lo = mid + 1; else hi = mid. Here: lo = 0, hi = 8, mid = 4, A[4] = 20 > A[5] = 17, so hi = 4; then mid = 2, A[2] = 9 < A[3] = 14, so lo = 3; then mid = 3, A[3] = 14 > A[4] = 20? No — 14 < 20, so lo = 4. Peak at index 4 in three comparisons.

Stage 2, search the ascending run A[0..4] for 11: not found, in three comparisons. Then the descending run A[5..8] = [17, 11, 6, 3], searched with the inequality reversed: found at index 6 in two comparisons.

Total 3 + 3 + 2 = 8 comparisons, and the worst case over all targets on nine cells is also 8. The asymptotic bound is Θ(log n), because the three stages add.

Example 6 — Binary search on a predicate

No array is sorted here. The question is: what is the smallest whole number x whose square is at least 1000?

The predicate P(x) = (x·x ≥ 1000) is monotone: once true it stays true, because squaring is increasing on non-negative numbers. So the answer is the flip point, and it can be found by halving the range of candidate answers, 0 to 63.

Six predicate calls, and the answer is 32. The cost is ⌈log₂ 64⌉ = 6, the logarithm of the range, not of any data. Verified fact The model checks this loop against a linear scan for every boundary value from 0 to 1000.

Example 7 — Iterations, comparisons, and array accesses are three numbers

For n = 1000 the worst-case comparison count is ⌊log₂ 1000⌋ + 1 = 9 + 1 = 10. But other counts differ:

  • Loop iterations can be one fewer than comparisons, because the last pass may exit without a further test.
  • Array accesses are usually two per comparison in a naive three-way test (one for A[mid], and one more if the code re-reads it), and one if the value is cached in a variable.
  • Time is comparisons multiplied by the cost of one comparison, which for strings or large records is not constant.

This is the most common source of lost marks: the stem says "comparisons" and the option list tempts you with the iteration count. Educational interpretation The distinction is not pedantry — a comparison of two 64-bit integers and a comparison of two 1 KB strings are both "one comparison" asymptotically and differ by three orders of magnitude in practice.

Example 8 — The lower bound, met exactly

For n = 7 cells, any comparison search needs at least ⌈log₂ 8⌉ = 3 comparisons in the worst case, because a tree of height 3 holds at most 2³ − 1 = 7 internal nodes, and we need one node per possible answer.

Binary search on 7 cells uses exactly 3 comparisons in the worst case. The bound is therefore tight: no comparison-based algorithm can do better, and this one does as well as possible.

What the bound does not say. It does not say 3 comparisons are needed to find a value you have stored elsewhere, and it does not apply to hashing, which reaches Θ(1) expected time by not comparing at all. A lower bound is always relative to a model of computation, and the model here is "the only thing you may do is compare".

Empty and single-cell arrays

n = 0. With lo = 0 and hi = −1 the condition lo ≤ hi is false immediately, so there are zero comparisons and the answer is −1. Any implementation that computes mid before testing will index cell 0 of an empty array.

n = 1. One comparison. This is the only size where a hit and a miss cost the same in the worst case, and the only size where ⌊log₂ n⌋ + 1 = ⌈log₂(n + 1)⌉ = 1 is easy to see.

Two cells: where every off-by-one lives

With lo = 0 and hi = 1 the floor of the average is 0, so the probe is the first cell. Every fault in this topic appears here: lo = mid stalls, hi = mid with a ceiling rounding stalls, and hi = mid − 1 with a floor rounding terminates correctly in one step.

Test with n = 2. A test suite with odd sizes only will pass a buggy loop, because the stall needs an even final window of exactly two cells.

All cells equal, and the meaning of "found"

A = [8, 8, 8, 8, 8] and x = 8. The first probe is index 2, which equals 8, so the loop returns 2. That is a correct index and not the first one.

If the question asks for the first occurrence, the answer is 0, and only the lower_bound loop finds it. If it asks for the count, the answer is 5, and only the difference of two boundary searches finds it. An option list containing 2 is testing whether you read the stem.

Target outside the range of values

A target smaller than A[0] or larger than A[n − 1] is a miss, and it costs ⌈log₂(n + 1)⌉ comparisons — the full worst case, not a shortcut. The loop has no way to know the target is outside until the range empties.

A one-line guard (if (x < A[0] || x > A[n−1]) return −1;) changes the constant and not the class, and it is worth mentioning when a question asks about the best case of an unsuccessful search.

The two loop shapes, side by side

Closed shape. while (lo <= hi) with hi = mid − 1 and lo = mid + 1. hi starts at n − 1. The loop can exit with lo = hi + 1, and both pointers may point outside the array.

Half-open shape. while (lo < hi) with hi = mid and lo = mid + 1. hi starts at n, which is a legal answer ("insert at the end"). On exit lo = hi is the answer index.

Both are correct. The error is borrowing the condition from one and the updates from the other, which is why a code-reading question is usually just asking you to pair them correctly.

Nearly the same problem, not the same problem

Search a sorted matrix (rows and columns sorted) — that is not a sorted array. The correct algorithm starts at the top-right corner and moves left or down, which is Θ(m + n), not Θ(log(mn)).

Find a peak in an arbitrary array — one probe compares a cell with its neighbours and eliminates a half, so it is Θ(log n), but the array need not be sorted at all. Confusing this with binary search on a sorted array is a common slip.

Find the median of two sorted arrays — Θ(log(min(m, n))) by partitioning, not by merging. The loop looks like binary search and the predicate is "the partition is correct"; a merge answer is Θ(m + n) and is the trap option.

Misconception 1 — "Binary search works on any array"

Belief. It is a search algorithm, so it finds the value whenever the value is there.

Minimal counterexample. A = [5, 1, 9, 3], x = 3. Probe index 1, value 1. Since 1 < 3 the code sets lo = 2 and never examines index 3, where the 3 sits. It reports "absent".

The repair. Sort first — which costs Θ(n log n), and often makes a linear scan the better answer for a single query.

Misconception 2 — "Binary search uses ⌈log₂ n⌉ comparisons"

Belief. The textbook formula with the ceiling is the count.

Minimal counterexample. n = 8. ⌈log₂ 8⌉ = 3, but a search for the largest element probes indices 3, 5, 6, 7 — four comparisons. The correct count is ⌊log₂ n⌋ + 1 = 4.

Why the confusion survives. ⌈log₂ n⌉ is the number of halvings needed to reduce n to 1, which is one fewer than the number of comparisons. Both appear in textbooks, describing different quantities.

Misconception 3 — "A miss is cheaper than a hit"

Belief. If the value is not there, the search stops early.

Minimal counterexample. n = 16, target 25 (absent) takes four comparisons; target 43 (present) also takes four. Neither is cheaper, and the worst miss equals the worst hit at ⌈log₂ 17⌉ = 5.

The general fact. Every root-to-leaf path in the comparison tree has length within one of every other, so all outcomes cost about the same. This is what makes the algorithm predictable.

Misconception 4 — "More comparisons per step means a better class"

Belief. Ternary search compares two cells and cuts to a third, so it must be faster than binary search.

Minimal counterexample. At n = 100,000 binary search needs at most 17 comparisons; ternary needs 22. The ratio tends to 2 / log₂ 3 ≈ 1.262, so ternary is about 26% worse, with the same Θ(log n) class.

The general fact. A k-way search costs (k − 1) log_k n = (k − 1)/log₂ k · log₂ n comparisons, which is minimised at k = 2. Binary is optimal in this family.

Misconception 5 — "lo = mid and hi = mid are always safe"

Belief. The boundary updates are a matter of taste.

Minimal counterexample. while (lo < hi) { mid = (lo+hi)/2; if (A[mid] < x) lo = mid; else hi = mid; } on [1, 3, 5, 7] with x = 7 enters the state lo = 2, hi = 3 and repeats it for ever, because mid = 2 = lo.

The general fact. Every iteration must strictly shrink the range. If a branch can leave both pointers unchanged, that branch is a bug.

Misconception 6 — "A lower bound is the answer to the question"

Belief. Since comparison search needs Ω(log n), an answer of Θ(log n) is always correct.

Minimal counterexample. A bitonic array is not sorted, yet Θ(log n) is achievable — because the array is two monotone runs. Conversely, searching a general unsorted array with one query has no better strategy than a scan, so the answer there is Θ(n) even though the Ω(log n) bound is still true.

The general fact. A lower bound says nothing can be faster; it never says something is achievable. A matching upper bound is a separate argument, and GATE questions that say "best possible" want both.

Misconception 7 — "Binary search is always better than linear search"

Belief. O(log n) beats O(n) on every input.

Minimal counterexample. n = 8, target at index 0. Linear search: 1 comparison. Binary search: 3.

The general fact. Asymptotics compare growth, not measurements. For one query on a small array, a scan can also avoid the cost of sorting entirely.

Misconception 8 — "Rotation makes it Θ(n)"

Belief. A rotated array is unsorted, so the halving argument fails and the best you can do is scan.

Minimal counterexample. [43, 47, 51, 3, 7, 11, 14] with target 7 is searched in three comparisons by the rotated variant. Every rotation of every array up to seven cells is checked in this page's model, with no wrong answer and the worst case still ⌊log₂ n⌋ + 1.

The general fact. What binary search needs is not global sortedness but a probe that eliminates a constant fraction. One sorted half per step is enough.
