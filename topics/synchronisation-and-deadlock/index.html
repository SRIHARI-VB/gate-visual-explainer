Topic and objective

TOPIC: Concurrency — the critical-section problem, the three requirements a solution must meet, semaphores and monitors, the classical coordination problems, and deadlock: its four conditions, the resource allocation graph, avoidance by Banker's algorithm, and detection. This is the clause "concurrency and synchronization. Deadlock" of Section 8 of the official GATE 2027 CS syllabus.

LEARNING OBJECTIVE: Given a concurrent program, decide what the shared state is and whether the statements are atomic; enumerate the possible outcomes; say which of mutual exclusion, progress and bounded waiting a proposed solution breaks, and produce the state that breaks it; trace a counting semaphore; decide whether a resource graph is deadlocked, and run the safety check on an allocation table.

I read this topic as two questions, one model. Synchronisation asks "can this interleaving happen, and what does it break"; deadlock asks "does a completion order exist". Both are answered by enumerating states, not by reciting algorithms — so the animation enumerates states and shows you the enumeration.

The five ideas to leave with

  1. A race condition is an interleaving problem. A statement that reads and writes is not atomic unless the question says it is, and that one sentence changes the whole answer set.
  2. Mutual exclusion, progress and bounded waiting are three different promises. Strict alternation proves safety is easy and liveness is not.
  3. A semaphore's value is permits left when non-negative, and minus the queue length when negative. Completed waits never exceed the initial value plus the signals issued.
  4. Never sleep while holding a lock the waker needs. The bounded buffer deadlocks exactly when the mutex is taken before the item or slot count.
  5. A cycle in a resource graph is a deadlock only when every resource type has one instance. With several instances, the test is whether a completion order exists — which is also the safety test.

Intuition: two clerks and one ledger

Two clerks share one ledger. Each has to record a payment: read the balance, add the amount, write the new balance. If clerk A reads 100, and before she writes, clerk B reads the same 100 and writes 120, then A writes 110 — and B's 20 rupees have vanished from the book. Nobody made an arithmetic mistake. The two readings simply overlapped.

The obvious fix is a rule: only one clerk may hold the ledger at a time. That is mutual exclusion. But now suppose the rule is "the ledger belongs to A on even minutes and to B on odd minutes" — if B has gone to lunch on an odd minute, A holds nothing and still cannot write. That is the progress failure: a rule that protects the data by giving a non-participant a veto.

Educational interpretation The analogy fixes two things: a critical section is a stretch of work on shared state, and a synchronisation rule is judged on both safety and liveness. It says nothing about how a machine implements the lock, which is the semaphore and monitor material below.

Formal definitions

  • Race condition — a situation where the result depends on the order in which concurrent accesses happen.
  • Critical section — a segment of a process that reads or writes state shared with another process.
  • Mutual exclusion — at most one process is inside its critical section at any time.
  • Progress — if no process is inside and some want in, the choice of who enters cannot be postponed indefinitely, and only the processes that want in take part in the choice.
  • Bounded waiting — after a process asks to enter, there is a bound on how many times others may enter before it does.
  • Semaphore — an integer with a queue, changed only by two atomic operations: wait (P, down) and signal (V, up).
  • Monitor — shared data plus procedures, with the language guaranteeing one process inside at a time; condition variables provide waiting.
  • Deadlock — a set of processes each waiting for an event only another member of the set can cause.
  • Safe state — a state from which some order of completion exists for every process.

The semaphore, symbol by symbol

wait(S): S = S − 1; if S < 0 then block "Decrease the count. If it has gone below zero, there was no permit, so sleep."

signal(S): S = S + 1; if S ≤ 0 then wake one "Increase the count. If it is still at or below zero, somebody was sleeping, so wake one of them."

So the value is the number of permits still available while it is non-negative, and minus the number of sleeping processes once it is negative. A binary semaphore, or mutex, is the case whose value is only ever 0 or 1.

What every answer depends on

  • Atomicity. If the question says each statement is atomic, a switch happens only between statements. If it does not, a switch inside a read-modify-write is legal.
  • Instances per resource type. One instance licenses the cycle test; several instances do not.
  • Memory model. Peterson's algorithm is correct under sequential consistency. Real hardware may reorder the two writes, which is why fences exist.
  • Who may wake whom. A blocked process can only be woken by a signal from a process that is running, so a lock held across a sleep can remove the only waker.

From one counter to a resource graph

The build-up so far is about time: which interleavings exist and what they break. Deadlock is the same question asked about resources. A process holds some resources and waits for others; if the waits form a cycle in which nobody can move, no interleaving exists that finishes everybody. The model is a directed graph, and the test is whether a completion order exists.

That is why the topic is one lesson rather than two: the semaphore material produces the deadlock (a consumer sleeping while holding a mutex), and the deadlock material is a state-enumeration question of exactly the kind the race material introduced.

The four Coffman conditions

Deadlock requires all four. They are necessary, not sufficient.

  • Mutual exclusion — at least one resource is held non-sharably.
  • Hold and wait — a process holds one resource while requesting another.
  • No preemption — a resource is released only voluntarily.
  • Circular wait — a closed chain of processes, each waiting for a resource the next one holds.

Three ways to handle deadlock

  • Prevention — make a condition impossible. Order the resource types to kill circular wait; request everything at once to kill hold and wait; allow preemption to kill the third. Cost: utilisation.
  • Avoidance — let the conditions hold, and refuse any request that would leave an unsafe state. Banker's algorithm is the standard instance, and it needs declared maximum needs.
  • Detection and recovery — let deadlock happen, find it by a cycle or a completion-order test, then kill or roll back a victim.

The words that decide the question

  • "In some order" — the answer must hold for every order, including the worst one.
  • "Always avoids" — a worst-case guarantee, which is what the bound n(K−1)+1 ≤ m encodes.
  • "Safe" — a completion order exists. It is not the same as "deadlock has occurred".
  • "One instance at a time" — requests are single, so the worst case is everyone holding one short of their maximum.

Worked examples, page 1 of 2 — the synchronisation half

Every number below is produced by the model in this lesson and re-checked on load. Where a step is a definition rather than a calculation, the step says so.

Example 1 — two increments, no protection

Counter starts at 0. Threads T1 and T2 each execute counter = counter + 1, which is read, add, write. Each statement is atomic.

1. The interleaving T1.read, T2.read, T1.write, T2.write gives: both registers hold 0, T1 writes 1, T2 writes 1. Final value 1. Justification: the second write overwrites the first.

2. The interleaving T1.read, T1.write, T2.read, T2.write gives 1 then 2. Final value 2.

3. Enumerating all six interleavings gives exactly the set {1, 2}. No other value is reachable.

Mathematical derivation Six schedules, two outcomes. A question asking "the number of distinct values" wants 2; one asking "the minimum" wants 1.

Example 2 — strict alternation, property by property

One shared variable turn, initially 0. Process i spins while turn != i, and sets turn = 1−i on exit.

1. Mutual exclusion. Entry requires turn to equal your own index, and the two indices differ, so both cannot be inside. Enumerating the reachable states finds no state with both in the critical section.

2. Progress fails. Take turn = 1, P1 in its remainder wanting nothing, P0 at its entry. The critical section is empty and P0 cannot enter.

3. Bounded waiting also fails. P0 may wait until P1 chooses to take a turn, and P1 may never do so.

Mathematical derivation The failure is a state, not a timing accident: no scheduling of P1 helps, because P1 is not requesting anything.

Example 3 — Peterson, counted rather than argued

Entry for process i: flag[i] = 1; turn = j; while (flag[j] && turn == j); and flag[i] = 0 on exit.

1. Treat every statement as atomic and a spin as a self-loop, and enumerate every reachable state from the initial state.

2. The enumeration reaches 34 distinct states, counting the all-finished one.

3. In none of them are both processes in the critical section, and in none of them is every process unable to move.

4. Bounded waiting holds because the loser of the tie waits only while the winner is inside.

Mathematical derivation An exhaustive enumeration is a proof for this model. It is not a proof for a machine that reorders writes.

Example 4 — a counting semaphore, traced

S starts at 5. Apply wait, wait, wait, signal, wait in that order.

1. After three waits: 5 → 4 → 3 → 2. Nobody blocked, because the value never went below zero.

2. One signal: 2 → 3.

3. One more wait: 3 → 2. Four waits completed, one signal issued, value 2.

4. Check the invariant: completed waits 4 ≤ 5 + 1 = 6. Consistent.

Mathematical derivation The value alone never tells you how many processes are inside; that is initial minus current, here 5 − 2 = 3.

Worked examples, page 2 of 2 — the deadlock half

These four are the shapes the paper actually uses: a permit count, a lock order, a safety table, and a resource bound.

Example 5 — the bounded buffer, both orders

Two slots. empty = 2, full = 0, mutex = 1.

Correct order. Producer: wait(empty) → 1, wait(mutex) → 0, insert, signal(full) → 1, signal(mutex) → 1. Consumer: wait(full) → 0, wait(mutex) → 0, remove, signal(empty), signal(mutex). No sleep holds a lock.

Swapped order. Consumer: wait(mutex) → 0, then wait(full) with full = 0 → −1, so it blocks holding the mutex.

Consequence. The producer reaches wait(mutex), finds 0, and blocks. The item the consumer waits for can never be produced.

Verified fact This is the code shape of GATE 2014 Set 2 Q31, where the consumer does semWait(s) then semWait(n); the paper's correct option is that deadlock occurs if the consumer acquires the mutex when the buffer is empty.

Example 6 — Banker's on a printed table

GATE 2018 Q39: resources E, F, G; available (3, 3, 0). Need is maximum minus allocation.

1. Need: P0 (3,3,0), P1 (1,0,2), P2 (0,3,0), P3 (3,4,1).

2. Work (3,3,0): P0 fits → work (4,3,1).

3. P2 fits → work (5,3,4). Then P1 fits → work (6,4,6). Then P3 fits.

4. Every process completes, so the state is safe. Sequence P0, P2, P1, P3.

Mathematical derivation The matrices are as printed in the paper; the verdict here is recomputed, and the paper's option is that the system is in a safe state.

Example 7 — the resource bound

n processes, m identical instances, each process needing at most K. Deadlock is impossible when n(K−1) + 1 ≤ m.

1. Worst case: every process holds K−1 and wants one more. Total held n(K−1).

2. If one instance is left over, some process gets its last instance, finishes, and returns everything.

3. GATE 2018 Q24: n = 3, m = 4 → 3(K−1) ≤ 3 → K ≤ 2.

4. Check K = 3: the split 2, 1, 1 uses all four instances and each process still wants one. Deadlock. So 2 is the largest safe K.

Verified fact GATE 2018 Q24, answer 2. The formula gives the same answer, and the counterexample at K = 3 is why the bound is tight rather than merely sufficient.

Example 8 — a cycle that is not a deadlock

R1 has two instances, R2 has one. P1 holds one instance of R1 and wants R2; P2 holds R2 and wants R1.

1. The graph has the cycle P1 → R2 → P2 → R1 → P1.

2. Work = (R1 1, R2 0). P2 needs R1 and it is available, so P2 runs to completion.

3. P2 returns R2: work = (R1 1, R2 1). P1 needs R2 and gets it.

4. Every process completes, so the state is not deadlocked although it has a cycle.

Mathematical derivation A cycle is necessary for deadlock and sufficient only when every resource type has one instance.

Boundaries, counterexamples and the condition each one violates

Each card names the smallest example that breaks a tempting rule, and the exact assumption the rule needed.

Counterexample: a cycle with no deadlock

R1 (two instances), R2 (one). P1 holds an R1 and wants R2; P2 holds R2 and wants R1. The cycle exists and nothing is stuck, because the free R1 instance lets P2 finish.

Condition violated by the tempting rule: "a cycle means deadlock" needs one instance per resource type. Drop that and the rule is false.

Counterexample: safe does not mean deadlock has happened

An unsafe state is one where no completion order is guaranteed. It may still complete, because processes may release resources earlier than their declared maximum. Safety is a worst-case guarantee, not a prediction.

Condition: the safety test assumes every process eventually requests its declared maximum. Without that assumption the test has no meaning.

Counterexample: two flags and no turn

With only flag[0] and flag[1], both processes can raise their flags, then both spin. Each waits for the other to lower a flag that will not be lowered until it enters. Deadlock.

Condition: Peterson needs the turn variable to break exactly this tie. Removing one variable removes liveness, not safety.

Counterexample: a signal with nobody waiting

A condition variable has no value. If signal is called when the queue is empty, it does nothing at all — the fact is not remembered. A later wait still blocks.

Condition: semaphores remember a signal (the value increments); condition variables do not. That is the difference between the two primitives.

Boundary: the negative semaphore value

From S = 0, two waits leave S = −2 with two processes blocked. That is not an error and not a contradiction: the magnitude is the queue length. A question that says "the semaphore is non-negative" is restricting the initial value, not the running value.

The one place the sign matters is the wake condition: signal wakes a sleeper exactly when the post-increment value is still ≤ 0.

Boundary: buffer of size one

With one slot, empty starts at 1 and full at 0. The correct order still works: the producer waits for the slot, then the mutex. The swapped order still deadlocks, and now on the very first item — a size-one buffer is the smallest demonstration.

With an unbounded buffer the producer never waits, so the swapped order happens not to deadlock — which is exactly why "it worked in my program" is not an argument.

Trap: the wait-for graph on several instances

Collapsing a resource type to "the process holding it" is only meaningful when there is one instance. With two instances a process may be waiting for the type, not for a particular holder, and the collapse can invent a cycle or hide one.

Use the allocation graph and the completion-order test instead, and reserve the wait-for graph for single-instance questions.

Trap: "it is a deadlock" when the property is progress

Strict alternation with turn pointing at an idle process is not a deadlock: no process holds the critical section, and no process holds a resource another needs. It is a progress violation, and the option distinguishing the two is usually present.

The diagnostic question: is anyone holding something? If nobody is, it is not a resource deadlock.

Six beliefs that cost marks

Each one names the belief, why it is tempting, the smallest counterexample, and the rule that replaces it.

1. "An assignment happens all at once"

Why it tempts: in a single-threaded program it is indistinguishable.

Minimal counterexample: two threads, one counter, one increment each: final value 1 is reachable.

Correct rule: read, modify and write are separate steps unless the question declares the statement atomic. Look for that sentence before anything else.

2. "Mutual exclusion is the whole job"

Why it tempts: it is the property the data needs.

Minimal counterexample: strict alternation — safe, and P0 can be blocked forever by an idle P1.

Correct rule: check three properties. Safety is necessary; progress and bounded waiting are what most exam solutions fail.

3. "A semaphore can never be negative"

Why it tempts: "counting" sounds like a count of things that exist.

Minimal counterexample: S = 0, two waits → S = −2, two blocked.

Correct rule: non-negative means permits left; negative means minus the queue length. The magnitude is information, not an error.

4. "The buffer code is symmetric, so order does not matter"

Why it tempts: both orders contain the same four calls.

Minimal counterexample: mutex first, empty buffer: the consumer sleeps holding the mutex and the producer cannot enter.

Correct rule: never block while holding a lock the waker needs. Wait on the counting semaphore first.

5. "A cycle in the graph proves deadlock"

Why it tempts: it is true in every textbook picture of two processes and two files.

Minimal counterexample: R1 with two instances, R2 with one: a cycle, a free instance, and a completion order.

Correct rule: cycle ⇒ deadlock only with one instance per type. With several, run the completion-order test.

6. "Safe means no deadlock, unsafe means deadlock"

Why it tempts: both words sound like verdicts.

Minimal counterexample: an unsafe state can still complete if processes finish below their declared maximum.

Correct rule: safe ⇒ no deadlock. Unsafe ⇒ the guarantee is gone, which is not the same as a deadlock.

One sentence that replaces all six

Every question here is "which states are reachable, and does a completion order exist" — asked about statements (synchronisation) or about resources (deadlock). Enumerate the states, then read the property off the enumeration.

The six question families, and the reasoning each demands

Families are ordered from the most frequent to the least. Frequency here is a reading of indexed archives, not an official count.

1. Possible values under interleaving

Shape: several threads run given code with a stated atomicity, and the question asks for the possible final values, the number of distinct values, or the maximum and minimum.

Reasoning: build the schedule that maximises and the one that minimises, then check each intermediate value is reachable. With a semaphore of value 2 or more, a thread can read a stale value and overwrite everything committed in between, which is what produces the extreme.

Wrong approach: simulating one interleaving and reporting it. The sequential answer is the best case and almost never the question.

2. Semaphore counting and blocking bounds

Shape: N waits and M signals in some order; find the largest initial value that still blocks, or how many processes can be inside at once.

Reasoning: completed waits ≤ initial + signals. Set that inequality to the blocking boundary and solve. Never trace orders.

Wrong approach: reading the final value only. The final value being zero is what makes an initial value safe, which is the complement of what "still blocks" asks.

3. Property verification on a proposed solution

Shape: given two flags, a turn, or a ticket, decide which of mutual exclusion, progress and bounded waiting hold.

Reasoning: for safety, argue about the entry condition; for progress, construct the state with an idle outsider; for bounded waiting, count how many times another process can enter first.

Wrong approach: judging by whether the code "looks like" Peterson. Many distractors are Peterson with one line changed, and the property that fails is precisely the line.

4. Deadlock in a lock or semaphore order

Shape: several processes acquire several locks in stated orders; does a deadlock-free order exist, or does this program deadlock?

Reasoning: draw the waits-for edges and look for a cycle, or apply a numbering: if every process requests in increasing order of a global numbering, no cycle can form.

Wrong approach: checking each process separately. Deadlock is a property of the set, and every process can be individually correct.

5. Single resource type, minimum instances

Shape: n processes, maximum K each, one instance requested at a time; find the smallest m that guarantees no deadlock, or the largest K.

Reasoning: n(K−1)+1 ≤ m. The worst case is everyone one short. Solve for the unknown.

Wrong approach: n·K ≤ m, which requires everyone to finish simultaneously and is far too strong.

6. Banker's safety check

Shape: an allocation table, a maximum table and an available vector; is the state safe, and what is the sequence?

Reasoning: need = max − alloc; scan for any process whose need fits work; add its allocation back; repeat. Any valid sequence is an answer unless the options differ.

Wrong approach: forgetting to add the allocation back, which stalls the scan early and turns a safe state into a reported deadlock.

The two sentences to carry into the exam

For synchronisation: enumerate the extreme interleavings and name the property that breaks. For deadlock: ask how many instances each type has, then either look for a cycle or look for a completion order.

NATMediumPYQ — GATE CSE 2016 Set 2, Q49

Consider a non-negative counting semaphore S. P(S) decrements S, V(S) increments S. During an execution, 20 P(S) operations and 12 V(S) operations are issued in some order. The largest initial value of S for which at least one P(S) operation will remain blocked is ______.

Answer: 7

Every V creates one permit and every completed P consumes one, so at most S₀ + 12 waits can ever complete. For all 20 to complete you need S₀ + 12 ≥ 20, that is S₀ ≥ 8. From S₀ = 7, at most 19 complete, so the 20th blocks whatever the order.

Check S₀ = 8: eight waits, twelve signals, twelve waits ends at value 0 with nothing blocked. So 7 is the largest value that still blocks, and 8 is the smallest that does not.

NATMediumPYQ — GATE CSE 2018, Q24

Consider a system with 3 processes that share 4 instances of the same resource type. Each process can request a maximum of K instances. Resource instances can be requested and released only one at a time. The largest value of K that will always avoid deadlock is ______.

Answer: 2

Worst case: each process holds K−1 and wants one more, so 3(K−1) are held. If one instance remains free, somebody finishes and the rest follow: 3(K−1)+1 ≤ 4 gives K ≤ 2.

K = 3 fails by the split 2, 1, 1: all four instances held, each process one short, nobody can proceed. So 2 is the largest safe K.

MCQMediumPYQ — GATE CSE 2014 Set 2, Q31

The producer does semWait(s); addToBuffer(); semSignal(s); semSignal(n); and the consumer does semWait(s); semWait(n); removeFromBuffer(); semSignal(s); consume();, with n = 0 and s = 1. Which one is TRUE?

(A) The producer will be able to add an item, but the consumer can never consume it.
(B) The consumer will remove no more than one item from the buffer.
(C) Deadlock occurs if the consumer succeeds in acquiring semaphore s when the buffer is empty.
(D) The starting value for n must be 1, not 0, for deadlock-free operation.

Answer: (C)

The consumer takes the mutex, then blocks on the item count while still holding the mutex. The producer cannot enter to add the item the consumer is waiting for, so nothing can move.

(A) and (B) describe a progress failure rather than this deadlock. (D) is the tempting repair: starting n at 1 admits one item that does not exist, so the consumer reads garbage. The real fix is the order of the two waits.

NATMediumPYQ — GATE CSE 2015 Set 1

P1 and P2 share a variable B, initially 2, and execute concurrently. P1 does C = B − 1; B = 2*C; and P2 does D = 2*B; B = D − 1;. Each statement is atomic. The number of distinct values B can take after execution is ______.

Numbered Q9 in one index and Q20 in the paper's own listing; the year and set are the same item.

Answer: 3

P1 then P2 gives 3; P2 then P1 gives 4; P1 reading before P2 runs and writing after gives 2. Enumerating all interleavings of the four statements yields exactly {2, 3, 4}.

The trap is answering 2 (the two sequential runs) or 4 (counting schedules instead of values). The question asks for distinct values, and three schedules collapse onto 3.

MSQMediumOriginal GATE-style

Two threads T1 and T2 each execute x = x + 1 once on a shared integer x that starts at 0. Each statement is atomic and a context switch may happen at any point. Which of the following are TRUE?

(A) The final value of x can be 1.   (B) The final value of x can be 2.   (C) The final value of x can be 0.   (D) The final value of x is always 2.

Answer: (A) and (B)

Both reads can precede both writes, giving 1; any other interleaving gives 2. There are six interleavings and exactly two outcomes.

(C) is impossible: no operation decrements x, so the value can never fall below 0. (D) is the belief that the statement is atomic at a coarser grain than it is.

MCQHardOriginal GATE-style

Two processes use one shared variable turn, initially 0. Process i spins while turn != i before its critical section, and sets turn = 1 − i after it. Which one of the following is TRUE?

(A) Mutual exclusion and progress hold; bounded waiting fails.
(B) Mutual exclusion holds; progress fails.
(C) Mutual exclusion fails.
(D) All three hold.

Answer: (B)

Entry needs turn to equal your own index, so both cannot be inside. With turn = 1, P1 in its remainder and P0 waiting, the critical section is empty and P0 still cannot enter: progress fails.

(A) misreads the failure: bounded waiting is also unbounded here, but the property that the standard counterexample is built for is progress. (C) is refuted by the one-line argument on turn. This is the GATE 2016 Set 2 Q48 construct with original options.

MCQMediumOriginal GATE-style

A resource allocation graph has two processes P1, P2 and two resource types R1, R2. R1 has two instances, R2 has one. P1 holds one instance of R1 and requests R2; P2 holds R2 and requests R1. Which one of the following is TRUE?

(A) The graph has no cycle and the system is deadlocked.
(B) The graph has a cycle and the system is deadlocked.
(C) The graph has a cycle and the system is not deadlocked.
(D) The graph has no cycle and the system is not deadlocked.

Answer: (C)

P1 → R2 → P2 → R1 → P1 is a cycle. But a second instance of R1 is free, so P2 gets it, completes, releases R2, and P1 then proceeds. A completion order exists.

(B) is the standard wrong answer: it applies the single-instance cycle test to a multi-instance graph. (A) and (D) misread the graph itself.

MCQHardPYQ table — GATE CSE 2018, Q39

Four processes over resources E, F, G. Allocation: P0 (1,0,1), P1 (1,1,2), P2 (1,0,3), P3 (2,0,0). Maximum: P0 (4,3,1), P1 (2,1,4), P2 (1,3,3), P3 (5,4,1). Available: (3,3,0). From the perspective of deadlock avoidance, which one is true?

(A) The system is in a safe state.
(B) Not safe, but safe if one more instance of E were available.
(C) Not safe, but safe if one more instance of F were available.
(D) Not safe, but safe if one more instance of G were available.

Answer: (A)

Need: P0 (3,3,0), P1 (1,0,2), P2 (0,3,0), P3 (3,4,1). Work (3,3,0) → P0 fits → (4,3,1) → P2 fits → (5,3,4) → P1 fits → (6,4,6) → P3 fits. Sequence P0, P2, P1, P3.

Every process completes, so the state is safe and the extra-instance options are all irrelevant. The matrices are as printed in the paper; the verdict is recomputed here.

Revision sheet

Definitions, the three requirements, the primitives, the deadlock tests and the traps, in the order a question uses them.

Definitions, one line each

  • Race condition — the result depends on the order of concurrent accesses.
  • Critical section — the part that touches shared state.
  • Mutual exclusion — at most one inside.
  • Progress — an idle outsider cannot block entry.
  • Bounded waiting — a bound on how many others enter first.
  • Semaphore — integer plus queue; wait decrements, signal increments.
  • Mutex — binary semaphore, value 0 or 1.
  • Monitor — data plus procedures, lock held by the language.
  • Condition variable — a queue with no value; signal with no waiter is lost.
  • Deadlock — a set of processes each waiting on another member.
  • Safe state — a completion order exists for every process.

Formulas and their licences

S = permits left (S ≥ 0); S = −(blocked) (S < 0) The magnitude is the queue length once the value is negative.

completed waits ≤ S₀ + signals Every signal creates one permit; nothing else does.

n(K − 1) + 1 ≤ m ⇒ no deadlock n processes, m identical instances, maximum K each, one at a time. Worst case: everyone one short.

need = max − allocation Banker's: then scan for any process whose need fits the work vector, and add its allocation back.

None of these four is universal. The first two assume the counting definition of a semaphore, the third assumes identical single-type resources and one-at-a-time requests, and the fourth assumes declared maximum needs.

Decision procedure

  1. What is shared, and are statements atomic?
  2. Value question → enumerate the extreme interleavings.
  3. Semaphore question → use the permit inequality, never trace.
  4. Liveness question → name the property, then build the state that breaks it.
  5. Deadlock question → how many instances per type? One: look for a cycle. Several: look for a completion order.
  6. Table question → need = max − alloc, then scan and add back.

The five traps

  1. Assuming atomicity the question did not grant.
  2. Reading a negative semaphore value as an error.
  3. Sleeping while holding the waker's lock.
  4. Using a cycle as a deadlock test with several instances.
  5. Reading safe as deadlock-free and unsafe as deadlocked.

Two sentences

Synchronisation: enumerate the extreme interleavings and name the property that breaks. Deadlock: count the instances per type, then either look for a cycle or look for a completion order.
