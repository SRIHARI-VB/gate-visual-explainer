Topic and objective

TOPIC: Lexical errors and error handling inside the lexer — where a scanner finds out that the input has no token at the current position, and the three things it can do next: delete to a token start, sync to a delimiter, or commit to the token it has begun.

LEARNING OBJECTIVE: Say what a token is and which two decisions the lexer makes. Read the 24-state automaton that decides where each token ends, and see why the run passes an accepting state instead of stopping at it. Name the only two ways a scan can fail — no move from the start state, or a run that can never finish — and give the reported position and the cause separately. Run panic mode and count characters deleted, not messages. Add the guard that makes it terminate. Tell a lexical error from a syntactic and a semantic one, using the phase test rather than the symptom. Count tokens under a printed token specification.

I read this topic as the first half of Section 7's word "lexical analysis": the neighbouring parsing lesson owns what a parser does after a well-formed token stream, and this one owns the character level and what happens when a character cannot become a token.

Prerequisites

  • Regular expressions and finite automata — a DFA, an accepting state, and the fact that a union of token patterns is an automaton. Everything here is one automaton run over a string.
  • Lexical analysis, parsing and syntax-directed translation — the compiler phases, the token stream, and FIRST and FOLLOW. This lesson adds the character level and the failures.
  • Error detection and recovery in parsers — the same question one level up. Useful for the contrast: a parser has a stack to pop and a lexer does not.
  • C fundamentals — only for reading the two quoted previous-year statements, which are C.

The five ideas, in one line each

  • A token is a class plus a lexeme. Every later phase sees only that, never characters.
  • Longest match, not first match. The run records an accepting state and keeps going.
  • Two failures only. No move from the start state, or a run that cannot reach an accepting state.
  • Recovery deletes characters. There is no stack; the two counts are characters deleted and errors reported.
  • The phase decides the label. A well-formed token in the wrong place is never a lexical error.

What the page computes, and how it is checked

The page builds a 24-state automaton (18 accepting states, 638 character moves) from a seven-class token specification, and runs it. A second, independently written matcher that never walks the table re-scans every string: the two agree on all 2,955 strings of length at most three and on all 13 corpus strings. A recursive-descent parser then classifies seven corpus strings by the phase that can see the fault. Three recovery rules are run and every deleted character is counted. 21 of 21 model checks pass, and the counter in the Animation tab shows the live count.

1. Intuition — the reader who does not know where the word ends

Imagine reading a line with no spaces at all, and being told that a word ends when the next letter could not continue it. You would read as far as you can and then stop, because stopping earlier would leave a letter that the next word cannot begin with. That is the whole of the lexer's second decision, and it is why 23mm is two words while x1 is one: a word may start with a letter and then hold digits, but a word may not start with a digit and then hold letters. Educational interpretation

Now imagine a character that no word may contain, in the middle of the line. The reader stops, and there is nothing to report except the character and where it sits. That is a lexical error, and it is worth noticing how little information it carries: no word, no class, no meaning. Everything the compiler says about a lexical error is a statement about one character.

The last piece is the one that surprises people. Some runs stop without ever reaching an end: an opening quotation mark is a promise that a closing one will arrive, and if it never does, the reader has read four characters and has nothing to show. Where does the message point? Not at the quotation mark — at the place the reader gave up. Keeping those two positions apart is the difference between fixing the program and deleting the wrong character.

2. Formal definitions

Token. A pair (class, lexeme), where the lexeme is the exact substring of the source that the class matched. Whitespace and comments are recognised and then skipped, so they are not tokens of the stream.

Longest match (maximal munch). At each position, take the longest prefix of the remaining input that is accepted by the token automaton. If two classes accept the same longest string, the class listed first wins.

Lexical error. A position at which no token can be formed: either the start state has no move on that character, or every run from the start state on that prefix reaches no accepting state.

Panic mode (lexer). Delete characters from the failing position until one is reached that can begin a token, then resume scanning there.

Progress guard. If a recovery pass deletes no character, delete the offending character itself. Without it the rule can return to the configuration it started from.

Delimiter sync. Delete characters up to but not including a chosen delimiter, usually ; or the end of the line, and resume at the delimiter.

3. Visual understanding — what the drawing has to show

An error is not visible in a picture of a token stream, because the stream is what failed to be produced. What exists at the moment of failure is a position in the input and a state of the run, so the animation draws those: the characters in a row, the position marked, and the state named.

The second thing the drawing must show is that the two failures look different. In the first, the run never leaves the start state, so there is no partial token to name. In the second, the run is several states away from the start and still has not accepted anything. A picture that marks only the position cannot tell those apart, and the message they deserve is different.

4. The four decisions, in the order a lexer makes them

  1. Start. Take the character at the current position. If the start state has no move on it, this is failure 1.
  2. Run. Follow transitions while they exist, remembering the last accepting state passed.
  3. End. Emit the longest accepted prefix as one token and move the position to its end. If no accepting state was passed, this is failure 2.
  4. Recover. On failure, delete to a character that can begin a token, or to a delimiter, with a guard. Then go back to step 1.

Step 3 is the whole of longest match, and it is one line of code: remember, do not stop. A scanner written to stop at the first accepting state looks tidier and reads == as two equals signs.

Worked examples — every number below is recomputed on this page

The language is stated once and used throughout: keywords if then else while print; identifier letter(letter|digit|_)*; number digit+; string literal in double quotes with \" as the only escape; operators == <= = < + - * / ( ) { } ;; comments /* ... */; whitespace skipped.

Example 1 — the counting question, word by word

String: x1 23mm 78 y 7z zz5 14A 8H AaYcD. Rules: id = letter(letter|digit)*, number = digit+.

  1. x1 — starts with a letter, digits may follow: 1 token.
  2. 23mm — digits, then a letter. A number cannot hold a letter, and an identifier cannot start with a digit: 2 tokens, 23 and mm.
  3. 78, y, zz5, AaYcD — one token each.
  4. 7z, 14A, 8H — two tokens each, by the same rule as step 2.
  5. Sum: 1+2+1+1+2+1+2+2+1 = 13.

Nine blank-separated words, thirteen tokens. The asymmetry between x1 and 23mm is the whole question.

Example 2 — one string, three scanners

Input a/*b*/c.

  1. Longest match: a, then at / the run accepts the slash, then reads * and enters the comment, then finds */ and accepts the whole comment, then c. Two live tokens.
  2. The same characters with spaces, a / * b / c: the star stands alone, no comment begins, six live tokens.
  3. A shortest-match scanner on the packed form: /, *, b, *, /, c — six tokens, and the comment is lost.

Same characters, different tokens, decided by one rule. This is why "what does the lexer produce" is a question about the automaton and not about the text.

Example 3 — a failure at the start, and a failure that cannot finish

Input x = 3 $ y; — the dollar admits no rule.

  1. Tokens x, =, 3 are emitted normally; the position reaches the space after the 3.
  2. Whitespace is skipped, the position reaches the dollar at character 7.
  3. The start state has no move on $, so the run never begins. There is no partial token and no class to name.

Input x = "abc followed by a newline — the literal opens and never closes.

  1. The quote opens the literal at character 5 and the run moves into the body.
  2. The body accepts any character except a quote, a backslash and a newline. The newline stops the run.
  3. No state on the way accepted anything, so nothing can be emitted: the failure is reported at character 9, four characters after the cause.

Two failures, two messages. The first names a character that no token can contain; the second names a literal that was never closed.

Example 4 — panic mode, then the guard

Panic mode on x = @@@ 3;.

  1. Failure at the first @. Delete characters until one can begin a token: three @ characters go, the space stays because whitespace can begin a token.
  2. Resume: x, =, 3, ;. One message, three characters deleted.

The same rule on x = "abc and a newline.

  1. Failure at the newline, at character 9. A newline can begin whitespace, so the rule deletes zero characters.
  2. Nothing changed, so the same failure returns: the rule loops. The guard deletes the offending character itself.
  3. One deletion, one message, and the remaining tokens are x, =, y, =, 2, ; — the literal has vanished, and the parser rejects the result.

Recovery keeps the scan going. It does not keep the program.

Example 5 — the same characters, three phases

Take 3 + 4 ;, x = 3 y; and x = 3 $ y;.

  1. x = 3 $ y; — the dollar fails the lexical test, so the lexer reports it and the parser never runs.
  2. 3 + 4 ; — every character forms a token. The parser rejects token 1, because a statement cannot start with a number.
  3. x = 3 y; — every character forms a token. The parser rejects token 4, expecting ; after the expression.

One lexical, two syntactic, and the labels come from which test failed — not from which one "looks worse".

Counterexample 1 — 12ab is not a lexical error

A learner who has just met "an identifier cannot start with a digit" often expects 12ab to be a lexical error. It is not. The number 12 is accepted, and ab begins a new token. The page scans x = 12ab; as five tokens: x, =, 12, ab, ;.

Whether that is then an error depends on the grammar, and on the grammar it usually is one — a syntactic error, found later.

Counterexample 2 — an unterminated comment raises no error

Under pure longest match, /* unterminated gives three tokens — /, *, unterminated — and no error at all, because the slash is an accepting state to fall back on. A lexer that reports the missing */ is doing something the automaton does not: committing to the comment when it sees the pair.

An unterminated string is different: a lone quote has no shorter token to fall back on, so the failure is unavoidable and is reported.

Counterexample 3 — a misspelt keyword is not a lexical error

whiel is a perfectly good identifier. The lexer has no rule that says keywords must be spelt correctly, so it emits an identifier and the parser complains later — if it complains at all.

The same is true of ifx: longest match takes the whole word as one identifier, because the identifier match is longer than the keyword match.

Boundary 1 — the empty string literal

"" is one token. The automaton leaves the start state on the opening quote and reaches the accepting state on the closing one, with nothing in between. A hand-built automaton that forgets the direct move from the opening quote to the closing quote will report a lexical error on a valid program — this page's own first draft did, and the cross-check against the second matcher caught it.

The check is the reason to write the second matcher at all.

Boundary 2 — a newline cannot appear inside a literal

In this language, and in C, a newline ends a string literal without closing it. That single rule is what turns "forgot a quote" into a failure at the end of the line rather than at the end of the file, and it is why the reported position is four characters away from the cause on x = "abc.

Remove the rule and the literal swallows the rest of the file, and the first message points at the end of the input instead.

Boundary 3 — the guard fires once, not repeatedly

After the guard deletes the newline, the scan resumes on the next line and finds ordinary tokens, so the loop ends. If the next line were also malformed the guard would fire again, but the count is per pass, not per character.

A rule that fires the guard on every pass without consuming anything is still broken; the guard must delete a character, and deleting one character always moves the position forward.

The one edge case worth memorising

Two positions, always: where the message points and where the cause sits. On x = "abc and a newline they are characters 9 and 5. Every lexical error message in every compiler is a claim about the first, and a learner who repairs the first without looking at the second deletes the wrong character.

1. "A lexical error means the program is wrong at that character."

Why it tempts. The message points at one character, so it reads like a verdict on that character.

What is true. It is a verdict on the character's form: no token can be formed there. Whether the program is wrong is decided by later phases, and often the repaired program still fails.

Minimal case. x = 3 $ y; is reported at the dollar; deleting the dollar leaves x = 3 y;, which the parser rejects.

2. "The lexer stops at the first accepting state."

Why it tempts. It is the simplest way to write the loop, and it is correct for every token class that has exactly one state.

What is true. The lexer remembers the last accepting state and keeps going while a longer token is possible. On this page's 13-string corpus, the two rules disagree on 6 strings.

Minimal case. x == 3; would become five tokens instead of four, and ifx = 1; would become six instead of four.

3. "A well-formed token in the wrong place is a lexical error."

Why it tempts. The eye sees something wrong at a position, and the lexer is the phase that looks at positions.

What is true. The lexer asks only whether a token can be formed. Order, declaration and type are three other questions, answered by three other phases.

Minimal case. 3 + 4 ; — every token is well formed, and the error is syntactic, at token 1.

4. "The position in the message is where the mistake is."

Why it tempts. A message that says "character 9" looks like a statement about character 9.

What is true. The position is where the run gave up. For a literal that never closes, that is the far end of what the literal consumed.

Minimal case. x = "abc and a newline: reported at 9, opened at 5, four characters apart.

5. "An unterminated comment is reported by the automaton."

Why it tempts. It is the same shape as an unterminated string, and the string is reported.

What is true. The slash is an accepting state, so longest match falls back to it: three tokens and no error. The message a real compiler prints comes from the scanner driver's decision to commit to the comment.

Minimal case. /* unterminated gives /, *, unterminated.

6. "Panic mode in a lexer pops a stack like a parser."

Why it tempts. The name and the four strategies are the same as the parser's, and the parser lesson comes first.

What is true. A lexer has no stack. Recovery can change one thing: the position in the input. So the counts are characters deleted and errors reported, not states popped and tokens discarded.

Minimal case. x = @@@ 3; — three characters deleted, one message, nothing popped.

What the exam actually asks

Three question shapes cover almost every item on this topic. Learn the shapes, and each one becomes a procedure you can run on the paper in front of you. None of them needs a remembered example, and none of them is answered by knowing that "the lexer is the first phase".

Shape 1 — count the tokens under printed rules

The question prints the token definitions and a string, and asks for an integer. The reasoning it demands: apply longest match word by word, and apply the start condition of each rule.

The wrong approach. Counting blank-separated words. On the GATE CSE 2026 Set 2 string that gives 9 against the correct 13.

The procedure. For each word: take the longest prefix that matches some rule, write the rule down, and continue at the next character. Add the counts.

Shape 2 — classify the error by phase

The question gives statements and asks which has a lexical, syntactic or semantic error. The reasoning it demands: apply the three tests in order, and stop at the first that fails.

The wrong approach. Deciding by how bad the line looks. A missing quote looks like a syntax problem to most readers, and it is the lexical one.

The procedure. Can every character be part of a token? If not, lexical. May the tokens appear in this order? If not, syntactic. Do the types and names obey? If not, semantic.

Shape 3 — trace the scanner, or the recovery

The question gives a short input and asks what the lexer emits, or how many characters a stated recovery deletes. The reasoning it demands: run the automaton, do not pattern-match.

The wrong approach. Guessing that a malformed run is deleted to the end of the line. The rule stops at the first character that can begin a token.

The procedure. Write the states in order, mark the accepting ones, and mark the last one passed. Then apply the recovery rule literally and count.

Two sentences worth keeping

"A lexical error is a position where no token can be formed" answers every classification item. "Longest match, remembering the last accepting state" answers every counting item.

Neither sentence mentions a compiler phase, and that is why they work: they are statements about characters and states, which is what the questions are about.

NATGATE CSE 2026 Set 2, Question 35

A lexical analyzer uses these token definitions: letter → [A-Za-z], digit → [0-9], id → letter (letter | digit)*, number → digit+, ws → (blank | tab | newline)+. For the string x1 23mm 78 y 7z zz5 14A 8H AaYcD, how many tokens (excluding whitespace) are produced?

Answer: 13

Why 13. Apply longest match per word. x1 is one identifier. 23mm is two tokens: 23 cannot extend into letters, and mm cannot begin with a digit. The same split applies to 7z, 14A and 8H. 78, y, zz5 and AaYcD are one each. The page's own scanner, run with exactly these rules, produces the same thirteen and the same split.

Why 9 is wrong. Nine is the number of blank-separated words. A word is not a unit of the token stream, and the question asks for tokens.

The distinction being tested. The identifier rule begins with a letter, so letters may follow digits inside one token but digits may not be followed by letters inside one token. The two directions are not symmetric.

MSQGATE CSE 2026 Set 1, Question 27

Consider the C statements S1: char *str1 = "Hello; S2: char *str2 = "Hello;"; S3: int *str3 = "Hello";. Which of the following is/are correct?

(A) S1 and S2 have syntactic errors
(B) S2 has a lexical error and S3 has a syntactic error
(C) S1 has a lexical error and S3 has a semantic error
(D) S1 has a syntactic error and S3 has a semantic error

Answer: C

Why S1 is lexical. The string literal opens and never closes on that line, so the lexer cannot form a token: no class accepts what is there. This page's scanner reports it at the position where the run gave up.

Why S2 is fine. The literal closes before the second quote, and the semicolon inside the quotes is a character of the literal, not a statement terminator. Nothing is wrong with it.

Why S3 is semantic. It is lexically clean and syntactically a well-formed declaration; the fault is that a pointer to char is assigned to a pointer to int. That is a type rule, checked by semantic analysis.

Why A, B and D fail. All three either call S1 syntactic or call S2 erroneous. Both mistakes come from judging by appearance: an unclosed quote looks like punctuation trouble, and a semicolon inside quotes looks like a missing terminator.

MCQOriginal practice question

Which one of the following is a lexical error in this lesson's language?

(A) a missing semicolon at the end of a statement
(B) the character @ outside any literal
(C) an assignment of a string literal to an integer pointer
(D) an undeclared identifier

Answer: B

Why B. No rule admits @, so the start state has no move on it and no token can be formed. That is the definition of a lexical error, and the page reports it at that character's position.

Why A is wrong. Every character of a statement without a semicolon forms a token. The parser is the phase that misses it.

Why C is wrong. Type rules are semantic analysis, and this page's parser accepts S3-shaped code lexically and syntactically.

Why D is wrong. An undeclared name is still a well-formed identifier token; the symbol table decides the rest.

NATOriginal practice question

Under this lesson's token rules, how many tokens (excluding whitespace) does x == 3; produce?

Answer: 4

x, ==, 3, ;. The == is one token because longest match continues past the accepting state for = and reaches the state for ==.

Why not 5. Five is what a shortest-match lexer produces: two single equals signs. The page scans both ways and reports the disagreement.

The trap. Reading == as two tokens because they are two characters. A token is a lexeme, and its length is not fixed.

NATOriginal practice question

A lexer stops at the first accepting state instead of using longest match. Under this lesson's rules, how many tokens (excluding whitespace) does it produce for ifx = 1;?

Answer: 6

It reads i, f, x, =, 1, ;. The first character i already matches the identifier rule, so it stops there and never reaches the keyword if or the identifier ifx.

Why not 4. Four is the correct count under longest match: ifx, =, 1, ;. Longest match gives one identifier, and the keyword table is consulted on the whole lexeme, which does not match if.

The distinction. Longest match decides the extent; the keyword table decides the class. Confusing the two produces both of the wrong answers above.

MCQOriginal practice question

Under pure longest match, what does a lexer produce for /* unterminated (with no closing */)?

(A) a lexical error at the slash
(B) a lexical error at the end of the input
(C) three tokens: /, *, unterminated, and no error
(D) one comment token that runs to the end of the input

Answer: C

The slash is an accepting state, so when the comment never closes, longest match falls back to the last accepting state it passed — the slash. The next pass reads the star, then the word as an identifier.

Why A and B are wrong. Both assume the failure is reported. Under pure longest match it is not: there is always a shorter accepted prefix to fall back on.

Why D is wrong. A comment token is only produced by an accepting state, and that state is reached only when the closing pair arrives.

What a real compiler does. The scanner driver commits to the comment on seeing the pair and reports the missing terminator at the end of the input. That is a decision outside the automaton, and it is worth saying so rather than attributing it to the table.

NATOriginal practice question

Panic mode deletes characters until one is reached that can begin a token. For x = @@@ 3;, how many characters are deleted?

Answer: 3

The failure is at the first @. The next two @ characters cannot begin a token either, so all three go. The space can begin whitespace, so the deletion stops there and scanning resumes.

Why not 1. The rule does not stop at the first character after the failure; it stops at the first character that can begin a token.

The count that is separate. One message is printed for those three deletions. Characters deleted and errors reported are different numbers, and the question asks for the first.

MSQOriginal practice question

Which of the following statements about a lexer's recovery are TRUE? Select all that apply.

  1. Panic mode in a lexer has no stack to pop.
  2. A recovery rule must eventually consume input, or it can return to the same configuration.
  3. Syncing to a semicolon keeps the semicolon so the token stream keeps its shape.
  4. After a successful recovery, the token stream is guaranteed to be the one the programmer intended.

Answer: A, B and C

A is why the counts are characters deleted and errors reported. B is the guard, and the page shows the rule deleting zero characters at a newline and looping without it. C is why the delimiter is skipped over, not through: on x = @ y ; z = 1; four characters go and the semicolon stays.

D is false. The guarded run on an unterminated literal leaves x = y = 2 ;, which the parser rejects. Recovery buys the compiler a way to keep reading, not a correct program.

The distinction being tested. "The scan continues" against "the program is valid". Only the first is promised by any recovery rule.

Definitions, in the words that earn the mark

  • Token: a class plus the exact text matched (the lexeme).
  • Longest match: the longest prefix accepted by the token automaton; ties broken by the order the rules are written.
  • Lexical error: a position where no token can be formed.
  • Panic mode (lexer): delete to the first character that can begin a token.
  • Guard: if a pass deletes nothing, delete the offending character.
  • Delimiter sync: delete up to, not including, ; or the end of the line.

The numbers on this page

  • 24 states, 18 accepting, 176 transitions.
  • 2,955 strings of length ≤ 3 checked against a second matcher: all agree.
  • 13 corpus strings; longest and shortest match disagree on 6.
  • 5 keywords as automaton paths: 21 extra states.
  • GATE CSE 2026 Set 2: 9 words, 13 tokens.
  • Unterminated literal: opened at 5, reported at 9.
  • Panic mode: 1 deletion, then 3 deletions; the guard fires once.

The procedure, in five lines

  1. Scan with longest match, remembering the last accepting state.
  2. At failure, name the character and the position.
  3. Decide the kind: no move at all, or a run that cannot finish.
  4. Recover with a guard, or sync to a delimiter.
  5. Report, resume, and keep the two counts apart.

Traps, one line each

  • Words are not tokens: 9 against 13.
  • A well-formed token in the wrong place is syntactic, not lexical.
  • The reported position is where the run gave up, not where the cause is.
  • An unterminated comment raises no error under pure longest match.
  • A misspelt keyword is an identifier.
  • Recovery does not make the program valid.

The single sentence to carry into the exam

A lexer makes two decisions per position — where a token starts and where it ends — and its only failure is a position where no token can be formed; everything else it does is a choice about where to resume.
