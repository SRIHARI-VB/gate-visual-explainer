Topic and objective

TOPIC: The symbol table — the dictionary a compiler keeps of every declared name and its attributes — the three structures that implement it (linear list, binary search tree, hash table with chaining), and the way nested scopes are handled with a stack of tables.

LEARNING OBJECTIVE: Given a small program and one of the three structures, say how many comparisons a name costs, how many entries the table holds, and which declaration a use of a name resolves to — and say which of those three questions the structure does not answer. State the cost of an insert, a lookup and a scope exit in each organisation, with the assumption each cost needs.

I read this topic as the one structure the compiler's phases share that no lesson in this repository yet owns. Lexical analysis and parsing names the symbol table once, Type checking names it once, and Lexer recovery names it once — each as a thing that exists, never as a thing that is built. Its structure, its cost and its handling of scope are what a question actually asks.

The five ideas this page is built on

1. A symbol table is a dictionary, not a list of code. Keys are names; values are attributes — type, scope, storage class, address, arity. Nothing on the page is about the program's data at run time.

2. The structure decides the cost, and every cost has an assumption. Linear list: a scan. Search tree: the height, which insertion order controls. Hash table: the chain length, which the hash function controls. A cost quoted without its assumption is not a fact.

3. Scope is a stack, not a filter. Entering a block pushes a table, leaving it pops one, and a lookup walks outward until the first match. The first match is what makes shadowing work.

4. One entry per declaration, not one per name. A name declared twice in nested blocks owns two entries, and the inner one is what a use sees.

5. The table is compile-time; the activation record is run-time. The table records what the compiler knows about a name; the activation record holds what the running program stores. Confusing them is the most expensive error on this topic.

1. Intuition — the hospital's patient register

A hospital keeps one register at the front desk. Every patient who is admitted gets a line: a name, a ward, a bed, a consultant. When a nurse asks "where is Meera?", the desk does not search the building; it searches the register. The register is not the patient. It is the record of what the hospital decided about the patient. Educational interpretation

Two details of the register carry the whole lesson. First, the desk needs the answer fast, so the register is organised — alphabetical cards, or drawers by first letter — and the organisation is chosen for the question, not for the admission order. Second, a patient can be admitted twice, once to each of two wards, and the name on both lines is the same name; the desk resolves "Meera" to the line that is current, and the older line is still there. That is scope, and that is shadowing.

2. Formal definitions

Symbol table. A data structure mapping each identifier of the source program to a record of its attributes. The identifier is the key; the record is the value. Its two core operations are insert (add a binding) and lookup (retrieve the binding for a name). Verified fact

Entry (record). One line of the table: the name, plus the attributes the compiler has established — type, scope, storage class, offset or address, for a function its parameter types and return type.

Binding. The association between a name and an entry. A name declared in two blocks has two bindings.

Scope. The region of the source text in which a binding is the one a use of the name resolves to.

Shadowing. A declaration in an inner scope hiding a binding of the same name in an outer scope, for the length of the inner scope.

Occupation density (load factor). The number of entries divided by the number of buckets in the hash table. At 8 entries in 11 buckets it is 8/11, about 0.73.

3. Who touches the table, and when

Lexer. Produces the identifier tokens. In the usual arrangement the table itself is created here, and an identifier is entered when it is first met. Verified fact

Parser. Adds entries for declarations it recognises, and asks whether a name used has been declared.

Semantic analysis and type checking. Reads and writes the attributes: the type of an identifier, whether a call's arguments match the parameter types.

Intermediate code and optimisation. Reads types and storage to choose instructions and to decide whether two names can be the same object.

Verified fact Because every phase reads it, a statement that the table is "not needed after parsing" is false — that is exactly the shape of the 2025 statement-selection item noted on the Overview tab.

4. Visual understanding — what the drawing has to show

Three things are invisible in prose and decide every question.

The cost is a count of comparisons. "Linear list" and "search tree" are not two words for the same slowness; on eight names the first costs 28 comparisons to build and the second costs 13 when the insertion order is good and 28 when it is bad. The animation counts them, name by name.

Scope is a stack with a direction. A lookup starts at the innermost table and moves outward. Drawing the stack vertically, with the inner table on top and an arrow walking up, is what makes "the first match wins" a picture instead of a rule.

5. Boundaries — when the picture applies

One table per scope, or one table with duplicates. Both arrangements are used; they differ in what a lookup costs and what a scope exit costs. The page teaches both and compares them.

The attributes are the language's, not the table's. What must be stored is decided by the language: a language without static types needs fewer attributes at compile time.

Names can live in separate namespaces. C keeps several: ordinary identifiers, tags, labels, members. A question about "how many entries" is only well posed once the namespace is fixed.

6. Edge cases that decide marks

A hash table can put every name in one bucket. Then lookup degrades to the linear list, and the expected-O(1) claim is worth nothing.

A search tree built from sorted input is a linked list. Height n − 1, and the cost matches the linear list exactly.

Re-declaring the same name in the same scope is an error the insert finds by scanning; in a hash table the scan is the chain, in a list it is the whole table.

The function's own name does not go in the function's own table. It goes in the enclosing table, so that the enclosing scope can call it.

9. Consolidation

Draw the structure before quoting a cost. A linear list scans, so building it costs a triangle of comparisons. A search tree costs its height, so say what the insertion order was. A hash table costs the chain, so say what the hash function and the bucket count were. And when a program has nested blocks, draw the stack and walk outward: the first match is the binding, and the second match is only reachable after the first has been popped.

Example 1 — the linear list, counted

main total count rate code limit index sum

Eight names, appended in the order they appear. Inserting the first scans nothing; the second scans one; the eighth scans seven.

Mathematical derivation The total is 0 + 1 + 2 + 3 + 4 + 5 + 6 + 7 = 28, which is 8 × 7 / 2. In general n names cost n(n − 1)/2 comparisons, so building the table is quadratic in the number of names.

Example 2 — the same eight names in a search tree, twice

Alphabetical insertion. code, count, index, limit, main, rate, sum, total. Each new name is larger than all before it, so it hangs off the right of the previous one: a chain of depth seven.

Median-first insertion. main, index, count, code, limit, sum, rate, total. The middle name lands at the root and the tree stays shallow: height three.

Mathematical derivation The chain costs 28 comparisons — exactly the linear list — and the shallow tree costs 13. Same names, same structure, half the work, decided by the insertion order alone.

Example 3 — a hash table of eleven buckets

Hash the name by adding its character codes and taking the remainder modulo 11.

main → 421 mod 11 = 3
total → 548 mod 11 = 9
count → 553 mod 11 = 3
rate → 428 mod 11 = 10

All eight names land in buckets 0, 3, 4, 8, 9 and 10. Six buckets are used, two of them twice, so the longest chain is 2 and the occupation density is 8/11. A lookup of main probes bucket 3 and compares against two entries at most.

Example 4 — the counterexample: a hash table that is a list

Suppose the hash function returns 0 for every name — a bad function, or a table with one bucket.

Then all eight entries sit in one chain, and a lookup of the last-inserted name compares against all eight.

What this breaks. The claim "a symbol table is O(1) per lookup" is about the expected chain length under a hash function that spreads keys. With one bucket the expected cost is the linear list's, and no amount of chaining recovers it. That is why the hash function and the bucket count belong in the answer, not in a footnote.

Example 5 — walking the scope stack

int total; /* global */
int main(void) {
  int count; /* main */
  float rate; /* main */
  { int count; /* inner */
    char code; /* inner */
    count = 0; }
  rate = 1.5; }

Inside the inner block, count resolves to the inner declaration at the first probe, and total resolves to the global one after three probes. Six entries exist across the three tables, and the inner count hides the outer one for exactly the length of the block.

One program, end to end

The program above declares six things and mentions five distinct names. The global table holds total and main. main's table holds count and rate, and main itself is not among them — a function's name lives in the scope that calls it. The inner table holds a second count and code. When the closing brace of the inner block is reached, two entries are popped and the outer count becomes visible again, with no change to its record. Every number in that paragraph is produced by the model on the Animation tab and re-derived by a second route.

A tree built from sorted input is a linked list

Insert names in alphabetical order and every node has exactly one child, on the same side. Height n − 1, and the search cost is the linear list's.

The condition that fails. A search tree is fast only when it is balanced. Nothing in the plain insertion algorithm balances it; that is what AVL and red-black trees add, and why a compiler that uses a tree usually uses a balanced one.

All keys in one bucket

A hash function that is constant, or a table with one bucket, degrades chaining to a single list of length n.

The occupation density is then n/1 = n, and every lookup compares against every entry. The expected-cost claim is a claim about the function, not about the word "hash".

Re-declaration in the same scope

Inserting a name that is already in the current table is an error, and finding it is what the insert's scan is for: in a list, the whole table; in a hash table, one chain; in a tree, one root-to-leaf path.

This is also why an unsorted linear list cannot skip the scan: the duplicate test needs it even though the append itself is free.

A name used before it is declared

Lookup walks every table outward and finds nothing. That is an undeclared identifier, and the error is reported at the use, not at the end of the block.

It is also why a procedure cannot call one declared later in the same scope without a prototype: at the moment the call is compiled, the later name is not in the table yet.

Shadowing, and what "visible" counts

At the deepest point of the example program, six entries are live, but only five names are reachable: the inner count is found first, so the outer count cannot be named at all from inside the block.

The distinction. "How many entries does the table hold" and "how many names can this statement see" are two different questions with two different answers: 6 and 5.

Two things that are not the table

A literal table holds constants; a label table holds jump targets; a reserved-word table holds keywords. They are separate structures with separate jobs, and a keyword is usually not entered as a user name at all.

The distinction. A question that asks how many entries the symbol table holds is asking about declared names, not about every string the lexer saw.

“The symbol table is a lexer data structure”

Why it tempts. The lexer is where the table is created, and where an identifier is first entered.

Correct rule. It is created there and used by every phase after it: parsing, semantic analysis, intermediate code, optimisation. Verified fact

Repair. Say "created in lexical analysis, shared by all phases" and both halves are safe.

“A hash-based symbol table is O(1)”

Why it tempts. The textbook figure of a bucket array with short chains.

Correct rule. The expected cost is O(1) when the hash function spreads the keys and the load factor stays bounded. The worst case is O(n), and one bucket reaches it.

Repair. Quote the expected cost with its two assumptions, and name the worst case.

“One entry per name”

Why it tempts. A name looks like one thing in the source text.

Correct rule. One entry per declaration. The example program has five distinct names and six entries, because count is declared twice.

Repair. Count the declarations, not the spellings, and count each block's table separately.

“The function's name goes in the function's own table”

Why it tempts. The name is written in the function's header, so it feels local to it.

Correct rule. The name goes in the enclosing table, so that the enclosing scope can call it. The parameters go in the new table, because only the body uses them. Verified fact

Repair. Ask who needs to name it. Callers need it, so it belongs where callers look.

“O(1) lookup means the scope stack is free”

Why it tempts. Each table is a hash table, so each probe is constant.

Correct rule. A lookup may probe one table per enclosing scope, so the cost is O(d) for nesting depth d. Each probe is O(1); the walk is not. Verified fact

Repair. Distinguish the cost of a probe from the number of probes.

The pair most often confused

Symbol table against activation record. The symbol table is built at compile time and holds what the compiler knows: a name's type, its scope, its offset. The activation record is built at run time, on a call, and holds the actual values of that call's locals and parameters.

One is a table of declarations that exists while the compiler runs. The other is a block of memory that exists while the program runs. A question about the address of a variable in a recursive call is about the activation record; a question about how many entries a program creates is about the symbol table.

Shape 1 — which statement is false

Four statements about the table, one of them wrong. The reasoning is a check of each statement against the phase list.

Procedure. For each statement, ask which phases it implies. "Created during lexical analysis" — true. "Used only up to parsing" — false. "Can be implemented as a tree" — true. "Tracks scope" — true.

Trap. A statement that is true of one implementation read as true of every one. "Implemented as a hash table" is a common choice, not a requirement.

Shape 2 — how many entries

A program with nested blocks, and a question about the number of entries, or the entries live at a named line.

Procedure. One table per block. One entry per declaration, including a repeated name in a new block. A function's name goes in the enclosing table. Parameters go in the new table.

Trap. Counting distinct spellings. The example program answers 6, not 5.

Shape 3 — the cost comparison

A question about which organisation is fastest, or how many comparisons a build takes.

Procedure. Name the structure. Name the quantity that decides its cost — the count of prior entries, the height, or the chain length. Compute that quantity.

Trap. Comparing a worst case with a best case. A degenerate tree is a linear list, and a sorted insertion order produces exactly that.

Shortcuts, and the assumption each one needs

"n(n−1)/2 comparisons to build a list" needs every insert to scan all earlier entries — true for the duplicate check, false if the table is known to be duplicate-free.

"A tree costs log n" needs the tree to be balanced. Without that, it costs the height, which can be n − 1.

"A hash lookup is one comparison" needs a perfect hash function. Otherwise it is one comparison per entry in the chain.

MCQOriginal practice question

Which ONE of the following statements about a compiler's symbol table is FALSE?

(A) It is created during lexical analysis.
(B) It is consulted by the code generator.
(C) It is no longer needed once parsing is complete.
(D) It can be implemented as a binary search tree.

Answer: C

The table carries attributes that later phases read: types for semantic analysis, storage and offsets for code generation, and scope information for optimisation. Nothing about parsing makes it disposable.

Why A is right. The lexer is where identifiers are first met, and the table is normally created there.

Why B is right. Choosing an instruction and an address for a variable needs the entry.

Why D is right. A search tree is one of the three classic organisations.

The distinction being tested. "Where the table is created" and "where it stops being used" are different facts.

NATOriginal practice question

Names are appended to an unsorted linear list in the order they appear. Each insert scans every earlier entry to check for a duplicate before appending.

How many comparisons does building the table of 8 names take in total?

Answer: 28

The first insert scans 0 entries, the second scans 1, and the eighth scans 7. The sum is 0 + 1 + 2 + 3 + 4 + 5 + 6 + 7 = 28, which is n(n − 1)/2 for n = 8.

The trap. Answering 8, which is the number of entries, or 36, which is n²/2 without the subtraction. The triangle is the count, not the square.

The assumption. The duplicate check is why each insert scans. An insert that skipped it would cost nothing and the answer would be 0.

MCQOriginal practice question

Eight names are inserted into an initially empty binary search tree in alphabetical order. What is the height of the resulting tree, counting the root as height 0?

(A) 2   (B) 3   (C) 7   (D) 8

Answer: C

Each name is larger than every name already present, so each becomes the right child of the previous one. The result is a chain of eight nodes, which has height 7.

Why B is wrong. 3 is the height of the balanced tree built from a median-first order — a different insertion sequence.

Why D is wrong. 8 is the number of nodes, not the height. A tree of height 7 has 8 nodes.

The counterexample in this set. A search tree is not automatically logarithmic. This one is a linked list with extra pointers.

NATOriginal practice question

A hash table has 11 buckets and uses separate chaining. Eight names are inserted, and they hash to buckets 0, 3, 3, 4, 4, 8, 9 and 10.

What is the length of the longest chain?

Answer: 2

Bucket 3 holds two entries and bucket 4 holds two entries; the rest hold one each. Six buckets are occupied and the chain lengths sum to 8, which is the entry count.

The trap. Answering 3, the number of collisions in some other counting, or 8/11 rounded. A chain length is a count of entries, so it is a whole number.

The check that catches errors. Chain lengths must add up to the number of entries. Six buckets with lengths 1, 2, 2, 1, 1, 1 sum to 8.

MCQOriginal practice question

Consider

int total;
int main(void) {
  int count; float rate;
  { int count; char code; count = 0; }
  rate = 1.5;
}

How many symbol table entries does this program create in total, across all scopes?

(A) 4   (B) 5   (C) 6   (D) 7

Answer: C

The global table holds total and main. main's own table holds count and rate. The inner table holds a second count and code. That is 2 + 2 + 2 = 6 entries.

Why B is wrong. 5 is the number of distinct spellings — total, main, count, rate, code — and the two count declarations share one spelling. The table counts declarations.

Why A is wrong. 4 forgets both that the two count declarations are separate entries and that main needs one.

Why D is wrong. 7 would count main twice, once in each table. It is entered once, in the enclosing scope.

The distinction being tested. Entries follow declarations; spellings follow names. This program has fewer names than declarations.

MSQOriginal practice question

A compiler implements one hash table per scope, pushed on entry to a block and popped on exit. Which statements are TRUE?

(A) Pushing a table costs O(1).
(B) A lookup in a name at nesting depth d may probe up to d tables.
(C) A scope exit costs time proportional to the number of entries in the table being popped.
(D) Popping the table makes the outer binding of a shadowed name visible again.

Answer: A, B, D

A. Pushing an empty table is one pointer operation.

B. The walk starts at the innermost table and moves outward, so a name declared at the outermost level is found only after every table has been probed.

D. That is exactly what shadowing means: the hidden binding was never altered, only covered.

Why C is wrong. Discarding a table whose storage is released wholesale is O(1) in the usual implementation; the entries are not visited one by one. A implementation that frees each entry individually would make C true, which is why the option is a statement about an implementation and not about the structure.

MCQOriginal practice question

Which statement about the cost of a hash-based symbol table is correct?

(A) A lookup is O(1) in the worst case.
(B) A lookup is O(1) expected, given a hash function that spreads the keys and a bounded load factor.
(C) A lookup is O(log n) because the chains are sorted.
(D) A lookup is O(n) always, because collisions are possible.

Answer: B

With chaining, the cost of a lookup is the length of the chain it lands in. Under a spreading hash function and a bounded load factor the expected chain length is constant.

Why A is wrong. A constant hash function puts all n entries in one chain, and the worst case is O(n).

Why C is wrong. Chains are appended to, not kept sorted; nothing about chaining implies a sorted order.

Why D is wrong. "Collisions are possible" is true and does not make the expected cost linear.

The assumption that matters. Every one of these answers is a statement about a hash function and a load factor, so the correct option is the one that names them.

NATOriginal practice question

A hash table has 152 buckets and holds 25 entries.

What is the occupation density, to two decimal places?

Answer: 0.16

Occupation density is entries divided by buckets: 25 / 152 = 0.1644…, which is 0.16 to two places.

The trap. Inverting the fraction gives 152/25 = 6.08, which is the average number of buckets per entry and means nothing. The density is at most 1 for chaining and can exceed 1 for open addressing.

The related number. The average chain length is also 0.16 entries per bucket — the same fraction, because with chaining the chain lengths must sum to the entry count.

MCQOriginal practice question

A function f is declared in a scope and its body is being compiled. Where does the entry for f itself live?

(A) In f's own table, as its first entry
(B) In the enclosing scope's table
(C) In both, so that recursion can find it
(D) In a separate table of functions

Answer: B

The enclosing scope is where callers look, so that is where the name and its signature must be. Parameters go in f's own table, because only the body uses them.

Why A is wrong. An entry in f's own table would be invisible to the code that calls f, which is the only code that needs the name.

Why C is wrong. Recursion needs no second entry: the call is resolved in the enclosing scope, and the new activation is a run-time object, not a compile-time one.

The closely confused pair. The name is compile-time and lives outward; the call's frame is run-time and is created on each call.

MSQOriginal practice question

Which of the following does a symbol table entry for a variable typically record?

(A) Its type
(B) Its scope
(C) Its current run-time value
(D) Its storage offset or address

Answer: A, B, D

Type, scope and storage location are exactly the attributes a compiler needs to compile a use of the name.

Why C is wrong. The value changes at run time and cannot be known at compile time. The table may hold the address at which the value will be found; it does not hold the value.

The distinction. A table of declarations, not a table of data. That is the difference between the symbol table and the activation record, and this option is the one that confuses them.

Definitions to hold exactly

Symbol table — a mapping from each declared name to its attributes; operations insert and lookup.

Entry — one declaration's record: name plus type, scope, storage class, offset.

Scope — the region of text in which a binding is the one a use resolves to.

Shadowing — an inner declaration hiding an outer binding for the length of its block.

Occupation density — entries divided by buckets.

The three organisations, with their costs

Linear list. Insert scans for a duplicate: n(n−1)/2 comparisons to build n names. Lookup scans to the end in the worst case.

Search tree. Cost is the height. Balanced: O(log n). Built from sorted input: n − 1, which is a list.

Hash table with chaining. Cost is the chain length. Expected O(1) under a spreading function and bounded load; worst case O(n) with one bucket.

Decision procedure

  1. Decide whether the question is about entries, about cost, or about resolution.
  2. For entries: one table per block, one entry per declaration, function name outward, parameters inward.
  3. For cost: name the deciding quantity — prior entries, height, or chain length.
  4. For resolution: start at the innermost table and walk outward; the first match wins.
  5. State the assumption behind any cost you quote.
  6. Say "expected" when the structure is a hash table, and name the worst case.

Traps, in the order they cost marks

  1. Counting distinct names instead of declarations.
  2. Saying the table is unused after parsing.
  3. Claiming O(1) worst case for a hash lookup.
  4. Quoting log n for an unbalanced search tree.
  5. Putting the function's name in its own table.
  6. Confusing the symbol table with the activation record.
  7. Forgetting that a lookup walks every enclosing scope.

One sentence to remember

One table per block, one entry per declaration, a lookup that walks outward from the innermost table, and a cost that is only ever as good as the assumption you state beside it.
