Topic and objective

TOPIC: The hardware instructions that make a lock possible — test-and-set, swap, compare-and-swap and fetch-and-add — and the locks built from each of them, including the two that put a queue behind the lock so that nobody starves.

LEARNING OBJECTIVE: Say what each instruction returns and what it stores, and why the word “indivisible” carries the whole argument. Build a lock from each instruction and decide mutual exclusion, progress and bounded waiting for it. Find the reachable state in which the published GATE 2012 fetch-and-add lock has nobody inside and can never be taken again. Read the waiting-array algorithm's exit scan and say why the wait is at most n − 1. Count the failed attempts a spinner makes.

I read this as the layer under semaphores: the synchronisation lesson builds semaphores and Peterson's algorithm in software, and this lesson supplies the one indivisible step they all rest on, plus the queue that turns a correct lock into a fair one.

GATE relevance

Verified fact Section 8 of the GATE 2027 CS syllabus, published by IIT Madras, reads: “System calls, processes, threads, inter-process communication, concurrency and synchronization. Deadlock. CPU and I/O scheduling. Memory management and virtual memory. File systems.”

Educational interpretation Class A by area, class B by name. “Test-and-set” is not a phrase in the syllabus; “concurrency and synchronization” is. These instructions are the standard content of that clause, and the lesson teaches them as its worked instances.

Prerequisites

The critical-section problem. The section, the entry and exit code, and the three requirements — mutual exclusion, progress, bounded waiting. The synchronisation lesson defines all of them; this lesson uses them without redefining them.

Interleaving. That a switch may occur between any two machine steps, so many orders of the same statements are legal. Scene 1 depends entirely on this.

Semaphores, lightly. That wait and signal block rather than spin. Scene 9 contrasts the two designs and needs the word, not the arithmetic.

Intuition first: one door, one key, and a note on the door

A room may hold one person at a time. The cheap way to enforce that is a note on the door: read the note, and if it says free, write “taken” and go in. Reading the note and writing on it are two separate acts, and in the gap between them somebody else can read the same word “free”. That is the whole problem, and no amount of careful coding fixes it, because the gap is in the hardware.

The fix is a door that will only let you read the note and write on it as one movement — a turnstile you cannot be interrupted inside. That is what test-and-set and its three cousins are. Educational interpretation The turnstile carries the idea; the arithmetic in scene 9 is what makes it a cost rather than a metaphor.

The four instructions, in words

test-and-set — returns what the word held, and stores 1, as one step.

swap — exchanges the contents of two words, as one step, and returns nothing.

compare-and-swap — returns what the word held, and stores a new value only if the word still held the expected value.

fetch-and-add — returns what the word held, and adds a value to it, as one step. The ticket lock is built on this one.

The lock each one builds

test-and-set: while (TAS(&lock)) ; swap: key = 1; do { swap(&lock, &key); } while (key); compare-and-swap: while (CAS(&lock, 0, 1) != 0) ; release (all): lock = 0;

The three acquire loops are the same idea with a different instruction. The release is identical in all three, and it is a plain store, because writing one word cannot be half done.

Why one word is enough for the release

A store of a single aligned word is indivisible at the hardware level: no observer can see the word half written. So the release needs no special instruction, and every lock on this page releases with lock = 0.

Mathematical derivation The asymmetry is worth stating plainly: the acquire needs an indivisible read-modify-write because it must know whether it won, and the release does not, because it does not need to know anything.

What a search can and cannot settle here

Each process is a small state machine, the shared word is part of the state, and a step is one statement. So the set of reachable states is finite, and walking it is a complete decision procedure for “can two processes ever be inside together” — not a sample of schedules. That is how every count on this page was produced.

Mathematical derivation What the search does not settle is fairness, because “can a process wait for ever” is a statement about infinite schedules. For that this page does two honest things instead: it exhibits an explicit schedule in which one process loses every race, and it checks the exit scan of the queued algorithm on every waiting vector, which is what bounds the wait.

Example 1 — the naive lock, with the schedule that breaks it

Two processes, one flag, and the lock written as a test and then a store. The enumeration of every interleaving gives 52 reachable states, and exactly one of them has both processes inside.

step process action flag inside 1 P0 reads flag 0 - 2 P1 reads flag 0 - 3 P0 stores 1 1 - 4 P1 stores 1 1 - 5 P0 enters 1 P0 6 P1 enters 1 P0, P1 <- the violation

The flag reads one from step 3 onward and is never wrong. What is wrong is that both processes took their decision from the value in step 1 and 2, and the write in step 4 destroyed no information that either of them used. This is why the repair has to be at the instruction level.

Example 2 — the test-and-set lock, traced

process TAS returns lock after verdict P0 0 1 enters P1 1 1 spins P2 1 1 spins P0 release: lock = 0 P1 or P2: next TAS returns 0, enters

Three processes each running the loop twice give 135 reachable states, and no state has two inside. The largest number inside at any reachable state is one, which is the requirement, and the word only ever holds 0 or 1 because only those two values are ever stored into it.

Example 3 — the same instruction, written out

Split test-and-set into A1: y = *x; A2: *x = 1; A3: return y; and the same search reports the same violation as the naive lock, because the three statements are exactly the load, the store and the return that the naive flag lock performed.

Mathematical derivation The two programs have the same reachable-state count, 52, and the same single violating state. That equality is the cleanest statement of the point: the code is not what changed.

Example 4 — the swap lock, cell by cell

attempt 1: lock 0, key 1 -> lock 1, key 0 enter attempt 1: lock 1, key 1 -> lock 1, key 1 retry attempt 2: lock 1, key 1 -> lock 1, key 1 retry release: lock 0

The search gives 425 states and no violation, and a second invariant holds at every state: a process is inside exactly when its private key reads zero. The extra states over test-and-set come from the private register being part of the state, not from any difference in the lock.

Example 5 — compare-and-swap as a lock and as an increment

As a lock: 135 states, no violation, identical to test-and-set. As an increment: two threads, a thousand each, with one stale read per round.

plain count = count + 1 loses the update on a stale read CAS do { old = count; } while (!CAS(&count, old, old+1)); 1000 retries, total exactly 2000

A retry is not a failure of the counter: it means somebody else succeeded, so the value advanced anyway. That is why the total lands exactly and the retries cost only time.

Example 6 — the published fetch-and-add lock, and the state that strands it

The GATE 2012 code loops while the returned value is non-zero and sets the word back to one inside the loop. The search over two processes gives 318 states. One of them has nobody inside and the word at one, and from that state the forward search visits 46 further states without ever entering the section.

P1: fetch-and-add returns 1, word becomes 2 P1: switched out before its body runs P0: releases, word = 0 P1: body runs, word = 1 nobody inside, word held P1: fetch returns 1 again, body stores 1, for ever

Note what is not wrong. Mutual exclusion is never violated: the search reports no state with two inside. The defect is that a release is overwritten, so the lock is held by nobody and can never be acquired. That is why the answer to the paper's question is “the implementation fails” rather than “it works but starves”.

Example 7 — the waiting array, on paper

waiting = [false, true, false] P0 exits, i = 0 scan: j = 1, waiting[1] is true -> clear it lock stays 1; P1 leaves its loop because waiting[1] is now false

The exiting process does not store zero when somebody is waiting. It hands the lock over by clearing one flag, and the chosen process leaves its loop on the flag test alone. The scan is checked on all 256 combinations of process and waiting vector for two to five processes.

Example 8 — the spin arithmetic

processes arriving together failed attempts P0 0 P1 1 P2 2 ... P(n-1) n-1 total = n(n-1)/2 n=4: 6 n=8: 28

The first process makes no failed attempt and the last makes n − 1. Both totals above are computed on this page rather than quoted, and the closed form is checked against the count for eight processes.

Boundary 1 — one process, and a lock that is never contended

With one process the loop runs once, returns zero, and the process enters. Every property holds trivially and no test on this page can distinguish a correct lock from a broken one, because the failure needs a second process to be switched in at the wrong moment. That is why questions in this family always name the number of processes.

Mathematical derivation The searches here use two processes for the naive and fetch-and-add programs and three for the rest, because two is the smallest number that can exhibit a violation and three is the smallest that can exhibit a queue.

Boundary 2 — the release is not a no-op if it is not a plain store

Every lock here releases by storing zero. The moment the release becomes a read-modify-write — because it also counts something, or checks something — it acquires the same gap the acquire had, and needs its own protection. The readers–writers solutions in the sibling lesson are exactly that case: the count is read, changed and written back under a separate mutex.

The test to apply: does the exit code depend on the current value of a shared word? If yes, it is a critical section of its own.

Boundary 3 — a uniprocessor hides most of this

On one core, mutual exclusion can be had by disabling interrupts around the section, and the naive flag lock fails only if a switch occurs inside the two statements — which a scheduler may well do. Disabling interrupts does not work across processors, and it does not stop a second core writing the same word, so the instructions on this page exist for the multiprocessor case.

A question that says “the scheduler may switch at any point” allows the naive failure on one core; a question about several cores needs an atomic instruction whatever the scheduler does.

Boundary 4 — compare-and-swap and the ABA problem

Compare-and-swap checks a value, not an identity. If a word goes A, then B, then back to A between the read and the instruction, the instruction sees the expected value and succeeds even though the world changed twice. That is harmless for a lock word, which only holds zero and one, and it is not harmless for a pointer in a lock-free list.

So the standard advice — “use compare-and-swap for lock-free structures” — comes with an assumption about what the word means, and the assumption is the part a question can test.

Boundary 5 — the ticket counters wrap

The dispenser only ever increases, so a fixed-width counter must wrap eventually. The comparison now_serving == t survives a wrap because it is an equality; a comparison of the form now_serving < t does not, because the order of unsigned numbers breaks at the wrap.

The repair is a wrap-safe difference, comparing t - now_serving as a signed quantity. It is a defect of the comparison and not of the ticket idea, and it is worth naming separately because the idea is right and the code is not.

Boundary 6 — test-and-test-and-set is not a different lock

Spinning on a read and calling the instruction only when the read says free changes the traffic and nothing else: the same 28 failed attempts for eight processes, the same starvation, the same absence of a queue. It is an optimisation, not a repair.

The trap is to replace the instruction with the read. A read loop alone has the gap of scene 1 and admits two processes; the instruction must still be the one that decides.

Misconception 1 — “a correct lock must be fair”

The belief. Since the plain test-and-set lock gives mutual exclusion and cannot deadlock, it is a correct solution and therefore starvation-free.

Why it is wrong. Correctness in this problem is three separate promises. The plain lock gives the first two and not the third: the computed schedule admits P0 and P2 six times while P1 fails six times. Deadlock-freedom and starvation-freedom are different properties, and a paper can ask for either one.

The fix in your head. Answer the property that was asked. “Correct” without a named property is not an answer here, and this is precisely the structure of the GATE 2009 item in the next tab.

Misconception 2 — “the flag was wrong”

The belief. In the naive lock the flag must have held a wrong value, or the two processes could not both have entered.

Why it is wrong. At the violating state the flag reads one, which is correct: somebody is inside. What failed is the decision, which each process took from an older value of the flag. A shared word cannot carry information about a decision that has already been made from a stale copy.

The fix. Say where the switch was, not what the value was. The exam answer is a schedule, not a number.

Misconception 3 — “atomic means fast”

The belief. An atomic instruction is a quick one, so a spin lock built on it is cheap.

Why it is wrong. Atomicity is a promise about indivisibility, not about time. An atomic instruction that touches a shared cache line can cost far more than an ordinary one, and a spinner issues it repeatedly: 28 failed attempts for eight processes, each one a write to the shared line.

The fix. Separate the two questions. Does the code need indivisibility? Yes. Is the resulting loop cheap? That is scene 9, and the answer depends on the number of cores.

Misconception 4 — “bounded waiting means nobody waits”

The belief. A fair lock admits a process immediately, or at least in arrival order with no wait.

Why it is wrong. Bounded waiting says there is a bound on how many other admissions may happen first — n − 1 here. A process can wait for every other process to go once and still satisfy the definition. What is forbidden is an unbounded wait, not a wait.

The tell. If an option says “no process ever waits”, it is stronger than the definition and is therefore the wrong option.

Misconception 5 — “one atomic instruction is enough”

The belief. If the code contains an atomic instruction, the lock must be right.

Why it is wrong. The GATE 2012 lock contains one and still fails, because an ordinary statement sits inside the loop beside it and can overwrite a release. The atomicity of the instruction says nothing about the statements around it.

The fix. Ask what else runs between the instruction and the section. That is the second question of the reading order in the Revision tab, and it is the one this family tests most often.

Misconception 6 — “the ticket lock has no contention”

The belief. Because the ticket lock is fair, the waiters must be queued by the operating system rather than spinning.

Why it is wrong. The ticket lock is a spin lock with a queue expressed in two counters. Every waiter still runs and still reads the display, which is exactly what makes it expensive under heavy contention.

The fix. Fairness and blocking are separate axes: a ticket lock is fair and spinning, a semaphore is unfair-ish and blocking. Scene 9 puts the two costs side by side.

The four question shapes in this family

Shape 1 — fill the blanks. Complete enter_CS and leave_CS for a given instruction. Solve by asking what the instruction returns and which value admits you.

Shape 2 — name the property that fails. “Deadlock-free? Starvation-free? FIFO?” Solve by checking the three requirements in order and saying which one breaks.

Shape 3 — find the flaw in a proposed lock. Usually a statement that is not atomic, or a body that overwrites a release. Solve by asking what else runs between the instruction and the section.

Shape 4 — count. The number of failed attempts, the number of processes in the system, the largest number inside. Solve from the arithmetic, then check against the code.

The answer is the second: the lock can read non-zero when it is in fact available.

Verified fact GATE CSE 2006, Q61. The atomic fetch-and-set x, y used to implement P and V on a binary semaphore, asking which of four statements is true. The answer is that the implementation may not work if context switching is disabled inside P.

Verified fact GATE CSE 2002, Q18-b. TEST-AND-SET given as three C lines, asking for the enter and leave functions, whether the solution is deadlock-free and starvation-free, and an example showing that mutual exclusion fails when the instruction is not atomic.

How the 2009 item is answered

Take the four statements in order and check each against a definition rather than a feeling. Mutual exclusion: the winner takes X from 0 to 1 and every loser reads 1, so no. More than one inside is false. Deadlock: the release stores 0 and some waiter's next call then returns 0, so no deadlock — true. Starvation: nothing orders the waiters, and the schedule in scene 7 shows one process losing six times, so not starvation-free. FIFO: nothing records an arrival order, so false.

One statement true, three false, which is option A. The value of the exercise is the method: each option is a property, and each property has a definition you can test the code against.

Traps that survive a careless check

Trap 1. Reading while (cond) L = 1; as an empty loop. There is no semicolon, so the assignment is the body.

Trap 2. Saying the 2012 lock “works correctly but starves”. It does not work: the release can be lost.

Trap 3. Awarding FIFO to any lock with an atomic instruction. Order needs a recorded arrival, and only the ticket lock and the waiting array have one.

Trap 4. Answering “yes” to starvation-free because the code cannot deadlock.

Trap 5. Assuming the answer changes with the instruction. Swap, test-and-set and compare-and-swap give the same three properties; only the loop and the queue change them.

Cross-topic connections worth carrying

Semaphores rest on these. A wait that must decrement and test indivisibly is the same problem as the acquire here, and the standard implementations are a spin lock on this page or the disabling of interrupts. The synchronisation lesson treats the semaphore as a given; this lesson is what makes it a given.

MCQGATE CSE 2009 Q33

The enter_CS() and leave_CS() functions for a critical section are realised with test-and-set as void enter_CS(X) { while (test-and-set(X)); } and void leave_CS(X) { X = 0; }. X is a memory location initialised to 0. Consider:

I. the solution is deadlock-free   II. the solution is starvation-free   III. processes enter in FIFO order   IV. more than one process can be inside at the same time

Which of the above statements is TRUE?

  1. I only
  2. I and II
  3. II and III
  4. IV only

Answer: A — I only

The winner takes X from 0 to 1 and every other process reads 1 and spins, so IV is false. The release stores 0, so some waiter's next call returns 0 and enters: no deadlock, I is true. Nothing records arrival order, so III is false, and the schedule in scene 7 shows one process losing six races in a row, so II is false.

Why B is tempting. “No deadlock” feels like “everybody gets in eventually”. It is not: a process can lose every race while others cycle, which is starvation without deadlock.

MCQGATE CSE 2012 Q32

Fetch_And_Add(X,i) is atomic: it reads X, adds i, and returns the old value. It is used as

AcquireLock(L){ while (Fetch_And_Add(L,1)) L = 1; } ReleaseLock(L){ L = 0; }

with L an unsigned integer initialised to 0. This implementation

  1. fails as L can overflow
  2. fails as L can take on a non-zero value when the lock is actually available
  3. works correctly but may starve some processes
  4. works correctly without starvation

Answer: B

A waiting process fetches 1 and leaves the word at 2, then is switched out before its body runs. The holder releases, storing 0. The waiter resumes and its body stores 1, so the word is 1 with nobody inside, and every later fetch returns non-zero. That is a non-zero value while the lock is available, which is exactly option B, and it is the state this page's search finds.

Why C is wrong. It does not work correctly; the release is lost and the lock can never be taken again. Why A is a weaker answer. The body restores 1 after every attempt, so overflow needs an enormous number of processes to be switched out at the same instant; the failure in B needs one switch. Why D is wrong twice over.

NATOriginal practice

Eight processes reach a test-and-set spin lock at the same moment, and each holds the critical section for exactly one time unit while every spin attempt also costs one time unit. Counting only the attempts that fail, how many failed attempts are made in total?

Answer: 28

The first process in fails 0 times, the second 1, the third 2, and the eighth 7. The sum is 0 + 1 + ... + 7 = 28, which is n(n − 1)/2 with n = 8. The page computes both the count and the closed form and checks that they agree.

Why 8 appears. Counting processes instead of failed attempts. Why 36 appears. Using n(n + 1)/2, which counts the successful attempt of each process as a failure.

MCQGATE CSE 2006 Q61

The atomic fetch-and-set x, y unconditionally sets x to 1 and fetches the old value of x into y, with no intervening access to x. It is used as

void P(binary_semaphore *s){ unsigned y; unsigned *x = &(s->value); do { fetch-and-set x, y; } while (y); } void V(binary_semaphore *s){ s->value = 0; }

Which one of the following is true?

  1. The implementation may not work if context switching is disabled in P
  2. Instead of fetch-and-set, a pair of normal load and store can be used
  3. The implementation of V is wrong
  4. The code does not implement a binary semaphore

Answer: A

With switching disabled inside P, a process that fails the test loops for ever and never yields, so the process that could execute V never runs and the wait never ends. Context switching is what lets the release happen.

Why B is wrong. A plain load and store is two steps, and two processes can both read 0 and both enter — the gap of scene 1. Why C is wrong. Storing 0 is the correct release. Why D is wrong. Only one process is ever inside, so it is a binary semaphore.

MSQOriginal practice

Which of the following are true of the bounded-waiting algorithm that keeps waiting[n] and spins on test-and-set?

  1. A process waits for at most n − 1 admissions by other processes.
  2. The exiting process stores 0 into the lock whenever any process is waiting.
  3. The chosen process leaves its loop because its waiting flag was cleared.
  4. It removes the need for an atomic instruction.

Answer: A and C

Each exit clears exactly one raised flag, the nearest going round, so at most n − 1 admissions precede any given waiter: A is true. The loop condition is waiting[i] && key, so clearing the flag ends the loop without the instruction: C is true. The exiting process stores 0 only when nobody is waiting, so B is false, and the spin still uses test-and-set, so D is false.

Why B is tempting. It looks like the ordinary release. Storing 0 with a waiter present reopens the race the array was added to close, and the chosen waiter could lose again.

NATOriginal practice

A ticket lock has next_ticket = 9 and now_serving = 6 at some instant. How many processes are inside or waiting for this lock?

Answer: 3

Every ticket from 6 up to 8 has been handed out and not yet served, so three processes hold tickets 6, 7 and 8. One of them is inside and two are waiting, and next_ticket − now_serving = 9 − 6 = 3 counts all three.

Why 2 appears. Reading the difference as the queue length only, which forgets the process inside. Why 9 appears. Reading the dispenser alone, which counts every ticket ever issued.

MCQOriginal practice

Two locks are built on the same instruction, one as while (TAS(&lock)); and one as key = 1; do { swap(&lock,&key); } while (key);. Which statement is exactly right?

  1. Both give mutual exclusion; neither bounds the wait.
  2. The swap version gives mutual exclusion and the test-and-set version does not.
  3. Both give mutual exclusion and both bound the wait.
  4. Neither gives mutual exclusion, because the release is not atomic.

Answer: A

The two searches report no state with two processes inside — 135 states for test-and-set and 425 for swap — and neither loop records arrival order, so neither bounds the wait. The extra states in the swap search come from the private key register being part of the state.

Why D is wrong. Writing one word is indivisible, so a plain store is a correct release; the acquire is the part that needed the instruction.

The sheet

test-and-set. Returns the old word, stores 1, indivisibly. Lock: while (TAS(&lock));. Mutual exclusion and progress hold; bounded waiting does not.

swap. Exchanges two words, indivisibly, no return value. Lock: key = 1; do { swap(&lock,&key); } while (key);. Same three properties as test-and-set.

compare-and-swap. Returns the old word and stores the new one only if the word still held the expected value. Lock: expect 0, ask for 1. Also makes an increment atomic.

fetch-and-add. Returns the old word and adds. Used by the ticket lock, and misused by the 2012 lock whose body stores 1 inside the loop.

The two queued locks. waiting[n] plus the exit scan, and the ticket lock's two counters. Both bound the wait by n − 1; neither stops the spinning.

Decision procedure for any question here

1. Which instruction is atomic, and what does it return?

2. What else runs between that instruction and the section?

3. Does anything record arrival order?

4. How many processes, and what is each one doing at the instant named?

5. Answer with the property that was asked, not with “correct” or “incorrect”.

Formulas to keep

Failed attempts with n processes arriving together: n(n − 1)/2.

Processes inside or waiting on a ticket lock: next_ticket − now_serving.

Wait bound for a queued lock: n − 1 admissions.

Lock word values: 0 free, 1 held. Nothing else is ever stored by any acquire on this page except by the 2012 body.

Five sentences worth memorising, and their exact scope

“The acquire needs an atomic read-modify-write; the release does not.” — scope: a release that stores a constant. A release that also counts needs its own lock.

“test-and-set and swap give the same three properties.” — scope: the same loop with no queue. Adding a queue changes the third property.

“A negative result of a failed acquire means somebody holds it.” — scope: not in the 2012 lock, where a non-zero value can mean nobody holds it.

“The ticket lock is fair.” — scope: with a wrap-safe comparison of the two counters.

“Bounded waiting allows a wait.” — scope: always; it forbids only an unbounded one.

What was verified, and how

Mutual exclusion. Decided by a complete breadth-first search over every interleaving, with each process running its loop twice and then stopping so the state space is finite. The invariant is asserted at every reachable state, and the naive program is included as a control that must fail.

The 2012 defect. Decided by a second search from the candidate state: if no forward state has anybody inside, the lock cannot be taken again. The search also reports the mutual-exclusion count, which is zero, so the defect is distinguished from a double entry.

The wait bound. The exit scan is checked against its definition on all 256 combinations of process and waiting vector for two to five processes, and the ticket invariant (whoever is inside holds the displayed ticket) is checked at every reachable state.
