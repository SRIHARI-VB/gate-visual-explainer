Topic and objective

TOPIC: Recursion in C, at the depth GATE CSE asks it inside "Programming in C".

LEARNING OBJECTIVE: Given a short recursive C function, decide two things without running it: the value it returns (by building the call tree from the base cases upward), and the cost it pays (by writing the recurrence for the number of calls and for the peak stack depth, and solving each).

I read this topic as the mechanism — the frame, the unwind, the termination argument, and the storage that each frame does or does not own — because those four things decide every recursion question, and because the algorithms that use recursion (divide and conquer, traversals, backtracking) each have their own lesson. This lesson is linked from them, not repeated inside them.

GATE relevance

Verified fact Class A — explicitly in the syllabus.

Section 4 of the official GATE 2027 CS syllabus (IIT Madras) reads: "Programming in C. Recursion. Arrays, stacks, queues, linked lists, trees, binary search trees, binary heaps, graphs." The word appears on its own, as a named item.

Class A does not mean "guaranteed to appear". It means a question on it is inside the declared boundary. The previous-year questions quoted here are recorded as observations about past papers, never as a forecast.

What you should be able to do afterwards

Take any recursive function in a GATE paper and answer, in this order: where does it stop?, what does each level return?, how many calls and how much depth?

The most expensive mistake in this topic is answering the second question with the first one's picture — treating a name as one variable when each frame has its own.

Level 1 — Intuition: the staircase and the notepad

Imagine climbing down a staircase to fetch something from the bottom, then climbing back up. Going down you do no arithmetic at all — you only remember which step you are standing on. At the bottom there is a note that says 0. Coming back up, at each step you add your own step number to the number you are carrying.

The descending is the calls. The paper you leave on each step is the frame. The note at the bottom is the base case. The climbing back up with a running total is the return path.

This picture answers most trace questions by itself: the base case is the first value produced, and every other value is produced on the way back up, in reverse order of the calls.

Level 2 — Formal: what a recursive definition is

A function is recursive if its body contains a call to itself. A base case is an argument value for which the body returns without such a call. A recursion is well founded when every chain of calls reaches a base case in finitely many steps.

In C, no syntax marks a function as recursive. The frame (the standard's term is not fixed, but the object is) holds that call's parameters, its automatic locals, and the return address. Frames live on the call stack.

Peak depth is the largest number of frames alive at one moment. The number of calls is how many frames were ever created. For sumTo(3) both are 4; for naive fib(10) they are 177 and 10.

Level 3 — The four shapes you will meet

Linear. One call per level: sumTo(n) = n + sumTo(n-1). Calls and depth are both about n.

Branching. Two or more calls per level: fib(n) = fib(n-1) + fib(n-2). Calls explode, depth stays linear.

Divide and conquer. Two calls on halves, plus linear work: merge sort, T(n) = 2T(n/2) + n.

Generative / converging. The argument is replaced by a computed value rather than a smaller integer: Newton's iteration in GATE 2014, or the gcd by subtraction in GATE 2021. Termination is then an argument about a measure that decreases, not about n falling to 0.

Level 4 — Worked example: sumTo(3), frame by frame

int sumTo(int n){ return n == 0 ? 0 : n + sumTo(n-1); }

Down: sumTo(3) → sumTo(2) → sumTo(1) → sumTo(0). Four frames; the last one returns 0 without calling.

Up: sumTo(1) completes 1 + 0 = 1, sumTo(2) completes 2 + 1 = 3, sumTo(3) completes 3 + 3 = 6.

The additions happen in the order 1, 2, 3 — the reverse of the call order. That reversal is why printing before and after a recursive call gives two different sequences, a fact the tree-traversal lessons rely on.

Level 5 — Boundaries: when the picture changes

No base case: the recursion never stops, frames accumulate until the stack is exhausted, and the standard calls the behaviour undefined.

Base case off the path: f(n) = f(n-2) with a base case at n == 1 terminates for odd n and not for even n.

Tolerance base case: the test is on the value, so the answer is an interval, and the number of calls depends on the starting guess.

Static inside: the object is shared by every frame, so the function's result can depend on how many times it was called before.

Level 6 — The one table to memorise

Per frame (fresh in every call): parameters, automatic locals, local arrays.

Shared by all frames: static locals, globals, and anything reached through a pointer — including any array passed as a parameter, because the parameter is the pointer.

Sort every name in the function into one of those two columns before you trace. Most wrong answers in this topic come from putting a name in the wrong column.

Level 7 — Cost: two recurrences, not one

For the number of calls: linear recursion gives T(n) = T(n-1) + 1 with T(0) = 1, so n+1 calls. Naive fib gives T(n) = T(n-1) + T(n-2) + 1, so 2·F(n+1) − 1 calls. Merge sort gives T(n) = 2T(n/2) + n, so n·log₂n + n calls when n is a power of 2.

For the peak depth: linear recursion reaches n+1 frames, branching reaches n+1, divide and conquer reaches 1 + log₂n.

The two answers are different. fib(30) needs 2,692,537 calls and only 30 frames. A program can be far too slow and perfectly safe on the stack at the same time.

Level 8 — Tail calls, stated carefully

A call is in tail position when its result is the function's result, with no work left to do afterwards. sumTo(n-1, acc+n) is in tail position; n + sumTo(n-1) is not, because an addition remains.

Verified fact The C standard does not require an implementation to reuse the caller's frame for a tail call. Whether a build does so depends on the compiler and the optimisation level.

So "tail recursion is constant space in C" is not a language guarantee. It is a property some compilers have. An accumulator plus a loop is the version that is constant space by construction.

Level 9 — Undefined behaviour that hides in recursion

Stack exhaustion. A recursion that never terminates exhausts the stack; the standard does not define what happens next.

Two calls in one expression with side effects. f(i++, i) has no defined order of evaluation for its arguments, so the program's result is not predictable.

Returning a pointer to a local. The frame is gone when the call returns, so the pointer dangles. A recursive function that returns the address of its own local is the same error as a non-recursive one, and just as undefined.

Level 10 — A counterexample to "recursion is always slower"

Merge sort, quicksort, and tree traversal are recursive and are the standard fast algorithms for their problems. The cost of a recursion is decided by its recurrence, not by the fact that it recurses.

Conversely, naive Fibonacci is recursive and exponential. The word "recursive" tells you the shape, not the speed.

Level 11 — The solving procedure, written out

  1. Find the base case, and check it is reachable. If it is not, the question has no value to give.
  2. Sort every name into per-frame or shared. A static or a pointer changes the answer.
  3. For a value: write the call tree, evaluate the leaves, combine upward. The base case is the first value, never the last.
  4. For a cost: write T(n) for calls, then T(n) for depth. They are different recurrences and answer different questions.
  5. If the recursion looks like a known algorithm, name it first. An identification beats a 16-step trace.

Level 12 — Consolidation

Recursion = a smaller copy of the problem + a reachable base case + a stack that remembers where to come back to.

Value questions are answered on the way up; cost questions are answered by a recurrence, not by the trace.

Parameters and automatic locals are per frame. Statics, globals and pointer targets are shared. Every trace question starts there.

Example 1 — the gcd by repeated subtraction

Verified fact GATE CSE 2021 Set 2, Question 23 (1 mark, NAT). Official answer key: 15.

int SomeFunction (int x, int y) {
    if ((x==1) || (y==1)) return 1;
    if (x==y) return x;
    if (x > y) return SomeFunction(x-y, y);
    if (y > x) return SomeFunction(x, y-x);
}
/* value of SomeFunction(15, 255) */

Step 1 — name it. Each call replaces the larger argument by the difference. That is the Euclidean algorithm by repeated subtraction, whose invariant is that gcd(x, y) is unchanged. So the function returns gcd(x, y).

Step 2 — apply it. 255 = 15 × 17, so subtracting 15 sixteen times walks the pair to (15, 15), where the second test returns 15. The function is called 17 times in total.

Step 3 — confirm. The page's model runs SomeFunction on every pair with both arguments from 1 to 40 and checks the result equals gcd(x, y) in all 1,600 cases.

Example 2 — the double recursion inside a loop

Verified fact GATE CSE 2015 Set 2, 1-mark NAT. Archives index it as Q11 (gateoverflow) or Q.14 of the paper; the text is identical. Official answer: 51.

int fun(int n) {
    int x = 1, k;
    if (n == 1) return x;
    for (k = 1; k < n; ++k)
        x = x + fun(k) * fun(n-k);
    return x;
}
/* return value of fun(5) */

Build a table, not a tree. fun(1) = 1. Then fun(2) = 1 + 1·1 = 2, fun(3) = 1 + 1·2 + 2·1 = 5, fun(4) = 1 + 1·5 + 2·2 + 5·1 = 15.

fun(5) = 1 + 1·15 + 2·5 + 5·2 + 15·1 = 1 + 15 + 10 + 10 + 15 = 51.

Cost of the tree route. The page counts the calls: 1, 3, 9, 27, 81 — 3n−1. Tracing every call of fun(5) means 81 frames for a one-mark question. The table is five lines.

Example 3 — digits in base r

Verified fact GATE CSE 2011, 2-mark MCQ: the recursive function below is given, and the return value of foo(513, 2) is asked.

unsigned int foo(unsigned int n, unsigned int r) {
    if (n > 0)
        return (n % r) + foo(n / r, r);
    else
        return 0;
}

Read it. n % r is the last digit of n in base r; n / r is n with that digit removed. The function therefore adds the digits of n written in base r.

Apply it. 513 in binary is 1000000001, which has two 1 digits, so foo(513, 2) = 2. With r = 10 the same function adds decimal digits: foo(345, 10) = 3 + 4 + 5 = 12.

Mathematical derivation The page computes both values and checks them against a digit-sum routine for every n below 500 and every base from 2 to 10. The answer 2 is derived here; the question's year and marks are the verified part.

Example 4 — a base case written as a tolerance

Verified fact GATE CSE 2014 Set 2, Q40 (NAT). Official key: a value between 1.72 and 1.74.

double f(double x){
    if (abs(x*x - 3) < 0.01)
        return x;
    else
        return f(x/2 + 1.5/x);
}
/* give a q such that f(q) returns q */

What the question asks. Not "what does f(1) return" but "for which q does the function return its own input" — either because the first test passes, or because the recursion settles on q.

Direct route. Any q with |q² − 3| < 0.01 returns immediately: q = 1.73 gives |2.9929 − 3| = 0.0071.

Fixed-point route. Solve x/2 + 1.5/x = x, which gives x² = 3, so x = √3 ≈ 1.732. Both routes land in the official range.

Example 5 — a linear recursion traced properly

Trace int f(int n){ if (n == 0) return 1; return n * f(n-1); } at n = 4.

  1. f(4) → f(3) → f(2) → f(1) → f(0). Five frames. Each frame holds its own n: 4, 3, 2, 1, 0.
  2. f(0) returns 1. The base case is the only value not produced by a multiplication.
  3. f(1) = 1·1 = 1; f(2) = 2·1 = 2; f(3) = 3·2 = 6; f(4) = 4·6 = 24. Combine upward, one frame at a time.
  4. Answer 24, from 5 calls at peak depth 5. Both numbers equal n+1, which is what "linear" means here.

With if (n == 1) return 1; instead, the same trace gives 24 as well — but f(0) would then recurse to f(-1), f(-2), … and never stop. A base case that works for the inputs you tried is not the same as a reachable base case for every input.

Example 6 — the same recursion, memoised

Naive fib(n) = n < 2 ? n : fib(n-1) + fib(n-2) recomputes the same subproblems. fib(10) is 177 calls for one value.

long memo[64];              /* 0 = not computed */
long fib(int n) {
    if (n < 2) return n;
    if (memo[n]) return memo[n];
    memo[n] = fib(n-1) + fib(n-2);
    return memo[n];
}

Why it works. The static-duration array is shared by every frame, so a value computed at one level is visible at all others. This is scene 9's "shared object" rule used deliberately.

New cost. Each n is computed once, so there are about 2n calls and depth n. The exponential disappears, and the recursion stays. Mathematical derivation

Example 7 — a recursion that fills an array in place

Write the first n Fibonacci numbers into an array, with one recursive call per element.

void fill(int a[], int n) {
    if (n == 0) { a[0] = 0; return; }
    if (n == 1) { a[0] = 0; a[1] = 1; return; }
    fill(a, n-1);
    a[n] = a[n-1] + a[n-2];
}

Why the array survives. a is a parameter of array type, so it is a pointer; every frame refers to the same array. The fill(a, n-1) call has already written a[0..n-1] by the time the next line runs.

Contrast. Replace the parameter with a local int a[10]; inside the function and every frame gets a private array — the writes of the deeper frame are lost when it returns. Same code, opposite behaviour, one declaration apart.

Example 8 — a cost question, answered as a cost question

"How many calls does this function make?" is not answered by tracing it.

void g(int n) {
    if (n <= 1) return;
    g(n/2);
    g(n/2);
}

Recurrence. C(n) = 2·C(n/2) + 1 with C(1) = 1. For n = 2k the solution is C(n) = 2n − 1 calls, at a peak depth of 1 + log₂ n.

Check. n = 8: 2·8 − 1 = 15 calls. The page's model counts them for n = 2, 4, 8, 16 and confirms the closed form. Mathematical derivation Note the two answers: 15 calls, 4 frames. Both are correct, and they answer different questions.

Edge 1 — a base case that no input reaches

int f(int n){ if (n == 1) return 1; return f(n-2); }

f(5) terminates: 5 → 3 → 1. f(4) does not: 4 → 2 → 0 → −2 → … and the base case is stepped over forever.

The code contains a base case, so the function looks finished. The correct statement is that it terminates only on the inputs that land exactly on 1.

Edge 2 — a base case tested after the call

void p(int n){ p(n+1); if (n == 3) return; }

The recursive call is made before any test, so no test can ever stop the descent. The order of the two statements is the whole question.

Placing the test first gives a function that descends until n reaches 3 and then returns — but note that the value of n is still growing on the way down, so a test such as n == 3 must be met on the way, not assumed.

Edge 3 — n = 0, and negative arguments

sumTo(0) makes exactly one call and returns 0. That is the smallest input, and it is a call like any other — so the count for sumTo(n) is n+1, not n.

Pass −1 and n == 0 never fires; the argument moves away from the base case. A guard such as if (n <= 0) return 0; handles both, which is why so much real code writes the base case as an inequality.

Edge 4 — a tolerance base case answers with a range

When the test is |x*x - 3| < 0.01, every q with q² between 2.99 and 3.01 returns itself immediately. That is a continuum of correct answers, and the official key gives a range.

Two things change together: the answer becomes an interval, and the number of calls depends on the starting guess. f(1.73) needs zero recursive calls; f(1) needs three.

Edge 5 — the frame is gone when the call returns

int *bad(int n){ int local = n; return &local; }

Returning the address of an automatic object gives a pointer to storage that no longer exists. In a recursive function the mistake is easier to make, because the address looks like it belongs to a level that is still on the stack.

Dereferencing it is undefined behaviour. A static local, or storage the caller owns, is the fix — and a static local is then shared by all frames, which is a different design decision.

Edge 6 — two calls in one expression

printf("%d %d", f(i++), f(i++));

The order in which the two arguments are evaluated is unspecified in C, so which call sees which value of i is not determined by the standard. The program's output is not a question with an answer.

GATE has asked versions of this with two calls to a function containing a static counter. The honest answer is that the result is not defined by the language.

Edge 7 — very deep recursion is a limit of the implementation, not of the language

The standard says nothing about how much stack exists. A typical desktop build allows a few thousand to a few hundred thousand frames depending on the frame size and the stack limit; an embedded build may allow dozens. So "does this recursion work for n = 100000?" is a question about a particular implementation, and the safe answer in an exam is the complexity statement, not a frame count.

What is portable: linear recursion uses O(n) stack, divide and conquer uses O(log n), and naive Fibonacci uses O(n) stack but exponential time.

Misconception 1 — "n is one variable that gets smaller"

Why it feels right: the source shows one name, n, and one line that changes it.

What is actually true: each call creates a new parameter object. sumTo(3) has four frames holding 3, 2, 1 and 0 at the same time. Nothing is overwritten.

What it costs: the trace of any function that uses its parameter after the recursive call becomes wrong. In sumTo, n + sumTo(n-1) uses the frame's own n after the deeper call returns.

Misconception 2 — "a static local is recreated on each call"

Why it feels right: it is declared inside the function, so it looks local, and the previous lesson said local objects are rebuilt per call.

What is actually true: static changes the storage duration. The object is created once, before the program starts, and every frame reads and writes the same one.

What it costs: a counter that was meant to be per-level becomes a call counter. depth(3) returns 4 and a later depth(0) returns 5 — the model checks exactly this.

Misconception 3 — "deep means slow"

Why it feels right: recursion looks like it is doing work at every level, and depth is easy to count.

What is actually true: the cost is the number of calls, which for branching recursion is the number of nodes in the tree, not its height. fib(30) makes 2,692,537 calls at depth 30.

What it costs: the complexity answer. "Depth is n, so it is O(n)" is right for sumTo and wrong for naive Fibonacci, which is O(1.6ⁿ).

Misconception 4 — "tail recursion is constant space in C"

Why it feels right: it is true in Scheme and in some functional languages, and many compilers do it for C at -O2.

What is actually true: the C standard does not require it. A build without optimisation typically keeps every frame, so a tail-recursive function with 100000 levels can still exhaust the stack.

What it costs: a claim in a written answer that the language does not support. The safe statement is "the compiler may reuse the frame; the standard does not require it".

Misconception 5 — "an array parameter is a copy, so each frame has its own array"

Why it feels right: pass by value really does copy, and that lesson was emphasised.

What is actually true: a parameter of array type is adjusted to a pointer, so what is copied is the address. Every frame therefore sees one array, and writes made at one level are visible at all others.

What it costs: the answer to every "what does the array hold at the end" question. The model bumps a[0] once per level: after three levels it is 3, not 1.

Misconception 6 — "a recursion with a base case terminates"

Why it feels right: the base case is the thing everyone says to add.

What is actually true: the base case must also be reachable. f(n) = f(n-2) with a base case at n == 1 never terminates for even n.

What it costs: you accept a "correct" function that does not return. The check is two questions, not one: does the argument move toward the base case, and is the base case on that path?

Closely confused pair — the value of a recursion and the cost of a recursion

These are two different computations over the same call tree. The value is obtained by combining what the base cases return on the way up; it is a number, and it is what "what does this print" asks for. The cost is the number of nodes in that tree (calls) and its height (depth); it is what "what is the time complexity" asks for.

A trace gives you the value for free and the cost only if you count while you go. A recurrence gives you the cost directly and the value not at all. In GATE 2015 Set 2 the value question (51) and the cost question (81 calls) are about the same function, and mixing them up produces a plausible wrong answer to whichever one was asked.

The five shapes a recursion question takes

Every recursion question in the papers consulted falls into one of these. Naming the shape first is what turns a 40-minute trace into a two-minute answer.

Shape 1 — value of a small recursion

"The return value of fun(5) is ___." Linear or double recursion of depth 3 to 6. Solved by a table from the base case upward.

Verified example: GATE CSE 2015 Set 2, fun(5) = 51.

Failure mode: expanding the tree instead of tabulating. 81 calls for a one-mark question.

Shape 2 — identify the algorithm

"The value returned by SomeFunction(15, 255) is ___." The code is a well-known algorithm written unusually: gcd by subtraction, digit sum in base r, binary search, power by squaring.

Verified examples: GATE CSE 2021 Set 2 (gcd), GATE CSE 2011 (base-r digit sum).

Failure mode: tracing all 16 subtractions and making one arithmetic slip, when the identification gives the answer in one line.

Shape 3 — fixed point and convergence

"Give a value q such that f(q) returns q." The recursion iterates a function; the answer is where the update returns its input, or where the tolerance accepts it.

Verified example: GATE CSE 2014 Set 2, Q40 — official range 1.72 to 1.74.

Failure mode: answering with a single number when the key is a range, or missing that the base case is a tolerance.

Shape 4 — storage class inside the recursion

A static or a global inside a recursive function, so the value carries across frames. The arithmetic is short; the classification is the question.

Related verified example: the static counter of GATE CSE 2019 (traced in the functions-and-scope lesson) and GATE CSE 2023 Q35's static int x.

Failure mode: treating the static as per frame, which produces a sequence of identical values instead of an increasing one.

Shape 5 — cost, not value

"How many times is the function called", or "what is the time complexity". Answered by a recurrence: T(n) = T(n-1)+1, T(n) = 2T(n/2)+n, T(n) = T(n-1)+T(n-2)+1.

Where it appears: as the Algorithms half of the same skill — asymptotic complexity and recurrences.

Failure mode: writing the depth recurrence and calling it the call count.

Working a trace question, in order

  1. Copy the function and mark the base case. Check that every call moves toward it.
  2. List every name and mark it per-frame or shared. Static, global and pointer targets are shared.
  3. Compute the smallest inputs first. f(1), then f(2), then f(3) — the base case is the first value.
  4. Write one line per input, not one tree. The tree is implicit in the table and costs nothing.
  5. State the answer with its type. An integer value, a printed string, or "not defined".

Working a cost question, in order

  1. Count the recursive calls per level. One call means linear; two means branching.
  2. Write T(n) for the call count, including the constant work. The "+1" per call is what makes 177 out of 89.
  3. Write D(n) for the depth separately. Depth is the space cost; calls are the time cost.
  4. Solve for powers of two or for the stated n. Closed forms are cleanest at n = 2^k.
  5. State both answers. "O(n) time and O(n) stack" is a complete answer; one of them alone is half.

Traps that have actually appeared

The loop bound. for (k = 1; k < n; ++k) excludes k = n. Adding that term changes 51 into 71.

The initial value. int x = 1 is part of the answer. Starting at 0 changes 51 into 50.

Integer division. n / r in the digit-sum recursion must be integer division, or the recursion never reaches 0.

The condition's type. In GATE 2014's snippet, abs takes an int in C, so the written test is not the mathematical one. The key answers the mathematical reading.

What is the return value of foo(513, 2)?

unsigned int foo(unsigned int n, unsigned int r) {
    if (n > 0)
        return (n % r) + foo(n / r, r);
    else
        return 0;
}

Answer: 2

The function adds the digits of n written in base r. 513 = 1000000001 in binary, and that numeral has two 1 digits, so the sum is 2.

Common wrong answer: 9. That is the number of bits in 513, not the number of 1 bits. Counting the digit positions instead of the digit values is the trap. 7 and 8 come from the same miscount.

MCQModerateOriginal GATE-style

What does this program print?

void p(int n) {
    if (n == 0) return;
    printf("%d ", n);
    p(n - 1);
    printf("%d ", n);
}
int main(void) { p(3); return 0; }
  1. 3 2 1 1 2 3
  2. 3 2 1 0 1 2 3
  3. 1 2 3 3 2 1
  4. 3 2 1 3 2 1

Answer: A — 3 2 1 1 2 3

Descending, each frame prints its own n before calling: 3, 2, 1. Ascending, each frame prints its own n again after the call returns: 1, 2, 3. Each frame holds its own n, so the second half is the first half reversed.

Option B prints 0, which the base case returns from before reaching either printf. Option C reverses the whole sequence, which would need the print before the call to be moved after the recursion. Option D treats n as one shared variable that is still 3 at every return.

This is the same mechanism that distinguishes pre-order, in-order and post-order tree traversal.

MSQModerateOriginal GATE-style

For int f(int n){ static int c = 0; c++; if (n == 0) return c; return f(n-1); }, which statements are TRUE?

  1. f(3) returns 4.
  2. If f(3) is called and then f(0) is called, the second call returns 5.
  3. Each frame has its own copy of c, so the value returned is always 1.
  4. Replacing static int c = 0 by int c = 0 makes f(3) return 1.

Answer: A, B and D

c is static, so one object serves every frame and is initialised once. f(3) makes four calls, so c reaches 4 and that is what the deepest frame returns. A later f(0) makes one more call, so c is 5. With an automatic c, every frame would start from 0, increment to 1, and the base case would return 1.

C is false and is the misconception this question exists to catch: static changes storage duration, not scope. The name is still local to the function; the object is not.

The page's model runs both versions and checks 4, then 5, and 1 for the automatic version.

NATHardOriginal, in the style of GATE 2015 Set 2

Using the function from GATE 2015 Set 2, how many times is fun called in total during the evaluation of fun(4)? (Count the outermost call.)

int fun(int n) {
    int x = 1, k;
    if (n == 1) return x;
    for (k = 1; k < n; ++k)
        x = x + fun(k) * fun(n-k);
    return x;
}

Answer: 27

The counts are 1, 3, 9, 27, 81 for n = 1, 2, 3, 4, 5 — three to the power n−1. Each call makes two recursive calls for each k, and the number of k values grows by one per level, so the count triples.

Common wrong answer: 15. That is fun(4)'s value, not its call count — the classic value-versus-cost mix-up. 9 counts only the calls at the deepest level, and 81 is the answer for fun(5).

The page's model counts the calls by instrumenting the recursion itself, and checks 3n−1 for n = 1 to 5.

MCQModerateOriginal, in the style of GATE 2014 Set 2

For the function below, which value of q makes f(q) return q at its very first test, with no recursive call?

double f(double x) {
    if (abs(x*x - 3) < 0.01) return x;
    else return f(x/2 + 1.5/x);
}
  1. 1.50
  2. 1.73
  3. 2.00
  4. 3.00

Answer: B — 1.73

The test is |q² − 3| < 0.01, so q² must lie between 2.99 and 3.01. For q = 1.73, q² = 2.9929 and the difference is 0.0071, which passes. For 1.50 the difference is 0.75; for 2.00 it is 1.00; for 3.00 it is 6.00.

The closely confused version: a question that asks for the fixed point rather than an immediate return has the same answer here, because the fixed point √3 is inside the tolerance band. That is a coincidence of this tolerance, not a rule: with a much tighter tolerance the two questions would separate, since only a starting value already close to √3 returns immediately while the fixed point is always √3.

The page's model checks that f(1.73) returns with zero recursive calls and that the fixed point of the update is √3.

MCQBasicOriginal GATE-style

For int s(int n){ return n == 0 ? 0 : n + s(n-1); }, what are the number of calls and the peak stack depth for s(5)?

  1. 5 calls, 5 frames
  2. 6 calls, 6 frames
  3. 6 calls, 5 frames
  4. 5 calls, 6 frames

Answer: B — 6 calls, 6 frames

The arguments are 5, 4, 3, 2, 1, 0 — six calls. No frame is popped before the deepest one returns, so all six are alive at once.

Option A forgets the call on n = 0. That base case is a call like any other, and it is the one that produces the first value. Options C and D assume calls and depth can differ, which happens only for branching or divide-and-conquer recursion, not for a linear one.

The page's model traces s(3), s(5) and s(n) for n up to 12 and checks calls = depth = n+1.

MSQHardOriginal GATE-style

Which of these functions are guaranteed to terminate for every input n ≥ 1?

  1. int a(int n){ if (n == 1) return 1; return a(n-1); }
  2. int b(int n){ if (n == 1) return 1; return b(n-2); }
  3. int c(int n){ if (n <= 1) return 1; return c(n/2); }
  4. int d(int n){ return d(n+1); }

Answer: A and C

A steps by 1 and its base case is n == 1, which every n ≥ 1 reaches. C halves, and integer division eventually reaches 0 for every positive n, where n <= 1 catches it.

B is the counterexample to "a base case means it terminates". The base case is present and correct, but an even n steps over 1 and continues into negative numbers forever. D has no base case at all, and its argument moves away from any stopping point.

The page's model runs B on n = 5 and n = 4 with a depth guard: the first terminates, the second exhausts the guard. It runs D the same way.

NATHardOriginal GATE-style

How many calls does g(8) make in total, counting the outermost call?

void g(int n) {
    if (n <= 1) return;
    g(n/2);
    g(n/2);
}

Answer: 15

C(n) = 2·C(n/2) + 1 with C(1) = 1. Then C(2) = 3, C(4) = 7, C(8) = 15 — that is 2n − 1 for n a power of two.

Common wrong answer: 7. That counts only the calls at the deepest level. 8 is n itself, and 31 comes from doubling one level too far.

Note the other number: the peak depth is 1 + log₂ 8 = 4 frames. Fifteen calls, four frames — both correct, and the question asks only for the first.

The page's model counts the calls for n = 2, 4, 8, 16 and checks 2n − 1.

The revision sheet

Everything on this tab is a statement you can check against the animation, the model, or one of the four verified previous-year questions. Nothing here is a shortcut that depends on an unstated assumption.

Definitions

Recursive function: a function whose body calls itself.

Base case: an argument for which the body returns without calling.

Well founded: every chain of calls reaches a base case in finitely many steps.

Frame: the per-call storage holding that call's parameters, automatic locals and return address.

Peak depth: the maximum number of frames alive at one moment.

Tail call: a call whose result is the function's result, with no work remaining afterwards.

Formulas, with their assumptions

sumTo / fact — calls = depth = n+1. Assumes the base case is n = 0 and the step is n−1.

Naive fib — calls = 2·F(n+1) − 1, depth = n+1. Assumes F(1) = F(2) = 1 and the base cases are n ≤ 1.

Merge-sort shape — T(n) = 2T(n/2) + n gives n·log₂n + n for n = 2k.

Halving shape — T(n) = 2T(n/2) + 1 gives 2n − 1 calls, depth 1 + log₂n.

GATE 2015's fun — value 1, 2, 5, 15, 51 for n = 1…5; calls 3n−1. Verified by the model, not assumed.

Decision procedure for any trace question

  1. Base case: present, and reachable? Two questions, not one.
  2. Each name: per frame or shared? Static, global, pointer target = shared.
  3. Value question: table upward from the base case. Never expand the tree unless it has fewer than ten nodes.
  4. Cost question: two recurrences — calls and depth. They answer different questions.
  5. Recognisable algorithm? Name it first. gcd, digit sum, binary search, power by squaring.

Traps, one line each

A static local is one object, not one per frame.

An array parameter is a pointer, so all frames share the array.

A base case that exists can still be unreachable.

Calls and depth are different numbers for branching recursion.

The C standard does not require tail call optimisation.

A tolerance base case makes the answer a range.

Running out of stack is undefined behaviour, not a defined error.
