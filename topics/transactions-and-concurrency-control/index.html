Topic and objective

TOPIC: Transactions and concurrency control — ACID as four separate promises; the conflict relation; the precedence graph and conflict serialisability; view serialisability and the blind write that separates them; the recoverable, cascadeless and strict ladder; two-phase locking; and timestamp ordering with the Thomas write rule. This is the last clause of Section 9 of the official GATE 2027 CS syllabus.

LEARNING OBJECTIVE: Given any schedule of two or three transactions, decide conflict serialisability by drawing one graph; name the serial order it is equivalent to, or produce the cycle that forbids one; test recoverability, cascadelessness and strictness from the commit positions; decide whether two-phase locking could have produced the schedule; and count the conflict-serialisable interleavings of a small pair by enumeration rather than by a remembered formula.

I read this topic as one test, applied five times. The test is: find the conflicts, turn each into an edge, and ask whether the edges can all be satisfied at once. Conflict serialisability asks it of the schedule; view serialisability asks a weaker version; locking asks whether a lock assignment can exist; counting asks it of every interleaving. The lesson teaches the test first and then reuses it.

Prerequisites

Read these first if any is unfamiliar. Each is a full lesson in this repository.

Relational algebra and SQL — relational-algebra-and-sql. A transaction reads and writes items; the lesson assumes you know what a relation and a row are, and treats a data item as one addressable value.

Graphs: connectivity and structure — graphs-connectivity. The precedence graph is a directed graph and the whole decision is a cycle test plus a topological order.

Synchronisation and deadlock — synchronisation-and-deadlock. Locking in an operating system and locking in a database are the same idea at different granularity; the deadlock cycle is identical.

Relations and their properties — relations-and-their-properties. Serialisability is an equivalence relation on schedules, and view equivalence is the quotient it defines.

The five ideas this lesson turns on

  1. A conflict is three conditions at once. Same item, different transactions, at least one write. Read-read is never a conflict, which is where most marks are won.
  2. One conflict, one edge. Each conflict pins an order the interleaving has already committed to. The precedence graph is the set of those pins.
  3. Acyclic is the whole test. Conflict serialisable means the pins are satisfiable at once, and that is exactly no cycle. The topological order is the serial schedule.
  4. Conflict serialisability is sufficient, not necessary. Blind writes let a cyclic schedule stay equivalent to a serial one. That is view serialisability, and the containment is strict.
  5. Protocols guarantee; they do not test. Two-phase locking forbids a shape of schedule, timestamp ordering refuses late operations. Each buys one property and pays for it somewhere else.

Build-up, page 1 of 2 — from a lost update to the graph

Levels 1 to 4: the analogy, the definitions, the structure, and the first worked decision. Nothing here needs the animation to be running.

Intuition: two clerks and one ledger

Two clerks each update the same ledger line. Each reads the current figure, does arithmetic on it, and writes the result back. If both read before either writes, the second write silently erases the first clerk's work.

The ledger is a data item. A clerk is a transaction. "Read, compute, write back" is the read-modify-write pattern that makes concurrency dangerous.

Educational interpretation The analogy carries the failure mode, not the terminology. What makes the update lost is not that two clerks exist; it is that both acted on the same stale copy.

Formal definition: transaction, schedule, serial

A transaction is a sequence of operations — read an item, write an item, commit, abort — that must be executed as a unit. Write ri(X) for "transaction i reads item X" and wi(X) for "transaction i writes item X".

A schedule is an interleaving of the operations of several transactions that keeps each transaction's own operations in their own order. A schedule is serial when no two transactions interleave at all.

S is serialisable ⇔ S is equivalent to some serial scheduleEquivalent in the sense the next paragraph fixes. Serialisability is always "equivalent to a serial order", never "is a serial order".

Two equivalence definitions are used. Conflict equivalence compares the order of conflicting operations. View equivalence compares only what each read saw and who wrote last. Conflict equivalence is stricter.

Formal definition: the conflict

Operations a and b, from different transactions, conflict when all three hold: they act on the same item; they belong to different transactions; at least one of them is a write.

That gives exactly three shapes: read-then-write, write-then-read, write-then-write. Read-then-read is not among them, and cannot be: neither operation changes the item, so their order cannot matter to anyone.

The precedence graph of a schedule has one vertex per transaction and a directed edge Ti → Tj whenever an operation of i conflicts with a later operation of j. Duplicate conflicts between the same pair collapse into one edge.

The theorem, with its assumption stated

Mathematical derivation A schedule is conflict serialisable if and only if its precedence graph is acyclic. Only if: a cycle demands that some transaction come both before and after another, which no serial order satisfies, so no serial order is conflict equivalent. If: when the graph is acyclic, any topological order gives a serial schedule; every edge points forward in that order, so every conflicting pair keeps its relative order, which is precisely conflict equivalence.

The theorem assumes nothing about how the schedule was produced. It is a test on a finished schedule, which is why it is used to mark answers rather than to build systems.

Where the intuition fails

"The graph is acyclic, so this is a good schedule" is a correct inference about conflict equivalence and a wrong inference about everything else. An acyclic graph says nothing about recoverability, nothing about deadlock, and nothing about whether the transactions preserved any business rule.

Scene 7 of the animation shows three schedules whose graphs are all identical — one transaction, one write — and which differ only in where the commits sit. Two of the three are unsafe.

Page 1 summary

A schedule interleaves transactions. Conflicting operations pin orders. The graph collects the pins. Acyclic means conflict serialisable, and the topological order names the serial schedule it is equivalent to. Everything after this page reuses that one test.

Build-up, page 2 of 2 — view equivalence, recovery, and the two protocols

Levels 5 to 7: boundaries, the weaker equivalence, the recovery ladder, and what each protocol actually promises.

View equivalence, and the blind write

Two schedules are view equivalent when three things match: every read sees a value written by the same transaction (or the initial value); every item's final write comes from the same transaction; and the same transaction performs each item's first read. A schedule is view serialisable when it is view equivalent to some serial schedule.

A blind write is a write with no read of that item earlier in the same transaction. Blind writes are what make view serialisability strictly larger: they are the only reason a cyclic schedule can still match a serial one.

The witness used in this lesson is r1(A) w2(A) w1(A) w3(A). Its graph has both T1→T2 and T2→T1, yet T1 reads the initial value and T3 writes last — exactly as in the serial order T1, T2, T3.

The recovery ladder, defined by commit positions

Recoverable: if Tj reads a value written by Ti, then Ti commits before Tj commits. Only the two commit points are compared.

Cascadeless (also called ACA): no transaction reads an item until the transaction that last wrote it has committed. The commit is compared with the read.

Strict: no transaction reads or writes an item until its last writer has committed. The commit is compared with any access.

strict ⇒ cascadeless ⇒ recoverableEach implication is one-way. Neither converse holds, and the animation gives a one-line witness for each failure.

Recoverable is the minimum for a system to be able to undo a failed transaction without leaving a committed transaction built on a value that never existed.

Two-phase locking

A transaction may acquire locks only during a growing phase, and may release them only during a shrinking phase. The instant of the last acquisition is the lock point. Once a lock is released, no further lock may be taken.

Mathematical derivation 2PL produces only conflict-serialisable schedules. If Ti → Tj is an edge, then Ti held the conflicting item's lock at the moment of its own operation and Tj could only obtain it after Ti released it, which is after Ti's lock point; so Ti's lock point precedes Tj's. A cycle would make some lock point precede itself.

The converse fails: conflict serialisable does not mean 2PL could produce the schedule. Scene 8 uses S1 of GATE 2014 Set 3 as the witness, and the model on this page verifies it.

Timestamp ordering

Every transaction gets a timestamp, and every item X keeps two numbers: R_TS(X), the largest timestamp of any transaction that has read X, and W_TS(X), the largest that has written it.

A read ri(X) is refused when ts(Ti) < W_TS(X): a later transaction has already written, so this read is too late. A write is refused when ts(Ti) < R_TS(X): a later transaction has already read.

The Thomas write rule handles the remaining case. If ts(Ti) < W_TS(X) on a write, this write is obsolete — a later write already landed — so it is skipped instead of aborting the transaction. Nothing observable changes.

The boundary this chapter keeps crossing

Serialisability is about the result of an interleaving. Recoverability is about what happens after an abort. Deadlock freedom is about whether a protocol ever makes a transaction wait. Locking and timestamps are two answers to the same problem with opposite trade-offs: locks wait and can deadlock, timestamps refuse and restart. No single protocol in the syllabus gives all four properties at once, and a question that offers one usually has an option claiming it does.

Worked examples, page 1 of 2 — three previous-year schedules, worked line by line

Every answer below was recomputed by the model on this page, not copied from a key. The Animation tab draws the same graphs in scenes 4, 5 and 6.

Example 1 — GATE CSE 2014 Set 3

T1: r1(X); r1(Z); w1(X); w1(Z). T2: r2(Y); r2(Z); w2(Z). T3: r3(Y); r3(X); w3(Y). Two schedules S1 and S2 use exactly these operations in different orders; the question asks which statement is true.

S1: r1(X); r3(Y); r3(X); r2(Y); r2(Z); w3(Y); w2(Z); r1(Z); w1(X); w1(Z).

Step 1, find conflicts. On X: r3(X) precedes w1(X), so T3→T1. On Y: r2(Y) precedes w3(Y), so T2→T3. On Z: w2(Z) precedes r1(Z) and w1(Z), so T2→T1.

Step 2, look for a cycle. Edges T2→T3, T3→T1, T2→T1. Acyclic. Topological order: T2, T3, T1, and it is the only one.

S2 moves r1(Z) to before w2(Z), which adds T1→T2 while T2→T1 survives. Cycle. Answer: only S1 is conflict serialisable, option A.

Example 2 — GATE CSE 2022

S: r4(X) r2(X) r3(X) r1(Y) w1(Y) w2(X) w3(Y) r4(Y). The question asks which serial order S is conflict equivalent to.

Conflicts on X: r4(X) before w2(X) gives T4→T2; r3(X) before w2(X) gives T3→T2.

Conflicts on Y: r1(Y) before w3(Y) gives T1→T3; w1(Y) before r4(Y) gives T1→T4; w3(Y) before r4(Y) gives T3→T4.

The graph: T1→T3, T1→T4, T3→T4, T3→T2, T4→T2. Acyclic, and the model finds exactly one topological order.

Answer: T1 → T3 → T4 → T2. Note that r4(X) being first does not put T4 first: T4 also reads Y, and that read must come after T1's and T3's writes.

Example 3 — GATE CSE 2016 Set 2

The question gives a serialisable schedule S and its precedence graph, and asks which ordering of the vertices is guaranteed to yield a serial schedule. Options: topological order, depth-first order, breadth-first order, ascending order of transaction index.

Reasoning. A serial order that is conflict equivalent must respect every edge, because each edge is a conflict the interleaving already fixed. Respecting every edge is the definition of a topological order. DFS and BFS orders respect no edges in general, and index order is unrelated to the conflicts.

Answer: topological order. The word guaranteed is doing the work — index order might happen to work on a given schedule, which is why it is the tempting wrong option.

Why these three are on one page

All three are the same computation with a different question attached: which statement is true (2014), which serial order (2022), which ordering is guaranteed (2016). The graph answers all three.

If you can draw the graph and read a topological order off it, you can answer any of them. If you memorise answers, you can answer none of them on a new schedule.

Worked examples, page 2 of 2 — the counting question, and the blind write

One numerical-answer question and one structural counterexample. Both are computed, not recalled.

Example 4 — GATE CSE 2017 Set 2, the count

T1: r1(X) w1(X) r1(Y) w1(Y). T2: r2(Y) w2(Y) r2(Z) w2(Z). The question asks for the total number of conflict-serialisable schedules the two can form. This is a numerical-answer question.

Step 1, count all interleavings. Eight operations in total, and choosing which four slots belong to T1 fixes the schedule, because each transaction then fills its own slots in order. C(8,4) = 70.

Step 2, find where conflicts can occur. X belongs only to T1 and Z only to T2, so no conflict can involve them. Only Y is shared: T1 touches it at its third and fourth operations, T2 at its first and second.

Step 3, split by direction. For T1→T2 we need w1(Y) before r2(Y) — T1's last operation before T2's first — so only the fully serial order T1, T2 qualifies: 1 schedule. Everything else that is conflict serialisable runs T2 before T1: 53 schedules.

Answer: 1 + 53 = 54. The model on this page enumerates all 70 interleavings, tests each one's graph, and reports 54.

Example 5 — the blind-write counterexample

T1: r1(A) w1(A). T2: w2(A). T3: w3(A). Consider S: r1(A) w2(A) w1(A) w3(A).

Conflicts. r1(A) before w2(A) gives T1→T2. r1(A) before w3(A) gives T1→T3. w2(A) before w1(A) gives T2→T1. w2(A) before w3(A) gives T2→T3. The graph has T1→T2 and T2→T1, so it has a cycle and S is not conflict serialisable.

Yet. In S, T1 reads A from the initial value, and T3 is the last writer. In the serial order T1, T2, T3, T1 also reads the initial value and T3 is also the last writer. Same reads-from relation, same final writer: S is view equivalent to a serial schedule.

The lesson. T2's write is a blind write — it never read A. That is what lets the order of T2's write be irrelevant to what anyone observes, and therefore what lets a cyclic schedule stay serialisable.

Example 6 — the same schedule under two-phase locking

Return to S1 of GATE 2014 Set 3, which is conflict serialisable. Could 2PL have produced it?

Spans. T1 accesses X at positions 0 and 8, so its lock on X spans 0 to 8. T3 accesses X only at position 2. T2's own spans are Y at 3 and Z at 4 to 6.

The overlap. T1 needs X across 0–8 while T3 needs X at 2. Whichever holds the lock, the other cannot be inside its own span. So no lock assignment can produce this interleaving, and 2PL cannot generate S1.

Conclusion. Conflict serialisable is necessary for a schedule to be 2PL-producible but not sufficient. The model reports the overlap on X between T1 and T3 and the fact that S1 is nevertheless acyclic.

Edge cases, boundaries, and the questions that turn on them

Each of these changes the answer while leaving the schedule looking familiar. They are the boundary conditions of the definitions on the Build-up tab.

A serial schedule is trivially serialisable

Its precedence graph has edges only in one direction along the execution order, so it cannot have a cycle. A question that includes "the serial schedules are also counted" is asking you not to exclude them: in the 2017 count, the single T1-before-T2 schedule is the fully serial one.

This is the difference between 53 and 54, and it is the most common single-mark loss in the chapter.

Duplicate conflicts collapse to one edge

If T1 and T2 conflict on three different items, the precedence graph still has one edge T1→T2. Counting conflicts and counting edges are different counts.

In GATE 2014 Set 3, S1 has several conflicting pairs but exactly three distinct edges. A cycle test on the deduplicated graph is what the theorem is about.

One transaction alone is always serialisable, and always recoverable

With a single transaction there is no other transaction to conflict with, no uncommitted value to read, and no cycle possible. Questions sometimes use this as a degenerate case to test whether you are applying a definition or a pattern.

The one thing that does not collapse: a single transaction can still deadlock if it re-locks an item it already holds, which is why lock upgrades are handled explicitly in real systems.

A cycle of length two is the common case, not the only one

Most exam schedules produce T1→T2 and T2→T1. But T1→T2→T3→T1 is equally fatal, and it is easy to miss if you only compare pairs.

Run a topological sort rather than scanning for mutual edges: if the sort does not consume every vertex, there is a cycle, of whatever length.

Recoverability is about commits, not about order of operations

Two schedules can differ only in where the two commits sit and have completely different recovery properties while sharing the same precedence graph. The graph sees reads and writes; recoverability sees commits.

This is why "conflict serialisable, therefore safe" is a wrong inference: serialisability and recoverability are properties of different things in the same schedule.

View serialisability without blind writes

For two transactions, if neither contains a blind write, view serialisability and conflict serialisability coincide. So a question that asks "is it view serialisable" and shows no blind write is asking the conflict question with different wording.

Check for a write with no preceding read of that item in the same transaction before you reach for the view test. If there is none, you do not need it.

Timestamp ordering and the equal-timestamp boundary

The tests are strict inequalities: a read is refused when ts(Ti) < W_TS(X), not when it is equal. Timestamps are unique in practice, so equality does not arise, but a question that writes ≤ is testing whether you know which side the boundary is on.

The Thomas write rule fires only on a write, only when ts(Ti) < W_TS(X), and only after the read test has already passed.

Strict 2PL is not the same as 2PL plus "strict"

2PL says: no acquisition after a release. Strict 2PL adds: no release until commit. The second is a restriction on when the shrinking phase starts, not a separate property of the schedule.

A schedule can be strict without being 2PL-producible and 2PL-producible without being strict. The two are independent constraints on different things.

Six beliefs that produce wrong answers, and the one-line correction for each

Each is stated as a learner would state it, then refuted with a minimal case rather than a paragraph.

1. "Serialisable means the transactions do not interleave."

Wrong. Serialisable means equivalent to some serial order, and the point of the whole chapter is that most serialisable schedules do interleave.

Minimal case: r1(X) w1(X) r2(Y) w2(Y) interleaves two transactions on two different items and is trivially serialisable, because they never conflict.

2. "Two reads of the same item conflict, since they both touch it."

Wrong. A conflict needs at least one write. Two reads leave the item unchanged, so their order cannot affect anything any transaction observes.

Minimal case: r1(X) r2(X) — no edge in either direction. Reverse the two operations and every reads-from relation is identical.

3. "Conflict serialisable and view serialisable are the same thing."

Wrong, and strictly. Conflict serialisable is contained in view serialisable, and the containment is proper whenever a blind write is present.

Minimal case: r1(A) w2(A) w1(A) w3(A) has a cycle and is still view equivalent to T1, T2, T3. Without the blind write by T2, no such example exists for two transactions.

4. "If the schedule is conflict serialisable, it is safe."

Wrong. Conflict serialisability says nothing about what happens after an abort. A conflict-serialisable schedule can still be non-recoverable if the commits sit in the wrong order.

Minimal case: w1(X) r2(X) c2 c1 — one transaction, two writes, no conflict at all, and T2 commits on a value that T1 then rolls back.

5. "Two-phase locking prevents deadlock, because it forces an order."

Wrong. 2PL forces the schedule to be conflict serialisable. It does nothing about two transactions each holding one lock and waiting for the other.

Minimal case: T1 locks X then requests Y; T2 locks Y then requests X. Both are in their growing phase, both are legal 2PL, and neither can proceed. Timestamp ordering is the protocol in the syllabus that avoids this by never waiting.

6. "Timestamp ordering is strictly better, since it cannot deadlock."

Wrong. It trades waiting for restarting. A transaction with a small timestamp can be aborted repeatedly, and the work it did is lost each time.

Minimal case: the trace in scene 9 — T1 with timestamp 10 reads X after T2 with timestamp 20 has written it, and must restart. Nothing waited; work was still lost.

The pair most often confused: recoverable and cascadeless

Both are about reading uncommitted data, and both are about commits, so they read as synonyms. They are not: recoverable compares the two commit points and permits the dirty read as long as the writer commits first; cascadeless forbids the dirty read outright.

One schedule separates them completely: w1(X) r2(X) c1 c2. T2 reads X before T1 commits, so it is not cascadeless; but T1 commits before T2 does, so an abort of T1 would still be recoverable. Recoverable yes, cascadeless no. Add the commit earlier — w1(X) c1 r2(X) c2 — and both hold, and the schedule is also strict.

How this topic is asked, and the procedure that answers each shape

Five shapes cover every item in this chapter that I checked. Each is the same graph computation with a different question attached.

Shape 1 — "which statement about these schedules is true?"

Two or three schedules, one statement each. Draw both graphs; do not compare the schedules line by line.

Seen as: GATE CSE 2014 Set 3 (S1 and S2 over three transactions). Procedure: one graph per schedule, then a cycle test on each.

Shape 2 — "which serial order is it conflict equivalent to?"

The graph has one topological order and the options are permutations. Compute the edges and read the order off.

Seen as: GATE CSE 2022. Procedure: deduplicate edges, then topologically sort. If the sort is not unique the question would be ill-posed, so a unique order is a useful self-check.

Shape 3 — "how many conflict-serialisable schedules?"

A numerical-answer question. Total interleavings is a binomial coefficient; the filter is the graph.

Seen as: GATE CSE 2017 Set 2, answer 54. Procedure: C(total operations, one transaction's count), then split by which transaction must precede which, then add. Include the serial schedules.

Shape 4 — "which protocol gives which guarantees?"

A multiple-select question listing properties. The answer is a set, and the wrong options are properties the protocol does not give.

Procedure: 2PL gives conflict serialisability only. Strict 2PL adds recoverability, cascadelessness and strictness. Timestamp ordering gives conflict serialisability and deadlock freedom, but not starvation freedom, and the Thomas rule weakens it to view serialisability.

Shape 5 — "which schedule(s) is/are conflict serialisable?"

Four candidate interleavings of the same two transactions, in a multiple-select question. The trap is a second, later conflict in the opposite direction.

Seen as: GATE CSE 2025 Set 2, answer B only. Procedure: for each option, scan every pair, not just the first conflict you notice — the second R1(X) after W2(X) is what creates the cycle in three of the four options.

The exam traps, ranked by how often they cost a mark

Forgetting that serial schedules count as conflict serialisable (53 instead of 54). Treating a read-read pair as a conflict. Answering "view serialisable" when the question said conflict, or the reverse. Assuming 2PL can produce every conflict-serialisable schedule. Reading "deadlock-free" as "better".

None of these is a knowledge gap. All five are a misread of which test was requested.

The procedure, in five steps

  1. Read what is asked. Conflict, view, recovery or locking — four tests, one schedule.
  2. Lay the schedule out as a table, one column per transaction and one row per position, so every conflict is a pair of cells in the same item.
  3. Add one edge per ordered pair of conflicting transactions, deduplicated, then run a topological sort.
  4. If the sort consumes every vertex, read the order off and answer. If not, name the cycle and answer.
  5. For counting or locking, switch to arithmetic: binomial coefficient then filter, or access spans then overlap.

Step 1 is the one that decides the mark. Steps 2 to 5 are mechanical.

Practice set — twelve questions

Six are previous-year items with their year and paper named; six are original practice written for this lesson and labelled as such. Answers are hidden until you reveal them, and each solution states why the wrong options are wrong.

Original practice Q1 (MCQ)

Which of these pairs of operations is not a conflict?

(A) r1(X) and w2(X)   (B) w1(X) and r2(X)   (C) w1(X) and w2(X)   (D) r1(X) and r2(X)

(D). Two reads leave the item unchanged, so their relative order cannot change any value anyone sees.

(A), (B) and (C) each contain at least one write on the same item by different transactions, which is exactly the definition.

GATE CSE 2014 Set 3 Q2 (MCQ, 2 marks)

With T1: r1(X); r1(Z); w1(X); w1(Z); T2: r2(Y); r2(Z); w2(Z); T3: r3(Y); r3(X); w3(Y), and S1, S2 as in Example 1, which statement is true?

(A) Only S1 is conflict serialisable. (B) Only S2 is conflict serialisable. (C) Both are. (D) Neither is.

(A). S1's graph is T2→T3, T3→T1, T2→T1 — acyclic, order T2, T3, T1. S2 adds T1→T2 on Z while T2→T1 survives, so it has a cycle.

(B) and (C) fail on that cycle. (D) fails because S1 has none. Sources disagree on whether this is Q25 or Q29 of the paper; the year, the set and the schedule agree.

GATE CSE 2016 Set 2 Q3 (MCQ, 1 mark)

Given a serialisable schedule S and its precedence graph, which ordering of the vertices is guaranteed to yield a serial schedule?

(A) Topological order   (B) Depth-first order   (C) Breadth-first order   (D) Ascending order of transaction indices

(A). A conflict-equivalent serial order must respect every edge, and respecting every edge is the definition of a topological order.

(B) and (C) respect no edges in general. (D) is unrelated to the conflicts — it may happen to work on a particular schedule, which is why it tempts.

GATE CSE 2017 Set 2 Q4 (NAT)

For T1: r1(X) w1(X) r1(Y) w1(Y) and T2: r2(Y) w2(Y) r2(Z) w2(Z), the total number of conflict-serialisable schedules is ______.

54. C(8,4) = 70 interleavings; 1 is equivalent to T1 then T2, 53 are equivalent to T2 then T1.

53 forgets the serial order T1, T2. 55 double-counts both serial orders. This page's model enumerates all 70 and reports 54 independently.

GATE CSE 2025 Set 2 Q5 (MSQ, 2 marks)

T1 is R1(X), W1(Y), R1(X), W1(X), COMMIT. T2 is W2(X), W2(Y), COMMIT. Which schedule(s) is/are conflict serialisable? (Each option is one interleaving of the same two transactions.)

(A) R1(X), W2(X), W1(Y), W2(Y), R1(X), W1(X)   (B) W2(X), R1(X), W2(Y), W1(Y), R1(X), W1(X)   (C) R1(X), W1(Y), W2(X), W2(Y), R1(X), W1(X)   (D) W2(X), R1(X), W1(Y), W2(Y), R1(X), W1(X)

(B) only. Every conflicting pair in (B) gives T2→T1 and no pair gives T1→T2, so the graph is acyclic.

(A) and (C) both contain the second R1(X) after W2(X), which adds T2→T1 while the first R1(X) already gave T1→T2 — a cycle. (D) has W1(Y) before W2(Y), giving T1→T2, alongside T2→T1 from X.

GATE CSE 2022 Q6 (MCQ, 2 marks)

For S: r4(X) r2(X) r3(X) r1(Y) w1(Y) w2(X) w3(Y) r4(Y), which serial schedule is conflict equivalent to S?

(A) T1→T3→T4→T2   (B) T1→T4→T3→T2   (C) T4→T1→T3→T2   (D) T3→T1→T4→T2

(A). Edges: T4→T2 and T3→T2 on X; T1→T3, T1→T4 and T3→T4 on Y. The unique topological order is T1, T3, T4, T2.

(B) reverses T3 and T4, contradicting T3→T4. (C) puts T4 first, contradicting T1→T4. (D) puts T3 first, contradicting T1→T3.

Original practice Q7 (MSQ)

Which of these does strict two-phase locking guarantee?

(A) Conflict serialisability (B) Recoverability (C) Cascadelessness (D) Freedom from deadlock

(A), (B) and (C). Strict 2PL holds every lock until commit, so no transaction reads or writes an uncommitted value — which is strictness, and strictness implies cascadelessness and recoverability. It is still 2PL, so it is conflict serialisable.

(D) is the wrong option: holding locks until commit makes deadlock more likely, not less. Deadlock freedom is timestamp ordering's contribution.

Original practice Q8 (NAT)

Two transactions have three operations each and act on the same two items. How many distinct interleavings are there?

20. Choosing which three of the six positions belong to T1 fixes the whole schedule, since each transaction keeps its own order: C(6,3) = 20.

720 = 6! counts all permutations of six operations, ignoring that each transaction's internal order is fixed. The binomial is always the right base case.

Original practice Q9 (MCQ)

The schedule w1(X) r2(X) c1 c2 is:

(A) not recoverable (B) recoverable but not cascadeless (C) cascadeless but not strict (D) strict

(B). T2 reads X before T1 commits, so it is not cascadeless. But T1 commits before T2 does, so an abort of T1 would still be recoverable.

(A) is wrong because the commits are in the right order. (C) and (D) are wrong because the read happened before T1's commit at all. Moving the commit earlier gives w1(X) c1 r2(X) c2, which is all three.

Original practice Q10 (MCQ)

Under timestamp ordering, T1 has timestamp 10 and T2 has timestamp 20. T2 has written X, so W_TS(X) = 20. T1 now issues r1(X). What happens?

(A) The read proceeds and R_TS(X) becomes 10. (B) The read is refused and T1 is aborted. (C) The read is silently ignored, as under the Thomas write rule. (D) T1 waits until T2 commits.

(B). The read test is ts(Ti) < W_TS(X): 10 < 20, so T1 would have to read a value written by a later transaction, which breaks timestamp order. It restarts.

(A) would silently violate timestamp order. (C) is the write rule, not the read rule, and applies only to writes. (D) is what a lock-based protocol would do; timestamp ordering never waits, which is why it cannot deadlock.

Original practice Q11 (MSQ)

For the schedule r1(A) w2(A) w1(A) w3(A), with T1: r1(A) w1(A), T2: w2(A), T3: w3(A), which statements are true?

(A) It is conflict serialisable. (B) It is view serialisable. (C) Its precedence graph has a cycle. (D) T2's write is a blind write.

(B), (C) and (D). The graph has T1→T2 and T2→T1, so (C) holds and (A) fails. T1 reads the initial value and T3 writes last, matching the serial order T1, T2, T3, so (B) holds. T2 never reads A, so (D) holds.

This is the standard witness that conflict serialisability is strictly stronger than view serialisability. Option (A) is the one to resist: a cycle and "not conflict serialisable" are the same statement.

Original practice Q12 (MCQ)

S1 of GATE 2014 Set 3 is conflict serialisable. Which is the correct statement about it?

(A) 2PL could produce it. (B) 2PL could not produce it, because T1 and T3 both need X over overlapping spans. (C) 2PL could not produce it, because it has a cycle. (D) 2PL could produce it only with a strict variant.

(B). T1 accesses X at positions 0 and 8, so its lock on X spans 0 to 8; T3 accesses X at position 2. Whichever transaction holds the lock, the other cannot be inside its own span.

(C) is a contradiction: S1 has no cycle. (A) and (D) fail for the same reason as (B) — no lock assignment exists, and strictness is a separate restriction that does not create one.

Revision sheet — definitions, decision rules, traps

One screen, no narrative. Everything here is derived on the Build-up tab and computed by the model on this page.

Definitions to state exactly

Conflict: same item, different transactions, at least one write. Three shapes only.

Conflict serialisable: precedence graph acyclic. The topological order is the equivalent serial schedule.

View serialisable: same reads-from relation, same final writer, same first reader per item, as some serial schedule. Strictly weaker than conflict serialisable; blind writes are what separate them.

Recoverable: reader's commit after writer's commit. Cascadeless: read only after the writer commits. Strict: read or write only after the last writer commits.

2PL: no acquisition after any release. Strict 2PL: no release before commit.

Decision rules

Conflict serialisable? Draw edges, run a topological sort. Sort consumes all vertices → yes.

View serialisable? Only ask if a blind write exists. Compare reads-from and final writer with each serial order.

Recoverable? Compare commit positions only. Cascadeless? Compare commit with read position. Strict? Compare commit with any access.

2PL-producible? Write each transaction's access span per item; any overlap between two transactions on the same item means no.

Counting? C(total, one transaction's count), then filter by the graph. Include serial schedules.

What each protocol buys

2PL: conflict serialisability. Not deadlock freedom. Not strictness.

Strict 2PL: conflict serialisability, strictness, cascadelessness, recoverability. Still deadlocks.

Timestamp ordering: conflict serialisability, deadlock freedom. Not starvation freedom. Aborts instead of waiting.

Timestamp ordering with Thomas write rule: the same, but only view serialisability is guaranteed, since an obsolete write is skipped rather than refused.

Five traps, five corrections

Read-read is not a conflict.

Serial schedules are counted; that is the 53-versus-54 difference.

Conflict serialisable does not imply recoverable — the graph does not see commits.

Conflict serialisable does not imply 2PL could produce it.

Deadlock-free is not the same as better: timestamps pay with restarts and possible starvation.

Three witnesses to keep in memory

View but not conflict: r1(A) w2(A) w1(A) w3(A) — cycle, still equivalent to T1, T2, T3, because T2's write is blind.

Conflict but not 2PL: S1 of GATE 2014 Set 3 — acyclic, but T1 and T3 both need X across overlapping spans.

Recoverable but not cascadeless: w1(X) r2(X) c1 c2 — the dirty read happened, but the commits are in the safe order.

One line to keep

Conflicts give edges; a cycle forbids a serial order; commits decide recovery; spans decide locking. Four questions, one schedule, four different things being read off it.

Where this research stopped

Five previous-year items were checked against published reproductions — two or more for each — and every answer was recomputed by the model on this page; none was checked against an original paper PDF. Items I could not pin to a year and a set are not reproduced here, and no question is presented as a previous-year item without both. The lesson does not cover multi-version concurrency control, snapshot isolation, validation-based (optimistic) protocols, logging and ARIES recovery, or isolation levels as defined in the SQL standard: the syllabus clause names "transactions and concurrency control", and those are either beyond it or belong to the recovery half of a full course. The schedules used are hand-sized, so no complexity claim is made about them; the counting routine enumerates 70 interleavings and would not be used at scale. The model's checks run on every load and are reported under the canvas, so a bug in it would be visible as a failing count rather than as a quiet error.
