Topic and objective

TOPIC: The entity-relationship model and its mapping to the relational model — Section 9 of the GATE CSE 2027 syllabus, whose first item is the single word "ER-model". Entity sets, attribute kinds, relationship sets and degree, cardinality ratios, participation constraints, weak entity sets and identifying relationships, specialisation and generalisation, and the rules that turn all of it into tables.

LEARNING OBJECTIVE: Read an ER diagram and say what each shape means. Count the relationship instances a cardinality ratio allows, by enumeration rather than by memory. Tell a cardinality ratio apart from a participation constraint, and say which one decides nullability. Decide when a weak entity's key is complete and when it is not. Run the mapping rules in the right order, get the number of tables, and justify each table by the rule that produced it.

I read the syllabus item "ER-model" as design plus mapping: the constructs a diagram may use, and the procedure that converts the diagram into relations. The relational algebra, tuple calculus and SQL that follow it in the same sentence belong to the relational-model lesson, which this one feeds.

Prerequisites

  • Sets and set operations — an entity set is a set, a relationship set is a set of tuples, and a table is a set of rows. The vocabulary of membership, subset and Cartesian product is used on every tab.
  • Relations and their properties — a binary relationship is a relation on two sets, so cardinality ratios are statements about a relation's structure.
  • Relational algebra, tuple calculus and SQL — the target of the mapping. Read it after this lesson, not before; it assumes tables already exist.
  • Functional dependencies and normal forms — why a multivalued attribute cannot be a column, and why a bad mapping produces a table that is not in third normal form.
  • No programming is needed anywhere in this lesson.

Six sentences worth keeping

  • Shapes. Rectangle entity, capsule attribute, diamond relationship; a double border means weak, on the rectangle and on the diamond alike.
  • Ratio. 1:1, 1:N, M:N limit how many partners an entity may have. They do not promise any.
  • Participation. Total means every entity appears; it is what lets a merged key be NOT NULL.
  • Weak. The partial key identifies nothing; the owner key plus the partial key identifies everything.
  • Mapping. Strong entity, weak entity, M:N, multivalued — those four make tables. 1:1 and 1:N make foreign keys.
  • Count. Justify each table by the rule that produced it, and never let participation change the count.

1. Intuition — the architect's sketch, not the building

An architect does not start by ordering bricks. She draws the building: rooms, the doors between them, and the rule that every room must have at least one door. Only afterwards does a builder turn the drawing into walls with thickness, because thickness is a fact about walls and not about rooms. Educational interpretation The ER model is the drawing and the relational model is the building. A room is an entity set. A door is a relationship set. "Every room has a door" is a participation constraint. And "two rooms share one door, but a door belongs to at most one pair of rooms" is a cardinality ratio.

The reason the drawing exists is that some things a designer needs cannot be said in a table. A reader with three phone numbers has no single row; a book's copies are numbered per book and not globally; a person may be both a student and a member of staff. The ER model lets you state all three, and the mapping rules then decide where each fact has to live. Every GATE question in this topic is either "what does this shape mean" or "where does this fact end up, and therefore how many tables".

2. Entity set and entity

An entity is a thing the database must describe. An entity set is a set of entities of the same kind — all readers, all books — drawn as a rectangle. A weak entity set is one whose entities cannot be distinguished without an owner, drawn as a double rectangle.

Mathematical derivation Because an entity set is a set, its members are distinct, so at least one attribute must be unique within it. That is why every strong entity set needs a key, and why a weak entity set — which has no such attribute — must borrow one. The requirement is not a convention; it follows from the word "set".

3. Four kinds of attribute

Simple: one value, one column. Composite: has parts (address = street, city, pin), drawn as a capsule with sub-capsules, and flattened into one column per part. Multivalued: may hold several values for one entity (phone), drawn with a double capsule, and given its own table. Derived: computed from others (age from date of birth), drawn dashed, and not stored at all.

Mathematical derivation Only the multivalued kind forces a table, and the reason is first normal form: a relational cell holds one atomic value. The page counts seven phone values for four readers with a maximum of three in one cell, so a flattened column would violate 1NF on the third value, not on some abstract principle.

4. Relationship set, degree, and its attributes

A relationship set is a set of associations among entities, drawn as a diamond. Its degree is the number of entity sets it connects: two is binary, three is ternary. It may carry attributes of its own, and it may have a key when it connects a weak entity to its owner — then it is an identifying relationship, drawn with a double diamond.

Verified fact GATE CSE 2005 asked where the rent for a room belongs when persons lodge in rooms many-to-many, and the answer is the relationship, not either entity: rent depends on the person and the room together. Mathematical derivation If the pair is M:N, a rent column on either entity would have to hold several values, which is the same 1NF failure as a multivalued attribute.

5. Cardinality ratio — and how many instances it allows

The cardinality ratio limits partners. 1:1: at most one on each side. 1:N: an entity on the one side may have many partners, an entity on the many side at most one. M:N: no limit. It is a limit, never a promise.

M:N → 2mn  ·  1:N → (m+1)n  ·  1:1 → Σk C(m,k)C(n,k)k!m and n are the numbers of entities on the two sides. The grid has mn cells, one per possible pair, and a relationship instance is a choice of cells — so there are 2^(mn) choices before any constraint bites.

Mathematical derivation The page enumerates all 2mn subsets, filters them by the constraint, and compares the total with the formula: 64, 13 and 256 all agree. That agreement is what makes the formula trustworthy, and it is also how you can tell you have used the right power.

6. Participation — total and partial

Total participation means every entity of that set appears in at least one pair; drawn as a double line. Partial means some may appear in none; a single line. The same information is written (min, max) in some books, where min = 1 is total and min = 0 is partial.

Mathematical derivation Participation is a constraint on the number of entities used, and cardinality is a constraint on the number of partners per entity. On two entities against three, a 1:N allows 27 instances; making the many side total cuts that to 8. Same ratio, same sizes, different constraint, different count.

7. Weak entity sets

A weak entity set has no key of its own. Its entities are identified by an owner entity together with a partial key, which is underlined with a dashed line. The relationship to the owner is the identifying relationship. Copy is the standard example: copy numbers restart for every book, so copy_no alone says nothing.

Mathematical derivation Three books with two copies each give six rows and only two distinct copy numbers: four collisions. The composite key (isbn, copy_no) gives six rows and six keys, no collisions. The collision count is what "no key of its own" means, stated numerically. Verified fact GATE CSE 2024 Set 2 asks which set must participate totally in the identifying relationship, and the answer is the weak set only: a book with no copies is still a book, but a copy with no book has no key.

8. Specialisation, generalisation, aggregation

A specialisation puts subclasses under a superclass, each inheriting its attributes: Student and Faculty under Person. Generalisation is the same diagram read upwards. Two independent flags describe it: total (the subclasses cover every superclass entity) or partial, and disjoint (no entity in two subclasses) or overlapping. Aggregation treats a relationship as an entity, so that it can itself take part in a relationship.

Mathematical derivation Two flags give four cases, not two, which is why the mapping has three strategies rather than one: a superclass table plus one per subclass; a single table with a discriminator; or one table per subclass with the inherited attributes copied. The third needs total and disjoint.

9. The mapping rules, in one place

These are the standard textbook rules, and the numbering below is the order that avoids rework — each rule either makes a table or adds a key to a table that already exists.

1 strong entity → table, key underlined
2 weak entity → table, key = owner key + partial key
3 1:1 → foreign key on the total side
4 1:N → foreign key on the many side
5 M:N → table, key = both keys
6 n-ary → table, key = all keys
7 multivalued → table, key = owner key + valueComposite attributes are flattened by rule 1. A derived attribute is never stored. An identifying relationship is never mapped on its own — its contribution is inside the weak entity's key.

Verified fact The seven rules are the standard ER-to-relational procedure of the database texts (Elmasri and Navathe; Silberschatz, Korth and Sudarshan). The order shown here is this lesson's arrangement of them.

10. What "minimum number of tables" is asking

The question asks for the smallest set of relations that carries every fact of the diagram without redundancy. It is not a fixed property of the picture: it depends on whether the relationships carry attributes, and on which specialisation strategy the question permits.

tables = strong entities + weak entities + M:N relationships + multivalued attributesParticipation never appears in this sum. Neither does a 1:1 or a 1:N relationship. Adjust only for the specialisation strategy and for n-ary relationships.

Mathematical derivation For the library schema the sum is 3 + 1 + 1 + 1 = 6, and the page's mapper returns exactly those six tables. Three past papers — 2015 Set 1, 2008 and 2005 — are run through the same mapper and return 4, 3 and 3, matching their keys.

11. The chain of dependencies this lesson sits in

Sets and relations (sets) give you the vocabulary; a relationship is a relation (relations); the ER model states the design; the mapping produces tables; the tables are then queried in relational algebra and SQL (relational model) and checked for redundancy in normal forms (normal forms). A bad ER design shows up later as a table that cannot be normalised, which is why the mapping is examinable and not clerical.

One diagram, mapped end to end: the library schema

Four entity sets, three relationship sets, one multivalued attribute. Each step below is what the page's mapper actually does, and each result is checked against the definition that produced it.

The diagram, in words

Reader (key rid; name; composite address = street, city, pin; multivalued phone). Book (key isbn; title; price). Branch (key bid; bname). Copy — weak under Book, partial key copy_no, attribute condition.

Relationships: Borrows M:N between Reader and Copy with attribute since; Keeps 1:N from Branch to Copy, total on Copy; Manages 1:1 between Reader and Branch, total on Branch.

Step 1 — the four entity tables

Reader(rid, name, street, city, pin). Book(isbn, title, price). Branch(bid, bname). Copy(isbn, copy_no, condition) with key (isbn, copy_no).

Mathematical derivation The composite address contributes three columns and no table. Copy's key is two columns because its owner's key is one and its partial key is one. Four entity sets, four tables — and the weak one is still an entity set.

Step 2 — Keeps and Manages become columns

Keeps is 1:N, so the one side's key joins the many side: bid goes into Copy. Manages is 1:1 with Branch total, so Reader's key joins Branch: rid goes into Branch. Neither relationship makes a table.

Mathematical derivation Both new columns are NOT NULL, because Copy is total in Keeps and Branch is total in Manages. In the sample data that is 5 copies and 3 branches with zero nulls. If either participation were partial, the same column would have to admit nulls.

Step 3 — Borrows is a table, and phone is a table

Borrows(rid, isbn, copy_no, since), key rid + isbn + copy_no. Reader_Phone(rid, phone), key rid + phone.

Mathematical derivation The M:N relationship cannot be folded into either side: folding it into Reader would keep one copy per reader and silently drop the rest. The page computes the loss — 3 pairs kept, 2 lost — which is precisely the information the third table preserves.

Step 4 — the count and the check

Six tables: Reader, Book, Branch, Copy, Borrows, Reader_Phone. The sum is 3 strong entities + 1 weak entity + 1 M:N relationship + 1 multivalued attribute.

Mathematical derivation Rejoining Borrows to Copy on (isbn, copy_no) recovers the universal relation exactly — all five rows of the sample, with the owning branch read through Copy. So the decomposition is lossless. The page also runs the wrong mapping and shows the two rows it loses. Both checks are registered in the model and their results are printed under the canvas.

Where each rule stops being safe

A rule applied outside its condition is a trap. Each card names the condition and says what breaks when it fails, with the number that shows the size of the break.

A relationship with attributes cannot always be folded

The 2008 question works because R1 has no attributes. Give R1 a date and the fold is no longer free: the date must live somewhere, and the many side already has its own row per entity.

Mathematical derivation If the many side may have several partners, the attribute has one value per pair, not one per entity — so it needs a table. This is the same argument as the 2005 rent question, applied to a different diagram.

1:1 with total participation on both sides forces equal sizes

A 1:1 relationship with total participation on both sides is a perfect matching, so it can exist only when the two sets have the same size. On 3 and 2 entities the enumeration returns zero instances.

Mathematical derivation Total on both sides means every entity of each set is used; injective on both sides means each used entity pairs with a distinct one. So the two counts must be equal. Total on one side only is P(3,2) = 6, which is why most 1:1 designs are total on one side.

Specialisation strategy C is the one that breaks silently

Keeping only subclass tables and copying the inherited attributes works only when the hierarchy is total and disjoint. Drop either condition and rows duplicate or disappear.

Mathematical derivation With one person in both Student and Faculty, three persons produce four rows: the identity is stored twice and the primary key pid now appears twice across the two tables, so no single table can enforce it. Strategies A and B do not fail on that diagram at all.

The minimum can be larger than the diagram suggests

"Minimum" means minimum subject to the constraints the question states. If it says all relations must be in 3NF, a fold that would create a partial dependency is not allowed, and the count rises.

Mathematical derivation GATE CSE 2015 Set 1 Q38 states 3NF in the question. The model's count of 4 agrees with the key, and each of the four relations has a key that determines all its attributes, so no partial dependency survives.

A ternary relationship is not two binary ones

Supplies(Supplier, Part, Project) with a quantity means one quantity per triple. Two binary relationships cannot express that: they would allow a quantity per pair, and three pairs per triple.

Mathematical derivation Degree 3 maps to one table whose key is all three keys, so the number of rows is the number of triples, not the number of pairs. Replacing it with two binary relationships changes the count of tables and the meaning of the data.

A counterexample to "a mapping that runs is a mapping that is correct"

Fold the many-to-many Borrows into Reader, keeping one copy per reader. The schema is valid, every column has a type, every key is declared, and the tables load without error. And two of the five borrow rows are gone.

Mathematical derivation The page computes both versions: the correct mapping rejoins to exactly the five universal rows, the folded mapping keeps 3 and loses 2. The test is not "does it run" but "does rejoining recover the original relation" — and a lossy decomposition is the only failure mode that does not announce itself.

Six beliefs that cost marks, and the smallest thing that corrects each

Each entry gives the belief as it is usually held, the correction, and the smallest check that settles it.

1. "Cardinality and participation are the same question."

Correction. Cardinality limits partners per entity; participation says whether an entity must appear at all. One is a maximum, the other a minimum.

Check. Two entities against three, 1:N: 27 instances with partial participation, 8 with the many side total, 12 with the one side total, 6 with both. Mathematical derivation Four different counts from one diagram.

2. "The foreign key goes on the one side of a 1:N."

Correction. It goes on the many side, because that is the side that has at most one partner and can therefore store one value. On the one side it would have to hold several values.

Check. Keeps is 1:N from Branch to Copy, and the page puts bid in Copy. Put it in Branch instead and the column must hold 5 values across 3 rows.

3. "A weak entity's key is its partial key."

Correction. The partial key identifies nothing. The key is the owner key together with the partial key.

Check. Six copies, two copy numbers, four collisions; with isbn added, six keys and no collisions. Mathematical derivation A key that admits collisions is not a key.

4. "The identifying relationship needs its own table."

Correction. It does not. Its contribution is the owner's key, which becomes part of the weak entity's key and a foreign key of its table.

Check. In the 2008 item, counting R2 separately gives 4 instead of the key's 3. In the library schema it would give 7 instead of 6.

5. "A double border always means a weak entity."

Correction. A double rectangle is a weak entity set, a double diamond is an identifying relationship, and a double capsule is a multivalued attribute. The shape matters as much as the border.

Check. Verified fact GATE CSE 2020 Q14 asks which shape represents the supporting many-one relationship of a weak entity set, and the answer is the diamond with a double or bold border — not the rectangle. That is the whole content of the question.

6. "More participation means more tables."

Correction. Participation never changes the number of tables. It changes whether a merged foreign key may be null, and which side of a 1:1 receives it.

Check. Make Copy's participation in Keeps partial and the table count is still six; only the NOT NULL declaration changes. Mathematical derivation The count formula has no participation term in it.

Closely confused pairs, side by side

Weak entity versus multivalued attribute. Both are drawn with a doubled shape and both produce a table, so they are routinely merged in memory. A weak entity has its own attributes and a partial key and is identified through an owner; a multivalued attribute is one property of one entity. Copy has a condition and a copy number; phone has nothing but a value.

Composite versus multivalued attribute. A composite attribute has parts, not repetitions: address is street, city and pin, and it flattens into three columns. A multivalued attribute has repetitions of one value and needs a table. Neither becomes the other, however many parts or values it has.

1:N versus N:1. The same diagram, read in two directions. "1:N from Branch to Copy" and "N:1 from Copy to Branch" are the same constraint; what changes is the sentence, not the foreign key. GATE words the merge question as "many-to-one from A to B", which puts the key in A.

Entity versus attribute. If the thing has its own attributes or takes part in its own relationships, it is an entity; otherwise it is an attribute. City as a name is an attribute of Reader; City with a population and a mayor is an entity, and the design changes with it.

Total participation versus exactly one partner. Total participation says at least one, never exactly one. It becomes exactly one only when combined with a cardinality limit of at most one — which is precisely the reasoning in GATE CSE 2018 Q11, where many-to-one plus total gives exactly one.

How this topic is actually asked

The shapes below are drawn from the papers named, each with its year and question number. The paper does not label questions by syllabus heading, so the grouping is mine and rests on what each question tests. Nothing here is a forecast of the 2027 paper.

Shape 1 — the table count

A small diagram, sometimes with one weak entity, and a request for the minimum number of tables, or for the attribute set of one table. The work is the mapping rules plus the two conditions: does the relationship have attributes, and does the question demand a normal form.

Verified fact GATE CSE 2015 Set 1 Q38 (four relations), GATE CSE 2008 Q82 (three tables, and the attribute set {M1,M2,M3,P1}), GATE CSE 2005 Q15 (three tables). All three are reproduced by this page's mapper.

Shape 2 — the condition under which a merge is safe

A relationship with no attributes, two entities, and four combinations of cardinality and participation. The work is to see that the foreign key must be single-valued (many-to-one) and non-null (total).

Verified fact GATE CSE 2017 Set 2 Q17 — the answer is many-to-one with total participation of A, option C. The reasoning is the null argument: partial participation would leave the merged column empty for some rows.

Shape 3 — read a statement off the diagram

A described relationship and a claim about which entities must be associated with how many. The work is to combine the cardinality limit with the participation minimum and say what follows.

Verified fact GATE CSE 2018 Q11 — many-to-one from E1 to E2, both total, |E1| > |E2|; the true statement is that every entity of E1 is associated with exactly one entity of E2 (option A). The page checks it over all six instances of a 2-by-3 version.

Shape 4 — the notation question

Which shape represents a construct. One line to answer if you know the notation, and unanswerable otherwise, because the options are four shapes rather than four meanings.

Verified fact GATE CSE 2020 Q14 — the supporting many-one relationship of a weak entity set is drawn as a diamond with a double or bold border. The option order differs between reproductions of the paper, so the answer is stated by content.

Shape 5 — the definitional statement about weak sets

A four-way statement about who must participate totally in the identifying relationship. The work is one line of reasoning: the weak side cannot exist without a key, the owner can exist without dependants.

Verified fact GATE CSE 2024 Set 2 — the weak entity set must have total participation in the identifying relationship (option A). GATE CSE 2024 Set 1 also carried an ER item, asking which of four diagrams correctly represents a written specification.

MCQGATE CSE 2024 Set 2

In the context of owner and weak entity sets in the ER model, which one of the following statements is TRUE?

  1. The weak entity set MUST have total participation in the identifying relationship
  2. The owner entity set MUST have total participation in the identifying relationship
  3. Both weak and owner entity sets MUST have total participation in the identifying relationship
  4. Neither weak entity set nor owner entity set MUST have total participation in the identifying relationship

Answer: A — the weak entity set must have total participation

A weak entity's key is incomplete without its owner, so it cannot exist unowned. The owner can exist with no weak entities at all: a book with no copies is still a book.

Why B fails. A department with no dependants is legal; requiring total participation of the owner would forbid it. Why C fails. It inherits B's error. Why D fails. Without the weak side's total participation the composite key would have a null part, which is no key at all.

The trap. The diagram is asymmetric and the sentence is symmetric-looking. Ask which side loses its identity if it is removed.

MCQGATE CSE 2017 Set 2 Q17

An ER model of a database consists of entity types A and B. These are connected by a relationship R which does not have its own attribute. Under which one of the following conditions can the relational table for R be merged with that of A?

  1. R is one-to-many and the participation of A in R is total
  2. R is one-to-many and the participation of A in R is partial
  3. R is many-to-one and the participation of A in R is total
  4. R is many-to-one and the participation of A in R is partial

Answer: C — many-to-one, with total participation of A

Merging R into A replaces R by a single column of A holding the key of B. That column can hold one value, so each A entity may have at most one B partner — which is many-to-one from A. Total participation means every A row has a partner, so the column is never empty.

Why A and B fail. One-to-many would give an A entity several B partners, so one column cannot hold them. Why D fails. Many-to-one is right, but partial participation leaves some A rows with no B, so the column must admit nulls — a nullable foreign key is not the clean merge the question asks for.

The trap. The question asks which condition can permit the merge. Both halves are necessary: many-to-one alone is not enough, and total participation alone is not enough.

MCQGATE CSE 2018 Q11

In an ER model, suppose R is a many-to-one relationship from entity set E1 to entity set E2. Assume that E1 and E2 participate totally in R and that the cardinality of E1 is greater than the cardinality of E2. Which one of the following is true about R?

  1. Every entity in E1 is associated with exactly one entity in E2
  2. Some entity in E1 is associated with more than one entity in E2
  3. Every entity in E2 is associated with exactly one entity in E1
  4. Every entity in E2 is associated with at most one entity in E1

Answer: A — exactly one partner for each E1 entity

Many-to-one from E1 to E2 means each E1 entity has at most one E2 partner. Total participation means each has at least one. At most one and at least one give exactly one.

Why B fails. That is precisely what many-to-one forbids. Why C and D fail. Since |E1| > |E2| and every E1 entity must be used, some E2 entity must serve several E1 entities — so an E2 entity can have more than one partner. The page enumerates the 2-by-3 case and finds the largest E2 load is at least 2 in every instance.

The trap. "Many-to-one" constrains the many side only. It says nothing about the one side except that it may serve many.

NATGATE CSE 2015 Set 1 Q38

Entity sets E1 and E2 are connected by an m:n relationship R12. E1 and E3 are connected by a 1:n relationship R13, with 1 on the side of E1 and n on the side of E3. E1 has attributes a11 (key) and a12; E2 has a21 (key) and a22; E3 has a31 (key) and a32. The relationships have no attributes. If a relational model is derived, the minimum number of relations, all in 3NF, is ______.

Answer: 4

E1, E2 and E3 give three tables. R12 is m:n, so it is a fourth table keyed by (a11, a21). R13 is 1:n with the 1 on E1's side, so E3 — the many side — takes a11 as a foreign key, and R13 makes no table.

The relations. E1(a11,a12), E2(a21,a22), E3(a31,a32,a11), R12(a11,a21). The page's mapper produces exactly these four.

Why 3 is wrong. It folds R12, which would lose the pairs. Why 5 is wrong. It maps R13 separately, which is redundant because a11 in E3 already says everything R13 says.

The trap. "1:n with 1 on the side of E1" fixes which side receives the key. Read the direction, not just the ratio.

MCQGATE CSE 2008 Q82

A diagram has strong entity sets M (M1 key, M2, M3) and P (P1 key, P2), a weak entity set N (partial key N1, attribute N2) owned by P through identifying relationship R2, and a many-to-one relationship R1 from M to P with M participating totally. R1 and R2 have no attributes. The minimum number of tables needed to represent M, N, P, R1, R2 is

  1. 2
  2. 3
  3. 4
  4. 5

Answer: B — 3

M and P are strong: two tables. R1 is many-to-one from M with M total and has no attributes, so P1 becomes a column of M and R1 makes no table. N is weak, so it takes P1 into its key and R2 makes no table. M(M1,M2,M3,P1), P(P1,P2), N(P1,N1,N2) — three tables.

Why 4 appears. Mapping R1 separately, which is redundant once P1 sits in M. Why 5 appears. Mapping R2 separately as well. Why 2 is impossible. N cannot be merged into P, because P has one row per book and N has many per owner.

The companion question on the same diagram asks for a correct attribute set of one table, and the answer is {M1, M2, M3, P1} — which is the M table the page's mapper produces.

MCQGATE CSE 2020 Q14

Which one of the following is used to represent the supporting many-one relationships of a weak entity set in an entity-relationship diagram?

  1. Diamonds with double/bold border
  2. Rectangles with double/bold border
  3. Ovals with double/bold border
  4. Ovals that contain underlined identifiers

Answer: A — diamonds with a double or bold border

The question asks about the relationship, so the shape is the diamond. The identifying relationship is drawn with a doubled diamond, while the weak entity set itself is the doubled rectangle.

Why B appears. The doubled rectangle is the weak entity set, not its relationship — the commonest wrong answer, because "double border" is strongly associated with weakness. Why C appears. A doubled oval is a multivalued attribute. Why D appears. An oval with an underlined identifier is a key attribute.

Note on the option order. Some reproductions of this paper list the rectangle first, so the letter differs between archives; the answer content does not.

MCQGATE CSE 2005 Q15

Let E1 and E2 be two entities in an ER diagram with simple single-valued attributes. R1 and R2 are two relationships between E1 and E2, where R1 is one-to-many and R2 is many-to-many. R1 and R2 do not have attributes of their own. What is the minimum number of tables required to represent this situation in the relational model?

  1. 2
  2. 3
  3. 4
  4. 5

Answer: B — 3

E1 and E2 are two tables. R1 is one-to-many and has no attributes, so its key joins the many side: no table. R2 is many-to-many, so it is the third table, keyed by both keys.

Why 4 appears. Mapping R1 separately. Why 2 appears. Folding R2, which would lose the pairs. Why 5 appears. Both mistakes at once.

The trap. Two relationships between the same two entity sets are two independent decisions. The fact that they share endpoints changes nothing.

MCQGATE CSE 2005

Consider the entities 'hotel room' and 'person' with a many-to-many relationship 'lodging'. If we wish to store information about the rent payment to be made by persons occupying different hotel rooms, then this information should appear as an attribute of

  1. Person
  2. Hotel Room
  3. Lodging
  4. None of these

Answer: C — Lodging

Rent depends on the person and the room together. As an attribute of Person it would have one value across many rooms; as an attribute of Room it would have one value across many persons.

Why A and B fail. Both would require a cell to hold several values for one entity, which is the 1NF failure this lesson counts on the second scene. Why D fails. Lodging is a perfectly good home for it, and the mapped table is exactly Lodging(person, room, rent).

The trap. The word "payment" suggests a person owns it. The dependency, not the wording, decides where it goes.

MCQGATE CSE 2012

Given the basic ER and relational models, which one of the following is INCORRECT?

  1. An attribute of an entity can have more than one value
  2. An attribute of an entity can be composite
  3. In a row of a relational table, an attribute can have more than one value
  4. In a row of a relational table, an attribute can have exactly one value or a NULL value

Answer: C — that statement is incorrect

The ER model allows multivalued attributes; the relational model does not, because a relation must be in first normal form. So A and B are true of the ER model, D is true of the relational model, and C is false.

Why A is not the answer. It is true: a reader may have three phone numbers. Why D is not the answer. One value or NULL is exactly what 1NF permits. Why C is the answer. It is the one sentence that describes the ER model and applies it to a table.

The trap. This question is the reason the multivalued attribute becomes a table rather than a column, and the page counts the seven values that would otherwise sit in four cells.

NATOriginal practice question

Written for this lesson. A diagram has three strong entity sets Supplier, Part and Project, each with a single-attribute key. It also has a ternary relationship Supplies among all three, carrying attribute quantity, and a multivalued attribute phone on Supplier. How many tables does the mapping produce?

Answer: 5

Three strong entities give three tables. The ternary relationship gives one table keyed by all three keys. The multivalued attribute gives one table keyed by (supplier key, phone). Three plus one plus one is five.

Why 4 appears. Forgetting the multivalued attribute. Why 6 appears. Replacing the ternary relationship by two binary ones, which also changes the meaning: quantity would then be per pair rather than per triple.

The trap. A ternary relationship is one table with three key columns, not two tables. Degree is not the number of tables.

MSQOriginal practice question

Written for this lesson. Relationship R between A and B is 1:1 and has no attributes. Which of the following are sufficient to merge R into A's table without introducing a nullable column?

  1. A participates totally in R
  2. B participates totally in R
  3. R is 1:1 and both sides are partial
  4. R has an attribute of its own

Answer: A

For a 1:1, the key can go on either side, so the choice is decided by participation. If A is total, every A row has a partner and the merged column is never null. If only B is total, the key belongs in B instead — the merge into A would then need nulls.

Why B is not sufficient. It justifies merging into B, not into A. Why C fails. Both partial means the column must admit nulls on whichever side you choose. Why D fails. An attribute of R forces a table of its own; that is the 2008 lesson, not a merge.

The trap. The question fixes the target table. Total participation is only sufficient for the side that is total.

MSQOriginal practice question

Written for this lesson. Which of the following statements are true of a weak entity set W owned by O through identifying relationship I?

  1. W's table has the key of O as part of its primary key
  2. I contributes no table of its own
  3. W's key alone determines all of W's attributes
  4. O must participate totally in I

Answer: A and B

W's key is O's key plus W's partial key, and I is folded into W's table as a non-nullable foreign key.

Why C fails. The partial key alone collides — six copies, two copy numbers, four collisions in the page's count. Why D fails. O may exist with no weak entities; only W must be total, which is the 2024 Set 2 answer.

The trap. A and B are the two facts that decide the table count; C and D are the two that misstate the definition.

The revision sheet

Definitions, the notation, the mapping table, the decision procedure and the traps — one screen, to be read the night before.

Notation

Rectangle: entity set. Double rectangle: weak entity set. Capsule: attribute. Double capsule: multivalued attribute. Dashed capsule: derived attribute. Underlined name: key. Dashed underline: partial key. Diamond: relationship set. Double diamond: identifying relationship. Double line: total participation. Single line: partial.

Verified fact The doubled diamond is examinable content in its own right — GATE CSE 2020 Q14 asks for exactly that shape.

Definitions, in one line each

Entity set: entities of one kind. Relationship set: associations among entities, with a degree. Cardinality ratio: the maximum number of partners per entity. Participation: whether every entity appears at least once. Weak entity set: no key of its own. Identifying relationship: the relationship to its owner. Specialisation: subclasses under a superclass, each either total or partial and either disjoint or overlapping.

Mathematical derivation Every definition above is a constraint on a set of tuples, which is why each one maps to a declaration: a key, a foreign key, NOT NULL, or a table.

The mapping table

strong entity → table, key = key attribute
weak entity → table, key = owner key + partial key, owner key NOT NULL
composite attribute → one column per part, no table
multivalued attribute → table, key = owner key + value
derived attribute → not stored
1:1 → foreign key on the total side (either side if both total), nullable if that side is partial
1:N → foreign key on the MANY side, NOT NULL if the many side is total
M:N → table, key = both keys, relationship attributes here
n-ary → table, key = all keys
ISA A → superclass table + one per subclass
ISA B → one table with a discriminator
ISA C → one per subclass with inherited attributes, needs total AND disjoint

Mathematical derivation Read the middle column as the count: table, no table. Strong, weak, M:N and multivalued make tables. 1:1, 1:N, composite and derived do not. For the library schema that is 3 + 1 + 1 + 1 = 6, which is what the mapper returns.

The decision procedure

  1. Read participation: single line partial, double line total.
  2. Read the cardinality and say which side is the one side.
  3. Look for a weak entity: double rectangle, partial key, owner.
  4. Look for multivalued attributes and for an ISA hierarchy.
  5. Count and justify each table; check participation changed nothing.

Three numbers to remember, and where they come from

6 — the library schema: 3 strong + 1 weak + 1 M:N + 1 multivalued.

4, 3, 3 — the 2015 Set 1, 2008 and 2005 keys, reproduced by the same mapper.

64, 13, 256 — the instance counts for M:N on 3-by-2, 1:1 on 3-by-2, and 1:N on 3-by-4, each enumerated and each matched to its closed form.

If you remember only five sentences

A relationship attribute belongs to the pair, and a many-to-many pair with an attribute is a table. A foreign key goes on the many side of a 1:N and on the total side of a 1:1. A weak entity's key is the owner's key plus the partial key, and the identifying relationship is never a table. Participation decides nullability, never the table count. And a mapping that runs is not a mapping that is correct — rejoin it and check.

Educational interpretation The five sentences cover every past item quoted in this lesson except the notation question, which the notation card answers.

What is computed rather than cited

The page enumerates relationship instances over the grid of pairs and compares each count with its closed form (64, 13, 256, 27, 8, 12, 6, and the inclusion–exclusion count for M:N with both sides total). It maps the library schema and three past-paper schemas with the same code, returning 6, 4, 3 and 3 tables, and checks each table's key and foreign keys. It counts the weak-key collisions with and without the owner's key (4 against 0). It rejoins the mapped tables and compares the result with the universal relation, then runs the wrong mapping and counts what that loses (2 rows). It counts the nulls that total and partial participation produce (0 and 2). And it counts the rows strategy C duplicates under an overlapping hierarchy (4 for 3 persons). All of it is registered as model checks, and the number passing is printed under the canvas.
