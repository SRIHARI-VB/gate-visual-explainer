Topic and objective

TOPIC: System calls — the boundary between user mode and kernel mode, the trap that crosses it, and the four calls (fork, execve, exit, wait4) that run a program. This is the item "System calls", the first phrase of Section 8 of the official GATE 2027 CS syllabus.

LEARNING OBJECTIVE: Given a call, say whether it crosses the privilege boundary and what it changes when it does. Follow one read from the call number in a register to the handler the kernel selects and back to the return value. Decide which of a list of events guarantees a transition to kernel mode. Count the system calls a buffered print run actually makes, and count the copies of an unflushed buffer that fork leaves behind. Sort the attributes execve preserves from the ones it replaces. Read a descriptor table and an open file description as two different objects, and answer a shared-offset question exactly.

I read this topic as one boundary plus two tables. The boundary is the mode bit and the trap instruction; the first table is the kernel's system-call table, indexed by a number; the second is the process's descriptor table, whose entries point at open file descriptions the kernel owns. Almost every exam question here is a question about which of those three things a call touches.

  • Counting processes after fork. The 2n rule and the 2n − 1 children rule are taught there. Here they are only a subroutine: scene 10 adds wait to the same program.
  • Stack frames and the program counter. A call pushes a return address; a trap saves the program counter and status word. Built in Functions, scope and lifetime.
  • stdio and the C library. That printf is a library function and write is a call into the kernel. Built in C fundamentals; the buffering rules are derived here.

The five ideas to leave with

  1. A system call is a mode switch, not a process switch: the same process keeps running, in kernel code, on its own behalf.
  2. The trap instruction itself is not privileged. That is the design, and it is why a user program can enter the kernel at all.
  3. printf is a library function with a buffer the process owns; only write crosses the boundary. Buffering is why five lines can cost one system call, and why fork can duplicate output.
  4. execve replaces the program and keeps the process: the identifier, the descriptors and the identity survive; the memory image and the caught signal handlers do not.
  5. fork copies the descriptor table but shares the open file description, so the offset is shared. Two separate open calls share nothing.

Intuition: the building with two floors

A bank has a public floor and a vault floor. On the public floor you may walk anywhere, fill in any form, and use the pens. You may not open the vault. If you need something from the vault, you do not break in — you fill in a numbered slip at a window, hand it over, and a clerk goes down for you. You get the result back at the same window, in the same place you were standing.

That is the whole design. The numbered slip is the system-call number, the window is the trap instruction, the clerk is the handler, and the fact that you are still standing at the same window afterwards is why a system call is a mode switch and not a process switch. Educational interpretation — an analogy for the mechanism, not a description of any particular hardware.

Formal definition: the two modes

The processor runs with a privilege level held in its status register. Two levels matter:

  • User mode. Privileged instructions are refused. I/O instructions, loading the page-table base, disabling interrupts, halting the CPU and writing the mode bit are all unavailable.
  • Kernel mode. Every instruction is available.

The mode bit is the field that holds the level. Textbooks write it as 1 for user and 0 for kernel; some processors use the opposite polarity, so the rule is what matters, not the digit. Educational interpretation for the polarity note.

Changing the mode is itself a privileged operation. If a user program could write the mode bit, the two-mode design would protect nothing.

Formal definition: the trap

A trap is an instruction that deliberately raises an exception. Executing it makes the hardware:

  1. save the program counter and status word, because the kernel must be able to return to the next instruction;
  2. switch to kernel mode, because the handler needs privilege;
  3. jump to a handler chosen from a fixed vector, so that the entry point is not chosen by the user program.

The trap instruction is not privileged. That is not an oversight: if entering the kernel required privilege, no unprivileged program could ever ask for anything. The checks happen inside, on the call number and the arguments. Verified fact — the mechanism, and the range-check on the number with ENOSYS for an unimplemented one, are documented in syscall(2).

One boundary, three doors

All entries to the kernel end in the same place, but they are raised by different things:

  • Trap (system call) — raised by the program on purpose, synchronous. read, write, fork.
  • Fault (exception) — raised by the instruction that is running, accidentally, synchronous. A page fault, a divide by zero, an illegal instruction.
  • Interrupt — raised by a device or the timer, asynchronously. A disk completion, a timer tick.

The four calls, as one protocol

A shell running ls uses four calls in sequence. Each answers a different question:

  1. fork — make a second process. Returns the child's identifier in the parent and 0 in the child.
  2. execve — put this program into the process. Replaces the memory image; does not return on success.
  3. exit — end this process and keep a status. Never returns.
  4. wait4 — block until a child ends, then collect its status. Returns the child's identifier.

Verified fact The return values and the no-return-on-success rule are from fork(2) and execve(2).

Descriptor and open file description

Two objects, and keeping them apart answers most of the questions:

  • The descriptor table belongs to the process. A descriptor is a small integer indexing it. On startup, 0, 1 and 2 are the standard input, output and error.
  • The open file description belongs to the kernel and holds the file offset, the status flags and the access mode.

Verified fact fork gives the child copies of the descriptor table, and "each file descriptor in the child refers to the same open file description … they share open file status flags, file offset, and signal-driven I/O attributes" (fork(2)). A descriptor created by open stays open across execve unless the close-on-exec flag is set (open(2)).

So fork shares the offset and execve keeps the descriptor — two independent facts that are easy to merge into one wrong rule.

Where the buffer sits

Verified fact stderr is unbuffered; stdout is line buffered when it points at a terminal, and partial lines do not appear until fflush, exit, or a newline is printed (stdout(3)). When it points at a file or a pipe, it is fully buffered instead.

Two consequences that this lesson uses:

  • The number of write calls is not the number of printf calls. It is a function of the buffering mode, the byte count and the buffer size.
  • An unflushed buffer is part of the process's memory, so fork copies it. Each copy is flushed by its own process at exit.

What "kept across execve" means

Verified fact execve(2) states that "all process attributes are preserved during an execve(), except" a list: caught signal dispositions are reset to default, the alternate signal stack is not preserved, memory mappings are not preserved, and so on.

Read the sentence in that direction — preserved except — and the exam question answers itself. The exceptions are the program's own furniture; what survives is the process's identity and its open files.

Four worked examples, each computed rather than recalled

Every number below is printed by the page's model. The first two are the previous-year counts, and the last two are the two-table questions that a paper can ask without any code at all.

Example 1 — the 2024 loop, counted two ways

int x = 3; while (x > 0) { fork(); printf("hello"); wait(NULL); x--; }

route 1: population of each iteration = 2, 4, 8, each printing once
2 + 4 + 8 = 14 executions of printf, in 8 processes.
route 2: sum over processes of the iterations each still had to run
3 (parent) + 3 + 2 + 2 + 1 + 1 + 1 + 1 = 14. The two routes agree, and so does the closed form 2k+1 − 2.

Why wait does not change it. wait stops a parent from running ahead of its own child; it does not stop any process from printing. The order changes, the count does not. Mathematical derivation

Example 2 — how many system calls did that print make?

Two runs, same bytes, different destination. Buffer size used here: 4096 bytes.

  • Five lines of six bytes (30 bytes): 5 writes at a terminal, 1 redirected.
  • Two thousand lines of ten bytes (20000 bytes): 2000 writes at a terminal, 5 redirected.
redirected writes = ceil(total bytes / buffer size)
ceil(20000 / 4096) = 5. The terminal column is one write per newline, because a line-buffered stream flushes on each one.

The factor is 400 in calls and 1 in bytes. That ratio is the entire reason buffered output exists. Mathematical derivation from the buffering rules, with the buffer size as a stated parameter.

Example 3 — the shared offset, byte by byte

fd = open("log.txt", O_RDONLY); then fork(), then each process reads four bytes.

  1. The parent reads: the description's offset is 0, so it gets bytes 0–3, and the offset becomes 4.
  2. The child reads through the same description: the offset is 4, so it gets bytes 4–7, and the offset becomes 8.
  3. Neither process restarted at byte 0, and neither overwrote the other's progress.

The counterexample that stops over-application: if the child instead calls open again on the same file, it gets a second description with its own offset of 0, and then it does read bytes 0–3. Sharing comes from fork, dup or passing a descriptor — not from naming the same file twice. Verified fact for the sharing rule (fork(2), open(2)); the byte arithmetic is a derivation from it.

Example 4 — what a status of 258 means

A child calls exit(258). The parent's wait fills an integer, and WEXITSTATUS extracts the low eight bits.

258 mod 256 = 2
The parent sees 2. A child calling exit(256) is indistinguishable from exit(0), and exit(512) is indistinguishable from both.

Verified fact WEXITSTATUS "consists of the least significant 8 bits of the status argument" (wait(2), and the same sentence in POSIX). Consequence: a program that wants to report a wide error code through its exit status cannot — it must use the low byte, or report through a file or a pipe.

Boundaries, and the condition each one violates

Each card names the tempting general rule, the case where it fails, and the condition that has to hold for the rule to be safe.

Counterexample: read returning 0

A return of 0 from read looks like failure, because every other error is negative or −1.

It is not an error. It means end of file: zero bytes were available. The error convention is different — the kernel returns a negative code in the window −4095 to −1, and the C wrapper converts that to −1 with errno set.

The condition: "negative means error" holds for the raw kernel return; the wrapper's −1 is a separate convention on top.

Counterexample: the same file twice

"Both processes are reading the same file, so they share an offset" is false when the two descriptors came from two open calls.

Sharing is a property of the open file description, not of the file. Two opens make two descriptions, and each starts at 0.

The condition: a shared offset needs a shared description — which fork, dup and descriptor passing provide, and a second open does not.

Counterexample: "signals survive exec"

Half true, and the half that is false is the one asked about.

A signal set to SIG_IGN stays ignored across execve. A signal with a caught handler is reset to its default disposition, because the handler was code in the old image.

The condition: a disposition that needs no code can survive; a disposition that needs code cannot.

Counterexample: "a newline flushes the buffer"

True at a terminal, false in a pipe or a file. The same program, redirected, keeps the bytes in the buffer.

That is exactly why printf("hello"); fork(); prints once at a prompt and twice into a file, and why fflush is the portable fix.

The condition: newline-flushes requires line buffering, which requires a terminal.

Counterexample: "wait reduces the number of prints"

It feels as if wait serialises the processes and so prevents some of them from printing.

It does not. wait blocks the caller until a child terminates; every process still reaches the printf in its own iteration. The 2024 loop prints 14 times with or without it.

The condition: wait changes when a parent proceeds, never whether a process prints.

Counterexample: "the call numbers are constants"

On x86-64 Linux, read is 0, write is 1 and fork is 57. On 32-bit x86, fork is 2.

The numbering is a property of the architecture's table, not of the operating system in the abstract.

The condition: quote a call number only with its architecture, and never build an argument on the number itself.

Five beliefs that produce wrong answers, and the sentence that corrects each

Each card states the belief, why it is tempting, a minimal counterexample, and the rule to keep instead.

"printf is a system call"

Why it tempts: it prints, printing needs the screen, and the screen is hardware.

Minimal counterexample: a redirected run of 2000 prints makes 5 system calls, not 2000. If printf were the call, the count could not differ from the print count.

The rule: printf is a library function that formats into a buffer the process owns; write is the system call, and buffering decides how often it happens.

"A system call switches the process out"

Why it tempts: the words "switch" and "kernel" appear together in both topics.

Minimal counterexample: the same process, with the same page tables and the same identifier, runs the handler. No scheduler decision is needed and none is taken.

The rule: a system call is a mode switch. A process switch contains a mode switch and adds scheduler, register-set and address-space work.

"fork duplicates the output because it duplicates the process"

Why it tempts: it sounds like the same statement twice.

Minimal counterexample: the same program with a trailing newline at a terminal prints once. Only the unflushed buffer is duplicated.

The rule: fork copies memory, and the buffer is memory. What was already written to the kernel is not copied; what was still in user space is.

"exec keeps everything because the process is the same"

Why it tempts: the identifier really does stay the same, so it feels as though nothing was replaced.

Minimal counterexample: a handler installed with signal before execve is gone afterwards, reset to default. So is the heap.

The rule: the process survives and the program does not. Identity, descriptors and limits belong to the process; the image and the caught handlers belong to the program.

"The trap instruction must be privileged, or user code could do anything"

Why it tempts: it sounds like the safer design, and privilege is the theme of the lesson.

Minimal counterexample: if the trap instruction were privileged, a user program could never enter the kernel, and no program could ever read a file. The design requires an unprivileged door with checks behind it.

The rule: entering the kernel is always allowed; what the kernel then does is gated by range-checking the call number and validating the arguments. A privileged instruction executed in user mode raises an exception instead of entering — that is the difference between a mistake and a request.

Four question shapes, and the reasoning each one demands

This page names no weightage. The shapes below are the ones this topic's previous-year items take, and each is stated as a reasoning task rather than a formula to recall.

Shape 1 — which event crosses the boundary

The reasoning: ask whether the processor could complete the operation without the kernel. If it could, the event does not guarantee a transition.

Seen as: GATE CSE 2023 Q13 — function call, malloc, page fault, system call; answer C and D.

The common wrong approach: answering D alone, because "system call" is the obvious one and the page fault looks like an error rather than a door.

Shape 2 — ordering two switch costs

The reasoning: containment. List the steps of each switch and show that one list contains the other. Then the ordering follows without any measurement.

Seen as: GATE CSE 2011 Q6 — T1 the mode switch against T2 the process switch; answer T1 < T2.

The common wrong approach: reasoning from imagined nanosecond figures, or assuming entering the kernel is the expensive part.

Shape 3 — count executions in a fork tree

The reasoning: draw the tree and ask how many processes reach each print. With wait present, the tree is serialised but the reachable set is unchanged.

Seen as: GATE CSE 2012 Q8 (three forks, 7 children), GATE CSE 2019 (five forks, 31 children), GATE CSE 2024 Set 1 Q47 (14 prints).

The common wrong approach: answering the process count when the question asks for print executions, or forgetting that the original parent is one of the printers.

Shape 4 — what a call changes, and what it leaves alone

The reasoning: name the call, name its mode, then sort the attributes into process properties and program properties.

Seen as: statement-style MSQs on exec, descriptor inheritance and signal dispositions. This page's practice set contains two such original items, labelled as original.

The common wrong approach: treating the process and the program as one object, so that "the pid is unchanged" is taken to imply "everything is unchanged".

MSQGATE CSE 2023 Q13

Which one or more of the following options guarantee that a computer system will transition from user mode to kernel mode?

  1. Function call
  2. malloc call
  3. Page fault
  4. System call

Answer: C and D — page fault and system call

D is immediate. A system call executes a trap instruction; the hardware switches to kernel mode and enters the handler.

C is a door too. A page fault is an exception raised by the running instruction. The fault handler that brings the page in must run with privilege, so the fault vectors into the kernel.

Why A and B fail. A function call is a jump inside user mode. malloc may extend the heap with a brk or mmap call, but when the request is served from memory the process already owns, no system call happens — so malloc guarantees nothing.

The word doing the work is guarantee. "Sometimes" is not an answer in an MSQ of this form.

MCQGATE CSE 2011 Q6

Let the time taken to switch from user mode to kernel mode of execution be T1, while the time taken to switch between two user processes be T2. Which of the following is true?

  1. T1 < T2
  2. T1 > T2
  3. T1 = T2
  4. Nothing can be said about the relation between T1 and T2

Answer: option 1 — T1 < T2

Why, without any timing figure. A mode switch saves the program counter and status word, flips the mode, and enters a handler. A process switch performs all of that and then runs the scheduler, saves the whole register set, loads a new page-table base and disturbs the translation cache. Every step of the first list appears in the second, and the second has more — so it cannot be cheaper.

Why option 4 is wrong. "Nothing can be said" would be right if the two switches were unrelated. They are not: one contains the other, and that containment is what settles the inequality.

Trap. Option 2 comes from imagining that entering the kernel is the expensive part. Entering is cheap; changing process is not.

NATGATE CSE 2024 Set 1 Q47

Consider the following code snippet using the fork() and wait() system calls. Assume that the code compiles and runs correctly, and that the system calls run successfully without any errors.

int x = 3;
while (x > 0) { fork(); printf("hello"); wait(NULL); x--; }

The total number of times the printf statement is executed is ______.

Answer: 14

The population doubles once per iteration. Iteration 1: 1 process forks, 2 processes exist, both print. Iteration 2: those 2 fork, 4 print. Iteration 3: those 4 fork, 8 print. Total 2 + 4 + 8 = 14, in 8 processes.

The second route agrees. Each process prints once for every iteration it still has left: the parent and its first child print 3 times each, the two processes born in iteration 2 print twice each, and the four born in iteration 3 print once each — 3 + 3 + 4 + 4 = 14.

Why wait does not change it. wait(NULL) blocks the parent until one child terminates, which serialises the tree. Serialising does not remove any process from the tree, so no print disappears.

Trap. 8 is the number of processes, not the number of prints. The question names printf.

MCQGATE CSE 2012 Q8

A process executes the code

fork();
fork();
fork();

The total number of child processes created is

  1. 3
  2. 4
  3. 7
  4. 8

Answer: option 3 — 7

Each fork doubles the number of processes: 1 → 2 → 4 → 8. Of those eight, one is the original parent, so seven are children.

Why this question is here. Not for the formula — the processes lesson owns it — but because it is the same tree that scene 10 uses with a printf and a wait added. The children count and the print count are different questions about one tree.

Trap. Option 4 is the process count. The question asks for children.

NATOriginal practice

A program writes 3000 lines of 20 bytes each with printf and then exits normally. Its standard output is redirected to a file. Assume the stream is fully buffered with a buffer of 4096 bytes and that every line is flushed only when the buffer fills or at exit.

The number of write system calls made is ______.

Answer: 15

The arithmetic. 3000 × 20 = 60000 bytes. ceil(60000 / 4096) = 15, because 14 full buffers carry 57344 bytes and the remaining 2656 bytes need one more write at exit.

Why not 3000. Redirected output is fully buffered, so a newline flushes nothing. The 3000 is the number of printf calls, not the number of system calls.

Why not 14. 14 buffers hold only 57344 of the 60000 bytes; the tail is flushed separately at exit. Rounding down loses that final write.

Assumption stated in the question: the buffer size. Change it and the answer changes — which is why the question fixes it.

MSQOriginal practice

A process has descriptor 4 open on a file, with the close-on-exec flag clear. It also has descriptor 5 open with the close-on-exec flag set. It then calls execve successfully. Which of the following are true of the new program?

  1. Descriptor 4 is still open
  2. Descriptor 5 is still open
  3. The file offset of descriptor 4 is preserved
  4. Signal handlers the old program had installed with a catch function are still installed

Answer: A and C

A is true. A descriptor survives execve unless its close-on-exec flag is set (open(2)).

B is false. That flag exists precisely to close the descriptor at execve.

C is true, and it is the subtle one. The descriptor is unchanged, so it still refers to the same open file description, and the offset lives in the description. Nothing about the offset is reset.

D is false. execve(2) resets the dispositions of caught signals to the default, because the handler was code in the replaced image. Ignored signals, by contrast, stay ignored.

Distinction to keep: "kept across exec" is a statement about descriptors and process attributes, not about the program's own state.

NATOriginal practice

A process opens a file, reads 10 bytes, then calls fork(). The parent then reads 5 bytes and the child reads 5 bytes, in that order.

The byte offset of the shared open file description after both reads is ______.

Answer: 20

Three reads, one offset. The first read moves the offset to 10. The parent's read moves it to 15, and the child's read moves it to 20 — because both descriptors refer to the same open file description, which is where the offset lives.

Why not 10. That is the answer if fork gave the child an independent offset. It does not: fork(2) says the descriptors in the child refer to the same open file description.

Why not 15. That counts only one of the two reads made after the fork.

Contrast: had the child called open again instead of inheriting, its own description would sit at 5 after its read, and the parent's would sit at 15 — two descriptions, two offsets.

MCQOriginal practice

A program does printf("hi") — no newline, no flush — and then calls fork() once. Both processes then terminate normally by returning from main. The program is run twice: once at a terminal, once with standard output redirected to a file.

How many times does the text hi appear in the output in each run?

  1. Terminal: 1, file: 1
  2. Terminal: 1, file: 2
  3. Terminal: 2, file: 2
  4. Terminal: 2, file: 1

Answer: option 3 — terminal 2, file 2

Nothing was flushed, in either run. The line-buffering rule flushes on a newline, and there is no newline. So at the terminal the two bytes are still in the buffer when fork runs, exactly as they are in the redirected run.

Two copies, two flushes. The child gets its own copy of the buffer, and each process flushes its own copy at exit. The text appears twice in both runs.

Now change one character. Write printf("hi\n") instead: at a terminal the newline flushes before the fork, so the terminal run shows it once, while the redirected run still shows it twice. The pair becomes (1, 2) — option 2 — and that is the version most previous-year questions describe.

The rule to carry. The buffering mode decides whether a newline flushes. Without a newline, neither mode flushes, and only fflush changes the answer.

Revision sheet — one screen

Definitions, the four calls, the two tables, the arithmetic and the traps. If a fact is not here, it is a consequence of something that is.

Definitions

  • Mode bit — the privilege level in the status register. User mode refuses privileged instructions; kernel mode allows all.
  • Trap — an instruction that deliberately raises an exception, switching to kernel mode at a fixed vector. The instruction is not privileged.
  • System call — a request to the kernel made through a trap, identified by a number in a register.
  • Mode switch — save PC and status, flip mode, enter handler, return. Same process.
  • Process switch — a mode switch plus scheduler, full context, new address space.
  • Open file description — the kernel object holding the offset and status flags. Descriptors point at it.

The four calls

  • fork — makes a process. Returns the child's pid in the parent, 0 in the child, −1 on failure.
  • execve — replaces the program image. Never returns on success; returns −1 on failure.
  • exit — ends the process, keeps a status. Never returns.
  • wait4 — blocks until a child changes state, then returns its pid and status.

Numbers worth carrying

  • x86-64 Linux: read 0, write 1, open 2, close 3, fork 57, execve 59, exit 60, wait4 61.
  • Error window from the raw kernel: −1 to −4095; the C wrapper reports −1 and sets errno.
  • Exit status reported = the exit argument mod 256, so 256 reports 0.
  • n forks: 2n processes, 2n − 1 children.
  • k iterations of the 2024 loop: 2k+1 − 2 prints, 2k processes.
  • Redirected writes = ceil(total bytes / buffer size).
  • Unflushed buffer across n forks: 2n copies written if buffered, 1 if line buffered.

The traps, in one line each

  • printf is a library call; write is the system call.
  • The trap instruction is not privileged; the operation behind it is.
  • A system call is a mode switch, not a process switch.
  • wait changes order, never the number of prints.
  • fork shares the open file description; a second open does not.
  • exec keeps the pid, the descriptors and ignored signals; it resets caught handlers.
  • A newline flushes only a line-buffered stream.
  • read returning 0 is end of file, not an error.

The procedure

Name the call. Name its mode — does it cross the boundary, and does it return? Then ask what it changes and what it leaves alone: the image, the descriptor table, the open file description, or the process itself. Those four objects answer every question on this page, and the arithmetic follows from whichever of them the question names.

Manual pages (behaviour)

  • syscall(2) — the call-number convention, the per-architecture calling table, the error window and ENOSYS.
  • fork(2) — the return values, and the sentence that the child's descriptors refer to the same open file description and share the offset.
  • execve(2) — "all process attributes are preserved … except": caught signals reset, alternate stack and mappings not preserved.
  • wait(2) — zombies, reaping, and the eight-bit exit status.
  • open(2) — descriptors stay open across execve by default; O_CLOEXEC changes that; duplicated descriptors share a description.
  • stdout(3) — stderr unbuffered; stdout line buffered at a terminal; partial lines wait for fflush or exit.
