Topic and objective

TOPIC: The socket API and the connection lifecycle — the clause "socket API" in Section 10, Computer Networks, of the GATE 2027 CS syllabus.

LEARNING OBJECTIVE: Name the calls on each side and the order they must come in. Explain why a server holds one listening socket and one connected socket per client, and count the sockets in a whole system as one plus twice the number of connections. Place SYN, SYN-ACK and ACK on a timeline and say that connect returns at one round trip while accept returns at one and a half. Read listen's second argument as a queue length and check a backlog simulation against its two identities. Count the connections one server endpoint can hold, and the ports one client address can spend. Say which side enters TIME-WAIT, for how long by the specification and on Linux, and why. Turn a connection rate and a holding time into ports in use, and find the ceiling at 470 connections per second.

I read this clause as four countable facts and one vocabulary: sockets are pairs, connections are four-tuples, the backlog is a queue length, and a port is held after the close. Every GATE-style question on the socket API is one of those four asked on small numbers.

GATE relevance

Verified fact Class A — explicitly in the syllabus.

Section 10 of the GATE 2027 CS syllabus, published by IIT Madras as CS_GATE2027_Syllabus.pdf, ends with "TCP – flow control and congestion control, socket API; DNS and HTTP". The words socket API are named, so the system calls, their order and their consequences are inside the declared boundary.

What you should be able to do afterwards

Given any socket question, decide whether it asks about sockets, connections, four-tuples, ports or round trips, apply the one invariant for that quantity, and produce an answer in the unit the question used. Then check it: the socket count is odd, the rate is a floor, and the side in TIME-WAIT is the side that closed first.

Intuition first: a doorway, a doorman and a room

Think of a building with one doorway. The doorway itself has a number painted on it, and it is always there, whether or not anybody is visiting. A doorman stands in the doorway. Each visitor who arrives is given a room of their own, and from then on the conversation happens in that room, not in the doorway. The doorway is never blocked by a conversation: a second visitor walks past the first one's room and gets their own.

The doorway is the listening socket, the doorman is accept(), and each room is a connected socket. The painted number is the port, and it is the same number for every room. Educational interpretation The analogy carries the one-port-many-connections idea, which is the hardest part of the clause. It does not carry the four-tuple, which is why the formal vocabulary comes next.

Formal vocabulary, every term in words

Socket — one endpoint of a transport conversation, identified by an address and a port, written address:port. It is a pair of numbers, not a connection.

Connection — the pair of two endpoints. Written as a four-tuple: source address, source port, destination address, destination port. The kernel demultiplexes an arriving segment on all four.

Descriptor — the small integer a process gets back from socket() or accept(). It names a socket inside that process only, and is reused after close().

Ephemeral port — a port chosen automatically for an outgoing connection. On Linux it comes from ip_local_port_range, which defaults to 32768 to 60999.

Backlog — the length of the queue of completed connections waiting for an accept() call, set by the second argument of listen().

TIME-WAIT — the state the active closer holds after the last acknowledgement, so that a lost final ACK can be answered and old duplicates can die before the four-tuple is reused.

The calls, in the order they must come

Server. socket() gives an unbound descriptor. bind() fixes the local address and port. listen() moves the socket to LISTEN, after which SYNs are answered. accept() takes one completed connection off the queue and returns a new descriptor. Then read() and write(), then close().

Client. socket(), then connect(). The connect call chooses an ephemeral port — a client does not normally call bind — records the peer, and sends the SYN.

Verified fact The call set, the states and the handshake are specified in RFC 793, and the POSIX interface is described in the socket(2), bind(2), listen(2), accept(2) and connect(2) manual pages. The three states of a normal passive open are LISTEN, SYN-RECEIVED and ESTABLISHED.

One port, many connections

A listening socket has a local port and no peer. A connected socket has the same local port and a peer. The two are distinguished by the peer, which is half of the four-tuple. So a server on port 443 can hold thousands of connections without ever needing a second port.

sockets in the system = 1 + 2None listening socket, N connected sockets at the server, and N sockets at the clients. Eight connections therefore mean seventeen sockets, which is the count a question usually wants.

Mathematical derivation The identity follows from counting both machines: the server holds one listener plus one per connection, and each client holds exactly one. It is checked in code for N = 1, 5, 8 and 100.

Where the handshake actually happens

connect() sends the SYN and blocks. When the SYN-ACK arrives — one round trip later — it returns and the kernel sends the final ACK. accept() returns when that ACK arrives at the server, one and a half round trips after the SYN.

connect returns at 1.0 RTT
accept returns at 1.5 RTTthe gap is the third segment travelling. A question that asks when the connection is established is asking about the server, so it wants 1.5, not 1.0.

Mathematical derivation The three segments each take half a round trip in the symmetric case the exam always assumes. The returns are placed at the arrival of the second and third segment, which gives 1.0 and 1.5 exactly.

The backlog is a queue, and it has two identities

The second argument of listen() bounds the completed-connection queue. Arrivals that find it full are dropped, and the client retransmits its SYN after a timeout, so an overflow shows up as latency rather than as an error.

queued = accepted + still waiting
arrivals = queued + droppedtwo lines that check any hand simulation. On the worked case — six arrivals, capacity two, accepts at 2.5 s and 4.5 s — four are queued and two are dropped.

Verified fact Linux keeps a separate SYN queue for half-open connections and an accept queue for completed ones, and caps the value passed to listen() at somaxconn. The single number in the question is the completed queue unless the question says otherwise.

The two ceilings: descriptors and ports

Hold the server endpoint fixed and the only free fields are the client address and the client port. With the Linux default range that is 28232 connections from one client address, and across all clients it is 2^32 × 2^16 = 2^48 four-tuples.

The server's ceiling is its descriptor table, its memory and its accept queue. The client's ceiling is its ephemeral ports, and how long each one is held after the close.

Verified fact The default range 32768 to 60999 and the per-destination nature of the limit are documented in the Linux ip-sysctl reference and in Cloudflare's write-up of ephemeral port exhaustion. The 2^48 figure is arithmetic on the field widths.

TIME-WAIT: who, how long, and why

The side that sends the first FIN is the active closer, and it is the side that ends in TIME-WAIT. It waits so that a retransmitted FIN can still be acknowledged, and so that a delayed segment from the old connection cannot be accepted by a new connection using the same four-tuple.

RFC 793: MSL = 120 s, TIME-WAIT = 2 × MSL = 240 s
Linux: TCP_TIMEWAIT_LEN = 60 s, fixedboth are correct in their own terms. A question that says "as specified" wants 240; a question about a Linux host wants 60.

Verified fact RFC 793 takes the maximum segment lifetime to be two minutes and specifies the two-times-MSL wait. Linux hard-codes sixty seconds in TCP_TIMEWAIT_LEN and exposes no sysctl for it.

Exhaustion is one product, and the ceiling is a floor

A client that closes first holds each port for the TIME-WAIT interval. So the number of ports unavailable at any moment is the connection rate multiplied by that interval.

ports in use = rate × seconds held
28232 / 60 = 470.53, so 470 fits and 471 does not470 × 60 = 28200 ports, inside the range. 471 × 60 = 28260, outside it. The answer is a floor because the constraint is a ceiling on a count.

Mathematical derivation Every figure in the table — 6000, 18000, 28200, 28260 — is the product of a rate and sixty seconds, and each is compared against 28232 in code. Verified fact The failure is EADDRNOTAVAIL from the local kernel, raised before any segment is sent.

Four worked examples, each with its numbers shown

Example 1 — sockets in a running system

A server listens on port 443 and has accepted eight connections. Each client holds one socket. How many sockets exist in the system?

Server: one listening socket plus eight connected sockets, so nine. Clients: eight, one each. Total seventeen.

1 + 2N = 1 + 16 = 17the one is the listener, the 2N is one connected socket at each end of every connection. The total is always odd, which is a one-second check.

Where the wrong answers come from. Nine counts only the server. Eight counts only the connections. Sixteen forgets the listener.

Example 2 — the backlog, simulated

A server calls listen(fd, 2). Connections complete at t = 0, 1, 2, 3, 4 and 5 seconds. The program calls accept() at 2.5 and 4.5 seconds. How many are queued, accepted, dropped and still waiting?

At 0 and 1 the queue fills to two. The arrival at 2 finds it full and is dropped. The accept at 2.5 removes one; the arrival at 3 takes the free slot; the arrival at 4 is dropped; the accept at 4.5 removes one; the arrival at 5 is queued.

queued 4 = accepted 2 + waiting 2
arrivals 6 = queued 4 + dropped 2both identities hold, so the trace is consistent. A simulation that fails either identity has miscounted an arrival or an accept.

The trap. A dropped SYN produces no error at the client. It retransmits after a timeout, so the visible effect is a slow connection, not a refused one.

Example 3 — the ceiling on new connections

A proxy opens short connections to one backend endpoint and closes each one first. The port range is 32768 to 60999 and TIME-WAIT lasts 60 seconds. What is the highest sustained rate that does not exhaust the range?

The range holds 28232 ports. Each closed connection holds one for 60 seconds. So the ports in use are 60 times the rate, and the largest rate whose product stays inside 28232 is 470.

28232 / 60 = 470.53 → 470 per second
470 × 60 = 28200 ≤ 28232
471 × 60 = 28260 > 28232the floor, not the nearest integer. Rounding up to 471 promises 28 ports that do not exist.

Under the specification. With the RFC's 240-second wait the same range gives 117 per second, because 117 × 240 = 28080 and 118 × 240 = 28320.

Example 4 — when each call returns

A client calls connect() at time zero and the round trip is one unit. When does the client's call return, when does the server's accept() return, and what is in flight at the first of those moments?

The SYN arrives at the server at 0.5 and the SYN-ACK arrives back at 1.0, so connect returns then. The final ACK leaves at 1.0 and arrives at 1.5, which is when the connection is established at the server and accept returns.

connect 1.0 RTT · accept 1.5 RTT · gap 0.5 RTThalf the gap is the ACK travelling and half is the server processing it, which the exam treats as instantaneous.

The trap. Saying the handshake is complete when connect returns. It is complete at the client; the server learns half a round trip later.

The boundaries where the standard answers stop holding

Each case below is a place where a rule from the Build-up tab is true only under an assumption, and the assumption is stated.

Boundary cases of the calls

  • bind to port 0. The kernel chooses a free port; getsockname() reports which. The port is not 0 after the call.
  • bind to a port in use. Fails with EADDRINUSE, unless SO_REUSEADDR is set, which allows binding while an old connection sits in TIME-WAIT.
  • accept on a non-listening socket. Fails with EINVAL. The socket must have been through listen().
  • connect to a closed port. The peer answers with a reset, and connect fails with ECONNREFUSED. This is a reply from the peer, unlike EADDRNOTAVAIL, which never leaves the host.
  • listen with a backlog of 0. Linux still admits a small number of completed connections, because the value is a hint that is clamped, not an exact bound.
  • close on the listening socket. New connections stop; connections already accepted continue.
  • shutdown(SHUT_WR). Sends the FIN without closing the descriptor, so the socket can still receive. This is a half-close, and it is not the same as close.

Boundary cases of the counts

  • 28232 is per destination endpoint. The same client port may be used at the same time for a different server address or port, because the four-tuple differs.
  • The 470 figure assumes the client closes first. If the server closes first, the client's port is freed at once and the ceiling disappears.
  • The range is a default, not a law. Widening ip_local_port_range raises the ceiling proportionally, and the reservation list removes ports from it.
  • The Linux default is not inside the "dynamic" range. It starts at 32768, in the registered range, and ends at 60999, in the dynamic range. Read the range from the number a question gives rather than from the name of a band.
  • 2^48 counts tuples, not sockets. A host is limited far earlier by descriptors, memory and the accept queue.
  • NAT changes the count. Behind a NAT every internal host shares one public address, so the port space is shared and the ceiling falls by the number of hosts.
  • IPv6 changes the width. The address is 128 bits, so the tuple space is far larger, but the port count is unchanged at 65536.

Counterexample: the server that "ran out of ports"

A server shows thirty thousand sockets in TIME-WAIT, all with local port 443. The claim is that it has exhausted its ports. It has not: those entries differ only in the client's address and port, so they consume memory and no ephemeral port at all. The kernel also caps them with tcp_max_tw_buckets.

The same count on a client or a proxy, all to one destination endpoint, is a genuine ceiling. The direction decides which of the two situations you are in, and the question has to tell you the direction.

Counterexample: a rate below the ceiling that still fails

An average rate of 400 connections per second to one endpoint is below 470, and can still fail. If the traffic arrives in bursts — 2000 connections in one second, then idle for four — then 2000 ports are held at once, and each stays held for 60 seconds, so the instantaneous demand is 120000 port-seconds against a pool that offers 28232 ports for 60 seconds.

Mathematical derivation The product is the same product; the average is the wrong statistic. A rate question must say whether the rate is sustained or bursty, and only a sustained rate can be compared with the ceiling.

Seven beliefs that produce a plausible wrong answer

Each entry states the belief, the counterexample that ends it, and the correct statement to carry into the exam.

1. "accept returns the same socket"

Why it feels right. The call is made on the listening descriptor, so the connection seems to be attached to it.

Counterexample. A server that accepts a hundred connections holds a hundred and one descriptors. If accept returned the listener, the second client would have nowhere to go.

Correct. accept returns a new descriptor. The listening socket stays in LISTEN and never carries data.

2. "each connection needs its own server port"

Why it feels right. A socket is address and port, and each connection is a different socket.

Counterexample. Every HTTPS connection in the world arrives at port 443. If each needed a port, there would be 65536 connections on the whole internet at once.

Correct. The connection is the four-tuple. The server's port is fixed; the client's port varies. Ports are a limit on the client side, not the server side.

3. "the server is the side in TIME_WAIT"

Why it feels right. Most connections are closed by the client's browser, and a server that serves many clients seems to be the busy party.

Counterexample. An HTTP/1.0 server that closes after every response is the active closer, so it enters TIME-WAIT while the client does not.

Correct. The side that sends the first FIN enters TIME-WAIT. It is a fact about the close, not about the role.

4. "TIME_WAIT is a bug, or a leak"

Why it feels right. The socket is closed, yet it sits in a state for a minute and blocks a port.

Counterexample. Remove the wait and a lost final ACK leaves the peer retransmitting a FIN that nothing answers, while a delayed duplicate can be delivered into a new connection with the same four-tuple.

Correct. It is the state that makes a close reliable. It costs ports only where short connections churn to one endpoint, and only on the closing side.

5. "TIME_WAIT always lasts four minutes"

Why it feels right. RFC 793 says two minutes of MSL and twice that in TIME-WAIT, and that is the number in every textbook table.

Counterexample. On Linux the interval is a fixed sixty seconds, and there is no sysctl for it; tcp_fin_timeout governs a different timer.

Correct. 240 seconds by the specification, 60 seconds on Linux. The question's wording decides which one is being asked.

6. "the backlog is the number of clients the server can serve"

Why it feels right. It is the second argument of listen, so it looks like a capacity.

Counterexample. A server with listen(fd, 5) serves millions of connections over a day, five waiting at a time at most.

Correct. It is a queue length at one instant. A slow accept loop, not a small backlog, is what drops connections.

7. "a socket is a connection"

Why it feels right. Programs call one socket a connection in conversation, and the descriptor is the handle for both.

Counterexample. One connection is three sockets in a two-machine system, and one listening socket is no connection at all. The units differ, so the counts differ.

Correct. A socket is an endpoint, a pair of numbers. A connection is a pair of endpoints, four numbers. Answering in the wrong unit is the single most common lost mark in this clause.

How this clause is tested, and what the wording gives away

Five patterns cover the clause. Each is recognisable from a phrase in the question, and each has one invariant behind it. No previous-year item on the socket API itself could be verified against a paper and a question number, so the patterns below are described from the syllabus clause and from the standard question forms, not attributed to a year.

Pattern 1 — count the sockets

Phrase. "How many sockets are open in the system / at the server" with a number of clients or connections.

Invariant. 1 + 2N for the system, 1 + N at the server, N at the clients. The system count is odd.

Check. If your answer is even and the question asks for the system, you have forgotten the listener.

Pattern 2 — count the connections one endpoint can hold

Phrase. "How many simultaneous connections can the server support" or "how many clients can connect to this port".

Invariant. With the server endpoint fixed, the free fields are the client address and port: 28232 per client address with the Linux default, 2^48 across all addresses.

Check. The server's own port count never appears in the answer. If you multiplied by 65536 for the server, you counted the wrong side.

Pattern 3 — the port-exhaustion product

Phrase. A rate of new connections, a TIME-WAIT duration, and a request for the maximum sustainable rate or the number of ports in use.

Invariant. ports in use = rate × seconds held, compared against the size of the range. The answer is a floor.

Check. Multiply your rate by the hold and confirm the product is at most the range, and that one more step exceeds it.

Pattern 4 — which call returns, and when

Phrase. "When does connect return", "when is the connection established at the server", or a round-trip count for a request over a fresh connection.

Invariant. connect at 1.0 RTT, accept at 1.5 RTT, and the third segment in flight at the first of the two.

Check. A total of one round trip for a full handshake is impossible unless the question explicitly piggybacks data on the third segment.

Pattern 5 — the state question

Phrase. "Which side is in TIME-WAIT", "which state follows CLOSE-WAIT", "why does the socket linger".

Invariant. Active closer: ESTABLISHED, FIN-WAIT-1, FIN-WAIT-2, TIME-WAIT, CLOSED. Passive closer: ESTABLISHED, CLOSE-WAIT, LAST-ACK, CLOSED.

Check. Only one of the two paths contains TIME-WAIT, and it is the path of the side that sent the first FIN.

The four-step procedure

  1. Name the side: client, server or the whole system. The same numbers differ by one between the three.
  2. Name the quantity: sockets, connections, four-tuples, ports or round trips. Five quantities, five invariants.
  3. Apply the invariant for that quantity. 1 + 2N, 28232, 2^48, rate × hold, or 1.0 against 1.5.
  4. Check the unit and the direction. A rate against a count, or a server-side count against a client-side ceiling, is where the last mark goes.

MCQOriginal practice

A server process listens on one TCP port and has accepted eight connections from eight different clients, each of which holds exactly one socket. How many sockets exist in the whole system?

  1. 8
  2. 9
  3. 16
  4. 17

Answer: D — 17

One listening socket, eight connected sockets at the server, eight sockets at the clients. 1 + 2 × 8 = 17.

Why 9. That counts only the server. Why 16. That counts the connections and forgets the listener. Why 8. That counts only the connections. The system total is always odd, which rules out two of the four options at a glance.

NATOriginal practice

A client process repeatedly opens a TCP connection to one fixed server endpoint, sends one request, and closes first. The client's ephemeral range is 32768 to 60999 and TIME-WAIT lasts 60 seconds. The largest sustained rate of new connections, in connections per second, that does not exhaust the range is ______.

Answer: 470

The range holds 28232 ports. Each closed connection holds one for 60 seconds, so ports in use is 60 times the rate. 28232 / 60 = 470.53, and the largest rate whose product stays inside the range is 470, using 28200 ports.

Why 471 is wrong. 471 × 60 = 28260, which is 28 ports more than exist. The constraint is a ceiling on a count, so it rounds down. Why 28232 is wrong. That is the number of ports, not the number of connections per second: the two differ by the holding time.

MSQOriginal practice

A server has called socket, bind and listen on port 9000, and has accepted three connections. Which statements are CORRECT?

  1. The server process holds four sockets that are bound to local port 9000.
  2. accept returned a descriptor different from the listening descriptor for each connection.
  3. The listening socket carries data for the most recent connection.
  4. The four sockets are distinguished from one another by their peer addresses and ports.

Answer: B and D

B is the definition of accept. D is the reason one port can serve several connections: the four-tuple differs in the peer fields.

Why A is wrong. The process holds four sockets, but only the listener was bound; the three accepted sockets inherit the local port without a bind call, so "bound" overstates what happened. Why C is wrong. A listening socket never carries data; reading from it fails.

MCQOriginal practice

A client calls connect() on a fresh TCP socket and the call returns successfully after one round trip. At the moment connect returns, which segment of the three-way handshake has NOT yet reached the server?

  1. The SYN
  2. The SYN-ACK
  3. The final ACK
  4. None; the handshake is complete at both ends

Answer: C — the final ACK

connect returns when the SYN-ACK arrives, which is one round trip after the SYN. The kernel sends the ACK at that moment, and it needs another half round trip to arrive, which is when the connection is established at the server and accept returns.

Why D is the tempting one. The handshake is complete at the client, so the client can write. It is not complete at the server, and a question about establishment at the server wants 1.5 round trips.

NATOriginal practice

A server calls listen(fd, 2). Completed connections arrive at t = 0, 1, 2, 3, 4 and 5 seconds, and the program calls accept() at t = 2.5 and t = 4.5 seconds. How many connections are dropped?

Answer: 2

Arrivals at 0 and 1 fill the queue of two. The arrival at 2 is dropped. The accept at 2.5 frees a slot, the arrival at 3 fills it, the arrival at 4 is dropped, the accept at 4.5 frees a slot and the arrival at 5 is queued. Four are queued, two are dropped.

The identity that checks it. Arrivals 6 = queued 4 + dropped 2, and queued 4 = accepted 2 + still waiting 2. Why 1 appears. Forgetting that an accept frees a slot for a later arrival, so the queue is not permanently full after t = 2.

MCQOriginal practice

Two processes on the same host use TCP. Process A sends the first FIN and completes the close. Process B receives the FIN and its application closes later. Which state does each process hold longest, and for how long on Linux?

  1. A in CLOSE-WAIT, B in TIME-WAIT, 60 seconds
  2. A in TIME-WAIT, 60 seconds; B passes through CLOSE-WAIT only while its application delays the close
  3. Both in TIME-WAIT for 240 seconds
  4. A in LAST-ACK, B in TIME-WAIT, 60 seconds

Answer: B

The active closer — the side that sent the first FIN — enters TIME-WAIT and holds it for a fixed 60 seconds on Linux. The passive closer sits in CLOSE-WAIT until its application calls close, which is a program decision and not a timer.

Why C. 240 seconds is the specification's 2 × MSL, not Linux's constant. Why A and D. Both put TIME-WAIT on the passive side, which is the commonest misreading of the state diagram.

MSQOriginal practice

Which statements about UDP sockets are CORRECT?

  1. A UDP socket cannot be put into TIME-WAIT, because there is no connection to protect.
  2. One unconnected UDP socket bound to a port can receive datagrams from many different clients.
  3. Calling connect on a UDP socket sends a SYN so that the peer creates state.
  4. A UDP server must call listen before it can receive datagrams.

Answer: A and B

A: TIME-WAIT protects a four-tuple that a new connection could reuse, and UDP keeps no such state, so the port is free at close. B: an unconnected UDP socket is demultiplexed by its local port alone, and recvfrom reports the source of each datagram.

Why C. connect on UDP only records a default peer locally; no packet is sent. Why D. listen fails on a datagram socket, because there is no connection queue for it to bound.

NATOriginal practice

A single server endpoint accepts connections from clients anywhere. Counting only the client address and the client port as free fields, the number of distinct TCP connections that could exist simultaneously to that one endpoint is 2k. Give k.

Answer: 48

2^32 client addresses times 2^16 client ports, which is 2^48, about 2.8 × 10^14.

Why 64 appears. Treating both ports as 32 bits. A port is 16 bits, so the two ports contribute 2^32 in total, not 2^64. Why 32 appears. Counting addresses only and forgetting that each address has a whole port range.

Revision sheet

Definitions, counts, formulas, decision procedures and traps, in the order you would use them. Nothing here needs the animation.

The calls

  • Server: socket, bind, listen, accept, read/write, close.
  • Client: socket, connect, read/write, close. connect binds an ephemeral port.
  • UDP: socket, bind (optional), sendto/recvfrom, close. No listen, no accept.
  • bind fixes the local address and port; listen sets LISTEN; accept takes a completed connection off the queue.
  • accept returns a new descriptor; the listener stays in LISTEN and never carries data.
  • A client that calls bind itself must choose a port, and can collide with one in TIME-WAIT.

The numbers

  • Port space 65536: 1024 well-known, 48128 registered, 16384 dynamic.
  • Linux ephemeral default 32768 to 60999, which is 28232 ports.
  • Sockets in the system 1 + 2N; at the server 1 + N.
  • Four-tuples for a fixed endpoint 2^48; per client address 28232.
  • connect returns at 1.0 RTT; accept returns at 1.5 RTT.
  • TIME-WAIT: 240 s by RFC 793, 60 s on Linux.
  • Port ceiling: 470 connections per second against a 60-second hold; 117 against a 240-second hold.

The four formulas

sockets = 1 + 2N (system), 1 + N (server)
ports in use = rate × seconds held
rate ceiling = floor(range / hold)
queued = accepted + waiting; arrivals = queued + droppedthe first is a count of descriptors, the second and third are one product seen from two sides, and the fourth checks a backlog simulation. Every one of them is verified in code on this page.

Plugged in: N = 8 gives 17; rate 470 with a 60-second hold gives 28200 ports, inside 28232; 471 gives 28260, outside.

Decision procedure, in four lines

  1. Name the side: client, server or system. 1 + 2N against 1 + N.
  2. Name the quantity: sockets, connections, tuples, ports, round trips. Five quantities, five invariants.
  3. Apply the invariant, then convert if the question asks for a rate. A rate is a count divided by the holding time.
  4. Check the unit and the direction. Server-side TIME_WAIT consumes no ephemeral port; client-side churn does.

Numbers from this lesson worth remembering

28232 ephemeral ports · 470 connections per second at a 60-second hold · 117 at a 240-second hold · 2^48 four-tuples for one server endpoint · 1 + 2N sockets, so 17 for eight connections · connect at 1.0 RTT and accept at 1.5 · six arrivals, capacity two, four queued and two dropped · 240 seconds by the specification and 60 seconds on Linux.

Every one of these was computed by this page's model and checked against its defining property, not copied from a table.

The five slips, one last time

accept returns the same socket · each connection needs its own server port · the server is the side in TIME_WAIT · the backlog is a client count · TIME_WAIT is always harmful. Write the side and the unit at the top of your working and none of the five survives.

What was consulted, and what each source supports

Standards, official documentation and the official syllabus are separated from practitioner write-ups. Every numeric answer on this page was computed from first principles by the page's own model, so the sources support the rules, not the arithmetic.

Official and standard

  • GATE 2027 CS syllabus, IIT Madras, CS_GATE2027_Syllabus.pdf, read on 3 November 2026. Supports the Section 10 wording quoted in Overview, including the clause "socket API".
  • RFC 793 — Transmission Control Protocol: the eleven connection states, the LISTEN, SYN-SENT, SYN-RECEIVED and ESTABLISHED descriptions, the state diagram with the 2MSL timeout from TIME-WAIT, and the statement that the maximum segment lifetime is taken to be two minutes.
  • RFC 6335 — the port-number registry procedure, which is the source of the 0–1023, 1024–49151 and 49152–65535 division quoted in scene 1.
  • Linux kernel documentation, ip-sysctl — ip_local_port_range with its defaults of 32768 and 60999, ip_local_reserved_ports, tcp_max_tw_buckets and tcp_tw_reuse.
  • POSIX and Linux manual pages — socket(2), bind(2), listen(2), accept(2), connect(2), shutdown(2), and the error names EADDRINUSE, EADDRNOTAVAIL, ECONNREFUSED and EINVAL.

Practitioner references, used for the implementation facts

  • Cloudflare, "How to stop running out of ephemeral ports" — the default range as 32768 to 60999, the count 28232, the four-tuple as the unit of connection identity, and the per-destination nature of the limit.
  • Wikipedia, "Maximum segment lifetime" and RFC 1337 — the two-minute MSL, Linux's TCP_TIMEWAIT_LEN of 60 seconds, and the TIME-WAIT assassination hazard that explains why the wait exists.
  • Baeldung, "How to forcibly close a socket in TIME_WAIT" — the two purposes of TIME-WAIT: answering a retransmitted FIN, and keeping an old duplicate out of a new connection with the same four-tuple.
  • damonsec, "Linux TIME_WAIT explained" — that the 60-second value is a kernel constant with no sysctl, that tcp_fin_timeout governs a different timer, and that server-side TIME-WAIT costs memory rather than ports.
  • netdata, "HAProxy ephemeral port exhaustion" — the arithmetic of ports in use against a sustained rate, and the ~470 per second ceiling for one destination endpoint.

What the research did not cover

No previous-year GATE item on the socket API itself was found and verified against a paper and a question number, so no question in this lesson is attributed to a year; the practice set is labelled original throughout. The 470-per-second ceiling assumes the client closes first, a sustained rather than bursty rate, and no port reuse; each of those assumptions is stated where the number is used. The backlog model here is a single completed-connection queue, while Linux actually keeps a SYN queue and an accept queue with separate bounds and a clamp at somaxconn; the single-queue model is what a GATE-style question describes, and the two-queue reality is described in Edge cases rather than modelled. The 60-second TIME-WAIT is a Linux kernel constant and has changed across kernel versions, so a question that names a different system would need a different constant. Sockets in this lesson are stream sockets unless a scene says datagram. Nothing here was checked against a printed textbook edition, and no claim is made about 2027 weightage.
