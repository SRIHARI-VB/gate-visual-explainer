Topic and objective

TOPIC: Canonical LR(1) items and the LALR(1) merge — the item that carries a lookahead, the closure that propagates it, the reduce rule that reads it, and the merging that can put two reductions into one cell.

LEARNING OBJECTIVE: Read an LR(1) item as a production with a dot plus one terminal, and say what that terminal records. Run the closure rule with FIRST(beta a) instead of FIRST(beta). Build a canonical LR(1) collection and place reduces only in the lookahead columns. Merge states with equal cores, union their lookaheads, and explain why the merged state count is always the LR(0) count. Prove that merging cannot create a shift/reduce conflict but can create a reduce/reduce conflict, and name a grammar that is LR(1) and not LALR(1). Decide a previous-year item on the three state counts by computing them rather than remembering them.

I read this topic as the rung above the survey of the LR family in the parsing lesson: that lesson names canonical LR(1) and LALR and gives their state counts, and this one builds both tables and separates the two classes with a witness.

Prerequisites

  • Lexical analysis, parsing and syntax-directed translation — FIRST and FOLLOW, the LR(0) automaton, shift, reduce, the handle, and the survey of the four LR parsers. This lesson starts where that one stops.
  • Context-free grammars and push-down automata — derivations, sentential forms and the language of a grammar, used whenever the page checks a table against a recognizer.
  • Deterministic push-down automata — the class of languages a deterministic parser can accept, which is the ceiling on all four rungs here.
  • Regular expressions and finite automata — the subset construction is the same idea as the item-set construction, and the vocabulary carries over.

The five ideas, in one line each

  • The lookahead is local. It records what may follow the whole right-hand side in this state, not in the grammar.
  • Closure uses FIRST(beta a). The extra terminal is what makes the canonical collection bigger.
  • The reduce reads the lookahead. A completed item writes one action, in its lookahead column.
  • Merging is by core. Same items, union the lookaheads, one state — so the count becomes the LR(0) count.
  • Merging can only create reduce/reduce conflicts. A shift/reduce conflict was already there.

What the page computes, and how it is checked

The page carries a complete LR(0), SLR, canonical LR(1) and LALR(1) implementation and rebuilds six grammars on every load: 69 canonical states, 51 LR(0) states, 18 merges. 1. Intuition — the door that will not open again

Picture a long corridor of rooms. Each room is a state of the parser, and each door is a grammar symbol. Some rooms have a locked door at the far end, and the key to that door is a single letter: you may pass only if the next thing you carry is that letter. LR(0) does not have keys. It is told, once, that this room might be followed by any of a set of letters, and it accepts all of them, so it opens doors with the wrong key and gets stuck. Educational interpretation

The key is the lookahead. It is not a property of the room's shape, which is what LR(0) knows as the core. It is a property of how you arrived: the same room shape can be reached through different doors, and then the letter you may carry out is different. That is the whole content of the change from LR(0) to LR(1), and it is why the same production appears twice in the canonical collection with two different keys.

LALR is what happens when you decide the two copies of a room are one room and put both keys on the same hook. It is cheaper, it almost always works, and once in a while it lets a visitor in through a door that belonged to the other room.

2. Formal definitions

An LR(1) item is a pair: a production with a dot marking a position in its right-hand side, and one terminal called the lookahead. Written [A → α·β, a], it asserts that the parser may be about to recognise αβ by the production A → αβ, and that the input terminal after the whole of αβ will be a.

Closure of a set I: for every [A → α·Bβ, a] in I and every production B → γ, add [B → ·γ, b] for each b in FIRST(βa). GOTO(I, X) is the closure of the set of items of I whose dot precedes X, with each dot advanced over X.

Reduce rule: if [A → α·, a] is in state I and a is the next input terminal, reduce by A → α. The shift rule is unchanged: if [A → α·Xβ, a] is in I with X a terminal, shift X.

The core of a state is its set of items with the lookaheads erased. Two states are merged by LALR when their cores are equal; the merged item carries the union of the lookaheads. A grammar is LR(1) when its canonical table has no multiply-defined entry, and LALR(1) when the merged table has none.

3. Visual understanding — what the drawing has to show

The natural picture of a state is a list of items, and a list is exactly what hides the point: two lists that look identical are two different states. So the animation prints the lookahead in a separate column, and the two states that share a core sit one above the other with only that column differing. When they merge, the column is what changes, and the conflict appears in the same place on the canvas that it appears in the table.

The second picture is the table: a reduce written into a column is a visible mark, and two marks in one cell are visible. That is why the SLR row and the LR(1) row are drawn one above the other — the subset relation is then something you see rather than something you are told.

4. Worked example — the closure, done by hand

Grammar: S → C C, C → c C | d. Start item [S′ → ·S, $].

  1. Closure of [S′ → ·S, $]: the dot is before S, and β is empty, so FIRST(β a) = FIRST($) = { $ }. Add [S → ·C C, $].
  2. Closure of [S → ·C C, $]: the dot is before C, β is C, so FIRST(C $) = FIRST(C) = { c, d }. Add [C → ·c C, c], [C → ·c C, d], [C → ·d, c], [C → ·d, d].
  3. Nothing else applies. I0 has six items over four cores.
  4. goto(I0, c) closes [C → c·C, c] and [C → c·C, d]; β is empty for each, so the lookaheads stay c and d. That is I3, six items again.
  5. goto(I0, C) gives [S → C·C, $] and closes with FIRST(C $) = { c, d } — but here the second C is the last symbol, so its closure is [C → ·c C, $], [C → ·d, $]. That is I2, three items.

The page prints these three states with their item and core counts, computed, in the Animation tab's second scene.

5. Boundaries — when each rung applies

All four rungs read the same LR(0) automaton. LR(0) reduces on every terminal; SLR reduces on FOLLOW of the head; LALR reduces on the lookaheads the merged state carries; canonical LR(1) reduces on the lookaheads its own state carries. The inclusions are strict: LR(0) ⊂ SLR ⊂ LALR ⊂ LR(1), and none of them contains every unambiguous grammar.

The ceiling is the deterministic context-free languages: an LR(1) parser is exactly as strong as a deterministic push-down automaton. So a grammar outside that class cannot be rescued by any amount of state splitting, and the page shows two such grammars (GE and GF) to make that concrete.

Example 1 — one closure, two lookaheads

Grammar S → C C, C → c C | d. Take the item [C → c·C, d].

  1. The dot is before C, so β is empty. With lookahead d, FIRST(β d) = { d }.
  2. Add [C → ·c C, d] and [C → ·d, d] — one lookahead each, not two.
  3. The same state also holds [C → c·C, c], because the state was entered on c from I0 and from I3. Its closure adds [C → ·c C, c] and [C → ·d, c].
  4. The union of the two closures is six items over three cores.

The page prints that state, I3, with its counts: 6 items, 3 cores.

Example 2 — the same state, reached twice, split in two

Still on S → C C. Compare the state reached by d from I0 with the state reached by d from I3.

  1. From I0 the dot in C → ·d has lookaheads c and d, so the new state holds [C → d·, c] and [C → d·, d]. That is I4.
  2. From I3 the item is [C → ·d, d] only, so the new state holds [C → d·, d] alone. That is I7.
  3. I4 and I7 have the same core — one item, C → d· — and different lookahead sets.

Why this is worth a card. The two states are reached by the same terminal from different places, and the canonical construction refuses to identify them. That refusal is the whole difference in state count: 10 against 7.

Example 3 — the SLR row and the LR(1) row, side by side

Assignment grammar: S → L = R | R, L → * R | id, R → L. State 2 holds [S → L·= R] and [R → L·].

SLR writes reduce R → L in every column of FOLLOW(R) = { =, $ }. The cell for = already holds shift = from the first item, so the table has a shift/reduce conflict.

Canonical LR(1) asks what can follow R here. The only production in which this R appears is S → L = R with the whole of it followed by the end marker, so the item is [R → L·, $] and the reduce goes into the $ column alone.

The page builds both tables and prints the counts: SLR 1 conflict, canonical LR(1) 0, LALR 0.

Example 4 — a merge that costs two strings

Grammar: S → a A d | b B d | a B e | b A e, A → c, B → c. Language: { acd, bcd, ace, bce }.

  1. After a the closure gives [A → ·c, d] and [B → ·c, e]: A here is followed by d, B here by e.
  2. After ac the state is [A → c·, d] and [B → c·, e]. Two reductions, two different columns, no conflict.
  3. After bc the state is [A → c·, e] and [B → c·, d]: same core, swapped lookaheads.
  4. LALR merges them, so both items carry both lookaheads, and d and e each call two reductions.

A generator that resolves in favour of A then reduces c to A on both terminals: right for acd and bce, wrong for bcd and ace. The canonical parser accepts all four.

A conflict that no merge caused

S → A | B, A → a, B → a. After reading a the state holds [A → a·] and [B → a·] with the same lookahead, the end marker. That is a reduce/reduce conflict in the canonical table, with nothing merged: the page builds 5 states and 0 merges and still reports the conflict.

The grammar is ambiguous, so no LR table can be clean. The lesson: a reduce/reduce conflict is not automatically evidence against LALR.

A merge that costs nothing at all

On S → C C the three merges take 10 states to 7 and no cell gains a second action. The merged lookahead on C → d· is { $, c, d }, which happens to be exactly FOLLOW(C).

So a union is not automatically harmful. Whether it hurts depends on whether the two members' lookahead sets overlap in a way that produces two different reductions in one cell — and on this grammar they do not, because there is only one completed item with that core.

The union is per item, not per state

When two states merge, each item takes the union of the lookaheads that that item had. It is not the union of all lookaheads in the state. On S → C C, the item S → C·C keeps its own lookahead $ while C → ·c C picks up c and d.

Merging the whole state's lookahead pool into every item would invent actions the grammar never permits, and would turn a clean LALR table into a conflicted one. The page checks that every merged item holds exactly the union of its own members' lookaheads.

Merging preserves the state count, not the power

LALR has exactly the LR(0) state count, and SLR has it too, yet the three tables differ in what they accept. On the assignment grammar SLR has one conflict and LALR none, on the same ten states.

So the count carries no information about power. What changes between the rungs is the reduce policy applied to a shared automaton, not the automaton.

A shift/reduce conflict survives every rung

S → S S | a is ambiguous, so it has a shift/reduce conflict in LR(0), SLR, LALR and canonical LR(1) alike: the page builds 4 states, performs 0 merges and finds one conflict in both the canonical and the merged table.

That is the check behind the claim that merging cannot create a shift/reduce conflict: the count is the same on both sides, and here the count is one.

Every rung reads the same automaton

The item sets of the LR(0) automaton are the cores of the canonical collection. So you build the automaton once and then choose a reduce policy: everything for LR(0), FOLLOW for SLR, merged lookaheads for LALR, own-state lookaheads for canonical LR(1).

That is why SLR, LALR and LR(0) always report the same state count, and why only canonical LR(1) can report a larger one.

"LALR has more states than SLR, because it is more powerful"

Why it tempts: power usually costs something, and merging sounds like it should add states.

The correct rule: LALR has exactly as many states as LR(0) and SLR, because every LR(0) state is a core and every core is one LALR state. On all six grammars here the two counts are equal: 7 and 7, 13 and 13, 10 and 10, 12 and 12, 5 and 5, 4 and 4.

What is bought instead: the same table size with the reduce rows narrowed, so some cells that held two actions now hold one.

"Merging two LR(1) states can create a shift/reduce conflict"

Why it tempts: merging is described as lossy, and a conflict sounds like the natural loss.

The correct rule: it cannot. A shift on a needs an item with the dot before a, and that item is determined by the core, so every member has it. A member that also holds [A → α·, a] already had both actions.

The witness: S → S S | a has one shift/reduce conflict in the canonical table and one in the merged table — the same one.

"An LR(1) grammar is automatically LALR(1)"

Why it tempts: the ladder is often drawn as a straight line, and the top rung is assumed to imply the rest.

The correct rule: S → a A d | b B d | a B e | b A e with A → c and B → c is LR(1) and not LALR(1). The two states after ac and after bc share a core with swapped lookaheads, and merging them creates a reduce/reduce conflict on d and on e.

What it costs: a merged parser that resolves the conflict to the earlier production accepts 2 of the grammar's 4 strings.

"A canonical LR(1) table is always conflict-free"

Why it tempts: the canonical construction is presented as the most powerful of the four, and "most powerful" is read as "always works".

The correct rule: canonical LR(1) handles every deterministic context-free language, which is not every grammar. Two of the six grammars on this page conflict in LR(1) itself: S → A | B with A → a and B → a, and the ambiguous S → S S | a.

The consequence: a conflict in the canonical table settles the question. Merging cannot remove it, because the union only ever adds actions.

"The lookahead is the next symbol of the right-hand side"

Why it tempts: the item is written with the dot in the middle, and the symbol after the dot is the obvious candidate.

The correct rule: the lookahead is the terminal that may follow the whole right-hand side, once it has been reduced. The symbol after the dot is part of β and is already accounted for by FIRST(βa).

The check: on S → C C, the item S → ·C C has lookahead $, but the symbol after its dot is C — a nonterminal, which could never be a lookahead.

"SLR and LALR place reduces in the same cells, so the tables are the same"

Why it tempts: both have the same number of rows, and the number of rows is what you usually count.

The correct rule: the rows are the same and the entries are not. The merged lookahead is a subset of FOLLOW — never wider — so LALR has fewer reduce entries and therefore fewer conflicts. On the assignment grammar SLR has 1 conflict and LALR 0.

How often it matters: of the 27 completed items in these six grammars, only one has a lookahead set strictly inside FOLLOW. Rare, and decisive.

Pattern 1 — "the number of states in SLR, LALR and LR(1) is n1, n2, n3"

The question gives a small grammar and asks for the relationship between the three counts, as an option over inequalities. Nothing needs to be parsed; only counted.

The reasoning it demands: SLR and LALR share the LR(0) automaton, so their counts are equal. Canonical LR(1) refines that automaton and can only split states, so its count is greater than or equal to theirs.

The shortcut and its assumption: answer n1 = n3 ≤ n2 and check whether the options offer strict inequality. The assumption is that the grammar is not so small that canonical LR(1) also fails to split — the page's GF, with 4 states in every rung, is exactly that case.

Pattern 2 — "is this grammar LL(1), SLR(1), LALR(1) or LR(1)?"

Four options, one grammar, and the options are statements of the form "X but not Y". The work is to find the highest rung the grammar reaches and the lowest one it fails.

The reasoning it demands: work up the ladder and stop at the first conflict. A canonical-table conflict ends it. A clean canonical table with a conflicted merged table means LR(1) and not LALR(1). A clean merged table with a conflicted SLR table means LALR(1) and not SLR(1).

The common wrong approach: testing only the top rung. "It is LR(1)" is compatible with three different options, so the lower rungs must be checked too.

Pattern 3 — "when can an LALR parser have a shift/reduce conflict?"

The options offer SLR, LR(0), canonical LR(1), and "when it has a reduce/reduce conflict". The answer turns on one direction of one argument.

The reasoning it demands: merging preserves shift/reduce conflicts exactly and can only create reduce/reduce ones. So an LALR shift/reduce conflict exists if and only if the canonical table has one.

The trap: the option that mentions reduce/reduce. It is the conflict merging creates, but the question asks about shift/reduce, and the two are different cells.

Pattern 4 — "which of these statements is/are TRUE?"

A multiple-select item over four claims about the LR family. Each claim is one of the facts on this page, and each has a counterexample here.

The reasoning it demands: for each claim, either a proof or a witness. "Merging cannot create shift/reduce" is proved by the core argument. "Not every LR(1) grammar is LALR(1)" is witnessed by the four-string grammar. "LALR has the LR(0) count" is witnessed by every grammar in the table.

The shortcut and its assumption: eliminate the claims that use a superlative ("always", "never", "more powerful than"), then verify the survivors. The assumption is that the examiner wrote one false claim per pair — true often enough to check first, never enough to skip the check.

MCQGATE CSE 2005

Consider the grammar S → ( S ) | a. Let the number of states in the SLR(1), LR(1) and LALR(1) parsers for the grammar be n1, n2 and n3 respectively. The following relationship holds good:

(A) n1 < n2 < n3    (B) n1 = n3 < n2    (C) n1 = n2 = n3    (D) n1 ≥ n3 ≥ n2

Answer: B — n1 = n3 < n2

Computed, not remembered. The page builds all three automata for this grammar: 6 LR(0) states, 10 canonical LR(1) states, 6 merged LALR states. SLR uses the LR(0) automaton, so n1 = 6; LALR merges that collection, so n3 = 6; canonical LR(1) splits states, so n2 = 10.

Why D fails. It allows n1 > n3 and n3 > n2. Neither can happen: the merged collection is the LR(0) collection, and canonical LR(1) can only be larger.

Why C fails. It claims canonical LR(1) has no more states than LR(0), which fails whenever two states share a core and differ in lookahead — here three pairs do.

Note on the wording. The chapter-wise compilation's text garbles the production. The page computes both readings that reproduce the stated answer — S → ( S ) | a and S → S ( S ) | a — and both give 6, 10 and 6, so the answer does not depend on which was printed.

MCQGATE CSE 2003

Assume that the SLR parser for a grammar G has n1 states and the LALR parser for G has n2 states. The relationship between n1 and n2 is:

(A) n1 is necessarily less than n2   (B) n1 is necessarily equal to n2   (C) n1 is necessarily greater than n2   (D) none of the above

Answer: B — n1 is necessarily equal to n2

The argument. The LR(0) collection is the set of distinct cores. The LALR collection is the set of distinct cores with lookaheads attached, and two canonical states with the same core become one merged state. So the number of merged states equals the number of distinct cores, which is exactly the number of LR(0) states. SLR uses the LR(0) collection, so its count is that same number.

Checked here. On all six grammars the two counts are equal: 7/7, 13/13, 10/10, 12/12, 5/5, 4/4.

Why the word "necessarily" matters. Without it, "equal" would be a claim about one grammar. With it, the question is whether any grammar can separate them — and none can, because the equality is a counting identity, not a coincidence.

MCQGATE CSE 2008

An LALR(1) parser for a grammar G can have shift-reduce (S-R) conflicts if and only if:

(A) the SLR(1) parser for G has S-R conflicts
(B) the LR(1) parser for G has S-R conflicts
(C) the LR(0) parser for G has S-R conflicts
(D) the LALR(1) parser for G has reduce-reduce conflicts

Answer: B

Why B. Merging cannot create a shift/reduce conflict. A shift on a terminal a needs an item with the dot before a, and whether such an item exists is fixed by the core, so every member of a merged group has it. A member that also holds [A → α·, a] already had the shift and the reduce itself. Hence the two tables have shift/reduce conflicts in exactly the same situations.

Why A fails. SLR conflicts more often than LALR, because FOLLOW is a wider lookahead. The assignment grammar is the witness: 1 shift/reduce for SLR, 0 for LALR.

Why C fails. LR(0) reduces on every terminal, so it conflicts even more often than SLR.

Why D fails. It answers a different question. Reduce/reduce is the conflict merging can create; the question asks about shift/reduce.

NATOriginal practice question

For the grammar S → C C, C → c C | d, how many states does the canonical LR(1) collection contain?

Answer: 10

The LR(0) collection has 7 states. Three of them split into two when lookaheads are attached: the state reached by c from I0 splits from the one reached by c from itself, and the two states holding C → d· and C → c C· each split by lookahead. 7 + 3 = 10.

Why not 7. 7 is the LR(0) count, and the LALR count, and the SLR count. The canonical collection is the only one of the four that is larger.

Edge case. A grammar can also have the same count in all four, if no two canonical states share a core: the page's GF has 4 states in every rung.

MCQOriginal practice question

Which one of the following can happen when canonical LR(1) states with equal cores are merged to form an LALR(1) table?

(A) a new shift/reduce conflict appears
(B) a new reduce/reduce conflict appears
(C) the number of states increases
(D) the language accepted becomes strictly larger

Answer: B

A merge unions lookaheads, and two members can hold different completed items with complementary lookaheads, so one cell can end up with two reductions. The four-string grammar is the witness: A → c· and B → c· end up on both d and e.

Why A fails. The shift side is core-determined, so a member would already have had both actions.

Why C fails. Merging only ever reduces the count, to the LR(0) count.

Why D fails. Merging can only add actions, and an added action either is resolved by a rule or rejects an input. It never accepts a string the canonical parser rejects.

MSQOriginal practice question

Which of the following statements are TRUE? Select all that apply.

  1. An LALR(1) parser has exactly as many states as an LR(0) parser for the same grammar.
  2. An SLR(1) parser has exactly as many states as an LALR(1) parser for the same grammar.
  3. Every LR(1) grammar is also LALR(1).
  4. A grammar whose canonical LR(1) table has a reduce/reduce conflict cannot be LALR(1).

Answer: A, B and D

A and B are the same counting identity seen twice: the merged collection has one state per distinct core, and the LR(0) collection is the set of distinct cores. SLR uses that collection unchanged. All six grammars here confirm both.

C is false. S → a A d | b B d | a B e | b A e with A → c and B → c is LR(1) and not LALR(1): 14 canonical states, no conflict, and two reduce/reduce cells after one merge.

D is true. Merging only adds actions, so a conflict already present in the canonical table is still there afterwards. It is a necessary condition, not a sufficient one.

The distinction being tested. Necessary versus sufficient. D says a canonical conflict rules LALR out; it does not say a clean canonical table rules LALR in.

MCQOriginal practice question

Consider S → a A d | b B d | a B e | b A e, A → c, B → c. Which statement is TRUE?

(A) it is SLR(1) but not LALR(1)
(B) it is LALR(1) but not canonical LR(1)
(C) it is canonical LR(1) but not LALR(1)
(D) it is neither LALR(1) nor canonical LR(1)

Answer: C

The canonical table has 14 states and no conflict, so the grammar is LR(1). After the single merge of the two states holding A → c· and B → c·, both lookahead sets become { d, e } and two cells hold two reductions.

Why A fails. SLR also conflicts here: FOLLOW(A) and FOLLOW(B) are both { d, e }, so the SLR table has reduce/reduce cells as well.

Why B fails. LALR is weaker than canonical LR(1), so a grammar cannot be LALR(1) and not LR(1).

Why D fails. The canonical table is clean, which is exactly what LR(1) means.

The shortcut. If two states differ only in swapped lookaheads, expect LR(1)-but-not-LALR(1). The assumption is that the swap is complementary, which is why the union conflicts; here it is.

NATOriginal practice question

For the grammar S → C C, C → c C | d, how many items does the initial canonical LR(1) state I0 contain?

Answer: 6

I0 = [S′ → ·S, $], [S → ·C C, $], then two C productions each with two lookaheads: [C → ·c C, c], [C → ·c C, d], [C → ·d, c], [C → ·d, d]. Six items over four cores.

Why not 3. Three is the LR(0) closure count: the same items with no lookahead. The doubling comes from FIRST(C $) = { c, d }.

Edge case. In state I2, S → C·C, the second C is followed by the end marker, so its closure has 3 items, not 6. The lookahead is recomputed per state.

Definitions in one line each

  • LR(1) item: [A → α·β, a] — a production with a dot and one terminal.
  • Lookahead: the terminal that may follow the whole right-hand side when this item is used to reduce.
  • Closure: for [A → α·Bβ, a] and B → γ, add [B → ·γ, b] for each b in FIRST(βa).
  • GOTO: advance the dot over X, then close.
  • Reduce rule: [A → α·, a] writes a reduce in column a only.
  • Core: the item set with lookaheads erased.
  • LALR merge: one state per core, lookahead on an item is the union over members.

The procedure, in five lines

  1. Add the augmented production S′ → S and index every production.
  2. Compute FIRST and nullable by repeated passes until nothing changes.
  3. Build the LR(0) automaton: closure, then goto, keeping distinct sets.
  4. Rebuild with lookaheads: closure uses FIRST(βa). If this table conflicts, stop — the grammar is not LR(1).
  5. Group states by core, union the lookaheads. If the merged table is clean, the grammar is LALR(1).

The traps, ranked by how often they are made

  • Claiming LALR has more states than SLR.
  • Claiming merging can create a shift/reduce conflict.
  • Claiming canonical LR(1) is always conflict-free.
  • Giving closure items the parent's lookahead instead of FIRST(βa).
  • Unioning a whole state's lookaheads into every item instead of per item.
  • Reading the lookahead as the symbol after the dot.
  • Calling a grammar ambiguous because SLR conflicts on it.

Four questions that decide almost every item

  • Which automaton? SLR, LALR and LR(0) share one; only canonical LR(1) is larger.
  • Which lookahead? FOLLOW for SLR, the merged union for LALR, the state's own set for LR(1).
  • Which conflict kind? Merging creates only reduce/reduce; shift/reduce is inherited.
  • Where did it stop? The first rung that conflicts names the class from above.

One-sentence summary

Canonical LR(1) attaches to each item the one terminal that can follow its head in that state, which makes the reduce local and the automaton larger; LALR buys the automaton back by merging states with the same core and unioning their lookaheads, which is free except when two different reductions end up sharing a terminal.
