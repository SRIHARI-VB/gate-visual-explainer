Topic and objective

TOPIC: Path MTU discovery, and the effective send size it produces: the path MTU as the smallest hop on the way, the Don't Fragment probe and the ICMP message that answers it, the Next-Hop MTU field, the plateau table used when that field is empty, the floors of 68 and 1280, and what a sender does when the answer never comes.

LEARNING OBJECTIVE: Given a list of hop MTUs, state the path MTU and the largest segment that fits over IPv4 and over IPv6. Given a peer's advertised MSS and a path, compute the effective send size and the datagram it builds. Given a returned total length and no next-hop MTU, run the plateau search and state how far it lands below the truth. Given a message reporting a value below a floor, say whether it is accepted.

I read the request as the discovery procedure and the arithmetic it feeds: the MSS lesson before this one computes a promise from a local link, and this page supplies the other half, the size the path will actually carry.

Section 10 of the GATE 2027 CS syllabus, read from the official PDF on 2026-11-04, prints: "TCP- flow control and congestion control, socket API; DNS and HTTP." A TCP sender chooses its segment size from this mechanism, so the flow-control clause cannot be applied without it.

Prerequisites

  • The MSS option — that the MSS counts data only, and is the datagram size minus 40.
  • IP fragmentation — the MTU, the DF bit, the identification and offset fields.
  • ICMP — the message types and how a router reports a drop.
  • Arithmetic: subtraction from a fixed ceiling, taking a minimum of several numbers, and percentages.

No network and no simulator are needed. Every number on the page is computed when the page loads.

The five ideas, in one line each

  • The path is the minimum of its hops, and the first hop is only a starting guess.
  • DF plus a message turns a silent drop into a measurement: one step per decrease.
  • The field counts headers: 1400 means 1400 with the IP header, so 1360 of data.
  • Floors hold: 68 octets over IPv4, 1280 over IPv6, and a lower report is discarded.
  • Silence needs a fallback: clamp the MSS, or probe without ICMP.

Intuition first: a doorway you cannot see

You are carrying parcels through a building whose doorways are of different widths, and you cannot see the narrowest one. You know the width of the first door, because you are standing in it. So you build a parcel to fit that door and set off. When it does not fit, someone at the narrow doorway sends back a note saying how wide the door is, and you rebuild the parcel to that width. Nothing tells you the width in advance; the note is the only measurement you get.

Educational interpretation The doorway explains why the first hop is the only starting point; it does not explain why the note counts the parcel's own wrapper, which scene 4 supplies.

Vocabulary, every term in words

Link MTU — the largest datagram one link carries without fragmenting.

Path MTU — the smallest link MTU over all the links on the path.

DF bit — the Don't Fragment flag in an IPv4 header; a router may not fragment the datagram.

Datagram Too Big — RFC 1191's name for ICMP type 3 code 4.

Next-Hop MTU — the 16-bit field that message carries, counting the IP header.

Plateau — a table value standing for a group of similar real MTUs.

Packet Too Big — the IPv6 message, ICMPv6 type 2, carrying an MTU.

Black hole — a path that drops packets without returning the message that explains why.

Why a host cannot simply ask

No field in IPv4 or IPv6 carries the path MTU. Routers know only their own next hop, and the path is a property of the whole route, which may change between two datagrams. The only number a host has at the start is the MTU of the link it is attached to.

So discovery is a conversation: send something too large, learn, send smaller. The design question is how few messages that conversation can take, and the Next-Hop MTU field is the answer to it.

What fragmentation would have cost

Before discovery, a host could let routers fragment. Then a 1500-byte datagram on a 1400-byte path becomes a 1400-byte fragment and a 100-byte fragment, and the loss of either one costs the whole datagram a retransmission.

Fragmentation is not wrong, it is expensive: it multiplies the number of things that can be lost per unit of data. Discovery avoids it by never producing the second fragment.

The 576-octet rule, in one line

RFC 1191 quotes RFC 1122's rule: a host must not send an IP datagram larger than 576 octets unless it has permission from the receiver. For TCP, that permission is the peer's MSS, so the limit is 40 plus the peer's MSS.

A default datagram of 576 gives a default MSS of 536, and that is exactly the value assumed when no MSS option arrives at all.

The four numbers this lesson keeps returning to

1400 — the tunnel path in every example, and the bottleneck hop.

1360 — 1400 minus 40: the largest segment that fits, over IPv4.

1006 — the plateau an old-style search lands on, 394 bytes low.

1280 — the IPv6 floor, leaving 1220 bytes of data.

Example 1 — the promise, the path and the gap

Given a host on a 1500-byte Ethernet link whose peer is reached over a path with hops 1500, 1400, 1500. Asked the MSS it advertises, the datagram it builds, and whether that datagram passes.

The advertised MSS is 1500 − 20 − 20 = 1460. The datagram is 1460 + 40 = 1500 bytes. The path MTU is the smallest hop, 1400, so the datagram is 1500 − 1400 = 100 bytes too large and is dropped at hop 2.

Mathematical derivation The page computes 1460, 1500, 1400 and 100 at load and prints them in scene 1.

Example 2 — the effective size, two ways

Given the same 1400-byte path, with a peer that advertises 1300 in one run and 1460 in another. Asked the effective send size in each.

The path ceiling is 1400 − 40 = 1360. With a peer at 1300 the minimum is 1300, and the datagram is 1340 bytes, which fits. With a peer at 1460 the minimum is 1360, and the datagram is 1400 bytes, which also fits, exactly.

Mathematical derivation 1300 + 40 = 1340 ≤ 1400 and 1360 + 40 = 1400 ≤ 1400, so both choices satisfy the path; only the first satisfies the peer as well.

Example 3 — the probe, counted in steps

Given a host that assumes 1500 and a path whose MTU is 1400, with a router that fills in the Next-Hop MTU field. Asked how many messages and how many datagrams are lost before the estimate is right.

One datagram is lost, one message is received, and the estimate becomes exactly 1400. The next datagram is 1400 bytes and is delivered. So: one loss, one message, one step.

Verified fact RFC 1191 section 4 requires the router to put the next-hop MTU in the message, which is what makes a single step possible.

Example 4 — the same probe without the field

Given the same path and a router that leaves the field zero, so the host must use the plateau table. Asked the estimates and the final error.

The greatest plateau below 1500 is 1492, which is still too large and is lost. The greatest plateau below 1492 is 1006, which fits. The estimate ends at 1006, which is 394 bytes below 1400, or 28.14 per cent.

Mathematical derivation 1400 − 1006 = 394 and 394 / 1400 = 0.2814; the page recomputes both and prints them in scene 6.

Example 5 — the IPv6 floor

Given an IPv6 path whose narrowest link is 1280 bytes, and a Packet Too Big message that reports 1000. Asked what the estimate becomes, and what the largest segment holds.

The message is below the IPv6 minimum link MTU, so it is discarded and the estimate stays 1280. The data is 1280 − 40 − 20 = 1220 bytes. Over IPv4 the same path would leave 1240, but that is not the version in use.

Verified fact RFC 8201 section 4 requires the message to be discarded and forbids reducing the estimate below the IPv6 minimum link MTU; RFC 8200 section 5 fixes that minimum at 1280 octets.

Example 6 — the black hole, and the clamp

Given a 1400-byte path, a host that advertises 1460, and a firewall that drops all ICMP errors. Asked why the connection opens and then stalls, and what a clamp does.

The handshake uses 60-byte segments, which pass; the first full-size segment is 1500 bytes, which does not, and no message comes back. Retransmissions repeat the same size. Clamping the advertised MSS to 1360 makes every datagram 1400 bytes, which fits.

Verified fact RFC 8201 section 1 names this a black-hole connection: the handshake completes and the transfer hangs.

Example 7 — the efficiency cost of a narrow path

Given four paths: 1500, 1492, 1400 and 1280, all over IPv4 except the last, which is read both ways. Asked the share of each datagram that is data.

1460/1500 = 97.33 per cent; 1452/1492 = 97.32; 1360/1400 = 97.14; 1240/1280 = 96.88 over IPv4; and 1220/1280 = 95.31 over IPv6.

The lesson is not that narrow paths are bad, but that the header share is fixed while the payload shrinks, so the cost grows faster than the MTU falls.

The boundaries, each with its number

Six cases where the arithmetic changes behaviour: the 68-octet floor, the IPv6 floor, a zero in the message, the default when no MSS arrives, a path that is wider than the first hop, and a message that arrives after the path widened.

The estimate never falls below 68

68 octets is the size every router must be able to forward, so RFC 1191 forbids reducing the estimate below it, and the Next-Hop MTU field is never filled with a smaller value.

68 − 40 = 28 bytes of data, which is legal and nearly useless; the floor exists to keep the mechanism from producing an unsendable number.

The IPv6 floor is 1280, and a lower report is discarded

Every IPv6 link must carry 1280 bytes. A Packet Too Big reporting less contradicts the protocol, so it is dropped and the estimate stays at 1280.

This is a difference in kind from IPv4, where a low report is simply a small path. On IPv6 a low report is evidence of a broken or forged message.

A zero in the field is not a zero-byte path

A zero means the router never implemented the field. The host must not read it as an MTU of zero; it must fall back to a search or to 576 bytes without DF.

The plateau search from 1500 lands on 1006 after two steps, which is what the fallback costs when the field is missing.

No MSS option means 536, not "anything"

If the peer sends no MSS option, the send size defaults to 536 bytes, which is the 576-octet datagram minus 40. It is a bound, not a permission.

Note that 576 is not itself a plateau: it sits inside the 508 group, so an old-style search for it lands on 508.

A path can be wider than the first hop

The first hop is an upper bound only when every later hop is at least as wide. A host on a 1280-byte link reaching a 1500-byte path is bounded by its own link, and discovery has nothing to find.

That is why the estimate starts at the first hop and only ever falls on evidence: starting low is safe, starting high is what the mechanism is for.

A message arriving after the path widened

Routes change. A Datagram Too Big message that was generated before a re-route can arrive afterwards and report a value that no longer holds. RFC 1191 handles this by allowing the estimate to fall on any message and to rise only on a deliberate probe, and by ageing a cached estimate back to the first hop after about ten minutes.

The asymmetry is the point: a stale low estimate costs throughput, a stale high estimate costs dropped data, so only the first is tolerated without evidence.

Seven beliefs that produce a wrong answer

Each is paired with the counterexample that breaks it. Every counterexample is computed by the page.

1 — "The path MTU is the first hop's MTU"

Wrong: the path MTU is the smallest link MTU over the whole path, and the first hop is only the one number the host knows.

Counterexample: hops 1500, 1400, 1500 have a first hop of 1500 and a path MTU of 1400. A 1500-byte datagram built from the first hop is dropped at hop 2.

2 — "The next-hop MTU is a payload size"

Wrong: the field counts the IP header and excludes link headers, so it is comparable with a datagram size.

Counterexample: a report of 1400 leaves 1360 bytes of data over IPv4, not 1400. Reading it as data overstates the segment by 40 bytes, and by 60 over IPv6.

3 — "A larger report means the path grew"

Wrong: a host must never raise its estimate because a message says so. The message may be stale, forged, or from a different path to the same destination.

Counterexample: a message reporting 9000 on a 1400-byte path would raise the estimate by 7600 bytes and lose every datagram that followed.

4 — "DF only matters on IPv6"

Wrong, and backwards: the DF bit is an IPv4 field, and it is the whole of the IPv4 mechanism. IPv6 has no DF bit at all, because routers never fragment.

Counterexample: IPv6 needs no flag to force a message, while IPv4 needs DF set on every datagram or the router will fragment silently and never report.

5 — "Discovery finds the exact path MTU"

Wrong when the field is missing: the plateau search is allowed to underestimate, and it does so by design.

Counterexample: over a 1400-byte path the search ends at 1006, which is 394 bytes and 28.14 per cent low, and it never notices.

6 — "A dropped ICMP message just costs one packet"

Wrong: it costs every packet of that size, indefinitely, because nothing else in the transport layer changes the size.

Counterexample: the 60-byte handshake succeeds and the 1500-byte data segment is retransmitted unchanged, so the connection is open and transfers nothing.

7 — "Lowering the estimate below the IPv6 floor is safer"

Wrong: the floor is a requirement on the links, so a report below it is not a smaller path but an invalid message. Following it produces segments no compliant path needs and hides the real fault.

Counterexample: a Packet Too Big reporting 1000 on an IPv6 path is discarded and the estimate stays 1280, leaving 1220 bytes of data. Reducing to 1000 would leave 940 and treat a broken message as a fact about the network.

How this becomes a question, and the procedure that answers it

Four shapes appear: a path MTU from a hop list, an effective segment size from two numbers, a plateau search, and a floor test. Each has a fixed procedure, and each has one step that is usually skipped.

Shape 1 — the path MTU and the segment

1. List the link MTUs and take the smallest.

2. Subtract the fixed headers: 40 for IPv4, 60 for IPv6.

3. Add the headers back to check the datagram fits exactly.

The skipped step is step 2's version: subtracting 40 on an IPv6 path overstates the data by 20 bytes.

Shape 2 — the effective send size

1. Compute the path ceiling as the path MTU minus the headers.

2. Take the minimum of that and the peer's advertised MSS.

3. State the datagram as the answer plus the headers, and compare with the path.

The skipped step is step 2: using the peer's value when the path is stricter, or the path when the peer is.

Shape 3 — the plateau search

1. Start from the total length of the datagram that was dropped.

2. Take the greatest plateau strictly below it.

3. Repeat while the value still exceeds the true path MTU, then state the underestimate.

The skipped step is step 3's direction: the plateau must be strictly below the returned length, because a value equal to it has already been proved too large.

Shape 4 — the floor test

1. Identify the IP version, because the floors differ: 68 and 1280.

2. Compare the reported value with the floor.

3. Below the floor, discard the message and keep the estimate; at or above it, lower the estimate.

The trap is treating the IPv4 floor as a lower bound on the estimate only: on IPv6 it also invalidates the message.

NATOriginal practice

A path crosses links of 1500, 1400 and 1500 bytes. A TCP connection over IPv4 uses this path. The largest amount of TCP data one segment can carry without fragmentation is ______ bytes.

Answer: 1360

The path MTU is the smallest hop, 1400. Over IPv4 the fixed headers are 20 + 20 = 40, so the data is 1400 − 40 = 1360.

Why 1460 appears. Using the 1500-byte first hop instead of the path. Why 1400 appears. Reading the path MTU as a data size and forgetting the two headers.

MCQOriginal practice

A router returns an ICMP type 3 code 4 message with a Next-Hop MTU of 1400. What does the 1400 count?

  1. The largest TCP payload that could have been forwarded.
  2. The largest IP datagram that could have been forwarded, including the IP header.
  3. The MTU of the link the datagram arrived on.
  4. The number of bytes by which the datagram exceeded the next hop.

Answer: B

The field is defined as the size of the largest datagram that could be forwarded along the path without being fragmented at that router, counting the IP header and IP data and excluding lower-level headers.

Why A appears. Reading it as a payload, which would overstate the segment by 40 bytes over IPv4. Why C appears. Confusing the incoming link with the next hop, which is the one that refused it. Why D appears. It is a size, not a difference.

NATOriginal practice

A host receives a Datagram Too Big message with a zero in the Next-Hop MTU field, after sending a 1500-byte datagram over a path whose MTU is 1400. Using the plateau table, the host's estimate after two steps is ______ bytes.

Answer: 1006

The greatest plateau below 1500 is 1492, which is still too large. The greatest plateau below 1492 is 1006, which fits.

Why 1492 appears. Stopping after one step, which is not yet small enough. Why 1400 appears. Using the true path MTU, which a zero in the field does not reveal.

MSQOriginal practice

Which of the following are true of path MTU discovery as RFC 1191 specifies it for IPv4?

  1. The estimate may be reduced below 68 octets if the message says so.
  2. The estimate must never be increased in response to a Too Big message.
  3. An attempt to raise the estimate must wait at least 5 minutes after a Too Big message.
  4. Setting the DF bit is optional, because routers fragment anyway.

Answer: B and C

B is the asymmetry rule: a message may lower the estimate but never raise it. C is the timer, with 10 minutes recommended.

A is false: the estimate must never go below 68 octets. D is false: DF is what forces the router to report instead of fragmenting, so without it there is no measurement at all.

MCQOriginal practice

An IPv6 node on a path whose MTU is 1280 receives a Packet Too Big reporting an MTU of 1000. What should it do?

  1. Reduce the path MTU estimate to 1000 and send 940-byte segments.
  2. Discard the message and keep the estimate at 1280.
  3. Reduce the estimate to 1280 and start fragmenting at the source.
  4. Raise the estimate to the local link MTU and probe again.

Answer: B

Every IPv6 link must carry 1280 bytes, so a report below the IPv6 minimum link MTU is inconsistent with the protocol and must be discarded; the estimate must not fall below 1280.

Why A appears. Treating a broken message as a fact about the path. Why C appears. The estimate is already 1280, so there is nothing to reduce. Why D appears. Raising needs a deliberate probe after the timers, not a response to a message.

NATOriginal practice

A peer advertises an MSS of 1300. The path MTU is 1400 and the connection runs over IPv4. The size of the largest datagram the sender may build is ______ bytes.

Answer: 1340

The effective send size is the smaller of 1300 and 1400 − 40 = 1360, which is 1300. Adding the 40 bytes of fixed headers gives 1340.

Why 1400 appears. Using the path ceiling and ignoring the peer's stricter promise. Why 1300 appears. Giving the data size when the question asks for the datagram.

MSQOriginal practice

A connection completes its handshake and then transfers nothing, while small requests still work. Which explanations are consistent with a path MTU black hole?

  1. The path MTU is smaller than the datagram size the sender uses.
  2. ICMP error messages are being filtered somewhere on the path.
  3. The receiver's advertised MSS is larger than the path allows.
  4. Lowering the sender's segment size to fit the path would restore the transfer.

Answer: A, B and D

A is the condition: full-size datagrams exceed the path and are dropped. B is why nothing corrects it: the message that would lower the estimate never arrives. D is the cure: a segment that fits is delivered.

C is not required: a receiver may legitimately advertise the MSS of its own link, and the sender is still expected to respect the path. A receiver whose promise exceeds the path is normal, not faulty.

NATOriginal practice

A host caches a path MTU of 1400. It is never reduced again. After how many seconds should the estimate be reset to the first-hop MTU?

Answer: 600

RFC 1191 section 6.3 says a cached estimate that has not been decreased for on the order of 10 minutes should be reset to the first-hop MTU, which is 600 seconds.

Why 300 appears. Confusing the 5-minute minimum between attempts to raise the estimate with the ageing timer. Why 120 appears. Confusing it with the recommended 2 minutes after a successful raise.

Definitions and constants

  • Path MTU: the smallest link MTU over all links on the path.
  • IPv4 headers: 20 bytes; IPv6 base header: 40; TCP: 20. So 40 and 60.
  • Message: ICMP type 3 code 4 (IPv4), ICMPv6 type 2 (IPv6).
  • Next-Hop MTU: 16 bits, counting the IP header, never below 68.
  • Floors: 68 octets (IPv4), 1280 octets (IPv6 minimum link MTU).
  • Default with no MSS option: 536 bytes, from a 576-byte datagram.

Procedures, in the order they are applied

  1. Take the minimum of the hop MTUs to get the path MTU.
  2. Subtract 40 for IPv4 or 60 for IPv6 to get the ceiling.
  3. Take the minimum of that and the peer's MSS to get the effective size.
  4. Probe with DF, or read the Next-Hop MTU field, to learn a decrease.
  5. If the field is zero, take the greatest plateau below the returned total length.

The numbers worth carrying

  • 1400 → 1360 over IPv4 and 1340 over IPv6.
  • 1492 → 1452; 1280 → 1220 over IPv6 and 1240 over IPv4.
  • 1500 → 1492 → 1006: the two-step plateau search, 394 bytes low.
  • 300 / 60 seconds: the minimum waits before raising; 600 / 120 recommended.
  • 600 seconds: when a cached estimate is aged back to the first hop.

The five slips

  • Using the first-hop MTU as the path MTU.
  • Counting the headers inside the MSS, or reading the next-hop MTU as data.
  • Raising the estimate because a message reports a larger path.
  • Reducing the estimate below 68, or below 1280 over IPv6.
  • Assuming the ICMP message will always arrive.

Three sentences to carry into the exam

The path MTU is the smallest link MTU on the path, not the first one, and the largest segment that fits is that number minus the fixed headers: 40 over IPv4 and 60 over IPv6. A host discovers it by setting DF and lowering its estimate on every Datagram Too Big message, which carries the next-hop MTU in two bytes that used to be padding, so one message gives one exact step. When that field is empty the host searches a table of plateaus and may underestimate by a quarter; when the message is filtered altogether the connection is a black hole, and the cures are clamping the advertised MSS or probing without ICMP.

What each source supports, and what it does not

RFC 1191 supports every IPv4 rule on the page, including the plateau values, which are reproduced as a table rather than as prose. RFC 8201 and RFC 8200 support the IPv6 floor and the discard rule. RFC 8899 supports the probing method and the black-hole language.

None of them states a formula for payload efficiency, and none gives the four example paths used here; those paths and the percentages are arithmetic on the sizes this page computes. RFC 1191's plateau table is explicitly an implementation suggestion and not a specification, which the lesson says on the page.

What was not verified, and the assumptions the model makes

No previous-year question is reproduced or attributed anywhere on this page, and no claim is made about how often this topic appears in GATE CSE papers. The four paths are illustrative hop lists, not measurements of any real network. The model assumes a single path with a fixed MTU for the life of the example, IPv4 headers with no options and IPv6 headers with no extension headers, one bottleneck per path, and a peer MSS of 1300 in the clamping example. It does not model equal-cost multipath with different path MTUs, IP options or extension headers, the congestion window, or the full DPLPMTUD state machine, all of which are outside this lesson's scope and are named here so the boundary is explicit.
