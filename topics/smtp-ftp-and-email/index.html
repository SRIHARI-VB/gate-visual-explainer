Topic and objective

TOPIC: SMTP, FTP and email — the three application protocols the GATE 2027 Computer Networks section no longer names.

LEARNING OBJECTIVE: Place the mail user agent, submission server, transfer agents, delivery agent and mailbox in order, with the port each hop uses. Trace one SMTP session command by command and read each reply code by its first digit. Count the round trips of a session as six plus one per recipient, and keep that number separate from the connection count. Separate the envelope the protocol routes on from the header the reader sees. Count the connections and round trips of any number of FTP transfers. Convert an attachment size into the bytes actually sent, using the four-thirds rule and the seventy-six character line.

I read this clause as three questions asked about three protocols: who opens the connection, how many round trips the dialog costs, and how many bytes the message takes. Every counting item below is one of those three.

GATE relevance

Verified fact Class C for 2027 — a useful extension beyond the named syllabus.

The 2026 CS syllabus ended Section 10 with the words "Application layer protocols: DNS, SMTP, HTTP, FTP, Email". The 2027 wording, published by IIT Madras, ends the section with "DNS and HTTP". SMTP, FTP and email are no longer named. That is a statement about the printed clause, not about the layer: DNS and HTTP still sit on the same transport, and the same three questions carry both.

Community observation Before 2027 these protocols were tested as short recall items — which protocol sends, which uses two connections, which port. Those are one-mark questions when they appear, and they now appear inside other questions rather than as their own.

Because the clause is gone, this lesson quotes no previous-year question: I could not verify a paper, set and question number for one, and an unverified attribution is worse than none. Every practice item is written for this lesson and labelled as original.

The five ideas, in one line each

  • Sending and fetching are different protocols. SMTP pushes; POP3 and IMAP pull.
  • One session, one connection, many commands. Recipients lengthen the dialog, never the connection count.
  • The envelope routes; the header is read. Six recipients, four names.
  • FTP is one control connection plus one data connection per transfer. So 1 + n connections and 3 + 3n round trips.
  • Encoding costs a third, and line ends cost more. Four characters per three bytes, wrapped at 76.

Intuition first: the letter, the envelope and the postbox

A letter has two sets of addresses. The envelope carries what the postal system routes on, and the sheet inside carries what the reader sees. You may send one letter to six people by writing their addresses on the envelope and naming only four of them on the sheet — that is Bcc. A post office that cannot deliver returns the letter to the address on the envelope, not to the name on the sheet. And a courier who carries parcels on a separate trip for each parcel, on a route agreed once by telephone, is FTP.

Educational interpretation The analogy carries the two address sets, the bounce and the two connections. It does not carry the wire format or the reply codes, which the next two cards supply.

Formal vocabulary, every term in words

Mail user agent — the program a person types a message in. Outlook, Thunderbird, or a web page.

Submission server — the server that accepts a message from a user, authenticates the user, and queues it. Port 587.

Mail transfer agent — the server that moves a queued message to the next server, or to the destination. Port 25.

Mail delivery agent — the server-side program that writes a message into the recipient's mailbox.

Envelope — the addressing SMTP routes on: one reverse path from MAIL FROM, one forward path per RCPT TO.

Header — the lines the reader sees: From, To, Cc, Subject, and one Received per hop.

Round trip — one request and its reply. Not the same thing as a connection.

The three protocols at a glance

SMTP — RFC 5321. Pushes a message from one server to the next. One TCP connection per session, on port 25 between servers and 587 for submission.

FTP — RFC 959. Moves files. Two TCP connections: control on 21 for the session, data on 20 by default for each transfer.

POP3 — RFC 1939, port 110. Downloads a mailbox and, by default, deletes from the server.

IMAP — RFC 3501, port 143. Keeps the mailbox on the server and synchronises flags and folders.

MIME — RFC 2045 to 2049. Encodes a binary attachment into seven-bit characters so SMTP can carry it.

The SMTP dialog, in full, for one recipient

Lines from the server begin with a three-digit code. Lines from the client begin with a command verb. The exchange is lock-step: one command, one reply, then the next command.

S: 220 mx.example.com ESMTP ready
C: EHLO mail.acme.com → 250 mx.example.com
C: MAIL FROM:<sender@acme.com> → 250 OK
C: RCPT TO:<user@example.com> → 250 OK
C: DATA → 354 Start mail input, end with .
C: (headers, blank line, body, then a line with one dot) → 250 OK: queued
C: QUIT → 221 ByeRead the right column as the server's answer to the line on its left. The 220 arrives without being asked for: the server speaks first. 354 is the only intermediate reply in base SMTP.

Verified fact RFC 5321 section 3.3 fixes the three steps of a transaction — MAIL, one or more RCPT, then DATA — and section 4.1.1.4 fixes the end of data as a line containing only a period.

FTP: what the two connections are for

Control connection — port 21, opened once, full duplex, follows the Telnet conventions, carries commands and replies as text. Login, current directory and transfer type live here.

Data connection — opened for one transfer, closed at the end. Carries the bytes of a file, or a directory listing.

Verified fact RFC 959 section 5.2: the server listens on the control port L = 21, and initiates the data connection from its default data port L − 1 = 20.

POP3 against IMAP, in one table

Where the mail lives. POP3 moves it to the client. IMAP leaves it on the server.

Second device. POP3 sees an empty mailbox. IMAP sees the same mailbox.

What crosses the wire. POP3 sends every body once. IMAP sends a header list and only the bodies a client opens.

State. POP3 has three states — authorisation, transaction, update — and commits deletions in the last. IMAP keeps flags per message on the server.

Which of the four is stateful?

HTTP is stateless: a request carries everything the server needs, and a cookie is the text that supplies memory. SMTP is stateful inside a session — the reverse path, the forward paths and the message data are three buffers that MAIL clears — and keeps nothing between sessions. FTP is stateful across a whole session: the current directory and the transfer type are held by the server until the connection closes. POP3 is stateful in its transaction state, where messages are marked and only deleted at the end.

Mathematical derivation The four statements follow from the standards: RFC 5321 section 3.3 for the three buffers, RFC 959 section 3.1 for the remembered transfer parameters, RFC 1939 section 3 for the three states. "Stateful" is therefore always per session here, never global.

Five worked items, each with its arithmetic shown

Every item here is an original practice question written for this lesson, not a previous-year question — see the Sources tab for why. Each step names the rule it uses, so a wrong answer can be traced to the step that produced it. The numbers are the ones the animation draws.

Example 1 — one session, three recipients

A message goes to three recipients who all have mailboxes on the same server. How many TCP connections and how many round trips does the SMTP session cost?

  1. Write the fixed exchanges: handshake, EHLO, MAIL, DATA, body, QUIT. Six, because each is one request and one reply.
  2. Add one RCPT TO per recipient: three. Each is its own command with its own reply.
  3. Round trips = 6 + 3 = 9.
  4. Connections = 1. A session is one connection; commands lengthen the dialog inside it.

Why 3 appears. That is the recipient count read as a connection count. Why 18 appears. Charging every exchange twice, once in each direction.

Example 2 — fan-out to three domains

The same message goes to three recipients, one each at three different domains. Count the sessions and the round trips, assuming the sending server accepts all three before relaying.

  1. Submission: the sending server is given all three recipients, so 6 + 3 = 9 round trips. One session, three RCPT commands.
  2. Relaying: one session per destination server, each carrying one recipient, so 6 + 1 = 7. A session ends at one server.
  3. Total = 9 + 3 × 7 = 30 round trips.
  4. Sessions and connections = 1 + 3 = 4.

Trap. The recipients are counted twice, once in the submission and once in each relay. That is correct: each is named twice, by two different servers.

Example 3 — three files and a listing

An FTP client logs in, downloads three files and lists the directory, then quits. Count the connections and the round trips.

  1. Control connection: handshake, USER, PASS — 3 round trips, and it stays open. Login is paid once.
  2. Transfers: three RETR plus one LIST is four. A listing uses a data connection like a file does.
  3. Each transfer: PASV, the data handshake, the transfer and its completion — 3 round trips.
  4. Connections = 1 + 4 = 5. Round trips = 3 + 3 × 4 = 15.

Why 4 connections. Forgetting the control connection. Why 12 round trips. Forgetting the login.

Example 4 — what a one-megabyte attachment costs

A 1,000,000-byte attachment is sent in a MIME base64 part, wrapped at 76 characters per line with CRLF line ends. How many bytes of mail data are transmitted?

  1. Groups: ⌈1,000,000 / 3⌉ = 333,334. The ceiling, because the last group may be partial.
  2. Characters: 4 × 333,334 = 1,333,336. Four characters per group, padded to a multiple of four.
  3. Lines: ⌈1,333,336 / 76⌉ = 17,544.
  4. Wire bytes: 1,333,336 + 2 × 17,544 = 1,368,424.

Overhead is 36.84%: one third from the encoding and 2.63% from the line ends. Why 1,333,333 appears. Dividing without the ceiling, which loses the partial last group.

Example 5 — POP3 against IMAP by bytes

A mailbox holds 100 messages of 20,000 bytes each. A client reads headers of about 500 bytes each and opens three messages. Compare the bytes transferred.

  1. POP3 transfers every body once: 100 × 20,000 = 2,000,000 bytes. It has no way to fetch a header without the body.
  2. IMAP transfers every header: 100 × 500 = 50,000. A header list is one fetch.
  3. IMAP then transfers three bodies: 3 × 20,000 = 60,000.
  4. IMAP total = 110,000 bytes, about 18 times less.

Trap. The saving is proportional to what is opened, not absolute. Open all hundred and IMAP sends 2,050,000 — slightly more than POP3, because of the headers.

The boundaries: where each rule stops working

Each card states the condition a rule needs and what changes when the condition fails. These are the cases that separate a correct answer from an almost-correct one.

Port 20 is a default, not a law

RFC 959 defines the server data port as L − 1, so 20 when the control port is 21. But most implementations do not use 20: in active mode they open the data connection from an ephemeral port, and a client announces its own port with PORT rather than accepting the default.

What to answer. If a question asks for the default, 20 is correct. If it asks what a real client does, the honest answer is an ephemeral port, and RFC 1579 is the document that explains why clients moved to PASV instead.

354 is not a success

A 3xx reply in SMTP means the server wants more input. It is the only intermediate class, and in base SMTP exactly one code uses it: 354, sent in answer to DATA.

Counterexample to "3xx is a redirect". That reading comes from HTTP. Here nothing has been accepted at 354; the server may still refuse the message after the final dot, with a 5xx.

A full mailbox and a busy mailbox

552 means the mailbox has exceeded its storage allocation — a permanent condition, so the message bounces. 450 means the mailbox is unavailable for a reason that may pass — temporary, so the message is queued and retried.

The rule. The first digit decides the action and the second decides the subject. Two codes can describe the same mailbox and demand opposite actions.

A line that begins with a dot

A line containing only a period ends the data. So a message line that genuinely begins with a period is sent with two periods, and the receiver removes one. This is dot-stuffing, and it is why the end of data is a sequence of five characters — CR, LF, dot, CR, LF — and not just a dot.

Consequence for counting. A body of n lines that all begin with a dot costs n extra bytes on the wire, which is a legitimate byte-arithmetic question.

Base64 when the size is not a multiple of three

One byte becomes four characters with two = padding characters. Two bytes become four characters with one =. Three bytes become four characters with none. The encoded length is always a multiple of four, so 1, 2 and 3 bytes all cost four characters.

Counterexample to "it is always four thirds". For tiny inputs the padding makes the ratio much worse: one byte costs four, a factor of four, not 1.333.

Pipelining changes the round trips, not the connection

RFC 2920 lets a client send EHLO, MAIL, RCPT and DATA without waiting for each reply. The dialog then costs four round trips — handshake, command batch, body, quit — whatever the recipient count.

What does not change. Still one connection, and still one reply per command, arriving in a batch. A question that says "lock-step" or quotes RFC 5321 alone wants 6 + r.

Two MTAs on one machine, one hop or none

A submission server and a transfer agent are often the same program on the same host. The hop from one to the other is then an internal hand-off, not a TCP session, and adds no Received line.

The rule to state. Count hops as the number of TCP sessions between distinct servers. The header count equals receiving servers, which is what the model here assumes: three sessions, three headers.

Eight-bit extensions exist

RFC 6152 defines 8BITMIME, which lets a server accept eight-bit data without base64. It is negotiated in the EHLO reply, so a client uses it only when the server advertises it.

For the exam. The classic question assumes the seven-bit channel, because the classic encoding answer is base64. If a question names 8BITMIME, the encoding cost disappears and only the line ends remain.

Six beliefs that produce a plausible wrong answer

Each card gives the belief, why it is tempting, the smallest case that refutes it, and the rule to use instead. These come from the shapes of wrong options in this layer's questions, not from a survey of learners.

1. "SMTP sends and receives mail"

Why it tempts. One protocol is described as "the mail protocol", so it seems to do the whole job.

Refutation. A client that only speaks SMTP can send but cannot read a mailbox. Retrieval is POP3 on 110, IMAP on 143, or a web page over HTTP.

Correct rule. SMTP pushes. POP3 and IMAP pull. Two directions, two protocols.

2. "Each recipient opens a connection"

Why it tempts. HTTP trains you that objects equal connections, and recipients feel like objects.

Refutation. One session carries MAIL and then as many RCPT commands as there are recipients. Three recipients on one server are one connection and nine round trips, not three connections.

Correct rule. Recipients lengthen the dialog. Servers, not recipients, decide the connection count.

3. "FTP uses one connection, like HTTP"

Why it tempts. Every other protocol in this layer uses one, so two looks like an error.

Refutation. RFC 959 separates control from data deliberately: commands must not queue behind a large transfer. That is out-of-band control, and it is why n files cost 1 + n connections.

Correct rule. Count the control connection once and add one data connection per transfer, including a listing.

4. "Base64 grows the data by a quarter"

Why it tempts. Four characters for three bytes sounds like one extra in four, which is a quarter.

Refutation. The extra is one character per three bytes, which is one third of the original: 3 → 4 is a growth of 33.3%, not 25%. Then line ends add more, giving 36.84% in the worked example.

Correct rule. Divide the original by three, take the ceiling, multiply by four.

5. "A Bcc recipient costs nothing"

Why it tempts. Bcc is invisible in the delivered message, so it looks like it did not happen.

Refutation. Every Bcc recipient needs a RCPT TO, so it costs one round trip and one mailbox. Three To, one Cc and two Bcc is six RCPT commands for four named addresses.

Correct rule. Hidden from readers, not from servers. The envelope is the count that matters.

6. "4xx and 5xx both mean the message failed"

Why it tempts. Both are negative replies, and both are failures of a sort.

Refutation. A 4xx is temporary and must be retried with the same message; a 5xx is permanent and must not. Treating them alike either loses deliverable mail or damages a sender's reputation.

Correct rule. Read the first digit before reading the words.

The one distinction to carry into the exam

Four pairs get confused, and each is settled by writing a definition rather than by intuition: connection against round trip, envelope against header, control against data, and temporary against permanent. In each pair the two members differ by one countable thing — a handshake, an address, a socket, a retry — and the question always says which it wants if you read the unit before computing.

How this material gets tested now that the clause is gone

Four patterns cover it. The first three are arithmetic and could be asked about any dialog on TCP; the fourth is a statement question. Since 2027, these appear inside DNS, HTTP or TCP items rather than as their own, which makes recognising the pattern more useful than memorising the protocol.

Pattern 1 — count the connections and the round trips

Shape. A dialog with some number of participants, and a question asking for connections, for round trips, or for both. The answer is a small integer.

Procedure. Write the fixed exchanges first, then add one per variable element: a recipient, a transfer, an object. Then ask separately how many connections the protocol opens.

For this clause. SMTP is 6 + r round trips on 1 connection. FTP is 3 + 3n on 1 + n connections. Both are the same shape as HTTP's connection counting, which is why the pattern transfers.

Pattern 2 — choose the protocol for a job

Shape. A one-line description of a task, and four protocol names. Which one is used?

Procedure. Ask the direction. Pushing a message is SMTP. Reading a mailbox is POP3 or IMAP. Moving a file is FTP. Fetching a page is HTTP.

The trap. "Retrieve mail from a server" is not SMTP. The direction decides, and the direction is always in the question.

Pattern 3 — byte arithmetic with an encoding

Shape. A file size, an encoding, a line length, and a question about bytes on the wire or time on a link.

Procedure. Encode first, then wrap, then add the line ends. Divide by the link rate last. Every step is exact integer arithmetic except the ceiling, and the ceiling is the step that is usually forgotten.

Extension. Add a transmission time and the question becomes a delay question, which is how this pattern joins the switching and performance clause.

Pattern 4 — a statement set about the layer

Shape. Four or five statements about ports, statefulness or connection counts; select all that are true.

Procedure. Test each statement against a definition you can state out loud: which protocol opens two connections, which is stateful and for how long, which port belongs to which service, which direction the data flows.

Where it appears now. As a distractor inside a DNS or HTTP item, or as one option in a transport-layer MSQ. A wrong option does not need the clause to be in the syllabus to cost a mark.

The four-step procedure, and where each step can go wrong

1. Name. Name the server and its port from the protocol, not from memory of a number. Fails when 587 and 25 are swapped, or when a retrieval protocol is given a sending port.

2. Open. Say who opens each connection, and how many there are. Fails when FTP's control connection is forgotten, or active and passive are reversed.

3. Run. Count the exchanges in the dialog, fixed part first. Fails when the handshake is folded into the first command.

4. Count. Count the unit the question asked for. Fails when connections are reported where round trips were wanted, or file bytes where wire bytes were wanted.

Why this lesson is still worth an hour, in a 2027 plan

Three reasons, and none of them is nostalgia. The counting pattern is identical to the one HTTP questions use, so the practice transfers directly. The envelope-against-header distinction is the clearest example in the syllabus of a protocol obeying data the reader cannot see. And the byte arithmetic is the only place in Computer Networks where an encoding changes the size of what crosses a link, which is exactly the reasoning a fragmentation or delay question wants. Spend the hour on the three patterns; skip memorising the full command list.

NATOriginal practice

A sending server delivers one message to five recipients, all with mailboxes on the same destination server, in one SMTP session. Counting the TCP handshake as one round trip and the greeting as free, the number of round trips is ______.

Answer: 11

Six fixed exchanges — handshake, EHLO, MAIL, DATA, body, QUIT — plus one RCPT TO per recipient: 6 + 5 = 11. The connection count stays at one.

Why 10 appears. Forgetting the handshake, which is a round trip because no command can be sent before the connection exists. Why 5 appears. Counting only the recipient commands.

MCQOriginal practice

A client logs in to an FTP server, downloads four files, and logs out. How many TCP connections are opened in total, counting the control connection?

  1. 1
  2. 4
  3. 5
  4. 8

Answer: C — 5

One control connection for the session, plus one data connection per transfer: 1 + 4 = 5.

Why 4. The data connections alone. Why 8. Counting a control and a data connection per file, which invents a control connection per transfer.

NATOriginal practice

A 2,000,000-byte attachment is encoded in base64 and wrapped at 76 characters per line, with a carriage return and a line feed at the end of every line. The number of bytes of encoded mail data, rounded to the nearest thousand, is ______ thousand.

Answer: 2737

⌈2,000,000 / 3⌉ = 666,667 groups, so 2,666,668 characters. ⌈2,666,668 / 76⌉ = 35,088 lines, so 70,176 bytes of line ends. Total 2,736,844 bytes, which is 2,737 thousand.

Why 2667. The encoding without the line ends. Why 2736. Rounding down instead of to the nearest thousand.

MSQOriginal practice

Which of the following statements are TRUE?

  1. An SMTP session is stateful between one session and the next.
  2. A 451 reply means the message should be queued and retried.
  3. The Bcc field is normally removed before the message is transmitted.
  4. In passive FTP the client opens the data connection.
  5. The FTP control connection carries the file bytes.

Answer: B, C and D

A 451 is a transient negative reply, so the message is queued (B). A sending client strips Bcc before transmission, which is the whole point of the field (C). In passive mode the server listens and the client dials, so the data connection is opened by the client (D).

Why A is false. SMTP keeps state inside a session — three buffers that MAIL clears — and nothing between sessions. Why E is false. The data connection carries the bytes; the control connection carries commands and replies.

NATOriginal practice

A message is sent to three recipients at three different domains. The sending server accepts all three in one submission session and then relays once to each destination server, one recipient per relay. Counting the TCP handshake in every session, the total number of round trips across all sessions is ______.

Answer: 30

Submission: 6 + 3 = 9. Relays: three sessions of 6 + 1 = 7, so 21. Total 30, over four connections.

Why 21. The relays alone, forgetting the submission. Why 27. Using 6 + 1 = 7 for the submission too, which drops the two extra recipients from the count.

MCQOriginal practice

A user wants the same mailbox readable from a phone and a laptop, with read and deleted flags staying in step, and does not want messages downloaded and removed from the server. Which protocol fits, and on which port does it listen by default?

  1. POP3 on 110
  2. IMAP on 143
  3. SMTP on 25
  4. FTP on 21

Answer: B — IMAP on 143

IMAP keeps the mailbox and the flags on the server, so two devices see one mailbox. POP3's default behaviour moves mail to the client, which is the opposite of what was asked.

Why C. SMTP pushes mail; it cannot read a mailbox. Why A. POP3 can be configured to leave mail, but it does not synchronise flags or folders.

Revision sheet

Definitions, counts, formulas, decision procedures and traps, in the order you would use them. Nothing here needs the animation.

SMTP: the facts worth memorising

  • RFC 5321. Relay on port 25, submission on 587.
  • Transaction: MAIL FROM, then one or more RCPT TO, then DATA.
  • End of data is a line containing only a period; a real leading dot is doubled.
  • Reply classes: 2 success, 3 intermediate, 4 temporary, 5 permanent.
  • 354 is the only 3xx in base SMTP. 220 greeting, 221 bye, 250 ok.
  • One connection per session; round trips = 6 + r.
  • One Received header per receiving server, newest at the top.
  • Mail data is seven-bit ASCII, so binary needs MIME.

FTP, POP3 and IMAP: the facts worth memorising

  • RFC 959. Control on 21, data on 20 by default — the data port is one below the control port.
  • Control stays open; one data connection per transfer, and a listing is a transfer.
  • Connections = 1 + n. Round trips = 3 + 3n.
  • Active: client sends PORT, server dials. Passive: client sends PASV, server answers 227, client dials.
  • Stateful per session: current directory, transfer type, login.
  • POP3 on 110, three states, deletes on quit. IMAP on 143, mailbox on the server, flags synchronised.
  • Base64: four characters per three bytes, wrapped at 76, CRLF on every line.

The three counting formulas

SMTP: connections = 1, round trips = 6 + r
FTP: connections = 1 + n, round trips = 3 + 3n
base64: chars = 4·⌈n/3⌉, wire = chars + 2·⌈chars/76⌉r is the number of recipient commands, n the number of transfers. For the encoded size, the ceiling is the step that is usually forgotten: it is what makes 1,000,000 bytes become 1,333,336 characters rather than 1,333,333.

Plugged in: r = 3 gives 9 round trips; n = 4 gives 5 connections and 15 round trips; 1,000,000 bytes gives 1,368,424 bytes on the wire.

Decision procedure, in four lines

  1. Name the protocol and its port from the job, not from memory. Push is SMTP, pull is POP3 or IMAP, files are FTP.
  2. Say who opens each connection and how many there are. FTP has two kinds; SMTP has one.
  3. Count the exchanges, fixed part first, then one per variable element. Six plus r, or three plus three n.
  4. Count the unit the question asked for. Connections, round trips and bytes are three different answers.

The five slips, one last time

Believing SMTP also receives mail · counting one connection per recipient · forgetting FTP's control connection · growing the data by a quarter instead of a third · treating a 4xx as permanent. Write the unit and the fixed part of the dialog at the top of your working, and none of the five survives.

Standards and official syllabus

  • RFC 5321 — SMTP. Section 3.3 for the three steps of a transaction and the three buffers, 4.1.1.2 to 4.1.1.4 for MAIL, RCPT and DATA, 4.1.1.4 for the end-of-data sequence and dot-stuffing, 4.4 for trace fields, 4.5.4 for the rule that a 5xx is never retried.

What the research did not cover, and the assumptions the model makes

The round-trip convention is the one this repository uses throughout: one round trip for a handshake and one for a command and its reply, with the server's 220 greeting folded into the connection rather than charged separately. A question that piggybacks a command on the third segment of the handshake would give a smaller total and would have to say so. The FTP round-trip count assumes one PASV exchange per transfer and a fresh data connection each time, which is what RFC 959 describes and what the counting questions assume; a client that reuses a data connection would differ, and RFC 1579 notes that real clients do not reuse. The MIME figures assume base64 with a 76-character line and CRLF line ends, and ignore the header lines of the MIME part, which are a few hundred bytes and not proportional to the attachment. The mail-chain figure assumes a submission server and two relays on three distinct hosts, so three TCP sessions; when a submission server and a transfer agent share a host, the hop is internal and the count drops by one. Nothing here was checked against a printed textbook edition, and no claim is made about how often this material will appear in 2027 — the clause no longer names it.
