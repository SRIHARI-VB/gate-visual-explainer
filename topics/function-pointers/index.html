Topic and objective

TOPIC: Function pointers in C — the declarator that names one, the call that goes through one, and the rules that make some of those calls undefined. This is the last Programming-in-C microtopic in Section 4 of the official GATE 2027 CS syllabus that had no lesson of its own.

LEARNING OBJECTIVE: Read any function-pointer declaration into one correct English sentence; write the declaration for a given English sentence; state what f, &f and *f denote; explain why (*p)(3) and *p(3) are different; state the comparator contract a callback must satisfy and name the two ways of breaking it; and say which of these behaviours the C standard calls undefined.

I read this topic as one grammar rule, one decay rule, one contract. The grammar rule gives the reading. The decay rule makes three spellings interchangeable. The contract is what a library like qsort imposes on the function you hand it. Everything else in the topic is a consequence, and every consequence is checked on this page.

The five ideas this page is built on

1. A declarator is a composition. pointer? then a direct-declarator; suffixes attach first, prefixes second, base type last.

2. A function designator decays to a pointer. Except under sizeof and unary &. That single exception list explains three of the four traps here.

3. A call needs a pointer to function. So f(3) and (*f)(3) are the same call, and *f(3) is not a call at all.

4. A comparator returns a sign, not a truth value. Three outcomes, and a difference of two large ints is not one of them.

5. Converting is legal; calling through the wrong type is not. The conversion is guaranteed to round-trip; the call is undefined behaviour.

Intuition first: a phone number, not the conversation

A function pointer is a stored phone number. The number tells you whom to call; it is not the conversation, and it is not the person. You can write the number on a card, copy the card, hand the card to someone else, and later dial it. Nothing about the person changes when the card is copied.

Educational interpretation The analogy is only for the first step: a function pointer is a value you can store, copy, compare and pass, and calling through it reaches code you did not name at the call site. It breaks down on arithmetic — you cannot dial "the next number in the directory" — which is exactly one of the rules in scene ten.

Formal definition: the two objects

A function is a piece of code with a type: a return type and a parameter list. A pointer to function is an object whose stored value is the address of such code.

Verified fact C11 6.5.2.2p1: "The expression that denotes the called function shall have type pointer to function returning void or returning an object type other than an array type."

Verified fact C11 6.3.2.1p4: "A function designator is an expression that has function type. Except when it is the operand of the sizeof operator or the unary & operator, a function designator with type 'function returning type' is converted to an expression that has type 'pointer to function returning type'."

In words: writing f where a value is expected already gives you a pointer to f. There is no separate "get the address" step, and no cost for one.

The declarator grammar, which is the whole reading rule

From C11 6.7.6, with the notation spelled out in words:

declarator := pointer? direct-declarator — a declarator is an optional star group followed by a direct-declarator.

direct-declarator := identifier | ( declarator ) | dd [ n ] | dd ( params ) — a direct-declarator is an identifier, or a parenthesised declarator, or a direct-declarator with a bracket suffix, or a direct-declarator with a parameter-list suffix.

Mathematical derivation The suffixes attach to the direct-declarator and the star attaches to the whole declarator. So the order in which constructors are built is: identifier, then suffixes left to right, then the stars from the inside out, then the base type. Reading that order out loud gives the English sentence. This page's parser is that derivation written as code, and its output is checked against sixteen published readings.

Where the two rules meet

int *f(int) — the suffix (int) attaches to f, so a function is built first; the star then wraps the result. Read out: f is a function taking (int) returning pointer to int.

int (*f)(int) — the parentheses make the star part of the inner declarator, so a pointer is built first; the suffix then wraps that. Read out: f is a pointer to function taking (int) returning int.

Both are legal, both compile, and they are different types. Nothing about the base type int changes: it is applied last in both cases.

What the standard fixes, and what it leaves to the implementation

Verified fact Fixed by the standard: the decay rule; the requirement that a called expression have pointer-to-function type; the adjustment of a function-type parameter to a pointer (6.7.6.3p8); the illegality of sizeof on a function type (6.5.3.4); the requirement that pointer arithmetic use a pointer to a complete object type (6.5.6p2); and that calling through an incompatible converted pointer is undefined (6.3.2.3p8).

Unverified claim Implementation-defined, and therefore not to be quoted as fact in an answer: the size of a function pointer (8 bytes on LP64, 4 on ILP32), and whether a given code address is reachable through an integer. This page uses an LP64 model — 8-byte pointers, 32-bit int — and labels every figure that depends on it.

The call rule, and the three spellings of one address

A call is written E(args) where E has pointer-to-function type. Because a designator already converts to a pointer, f(3) works with no & and no *. Because *p on a function pointer yields the designator again (6.5.3.2p4), and a designator converts back to a pointer, (*p)(3) is the same call. The model resolves f, &f and *f to the same address, 0x401136, and checks that all three agree.

What is not the same: &p, which is the address of the pointer cell, with type pointer to pointer to function; and *p(3), which groups as *(p(3)) because the call binds tighter than the star.

The callback contract

Verified fact The glibc manual on qsort: the compare function "should return an integer less than, equal to, or greater than zero corresponding to whether its first argument is considered less than, equal to, or greater than its second argument. The function must not alter the array's contents, and must define a total ordering on the array elements... the function's return value must not depend on the element addresses or the relative positions of elements within the array."

Three obligations, not one: a sign, no mutation, no address dependence. And the manual's warning: "If two elements compare equal, their order after sorting is unpredictable."

Why a table of pointers is a jump table

If the operations are named by small integers — an opcode — then an array of function pointers indexed by the opcode replaces a chain of tests with one subscript. The model evaluates 1728 three-step programs both ways and gets the same answer 1728 times.

Mathematical derivation An if-chain over k operators tests on average (k+1)/2 conditions; a table tests once. For k = 4 that is 2.5 against 1, so over 1000 instructions, 2500 against 1000. This is a count of tests in a stated model, not a measurement of compiled code — a compiler is free to build the same table for a dense switch.

One sentence to carry into the exam

Read the declarator from the identifier outward, applying suffixes before prefixes and the base type last; remember that f, &f and *f are one address while *p(3) is a different expression entirely; and remember that a comparator returns a sign, so never subtract two values that might overflow.

Worked example 1 — the GATE CSE 2005 item, recomputed

Verified fact The question, as archived: "What does the following C-statement declare?" — int (*f)(int *); — with options (A) a function that takes an integer pointer as argument and returns an integer; (B) a function that takes an integer as argument and returns an integer pointer; (C) a pointer to a function that takes an integer pointer as argument and returns an integer; (D) a function that takes an integer pointer as argument and returns a function pointer.

Step 1: the identifier is f. Step 2: inside the parentheses the star binds first, so f is a pointer. Step 3: outside them, (int *) is the parameter list of what it points at — a function taking a pointer to int. Step 4: the remaining int is the return type.

Answer: C. The page's parser produces exactly this reading and the model checks it. A drops the pointer and calls f a function; B moves the star to the return type; D invents a return type that is itself a function pointer — each wrong option changes one word of the sentence.

Worked example 2 — from English to declaration

"A function taking an int and returning a pointer to a function taking an int and returning an int."

Build from the outside in: the outermost thing is the function that takes the int, so start with f(int). It returns a pointer, so the star goes before f — but the pointer must bind before the parameter list, so it needs parentheses: (*f(int)). That pointer points at a function taking an int, so append the parameter list and put the base type in front: int (*f(int))(int).

Mathematical derivation The parser reads int (*f(int))(int) back as f is a function taking (int) returning pointer to function taking (int) returning int, and the model checks that this is the exact round trip. Note the rejected alternative int (*f)(int)(int): that is a function returning a function, which 6.7.6.2 forbids, and the parser reports it as an error.

Worked example 3 — the signal declaration

void (*signal(int, void (*)(int)))(int)

Step 1: signal( ... ) — signal is a function. Step 2: its parameters are an int and void (*)(int), an abstract declarator meaning a pointer to a function taking an int and returning void. Step 3: the star before signal( ... ) makes the result a pointer. Step 4: the trailing (int) is the parameter list of what that pointer points at.

Reading, as produced by the page's parser: signal is a function taking (int, void (*)(int)) returning pointer to function taking (int) returning void. The return is the previous handler, which is why signal can be used to restore a handler later.

Worked example 4 — the array of pointers

int (*f[3])(int) and int (*f[3])[4] look alike and are different.

First: the brackets bind tighter than the star, so f is an array of 3; each element is a pointer to a function taking an int. Second: the inner declarator is (*f[3]) — again an array of 3 pointers — and the trailing [4] applies to what they point at, so each element is a pointer to an array of 4 ints.

Verified fact The published "C to English Declarations" table lists int (*f11[3])[4] as "an array of 3 pointers to an array of 4 ints" and int *(*f12[3])[4] as "an array of 3 pointers to an array of 4 pointers to int"; both readings are in the parser's sixteen checked cases.

Worked example 5 — the correct comparator, counted

Array [5, 3, 9, 1, 7, 3], comparator (a < b) ? -1 : (a > b) ? 1 : 0, insertion sort that shifts while cmp(key, prev) < 0.

Result [1, 3, 3, 5, 7, 9] in 11 comparisons, against the bounds of 5 (= n − 1) and 15 (= n(n−1)/2). The model checks the sorted output against the platform's own numeric sort and checks the count against both bounds.

Mathematical derivation The count is a property of the algorithm, not of the contract: a different sort on the same array with the same comparator makes a different number of comparisons. Only the two bounds follow from the comparator alone.

Worked example 6 — the subtraction comparator

return a - b; with a = 2000000000 and b = -2000000000.

The true difference is 4000000000, which does not fit in a 32-bit int. On the stated two's-complement model it wraps to −294967296, so the comparator reports that the larger value is smaller. The pair [2000000000, -2000000000] therefore stays in the order it arrived — descending — and the model checks that the output is not ascending.

Two separate defects. The wrap is one; the standard's classification is the other. Signed overflow is undefined behaviour in C, so the wrapped value is what the stated model produces, not what the standard promises. Either way the sign is not the sign of the true difference, and that alone breaks the contract.

Worked example 7 — the boolean comparator

return a > b; returns 1 when the first is larger and 0 otherwise — never a negative number.

With such a comparator every pair reads as "not less", so no element is ever moved: [3, 1, 2] comes back as [3, 1, 2]. The model checks both that the output equals the input and that the output is not ascending.

Why it compiles. The type is right: int-returning, two const void * parameters. The contract is wrong, and a compiler has nothing to check. This is the difference between a type error and a semantic error, and it is the reason the contract has to be memorised.

Worked example 8 — the dispatch table

int (*ops[4])(int, int) = { add, sub, mul, div }; and a program +5, *3, −2 applied to an accumulator starting at 0.

Table route: ops[0](0,5) = 5, ops[2](5,3) = 15, ops[1](15,2) = 13. Switch route: the same three steps, 13. The model enumerates all 4³ × 3³ = 1728 three-step programs and the two routes agree on all of them.

Mathematical derivation The two routes compute the same function because the table is a lookup of the same four operations the switch branches to. The agreement is checked exhaustively rather than argued, which is the only honest way to claim "they are the same".

A function cannot return a function, and an array cannot hold one

int f(void)(int) — a function returning a function. Rejected: 6.7.6.2 requires the return type of a function to be void or an object type, and a function type is neither.

int f[3](void) — an array whose elements would be functions. Rejected: an array element must be a complete object type. Both are in the model as negative checks, so the parser is shown rejecting them rather than silently accepting a nonsense declaration.

sizeof: three different answers to three similar questions

sizeof p where p is a function pointer: the pointer size, 8 on LP64.

sizeof f where f is a function: a constraint violation (6.5.3.4). GCC accepts it as an extension and returns 1, which is why the rule is worth knowing.

sizeof *p: also a violation, because *p is again the designator, and the decay does not happen under sizeof.

Pointer arithmetic on a function pointer

6.5.6p2 permits addition when one operand is "a pointer to a complete object type" and the other has integer type. A function type is not an object type, so p + 1 on a function pointer is not permitted.

GCC and Clang accept it as an extension, treating the size of a function as 1; -pedantic and -Wpointer-arith are what surface it. The model checks that the predicate "arithmetic allowed" is false for a function pointer and true for an int pointer.

Parameter adjustment, and the extra level inside the callee

6.7.6.3p8: "A declaration of a parameter as 'function returning type' shall be adjusted to 'pointer to function returning type'." So void g(void cb(int)) and void g(void (*cb)(int)) declare the same function.

Consequence: inside g, cb is already a pointer, so &cb is a pointer to pointer to function, and assigning to cb changes only the local copy.

Conversion is legal; the call is not

6.3.2.3p8: a pointer to a function of one type may be converted to a pointer to a function of another type and back, and the result compares equal. But: "If a converted pointer is used to call a function whose type is not compatible with the pointed-to type, the behavior is undefined."

The qsort cast is exactly this case. The model checks that int (*)(const void *, const void *) is incompatible with int (*)(int *, int *), and also with the version that drops const.

What a function pointer can and cannot be

It can be: compared with == and != against another function pointer or against a null pointer constant; assigned; passed; returned; stored in an array; and stored in a struct.

It cannot be: converted to void * portably (that is not guaranteed by the standard), incremented, subscripted, or used to reach "the next function". A null function pointer that is called is a call through a null pointer — undefined, and usually a crash.

The edge-case test, in one line

Before answering any question about a function pointer, ask which of the three things it is: a type question (read the declarator), an address question (f, &f, *f agree; &p does not), or a behaviour question (which clause applies, and does it say undefined).

"int (*f)(int) and int *f(int) are the same thing"

Why it tempts. The two strings contain the same characters in almost the same order, and both involve a function and a pointer to int.

Minimal counterexample. int *f(int) can be defined and called as f(3), returning a pointer. int (*f)(int) cannot be defined at all — it is a variable, and it must be assigned before it is called. One is code, the other is data.

Correct rule. Suffixes bind before prefixes; parentheses change the order. The page's parser returns two different type trees for the two strings and the model checks they differ.

"*p(3) is how you call through a pointer"

Why it tempts. *p is the thing pointed at, so *p(3) looks like "the thing pointed at, applied to 3".

Minimal counterexample. The call operator binds tighter than the star, so *p(3) is *(p(3)): call p with 3, then dereference the result. If p is a pointer to function taking an int and returning a pointer to int, this compiles and dereferences the returned pointer — a different program.

Correct rule. Either write p(3) — the designator rule makes the star unnecessary — or write (*p)(3) with the parentheses that force the star to apply to the pointer.

"return a - b; is the standard comparator"

Why it tempts. It is short, it is correct for small integers, and it appears in a great deal of real code.

Minimal counterexample. a = 2000000000, b = -2000000000: the difference is 4000000000, which wraps to −294967296 on the stated 32-bit model, so the comparator reports the wrong sign and the pair is not sorted.

Correct rule. Return a sign, not a difference: (a > b) - (a < b). Three outcomes, no overflow, and the model checks it on both test arrays.

"A comparator returning 0 or 1 is fine — the sort only needs to know which is bigger"

Why it tempts. For a yes/no question, 0 and 1 look sufficient, and the function's type is correct.

Minimal counterexample. return a > b; never returns a negative value, so every pair reads as "not less" and nothing moves: [3, 1, 2] comes back unchanged, and the model checks that it is not ascending.

Correct rule. Three outcomes are required, not two: less, equal, greater. A two-valued comparator silently declares every pair equal-or-greater.

"&f is the address of the function, and f is not"

Why it tempts. For ordinary variables, x and &x are clearly different things, and the same is expected here.

Minimal counterexample. None exists: 6.3.2.1p4 converts a function designator to a pointer to function except under sizeof and &, so f and &f have the same type and the same value. The model resolves f, &f and *f to 0x401136 and checks all three.

Correct rule. For a function, the three spellings agree. For the pointer variable, &p is different: it is the address of the cell.

"Casting a comparator to the right signature makes it correct"

Why it tempts. The cast removes the compiler's complaint, and the program usually appears to work.

Minimal counterexample. 6.3.2.3p8: calling through a converted pointer whose type is not compatible with the function is undefined behaviour. It "works" because on common platforms every pointer has the same representation — which is a property of the platform, not of the program.

Correct rule. Write the comparator with the exact signature int (const void *, const void *) and cast the elements inside it, not the function.

Five question shapes this topic takes

Each shape is described by the reasoning it demands, not by a claim about how often it appears. One of the five has a verified previous-year instance; the rest are patterns the syllabus's clause makes possible.

1. Read the declaration

Shape. A declaration, four English sentences, one mark. Verified instance: GATE CSE 2005, int (*f)(int *).

Reasoning demanded. Locate the identifier, apply the parentheses, then the suffixes, then the base type.

Common wrong approach. Reading left to right, which makes int (*f)(int) "an int pointer function" — a sentence that is not even well formed. The four options in the 2005 item are built to catch exactly one misplaced word.

2. Write the declaration

Shape. An English description, and four candidate declarations, of which one is legal. Or a fill-in-the-blank declarator.

Reasoning demanded. Build from the outside in, then check the result against the two illegality rules: no function returning a function, no array of functions.

Common wrong approach. Producing int (*f)(int)(int) for "function returning a function pointer" — illegal, and a favourite distractor because it looks like the right shape.

3. Trace a program that calls through a pointer

Shape. A short program with an array of function pointers or a callback, asking for the output.

Reasoning demanded. Track which cell holds which function at the moment of the call, then evaluate the call. Watch for a pointer being reassigned between two calls.

Common wrong approach. Reading the table's initial contents and ignoring an assignment in between — the same error as ignoring a reassignment of any other pointer.

4. Judge a comparator or a callback

Shape. A comparator is given; the question asks whether the array is sorted, what it becomes, or which comparator is correct.

Reasoning demanded. Apply the contract: a negative, zero or positive result, and no dependence on addresses. Then simulate on the given array, not on a remembered one.

Common wrong approach. Assuming the sort is stable, or assuming the output for a boolean comparator is the reverse of the input. Neither follows.

5. Classify the behaviour

Shape. "Which of the following is undefined / illegal / implementation-defined?" with function pointers as the subject.

Reasoning demanded. Name the clause. Conversion between function pointer types: legal. Calling through an incompatible one: undefined. Arithmetic: a constraint violation. sizeof on a function: a constraint violation.

Common wrong approach. Treating "my compiler accepts it" as evidence. GCC accepts function-pointer arithmetic and sizeof of a function as documented extensions; both remain outside the standard.

The one habit that solves shapes 1 and 2

Write the constructor chain before writing the sentence. Identifier, suffixes, prefixes, base type. Then the sentence is a transcription, and both directions of the question become the same exercise.

MCQGATE CSE 2005

What does the following C-statement declare? int (*f)(int *);

  1. A function that takes an integer pointer as argument and returns an integer
  2. A function that takes an integer as argument and returns an integer pointer
  3. A pointer to a function that takes an integer pointer as argument and returns an integer
  4. A function that takes an integer pointer as argument and returns a function pointer

Answer: C

The identifier is f; the star inside the parentheses makes it a pointer; (int *) is the parameter list of what it points at; the leading int is the return type. So: a pointer to a function taking a pointer to int and returning an int.

Why the others fail. A deletes "pointer to" and calls f a function — that would be int *f(int *). B moves the star to the return type — that is int *f(int), with the parameter also changed. D invents a return type that is itself a function pointer, which no part of the declaration mentions.

What is being tested. Only the precedence of ( ) over * in a declarator. There is no program to trace and no machine model involved.

MCQOriginal practice question

Which declaration matches "a function taking an int and returning a pointer to a function taking an int and returning an int"?

  1. int (*f)(int)(int);
  2. int (*f(int))(int);
  3. int *(*f)(int);
  4. int (**f)(int);

Answer: B

Build it outside in: the outer thing is a function taking an int, so f(int); it returns a pointer, so (*f(int)); that pointer points at a function taking an int, so append (int) and prefix the base type: int (*f(int))(int). The page's parser reads it back as f is a function taking (int) returning pointer to function taking (int) returning int.

Why the others fail. A is illegal: a function cannot return a function (6.7.6.2), and the model's parser rejects it. C is a pointer to a function taking an int and returning a pointer to int — the pointer is on the return value of the inner function, not on the function itself. D is a pointer to a pointer to a function; there is no outer function at all.

Assumption. None: this is a declarator question, and the answer does not depend on any machine model.

NATOriginal practice question

On an LP64 machine — 8-byte pointers, 4-byte int — how many bytes does the object declared by int (*f[3])(int); occupy?

Answer as an integer.

Answer: 24

f is an array of 3 elements, each a pointer to function. A function pointer is 8 bytes on this model, so the array is 3 × 8 = 24 bytes. No function body is stored in the array: only three addresses.

Traps. Answering 8 reads the declaration as a single pointer; answering 12 uses a 4-byte pointer, which is the ILP32 model; answering 0 assumes a function occupies no storage — true of the function, false of the array of pointers to it.

Assumption stated. The 8-byte figure is the model, not a guarantee of the standard: the size of a function pointer is implementation-defined, and the question states the model so the answer is determined.

MCQOriginal practice question

A comparator for qsort is written as return a - b; where the elements are 32-bit int and the pair being compared is a = 2000000000, b = -2000000000. Which statement is correct?

  1. It returns 4000000000 and the pair is ordered correctly.
  2. It returns a negative value on a two's-complement machine, and the C standard calls the overflow undefined, so the program is not well defined.
  3. It returns a positive value, so the pair is ordered correctly.
  4. It returns 0, so the pair is treated as equal and the sort still produces ascending order.

Answer: B

The true difference is 4000000000, which does not fit in a 32-bit int. On the two's-complement model used on this page it wraps to −294967296, so the comparator reports that the larger value is smaller and the pair stays in descending order. The model computes both the wrap and the resulting order.

Why the others fail. A assumes int is wide enough — that is the whole point of the question. C contradicts the arithmetic: the wrapped value is negative on this model. D would require the difference to be zero, which it plainly is not.

Why B is the examinable answer rather than just "it wraps". Signed overflow is undefined behaviour, so a page that reported only the wrapped value would be describing one implementation. The safe comparator, (a > b) - (a < b), avoids the question entirely, and the model checks that it returns −1, 0 and 1 exactly.

MSQOriginal practice question

Let f be a function with no pointer in its declaration, and p a variable of pointer-to-function type holding f. Which statements are true?

  1. f, &f and *f all denote the same address.
  2. p + 1 denotes the next function in memory.
  3. sizeof p is the machine's pointer size.
  4. Calling a function through a converted pointer of an incompatible function type is undefined behaviour.

Answer: A, C and D

(A) 6.3.2.1p4 converts the designator to a pointer except under sizeof and unary &, and 6.5.3.2p4 turns *p on a function pointer back into the designator, which converts again. The model resolves all three to 0x401136. (C) p is an object of pointer type, so it has a size; the model states 8 bytes on LP64. (D) is 6.3.2.3p8 word for word.

Why B fails. Addition requires "a pointer to a complete object type" (6.5.6p2), and a function type is not an object type. GCC allows it as an extension with size 1 — an extension, not the language. There is also no defined "next function": the standard says nothing about the order of functions in memory.

The distinction being tested. "Legal to convert" and "legal to call through" are different permissions, and "my compiler accepts it" is evidence about the compiler, not about C.

MCQOriginal practice question

An array of four function pointers is used instead of a switch over four opcodes. Which statement about the two is correct?

  1. The table is faster for every input, because it avoids all comparisons.
  2. The table and the switch compute the same function; the table's advantage is a count of tests in a stated model, and it can be rewritten at run time.
  3. The switch cannot express more than four operations, so the table is strictly more general.
  4. The table uses less memory than the switch in every case.

Answer: B

The model evaluates all 1728 three-step programs both ways and they agree on all of them, so the two routes compute the same function. The cost difference is a count of tests: an if-chain over four operators averages 2.5 per instruction against 1 for the table, so 2500 against 1000 over 1000 instructions.

Why the others fail. A overstates it: a compiler may compile a dense switch into a jump table, in which case the comparison disappears anyway. C is false — a switch can have any number of cases. D is false in general: the table costs four pointers plus the functions themselves, and it prevents inlining.

The honest version of the claim. The table buys an O(1) dispatch and the ability to change behaviour at run time, and it pays for both in indirection and in safety: a corrupted entry is a jump into arbitrary code.

NATOriginal practice question

Using insertion sort that shifts while cmp(key, previous) < 0, with the comparator (a < b) ? -1 : (a > b) ? 1 : 0, how many comparisons does the model make on the array [5, 3, 9, 1, 7, 3]?

Answer as an integer.

Answer: 11

The model counts 11 comparisons and produces [1, 3, 3, 5, 7, 9], which it checks against a numeric sort. The bounds from the comparator alone are 5 (= n − 1) and 15 (= n(n−1)/2), and 11 sits inside them.

Why the count is not a property of the contract. A different sorting algorithm on the same array with the same comparator makes a different number of comparisons. Only the two bounds follow from the comparator; the exact figure follows from the algorithm, and the question states the algorithm for that reason.

Trap. Answering 15 assumes the worst case; answering 5 assumes a presorted array. Neither is the given input, and the array is given precisely so the count can be computed rather than bounded.

The grammar, in four lines

declarator := pointer? direct-declarator

direct-declarator := ident | ( declarator ) | dd [ n ] | dd ( params )

Suffixes attach to the direct-declarator; stars attach to the whole declarator; the base type is applied last.

Reading order = identifier, suffixes left to right, stars inside out, base type.

Six declarations to be able to read on sight

int *f(int) — function taking int, returning pointer to int

int (*f)(int) — pointer to function taking int, returning int

int (*f[3])(int) — array of 3 pointers to such functions

int (**f)(int) — pointer to pointer to such a function

int (*f(int))(int) — function taking int, returning pointer to such a function

void (*signal(int, void (*)(int)))(int) — function taking (int, handler), returning a handler

Clause numbers worth memorising

6.3.2.1p4 — a function designator converts to a pointer, except under sizeof and &.

6.5.3.2p4 — *p on a pointer to function yields the designator.

6.5.2.2p1 — the called expression must have pointer-to-function type.

6.3.2.3p8 — conversion is legal; calling through an incompatible converted pointer is undefined.

6.5.6p2 — arithmetic needs a pointer to a complete object type.

6.5.3.4 — no sizeof on a function type.

6.7.6.3p8 — a function-type parameter is adjusted to a pointer to function.

Six traps, six answers

  • Same characters, same type? No — parentheses change the order.
  • *p(3) is a call? No — it is *(p(3)).
  • &f differs from f? No — same address, same type.
  • a - b as a comparator? Overflows; use (a > b) - (a < b).
  • return a > b;? Never negative, so nothing moves.
  • Casting a comparator? Legal; calling through it is undefined.

What to do in the first ten seconds of a function-pointer question

Decide which of the three the question is. A type question: write the constructor chain. An address question: remember f, &f, *f agree while &p does not. A behaviour question: name the clause, and be careful that "the compiler accepted it" is not a clause.
