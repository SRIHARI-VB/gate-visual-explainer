Topic and objective

TOPIC: Structures, unions and enumerations in C — their memory layout, the padding between their members, and what happens when one member is written and another is read. This is part of Programming in C, Section 4 of GATE 2027.

LEARNING OBJECTIVE: Compute the offset of every member of a struct and its total size from the alignment rule, rather than from the sum of the member sizes. Show that the same members in a different order give a different size, and explain why the language permits that. Size a nested struct, an array of structs and a union. Trace a write to one union member and a read of another through the machine's byte order, and say exactly what the C standard guarantees and what it leaves to the implementation. Read an enumeration as a list of integer constants with a chosen underlying type. Finally, explain why a struct may hold a pointer to its own type but not an object of its own type, and size a list node.

I read this topic as one question asked in three costumes: where does each thing start, how many bytes does the block take, and what do those bytes mean. A struct answers the first two by stacking, a union answers them by overlapping, and an enumeration answers the third by naming integers. Almost every exam question in this topic is the same subtraction — the offset of the next member minus the end of the current one — and almost every lost mark is a bytes-versus-members confusion.

Prerequisites

  • Objects, bytes and addresses. An object owns a range of bytes, and an address is a number. Built in Pointers in C.
  • sizeof and its type. sizeof yields a size_t, counts bytes, and does not evaluate its operand. Also in Pointers in C.
  • Integer widths and the conversion ranks. Why int is four bytes here and why that is a platform fact rather than a C fact. Built in C fundamentals.
  • Binary and hexadecimal place values. Reading 0x12345678 as four bytes needs both. Built in Number Representation and Arithmetic.
  • Pointers to incomplete types. A declaration may name a struct before it is defined, which is what makes the self-referential node legal. Built in Pointers in C.
  • Arrays and their stride. Element k of an array starts at base + k * sizeof(element). Built in Arrays, Stacks and Queues.

No knowledge of malloc, of bit-fields or of compiler pragmas is assumed; the first two appear only in Edge cases, and the third appears as a counterexample.

The five ideas to leave with

  1. An offset is rounded up to the member's alignment; the total is rounded up to the largest alignment in the struct. Padding is whatever that costs.
  2. sizeof is a property of the declaration. The same members in another order may give a different size, and that is legal C.
  3. A struct stacks, a union overlaps. A union's size is its largest member rounded up to its largest alignment.
  4. Writing one union member and reading another reinterprets bytes, not values. The result depends on the machine's byte order, so a program that does it has no single portable output.
  5. Alignment and sizes are ABI facts. Only sizeof(char) == 1 is fixed by the C standard, so a size question without a stated platform has no single answer.

Intuition: a locker wall, and the rule about which lockers may be used

Picture a wall of numbered lockers, one byte each. A struct is a booking: "locker 0 is yours, lockers 1 to 3 stay empty, lockers 4 to 7 are yours, locker 8 is yours." The booking is a type. Making a booking reserves nothing; only renting one — declaring an object — takes the lockers.

Now the rule that creates the empty lockers. A four-locker booking must start at a locker number divisible by four. That is all alignment is: a constraint on the starting number, not on the contents. The receptionist cannot move your booking to locker 1, so lockers 1 to 3 are wasted. And because the next person's booking must also start on a legal number, the whole booking is rounded up to a multiple of the largest demand in it. A union is a different booking: everybody is told to use locker 0, and the booking is as big as the largest person needs. An enumeration is not a booking at all — it is a list of nicknames for the numbers 0, 1, 2.

Level 1 — Intuition, in one sentence each

  • Struct. One block of bytes, members stacked in declaration order, gaps allowed between them.
  • Offset. How many bytes from the start of the object a member begins.
  • Alignment. The divisor that a member's starting offset must be a multiple of.
  • Padding. Bytes inside the object that belong to no member.
  • sizeof. The whole block, padding included, rounded so that arrays of it stay aligned.
  • Union. One block, members overlapping at offset 0, sized by the largest.
  • Enumeration. Named integer constants, stored as one integer.

Level 2 — Formal definitions

Verified fact A structure type is a type consisting of a sequence of members whose storage is allocated in an ordered sequence. C11 §6.7.2.1 requires the members to be laid out in the order declared, and adds that there may be unnamed padding between members and at the end, but not at the beginning.

Verified fact Alignment is a requirement that objects of a given type be stored at addresses that are multiples of a value. C11 §6.2.8 makes the alignment of every type except char implementation-defined. char has alignment 1, which is why a character can go anywhere.

The layout rule, as this page applies it. For members in declaration order, with running offset o:

offset(m) = ceil(o / align(m)) * align(m), then o = offset(m) + size(m).

At the end, sizeof = ceil(o / A) * A where A is the largest alignment among the members.

Verified fact A union type is a type whose members all begin at offset 0 and overlap; its size is at least the size of its largest member (C11 §6.7.2.1, §6.5.2.3). An enumeration declares a set of named integer constants; the type of each enumerator is int, and the implementation chooses an integer type that can represent every value of the enumeration (C11 §6.7.2.2).

Level 5 — the boundary conditions, stated up front

The layout rule above is not a law of C. It is the rule of one ABI, the x86-64 System V ABI that Linux and macOS compilers follow for these types. The standard fixes only two things: members appear in declaration order, and the object has no padding before its first member. Everything else — the alignment of each type, the size of the gaps, the rounding of the total — is the implementation's choice. So: a struct may legally be 6 bytes where this page says 12, and a question that does not state the platform is not a well-posed question. Two further boundaries matter. A struct may not contain an object of its own type by value, only a pointer to it, because a value member would need the size being computed. And sizeof counts padding, so two structs with equal members can compare unequal byte for byte.

Level 3 and 4 — why the third rule exists

The first two rules are forced by the alignment requirement: a member cannot start anywhere it likes. The third rule — round the whole block up — is not forced by anything inside the object. It is forced by what comes after the object.

An array of structs is a contiguous run of objects, so element k begins at base + k * sizeof. If the size were 9 for a struct whose alignment is 4, element 1 would begin at an address that is 1 modulo 4 — misaligned — and the guarantee that every element is properly aligned would fail for every element after the first. Rounding the size up to a multiple of the alignment is the smallest change that keeps the guarantee. That is why char, int, char is 12 and not 9, and it is the one step that candidates forget under time pressure.

Every type in this table is self-aligned: its alignment equals its size. That is a coincidence of this ABI, not a rule of C, and it is why the arithmetic in the exam is so often "round up to the size".

Why padding bytes are a hazard, not just a waste

Verified fact C11 §6.2.6.1 says that when a value is stored in a member of a structure or union object, the bytes of the padding take unspecified values. Nothing in the standard says they are zero.

Mathematical derivation Two structs with identical members can therefore have identical member bytes and different padding bytes. Comparing them with memcmp compares the padding too, so a correct program can be told the objects differ. The safe comparison is member by member, and the safe copy is assignment — which the compiler is allowed to implement field by field precisely because padding carries no value.

Why a union is the useful shape for a protocol

Educational interpretation A union says "these are alternative readings of one object". That is exactly what a wire format is: the same four bytes are an integer to one part of the code and a length-prefixed field to another. The type records the overlap instead of hiding it behind a cast.

Mathematical derivation The cost is that a union carries no tag. Nothing in the object says which member was last written, so the program must track it separately — a struct holding the union plus an enum saying which member is live. That combination is the standard way to write a tagged variant in C, and it is the only reason the enum in this lesson earns its place next to the union.

Level 6 and 7 — where the exam actually bites

Two shapes account for nearly every question. The first hands you a declaration and a platform, and asks for sizeof, an offset, or the value printed by reading one member through another. The second hands you a program and asks what it prints, where the answer turns on byte order or on a member that was never written.

Both are decided by writing the offsets down. A candidate who writes c:0, i:4, c2:8, size 12 on the paper cannot then choose 9, and a candidate who writes the four bytes out cannot then choose the value that belongs to the other endianness. The GATE patterns tab lists the shapes with the reasoning each demands.

What breaks each step

  • Offset rounding assumes you know the member's alignment. If the member is an array, the alignment is that of the element type, not of the array's length.
  • Total rounding assumes the largest alignment is among the members. For a nested struct it is the nested struct's own alignment, which is the maximum inside it.
  • Union size assumes the largest member is also the strictest. When it is not — char[5] with int — the size is the larger of "largest member" and "rounded to the largest alignment".
  • Array stride assumes the elements are contiguous. A pointer array is contiguous pointers, not nodes.
  • Byte reading assumes a byte order. Without one stated, the answer is "undefined or machine-dependent", and that is often the correct option.

Level 9 — consolidation before the animation

  1. Write the offsets, not the sizes. The size falls out of the last offset plus the rounding.
  2. Round up, place, round up again. Three lines, every time, and the third line is the one that scores.
  3. A union is one block with every member at zero. Its size is the largest member, rounded.
  4. Reading another member reinterprets bytes. State the byte order before you state an output.
  5. Name the platform. Every number in this topic is an ABI fact.

Worked examples — every offset written down

Each example states the declaration, the platform, and the running offset after every step. The numbers are the ones the page computed; the animation draws the same values from the same model.

Example 1 — char, int, char is 12

1. c is a char: align 1, so offset 0. Running offset becomes 1. Justification: offset 0 is divisible by every alignment.

2. i is an int: align 4. Round 1 up to 4. Offset 4, three padding bytes. Running offset becomes 8.

3. c2 is a char: align 1. Offset 8, no padding. Running offset becomes 9.

4. Largest alignment is 4. Round 9 up to 12. Three trailing padding bytes.

Answer: offsets 0, 4, 8; sizeof 12; padding 6 — three bytes between c and i, three at the end.

Example 2 — the same members as int, char, char is 8

1. i at 0, running offset 4.

2. c at 4, running offset 5.

3. c2 at 5, running offset 6.

4. Largest alignment 4, round 6 up to 8. Two trailing bytes.

Answer: 8 bytes. Four bytes fewer than Example 1, for exactly the same data. Nothing was removed; the gaps moved.

Example 3 — double, char is 16, and 7 of them are waste

d at 0 (align 8), running offset 8. c at 8, running offset 9. Largest alignment 8, round 9 up to 16.

Answer: 16 bytes holding 9 bytes of data. The 7 trailing bytes exist only so that the next element of an array would start on a multiple of 8.

Example 4 — nesting: Inner inside Outer is 12

struct Inner { char a; int b; }: a at 0, b at 4, running offset 8, largest alignment 4, so size 8 and alignment 4.

struct Outer { char c; struct Inner in; }: c at 0, running offset 1. in has alignment 4, so round 1 up to 4. in spans offsets 4 to 11. Running offset 12, largest alignment 4, so size 12.

Answer: 12 bytes. The inner struct's own trailing padding is already inside its 8 bytes and is counted once, not twice.

Example 5 — union { char s[5]; int i; } is 8

Both members start at offset 0. The largest member is s, five bytes. The largest alignment is 4, from i. Round 5 up to 8.

Answer: 8 bytes, of which bytes 5 to 7 are trailing padding. Saying 5 is the standard slip: the trailing bytes keep an array of the union aligned, exactly as rule three does for a struct.

Example 6 — GATE CSE 2000 Q1.17, both readings

Verified fact The question gives struct { short s[5]; union { float y; long z; } u; } t; with short 2, float 4 and long 8 bytes, and asks for the requirement ignoring alignment considerations. Its key is 18.

1. s[5] is five shorts: 10 bytes.

2. The union is the larger of float (4) and long (8): 8 bytes.

3. Ignoring alignment, the members simply add: 10 + 8 = 18.

With alignment on x86-64 the same object is 24: s ends at 10, the union needs alignment 8 so it starts at 16, ends at 24, and 24 is already a multiple of 8. The question says to ignore alignment, so 18 is the answer, and 24 is the number you would get by answering a question that was not asked.

Example 7 — GATE CSE 2018 Q2 prints 0, c

Verified fact struct Ournode { char x, y, z; } p = {'1','0','a'+2}; then printf("%c, %c", *((char*)q+1), *((char*)q+2)) with q = &p. The official key is option A, 0, c.

1. Three chars, all alignment 1: offsets 0, 1, 2. No padding anywhere, size 3.

2. 'a' + 2 is evaluated as an int expression and stored in a char, giving 'c'.

3. (char*)q + 1 is byte 1, holding '0'; +2 is byte 2, holding 'c'.

Answer: 0, c. The quotes in options C and D are not printed by %c, and option B treats 'a'+2 as a string of three characters, which it is not.

Example 8 — ten elements of { char; int; } are 80 bytes

One element: c at 0, i at 4, running offset 8, largest alignment 4, size 8. Stride 8.

Answer: 10 × 8 = 80 bytes, of which the members hold 10 × 5 = 50. Element k begins at base + 8k, and every one of those addresses is a multiple of 4, so every element is aligned. This is the premise a question states when it says the array starts at an address divisible by 8.

Boundaries, and what each one breaks

Each card names a condition that the rule in Build-up assumes, then shows the smallest case where the condition fails and what the answer becomes. None of these is a curiosity: the first is the reason a size question must state its platform, and the last is the reason a "what does this print" question must state its byte order.

Counterexample — the same declaration, a smaller size

With #pragma pack(1), or the equivalent attribute, the compiler is told to ignore alignment. char, int, char then occupies 6 bytes, not 12, with offsets 0, 1, 5.

What it breaks: nothing in the C standard. The standard never promised 12. It promised declaration order and no leading padding, and a packed struct keeps both. A packed struct can fault on a machine that refuses misaligned access, which is why the pragma is a request, not a guarantee of correct behaviour.

Counterexample — 32-bit against 64-bit

struct node { int elt; struct node *next; } is 16 bytes on x86-64 (int at 0, four padding, pointer at 8) and 8 bytes on a 32-bit ABI (int at 0, pointer at 4).

What it breaks: any claim that sizeof is a property of the source text. It is a property of the source text plus the ABI, and the pointer size is the part that changes.

Counterexample — padding is not zero

Two objects of struct A with identical member values may differ in their three padding bytes, because C11 §6.2.6.1 leaves those bytes unspecified when a member is stored.

What it breaks: memcmp(&x, &y, sizeof x) == 0 as a test of equality. Compare members, or use == on a struct that has been assigned, which the compiler is allowed to do member by member precisely because padding carries no value.

Counterexample — a union whose largest member is not the strictest

union { char s[5]; int i; }: the largest member is 5, but the alignment is 4, so the size is 8, not 5.

What it breaks: the shorthand "a union is the size of its largest member". The correct statement has two clauses: the largest member, rounded up to the largest alignment. The rounding matters exactly when the two disagree.

Counterexample — an array of pointers is not an array of nodes

struct node *s[10] is ten pointers: 80 bytes on x86-64, and zero nodes. struct node s[10] is ten nodes: 160 bytes.

What it breaks: the reading that the star belongs to the array. It belongs to the name: s is an array whose elements are pointers. Each element still has to be pointed at something before it can be used, and none of them is initialised.

A struct with no members, and a flexible array member

Verified fact C does not permit an empty struct; a compiler that accepts one is offering an extension, and the size is then its own choice (GCC gives 0, C++ gives 1). A struct whose last member is an incomplete array type — char data[]; — is a flexible array member, permitted since C99, and it contributes no bytes to sizeof.

Why it matters here: both are cases where "the sum of the members" and sizeof disagree in a way the three rules do not predict. The rules describe ordinary objects, and a question about an empty struct is testing whether you know the rules have an edge.

Bit-fields: declared in bits, laid out by nobody in particular

Verified fact struct { unsigned a : 3; unsigned b : 5; } declares bit-fields. C11 §6.7.2.1 says the allocation order within a unit is implementation-defined, that padding bits may be inserted, and that a bit-field may not straddle a storage unit unless the implementation allows it.

What it breaks: the whole offset model. There are no byte offsets to compute, and two compilers may give different sizes for the same declaration. A question that asks for the size of a bit-field struct without naming the compiler has no defensible answer.

Byte order, and the question that has no answer

On a little-endian machine 0x12345678 read as four chars gives 78 56 34 12. On a big-endian machine the same program gives 12 34 56 78.

What it breaks: any single printed answer. If a question does not state the byte order, either the options include "implementation-dependent", or the question is testing whether you notice that it is. GATE has used the little-endian premise explicitly when it wanted a number.

Six beliefs that produce the wrong option

Each card states the wrong belief, why it is tempting, the smallest case that refutes it, and the rule that replaces it. The refutations are computed, not asserted.

1. "sizeof of a struct is the sum of its members"

Why it tempts: for an array it is true, and for a struct of all chars it is true too.

Minimal counterexample: char, int, char sums to 6 and occupies 12.

The rule: sum plus padding, and the padding is decided by alignment, not by the members.

2. "Offsets follow declaration order one after another"

Why it tempts: the 2018 question works exactly that way, because all three members are chars.

Minimal counterexample: put one int second and the third member moves from offset 2 to offset 8.

The rule: offsets follow declaration order, but each is rounded up to its own alignment first.

3. "A union is as big as its largest member"

Why it tempts: it is the sentence in most notes, and it is right most of the time.

Minimal counterexample: union { char s[5]; int i; } is 8, not 5.

The rule: the largest member, rounded up to the largest alignment. Two clauses, and the second one is the question.

4. "Reordering the members is not allowed"

Why it tempts: the compiler does not reorder, so it looks as though order is fixed.

Minimal counterexample: int, char, char is 8 while char, int, char is 12 — the same three members, and the programmer chose the order.

The rule: the compiler must keep the order you wrote. You are free to write a different one, and it may be smaller.

5. "Reading the other union member converts the value"

Why it tempts: u.i and u.b look like two variables, so a read looks like a read of a converted value.

Minimal counterexample: write u.i = 0x12345678 and read u.b[0]; you get 0x78, not a converted number.

The rule: no conversion happens. The bytes are reinterpreted under the new type, so the result depends on the machine's byte order and may be a trap representation.

6. "sizeof(enum) is the number of enumerators"

Why it tempts: the enumeration lists three things and sizeof asks how big it is, so counting feels natural.

Minimal counterexample: enum colour {RED, GREEN, BLUE} holds one value at a time, and its size is 4 — the size of an int — whether it has two enumerators or twenty.

The rule: an enumeration object is one integer. The number of enumerators changes nothing, and the longest name changes nothing.

The question shapes, and the reasoning each demands

These are categories of question, not predictions. Where a previous-year item is quoted it carries its year and question number, and its answer was recomputed here. Where a shape has no verified item behind it, the card says so and labels the example as original practice.

Shape 1 — compute sizeof, or one offset

Given a declaration and a platform, produce a number.

Reasoning demanded: write the running offset for each member, round up before placing, round the total at the end. State the platform's sizes first, on the paper.

The common wrong approach: adding the member sizes, or rounding only at the end and not between members. Both produce numbers that look plausible and are not among the options only sometimes — which is why writing the offsets is safer than trusting the arithmetic.

Shape 2 — what does this program print

Given a program that reads a struct or union through a different type, produce the output.

Reasoning demanded: fix the offsets first, then decide whether padding sits between the two members you are reading. Then fix the byte order if an integer is being read as bytes.

The common wrong approach: assuming byte k of the object is member k. That is true only when every member before it is one byte wide — which is exactly the 2018 case, and exactly why that question is easy and the padded version is not.

Shape 3 — a statement set about unions and structs

MSQ: which statements are true. Typical candidates are "the members overlap", "only one member is meaningful at a time", "the size is the largest member", "writing one member invalidates the others".

Reasoning demanded: test each statement against a concrete two-member union. "Invalidates" is the usual false one: the bytes of the others are still there; what changed is which of them the program last wrote.

Shape 4 — declaration reading: what is s?

Verified fact GATE CSE 2000 Q1.31 gives struct node { int i; float j; }; struct node *s[10]; and asks what s is declared to be. The answer is an array, each of whose elements is a pointer to a structure of type node.

Reasoning demanded: read the declarator from the name outward: s is an array of 10 of pointer to struct node. The common wrong approach: attaching the star to the array, which would be struct node (*s)[10] — a pointer to an array of ten nodes, and a different declaration.

Shape 5 — the union inside a struct, with alignment to ignore

Verified fact GATE CSE 2000 Q1.17 gives a struct holding an array and a union and asks for the memory requirement "ignoring alignment considerations". Its key is 18.

Reasoning demanded: size the union as its largest member, then add. The trap: computing the aligned size (24) and finding it among the options. When the question says to ignore alignment, it is asking a question about sizes, and adding the numbers is the intended act.

What is not a pattern

No verified GATE item in the papers consulted asks for the size of a bit-field struct, or for the effect of #pragma pack. Those appear here as Edge cases because they are the honest counterexamples to "layout is fixed", not because they are a question shape. MCQGATE CSE 2018 Q2

Consider the following C program.

struct Ournode { char x, y, z; };
int main() {
  struct Ournode p = {'1', '0', 'a'+2};
  struct Ournode *q = &p;
  printf("%c, %c", *((char*)q+1), *((char*)q+2));
  return 0;
}

The output of this program is:

  1. 0, c
  2. 0, a+2
  3. '0', 'a+2'
  4. '0', 'c'

Answer: A — 0, c

Three chars have alignments 1, so the offsets are 0, 1, 2 and there is no padding. 'a' + 2 is computed as an int and stored in a char, giving 'c'. Byte 1 holds '0', byte 2 holds 'c', and %c prints the characters without quotes.

Why the others fail. B treats 'a'+2 as the three-character text a+2; the expression was evaluated, not stored as text. C and D keep the single quotes, which are part of the C source and not of the value printed by %c.

What it tests. That a struct of same-sized members has no padding, so byte k is member k. Put one int in the same struct and this shortcut stops working.

NATGATE CSE 2000 Q1.17

Consider the following C declaration:

struct { short s[5]; union { float y; long z; } u; } t;

Assume that objects of type short, float and long occupy 2 bytes, 4 bytes and 8 bytes respectively. The memory requirement for variable t, ignoring alignment considerations, is ______ bytes.

Answer: 18

s[5] is 5 × 2 = 10 bytes. The union is the larger of float (4) and long (8), so 8 bytes. Ignoring alignment, 10 + 8 = 18.

Why the alternatives appear. 22 comes from adding both union members (4 + 8) instead of taking the larger. 14 comes from taking float as the union. 10 comes from treating the union as free.

Edge case. With x86-64 alignment the same object is 24 bytes: s ends at 10, the union needs an 8-aligned address so it starts at 16, and the total rounds to 24. The question explicitly excludes alignment, so 18 is the answer being asked for — but knowing both numbers is what stops you choosing 24 when a later paper does not say "ignoring alignment".

NATOriginal practice

On x86-64, with char 1 byte (align 1), short 2 (align 2), int 4 (align 4) and double 8 (align 8), what is sizeof of the following?

struct S { char a; short b; char c; double d; char e; };

Answer: 24

a at 0, running offset 1. b needs 2, so 1 padding byte and b at 2, running offset 4. c at 4, running offset 5. d needs 8, so 3 padding bytes and d at 8, running offset 16. e at 16, running offset 17. Largest alignment 8, round 17 up to 24.

Trap. Stopping at 17, or rounding to 20 because the largest alignment seen so far was 4. The largest alignment is a property of the whole struct, not of the members placed so far.

MSQGATE CSE 2000 Q1.31

The following C declarations

struct node { int i; float j; };
struct node *s[10];

define s to be:

  1. An array, each element of which is a pointer to a structure of type node
  2. A structure of 2 fields, each field being a pointer to an array of 10 elements
  3. A structure of 3 fields: an integer, a float, and an array of 10 elements
  4. An array, each element of which is a structure of type node

Answer: A

Read the declarator from the name outward: s is an array of 10 of pointer to struct node. On x86-64 the whole declaration occupies 10 × 8 = 80 bytes and contains no node at all.

Why the others fail. B and C read the declaration as if it were a struct definition. D is the same text without the star — struct node s[10] — which would be ten nodes, 160 bytes with this ABI.

The closely confused pair. struct node *s[10] is an array of pointers; struct node (*s)[10] is a pointer to an array. The brackets bind first, so the star attaches to the name in the first form and to the whole array in the second.

MCQOriginal practice

On a little-endian machine, union V { int i; char b[4]; } v; v.i = 0x12345678; is executed. What is v.b[0]?

  1. 0x12
  2. 0x78
  3. 0x34
  4. Unspecified, because reading a member other than the one last written has no defined result

Answer: B — 0x78

All members of the union start at offset 0, so v.b[0] is the lowest-addressed byte of the integer. Little-endian stores the least significant byte first, and the least significant byte of 0x12345678 is 0x78. The four bytes are 78 56 34 12.

Why D is wrong here. Option D is a fair instinct — reinterpreting one member as another is not a conversion — but reading through a character type is the one reinterpretation C always permits (C11 §6.5p7), and the byte order is stated. The answer is determinate.

Where D would be right. Read v.i after writing a different non-character member, or read the bytes on a machine whose order is not given, and the result is no longer determinate.

NATOriginal practice

On x86-64, what is sizeof of the following, and what is the offset of next? Give the size.

struct node { char tag; int elt; struct node *next; };

Answer: 16 bytes, with next at offset 8

tag at 0, running offset 1. elt needs 4, so 3 padding bytes and elt at 4, running offset 8. next is a pointer with alignment 8, so offset 8, running offset 16. Largest alignment 8, and 16 is already a multiple of 8.

Trap. Answering 13 by adding 1 + 4 + 8 and forgetting both gaps, or answering 12 by rounding to 4 instead of 8. The pointer is what raises the largest alignment.

MCQOriginal practice

Which of the following is true of the C standard, as opposed to one particular compiler?

  1. A struct's members are stored in the order declared, and there may be padding between them.
  2. A struct's members are stored with no padding, so sizeof equals the sum of the member sizes.
  3. The alignment of an int is 4 bytes on every implementation.
  4. A union's size equals the sum of its members' sizes.

Answer: A

C11 §6.7.2.1 requires declaration order and permits unnamed padding between members and at the end, while forbidding it before the first member. Everything else in the options is a claim about one ABI.

Why B, C and D fail. B is false whenever alignment forces a gap — char, int, char is 12, not 6. C is false because the standard leaves every alignment except char's to the implementation. D is false because a union overlaps its members; its size is the largest member rounded up.

NATOriginal practice

enum size { S = 3, M, L = 3, XL };

What is the value of XL, and how many distinct values do the four enumerators take?

Answer: XL is 4, and the four enumerators take 2 distinct values

S is written as 3. M follows it, so M = 4. L is written as 3 again. XL follows L, so XL = 4. The values are 3, 4, 3, 4, which is two distinct values.

The trap. Writing a value explicitly resets the counter to it, and duplicates are legal, so S and L share 3 while M and XL share 4. Answering "4 distinct" counts the names; answering "XL = 5" assumes the counter continues from the largest value seen rather than from the previous enumerator.

What it tests. That an unwritten enumerator continues from the previous one, and that two names may denote one value. A switch on this enum cannot have separate cases for S and L.

One-screen revision sheet

Everything on this page, compressed to what you would write on the rough sheet in the first minute of the paper. Sizes are x86-64 System V; write the platform down before you start.

The procedure, in four lines

1. Write the member, its size, its alignment. For an array, the alignment is the element type's.

2. Offset = current rounded up to that alignment. Then current = offset + size.

3. At the end, size = current rounded up to the largest alignment.

4. Padding = size − sum of member sizes. Check it is non-negative and that size is a multiple of the largest alignment.

Numbers worth knowing

char, char, char3
char, int, char12
int, char, char8
double, char16
union { char[5]; int }8
struct { int; node* }16
node *s[10]80
enum (small)4

Every one of these was computed by this page and re-checked against its defining property.

Definitions in one line each

  • Struct: stacked members in declaration order, gaps permitted.
  • Union: overlapping members, all at offset 0, sized by the largest rounded up.
  • Enum: named integer constants; the object is one integer.
  • Padding: bytes belonging to no member, of unspecified value.
  • Alignment: a divisibility constraint on the starting address.

Five traps, five answers

  • Summed the members? Add the padding and round the total.
  • Forgot the last rounding? Size must be a multiple of the largest alignment.
  • Union = largest member? Largest, then rounded to the largest alignment.
  • Read another member and got a number? State the byte order, or say implementation-dependent.
  • No platform given? Only sizeof(char) == 1 is guaranteed.

Two sentences to carry into the next topic

A list node is a struct with a pointer to its own type, and its size on this ABI is 16 bytes because the pointer needs an 8-aligned address — which is why the next topic, Linked Lists, can talk about nodes without ever asking what one weighs. And the tag-and-union pair — a struct holding an enum saying which member is live — is the C idiom for a value that may be one of several shapes, which is the same idea a tagged union in a type system formalises.
