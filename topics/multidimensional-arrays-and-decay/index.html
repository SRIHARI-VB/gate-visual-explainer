Topic and objective

TOPIC: Multidimensional arrays in C — what the type int a[3][4] actually is, what each expression made from it becomes, and why a pointer to an array and a pointer to a pointer are not interchangeable.

LEARNING OBJECTIVE: Given a declaration such as int a[3][4], state its size, the size of a[0] and the size of a[0][0]; name the type each expression decays to; say how many bytes a + 1, a[0] + 1 and &a + 1 move; write a function parameter that accepts the array and say which dimension is ignored; and compute a cell address in row-major and column-major order and back-solve a base address from two given cells.

I read this topic as one type read carefully. Every number in the lesson — 48, 16, 4, the three strides, the twelve verified addresses, the two order formulas — is a consequence of the sentence "a is an array of three arrays of four ints". Nothing here is a rule to memorise.

How this differs from the lesson next door

Arrays, Stacks and Queues answers where is the cell: it gives address = base + (i - L1) * cols + (j - L2)) * w, works row-major against column-major, and computes an address on a declared array. That is the arithmetic half.

Level 1 — Intuition: a row of drawers, each holding a row of pigeonholes

A filing cabinet has three drawers, and each drawer has four pigeonholes. The cabinet is one object. There is no list on the front saying where each drawer starts — you know, because every drawer is the same width. Ask for "drawer 2, hole 3" and anyone who knows the drawer width can walk straight there.

Educational interpretation The analogy carries exactly two facts: the rows are inside one object, and their positions are computed from a width rather than looked up. It does not carry the type system, which is the rest of this lesson.

Level 2 — Formal definition

int a[3][4]; declares an object a of type int[3][4]. Read the declarator outwards: a is an array of 3 elements, each element is an array of 4 int.

Verified fact C11 6.7.6.2 requires the element type of an array to be complete. int[4] is complete, so int[3][4] is a legal declaration; int[][] is not, because its element type would be the incomplete type int[].

The standard's conversion rule, C11 6.3.2.1p3: "Except when it is the operand of the sizeof operator or the unary & operator, or is a string literal used to initialize an array, an expression that has type 'array of type' is converted to an expression with type 'pointer to type' that points to the initial element." The blank is filled with the element type — here int[4], not int.

Level 3 — The three levels, in one table

a has type int[3][4], size 48, and decays to int (*)[4].

a[0] has type int[4], size 16, and decays to int *.

a[0][0] has type int, size 4, and does not decay.

Mathematical derivation 48 = 3 × 16 and 16 = 4 × 4. The sizes nest exactly as the types do, which is the check that the reading is right.

Level 5 — Boundaries and constraints

The array-to-pointer conversion happens once per expression, at the level you are standing on. It does not cascade inside a single expression: a becomes a pointer to a row, and it stays a pointer to a row until you dereference it.

A function parameter declared as an array is adjusted to a pointer before anything else is analysed (C11 6.7.6.3p7). Only the outermost dimension is discarded, so sizeof inside the callee is the size of a pointer.

A pointer may point at an incomplete type — int (*a)[] is legal — but arithmetic through it is not, because pointer arithmetic needs the pointed-to type to be complete (C11 6.5.6p2).

Level 4 — Worked example: one address, three expressions

With int a[3][4] at 1000 and 4-byte ints: a, &a[0] and &a all hold 1000. Their types are int (*)[4], int (*)[4] and int (*)[3][4].

So a + 1 is 1016 (one row of 16 bytes), &a[0] + 1 is 1016, and &a + 1 is 1048 — one past the end of the whole object. a[0] + 1 is 1004, because a[0] decays to int * and an int is 4 bytes.

Level 4 — Worked example: the two dereferences

a[2][3] expanded: *(*(a + 2) + 3).

Step 1: a + 2 is 1000 + 2 × 16 = 1032, type int (*)[4]. *(a + 2) is the row itself, type int[4], which decays to int * at 1032.

Step 2: adding 3 moves 3 × 4 = 12, giving 1044. The final * is the value stored there.

The index form gives 1000 + (2 × 4 + 3) × 4 = 1000 + 44 = 1044. Same byte. This is checked on all twelve cells, not just this one.

Level 4 — Worked example: the parameter

void f(int a[3][4]) adjusts to void f(int (*a)[4]). Inside, sizeof a is 8.

a[i][j] in the callee is still *(*(a + i) + j), which works because a + i moves i × 16 — the row width survived the adjustment.

The caller's 3 is gone. If the function needs the row count it must be a second parameter, because no expression inside the callee can recover it.

Level 6 — Edge cases preview

A row of one column: int a[3][1] — the pointer-to-array step is 4 bytes, the same as an int *, and the two orders agree on every cell.

A single row: int a[1][4] — a + 1 is one past the end, and again both orders agree.

An array of arrays of arrays: int b[2][3][4] — b decays to int (*)[3][4], which is the type of &a in the worked example above. Same type, different object.

Example 3 — forward and backward on a different shape

int a[5][6], base 1000, 4-byte ints. Find a[3][4] in both orders; then a different array, int b[4][5], whose base is not given.

Forward

Row-major: 1000 + (3 × 6 + 4) × 4 = 1000 + 88 = 1088.

Column-major: 1000 + (4 × 5 + 3) × 4 = 1000 + 92 = 1092.

The row-major multiplier is the column count (6); the column-major multiplier is the row count (5). Swapping them is the commonest arithmetic slip, and it is invisible in a square array.

Backward

Given &b[2][3] = 1112 and &b[3][1] = 1124.

The gap is 12 bytes = 3 elements. The row difference is 1 and the column difference is −2, so the column count must satisfy 1 × C − 2 = 3, giving C = 5, which matches the declaration.

Base = 1112 − (2 × 5 + 3) × 4 = 1112 − 52 = 1060. Check: 1060 + (3 × 5 + 1) × 4 = 1060 + 64 = 1124. It comes back, so the base is right.

The habit worth keeping

Back-solving produces a number whether or not the reasoning was right, so it needs a check. Recomputing a cell the question already gave you costs one multiplication and catches every slip that does not happen to cancel.

The boundary cases that change the numbers

Six shapes where a general statement becomes false or degenerate. Each is a real declaration, not a hypothetical.

A one-column row

int a[3][1]: the row is 4 bytes, so a pointer to a row and a pointer to an int have the same stride. a + 1 and a[0] + 1 both move 4 bytes.

The types still differ, so a is still not assignable to int *. Equal strides do not make equal types.

A single row

int a[1][4]: a + 1 is one past the end of the object, which is legal to form and illegal to dereference.

Row-major and column-major give the same address for all four cells, because one dimension is 1. The formulas are still different expressions.

Three dimensions

int b[2][3][4] decays to int (*)[3][4] — the same type as &a above, for a different object. Its +1 moves 48 bytes.

As a parameter, int b[][3][4] is required: two inner dimensions survive, one is discarded.

An incomplete element type

int a[][] is a constraint violation: the element type would be int[], which is incomplete, and C11 6.7.6.2 forbids an array of an incomplete type.

int (*p)[] is legal, because a pointer may point at an incomplete type. But p + 1 is not, because 6.5.6 requires the pointed-to type to be complete for arithmetic.

Two more, and the counterexample that matters most

The ragged table, and the exact byte-level failure of the int ** substitution.

The ragged table

int *rows[3] with three separate allocations: sizeof rows is 24, rows decays to int **, and rows[i] is an int *.

Rows of different lengths are impossible in one int[R][C], because every row must be the same width. That is the whole reason the pointer-array form exists.

A rectangular array passed to an int ** parameter

Reading the first 8 bytes of a as a 64-bit pointer gives 0x000003ec000003e8 — decimal 4,312,147,166,184 — because the two ints 1000 and 1004 sit next to each other in little-endian order.

That value is not inside the array object, so dereferencing it is undefined behaviour. The mistake is not "slightly wrong output"; it is a program with no defined meaning.

Counterexample: the same call, correct for one object and undefined for another

void show(int **p, int n) is a perfectly good function. Pass it rows — an int *[3] — and it is correct. Pass it a — an int[3][4] — and the behaviour is undefined, even though both calls read as show(x, 3).

So "does this function accept my array" cannot be answered from the call site. It is answered by the declaration of what you are passing. This is the one place in the topic where a program can look right, compile with a cast, and still be meaningless.

Six beliefs that survive practice, and the one line that kills each

Each entry gives the belief, the shortest refutation available, and the closely confused concept it is being mixed up with.

1. "A two-dimensional array is a pointer to a pointer"

Refutation: sizeof(a) is 48, not 8. An int ** is one word and points at stored pointers; a is 48 bytes and stores no pointers at all.

Confused with: int *rows[3], which is an array of pointers and does decay to int **. The confusion is between an array of arrays and an array of pointers, which are different objects with different contents.

2. "a and &a are different addresses"

Refutation: both are 1000. The address of an object and the address of its first byte are the same byte.

Confused with: the type, which is genuinely different: int (*)[4] against int (*)[3][4]. So +1 moves 16 against 48. Same number, different arithmetic — the trap is that comparing the printed values tells you nothing.

3. "The row count belongs in the address formula"

Refutation: address = base + (i × C + j) × w. C appears because moving down a row steps over a row of C ints. Nothing in the formula uses R.

Confused with: column-major order, where R does appear — as the multiplier for the column index. Both formulas are right; they answer different layout questions, and R belongs to only one of them.

4. "int (*p)[4] is an array of four pointers"

Refutation: sizeof is 8, not 32. The parentheses force the pointer to be declared first, so the array belongs to its target.

Confused with: int *p[4], the array of four pointers. One pair of parentheses, two types, and the difference shows in sizeof and in the stride of +1.

Two more, and a pair worth separating carefully

The parameter rule and the cast, then the distinction the whole lesson turns on.

5. "Every dimension of a parameter is optional"

Refutation: int a[][] does not compile. Exactly one dimension is discarded, and it is the outermost one; the rest must be complete types.

Confused with: int a[] as a parameter, where the single dimension is the outer one and therefore is the one that goes. The rule did not change; the number of dimensions did.

6. "A cast makes it work"

Refutation: the cast changes the compiler's opinion, not the bytes. An int ** over a rectangular array dereferences 1000 and 1004 fused into one 64-bit value.

Confused with: a cast between two pointer types that really are compatible, such as void * round trips. Those are defined; this one is not. "It compiles" is not the test.

The pair that decides most questions

Decay is a conversion: an array expression becomes a pointer to its first element, once, and only outside sizeof, & and string initialisation. It changes the type of the expression.

Parameter adjustment is a declaration rule: a parameter written with brackets is declared to be a pointer, before anything else is analysed. It changes the type of the object the function has.

They agree in effect — int a[3][4] as a parameter is int (*)[4], which is also what the caller's argument decays to — but they are two different rules in two different clauses. Mixing them up produces the belief that a function "receives the array", which it never does.

The four question shapes, and what each one is really testing

No question numbers or years are claimed here. These are shapes observed across C and data-structure questions generally, described so you can recognise them; the practice set is original.

Shape 1 — cell address

"An array A[1..10][1..15] is stored at 100 with one-byte elements in row-major order; find the address of A[i][j]."

Testing: whether you subtract the lower bounds before multiplying, and whether the multiplier is the column count. With lower bounds the formula is base + ((i − L1) × C + (j − L2)) × w.

Shape 2 — base recovered

Two cells are given and the base is asked for, or a cell is given and a different cell is asked for.

Testing: whether you convert a byte gap into an element gap before reasoning, and whether you check the answer against the second given cell. The check is one multiplication and it is the difference between right and nearly right.

Shape 3 — what the expression means

"What is the type of &a + 1?" or "are *(*(a + i) + j) and a[i][j] the same?"

Testing: whether you name the type before computing anything. The second question is answered by the definition of subscripting, not by arithmetic: they are the same by definition.

Shape 4 — which declaration is legal

"Which of these parameter declarations compiles?" with options such as int a[][4], int a[][], int **a, int (*a)[4].

Testing: the parameter rule and the completeness requirement on element types. Three of the four are legal; int a[][] is not, and int **a is legal but wrong for a rectangular array.

The solving procedure, and the traps that survive it

Four steps, in this order. Doing them out of order is where most lost marks come from.

The procedure

1. Name the object. Write the type in words: array of R arrays of C T.

2. Say what the expression became. Pointer to the element type, one level in.

3. Scale by the pointed-to type. Row width for a row pointer, element width for an element pointer.

4. Check the units. Bytes or an element index — the question asked for one of them.

Traps inside the procedure

Forgetting to subtract the lower bounds when the declaration is A[1..n] rather than A[0..n-1].

Using the row count where the column count belongs — invisible in a square array.

Reading int (*)[4] as an array of pointers, which changes sizeof from 8 to 32.

Assuming every parameter dimension is optional, when exactly one is.

What to do when the question looks unfamiliar

Almost every unfamiliar version of this topic is one of the four shapes wearing different notation. Three moves recover it: write the declared type in words; write the expression you are asked about as a pointer plus an offset; and compute the offset in elements first, then multiply by the width.

If two expressions look identical but the question says they differ, the difference is almost always the type — and the type is visible in sizeof and in the stride of +1.

Q1 MCQ Original

For int a[3][4], what is the type of the expression &a + 1?

(A) int *
(B) int (*)[4]
(C) int (*)[3][4]
(D) int **

Answer: C. &a is a pointer to the whole object, whose type is int[3][4], so the pointer type is int (*)[3][4]. Adding 1 keeps the type and moves 48 bytes, to 1048.

A ignores the missing decay: & is an exception, so a stays an array. B is the type of a itself and of &a[0], and is the commonest wrong answer because it is right for two of the three expressions. D is the type a would have if it were an array of pointers, which it is not.

Check on this page's model: a, &a[0] and &a all read 1000, and their strides are 16, 16 and 48.

Q2 NAT Original

An array int A[1..10][1..15] is stored in row-major order at base address 100 with 1-byte elements. What is the address of A[4][6]?

Answer: 150. Subtract the lower bounds first: 4 − 1 = 3 and 6 − 1 = 5. Then 100 + (3 × 15 + 5) × 1 = 100 + 50 = 150.

Two facts are being tested, and each has its own wrong answer. Forget the lower bounds and you compute 100 + (4 × 15 + 6) = 166. Use the row count 10 where the column count 15 belongs and you compute 100 + (3 × 10 + 5) = 135. Only 150 uses both facts correctly.

With one-byte elements the element index and the byte offset coincide, which is why the multiplier is 1 here. Change the element size to 4 and the same element index 50 becomes a 200-byte offset, for an address of 300.

Q3 MSQ Original

Which of these are true of int a[3][4]?

(A) sizeof(a[0]) is 16.
(B) a[0] and a have the same value.
(C) a[0] and a have the same type.
(D) a[2][3] is at 1044.

Answer: A, B and D.

A: a[0] is an int[4], four ints of four bytes. B: both name the first byte of the same object, 1000. D: 1000 + (2 × 4 + 3) × 4 = 1044.

C is false, and it is the distinction this lesson is about. a has type int[3][4]; a[0] has type int[4]. In an expression they decay to int (*)[4] and int * — different types with the same value. B is true and C is false simultaneously, which is exactly why comparing addresses proves nothing.

Q4 MCQ Original

Which declaration of a function parameter can accept int a[3][4] and index it correctly as p[i][j]?

(A) void f(int p[][])
(B) void f(int **p)
(C) void f(int (*p)[4])
(D) void f(int p[])

Answer: C. int (*p)[4] is exactly what a decays to, so p[i][j] moves i × 16 + j × 4 and lands correctly.

A does not compile: the element type would be incomplete. B compiles and is undefined — the first dereference reads 1000 and 1004 as one 64-bit pointer. D compiles, and p[i][j] would read an int as a pointer, which is undefined.

Note that void f(int p[3][4]) is also correct, because it adjusts to C. The question offers the adjusted form to check that you know the adjustment exists.

Q5 NAT Original

int b[4][5] has &b[2][3] = 1112 and &b[3][1] = 1124, with 4-byte ints and row-major order. What is the base address of b?

Answer: 1060. The gap is 1124 − 1112 = 12 bytes, which is 3 elements. The row difference is 1 and the column difference is −2, and 1 × 5 + (−2) = 3, which confirms C = 5.

Then base = 1112 − (2 × 5 + 3) × 4 = 1112 − 52 = 1060.

Check: 1060 + (3 × 5 + 1) × 4 = 1124. Without the check, an error of one row would give 1040 or 1080 and look perfectly plausible.

Q6 MCQ Original

For the same int a[3][4] at 1000, which pair of expressions has equal values but different types?

(A) a and a[0]
(B) a[0] and &a[0][0]
(C) a + 1 and a[1]
(D) a and a + 0

Answer: A. Both are 1000. a decays to int (*)[4] and a[0] decays to int *.

B is equal in value (both 1000) and equal in type: a[0] decays to int *, and &a[0][0] is an int * directly. It is the pair people expect to be the answer, and it is the pair where nothing differs. C is also equal in value and in type — both are int (*)[4] pointing at row 1, at 1016. D is the same expression twice: adding zero changes nothing, type included.

The lesson's point, stated as a rule: equal values with different types is the normal case here, not the exception.

Q7 NAT Original

What is sizeof(a[1]) for int a[3][4], with 4-byte ints?

Answer: 16. a[1] is an int[4], and sizeof is one of the three contexts where no conversion happens, so it measures the array and not a pointer.

The trap is answering 8: that is sizeof of the decayed expression, which is what you would get by writing sizeof(&a[1][0]) or by passing a[1] to a function. Inside sizeof the array stays an array.

Q8 MSQ Original

Which statements are true?

(A) int (*p)[4] and int *q[4] have the same sizeof.
(B) int a[][] is not a legal declaration.
(C) A parameter written int a[3][4] is adjusted to int (*a)[4].
(D) Row-major and column-major order agree on every cell when the array is square.

Answer: B and C.

B: the element type would be the incomplete int[], which C11 6.7.6.2 forbids. C: that is the parameter adjustment of C11 6.7.6.3p7, and only the outer dimension is discarded.

A is false: 8 against 32 — one pointer against four. D is false, and it is the trap worth remembering: on a square array the two orders agree only on the diagonal and the first row. On int a[3][3], row-major gives a[1][2] at 1020 and column-major at 1024. "Square" is not "thin": the orders agree on every cell exactly when one dimension is 1.

The five numbers

sizeof a = 48, sizeof a[0] = 16, sizeof a[0][0] = 4Three levels of the same object. A pointer would be 8.

strides: a + 1 = 16, a[0] + 1 = 4, &a + 1 = 48Scaled by the pointed-to type, which is int[4], int and int[3][4] respectively.

sizeof (int (*)[4]) = 8, sizeof (int *[4]) = 32A pointer to an array against an array of pointers. One pair of parentheses.

All five are read off the type. None is a fact about this machine beyond the two platform constants.

The two formulas

address = base + (i × C + j) × wRow-major: the multiplier is the column count, because a row holds C elements.

address = base + (j × R + i) × wColumn-major: the multiplier is the row count. C arrays are row-major; this appears as a hypothetical.

With lower bounds: replace i by (i − L1) and j by (j − L2). The two orders agree on every cell exactly when R = 1 or C = 1.

The routine

1. Name the object in words: array of R arrays of C T.

2. Say what the expression became: pointer to the element type, one level in.

3. Scale by the pointed-to type, then add.

4. Check the units: bytes, or an element index.

The five traps

Treating a as a pointer because a[i] works.

Writing R where C belongs in the row-major formula.

Reading int (*p)[4] as an array of pointers.

Thinking every parameter dimension is optional.

Casting to silence the compiler.

Three sentences to leave with

A two-dimensional array is one object whose elements are arrays; every other fact in this topic is a consequence of that sentence.

Decay is a conversion of the expression, and parameter adjustment is a rule about the declaration; they agree in effect and are not the same rule.

If two expressions print the same address, ask for their types before you compare where +1 goes.

What this lesson rests on, and where the research stopped

Each source is listed with what it supports. Verified facts are things a source states; derivations are worked out on the page; interpretations are analogies.

The standard

ISO/IEC 9899 (C11/C17), clause 6.3.2.1p3 — the array-to-pointer conversion and its three exceptions. Quoted verbatim on the Build-up tab.

Clause 6.7.6.3p7 — "A declaration of a parameter as 'array of type' shall be adjusted to 'qualified pointer to type'". This is the parameter rule in scene 7.

Clause 6.7.6.2p1 — the element type of an array shall not be incomplete. This is why int a[][] is rejected.

Clause 6.5.2.1p2 — E1[E2] is defined as *((E1) + (E2)). This is the definition scene 5 applies twice. Clause 6.5.6 — pointer arithmetic requires a complete pointed-to type.

Secondary sources consulted

Public discussion of clauses 6.3.2.1p3 and 6.7.6.3p7 on Stack Overflow, including answers that quote both clauses in full and work through int x[3][4] adjusting to int (*x)[4], and why the implementation needs the second dimension but never the first.

These were used to check the wording of the rules, not to source any number. Every number on the page comes from the page's own model.

The syllabus

GATE 2027 CS syllabus, IIT Madras, Section 4 Programming and Data Structures: "Programming in C. Recursion. Arrays, stacks, queues, linked lists, trees, binary search trees, binary heaps, graphs." Read from the official syllabus PDF for GATE 2027 during this run.

The clause Arrays is named, which is why this lesson is classified A. The multidimensional case is a sub-topic of that clause and is not separately named — the classification is about the clause, and the depth here is a teaching decision.

What was not established

No previous-year question on multidimensional arrays could be matched to a GATE year and paper in this run's research, so none is quoted. Practice archives do circulate such items, but the attributions did not survive checking.

No frequency or weightage claim is made. The two platform constants — 4-byte ints and 8-byte pointers — are a stated model, not a measurement of any machine. Every conclusion holds for any width; only the byte counts change.

How the numbers were produced

The page builds the declared type as nesting — arrayOf(3, arrayOf(4, int)) — and reads every size and stride off that structure rather than writing the numbers down. It then computes all twelve cell addresses twice, once by the index formula and once by the pointer walk, and compares them; it builds the 48-byte image of the array and reads the first two 8-byte words out of it as a little-endian machine would; and it checks that the row-major and column-major formulas agree on every cell of sixteen shapes exactly when one dimension is 1. The check panel in the Animation tab states how many of the page's own claims passed. A separate prototype of the same arithmetic was written and run first, and the two agree on every value.
