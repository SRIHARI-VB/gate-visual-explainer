Topic and objective

TOPIC: What the TCP option space costs and what it buys: the forty bytes a header can spare, the maximum segment size computed as MTU minus the fixed headers, the rule that options reduce the data and not the advertised MSS, and the window retraction that a scaled window cannot avoid.

LEARNING OBJECTIVE: Given a list of options, add their lengths, round the total to a multiple of four and state the header size and the payload that remains. Given an MTU and an IP version, compute the MSS and the data a segment carrying options can hold. Given a shift count, an acknowledgement and a receive buffer, say which window fields are expressible, which one is safe, and bound the retraction in bytes.

I read the request as the option space and the two arithmetic rules that hang off it: the MSS clause of Section 10 and the window-retraction rule that the flow-control lesson names without building. Both are this page.

The five ideas, in one line each

  • Forty bytes is the whole option area: 20 to 60 bytes of header, and every option shares the difference.
  • MSS is data only: the MTU minus 40 for IPv4 and minus 60 for IPv6, and 536 when no option arrives.
  • Options lower the data, not the MSS: 1460 advertised, 1440 sent with twenty bytes of options.
  • The field counts steps: a scaled window can only name right edges that are a whole number of 2^s from the acknowledgement.
  • Retraction is bounded: at most 2^s − 1 bytes, and the rules require both ends to handle it.

Intuition first: a fixed-size envelope with a fixed-size label strip

Picture an envelope that may be at most sixty units long, of which the first twenty are printed with the address. The remaining forty units are blank, and every label you stick on has to come out of that strip. One label says how big a parcel the recipient can take; another says how to read a number that has outgrown its box; a third is a permission slip; a fourth is a clock reading. They are cheap individually and expensive together, and the envelope does not grow.

Educational interpretation The envelope explains why options compete; it does not explain why the MSS must not absorb their cost, which is a separate rule about what the promise means. Scene 4 supplies that.

Vocabulary, every term in words

MTU — the largest IP datagram a link will carry without fragmenting it.

MSS — the largest amount of TCP data a host will accept in one segment; data only.

Option kind — the first byte of an option, naming which option it is.

Option length — the second byte, counting the kind and length bytes themselves.

NOP and EOL — kinds 1 and 0, each one byte, used as padding and as an end marker.

Shift count s — the exponent in the window scale option; one step is 2^s bytes.

Right edge — acknowledgement number plus window; the last byte the sender may write.

Retraction — advertising a smaller window than before, so the right edge moves back.

Granularity — the step size 2^s, which is the smallest change the field can express.

The three rules, stated once

The sizes, in the form the documents write them:

header = 20 + options <= 60
MSS = EMTU_R - fixed IP header - 20
SEG.WND = RCV.WND >> Rcv.Wind.Shift

Verified fact The header ceiling is from RFC 9293's four-bit data offset; the MSS rule is RFC 6691 section 2; the window rule is RFC 7323 section 2.3. All three were read on 2026-11-04.

Why the budget is fixed

The header length is a four-bit count of 32-bit words, so it can name at most fifteen words. That field is in every segment on the network, and changing it would break every implementation that parses the header, so the ceiling of sixty bytes is part of the format rather than a choice.

Every extension TCP has gained since 1981 — window scaling, timestamps, SACK, MD5 signatures — had to be paid for inside those forty bytes.

Example 1 — the header four options produce

Given a SYN carrying MSS (kind 2, length 4), window scale (kind 3, length 3), SACK-permitted (kind 4, length 2) and timestamps (kind 8, length 10). Asked the option area, the header size, and the data a 1500-byte MTU leaves.

The lengths add to 4 + 3 + 2 + 10 = 19. The header must be a whole number of 32-bit words, so the area rounds up to 20 and the header is 20 + 20 = 40 bytes. On a 1500-byte MTU with a 20-byte IPv4 header, the data is 1500 − 20 − 40 = 1440 bytes.

Mathematical derivation The page recomputes 19, 20, 40 and 1440 at load and prints them in scenes 2 and 4.

Example 2 — the same options, padded per option

Given a stack that pads each option to its own word boundary, using no-operation bytes before the window scale and before the timestamps. Asked the cost and the header.

MSS 4, then one NOP and window scale 3 for 4, then SACK-permitted 2, then two NOPs and timestamps 10 for 12. The raw total is 22, which rounds to 24, so the header is 44 bytes and the data is 1436.

Verified fact RFC 7323 Appendix A recommends exactly the two-NOP-plus-timestamps layout for alignment, so both totals are real: 20 bytes when only the header must be aligned, 24 when each option is.

Example 3 — four MTUs, two IP versions

Given MTUs of 576, 1500 and 9000 over IPv4, and 1500 over IPv6. Asked the MSS each host advertises.

IPv4 subtracts 20 for the IP header and 20 for TCP: 536, 1460 and 8960. IPv6 subtracts 40 and 20: 1440. The IPv6 minimum MTU of 1280 gives 1220, and the smallest legal IPv4 MTU of 68 gives 28.

Mathematical derivation Each value is the MTU minus the two header sizes, and 536 is also the default assumed when no MSS option arrives at all.

Example 4 — the segment that would fragment

Given an advertised MSS of 1460 and 20 bytes of options in the segment. Asked what happens if the sender uses the full MSS.

1460 + 40 + 20 = 1520 bytes, which is 20 bytes past the 1500-byte MTU. IP must fragment the segment, so one lost fragment costs the whole segment and the retransmission repeats the problem.

Verified fact RFC 6691 section 2 says the sender must reduce the data length to account for the options it includes, for exactly this reason.

Example 5 — filling the budget exactly

Given the same four options and a TCP MD5 signature option (kind 19, length 18). Asked whether they fit, and what the header becomes.

19 + 18 = 37 raw bytes, which rounds to 40. The option area is full, the header is 60 bytes, and on a 1500-byte MTU the data is 1420 bytes. Payload efficiency is 94.67 per cent, against 97.33 with no options at all.

Mathematical derivation One more four-byte option would give 41, one byte over, before any padding — so the five-option combination is already at the ceiling.

Example 6 — which window fields exist

Given a shift count of 7, an acknowledgement of 1000, and a receive buffer that ends at 1300. Asked the expressible right edges and the safest field.

One step is 128 bytes, so the field can name 1128, 1256, 1384 and so on. The buffer end at 1300 is not on that list: field 2 understates the window by 44 bytes, and field 3 overstates it by 84.

The safe choice is 2, because understating the window costs throughput and overstating it costs data the buffer cannot hold.

Example 7 — the retraction, row by row

Given the appendix example: acknowledgement 1000 with field 2, then 1040 with field 2, then 1045 with field 2 or field 1.

The right edges are 1256 (44 short), 1296 (4 short), 1301 (one past the buffer) and 1173 (127 short). At the last acknowledgement no field puts the edge at 1300, so the receiver must either over-promise by one byte or retract by 127.

Mathematical derivation 1045 + 2×128 = 1301 and 1045 + 1×128 = 1173; the true edge 1300 lies strictly between the two expressible edges, so no field value reaches it.

The boundaries, each with its number

Six cases where the arithmetic changes behaviour: the smallest legal MTU, the largest MTU, the IPv6 header, the absent option, the zero shift, and the full option area.

A 68-byte MTU leaves an MSS of 28

The smallest legal IPv4 MTU is 68 bytes. Subtract 20 for the IP header and 20 for TCP and 28 remain, which is legal and nearly useless.

The number matters because it shows the MSS is a subtraction and not a constant: no formula with a fixed 1460 survives an unusual link.

Jumbo frames give 8960, and a jumbogram gives infinity

A 9000-byte MTU gives an MSS of 8960. Over IPv6 jumbograms, where a segment may exceed 64 KiB, a value of 65,535 in the sixteen-bit field is treated as infinity and path MTU discovery decides the real size.

So the largest number the field can hold is a special case, not a measurement of 65,535 bytes of payload.

IPv6 subtracts sixty, not forty

The IPv6 base header is 40 bytes with no options field, so the subtraction is 40 + 20. A 1500-byte MTU gives 1440, and the IPv6 minimum MTU of 1280 gives 1220.

An IPv6 extension header is not in the fixed count, so it behaves like a TCP option: the data shrinks by its size and the advertised MSS does not.

No option means 536, not "anything"

If no MSS option arrives, the sender must assume a send MSS of 536 bytes, which is 576 minus 40. The absent option is not permission to send any size; it activates a conservative default.

The coincidence is worth noticing: 536 is both the default and the MSS computed from a 576-byte MTU, because the default was derived from the minimum reassembly size.

A zero shift retracts nothing

With s = 0 the step is one byte, so the field can name every window exactly and the bound 2^s − 1 is zero. Retraction is a consequence of scaling, not of TCP itself.

That is why the rule lives in the window scale document rather than in the base specification.

The full option area: exactly forty, and not one byte more

With 40 bytes of options the header is 60, which is the largest the four-bit data offset can name. The data on a 1500-byte MTU is 1420 bytes, and every byte of option is a byte of payload given up on every segment of the connection.

A combination that needs 41 bytes cannot be sent in one segment at all: options cannot spill into a second header, and there is no way to negotiate a longer header.

Seven beliefs that produce a wrong answer

Each is paired with the counterexample that breaks it. Every counterexample is computed by the page.

1 — "The MSS counts the headers as well"

Wrong: the MSS counts data octets only, which is why an MSS of 1460 exactly fills a 1500-byte MTU with 20 + 20 bytes of header.

Counterexample: 1460 + 20 + 20 = 1500. Adding the headers inside the MSS would leave the datagram 40 bytes short of the MTU, not exactly at it.

2 — "Options reduce the MSS you advertise"

Wrong: RFC 6691 says to subtract only the fixed headers, and to reduce the data instead.

Counterexample: a host that will send 20 bytes of options still advertises 1460, and the segment carries 1440 bytes of data. Advertising 1440 would understate what it can receive by 20 bytes on every segment.

3 — "Both directions use one negotiated MSS"

Wrong: the MSS is a promise about receiving, made separately by each side, and the two values can differ.

Counterexample: a client on a 1500-byte link advertises 1460 while a server behind a tunnel advertises 1360. The client may send 1360-byte segments to the server, and the server 1460-byte segments to the client.

4 — "MSS = MTU − 40 always"

Wrong: 40 is the IPv4 case. IPv6 subtracts 60, and IP options or extension headers take more still.

Counterexample: an MTU of 1500 gives 1460 over IPv4 and 1440 over IPv6 — a difference of 20 bytes on every segment.

5 — "Each option may be up to 40 bytes"

Wrong: 40 is the whole option area, shared by every option in the header.

Counterexample: the four handshake options use 19 bytes and an MD5 signature uses 18, which is 37 and fits; a fifth four-byte option would reach 41 and cannot be sent at all.

6 — "A shrinking window means the receiver lost data"

Wrong: the retracted bytes were never acknowledged as receivable; the receiver simply cannot express the true edge in whole steps.

Counterexample: at acknowledgement 1045 with a step of 128, the true edge 1300 lies between 1173 and 1301, so both available fields are wrong by construction, and the smaller one is the safe one.

7 — "A sender may ignore a shrinking window entirely"

Wrong: only the first retransmission gets that allowance, and only when it is out of window by less than one step and the original was in window when it was sent.

Counterexample: after the first retransmission, every further one must lie inside the latest advertised window, so a sender that keeps retransmitting past the retracted edge is outside the rules and will be dropped by a receiver that honours only its latest advertisement for new data.

How this becomes a question, and the procedure that answers it

Three shapes appear: an MSS from an MTU, a header and payload from a list of options, and a window decision from a shift count. Each has a fixed procedure, and each procedure has one step that is usually skipped.

Shape 1 — the MSS

1. Read the MTU and the IP version.

2. Subtract the fixed IP header: 20 for IPv4, 40 for IPv6.

3. Subtract the fixed TCP header, 20.

The skipped step is the IP version: subtracting 40 for an IPv6 datagram gives a value 20 bytes too large.

Shape 2 — header and payload from options

1. Add the option lengths, counting the kind and length bytes.

2. Round the total up to a multiple of four.

3. Header = 20 + that total; payload = MTU − IP header − header.

The skipped step is the rounding: 19 bytes of options is a 40-byte header, not a 39-byte one, because the offset counts whole words.

Shape 3 — the window decision

1. Compute the step 2^s and list the expressible edges from the acknowledgement.

2. Compare each with the true buffer end.

3. Choose the largest edge that does not exceed the buffer, and state the shortfall.

The skipped step is step 3's direction: the safe error is understating the window, and the bound on it is 2^s − 1 bytes.

Shape 4 — the budget combination

1. Add the lengths of the options named in the question.

2. Round to a multiple of four and compare with 40.

3. If the total exceeds 40, say which option must be dropped and why.

The trap here is step 1: forgetting that a length byte counts itself, so MSS is 4 and not 2.

NATOriginal practice

A TCP SYN carries the MSS option (length 4), the window scale option (length 3), SACK-permitted (length 2) and timestamps (length 10). The TCP header length in bytes is ______ .

Answer: 40

The lengths add to 19. The header must be a whole number of 32-bit words, so the option area rounds up to 20 and the header is 20 + 20 = 40 bytes.

Why 39 appears. Adding the fixed header to the raw 19 and forgetting the rounding. Why 44 appears. Padding each option to its own word boundary, which is a different convention and not what the question asks.

MCQOriginal practice

A host is attached to an IPv6 link with an MTU of 1500 bytes. It sends no MSS option value of its own choice but follows the standard arithmetic. The MSS it advertises is

  1. 1460
  2. 1440
  3. 1480
  4. 1220

Answer: B

1500 − 40 for the IPv6 base header − 20 for the TCP header = 1440.

Why 1460 appears. Subtracting 40 as if the datagram were IPv4. Why 1480 appears. Subtracting only the TCP header. Why 1220 appears. Using the IPv6 minimum MTU of 1280 instead of the link MTU.

NATOriginal practice

An IPv4 connection has an MTU of 1500 bytes and carries 20 bytes of TCP options in every data segment. The largest amount of TCP data one segment can carry is ______ bytes.

Answer: 1440

1500 − 20 for the IPv4 header − 40 for the TCP header (20 fixed plus 20 of options) = 1440.

Why 1460 appears. Using the advertised MSS and ignoring the options, which would make a 1520-byte datagram. Why 1420 appears. Subtracting 40 bytes of options instead of 20.

MSQOriginal practice

Which of the following are true of the TCP MSS option?

  1. It counts data octets and excludes the TCP and IP headers.
  2. It is reduced by the size of the TCP options the sender uses.
  3. Each direction has its own value, advertised by the receiver of that direction's data.
  4. If no option arrives, any segment size is allowed.

Answer: A and C

A is the definition: data only. C is the directionality: each side promises what it can receive.

B is false: options do not reduce the advertised MSS; the sender reduces the data in the segment instead. D is false: the absent option activates a default send MSS of 536 bytes, which is a bound and not a permission.

MCQOriginal practice

A connection uses a shift count of 7. The receiver has acknowledged byte 1045 and its buffer ends at byte 1300. Which window field can it advertise without promising a byte it cannot store?

  1. 1
  2. 2
  3. 3
  4. No field can be advertised.

Answer: A

Field 1 means 128 bytes, putting the right edge at 1173, which is below 1300. Field 2 means 256 bytes, putting the edge at 1301, one byte past the buffer.

Why 2 appears. Reading the true window of 255 bytes and rounding to the nearest field instead of down. Why 3 appears. Rounding the window up. Why D appears. Concluding that an inexact window cannot be advertised, when understating it is always allowed.

NATOriginal practice

A scaled connection has a shift count of 10. The largest number of bytes by which a single advertised window can be retracted is ______ .

Answer: 1023

One step is 2^10 = 1024 bytes, and the worst case is one step minus one byte, so 1023.

Why 1024 appears. Using the step itself rather than the gap below the next expressible edge. Why 10 appears. Reading the shift count as a byte count.

MSQOriginal practice

Which statements about window retraction are true?

  1. It can only happen when a non-zero shift count is in use.
  2. A receiver must honour a segment that was in window for an acknowledgement it has already sent.
  3. A sender may ignore the window for every retransmission of a segment.
  4. The worst case is 2^s bytes, where s is the shift count.

Answer: A and B

A follows from the arithmetic: with s = 0 the step is one byte and every window is expressible, so the bound is zero. B is the receiver's honour rule, which protects data already promised.

C is false: only the first retransmission has that allowance, and only when it is out of window by less than one step. D is false: the bound is 2^s − 1, because the true edge can sit just below the next expressible edge.

MCQOriginal practice

A SYN carries MSS (4 bytes), window scale (3), SACK-permitted (2), timestamps (10) and a TCP MD5 signature option (18). What happens?

  1. The header is 62 bytes, which exceeds the maximum.
  2. The options total 37 bytes, pad to 40, and the header is 60 bytes.
  3. The options total 37 bytes and the header is 57 bytes.
  4. The MSS option must be dropped because the total exceeds 40.

Answer: B

4 + 3 + 2 + 10 + 18 = 37, which rounds up to 40. The header is 20 + 40 = 60 bytes, exactly the ceiling the four-bit data offset allows.

Why A appears. Padding each option separately and adding. Why C appears. Forgetting the rounding. Why D appears. Adding one more option than the question lists: 37 + 4 = 41 would indeed not fit, but no fifth option is present.

Definitions and constants

  • TCP header: 20 bytes fixed, 60 bytes maximum, so 40 bytes of options.
  • Option lengths: MSS 4, window scale 3, SACK-permitted 2, timestamps 10, MD5 18.
  • Padding: the option area is a whole number of 32-bit words.
  • MSS: the effective MTU minus the fixed IP and TCP headers, counting data only.
  • Default send MSS with no option: 536 bytes.
  • Retraction bound: 2^s − 1 bytes, where one step is 2^s.

Procedures, in the order they are applied

  1. Add the option lengths, round the total up to a multiple of four, add 20 for the header.
  2. Subtract the IP header and the whole TCP header from the MTU to get the data.
  3. Compute the MSS as the MTU minus only the fixed headers, and never reduce it for options.
  4. For a window, compute the step 2^s and list the edges from the acknowledgement.
  5. Choose the largest edge that does not exceed the buffer, and state the shortfall.

The numbers worth carrying

  • 19 bytes: the four handshake options, raw; 20 after rounding.
  • 40 bytes: the header those options produce; 1440 bytes of data on Ethernet.
  • 1460 and 1440: the MSS over IPv4 and over IPv6 on a 1500-byte MTU.
  • 1520: the datagram produced by ignoring options, 20 bytes too large.
  • 127 and 16,383: the worst retraction at shift 7 and at shift 14.
  • 11.22: how many 1460-byte segments 16,383 bytes is.

The five slips

  • Counting headers inside the MSS, which leaves a datagram 40 bytes short.
  • Reducing the advertised MSS for options, understating what the host can receive.
  • Assuming one shared MSS, when each direction has its own.
  • Reading 40 bytes as a per-option limit instead of the whole area.
  • Treating a shrinking window as an error rather than handling it.

Three sentences to carry into the exam

The header cannot grow past sixty bytes, so every option is paid for out of one forty-byte budget, and the sum of option lengths is rounded up to a whole number of words. The MSS is a promise about data only, computed from the MTU and the fixed headers, and options reduce the data in the segment rather than the promise. A scaled window can only name right edges that are whole steps from the acknowledgement, so a receiver may have to advertise a smaller window than before, by at most one step minus a byte, and both ends must handle it.

What each source supports, and what it does not

RFC 9293 supports the header ceiling and the option format. RFC 6691 supports the MSS arithmetic and the split between the promise and the payload. RFC 7323 supports the retraction rules and the example, whose four rows the page reproduces as arithmetic rather than as a quotation. The IANA registry supports the lengths.

None of them states that 40 bytes is a good design, and none gives a payload-efficiency formula; the efficiency figures are arithmetic on the sizes this page computes.
