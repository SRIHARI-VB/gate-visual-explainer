Topic and objective

TOPIC: Journaling in a file system — the write-ahead log, the commit record, the three commit orders (journal, ordered, writeback), and the recovery that replays the log. One mechanism, one question: after a crash in the middle of a metadata update, is the file system half updated?

LEARNING OBJECTIVE: Given a workload of transactions and a commit discipline, write out the sequence of block writes, choose any crash point, recover the disk by replaying to the last commit record, and say whether the result breaks a metadata invariant or exposes bytes the file never wrote. Then count the write cost of the log as $$2m+3$$ block writes for $$m$$ metadata blocks, bound a circular journal by its capacity and by the largest transaction that must fit in it, and say which of the four disciplines removes which kind of failure.

I read this topic as one ordering rule, one atomic block, and four ways of using them. Every number on this page — the 10 crash points of the unjournaled run and the 6 that break, the 88 recovered images across four disciplines, the 3 of 6 in-place orders that expose stale bytes, the 7 writeback crash points that do, the 2m+3 cost, the 16 transactions a 64-block journal holds, and the 4,096-fold difference between replaying a log and scanning a disk — is produced at load by the lesson's own block-level model and re-checked against the property it claims.

The five key ideas

  1. A file operation is several independent block writes, and a crash can land between any two of them.
  2. Write the new image of every block into a log first, and never overwrite a home block before its image is durable.
  3. One extra block — the commit record — turns several writes into one atomic unit.
  4. Recovery is redo only: replay to the last commit, discard everything after it, and never undo.
  5. Which journal you run decides whether you also get the bytes: metadata-only ordered protects structure and data; metadata-only writeback protects structure only.

Takeaway

A journal buys atomicity, and atomicity is a statement about a transaction — never about the values inside it. The commit record makes a transaction happen exactly once; the ordering rule decides whether the bytes it describes are there when you read them. On this page those two promises are measured separately, which is why writeback can be durable at 5 crash points and intact at only 2.

Level 1 — Intuition: the order book

A shopkeeper who must never be caught mid-edit keeps two books. In the first she writes down exactly what she is about to change in the second, signs the page, and only then copies the changes across. If the lights go out, she opens the first book: any page with her signature gets copied across again, and any page without one is torn out and forgotten. She is never left with half an entry, because "signed" is a single act that either happened or did not.

That is the whole design. The first book is the journal, the signature is the commit record, copying across is the checkpoint, and reopening the first book is recovery. Educational interpretation The analogy stops at one point: the shopkeeper tears out pages, while a real journal overwrites them in a circle.

Level 2 — Formal definition

A transaction is a set of block writes that must all take effect or none. Write it as a list of pairs $$(b, I)$$ where $$b$$ is the home block number and $$I$$ is the complete new image of that block.

The write-ahead rule: for every pair in the transaction, the image $$I$$ must be durable in the journal before any byte of block $$b$$ is overwritten.

The commit record is one journal block written after every image of the transaction. A transaction is committed exactly when its commit record is durable.

The descriptor block precedes the images and lists the home block of each one, so recovery knows where to copy.

Recovery scans the journal from its tail to the last commit record and copies each logged image to its home block. Nothing is undone, and nothing after the last commit is applied.

The four invariants this lesson checks

"Consistent" is not a feeling. It is four properties of the disk image, and the model checks all four on every recovered image:

M1 no dangling reference. Every block an inode names is marked used in the bitmap. Break it and the block can be handed to another file while it is still referenced.
M2 no leak. Every used block is named by some inode. Break it and the space is lost until a full scan rebuilds the bitmap.
M3 no aliasing. No block is named by two inodes.
D1 no foreign bytes. A block a file names holds content that file wrote. Break it and the file reads a deleted file's data.

M1, M2 and M3 are metadata invariants. D1 is a data invariant. Every journal protects the first three; only some protect the fourth.

Level 3 — The workload, in full

A tiny but real file system: a bitmap, one inode table, and eight data blocks of 4 KiB. File g owns block 0. Blocks 1, 2 and 3 are free but still hold the bytes x#1, x#2, x#3 of a file deleted earlier — freeing a block does not erase it.

Three transactions run in sequence:

  • T1 create f — 2 metadata blocks (bitmap, inode table) and 2 data blocks.
  • T2 unlink g — 2 metadata blocks, no data block at all.
  • T3 append to f — 2 metadata blocks and 1 data block.

Without a journal that is 9 in-place writes and therefore 10 crash points. With metadata journaled it is 24 write points and 25 crash points; with the data journaled too, 27 and 28. Across four disciplines the model recovers and checks 88 images.

Level 3 — The four disciplines

The same three transactions under each:

none. No journal. Every block written in place, metadata first. This is ext2.
writeback. Metadata journaled. Data may reach its home block after the commit record is durable.
ordered. Metadata journaled. Data is forced to its home block before the commit record. This is the ext4 default.
journal. Data and metadata both written into the log first. This is data=journal.

The first three letters of each name are what a mount option chooses. They are not four algorithms: the last three share one redo journal and differ only in where the data block sits.

The one-line reminder for the prerequisites

An inode is a fixed-size record holding a file's size and the numbers of its data blocks. The bitmap is one bit per block saying used or free. A directory is a list of (name, inode number) pairs. Nothing else is needed to read the rest of this lesson: every operation in the workload is a change to one of those three structures, and each change is one block write.

Worked example 1 — the unjournaled crash census, crash point by crash point

Nine in-place writes, ten crash points. Writing each one out and checking the four invariants gives:

k=0 nothing written: clean. k=1 bitmap says blocks 1 and 2 are used, but no inode names them: two leaked blocks. k=2 the inode for f is in place and names blocks 1 and 2, which still hold x#1 and x#2: foreign bytes. k=3 block 1 holds f#1, block 2 still holds x#2: still foreign. k=4 T1 complete: clean.

k=5 T2's bitmap write frees block 0, but the inode for g still names it: a dangling reference, which is real corruption, because block 0 can now be handed to a new file. k=6 T3 marks block 3 used with no inode naming it: a leak. k=7 f now has size 3 and names block 3, which still holds x#3: foreign. k=8 and k=9: clean.

Result: 6 broken crash points, 4 clean, and exactly 1 at which all three operations survive whole. Note that the two kinds of failure alternate: three are metadata failures and three are byte failures, and the model counts them separately for that reason.

Worked example 2 — the same workload journaled

Journal the metadata only. Each transaction now costs 1 descriptor + 2 images + 1 commit record in the log, plus the in-place writes, plus one head update. T1 becomes 9 write points, T2 becomes 7, T3 becomes 8: 24 write points and 25 crash points.

Crash anywhere and recover. Before T1's commit record the journal has no commit, so nothing is replayed and the disk is the old image: consistent. After it, the two logged images are copied home whatever the in-place writes had done: consistent.

Result: 0 of 25 crash points break a metadata invariant. Adding the data to the log as well gives 27 write points and 28 crash points, and 0 of 28 break either kind.

Worked example 3 — where writeback loses the bytes

T1 under data=writeback: descriptor, two images, commit, then the in-place bitmap, the in-place inode, then the two data blocks. Recovery replays the metadata the moment the commit record is durable, which is write point 4.

From write point 4 to write point 7 the file is listed with size 2 and blocks [1, 2] while blocks 1 and 2 still hold x#1 and x#2. That is 4 crash points inside T1. T3 adds 3 more between its commit and its data block.

Result: 7 of 25 crash points expose foreign bytes, and 0 of 25 break metadata. The same workload under data=ordered is 0 and 0, because the data block is forced home before the commit record exists.

Worked example 4 — the cost, counted

A journaled transaction of $$m$$ metadata blocks writes: 1 descriptor, $$m$$ images, 1 commit record, then $$m$$ in-place writes, then 1 head update. That is $$2m+3$$.

At $$m=1$$: 5 writes instead of 1, a ratio of 5. At $$m=2$$: 7 instead of 2, a ratio of 3.5. At $$m=4$$: 11 instead of 4. At $$m=64$$: 131 instead of 64, a ratio of 2.047.

The +3 is constant, so the ratio falls towards 2 as transactions get larger — which is why the constant is amortised by batching many blocks into one commit.

Worked example 5 — bounding the journal

A 64-block journal. One transaction of 2 metadata blocks occupies 1 + 2 + 1 = 4 blocks, so $$\lfloor 64/4 \rfloor = 16$$ transactions fit before the head catches the tail and the writer stalls for a checkpoint.

A single transaction must fit whole, so the largest one this journal can commit has $$64-2 = 62$$ metadata blocks. A 63-block transaction cannot be journaled at all.

And replay is bounded by the journal, not the disk: 64 blocks against the 262,144 blocks of a 1 GiB disk in 4 KiB blocks — 4,096 times less work, with the ratio growing as the disk grows.

Worked example 6 — the six orders of one append

T3 writes a bitmap block, an inode block and one data block, in place. All six orders of those three writes:

bitmap, inode, data — unsafe. bitmap, data, inode — safe. inode, bitmap, data — unsafe. inode, data, bitmap — unsafe. data, bitmap, inode — safe. data, inode, bitmap — safe.

Exactly 3 of 6 are unsafe, and they are precisely the orders that place the inode before the data block. The rule is not "3 out of 6" as a fact to memorise; the rule is that the inode must not name a block before that block holds the file's bytes.

Where the rule stops working, and what each boundary actually does

A journal is a small mechanism with sharp edges. Each card names one boundary, the condition it violates, and the consequence measured on this page or stated in the kernel documentation.

Counterexample 1 — a leak is not corruption, and a dangling reference is

Crash point 1 of the unjournaled run leaves two blocks marked used that no inode names. Nothing reads them, nothing is wrong with any file: the only loss is space, and a scan that rebuilds the bitmap from the inodes recovers it.

Crash point 5 is different in kind. Block 0 is marked free while the inode for g still names it. The allocator may now hand block 0 to a new file, and g will read that file's data. The same class of half-update, two very different severities — which is why the model counts them separately.

Boundary 1 — a transaction larger than the journal

The write-ahead rule requires the whole transaction's images to be durable before any home block is touched. If the transaction does not fit in the journal, there is no legal place to put it.

In this lesson's 64-block journal the ceiling is 62 metadata blocks, because the descriptor and the commit record need a block each. Real file systems therefore split large operations into several transactions, and the split point becomes an atomicity boundary — two commits, not one.

Boundary 2 — revoke records

Suppose a block is written, committed, then freed and reused by a later transaction, and the crash comes before the first transaction's log space is reused. Replaying the old image would resurrect data into a block that now belongs to somebody else.

The kernel's journal layer therefore assembles a list of revoke blocks during recovery, and the final pass replays only un-revoked blocks. Recovery is three passes for exactly this reason: find the end of the log, assemble the revokes, replay the rest.

Boundary 3 — the commit interval is a durability window

The commit record is only written when a transaction closes. ext4 closes one every 5 seconds by default, so up to 5 seconds of acknowledged work can vanish in a crash while the file system itself stays perfectly consistent.

Those are two different failures and a question can ask either. Losing recent work is the commit interval; damaging the structures is what the journal prevents. A smaller interval narrows the first and does nothing for the second.

Boundary 4 — write barriers and volatile caches

The ordering rule in data=ordered is only real if the device honours a flush. A disk with a volatile write cache may acknowledge the data block and reorder it behind the commit record anyway, and then the ordering rule is a fiction.

That is what a write barrier is for, and why ext4 enables barriers by default while ext3 did not. With a battery-backed cache the barrier can be turned off safely, and that is a performance decision rather than a correctness one.

Boundary 5 — a crash during recovery

Recovery itself can be interrupted. Because replay copies images, replaying twice leaves the same disk as replaying once — the model compares the two images byte for byte and finds them equal.

This is why a machine that loses power while replaying the journal on boot is not a disaster: the next boot replays again from the same tail. It is also why image redo is preferred to a scheme that applies deltas.

Boundary 6 — the clean unmount

If the file system was unmounted cleanly there is nothing to replay, and the journal is skipped entirely. norecovery and noload force that skip even after an unclean shutdown.

The documentation is explicit that skipping the replay on a dirty file system leads to inconsistencies that can cause any number of problems. The skip is a diagnostic tool, not an optimisation.

Counterexample 2 — a wrong value replays just as faithfully

The model journals a deliberately corrupt inode that names block 4 while the bitmap says block 4 is free, commits it, and recovers. The recovered image contains exactly that inode: the dangling reference is restored with perfect fidelity, along with four byte-level violations on the other blocks. Atomicity did its job — the transaction happened exactly once — and the file system is still wrong. No amount of journaling can distinguish a wrong block number from a right one; only a check that compares the disk against an expectation can, and a file system has no such expectation.

Five wrong beliefs, each with the smallest thing that refutes it

A misconception is worth stating in the form that makes it tempting, then breaking it with one measurement rather than with an assertion.

1. "A journaling file system is a log-structured file system"

Why it tempts: both write sequentially, both are described as "logging", and both appear in the same chapter.

The refutation: in this lesson every block has a fixed home address and is overwritten there once the log is committed. A log-structured file system never overwrites in place — it writes new versions at the head of the log and makes the whole disk the log.

Correct rule: a journal is a small circular buffer in front of fixed block positions; an LFS replaces the block positions with the log.

2. "If the transaction committed, my data is safe"

Why it tempts: the commit record is the moment the file system treats the operation as having happened, so it feels like the moment everything is on disk.

The refutation: under writeback the workload is durable at 5 crash points and intact at only 2. The other 3 have a durable commit record whose data block had not landed.

Correct rule: the commit record covers the transaction; whether the bytes are there is a separate promise, made by the ordering rule or by journaling the data.

3. "Replaying the journal twice corrupts the disk"

Why it tempts: in an undo log, applying a compensation twice really would be wrong, and the vocabulary is shared.

The refutation: replay copies block images. Copying an image twice leaves the image. The model replays once and twice and compares the two recovered images byte for byte; they are equal.

Correct rule: image redo is idempotent, and that is exactly what makes a crash during recovery harmless.

4. "Journaling removes the consistency check"

Why it tempts: boot time after a crash drops from minutes to milliseconds, so the check appears to be gone.

The refutation: the check is still the only tool that can rebuild the structures after a bad log block, a media error, or a deliberately forced scan. It has moved off the normal path, not out of the system.

Correct rule: journaling replaces the routine full scan; it does not replace the tool.

5. "Ordered mode is a stronger journal"

Why it tempts: ordered gives strictly better guarantees than writeback, so it reads as "more journaling".

The refutation: the journal is identical. The only difference is one ordering rule plus a flush: the data must reach its home block before the commit record does. The write-point count is the same, 24 in this workload for both.

Correct rule: ordered is the same redo journal with a barrier in front of the commit; the extra guarantee comes from ordering, not from logging more.

6. "Metadata-only journaling is a partial journal, so it is unsound"

Why it tempts: "partial" sounds like "incomplete", and the writeback failure mode makes it look broken.

The refutation: metadata-only ordered keeps all four invariants at all 25 crash points of this workload. It is sound for the promise it makes — a structurally valid file system — and silent about the promise it does not make.

Correct rule: ask which promise the question is about before judging the mode. Ordered keeps two of them, writeback one, full data journaling both.

Three kinds of question, three mechanical procedures

Every journaling question on this topic is a count, an order, or a state. Decide which before computing anything: a count is answered by a formula, an order by the commit record, and a state by writing the sequence out and replaying to the last commit. Mixing the three is where marks are lost.

Shape 1 — count the block writes

Asked as: "the file system writes X blocks of metadata per operation; with a journal, how many block writes does one operation cost?"

Procedure: count the distinct blocks the transaction touches, call it $$m$$. Journaled cost is $$2m+3$$; unjournaled is $$m$$. If the data is journaled too, use $$2(m+d)+3$$.

Common wrong approach: counting one descriptor block per logged block instead of one per transaction. The descriptor is a list, so it is written once.

Shape 2 — count what recovery reads

Asked as: "how many disk blocks must be read during recovery?"

Procedure: the journal, from its tail to its head — at most the journal's size, not the disk's. Here 64 against 262,144, a ratio of 4,096.

Common wrong approach: answering with the number of blocks the transaction wrote. Recovery reads the log entries that exist, which includes transactions that were checkpointed but not yet freed.

Shape 3 — which ordering is safe

Asked as: "which of the following write orders can leave a file whose data was not written?"

Procedure: ask where the data block sits relative to the commit record. Data before commit — safe. Data after commit — unsafe, in every order. Then, if the question is about in-place order only, ask whether the inode precedes the data: 3 of 6 orders here do.

Common wrong approach: judging the order of the metadata blocks. Once the commit is durable, the in-place metadata order stops mattering, because replay overwrites it.

Shape 4 — what the commit record makes atomic

Asked as: a statement-selection question about what the commit record guarantees.

Procedure: it makes exactly one transaction all-or-nothing, and it says nothing about the values inside it. Anything stronger — "the data is on disk", "the file is uncorrupted", "the disk is checked" — is false.

Common wrong approach: accepting "the commit record guarantees the data reached the disk". That is the durability promise of a flush, not of a journal.

Shape 5 — the state after a given crash

Asked as: "the system crashes after write W of this sequence; what does the disk contain after recovery?"

Procedure: three steps, in order. Write the sequence out and stop at W. Find the last commit record present. Copy every logged image up to it, and discard the rest. Then read the resulting structures.

Common wrong approach: reasoning from intuition about which write "probably" landed. Run the order; the answer is mechanical, and intuition gets the boundary case wrong almost every time.

Where a question usually hides the difficulty

Three places, in order of frequency:

  • The +3. A transaction of one block costs 5 writes, not 2 and not 3.
  • Data or metadata. A question that says "the file system is journaled" without naming the mode cannot be answered about bytes. If the options differ only on data integrity, the intended mode is writeback or ordered, and the wording usually says which.
  • The uncommitted tail. Entries in the log after the last commit record are present on disk and irrelevant. Counting them as replayed work is the standard error.

None of these is a trick. Each is a definition applied literally, which is the whole of what this topic asks.

Q1 MCQ Original

A file-system operation modifies 4 metadata blocks. The file system uses a redo journal that stores the complete new image of each block. Ignoring any data blocks, how many block writes does the journaled operation cost in total?

(A) 4   (B) 8   (C) 11   (D) 13

Answer: (C) 11. One descriptor + 4 images + 1 commit record = 6 log writes; then 4 in-place writes; then 1 head update. $$2m+3 = 2(4)+3 = 11$$.

Why the others fail: (A) 4 is the unjournaled cost. (B) 8 counts the images twice and forgets the three overhead writes. (D) 13 comes from counting one descriptor per image — 4 + 4 + 4 + 1.

Trap: the descriptor is one block that lists the others. It is not written once per logged image.

Q2 NAT Original

A 128-block journal is used by a file system whose transactions each modify 6 metadata blocks and no data blocks. Each transaction occupies one descriptor block, one image block per modified metadata block, and one commit record. What is the largest number of transactions the journal can hold before the head reaches the tail?

Answer: 16. One transaction occupies $$1 + 6 + 1 = 8$$ blocks. $$\lfloor 128/8 \rfloor = 16$$.

Why not 21 or 18: 21 comes from dividing 128 by 6 and ignoring the two overhead blocks; 18 from forgetting the commit record only. Both undercount the per-transaction footprint.

Trap: the descriptor and the commit record are per transaction, so they are inside the 8, not once per journal.

Q3 MSQ Original

A journaled file system crashes during a transaction. Which of the following are TRUE?

I. Entries written to the journal after the last commit record are ignored during recovery.
II. If the crash happened before the commit record was durable, the transaction's in-place writes must be undone.
III. Replaying the journal a second time leaves the disk in the same state as replaying it once.
IV. Recovery reads the whole disk to find the last commit record.

(A) I and III only   (B) I, II and III only   (C) II and IV only   (D) I, III and IV only

Answer: (A). I is the discard rule. III is idempotence: replay copies images, so a second pass writes the same bytes — the model compares the two recovered images and finds them equal.

Why the others fail: II is false because the write-ahead rule guarantees no in-place write happened before the commit, so there is nothing to undo — a redo journal has no undo pass at all. IV is false because recovery scans the journal, whose head and tail are recorded in header blocks; here that is 64 blocks against 262,144.

Trap: II is the statement people accept, because they import the undo list from database recovery. The file-system journal is redo-only precisely so that no undo is needed.

Q4 MCQ Original

An operation appends one data block to a file, so it writes a bitmap block, an inode block and the data block. The journal is in data=writeback mode. Which statement is correct?

(A) No crash point can leave the file system inconsistent, because the metadata is journaled.
(B) A crash after the commit record but before the data block reaches its home location leaves the file with its new size and foreign bytes in the new block.
(C) The file system can end up with two files claiming the same block.
(D) The file system can end up with a block marked free that an inode still names.

Answer: (B). Writeback lets the data land after the commit. Replay restores the inode immediately, so from that write point until the data block arrives the file reads whatever the block held before — here, a deleted file's bytes.

Why the others fail: (A) is exactly the belief this mode refutes: metadata is perfect and the bytes are not, at 7 of 25 crash points in the model. (C) and (D) are metadata failures, and writeback has none of them: 0 of 25.

Trap: the failure is silent. A test that mounts the file system and lists files passes; a test that reads them fails.

Q5 NAT Original

A journal holds at most 4096 blocks. Each transaction modifies 30 metadata blocks and 10 data blocks, and the journal is in full data journaling mode, so one descriptor block and one commit record are written per transaction. What is the largest number of complete transactions that can be present in the journal at once?

Answer: 97. In full data journaling the transaction logs its data blocks too, so one transaction occupies $$1 + 30 + 10 + 1 = 42$$ blocks. $$\lfloor 4096/42 \rfloor = 97$$, since $$42 \times 97 = 4074$$ and the remaining 22 blocks cannot hold another transaction.

Why not 102 or 132: 102 comes from using 40 blocks per transaction, which is metadata only — that is data=ordered, not full data journaling. 132 comes from ignoring the two overhead blocks entirely ($$4096/31$$).

Trap: the mode decides what is counted. Read the mode before dividing, and remember the descriptor and commit record are per transaction.

Q6 MCQ Original

A redo journal commits a transaction that writes a block number into an inode, but the block number is wrong: it names a block the bitmap marks free. The system crashes, and recovery replays the journal. What is the state of the file system after recovery?

(A) The transaction is discarded, because the value is invalid.
(B) The transaction is replayed exactly as written, and the inode now names a free block.
(C) Recovery detects the inconsistency and repairs the inode.
(D) The file system falls back to the full consistency check and removes the file.

Answer: (B). Replay copies block images. It has no notion of a value being wrong, only of a transaction being committed. The model journals exactly such an inode and the recovered image contains it, with a dangling reference to a free block.

Why the others fail: (A) confuses "invalid" with "uncommitted". (C) and (D) attribute a repair to recovery that only a consistency check performs — and even then, only if the check is run.

Trap: atomicity and correctness are independent. A journal makes a transaction happen exactly once; it never makes it the right transaction.

Revision sheet — one screen

Definitions, the formulas, the decision procedure, and the numbers this lesson computed. If you can reproduce the four-step procedure and the two formulas from memory, the rest is arithmetic.

Definitions

  • Transaction — a set of block writes that must all take effect or none.
  • Write-ahead rule — a block's new image must be durable in the journal before its home block is overwritten.
  • Descriptor block — lists the home block of each image that follows it.
  • Commit record — one block, written after all the images; the transaction is committed exactly when it is durable.
  • Checkpoint — copying logged images to their home blocks.
  • Recovery — redo every committed image, discard everything after the last commit record.
  • Revoke record — marks a block that must not be replayed from an earlier transaction.

Verified fact The journal stores whole block images, not deltas: however small the change, one whole block is logged.

Formulas

journaled cost, metadata only: $$2m+3$$

for $$m$$ metadata blocks: 1 descriptor, $$m$$ images, 1 commit, $$m$$ in-place writes, 1 head update.

journaled cost, data too: $$2(m+d)+3$$

for $$m$$ metadata and $$d$$ data blocks.

transactions held: $$\left\lfloor \frac{J}{m+2} \right\rfloor$$

for a journal of $$J$$ blocks and $$m$$ metadata blocks per transaction.

largest transaction: $$J-2$$

metadata blocks, because the descriptor and the commit record need one block each.

The four-step procedure for any crash question

1. Write out the sequence of block writes for the mode named, and stop at the crash point.
2. Find the last commit record that is present on disk.
3. Copy every logged image up to and including it; discard the rest. Nothing is undone.
4. Read the resulting bitmap, inodes and data blocks, and check the four invariants.

This procedure answers every state question, and it never requires a judgement call.

Three transactions: T1 = 2 metadata + 2 data, T2 = 2 metadata + 0 data, T3 = 2 metadata + 1 data. Eight data blocks, one bitmap, one inode table.

none — 9 writes, 10 crash points, 3 metadata failures, 3 byte failures, 4 clean, workload intact at 1
writeback — 24 writes, 25 crash points, 0 metadata, 7 byte, 18 clean, durable at 5, intact at 2
ordered — 24 writes, 25 crash points, 0 metadata, 0 byte, 25 clean, intact at 4
journal — 27 writes, 28 crash points, 0 metadata, 0 byte, 28 clean, intact at 5

88 recovered images checked in total. 3 of 6 in-place orders expose foreign bytes. A 64-block journal holds 16 transactions and at most 62 metadata blocks. Replay reads 64 blocks instead of 262,144: 4,096 times less.

Traps in one line each

A journal is not a log-structured file system — blocks keep their home addresses. A commit record is not durability for the bytes — under writeback, 5 durable crash points are only 2 intact ones. Replay is idempotent — twice equals once. Journaling does not remove the consistency check — it moves it off the boot path. Ordered mode is not a stronger journal — it is the same journal with a barrier. Metadata-only is not unsound — it makes a narrower promise. A leaked block is not corruption; a dangling reference is. And the +3 in $$2m+3$$ is per transaction, never per block.

What the research covered, and where it stopped

Four kinds of source were consulted: the official syllabus for the exam year, the kernel documentation for the journal implementation, the original ext3 design paper, and one textbook treatment for the general vocabulary. Every load-bearing claim below is labelled. Nothing here is quoted from a coaching site, and no previous-year question is claimed because none was verified against an official paper for this topic.

Official

GATE 2027 CS syllabus, IIT Madras, gate2027.iitm.ac.in, CS_GATE2027_Syllabus.pdf — fetched and read in full. Section 8 reads "System calls, processes, threads, inter-process communication, concurrency and synchronization. Deadlock. CPU and I/O scheduling. Memory management and virtual memory. File systems." Section 9 names "Transactions and concurrency control". It supports the class B registration and nothing more: journaling is not named.
The Linux kernel documentation, ext4 journal (jbd2), docs.kernel.org/filesystems/ext4/journal.html — supports the three-phase commit, the commit record, the 10,240,000-block journal ceiling, and the statement that ext4 by default journals only metadata so data blocks are not guaranteed consistent after a crash.
The Linux kernel documentation, ext4 mount options, kernel.org/doc/Documentation/filesystems/ext4/ext4.rst and ext4(5) — supports the definitions of data=journal, data=ordered (marked default), data=writeback, the 5-second default commit interval, and the statement that writeback "can allow old data to appear in files after a crash and journal recovery".
The Linux kernel documentation, the journalling API, docs.kernel.org/filesystems/journalling.html — supports the three-pass recovery: find the end of the log, assemble revoke blocks, replay un-revoked blocks.

Papers and textbooks

S. Tweedie, "Journaling the Linux ext2fs Filesystem" (1998) — the original ext3 design. Supports the three journal block types (metadata, descriptor, header), the head and tail of the log, the sequence number in header blocks, the rule that a transaction's log space is reusable only after its blocks are written home, and the statement that the journal records whole block contents rather than deltas.
M. Rosenblum and J. Ousterhout, "The Design and Implementation of a Log-Structured File System", ACM TOCS 10(1), 1992 — supports the distinction between a journaling file system, which keeps fixed block positions, and a log-structured file system, which makes the whole disk the log.
C. Mohan et al., "ARIES: A Transaction Recovery Method", and the write-ahead logging treatment in standard operating-systems texts — support the general vocabulary of redo, undo, the commit point and the checkpoint. The file-system journal is the redo-only special case.
Unverified claim The claim that a two-fold metadata write amplification is usually invisible in throughput is an engineering judgement from the sequential-write argument, not a measurement made here. No benchmark was run.

What is derived here and what is measured here

The specific numbers — 9 writes, 10 crash points, 6 failures, 88 recovered images, 7 writeback byte failures, 3 of 6 unsafe orders, 4,096-fold replay saving, 16 transactions in a 64-block journal — are all produced by the model in lesson.js and re-verified by 50 checks at page load. They describe this three-transaction workload on this eight-block disk. They are not measurements of any real file system, and no real crash was induced.

Mathematical derivation The formulas $$2m+3$$, $$\lfloor J/(m+2)\rfloor$$ and $$J-2$$ follow from counting the four phases of a transaction; they are derived on the page and checked against the model's own write-point list.

Community observation

Community observation In discussion of this topic the two points that are most often reported as confusing are (i) whether a commit record means the data is safe, and (ii) whether the file-system journal needs an undo pass like a database log. Both are treated as full misconceptions above with a measurement, not as a matter of opinion. This is a report of what learners say they find hard, not an independent measurement of difficulty.

Where the research stopped

No previous-year GATE question on journaling was verified against an official paper, so none is quoted and none is labelled a PYQ; all six practice questions are marked original. The jbd2 on-disk structures were read at the level of the documentation, not the source, so block-level field layouts are not claimed. NTFS, XFS and ZFS journals were not studied, so no comparison across file systems is made beyond the one mode table the ext4 documentation states.
