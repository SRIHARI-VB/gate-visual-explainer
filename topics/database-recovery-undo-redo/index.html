Topic and objective

TOPIC: Log-based database recovery — the log record and its two values, write-ahead logging, the undo list and the redo list, the order each one runs in, the checkpoint and its active-transaction list, and what a crash during recovery does. This is the mechanism that makes atomicity and durability true, inside the "Transactions" clause of Section 9 of the GATE 2027 CS syllabus.

LEARNING OBJECTIVE: Given any log of start, write, commit, abort and checkpoint records, produce the undo list and the redo list, replay them in the correct direction, and state the recovered value of every item. Check the answer against the committed-only state. Recognise the two transactions most often mis-assigned — one that started before the checkpoint and one that committed before it — and know what a fuzzy checkpoint changes.

I read this topic as one walk over the log, run in two directions. The log records the old value and the new value of every change; redo walks it forwards applying new values, undo walks it backwards applying old values. Everything else — the lists, the checkpoint, the active list — is bookkeeping that decides which records that walk touches.

GATE relevance

Verified fact Class A — inside the syllabus, with a caveat worth stating. Section 9 of the official GATE 2027 CS syllabus (IIT Madras, CS_GATE2027_Syllabus.pdf) ends: "File organization, indexing (e.g., B and B+ trees). Transactions and concurrency control."

The words "recovery" and "log" do not appear in that sentence. What appears is "Transactions", and atomicity and durability — two of the four properties the word transaction denotes — are impossible without this mechanism. The topic is therefore inside the clause, but it is not named separately, and this lesson does not pretend otherwise.

Verified fact Two direct questions exist, both recomputed on this page: GATE CSE 2015, Set 2 asked for the undo and redo lists of a checkpointed log (official key: undo T3 and T1, redo T2), and GATE CSE 2021, Set 1 asked what happens when a system crashes again during recovery (official key: the same undo and redo list is used).

Class A means a question here is inside the declared boundary, not that one is guaranteed. No marks distribution is claimed for 2027.

The five ideas this lesson turns on

  1. A write record keeps both values. Old value for undo, new value for redo. One value would not support both directions.
  2. The log reaches disk before the page. Write-ahead logging is what makes the record usable after a crash at any instant.
  3. A start joins the undo list; a commit moves its transaction to the redo list. The two lists are disjoint by construction.
  4. Redo walks LSN up, undo walks LSN down. Reverse either and the database holds a value nothing wrote.
  5. A checkpoint's active list is not optional. It is the only record of a transaction that started before the checkpoint and never committed.

Build-up, page 1 of 2 — from a crash to the two lists

Levels 1 to 4: the intuition, the formal definitions, the structure of a log, and the first complete decision. Nothing here needs the animation running.

Intuition: the shopkeeper's day book

A shopkeeper writes every sale in a day book before touching the cash box. If the shop is robbed mid-transaction, the day book still says what was meant to happen, so the books can be put right the next morning.

The day book is the log. The cash box is the data page. "Write it down before you do it" is write-ahead logging, and it is the whole trick.

Educational interpretation The analogy carries the ordering, not the arithmetic. What makes recovery possible is not that a record exists, but that it exists before the change it describes.

Formal definitions

A log is an append-only sequence of records on stable storage. Each record carries an LSN, a log sequence number: a strictly increasing integer that is its address in the log.

A write record for transaction T on item X holds four fields: the transaction, the item, the old value and the new value. Written as <T, X, old, new>.

The undo list holds transactions that have no commit record. The redo list holds transactions that do.

Recovery is correct when the state it produces equals the state obtained by applying exactly the writes of committed transactions, in LSN order, to the initial state. That state is the committed-only state and this page computes it separately for every scenario.

Symbols, in words

  • <start T> — transaction T has begun.
  • <T, X, old, new> — T changed item X from old to new.
  • <commit T> — T finished successfully; its work must survive.
  • <abort T> — T was rolled back; its work must not survive.
  • <checkpoint L> — all dirty pages were forced, and L lists the transactions still running.
  • LSN — the record's position; replay order is LSN order.
  • x, y, z — the data items in this lesson, holding integers.

Write-ahead logging, stated exactly

Before a data page carrying a change is written to the data file, the log record describing that change must already be on stable storage.

log record reaches disk  →  then the page it describesThe consequence used throughout: at the instant of any crash, every value that reached the disk has a record on the disk that explains it.

The page also tests this: for every item whose value on disk at the crash differs from its initial value, the log contains a write record producing that value. That check passes on all six scenarios.

Build-up, page 2 of 2 — the two algorithms and the checkpoint

Levels 4 to 6: the list builder, the replay engine, the buffer policies, and the checkpoint rule with its one assumption.

Algorithm 1 — build the two lists

  1. Find the last <checkpoint L>. If there is none, the read starts at the first record and the undo list starts empty.
  2. If there is one, copy L into the undo list. This is the only way to see a transaction that started before the checkpoint.
  3. Read every record from there to the crash:
    • <start T> — add T to the undo list.
    • <commit T> — remove T from the undo list, add T to the redo list.
    • <abort T> — remove T from both lists.
    • <T, X, old, new> — no effect on either list.

The lists end disjoint: every transaction either has a commit record in the window or it does not.

Algorithm 2 — replay

  1. Redo every write record of every redo-list transaction, in increasing LSN, applying the new value.
  2. Undo every write record of every undo-list transaction, in decreasing LSN, applying the old value.
  3. Compare the result with the committed-only state.
redo: new values, LSN up  ·  undo: old values, LSN downBoth directions are one walk along the LSN axis. Reversing either produces a value that some transaction held mid-flight, which no committed state contains.

Both directions are idempotent: applying the same record twice leaves the value it sets. That is why a crash during recovery is survivable.

The four buffer policies, and the two names to know

PolicyMeaningNeeds
no-forcepages need not be flushed at commitredo
forcepages are flushed at commitno redo

no-stealit may notno undo

Deferred modification = no-steal, no-force: redo only. Immediate modification = steal, no-force: undo and redo. These are the two names GATE uses.

Deferred does not mean the log is unused. The undo list is still built; the page checks that both of its undo steps change nothing.

The checkpoint rule, and the assumption it makes

A simple (also called sharp) checkpoint forces every dirty page and writes <checkpoint L> with the active list. Two consequences follow, and they pull in opposite directions:

A transaction that committed before the checkpoint needs no redo, because its pages were forced. A transaction that started before the checkpoint and never committed still needs undo, and only the active list reveals it.

The assumption: a fuzzy checkpoint does not force the pages. Then a transaction committed before it may still be missing from disk, so the read must go back to the start of the oldest transaction active at the checkpoint and redo more. On the GATE 2015 log that grows the redo list from {T2} to {T4, T2} and the records read from 5 to 9.

Worked example 1 — a plain log, six records, no checkpoint

Initial state x = 100, y = 50, z = 10. The log below ends in a crash. Every number in the answer is recomputed by the page.

LSNRecordEffect on the lists
1<start T1>T1 joins undo
2<T1, x, 100, 60>no change
3<start T2>T2 joins undo
4<T2, z, 10, 20>no change
5<commit T2>T2 leaves undo, joins redo
6<T1, y, 50, 90>no change

Lists: undo {T1}, redo {T2}. Disk at the crash: x = 60 (T1's page was flushed early), y = 50 (T1's second write never reached a page), z = 10 (T2's page is still in memory).

The replay, step by step

  1. Redo, ascending. LSN 4 is T2's write, and T2 is in the redo list. z becomes 20. One write redone.
  2. Undo, descending. LSN 6 is T1's write to y: apply the old value 50. y is already 50, so this step changes nothing.
  3. Undo continues. LSN 2 is T1's write to x: apply the old value 100. x returns to 100.
  4. Compare. Recovered: 100, 50, 20. Committed-only: start at 100, 50, 10 and apply T2's write, giving 100, 50, 20. Equal on all three items.

Three replay steps in total: one redo, two undo. One of the three changes no value.

What the no-op teaches

The undo of y looks pointless. It is not: the recovery algorithm does not know which pages were flushed, so it restores every old value of every undo-list transaction and lets the ones already correct stay correct.

So a question that asks how many undo operations are performed wants 2 here, not 1. A question that asks which items change wants x only. Both questions are answerable, and they are different questions.

Why the redo alone is not enough

If recovery stopped after redo, the state would be x = 60, y = 50, z = 20. The item x holds a value written by a transaction that never committed, and the sum of x and y is 110 rather than 150.

The page checks this explicitly: the redo-only state differs from the committed-only state. Undo is not a belt-and-braces step; on this log it is the step that fixes the only wrong value.

Worked example 2 — the GATE CSE 2015 Set 2 log, with a checkpoint

The question, as published: (start, T4); (write, T4, y, 2, 3); (start, T1); (commit, T4); (write, T1, z, 5, 7); (checkpoint); (start, T2); (write, T2, x, 1, 9); (commit, T2); (start, T3); (write, T3, z, 7, 2); then a crash. Initial state x = 1, y = 2, z = 5.

Official key: Undo T3, T1; Redo T2. The page derives the same two lists from the log rather than copying them, and then replays them to a state it compares with the committed-only state.

Step 1 — read the checkpoint

The last checkpoint is at LSN 6. Its active list is {T1}: T1 started at LSN 3 and has no commit record anywhere. T4 committed at LSN 4, before the checkpoint, so T4 is not in the list.

The page also computes the active set from the log independently — every transaction that started and has neither committed nor aborted by that LSN — and gets {T1}, which agrees with the record. That is the check that catches a mis-transcribed question.

Step 2 — read forward to the crash

From LSN 7 to LSN 11 there are five records: start T2, write T2, commit T2, start T3, write T3.

T2 joins the undo list at its start and leaves it at its commit, joining the redo list. T3 joins the undo list and stays. The undo list, seeded with {T1}, ends as {T1, T3}.

Lists: undo {T1, T3}, redo {T2}. Five records read instead of eleven.

Step 3 — replay and compare

Disk at the crash: x = 1 (T2's page still in memory), y = 3 (forced at the checkpoint), z = 2 (T3's page was flushed).

  1. Redo T2 at LSN 8: x becomes 9.
  2. Undo T3 at LSN 11: z becomes 7.
  3. Undo T1 at LSN 5: z becomes 5.

Recovered: x = 9, y = 3, z = 5. Committed-only: start at 1, 2, 5, apply T4's write (y = 3) and T2's write (x = 9) — the same three values. y is touched by nobody in the replay, because T4 is in neither list.

Step 4 — the two traps in this one question

Dropping T1. A reader that starts at the checkpoint never sees LSN 3. The page computes what that costs: z would end at 7, the value of a transaction that never committed, instead of 5. Nothing in the log after LSN 6 mentions T1 at all.

Adding T4. "T4 committed, so redo it" is the other reflex. T4's page was forced at the checkpoint, so redoing it is unnecessary. Without a checkpoint in the log the redo list becomes {T4, T2} and two writes are redone instead of one — which is the same log read under a different protocol.

Worked example 3 — the order witness, on one item

Initial x = 0. Log: <start T1>, <T1, x, 0, 5>, <T1, x, 5, 9>, crash. T1 never commits, so T1 is in the undo list and both of its writes are undone. The disk holds 9.

Forward order applies old values 0 then 5, leaving 5 — an intermediate value of a transaction that never committed. Reverse order applies 5 then 0, leaving 0, which is the initial value.

The page computes both and asserts that only the reverse order equals the committed-only state. The same argument in the other direction: a committed transaction writing one item twice must be redone in increasing LSN, or it ends at the earlier new value.

The boundary cases, each one computed rather than described

Six logs are modelled on this page: A (plain), B (one item written twice), C (the 2015 checkpoint log), D (deferred modification), E (a committed transaction writing one item twice), F (a transaction that wrote nothing). Every claim below is one of the checks reported on the Animation tab.

No checkpoint at all

With no checkpoint record, the read starts at the first record, so every committed transaction is in the redo list whether or not its pages reached disk. Redo is then partly wasted work, never wrong work.

On the 2015 log: 11 records read, redo {T4, T2}, two writes redone, and the same recovered state as the checkpointed read. The checkpoint buys time, not correctness.

Deferred modification

If no uncommitted page is ever written, then at the crash the disk holds the initial values plus whatever committed work was flushed. Every undo step is therefore a no-op.

Computed on the A log: the undo list is still {T1} with two write records, and both undo steps change nothing (y stays 50, x stays 100). So the algorithm reduces to redo — which is what "deferred needs only redo" means, stated precisely.

An abort record in the log

A transaction with <abort T> was rolled back before the crash, so its changes are already gone. The list builder removes it from both lists.

Some texts instead leave it in the undo list. Both give the same database state, because undo is idempotent and the old values are already in place. When a question's options differ on this, read which convention the question states; when it states none, "aborted means already rolled back" is the safe reading.

A transaction that wrote nothing

Scenario F: T1 starts and commits with no write records; T2 starts and never commits. Lists: redo {T1}, undo {T2}.

Replay touches nothing: T1 contributes zero write records and T2 wrote nothing either. The state stays x = 7. A transaction can be in a list and still do no work — the lists are about transactions, the replay is about records.

A fuzzy checkpoint

A fuzzy checkpoint does not force the dirty pages, so a transaction committed before it may still be missing from disk. The read must then go back to the start of the oldest transaction that was active at the checkpoint.

On the 2015 log that moves the floor from LSN 7 to LSN 3, the records read from 5 to 9, and the redo list from {T2} to {T4, T2}. The recovered state is unchanged, because redoing a change that is already on disk is idempotent. Say which protocol you assumed if the question does not.

A checkpoint with an empty active list

If every transaction had committed before the checkpoint, the active list is empty, the undo list starts empty, and the read begins at the record after the checkpoint.

This is the cheapest possible recovery: no transaction from before the checkpoint is in either list, and only post-checkpoint transactions are examined. It is also the case that most illustrates why the active list is stored rather than inferred.

The counterexample that catches a wrong answer

Take the 2015 log and drop T1 from the undo list — the mistake a reader makes who starts at the checkpoint. The replay then ends with z = 7.

Seven is a value that does appear in the log, as T1's new value, so nothing looks obviously wrong. Only the comparison with the committed-only state exposes it: z should be 5. This is why the lesson checks the recovered state against that reference instead of trusting the lists.

Where recovery alone stops: cascading rollback

If T2 had read x while T1 held it uncommitted, and then committed, undoing T1 would change a value T2 had already used. Recovery would then have to roll T2 back as well, even though T2 committed.

No log of the kind in this lesson can repair that, which is why recoverability and strictness are properties of the protocol, not of the recovery algorithm. Strict two-phase locking prevents the situation; the transactions lesson covers the ladder. Undo/redo lists assume no such dirty read occurred.

"A committed transaction is always in the redo list"

Why it tempts: the list builder says a commit record moves a transaction to the redo list, and that is exactly what it does.

Why it is wrong: the rule applies to commits inside the read window. With a sharp checkpoint, the window starts after the checkpoint, and a transaction that committed before it never appears.

Minimal counterexample: the GATE 2015 log. T4 commits at LSN 4, the checkpoint is at LSN 6, and the official key puts T4 in neither list.

Correct rule: redo needs the page to be possibly missing. A checkpoint that forced the page removes the need.

"A transaction that started before the checkpoint is already safe"

Why it tempts: the checkpoint declares that everything before it is consistent on disk, and the reader is told to stop there.

Why it is wrong: the checkpoint makes the pages consistent, not the transactions. A transaction still running at that instant has pages on disk that must be rolled back.

Minimal counterexample: T1 in the 2015 log. Dropping it leaves z = 7 instead of 5 — the page computes both.

Correct rule: seed the undo list from the checkpoint's active list before reading a single record after it.

"Undo applies old values in the order the writes happened"

Why it tempts: the log is read forwards, and the records are naturally in that order.

Why it is wrong: a transaction that wrote the same item twice leaves an intermediate value behind if the old values are applied in log order.

Minimal counterexample: x: 0 → 5 → 9, uncommitted. Forward undo gives 5; reverse undo gives 0. Only 0 is the value before the transaction.

Correct rule: undo in decreasing LSN. The last old value applied must be the oldest.

"A crash during recovery makes the database inconsistent"

Why it tempts: recovery is half-finished, so the database is obviously in some intermediate state.

Why it is wrong: the log has not changed and neither redo nor undo accumulates. Restarting rebuilds the same lists and replays the same records.

Minimal counterexample: recover the A log, then recover it again from the recovered state. The page computes both and they are identical.

Correct rule: recovery is idempotent, so it is restarted, not resumed. GATE CSE 2021 Set 1 keys exactly this.

"Undo and redo are inverses, so their order does not matter"

Why it tempts: both act on the same records, and one is described as the reverse of the other.

Why it is wrong: they act on disjoint sets of transactions, so there is no record that both would touch. Within a direction, the order is forced; across directions, the phases are separate.

Minimal counterexample: the A log — undo touches x and y, redo touches z. No item appears in both phases.

Correct rule: redo all, then undo all. The lists are disjoint, so the phases cannot interfere.

"A no-op undo is a bug"

Why it tempts: the algorithm applies an old value that the item already holds, which looks like wasted work or a wrong list.

Why it is wrong: recovery cannot know which pages were flushed. It restores every old value of every undo-list transaction, and the correct ones stay correct.

Minimal counterexample: the A log — undoing T1's write to y sets 50 to 50. Exactly one of the two undo steps is a no-op.

Correct rule: count records when a question asks how many operations run; count changes only when it asks which items change.

The one-line summary

Read the checkpoint's active list first, seed the undo list with it, move transactions only on commit, redo oldest first, undo newest first — and then check the result against the state the committed transactions alone define.

GATE CSE 2015, Set 2 — the checkpoint log

Consider a simple checkpointing protocol and the following set of operations in the log. (start, T4); (write, T4, y, 2, 3); (start, T1); (commit, T4); (write, T1, z, 5, 7); (checkpoint); (start, T2); (write, T2, x, 1, 9); (commit, T2); (start, T3); (write, T3, z, 7, 2); If a crash happens now and the system tries to recover using both undo and redo operations, what are the contents of the undo list and the redo list?

Official key: Undo T3, T1; Redo T2.

What it tests: the active list (T1), and the exclusion of a transaction that committed before the checkpoint (T4). Both are traps, and the four options are built from exactly those two mistakes.

GATE CSE 2021, Set 1 — a crash during recovery

Suppose a database system crashes again while recovering from a previous crash. Assume checkpointing is not done by the database either during the transactions or during recovery. Which of the following statements is/are correct? (A) The same undo and redo list will be used while recovering again. (B) The system cannot recover any further. (C) All the transactions that are already undone and redone will not be recovered again. (D) The database will become inconsistent.

Official key: A only.

What it tests: that the log is unchanged and that both directions are idempotent. C is the interesting distractor: it sounds like a resume, but without a checkpoint the lists are rebuilt from the same records.

The five question shapes

  1. Give the two lists. Most common. Fix the window, then move transactions only on commit.
  2. Give the recovered value of an item. Requires replaying in the right direction, not just the lists.
  3. Count the records read or redone. The checkpoint's saving, as a number.
  4. Which transaction needs neither undo nor redo. The committed-before-the-checkpoint case.
  5. Reason about a failure during recovery. Idempotence, and whether the log changes.

What the question usually withholds

Three facts are often left implicit, and each changes the answer:

  • The protocol. "Simple checkpointing" means pages were forced. Without that phrase, a fuzzy checkpoint is possible and the redo list can grow.
  • The disk state at the crash. When the question does not give it, the answer is only the two lists; when it does, the recovered values depend on it.
  • Whether abort records exist. A transaction that aborted before the crash belongs to neither list under the usual convention.

If a question gives no disk state and asks for values, say which values you assumed were flushed; the list answer does not depend on it.

Ninety seconds, in an exam

  1. Underline the checkpoint and copy its active list — write it down before anything else.
  2. Walk the records after it, writing each transaction's name once, in the undo column, and moving it across at its commit.
  3. Replay: redo up the log, undo down it. Do not re-derive the lists.
  4. If values are asked, compare with the committed-only state — that is faster than checking each item by eye.

The distractor grammar

Wrong options are built from four moves: including T4 in redo (committed before the checkpoint); omitting T1 from undo (started before it); putting the same transaction in both lists; and treating a committed transaction as needing no replay at all.

On the 2015 question the four options are exactly: the key; the key plus T4 in redo; everything in redo and nothing in undo; and T4 in undo as well. Naming the moves is faster than evaluating each option.

MCQGATE CSE 2015, Set 2

Log: (start, T4); (write, T4, y, 2, 3); (start, T1); (commit, T4); (write, T1, z, 5, 7); (checkpoint); (start, T2); (write, T2, x, 1, 9); (commit, T2); (start, T3); (write, T3, z, 7, 2). A crash happens now and the system recovers using both undo and redo. The contents of the lists are

  1. Undo: T3, T1; Redo: T2
  2. Undo: T3, T1; Redo: T2, T4
  3. Undo: none; Redo: T2, T4, T3, T1
  4. Undo: T3, T1, T4; Redo: T2

Answer: A — Undo T3, T1; Redo T2

The checkpoint at LSN 6 has active list {T1}, so T1 is in the undo list before any later record is read. T2 starts and commits after it, so T2 moves to the redo list. T3 starts and never commits, so T3 stays in undo. T4 committed at LSN 4, before the checkpoint, so its page was forced and it needs no redo.

Why B is wrong. It adds T4, the committed-before-the-checkpoint trap. Why C is wrong. It treats every transaction as needing redo and none as needing undo, which would keep T1's and T3's uncommitted work. Why D is wrong. It puts T4 in the undo list, which would roll back a committed transaction.

Official GATE 2015 answer key: option A. The page recomputes both lists from the log and reaches the same pair.

MSQGATE CSE 2021, Set 1

Suppose a database system crashes again while recovering from a previous crash. Assume checkpointing is not done by the database either during the transactions or during recovery. Which of the following statements is/are correct?

  1. The same undo and redo list will be used while recovering again.
  2. The system cannot recover any further.
  3. All the transactions that are already undone and redone will not be recovered again.
  4. The database will become inconsistent.

Answer: A only

The log on stable storage is unchanged by a recovery attempt: no records are removed and no checkpoint is written. So the second attempt reads the same records and rebuilds the same two lists. Both redo and undo are idempotent, so replaying them again leaves the values they set.

Why B is wrong. Nothing is consumed by a failed attempt; the log is still there. Why C is wrong. It describes a resume, but without a checkpoint there is nothing to resume from — the lists are rebuilt from the beginning. Why D is wrong. Once recovery completes, the state equals the committed-only state; an interrupted attempt leaves a state that the next attempt repairs.

Official GATE 2021 Set 1 answer key: A. The page recovers the same log twice and checks that the state is identical.

MCQOriginal practice question

A system uses deferred modification, so a page is written to disk only after its transaction commits. At a crash, which lists does recovery need?

  1. Both an undo list and a redo list
  2. Only a redo list
  3. Only an undo list
  4. Neither list

Answer: B — only a redo list

Under deferred modification no uncommitted value ever reaches the disk, so there is nothing to undo: every undo step would be a no-op. But a committed transaction's pages may still be in memory at the crash, so its writes must be redone.

Why A is wrong. Both are needed only when an uncommitted page may be flushed — the steal case, which is immediate modification. Why C is wrong. Undo alone would lose committed work that never reached the disk. Why D is wrong. That is the force plus no-steal corner, which needs neither.

The page checks the deferred case directly: both undo steps of the A log change nothing under deferred modification.

NATOriginal practice question

Initial x = 0. The log is <start T1>, <T1, x, 0, 5>, <T1, x, 5, 9>, and then a crash. T1 never commits, and the disk holds x = 9. If undo applies the old values in increasing LSN order, the value of x after recovery is _________.

Answer: 5

Increasing LSN applies LSN 2 first, setting x to 0, then LSN 3, setting x to 5. The last write wins, so x ends at 5 — the intermediate value of a transaction that never committed.

The likely error. Answering 0 by applying the values in the correct (decreasing) order, which is the right answer to a different question. Read the direction the question states.

The page computes both orders: forward gives 5, reverse gives 0, and only the reverse equals the committed-only state.

NATOriginal practice question

For the GATE CSE 2015 Set 2 log (11 records, checkpoint at LSN 6 with active list {T1}), how many log records does a sharp-checkpoint recovery read, counting from the record after the checkpoint to the crash?

Answer: 5

Records at LSN 7, 8, 9, 10 and 11: start T2, write T2, commit T2, start T3, write T3. Everything before LSN 6 is settled by the checkpoint, and LSN 6 itself is the checkpoint record whose active list was already copied.

The likely error. 9, from reading back to LSN 3, the start of the oldest active transaction — that is the fuzzy-checkpoint rule, which reads 9 records. Another. 11, the whole log, which is the no-checkpoint answer.

The page computes 5 for the sharp protocol, 9 for the fuzzy variant, and 11 with no checkpoint at all.

MSQOriginal practice question

Which of the following are true of a simple (sharp) checkpoint?

  1. Every dirty page is forced to disk at the checkpoint.
  2. The checkpoint record names the transactions active at that instant.
  3. A transaction that committed before the checkpoint needs no redo.
  4. A transaction that started before the checkpoint and never committed needs no undo.

Answer: A, B and C

A sharp checkpoint forces the pages (A) and records the active list (B). Because the pages are forced, a transaction committed before it is certainly on disk and needs no redo (C).

Why D is wrong. The opposite is true, and it is the single most common error on this topic. T1 in the 2015 log started before the checkpoint and never committed; it must be undone, and only the active list reveals it. Dropping it leaves z at 7 instead of 5.

A fuzzy checkpoint is the one where A fails — and then C fails too, because a committed page may still be missing.

MCQOriginal practice question

A transaction T wrote item x twice and committed: <T, x, 1, 5> at LSN 2 and <T, x, 5, 9> at LSN 3. The page is not on disk at the crash. If redo applies the new values in decreasing LSN order, the value of x after recovery is

  1. 1
  2. 5
  3. 9
  4. Undefined, because redo order is irrelevant

Answer: B — 5

Decreasing LSN applies LSN 3 first (x becomes 9), then LSN 2 (x becomes 5). The last write wins, so x ends at 5, an intermediate value that the committed transaction no longer holds.

Why C appears. 9 is the correct answer to the correctly ordered question — redo must run in increasing LSN. Why A appears. 1 is the pre-transaction value, which is what undo would restore, not redo. Why D is wrong. Order matters exactly when one transaction writes one item more than once.

The page computes both orders on this log: ascending gives 9 and equals the committed-only state; descending gives 5.

MCQOriginal practice question

Why must a write record hold the old value as well as the new one?

  1. So that a committed transaction can be rolled back if the user changes their mind.
  2. So that recovery can restore the item when the transaction did not commit.
  3. So that the log can be compressed by storing only the difference.
  4. It need not; the new value alone is sufficient.

Answer: B

Undo applies the old value. Without it, a page flushed early by an uncommitted transaction could never be repaired — there would be no record of what the item held before.

Why A is wrong. A committed transaction cannot be rolled back by the recovery system; that would break durability. Why C is wrong. Compression is not why the field exists, and a difference is not what is stored. Why D is wrong. With only the new value, redo would work and undo would be impossible, which is precisely the deferred-modification restriction.

The mirror question — why the new value is needed — has the same shape: redo applies it, and without it a committed page still in memory could not be reconstructed.

MSQOriginal practice question

A log contains <start T1>, <T1, x, 4, 6>, <commit T1>, <start T2>, <T2, y, 1, 2>, and then a crash. No checkpoint exists. Which statements are correct?

  1. The undo list is {T2} and the redo list is {T1}.
  2. The two lists are disjoint.
  3. If T2's page had already been flushed, recovery restores y to 1.
  4. T1's write to x must be undone because its page may not be on disk.

Answer: A, B and C

T1 commits, so it is in the redo list; T2 never commits, so it is in the undo list. The lists are disjoint by construction. If T2's page reached the disk, undo applies the old value 1 to y.

Why D is wrong. T1 committed, so its work must survive; nothing about it is undone. The uncertainty about whether its page reached disk is the reason it is redone, not undone.

Note that C is true whether or not the page was flushed: if it was, undo changes y; if it was not, undo is a no-op and y is already 1.

Revision sheet — the whole lesson on one screen

Definitions, the two algorithms, the checkpoint rule, the two orders, and the four traps. Every number here is one the page computes.

Definitions

  • Log — append-only records on stable storage, each with an LSN.
  • Write record — <T, X, old, new>; old for undo, new for redo.
  • Write-ahead logging — the record reaches disk before the page it describes.
  • Undo list — transactions with no commit record in the read window.
  • Redo list — transactions with one.
  • Committed-only state — the initial state with exactly the committed transactions' writes applied. The correctness target.
  • Sharp checkpoint — forces every dirty page and writes <checkpoint L>.
  • Fuzzy checkpoint — does not force; the read must go back further.

Procedure

  1. Last checkpoint? Copy its active list into undo. None? Start at record 1, undo empty.
  2. Read to the crash: start → undo; commit → undo→redo; abort → neither; write → nothing.
  3. Redo write records of redo-list transactions, LSN increasing, new values.
  4. Undo write records of undo-list transactions, LSN decreasing, old values.
  5. Check: lists disjoint; state equals the committed-only state.
redo: new, LSN up  ·  undo: old, LSN downThe two directions of one walk. Reverse either and the database holds a value some transaction held mid-flight.

The four traps

  1. Committed before the checkpoint ≠ redo. Its pages were forced.
  2. Started before the checkpoint ≠ safe. Read the active list; it may be the whole answer.
  3. Undo runs backwards. One item written twice exposes it: 5 instead of 0.
  4. A no-op undo is still an operation. Count records, not changes.

And one trap outside the algorithm: recovery assumes no transaction read uncommitted data. If one did, undo would need a cascading rollback, which is a protocol property.

Three sentences to carry

The log keeps both values, so either direction is always possible. The lists decide which records each direction touches; the LSN decides the order within a direction. Correctness is the recovered state equalling the committed-only state, and that equality is checkable in seconds.

Mathematical derivation The order claims are proved by the two single-item logs on this page: forward undo gives 5 where reverse gives 0, and descending redo gives 5 where ascending gives 9. Both are computed, not asserted.

Where this connects

Transactions and concurrency control defines commit, abort, recoverability and strictness — this lesson is what those properties cost to implement. File systems supplies stable storage and the distinction between a buffered write and a completed one. Memory management supplies dirty pages and flushing, which is where "steal" and "no-force" come from. Integrity constraints is the reason undo must restore a consistent state rather than an arbitrary one: an aborted transaction that broke a foreign key must leave no trace of having done so. And the ordering argument — one walk, two directions, an order that is forced — is the same reasoning as a topological order in graphs.
