Topic and objective

TOPIC: View serialisability, and the blind write that separates it from conflict serialisability: view equivalence as three observations, the read-from relation built with two dummy transactions, the schedule whose precedence graph has a cycle and is still equivalent to a serial order, and the exact boundary between the two classes.

LEARNING OBJECTIVE: Given a schedule of read and write operations, decide whether it is conflict serialisable, whether it is view serialisable, and whether those verdicts differ. Build the read-from table by hand, compare it with each serial order, and identify every blind write in the schedule. Given a family of transactions, count how many interleavings fall in each class.

I read the request as the weaker equivalence class and its exact boundary: the prerequisite lesson draws the precedence graph and shows one view-serialisable schedule with a cycle; this page owns the table test, the enumeration that measures the gap, and the four-class ladder.

GATE relevance

Verified fact Class A — explicitly in the syllabus.

Section 9 of the GATE 2027 CS syllabus (IIT Madras, official PDF, read 2026-11-04) names: "Transactions and concurrency control." Serialisability and its two equivalence classes are the standard content of that clause in every textbook the clause follows.

Unverified claim The words view serialisability and blind write are not printed in the syllabus. No claim is made here about how often such a question appears; the page teaches the mechanism, not a frequency.

Educational interpretation The topic is examinable because every step is a comparison of two small tables plus a count of writes, both of which can be done by hand in under two minutes.

Prerequisites

  • Conflict serialisability — a schedule as a list of read and write operations, the three conflict shapes, the precedence graph and the cycle test.
  • What a blind write is, at least in one sentence: a write whose transaction never read that item.
  • Reading a two-row table and comparing it with another: no probability, no calculus, no counting beyond permutations.

Nothing on this page needs a database. Every schedule is enumerated in the browser when the page loads.

The five ideas, in one line each

  • A cycle is not a verdict — it rules out conflict serialisability only.
  • Three observations — initial reads, read-from, final writes; nothing else survives.
  • Two dummy transactions collapse the three into one read-from relation.
  • A blind write is necessary for the gap, and never sufficient.
  • Testing is NP-complete, which is why practice aims at the conflict level.

Intuition — what a customer can still tell afterwards

Two shopkeepers keep the same ledger. One serves customers strictly in a queue; the other serves them in any order that keeps each customer's own steps in sequence. A customer who comes back the next day cannot tell which shopkeeper served her: she knows what she read, who she read it from, and what the last entry says.

She cannot tell how many times an entry was overwritten in between, because those versions are gone. That is the whole of view equivalence: the same three things, whatever happened in between.

Formal definition — view equivalence

Let S and S′ be schedules of the same set of transactions, with operations read(Q) and write(Q). They are view equivalent when all three hold:

1. Initial reads. If transaction T reads the initial value of item Q in S, it reads the initial value of Q in S′ too.

2. Read-from. If T reads a value of Q that was written by transaction T′ in S, then T reads a value of Q written by T′ in S′.

3. Final writes. If T performs the last write of Q in S, then T performs the last write of Q in S′.

A schedule is view serialisable when it is view equivalent to some serial schedule of the same transactions.

One relation instead of three conditions

Add a transaction Tinit that writes every item before the schedule starts, and a transaction Tfinal that reads every item after it ends. Then a read that took the initial value is a read from Tinit, and the final write of an item is the write that Tfinal reads.

The three conditions become one: two schedules are view equivalent exactly when their read-from relations are identical. The relation is a set of triples — this reader, this item, this writer.

Verified fact The read-from characterisation with the two dummy transactions is the standard formulation (Yannakakis, Serializability by Locking, J. ACM 1984).

Blind write, and why it is the hinge

A write of item Q by transaction T is blind when T has not read Q earlier in its own program. The test is inside one transaction: it does not depend on where the operation sits in the schedule.

If every write in a schedule is preceded, inside its own transaction, by a read of the same item, then no write can be a pure constant that nobody needed to see. In that situation the precedence graph decides both classes at once.

Verified fact Silberschatz, Korth and Sudarshan (Database System Concepts, ch. 17) state both halves: every conflict-serialisable schedule is view serialisable, and every view-serialisable schedule that is not conflict serialisable has blind writes.

The witness, in one table

Take T1: read(X), write(X); T2: write(X); T3: write(X). The schedule rT1(X) wT2(X) wT1(X) wT3(X) has two edges in opposite directions in its precedence graph, so it is not conflict serialisable.

Its read-from relation, with the two dummy transactions, is two rows:

T1 reads X from Tinit — the initial value.

Tfinal reads X from T3 — the last writer.

The serial order T1, T2, T3 produces exactly the same two rows. So the schedule is view serialisable, and the graph verdict was one-sided.

The ladder, and where each gap is witnessed

  • serial ⊂ conflict serialisable. Witness: rT1(X) wT1(X) wT2(X) rT2(Y) wT3(X) wT2(Y) wT3(Y) — two transactions on different items interleaved, so no conflict pins them, yet it is not a serial order.
  • conflict ⊂ view serialisable. Witness: the four schedules of family A with a two-cycle.
  • view ⊂ final-state serialisable. Witness: the lost update rT1(X) rT2(X) wT1(X) wT2(X), whose final value matches serial T1, T2 while its reads do not.

Worked examples — every number computed on load

Six examples, in the order the reasoning needs them: the witness with real values, all twelve interleavings of its family, two larger families, a schedule with no blind write, the lost update, and the hand procedure.

Example 1 — the witness, with values

X starts at 100. T1 writes what it read plus 50. T2 writes 200. T3 writes 300. Schedule: rT1(X) wT2(X) wT1(X) wT3(X).

1. rT1(X) — T1 reads 100, the initial value.

2. wT2(X) — X becomes 200. T2 never read X, so this is a blind write.

3. wT1(X) — X becomes 150, computed from the 100 that T1 read. The 200 is now dead.

4. wT3(X) — X becomes 300. Final value 300.

Serial T1, T2, T3 gives the same final value 300, with T1 reading the initial value and T3 writing last. Two rows agree, so the schedule is view serialisable.

Example 1 continued — the graph, for contrast

The conflicts of the same schedule, in execution order:

rT1(X) before wT2(X) → edge T1 → T2.

wT2(X) before wT1(X) → edge T2 → T1.

rT1(X) before wT3(X) → edge T1 → T3.

wT2(X) before wT3(X) → edge T2 → T3.

Four edges and a two-cycle between T1 and T2, so the graph says no. The table says yes. Both verdicts are correct, and they answer different questions.

Example 2 — all twelve interleavings

Family A: T1 reads then writes X, T2 writes X, T3 writes X. Four operations give 4!/(2!1!1!) = 12 interleavings. Enumerated in the browser:

Example 3 — two larger families

Family D: T1 reads then writes X; T2 writes X, reads Y, writes Y; T3 writes X and Y. Seven operations, so 7!/(2!3!2!) = 210 interleavings.

210 interleavings enumerated.

54 are conflict serialisable — six serial orders plus 48 interleaved ones.

71 are view serialisable, so 17 sit in the gap.

Family F has eight operations and 560 interleavings: 86 conflict, 110 view, 24 in the gap. One of those 24 has only a single blind write, which is the smallest amount of blindness the gap can contain.

Example 4 — no blind write, and the graph decides

Family G: T1 reads then writes X, T2 reads then writes X, T3 reads then writes Y. Every write is preceded by a read of the same item inside its own transaction, so nothing is blind.

90 interleavings enumerated.

30 conflict serialisable.

30 view serialisable — the same thirty.

So in a schedule with no blind write you may answer a view question with the precedence graph and lose nothing. That is the practical value of the necessary condition.

Example 5 — the lost update: same final state, different view

Family C: both transactions read X then write it, and T2 writes the constant 200. The schedule rT1(X) rT2(X) wT1(X) wT2(X) is not conflict serialisable — its graph has the cycle T1 → T2 (from rT1 before wT2) and T2 → T1 (from rT2 before wT1).

Its final value is 200, which is exactly the final value of the serial order T1, T2. So the schedule is final-state serialisable.

But T2 read the initial value here, while in serial T1, T2 it would have read T1's write. The read-from rows differ, so the schedule is not view serialisable. Final state alone is the weakest of the three tests.

Example 6 — the hand procedure on the witness

1. Lay out the operations: T1 has r(X) w(X), T2 has w(X), T3 has w(X).

2. Mark blind writes along each row: T2's write and T3's write. T1's write is not blind.

3. Blind writes exist, so the graph is not enough: build the table. Rows: T1 reads X from Tinit; Tfinal reads X from T3.

4. Compare with each of the six serial orders. Only T1, T2, T3 reproduces both rows.

5. Report both verdicts: not conflict serialisable, view serialisable, equivalent to T1, T2, T3.

Two minutes, one table, no guessing.

Edge case 1 — a blind write is necessary, never sufficient

Every schedule in the gap contains a blind write, but most schedules containing a blind write are not in the gap. Family A has two blind writes in every one of its twelve interleavings, and only ten are view serialisable, of which four are outside the conflict class.

Family F makes the point sharper: 560 interleavings, one blind write in the transaction set, and 86 conflict against 110 view. A blind write opens the possibility of the gap; it does not create one.

Edge case 2 — a cycle with no blind write is fatal

Take two transactions that both read X and then write it, and run rT1(X) rT2(X) wT1(X) wT2(X). The graph has T1 → T2 and T2 → T1, and nothing is blind.

No serial order can reproduce the two reads: whichever runs second reads the first one's write. So the schedule is neither conflict nor view serialisable, and the lost update is the classic exam example of both.

Edge case 3 — a dead write may move

In the witness, the 200 that T2 wrote is never read. Moving that write to any later position where it is still unread leaves the read-from relation unchanged, so it leaves the view class unchanged.

This is the mechanism, not a special case: the weaker equivalence tolerates reordering exactly where no observation is affected. It is why the containment is strict rather than a coincidence of small examples.

Edge case 4 — one transaction, or none

A schedule of one transaction is serial, so it is in every class. An empty schedule is serial too. Neither is worth a question, but they fix the bottom of the ladder and stop you from treating the classes as disjoint.

The classes are nested, never disjoint: every serial schedule is conflict serialisable, every conflict-serialisable schedule is view serialisable, and every view-serialisable schedule has a serial order with the same final state.

Edge case 5 — two reads never conflict

The conflict definition needs at least one write. Two reads of the same item by different transactions produce no edge, however many of them there are, and no amount of interleaving changes that.

This is also why read-only transactions can be ignored when the graph is drawn, and why a family of pure readers collapses to one node.

Edge case 6 — serialisability says nothing about recovery

A schedule can be view serialisable and still be unrecoverable, or non-cascadeless: a transaction may read a value from a transaction that later aborts. Serialisability constrains the order of committed work; recoverability constrains what happens when a transaction fails.

A question that asks whether a schedule is recoverable is not answered by either graph or table. See the recovery lesson for that test.

1. "A cyclic precedence graph means the schedule is wrong"

Why it tempts. The prerequisite lesson teaches one test, and one test becomes the whole idea. The graph is drawn first, so its verdict feels final.

Counterexample. rT1(X) wT2(X) wT1(X) wT3(X) has a two-cycle and is view equivalent to T1, T2, T3 — four of the twelve interleavings of that family are exactly like this.

Correct rule. A cycle rules out conflict serialisability only. The view question needs the read-from table.

2. "View serialisability is what a real system should enforce"

Why it tempts. It is weaker, so it admits more schedules, so it looks like the better criterion on paper.

Counterexample. Deciding view serialisability is NP-complete, while the conflict test is a cycle check. And a correct locking protocol produces only conflict-serialisable schedules: the schedules it loses are exactly the ones outside that class.

Correct rule. The weaker class is a definition for reasoning about correctness, not a protocol anyone implements.

3. "A blind write is a bug"

Why it tempts. The word sounds like an error, and blind writes do often overwrite a value nobody wanted.

Counterexample. UPDATE account SET balance = 0 WHERE id = 7 is a legitimate blind write: the transaction sets a constant and never needed the old value.

Correct rule. A blind write is a structural feature — the only place the two equivalence classes can part company. It is neither right nor wrong.

4. "Same final value means view equivalent"

Why it tempts. The final state is what a person checks, and it is easy to compute.

Counterexample. The lost update rT1(X) rT2(X) wT1(X) wT2(X) ends at 200, exactly as serial T1, T2 does, but T2 read the initial value instead of T1's write. Final-state serialisable, not view serialisable.

Correct rule. Three observations, not one. The final state is the weakest of the three tests.

5. "The last writer is the transaction that ran last"

Why it tempts. In a serial order that is true, so it gets carried into concurrent schedules.

Counterexample. In rT1(X) wT2(X) wT3(X) wT1(X) T1 writes last but the final value is 150, computed from the initial 100 — a value no serial order produces. The schedule is in neither class.

Correct rule. The final write is the last write in execution order; what it wrote depends on what its own transaction read, which may be much older.

6. "Two transactions are enough to show the gap"

Why it tempts. Two transactions make every table short, and the classic witness looks like it only needs two writers.

Counterexample. On the 29 schedules of the three two-transaction families this page enumerates, the two classes never separate: 2 of 3, 2 of 6, 8 of 20.

Correct rule. Build a gap example with three transactions, one reader-writer and two blind writers. The page does not claim more than its enumeration shows.

Pattern 1 — classify two schedules

Two schedules of the same transactions, one statement per option: "S1 is conflict serialisable", "S2 is view serialisable", and so on. The reasoning demanded is two independent verdicts, and the common wrong approach is to answer the second with the first test's result.

Procedure. Draw one graph, build one table, then read each option against the verdict it names.

Pattern 2 — which schedule is view but not conflict serialisable

Four schedules offered, exactly one in the gap. Every distractor is either conflict serialisable or in neither class, so both a false positive and a false negative are available.

Procedure. First eliminate every option with no blind write: it cannot be in the gap. Then for the rest, compare tables.

Pattern 3 — count the serialisable interleavings

"How many of the interleavings of these transactions are view serialisable?" A counting question over a small family, where the answer is found by enumeration, not by a formula.

Procedure. Fix one transaction's operations in order, place the others in every legal way, and test each placement. On family A the answer is 10 of 12; on the conflict version of the same question it is 6.

Pattern 4 — identify the blind writes

A schedule is given and one option lists the writes that are blind. The trap is reading blindness off the schedule instead of off the transaction's own program.

Procedure. Follow one row at a time and ask: has this transaction already read this item? The order of the schedule is irrelevant to this question.

Pattern 5 — the statement question

"Which of the following is true?" with options mixing containment (every conflict-serialisable schedule is view serialisable), necessity (a gap schedule has a blind write), and complexity (the test is NP-complete).

Procedure. Check each option against one of the three verified statements, and reject any option that reverses an inclusion or upgrades "necessary" to "sufficient".

Pattern 6 — the final-value trap

A schedule and its final value are given, and the options ask what can be concluded. "The schedule is view serialisable because the final value matches the serial order" is the offered reasoning, and it is invalid.

Procedure. Compute the read-from rows before trusting any value. The lost update ends on the right number and is still in neither class.

MCQOriginal practice

Transactions: T1 = r(X), w(X); T2 = w(X); T3 = w(X). Which of these schedules is view serialisable but not conflict serialisable?

  1. rT1(X) wT1(X) wT2(X) wT3(X)
  2. rT1(X) wT2(X) wT1(X) wT3(X)
  3. rT1(X) wT2(X) wT3(X) wT1(X)
  4. wT2(X) wT3(X) rT1(X) wT1(X)

Answer: B

Option B has the two-cycle T1 → T2 → T1, so it is not conflict serialisable. Its read-from rows are T1 from Tinit and Tfinal from T3, which is exactly the table of serial T1, T2, T3 — so it is view serialisable.

Why A and D are wrong. Both are serial orders, so they are conflict serialisable and outside the gap. Why C is wrong. T1 writes last there, but computed from the initial value, so the final value is 150 and no serial order produces it: it is in neither class.

NATOriginal practice

For the same three transactions, how many of the twelve interleavings are view serialisable?

Answer: 10

Twelve interleavings, of which six are conflict serialisable. Four more — rT1 wT2 wT1 wT3, rT1 wT3 wT1 wT2, wT2 rT1 wT3 wT1 and wT3 rT1 wT2 wT1 — have a cycle and still match a serial order's table. Two are in neither class.

Trap. Answering 6 by counting acyclic graphs. Trap. Answering 12 by assuming every interleaving of three transactions must be serialisable; rT1 wT2 wT3 wT1 ends on a value no serial order can produce.

MSQOriginal practice

Which of the following statements are true for schedules of read and write operations?

  1. Every conflict-serialisable schedule is view serialisable.
  2. Every view-serialisable schedule is conflict serialisable.
  3. A schedule that is view serialisable but not conflict serialisable contains at least one blind write.
  4. If a schedule contains a blind write, it is view serialisable.

Answer: A and C

A is the containment proved by the definition: identical conflict orders give identical read-from rows. C is the necessity half of the textbook statement, and this page re-checks it on all 45 schedules in its gap.

Why B is wrong. Four of family A's twelve interleavings are counterexamples. Why D is wrong. That is the reversed direction: blindness is necessary, not sufficient — 86 of family F's 560 interleavings are conflict serialisable while all of them contain a blind write.

MCQOriginal practice

The schedule rT1(X) wT2(X) wT1(X) wT3(X) is given. Which serial order is it view equivalent to?

  1. T1, T2, T3
  2. T1, T3, T2
  3. T2, T3, T1
  4. T3, T2, T1

Answer: A

The table has two rows: T1 reads X from Tinit, and Tfinal reads X from T3. Only the order ending in T3 has T3 as the final writer while T1 still reads the initial value.

Why B is wrong. T2 writes last there, so the final-writer row says T2. Why C and D are wrong. In both, T1 runs after a write, so its read comes from T2 or T3 instead of the initial state.

NATOriginal practice

Three transactions, T1 = r(X), w(X); T2 = w(X), r(Y), w(Y); T3 = w(X), w(Y). Seven operations in all. How many interleavings of these three transactions exist in total?

Answer: 210

Seven positions, of which two are taken by T1's operations in their fixed order, three by T2's, two by T3's: 7!/(2!3!2!) = 5040/24 = 210. The page enumerates all 210, and finds 54 conflict serialisable and 71 view serialisable.

Trap. Answering 5040 by forgetting that each transaction's own order is fixed. Trap. Answering 6, the number of serial orders, which is a different count.

MCQOriginal practice

A schedule ends with the value 200, which is also the value produced by the serial order T1, T2. What follows?

  1. The schedule is view equivalent to T1, T2.
  2. The schedule is conflict serialisable.
  3. Nothing follows: the final value is only one of the three observations.
  4. The schedule is not serialisable at all.

Answer: C

View equivalence needs the initial reads and the read-from pairs as well. The lost update rT1(X) rT2(X) wT1(X) wT2(X) ends on 200 and is view equivalent to nothing, because T2 read the initial value where the serial order would have it read T1's write.

Why A is wrong. That is the conclusion the final value alone cannot support. Why B is wrong. The same schedule has a two-cycle. Why D is wrong. It is final-state serialisable, so "not serialisable at all" overstates the case.

MCQOriginal practice

In the schedule wT2(X) rT1(X) wT3(X) wT1(X), which writes are blind?

  1. wT2 and wT3 only
  2. wT2 and wT1 only
  3. All three writes
  4. wT3 only

Answer: A

T2 never reads X before writing it, and T3 never reads X before writing it, so both are blind. T1 reads X and then writes it, so its write is not blind, even though the read happens late in the schedule.

Why B is wrong. It reads blindness off the schedule's order rather than off T1's own program. Why C is wrong. T1's write follows its own read. Why D is wrong. T2's write comes first in the schedule, which is irrelevant to blindness.

Definitions in one line each

  • View equivalence. Same initial reads, same read-from pairs, same final writers.
  • View serialisable. View equivalent to some serial order.
  • Read-from relation. The triples (reader, item, writer), with Tinit and Tfinal added at the two ends.
  • Blind write. A write of an item the same transaction never read.
  • Final-state serialisable. Same final state as some serial order — weaker than view.

The tests, and what each one costs

  • Conflict. Build the precedence graph from conflicting pairs, test for a cycle. Linear in the number of pairs.
  • View. Build the read-from table, compare with each serial order. NP-complete in general; trivial on three transactions by hand.
  • Final state. Compare the last writer of every item, then check the value. Never sufficient for the other two.

Counts worth remembering from this page

  • Family A, twelve interleavings: 6 conflict, 10 view, 4 in the gap, 2 in neither.
  • Family D, 210 interleavings: 54 conflict, 71 view, 17 in the gap.
  • Family F, 560 interleavings: 86 conflict, 110 view, 24 in the gap.
  • Family G, no blind write, 90 interleavings: 30 conflict and 30 view.
  • Across A, D and F: 45 schedules in the gap, every one with a blind write.

Five traps

  • A cycle rules out conflict serialisability only.
  • A blind write is necessary for the gap and never sufficient.
  • The final value alone never establishes view equivalence.
  • Blindness is read along one transaction's row, not along the schedule.
  • Serialisability and recoverability are different questions with different tests.

The four-class ladder

serial ⊂ conflict serialisable ⊂ view serialisable ⊂ final-state serialisable. Each inclusion is strict, and this page exhibits a schedule in each gap: an interleaving of two transactions on different items, the two-cycle witness, and the lost update.

One sentence to carry into the exam

Draw the graph for the conflict question, build the two-row table for the view question, and never let one verdict answer the other — the schedule that separates them is a blind write followed by the same transaction writing again.
