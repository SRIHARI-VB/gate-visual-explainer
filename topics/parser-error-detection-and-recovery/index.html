Topic and objective

TOPIC: Error detection and error recovery in parsers — where a parser finds out that the input is wrong, and the three strategies that let it continue: panic mode, phrase-level recovery and error productions.

LEARNING OBJECTIVE: Say exactly where an error is detected — a blank ACTION cell — and why the GOTO table can never detect one. State the viable-prefix property and use it to explain why an LR parser stops at the first token it cannot use. Run panic mode by hand: pop to a state with a GOTO on a nonterminal, discard to a token that can follow it, push, resume. Explain why the rule as written can loop and what the progress guard does. Use FOLLOW as an LL parser's synchronising set, and tell popping from discarding. Enumerate the one-token repairs of phrase-level recovery and say why reach is not acceptance. Add an error production, measure what it costs, and run the pop-shift-delete procedure.

I read this topic as the recovery half of Section 7's word "parsing": the neighbouring lesson owns detection and the table construction, and this one owns what happens after the blank cell.

Prerequisites

  • Lexical analysis, parsing and syntax-directed translation — FIRST and FOLLOW, the LR(0) automaton, shift and reduce, the SLR table, and the LL(1) table. This lesson assumes all of it and adds nothing to it.
  • Canonical LR(1) items and the LALR merge — the lookahead that makes a reduce local. Used here only for the reduction count comparison.
  • Context-free grammars and push-down automata — derivations and sentential forms, which the viable-prefix definition is stated in.
  • Regular expressions and finite automata — a lexer's own error handling is the earlier, simpler case, and the vocabulary of "no transition" carries over.

The five ideas, in one line each

  • Detection is a missing cell. The ACTION table has no entry, and that is the whole of the error signal.
  • The stack is always a viable prefix. The error is the first token that makes it unviable.
  • Recovery changes two counts. States popped and tokens discarded — or the input itself, in phrase-level recovery.
  • Every recovery needs a guard. Without one, the rule can return to the configuration it started from.
  • Acceptance after recovery is not validity. It means the repaired string parsed.

1. Intuition — the reader who stops at a word that is not in the dictionary

Picture someone reading a sentence aloud, word by word, holding a small card that says what may come next. The card changes with every word. At some point the next word is not on the card: the reader stops. That stop is error detection, and it happens at a word, not at the end of the sentence. Educational interpretation

What the reader does next is error recovery, and there are only a few things anyone can do. Skip words until one appears that could follow where the reader has got to. Guess that a word was missing and carry on as if it had been there. Or have a rule ready for the mistake that was actually made — a rule written by whoever knows what mistakes people make.

The interesting part is that the reader's card is a table built from the grammar, so "the word is not on the card" is a statement about the table and the word, not about the sentence's meaning. That is why two different parsers can stop at the same word and disagree about nothing.

2. Formal definitions

Error detection (LR). The parser is in state s with a the next input terminal. If ACTION[s, a] is empty, an error has been detected. GOTO is indexed by state and nonterminal and is consulted only after a reduction, so it cannot detect one.

Viable prefix. A string x is a viable prefix of a grammar G when x is a prefix of some right sentential form of G. The symbol string on an LR parser's stack is always one.

Panic mode (LR). Scan down the stack for a state s with a GOTO on some nonterminal A; pop everything above s; discard input symbols until one is found that can follow A; push GOTO(s, A) and resume.

Panic mode (LL). With M[A, a] empty: if a is in FOLLOW(A), pop A; otherwise discard a. Repeat.

Phrase-level recovery. At the error point, apply a local correction to the input — insert, delete or replace one token — and continue.

Error production. A production containing the distinguished terminal error, for example F → ( error ). The parser shifts error in place of the offending token and carries on through the production.

3. Visual understanding — what the drawing has to show

An error is invisible in a picture of a tree, because the tree does not exist yet. What exists is a stack of states and a position in the input, so the animation draws those two things and nothing else: the state stack as a column, the input as a row of tokens with a pointer, and the cell being looked up. Detection is then a cell that is empty, and recovery is visible movement — the column shrinking, the pointer advancing.

The second thing the drawing must show is that recovery changes the input. In phrase-level recovery the token row itself is edited, and in the guarded panic run the accepted string is shorter than the string that was typed. That is the fact a diagram of a parse tree can never show.

4. Worked example — detection, by hand

Grammar: E → E + T | T, T → T * F | F, F → ( E ) | id. Input: id + ) id.

  1. Shift id, reduce F → id, T → F, E → T. The stack of symbols is now E, the states 0 3.
  2. Shift +. Symbols E +, states 0 3 7.
  3. State 7 holds E → E + · T and the items that expect an operand: F → · ( E ), F → · id. Look up ACTION[7, ")"].
  4. There is no column for ")" in state 7. The lookup returns nothing: error, at token 3, after 3 reductions.
  5. Canonical LR(1) also stops at token 3, also after 3 reductions — the two differ on other strings, not this one.

The page prints the state, the token, the position and the stack in the first scene, computed at load.

5. Boundaries — which strategy applies where

Panic mode works for any table-driven parser and is the cheapest. Phrase-level recovery needs a way to judge a repair, so it needs a cost or a reach measure. Error productions need the grammar to be rewritten and re-analysed, and they change the automaton. Global correction — the least-cost change to the whole input — is defined and not used, because its cost grows faster than the parse.

None of them is part of the language definition. All four are policies attached to a parser, and the language accepted by the parser without recovery is unchanged by all four.

Example 1 — the detection point, traced

Grammar E → E + T | T, T → T * F | F, F → ( E ) | id. Input id + ) id.

  1. States 0 → shift id → 0 2. Reduce F → id: states 0 4.
  2. Reduce T → F: 0 5. Reduce E → T: 0 3. Three reductions, all correct for the prefix id.
  3. Shift +: 0 3 7. The next token is ")".
  4. State 7 has entries for ( and id only. ACTION[7, ")"] is blank: error at position 3, stack 0 3 7.

The page prints state 7, token ")", position 3 and the stack, from the run rather than from this list.

Example 2 — panic mode on id id

After the first id the parser has reduced to E and sits in state 3; but this input is not yet reduced when the second id arrives, so the run is: shift id, reduce F → id, and the error comes in state 2.

  1. State 2 completes F → id. The next token is another id, and ACTION[2, id] is blank.
  2. Scan down the stack 0 2: state 2 has a GOTO on no nonterminal of interest; state 0 has GOTO on E = 3.
  3. Pop 1 state. Discard 1 token, because FOLLOW(E) = { $, ), + } and the offending id is not in it.
  4. Push GOTO(0, E) = 3. The input is exhausted and the parse accepts.

What was accepted. The string id, not id id. The second operand was deleted and never reported.

Example 3 — LL panic mode on b b c

Grammar S → A B C, A → a | ε, B → b | ε, C → c. FOLLOW(A) = { b, c }, FOLLOW(B) = { c }, FOLLOW(C) = { $ }.

  1. Stack S, token b. M[S, b] = S → A B C. Stack A B C.
  2. M[A, b] is A → ε, because b is in FOLLOW(A). Pop A. Stack B C.
  3. M[B, b] = B → b. Match the first b. Stack C, token b at position 2.
  4. M[C, b] is blank and b is not in FOLLOW(C) = { $ }. Discard the token.
  5. Token $, M[C, $] = C → c, match c… the run reports one error, one discard, and accepts.

The count of pops and discards is the whole answer to an LL recovery question, and the page prints both.

Example 4 — one error production, one new conflict

Add F → ( error ) and E → error to the expression grammar.

  1. The two productions add items wherever E and an open bracket are expected: 12 states become 15.
  2. State 7 — reached after reading ( error — now holds both F → ( error · ) and E → error ·.
  3. On ")" the table must shift to finish the phrase, or reduce E → error. Two entries, one cell: a shift/reduce conflict.
  4. Resolved in favour of shift, recovery on id + ) id gives one report, two pops and two silent deletions.

Why this is worth a card. The grammar that was conflict-free is not conflict-free any more, and nothing in the language changed. Error productions are edits to the parser, not to the language.

The error at the very first token

Input ) id. State 0 has entries for ( and id only, so the error is detected before anything is shifted: stack 0, position 1, zero reductions. Panic mode then has nothing to pop and no nonterminal below it to push, so it reports and stops.

An error with an empty stack history is the one case where panic mode has no move at all.

The error at the end marker

Input ( id. The parser consumes both tokens and then finds ACTION[6, $] blank: the close bracket is missing, and the offending token is the end marker.

Deletion-based recovery cannot help: there is nothing left to delete. The repair needed is an insertion, which is why error productions alone do not cover this case. The page checks that the error-production recovery fails on exactly this input.

Two errors in one input

Input id id id. Panic mode discards both extra ids in a single recovery: it discards until a token can follow E, and the end marker is the first such token, so both ids go at once and one message covers two mistakes.

That is the documented drawback of panic mode: a considerable amount of input is skipped without being checked for further errors.

The recovery that loops

Input id + ) id. The ")" is in FOLLOW(T) and in FOLLOW(E), so the discard step finds a synchronising token immediately and discards nothing. The pushed state reduces back to E, the same cell fails again, and the configuration repeats.

The page records the repeat and adds one forced deletion. Without that guard the procedure never terminates, which is why every implementation carries a progress rule.

Popping past a recognised nonterminal

If the scan down the stack passes a state that covers a nonterminal, the recovery deletes a phrase that had already been parsed correctly. On ( id + ) id the recovery pops two states, discarding the partial ( id + construct entirely.

The usual advice is to avoid popping such a state, and to prefer a nonterminal as high in the stack as will still let the parse continue.

The repair that reaches furthest but does not accept

On id + ) id the ten one-token repairs are tried. Deleting the ")" accepts. Replacing ")" by "(" gets one token further before failing.

So a rule that picks the furthest-reaching repair picks the wrong one here. Any usable rule combines reach with a cost, and the cheapest accepting repair is the one that is applied.

"A canonical LR(1) parser makes no reduction before announcing an error"

Why it tempts: it is repeated in lecture notes, and it sounds like the precision that separates LR(1) from SLR.

What is measured here: on 777 erroneous strings the canonical LR(1) parser performed 218 reductions before it gave up, and 80 of those strings involved at least one. On id + ) id it performs three, the same as SLR.

The safe statement: every reduction an LR parser performs is one its own table licensed; canonical LR(1) licenses fewer of them, 218 against SLR's 344, and on ( id it licenses none where SLR licenses three.

"The GOTO table can report an error"

Why it tempts: both tables are printed side by side and both can be blank.

The correct rule: GOTO has no terminal columns. It is consulted after a reduction has already been chosen, and only with a nonterminal. A blank GOTO would mean the table is malformed, not that the input is wrong.

The check: every error on this page is an ACTION entry, and the detection trace records the state and the token, never a nonterminal.

"Several reductions before the error means the parser went wrong earlier"

Why it tempts: the error is reported after the reductions, so the reductions look like the cause.

The correct rule: each reduction was a table entry for the state and the lookahead. On id + ) id the three reductions build E from id, which is exactly what the prefix needs.

What to look at instead: the state and the token at the stop, and whether any shift was ever taken on a rejected token. No LR parser takes one.

"Panic mode always terminates"

Why it tempts: the description says "discard until a synchronising token", and discarding sounds like progress.

The correct rule: when the offending token is itself in FOLLOW of the chosen nonterminal, nothing is discarded, and the pushed state can lead back to the same cell. On id + ) id the page records six identical configurations before its report cap stops the run.

The guard: if the same stack and position recur, delete the token. That single rule makes the run terminate and accept the repaired string.

"Recovery means the parser accepted my program"

Why it tempts: the run ends with "accepted", and accepted is the word for a valid parse.

The correct rule: acceptance after recovery is acceptance of the repaired input. The panic run on id + ) id accepts id +; the phrase-level run accepts id + id; the original string is rejected by the table in every case.

The habit: read the accepted string out of the trace, not the verdict alone.

"Adding error productions is free"

Why it tempts: the productions are never used on valid input, so they look like comments.

The correct rule: they are productions, so they add items, states and table entries. Two of them take this grammar from 12 states to 15 and from 0 conflicts to 1.

What follows: an error production can make an LR(1) grammar stop being LR(1), and the conflict is on the recovery path, not on any valid sentence.

Pattern 1 — "which of these is TRUE at any valid state?"

A statement about the stack, the viable prefix, or the table. The item is answered by a definition, not by a calculation, and the distractors are usually over-strong versions of the true statement.

The reasoning it demands: the stack holds one string of grammar symbols, and that string is one viable prefix — not a set of them, not only at the bottom, not only at the top.

The shortcut and its assumption: eliminate options containing "only" or "never", then check the survivor against the definition. The assumption is that the examiner wrote one over-strong distractor per item — usually true, never a substitute for the check.

Pattern 2 — "where is the error detected, and how many reductions came first?"

A grammar, a table and an input; the question asks for the state, the token, or the number of reductions before the stop.

The reasoning it demands: run the parse, and stop at the first blank cell. Reductions are steps like any other and must be counted; they are not part of the error.

The trap: counting the reductions that could have happened instead of the ones that did. The order is fixed by the table.

Pattern 3 — "which statement about panic mode is correct?"

Options over the two steps, their order, and what is pushed at the end. The wrong options usually swap the order or push the popped state.

The reasoning it demands: pop first, discard second, push GOTO(s, A) last, where s is the state the popping stopped at.

The shortcut: remember it as "find the nonterminal, then find the token". The assumption is that A is chosen by the recovery policy, not by the grammar alone.

Pattern 4 — "how many tokens are discarded?"

A numerical item: a grammar, a table, an input with one bad token, and a synchronising set. The answer is the length of the run of tokens that cannot follow the chosen nonterminal.

The reasoning it demands: compute FOLLOW of the chosen nonterminal, then count from the error point up to the first token in that set. If the bad token is already in the set, the answer is zero — and then the recovery makes no progress, which the next question usually exploits.

The edge case: the end marker is always in FOLLOW of the start symbol, so a discard that runs to the end of the input always stops there and reports zero tokens left.

MCQGATE CSE 2015 Set 1

Which one of the following is TRUE at any valid state in shift-reduce parsing?

(A) viable prefixes appear only at the bottom of the stack and not inside
(B) viable prefixes appear only at the top of the stack and not inside
(C) the stack contains only a set of viable prefixes
(D) the stack never contains viable prefixes

Answer: C

Why C. The stack holds a string of grammar symbols, and a string is a viable prefix exactly when some right sentential form begins with it. Every shift is licensed by a table entry, so the stack can never leave that set. The page checks this on 48 configurations of four valid parses, against 514 enumerated right sentential forms: no exceptions.

Why A and B fail. "Only at the bottom" and "only at the top" both deny that the stack is a viable prefix. The stack is one string, so it is one prefix, not several inside one another.

Why D fails. It contradicts the definition outright, and it would make every parse impossible.

Note on the wording. "A set of viable prefixes" is the phrasing in the compilation this item was read from; the mathematical content is that the stack string is a viable prefix.

MSQOriginal practice question

For a table-driven LR parser, which of the following statements are TRUE? Select all that apply.

  1. An error is detected when an ACTION table entry is empty.
  2. An error can be detected by an empty GOTO table entry.
  3. Every reduction performed before the error is announced is one the table licensed.
  4. No erroneous terminal is ever shifted onto the stack.

Answer: A, C and D

A is the definition. C is why "several reductions before the error" is not a mistake: each was an entry in the table for that state and lookahead — 218 of them on this page's canonical LR(1) runs. D follows from A: a shift needs an entry, so a token the table rejects is never shifted.

B is false. GOTO has no terminal columns and is consulted only after a reduction has been chosen, with a nonterminal.

The distinction being tested. "Reduced before the error" against "reduced wrongly". Only the first is true, and it is not a fault.

NATOriginal practice question

Grammar: E → E + T | T, T → T * F | F, F → ( E ) | id, with FOLLOW(E) = { $, ), + }, FOLLOW(T) = { $, ), *, + }, FOLLOW(F) = { $, ), *, + }. Input: id id id. Using panic mode, how many input tokens are discarded in total?

Answer: 2

After the first id the error comes on the second. The recovery picks A = E, pops one state, and discards tokens until one can follow E. Neither id is in FOLLOW(E); the end marker is. So both extra ids are discarded in one recovery, and the run reports one error for two mistakes.

Why not 1. Discarding stops at the first token that can follow E, not at the first token that is a plausible operand.

Edge case. If the offending token had been ")", the answer would be 0, because ")" is in FOLLOW(E) — and then the recovery makes no progress at all, which is the loop in the next question.

MCQOriginal practice question

Panic-mode recovery can fail to terminate. Which one of the following is the reason?

(A) the stack is empty when the error is detected
(B) the offending token is itself in the synchronising set, so nothing is discarded and the same configuration recurs
(C) the table has a shift/reduce conflict
(D) the grammar is ambiguous

Answer: B

Discarding stops at the first token that can follow A. If that token is the one that caused the error, zero tokens are discarded; the pushed state then reduces back to the same place and the same cell fails again. On id + ) id the page records the identical configuration six times.

Why A fails. An empty stack is the case where recovery has no move and stops; it does not loop.

Why C fails. A conflict changes which action is chosen, not whether recovery makes progress.

Why D fails. Ambiguity affects the table, not the discard loop.

The fix. A progress rule: if the same stack and position recur, delete the token.

NATOriginal practice question

A grammar has 5 terminals. At the error point, phrase-level recovery tries every one-token correction: one deletion of the offending token, one insertion of each terminal, and one replacement of the offending token by each other terminal. How many candidates are tried?

Answer: 10

1 + 5 + 4 = 10, which is 2n for n = 5. Each candidate is a complete re-parse, so one error costs ten parses.

Why not 9. Inserting the offending terminal before itself is a different string from deleting it, and both are candidates.

The general rule. 1 + n + (n − 1) = 2n candidates, linear in the alphabet and not in the input length.

MCQOriginal practice question

In an LL(1) parser, the table entry M[A, a] is empty. Which action does panic-mode recovery take first?

(A) discard a if a is in FOLLOW(A), otherwise pop A
(B) pop A if a is in FOLLOW(A), otherwise discard a
(C) pop A and discard a together
(D) shift a onto the stack and continue

Answer: B

If a can follow A, the cheapest explanation is that A should have derived the empty string, so A is popped. If a cannot follow A, the token itself is the intruder and is discarded. The two decisions are counted separately — on b b b the page reports 2 discards and 1 pop.

Why A fails. It reverses the test, which would discard exactly the tokens that were legal.

Why C fails. Doing both at once hides one of the two errors and makes the counts meaningless.

Why D fails. An LL parser never pushes an input token; it matches it and consumes it.

MSQOriginal practice question

Which of the following are true of error productions — productions containing the terminal error?

  1. They are used to detect the error in the first place.
  2. They can add states to the parser's automaton.
  3. They can introduce conflicts that were not present before.
  4. They let the parser skip a bad phrase and resume at a synchronising token.

Answer: B, C and D

B and C are measured here: two error productions take the expression grammar from 12 states to 15, and from 0 conflicts to 1 — a shift/reduce conflict in state 7 on ")". D is the procedure: pop until error can be shifted, shift it, then delete offending tokens while in error mode.

A is false. Detection is still the blank ACTION cell. The error production is used after detection, to recover.

The closely confused pair. Detection and recovery. The error token belongs to the second; the empty cell belongs to the first.

MCQOriginal practice question

A parser recovers from an error and its run ends with "accept". Which conclusion is justified?

(A) the original input is a sentence of the grammar
(B) the input after the recovery's edits is a sentence of the grammar
(C) the grammar is ambiguous
(D) the parser is not LR(1)

Answer: B

Recovery edits the input — by deleting tokens, by inserting a state through a GOTO, or by shifting error — and the accept refers to the edited string. On id + ) id the guarded panic run accepts id +.

Why A fails. The table rejected the original string at position 3, and nothing in recovery changes the table.

Why C and D fail. Neither follows from anything about recovery. This grammar is unambiguous and SLR(1) with 12 states and no conflicts.

The habit worth keeping. Print the accepted string, not just the verdict.

Definitions in one line each

  • Detection: ACTION[state, token] is empty. GOTO never detects.
  • Viable prefix: a prefix of some right sentential form.
  • Panic mode (LR): pop to a state with a GOTO on A, discard to a token that can follow A, push GOTO(s, A).
  • Panic mode (LL): token in FOLLOW(A) → pop A; otherwise discard the token.
  • Phrase-level: one local insertion, deletion or replacement, then continue.
  • Error production: a production containing the terminal error.
  • Error mode: the state in which further offending tokens are deleted without a message.

The procedure, in five lines

  1. Look up ACTION(state, token). A blank cell is the error.
  2. Record the state, the token and the position — that triple is the message.
  3. Choose the recovery: pop and discard, a one-token repair, or the error token.
  4. Guard it: every pass must consume a token or shorten the stack.
  5. Resume, and report the accepted string if the run ends with accept.

The traps, ranked by how often they are made

  • Saying canonical LR(1) never reduces before an error.
  • Saying the GOTO table can detect an error.
  • Treating several reductions as evidence of a wrong parser.
  • Assuming panic mode terminates as written.
  • Reading "accepted" as "the program is valid".
  • Forgetting the end-of-input case, where deletion cannot help.
  • Assuming error productions cost nothing.

Four questions that decide almost every item

  • Where did it stop? State and token at the first blank ACTION cell.
  • What moved? States popped, tokens discarded — or the token that was edited.
  • What was the sync set? FOLLOW of the chosen nonterminal for panic mode; the error token's column for error productions.
  • What was accepted? The repaired string, not the original.

One-sentence summary

An error is a blank cell in the ACTION table, and recovery is any policy that changes the two counts — states popped and tokens discarded — or edits the input, so that the parser can continue; every such policy accepts a repaired string, never the one that was written.
