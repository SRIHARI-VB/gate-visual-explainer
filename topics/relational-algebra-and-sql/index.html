Topic and objective

TOPIC: The relational model's three languages — relational algebra, tuple relational calculus, and SQL — plus the mapping from an ER design to relations. This is the whole of the clause "ER-model. Relational model: relational algebra, tuple calculus, SQL" in Section 9 of the official GATE 2027 CS syllabus.

LEARNING OBJECTIVE: Given relations printed as tables, evaluate any relational-algebra expression on them, write "for all" requirements as division or as a double difference, translate between a calculus expression and an algebraic one, translate a query between SQL and the algebra knowing where the two deliberately differ, and predict what a SQL query returns when a column contains NULL.

I read this topic as one set of tuples, three notations. Every operator in this lesson takes relations and returns a relation, so every question is either "what is the answer relation" or "which expression gives that relation". The three notations differ in what they let you say — algebra says how, calculus says what, SQL says what but keeps duplicates — and nearly every mark is lost at one of those three seams.

Prerequisites

  • Sets, and what membership means. A relation is a set, so duplicates do not exist and order does not exist. Built in Sets and Set Operations.
  • Relations as sets of pairs. A two-attribute relation is a set of ordered pairs. Built in Relations and Their Properties.
  • Cartesian product and its cardinality. $$|R \times S| = |R|\cdot|S|$$ — the size multiplies while the degree adds.
  • Existential and universal quantifiers. "There exists" and "for all", and the fact that a universal statement over an empty set is vacuously true. Built in First-Order Logic.

No SQL is assumed. Every clause used here is defined on the Build-up tab, and no question depends on a feature of a particular database engine.

The five ideas to leave with

  1. Every operator returns a relation, and you can write its schema before computing a single tuple. Do that first.
  2. Projection removes duplicates and SQL's SELECT does not. π is SELECT DISTINCT, not SELECT.
  3. Division is the algebra's "for every". On the GATE 2017 instance CR ÷ T1 has 4 rows, and it needs no operator beyond projection, product and difference.
  4. A shared variable in a calculus expression becomes an equality join condition — by position, not by name.
  5. NULL makes a third truth value. WHERE keeps only TRUE, so a row can be dropped by a test and by its negation, and NOT IN over a NULL returns nothing.

Intuition: one filing cabinet, three ways to ask

A clerk has a cabinet of cards. Each card records one fact — this student took this course — and the cards are kept in a set with no order and no duplicates. Three colleagues ask the same questions in three different habits.

The first colleague gives instructions: take the drawer, keep the cards with SA on them, then copy out only the course column. That is relational algebra. The second writes a description: "all courses c such that some card exists with SA and c on it". That is tuple calculus. The third writes it in the house form: SELECT DISTINCT c FROM CR WHERE s = 'SA'. That is SQL — and the house form has one habit the cabinet does not: it will happily hand you the same card twice.

Formal definition

A relation instance over attributes $$A_1,\dots,A_n$$ is a subset of $$D_1 \times \dots \times D_n$$, where each $$D_i$$ is the domain of $$A_i$$. A tuple is one element of that subset. A schema is the name plus the attribute list; the instance is the set of tuples at one moment.

Degree (also called arity) is $$n$$, the number of attributes. Cardinality is the number of tuples in the instance.

The six primitive operators. Selection $$\sigma_\theta(R)$$ keeps tuples satisfying $$\theta$$; projection $$\pi_X(R)$$ keeps attributes $$X$$ and removes duplicate tuples; rename $$\rho$$ changes a name; union, difference and the Cartesian product act on whole tuples. Everything else is written from these six.

Why set semantics matters here

Because a relation is a subset, it cannot hold two equal tuples. That single sentence has three consequences that questions exploit:

Projection on 18 tuples of CR gives 4 tuples, not 18, because CA appears five times. Union of a relation with itself is the relation. And an insert of an existing tuple changes nothing.

Mathematical derivation This page's model computes both readings: 4 tuples under set semantics and 18 under bag semantics, on the same instance. Both numbers appear in the model checks.

What each operator needs to be legal

Union, difference and intersection need identical schemas in the same attribute order. Division needs the right operand's attributes to be a subset of the left operand's. A join needs the join attributes to exist on both sides. These are requirements, not conventions — an expression that violates one is undefined, and a question can ask you to spot that.

A natural join with no attribute in common is defined and equals the Cartesian product, which surprises people precisely because it is legal.

The derived operators, and the two other languages

Once the six primitives are fixed, the rest is abbreviation. The three blocks below are the whole of what this lesson adds: derived algebra, the calculus, and SQL's clause order.

Derived algebra

R ∩ S = R − (R − S)Intersection is a double difference. No new operator.
R ⋈θ S = σθ(R × S)A theta join is a product filtered by the condition θ.
degree(R ⋈ S) = degree(R) + degree(S) − |common|A natural join keeps one copy of each equally named attribute.
R ÷ S = πA(R) − πA( πA(R) × S − R )Division from projection, product and difference, where A is the attributes of R that S does not share.

Mathematical derivation The page's model checks the division identity against the definition on five instances, including one where S is empty.

Tuple relational calculus

A query is a set former: { t | P(t) }, where t is a tuple variable and P is a formula built from membership tests, comparisons, ∧, ∨, ¬ and the quantifiers ∃ and ∀.

A variable is bound if a quantifier introduces it and free otherwise. The free variables are what the answer reports.

An expression is safe when its answer draws only values from the relations mentioned. Unsafe expressions are excluded, which is what keeps the calculus equal in power to the algebra.

Educational interpretation Read a shared variable as a join and a quantified-but-unreported variable as a projection. That reading reproduces GATE 2026 Set 1 Q43 exactly.

SQL's evaluation order

FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. Typed top to bottom, evaluated in that order instead.

Consequences: an alias made in SELECT cannot be used in WHERE; an aggregate cannot appear in WHERE because groups do not exist yet; HAVING removes whole groups.

The correspondence: π ↔ SELECT DISTINCT, σ ↔ WHERE, × ↔ several tables in FROM, ∪/∩/− ↔ UNION/INTERSECT/EXCEPT, ρ ↔ AS. Only the first of those carries a warning, and it is the most tested one.

ER to relations: the five rules

One: each strong entity becomes a relation keyed by its own key. Two: a 1:1 or 1:N relationship needs no relation of its own — the key of the "one" side is placed in the relation of the "many" side as a foreign key. Three: an M:N relationship becomes its own relation, keyed by the pair of foreign keys. Four: a multivalued attribute becomes its own relation, keyed by the owner key plus the attribute. Five: a weak entity becomes its own relation, keyed by the owner key plus its partial key, with a foreign key to the owner.

Worked examples, page 1 of 2 — the operators

Every number on this page is produced by the model on the Animation tab. The reference instance is CR(StudentName, CourseName) with the eighteen tuples printed in GATE CSE 2017 Set 1 Q46.

E1. Selection, then projection

σs='SA'(CR)3 tuples: (SA,CA), (SA,CB), (SA,CC). Schema still (s, c).
πc(σs='SA'(CR))3 tuples: CA, CB, CC. Now degree 1.
πc(CR)4 tuples: CA, CB, CC, CD — from 18 printed tuples.

The step list is the answer to "how many tuples": count the rows first, then remove repeats. The selection changed 18 to 3 and kept the degree; the projection changed the degree and, applied to the full relation, changed 18 to 4.

E2. Set operators, step by step

With R = {(1,x),(2,y),(3,x)} and S = {(2,y),(4,z)}, both over (A,B):

R ∪ S = 4 tuples(2,y) is in both and appears once.
R − S = {(1,x), (3,x)}The rows of R that S does not contain.
R ∩ S = {(2,y)}Derived as R − (R − S), and it agrees.
R × S = 6 tuples, degree 4|R|·|S| tuples, degree(R)+degree(S) attributes.

The model checks all four, plus R ∪ R = R and R − R = ∅.

E3. A theta join that loses a row

R(P,Q) = {(1,10),(2,20),(3,10),(4,40)} and S(X,Y) = {(10,a),(30,b),(40,c)}.

R ⋈R.Q=S.X S3 tuples, degree 4: (1,10,10,a), (3,10,10,a), (4,40,40,c).

The row (2,20) has no partner, because no tuple of S has X = 20. Nothing is "merged": the two joined attributes are named Q and X, so both survive.

If the attributes had both been named k, the natural join would have produced degree 3, not 4: 2 + 2 − 1. That single subtraction is worth a mark in most papers that ask it.

E4. Division on the GATE 2017 instance

T1 ← πCourseName(σStudentName='SA'(CR)) = {CA, CB, CC}
T2 ← CR ÷ T1Students paired with all three courses: SA, SC, SD, SF.

The number of rows in T2 is 4. SB is excluded because it has no CA; SE is excluded because it has no CC. Each of them fails on exactly one course, and one failure is enough.

Mathematical derivation Recomputed here two ways — directly from the definition, and through πA(R) − πA(πA(R) × S − R) — and both give the same four students.

Worked examples, page 2 of 2 — "for all", calculus, and SQL

These four examples are the ones that carry the marks: a universal requirement, a translation between notations, and a query whose answer changes because a column holds NULL.

E5. "Owns all the brands", four ways (GATE 2022 Q25)

Witness 1: Own = {(E1,B1),(E1,B2),(E2,B2)}, Brand = {B1,B2,B3,B4}. Nobody owns all four, so the answer is ∅.

(A) πeId(πeId,bId(Own) ÷ πbId(Brand)) = ∅ ✓
(B) πeId(Own) − πeId(πeId(Own) × πbId(Brand) − Own) = ∅ ✓
(C) πeId(πeId,bId(Own) ÷ πbId(Own)) = {E1} ✗
(D) πeId(πeId(Own) × πbId(Own) ÷ πbId(Brand)) = ∅ ✓

Witness 2: Own = {(E1,B1),(E2,B2)}, Brand = {B1,B2}. Correct answer ∅. Now (D) returns {E1,E2} ✗ while (C) returns ∅.

Each of C and D is wrong, but each is wrong on a different instance. The model checks both witnesses, and confirms A and B agree with the definition on five further instances.

E6. Calculus to algebra (GATE 2026 Set 1 Q43)

E = { ⟨u⟩ | ∃v ∃w (⟨u,v⟩ ∈ R ∧ ⟨v,w⟩ ∈ S) } with R(P,Q) and S(X,Y).

⟨u,v⟩ ∈ R fixes u = R.P and v = R.Q. ⟨v,w⟩ ∈ S fixes v = S.X and w = S.Y. So the shared variable forces R.Q = S.X, the output is P, and w is projected away.

E = πP( S ⋈S.X=R.Q R )Option (B) of the four.

On R = {(1,10),(2,20),(3,10),(4,40)} and S = {(10,a),(30,b),(40,c)} the answer is P ∈ {1,3,4}, and (A), (C), (D) each return ∅ because they join on P or on Y.

E7. Two tests, one missing row

A table holds x = 6, 5 and NULL. Count the rows returned by each query.

WHERE x = 5 → 1 rowThe row with 5. NULL gives UNKNOWN, which is dropped.
WHERE x <> 5 → 1 rowThe row with 6. The NULL row is dropped again.

The two counts add to 2, not 3. The only test that reaches the NULL row is IS NULL.

GATE 2000 Q2.26 asks the same fact from the other direction. The paper stipulates that a comparison with NULL counts as false. Under that stipulation x ≠ 5 and NOT(x = 5) disagree on the NULL row — x ≠ 5 is false, NOT(false) is true — so pair C is not equivalent and the key is C. Under ordinary three-valued logic all three pairs agree, which is why the stipulation has to be noticed.

E8. What AVG divides by

Emp(eid, dept, sal) = (1,A,100), (2,A,NULL), (3,B,200), (4,NULL,300), (5,B,NULL).

COUNT(*) = 5 COUNT(sal) = 3Star counts rows; a column counts values.
SUM(sal) = 600 AVG(sal) = 200600 divided by 3, not by 5.
GROUP BY dept → 3 groupsA with 2 rows, B with 2 rows, and one group whose key is NULL.

HAVING COUNT(*) > 1 keeps 2 of those 3 groups. All rows whose grouping key is NULL form one group, and HAVING filters groups rather than rows.

Boundaries, and the condition each one breaks

Every item here is a case where the ordinary rule stops applying. The condition in italics is what makes it stop.

Division by an empty set

If S has no tuples, then "paired with every tuple of S" is true of every A-value, because the test is vacuously true. So R ÷ S returns πA(R) in full.

The model checks this on a five-instance set that includes an empty S. It is the same vacuous-truth rule that makes > ALL (empty) true in SQL — and > ANY (empty) false.

A natural join with nothing in common

R(A) and S(B) share no attribute, so there is no condition to test and every pair survives. The natural join equals the Cartesian product: 2 × 3 = 6 tuples and degree 2.

Breaks the intuition that a join always reduces the number of tuples. A join reduces rows only when a condition can fail.

Union of two different schemas

R(A,B) ∪ S(B,A) is not a union of the same schema in a different order — the operands must agree attribute by attribute, in order. R(A,B) ∪ S(A,C) is undefined outright.

Breaks the intuition that a union is always available. Rename first, then union.

A join on a NULL key

The join condition R.k = S.k evaluates to UNKNOWN when either k is NULL, so the row never matches — not even another row whose k is also NULL.

Breaks the intuition that equal values match. NULL is not a value; it is the absence of one, so two absences are not equal.

NOT IN against a NULL

S(x) = {1,2,3} and T(y) = {2, NULL}. x NOT IN (SELECT y FROM T) returns 0 rows, because x ≠ NULL is UNKNOWN and an AND chain containing UNKNOWN cannot be TRUE.

The equivalent NOT EXISTS returns 2 rows, 1 and 3. Both numbers are computed by the model. Breaks the equivalence between the two spellings, which holds only when the subquery is NULL-free.

UNION versus UNION ALL

Plain UNION removes duplicate rows; UNION ALL keeps them. Relational-algebra union is the plain one, so a question that says UNION ALL is asking about bags.

Breaks the correspondence between ∪ and UNION if you read the wrong keyword.

A self-join without a rename

"Find employees who earn more than their manager" needs Employee twice. Without ρ (or SQL's AS), both copies have the same attribute names and the condition is ambiguous.

Breaks the assumption that a relation can be used once per expression. Rename is the operator that exists for exactly this.

π on a single attribute of a many-attribute relation

πA(R) can have fewer tuples than R even when A never repeats a value — and it always has fewer when A does. Asking "how many tuples does π return" is a distinct-count question, not a row-count question.

Breaks the intuition that projection only changes the width. It changes both the width and the count.

Degree and cardinality swapped

A relation with 3 attributes and 7 tuples has degree 3 and cardinality 7. GATE CSE 2023 asked which option names the degree.

Breaks nothing mathematically, but it is the cheapest mark in the subject and the most commonly misread word.

Seven beliefs that cost marks

Each one is written as the belief, then why it tempts, then the smallest case that breaks it, then the rule to use instead.

"SELECT is projection"

Why it tempts: every textbook prints the mapping as a one-line table, and the words are synonyms in English.

Minimal counterexample: πc(CR) has 4 tuples; SELECT c FROM CR has 18. Only SELECT DISTINCT c gives 4.

Correct rule: π = SELECT DISTINCT. SELECT alone is bag projection.

"R − S is the same as S − R"

Why it tempts: intersection is symmetric, and the two operators sit next to each other in every list.

Minimal counterexample: R = {(1,x),(2,y)}, S = {(2,y),(4,z)}. R − S = {(1,x)}; S − R = {(4,z)}.

Correct rule: difference is one-directional. The left operand is the source of the answer's tuples.

"Division is a primitive, or a numeric operation"

Why it tempts: the symbol ÷ looks like arithmetic and is usually introduced last.

Minimal counterexample: a question can ask for "owns all brands" with only selection, projection, product and rename available — GATE 2024 Set 2 Q45 did exactly that.

Correct rule: R ÷ S = πA(R) − πA(πA(R) × S − R), using no selection at all.

"An option that works on one instance is correct"

Why it tempts: you test the option on the instance printed in the question, and it gives the right answer.

Minimal counterexample: on GATE 2022's own relations, option D is harmless. On Own = {(E1,B1),(E2,B2)} with Brand = {B1,B2} it returns {E1,E2} while the answer is ∅.

Correct rule: an expression is correct when it is correct on every instance. Construct the instance where the candidate is weakest — usually one with an unowned brand, or one with nobody owning anything.

"NULL = NULL is true"

Why it tempts: in every programming language you have used, two empty values compare equal.

Minimal counterexample: a column holding NULL: WHERE k = NULL returns 0 rows, and a join on two NULL keys matches nothing.

Correct rule: any comparison with NULL is UNKNOWN; only IS NULL and IS NOT NULL give a definite answer.

"WHERE p OR NOT p returns every row"

Why it tempts: it is the law of the excluded middle, and it holds in the two-valued logic of the Discrete Mathematics lesson.

Minimal counterexample: on x = {6, 5, NULL}, the condition x = 5 OR x ≠ 5 is UNKNOWN on the NULL row, so that row is dropped.

Correct rule: three-valued logic has no excluded middle. Rows with UNKNOWN are excluded by WHERE.

"NOT IN and NOT EXISTS are the same query"

Why it tempts: on a NULL-free database they agree on every instance, so the difference never shows up in practice.

Minimal counterexample: S = {1,2,3}, T = {2, NULL}: NOT IN returns 0 rows, NOT EXISTS returns 2.

Correct rule: they agree only when the subquery has no NULLs. EXISTS yields TRUE or FALSE and never UNKNOWN.

The distinction that resolves most of them

The algebra is about sets; SQL is about bags with a third truth value. Every one of the seven beliefs above comes from carrying a set habit into SQL, or a SQL habit into the algebra. Before answering, decide which of the two notations the question is actually asking about, and the trap usually disappears.

Six question shapes, and the reasoning each one demands

This is a classification of what the papers ask, not a prediction. Community observation Two question-indexed archives list 38 relational-algebra items and 15 relational-model/SQL items across the papers they index; their tagging is the source of that shape list.

1. Evaluate an expression on a printed instance

Demands: write the result schema, then the tuples, in that order. Count rows only after removing duplicates.

Common wrong approach: reading the operator list left to right and drawing a table at every step, which loses track of which duplicates have already collapsed.

2. Translate between calculus and algebra

Demands: map each tuple variable to an attribute by position; a shared variable is an equality condition; a quantified variable that is not reported is projected away.

Common wrong approach: joining on the first attribute of each relation because the expressions look symmetrical.

3. "For all" requirements

Demands: recognise all/every/each and write division, or the double difference. Check the answer on an instance with an unused value.

Common wrong approach: dividing by the projection of the fact table instead of by the dimension table, which silently drops values nobody has.

4. SQL row counts with NULLs

Demands: check every predicate that touches a nullable column; remember WHERE keeps only TRUE; remember NOT IN dies on a NULL.

Common wrong approach: counting the rows that "should" match by intent, and adding the counts of a predicate and its negation.

5. Aggregation and grouping

Demands: separate WHERE from HAVING; know that COUNT(*) counts rows while COUNT(col) counts values; know that all NULL keys form one group.

Common wrong approach: putting an aggregate in WHERE, or computing AVG as a sum divided by the row count.

6. Vocabulary and ER mapping

Demands: degree versus cardinality; which relationships need their own relation; where a foreign key lands.

Common wrong approach: creating a relation for every relationship, including the 1:N ones that need none.

The solving procedure that works for all six

  1. Fix the schemas. Write each operand's attributes. Check that every set operator has matching schemas and that division has a subset. Justification: an illegal expression has no answer, and that is sometimes the option being tested.
  2. Write the answer schema. Which attributes survive, and does any attribute merge? Justification: it eliminates wrong options before any tuple is computed.
  3. Enumerate the tuples on the printed instance. Do not estimate from the English. Justification: every count in this topic is small enough to write out.
  4. Check the boundary. Is the right operand of a division empty? Is the subquery NULL-free? Does the column hold a NULL? Justification: that is where the printed instance and the general rule diverge.
  5. Convert only at the end. If the answer is asked in rows, count distinct tuples; if in marks or milliseconds, convert once. Justification: rounding early is how a 4 becomes a 3.

NATMediumPYQ — GATE CSE 2017 Set 1, Q46

CR(StudentName, CourseName) holds 18 tuples: SA takes CA, CB, CC; SB takes CB, CC; SC takes CA, CB, CC; SD takes CA, CB, CC, CD; SE takes CD, CA, CB; SF takes CA, CB, CC. With T1 ← πCourseName(σStudentName='SA'(CR)) and T2 ← CR ÷ T1, the number of rows in T2 is ______.

Answer: 4

T1 = {CA, CB, CC}. Students holding all three: SA, SC, SD, SF. SB lacks CA and SE lacks CC, so both are dropped.

Answering 6 counts the students instead of the qualifying students; answering 3 counts the courses in T1. Division returns the non-common attributes of the left operand, so the answer is a set of students.

MSQMediumPYQ — GATE CSE 2022, Q25

Employee(eId, Name), Brand(bId, bName), Own(eId, bId). Which of the following return the set of eIds who own all the brands?

(A) πeId(πeId,bId(Own) ÷ πbId(Brand))
(B) πeId(Own) − πeId((πeId(Own) × πbId(Brand)) − πeId,bId(Own))
(C) πeId(πeId,bId(Own) ÷ πbId(Own))
(D) πeId((πeId(Own) × πbId(Own)) ÷ πbId(Brand))

Answer: (A) and (B)

A is division by the brand relation; B is the double difference that spells the same thing out. The model confirms both agree with the definition on five further instances.

(C) divides by the brands that appear in Own, which is a smaller set whenever some brand is owned by nobody. On Own = {(E1,B1),(E1,B2),(E2,B2)} with Brand = {B1,B2,B3,B4} it returns E1, while the true answer is empty.

(D) forms every pair of employee and owned brand before dividing, so on Own = {(E1,B1),(E2,B2)} with Brand = {B1,B2} it returns both employees, while the true answer is empty.

MCQMediumPYQ — GATE CSE 2026 Set 1, Q43

With R(P,Q) and S(X,Y), let E = { ⟨u⟩ | ∃v ∃w (⟨u,v⟩ ∈ R ∧ ⟨v,w⟩ ∈ S) }. Which expression is equivalent to E?

(A) πP(R ⋈R.P=S.X S)   (B) πP(S ⋈S.X=R.Q R)   (C) πP(R ⋈R.P=S.Y S)   (D) πP(S ⋈S.Y=R.Q R)

Answer: (B)

⟨u,v⟩ ∈ R puts u in position 1 (P) and v in position 2 (Q). ⟨v,w⟩ ∈ S puts v in position 1 (X) and w in position 2 (Y). The shared variable v therefore forces R.Q = S.X, and the reported variable u is P.

(A) and (C) join on P, which is the reported attribute, not the shared one. (D) joins on Y, the second attribute of S. On the instance used in this lesson, (B) returns P ∈ {1,3,4} and the other three return nothing.

MCQHardPYQ — GATE CSE 2000, Q2.26

In SQL, relations can contain null values, and comparisons with null values are treated as unknown. Suppose all comparisons with a null value are treated as false. Which of the following pairs is not equivalent?

(A) x = 5 and NOT(NOT(x = 5))   (B) x = 5 and (x > 4 AND x < 6)   (C) x ≠ 5 and NOT(x = 5)   (D) none of the above

Answer: (C)

Under the stipulation, take x = NULL. Then x ≠ 5 is false, while NOT(x = 5) is NOT(false) = true. The two differ, so C is not a pair of equivalent expressions.

(A) survives because NOT(NOT(false)) is false again. (B) survives because x > 4 AND x < 6 is false on the NULL row, matching x = 5.

Worth knowing: under ordinary three-valued logic, all three pairs are equivalent, because NOT(UNKNOWN) is UNKNOWN and x ≠ 5 is UNKNOWN too. The model on this page computes both readings, which is why the stipulation in the question has to be read carefully.

NATMediumOriginal practice question

S(x) holds 1, 2 and 3. T(y) holds 2 and NULL. The query SELECT x FROM S WHERE x NOT IN (SELECT y FROM T) returns ______ rows, and the query SELECT x FROM S WHERE NOT EXISTS (SELECT * FROM T WHERE T.y = S.x) returns ______ rows.

Answer: 0 and 2

NOT IN expands to x ≠ 2 AND x ≠ NULL. For x = 1 the second conjunct is UNKNOWN, so the conjunction is UNKNOWN, and WHERE keeps only TRUE. For x = 2 the first conjunct is FALSE. For x = 3 the second is UNKNOWN again. Nothing survives.

NOT EXISTS yields a definite truth value: 1 and 3 have no matching row, so both are returned; 2 matches and is excluded. Both counts are computed by the model.

NATMediumOriginal practice question

Emp(eid, dept, sal) holds (1,A,100), (2,A,NULL), (3,B,200), (4,NULL,300), (5,B,NULL). The query SELECT dept FROM Emp GROUP BY dept HAVING COUNT(*) > 1 returns ______ rows, and SELECT AVG(sal) FROM Emp returns ______.

Answer: 2 rows, and 200

The groups are A (2 rows), B (2 rows) and one group whose key is NULL (1 row). HAVING COUNT(*) > 1 keeps A and B.

AVG ignores NULLs: the sum is 600 over 3 non-NULL salaries, so the average is 200, not 120. Dividing by the 5 rows would give 120, which is the standard error.

Practice, page 3 of 3 — operators and mapping

MCQEasyOriginal practice question

R(A,B) has 3 tuples and S(B,C) has 5 tuples, and every tuple of R agrees with some tuple of S on B. What is the degree of R ⋈ S (natural join), and what is its maximum possible cardinality?

(A) 3 and 15   (B) 4 and 15   (C) 3 and 8   (D) 4 and 8

Answer: (A) — degree 3, at most 15 tuples

Degree = 2 + 2 − 1 shared attribute = 3: A, B, C with B kept once. The cardinality is at most |R| × |S| = 15, reached when the B values match in the worst-case many-to-many way.

(B) adds the degrees and forgets the merged attribute. (C) and (D) add the cardinalities. The condition that every R tuple finds a partner removes no R tuple, so 15 remains possible.

NATMediumOriginal practice question

R(A,B) = {(1,x),(1,y),(2,x),(3,z)} and S(B) = {(x),(y)}. The number of tuples in R ÷ S is ______. If S were empty instead, the number would be ______.

Answer: 1, and 3

Only A = 1 is paired with both x and y. A = 2 has x only; A = 3 has z, which is not in S at all.

With S empty, the test "paired with every tuple of S" is vacuously true, so every distinct A-value qualifies: 1, 2 and 3, which is 3 tuples. This is the same vacuous truth that makes > ALL (empty subquery) true in SQL.

MSQHardOriginal practice question

Which of the following pairs are not equivalent on every instance?

(A) πA(σθ(R)) and σθ(πA(R)), where θ mentions only attributes in A
(B) πA(R) and R, when A is every attribute of R
(C) R ⋈ S and σR.k=S.k(R × S), when k is the only common attribute
(D) R ÷ S and πA(R) when S is empty, where A is the attributes R does not share with S

Answer: none of them — all four are equivalent

(A) holds when the test survives the projection, which the condition guarantees. (B) holds because projecting on every attribute removes only duplicates, and a relation has none.

(C) is the definition of the natural join written out. (D) is the vacuous-truth case, and the model checks it directly.

This is the deliberate trap: a multiple-select question with no wrong option is unusual but possible, and each option has to be justified rather than assumed wrong. If θ mentioned an attribute outside A, (A) would fail — that is the counterexample to keep in mind.

MCQMediumOriginal practice question

An ER design has strong entities Employee, Department and Project; a 1:N relationship "works" from Department to Employee; an M:N relationship "owns" between Employee and Project; a multivalued attribute Phone on Employee; and a weak entity Dependent of Employee with partial key dname. How many relations does the standard mapping produce, and what is the key of the relation for Dependent?

(A) 5, key dname   (B) 6, key (eid, dname)   (C) 7, key (eid, dname)   (D) 6, key (eid)

Answer: (B) — 6 relations, key (eid, dname)

Employee, Department, Project, WorksOn, Phone, Dependent. The 1:N relationship adds no relation: it puts did into Employee as a foreign key.

(A) forgets the multivalued attribute, which needs its own relation. (C) invents a relation for the 1:N relationship. (D) drops the partial key, which cannot identify a dependent uniquely on its own.

One-screen revision sheet

Everything below is either a definition or a formula you can write from memory. The numbers are the ones this lesson computed.

Vocabulary

Schema — name plus attribute list. Instance — the set of tuples now.

Degree — number of attributes. Cardinality — number of tuples.

Bag — a multiset, which is what a SQL table is. Set — no duplicates, which is what a relation is.

Operators

Primitive: σ, π, ρ, ∪, −, ×.

Derived: ∩ = R − (R − S); R ⋈θ S = σθ(R × S); ÷ = πA(R) − πA(πA(R) × S − R).

Counts: |R × S| = |R|·|S|; degree(R × S) = degree(R) + degree(S); degree(R ⋈ S) = sum − |common|.

SQL correspondence

π → SELECT DISTINCT · σ → WHERE · × → tables in FROM · ∪ → UNION · − → EXCEPT · ∩ → INTERSECT · ρ → AS

Order: FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY. Aggregates belong in HAVING, never in WHERE.

NULL rules

Any comparison with NULL is UNKNOWN. WHERE keeps only TRUE. NOT UNKNOWN is UNKNOWN. NULL AND FALSE is FALSE; NULL OR TRUE is TRUE.

COUNT(*) counts rows, COUNT(col) counts values. AVG divides by the non-NULL count. NULL keys form one group. NOT IN over a NULL returns nothing; NOT EXISTS does not.

The four answers to memorise

GATE 2017 Set 1 Q46: CR ÷ T1 has 4 rows — SA, SC, SD, SF.

GATE 2022 Q25: options A and B; C and D each fail on a witness.

GATE 2026 Set 1 Q43: option B, πP(S ⋈S.X=R.Q R).

GATE 2000 Q2.26: option C, under the paper's own stipulation that a NULL comparison is false.

Five sentences worth remembering

  1. Write the answer's schema before computing a single tuple.
  2. π is SELECT DISTINCT; SELECT alone keeps duplicates.
  3. "All" is division, and division is a double difference with no selection in it.
  4. A shared calculus variable becomes an equality join condition, decided by position.
  5. WHERE keeps only TRUE, so a NULL row can be lost twice — by a test and by its negation.
