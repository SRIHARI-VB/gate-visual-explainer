Topic and objective

TOPIC: Trees, binary search trees and heaps — the shape, the traversals, the search promise, the counting, and the array trick that removes the pointers.

LEARNING OBJECTIVE: Given a tree question, decide first which of the three promises is being made — a shape, a search order, or a heap order — and then answer from that promise: read a traversal, test whether a tree is a search tree, count the trees on n nodes, delete a node without breaking the order, index a heap in an array, and cost an insertion, a removal and a build.

I read this topic as three promises over one shape, because every GATE question in it turns on one of three things: which traversal list you were given, whether the order promise is global or merely local, or which base index the array uses. Balanced trees, AVL rotations and B-trees are named as the next step and are not taught here.

GATE relevance

Verified fact Class A — explicitly in the syllabus.

Section 4 of the official GATE 2027 CS syllabus (IIT Madras) reads: "Programming in C. Recursion. Arrays, stacks, queues, linked lists, trees, binary search trees, binary heaps, graphs." The words trees, binary search trees and binary heaps are all named, in that order, after linked lists.

Class A means a question on this is inside the declared boundary. It does not mean one is guaranteed, and it says nothing about how many marks. The previous-year questions quoted in this lesson are observations about old papers, not a forecast.

Prerequisites

Three published lessons carry the machinery this one uses:

  • Linked Lists — a node holds a value and the address of the next one, and a splice is two writes in a fixed order. A binary tree is that node with two addresses instead of one, so scenes 4 and 6 are the same surgery.
  • Recursion — every traversal in scene 2 is a recursive procedure over subtrees, and the height of a tree is a recurrence.
  • Arrays, Stacks and Queues — index arithmetic, and the queue that level order needs.

Helpful but not required:

  • Counting and Combinatorics — scene 5 counts trees with the Catalan numbers, which that lesson meets from the other side.
  • Recurrence Relations — the recurrence T(n) = sum T(k-1) T(n-k) and the level-sum argument in scene 9.

If you can already write a traversal and say what a heap is, start at the Animation tab and come back when a caption surprises you.

Visualization plan

Ten scenes, each one argument:

  1. A tree is a chain that branches. Parts, height and depth, n0 = n2 + 1, and the three words full, complete, perfect.
  2. Four walks. Preorder, inorder, postorder, level order, then reconstruction from a traversal pair.
  3. A promise about every descendant. Bounds, the parent-only counterexample, and a search path as narrowing bounds.
  4. Insertion writes the shape. The same keys in two orders; the chain; the height bounds for 15 nodes.
  5. Counting the trees. The root split, the Catalan numbers, and shapes against fillings.
  6. Deletion. Leaf, one child, two children, and why only the successor keeps the promise.
  7. A heap makes a different promise. Two promises, array indexing, where the maximum lives, and how deep a small key can go.
  8. Sift up, sift down. Insert and remove-the-minimum as one path each, and the arbitrary deletion recipe.
  9. Linear-time build. The level sum, a real array traced through it, then heapsort.
  10. Three promises, one table. The comparison, and the four questions that decide an option.

What you should be able to do afterwards

Take any tree question and answer, in this order: which promise is stated?, is the shape fixed or the order fixed?, which base index is in force?

The most expensive mistake here is answering from the name of the structure instead of from its promise. "Search tree, so log n" is false the moment the tree is a chain, and "heap, so sorted" is false always.

Level 1 — Intuition: the family tree and the filing clerk

The tree is a family tree that only ever has two children. One person is the ancestor at the top. Everyone below is reached by going down through someone. A person with no children is a leaf; the distance from the ancestor is the depth.

The search tree is a filing clerk with one rule. Everything smaller goes in the left drawer, everything larger in the right. To find a folder you never look at everything: you open one drawer at a time, and each drawer is again split by the same rule.

The heap is a different clerk. This one only promises that the most urgent file is on top. That is enough to hand you the next job immediately, and not enough to find any particular file.

Educational interpretation The two clerks are a good picture of two different promises and a poor one of memory: in a heap the "drawers" are array slots, and in a search tree they are pointers, which is why the same tree is cheap in one representation and costly in the other.

Level 2 — Formal definitions

Binary tree. Either empty, or a node with an ordered pair of binary trees called its left and right subtrees.

Depth, height, level. The depth of a node is the number of edges from the root to it; the root has depth 0. The height of a tree is the largest depth of any node, so a single node has height 0. The level of a node is its depth.

Full, complete, perfect. Full: every node has 0 or 2 children. Complete: every level except possibly the last is full, and the last level is filled left to right. Perfect: every level is full.

Binary search tree. For every node x, every key in the left subtree of x is smaller than the key at x, and every key in the right subtree is larger.

Min-heap. A complete binary tree in which the key at every node is no larger than the keys at its children. A max-heap reverses the comparison.

Verified fact These definitions are the standard ones and match the wording used in the GATE 2027 syllabus item and in the papers quoted below, each of which states the height convention when it matters.

Level 4 — Worked example: 15 nodes, two heights

Claim. A search tree with 15 nodes has height at least 3 and at most 14.

Upper bound. A tree in which every node has at most one child is a chain, and a chain of 15 nodes has 14 edges. That height is reachable by inserting 1, 2, ..., 15 in order, so 14 is attainable.

Lower bound. A tree of height h has at most 2h+1 − 1 nodes, since level i holds at most 2i. With h = 2 the maximum is 7, which is fewer than 15, so h ≥ 3.

Attainment. The perfect tree of height 3 has exactly 15 nodes, so 3 is reachable. Derivation The page checks both bounds by enumerating every insertion order of 7 keys and confirming the extreme heights are 6 and 2.

Level 5 — Boundaries: what each promise does and does not give

The search promise is about order, not balance. It guarantees that an inorder walk is sorted and that a search follows one root-to-leaf path. It guarantees nothing about the length of that path.

The heap promise is about one comparison per edge, not about order between siblings. It guarantees the minimum at the root. It does not let you search, and it does not make the array sorted.

The shape promise (complete) is what makes the array representation possible. It is also what bounds the height logarithmically, and it is why a heap cannot degenerate the way a search tree can.

Each promise is stated separately in the question. Find the sentence that states one before you compute anything.

Level 6 — Edge cases and counterexamples

A non-search-tree that passes the parent test. Root 10, left child 5, and 12 as the right child of 5. Every parent-child pair is ordered correctly and 12 is still greater than the root while sitting in its left subtree. The inorder list 5, 12, 10 is not sorted, which is the cheap test that catches it.

A heap that is not a search tree. Array 1, 3, 2, 7, 4 satisfies the heap promise. Its root 1 has left 3 and right 2, so left > right, which the search promise forbids.

A search tree that is not complete. Insert 2, 1, 3, 0. The node 0 hangs at depth 2 on the left, so the tree is a legal search tree and is not complete, and an array would waste a slot.

A "sorted array" that is a valid heap. An increasing array is a valid min-heap, which is exactly why "the heap array is sorted" feels true and is false in general: 1, 3, 2, 7, 4 is a heap and not sorted.

Level 7 — How GATE asks it

Read a traversal. Given one traversal of a search tree, produce another. Since the inorder of a search tree is sorted, one list plus the sorted list is a traversal pair, and the tree is determined.

Test a promise. Which sequence could be a search path; which tree is a valid search tree; which array is a heap.

Count. How many trees, how many insertion orders, how many indices, how many ways.

Cost. The height of a heap or a search tree, the number of comparisons, the complexity of a build or a deletion.

Level 9 — Consolidation

The one-sentence version. A binary tree is a shape; a search tree adds a global order promise that makes an inorder walk sorted; a heap adds a local order promise plus a completeness promise that makes an array hold it, and gives up searching to get a constant-time minimum.

Five things to carry.

  • n0 = n2 + 1 for every binary tree.
  • Inorder is sorted in a search tree, and sorted is only necessary.
  • The number of binary tree shapes on n nodes is the n-th Catalan number, and so is the number of search trees on n distinct keys.
  • A heap's maximum is a leaf, and the leaves of an n-key heap indexed from 1 are the indices n/2 + 1 to n.
  • Bottom-up build is O(n) because most nodes are near the bottom; the level sum is what proves it.

The habit. Before answering, name the promise. Almost every wrong option on a tree question is a true statement about a different promise.

Where the rest of this topic goes

Balanced search trees — AVL, red-black, and the rotation that is three or four link writes — are the natural next lesson and are named here as the next step, not taught. B and B+ trees belong to the database indexing unit and are taught there, with the same node-and-pointer reasoning at a higher branching factor.

Heaps reappear in three later places: heapsort in sorting, priority queues in greedy algorithms, and Dijkstra's algorithm, where the decrease-key operation is the reason a heap is used at all.

GATE CSE 2008 — how many distinct BSTs with 3 distinct keys?

The options were 4, 5, 6 and 9. The answer is 5.

Enumerate the shapes rather than the orders. A tree on 3 nodes is either a chain (root at one end) or a fork (root in the middle). Chains: root 1 with 2 and 3 down the right, or root 3 with 2 and 1 down the left — 2 shapes. Forks: root 2 with 1 and 3 as children, and then the two chains with the root at an end give 3 more... the honest count is the Catalan number C3 = 5, and the page lists all five explicitly.

Why 6 is the trap. There are 3! = 6 insertion orders, and 6 feels like the count of trees. But two different orders can produce the same tree — 2, 1, 3 and 2, 3, 1 both give the fork with root 2 — so the number of orders overcounts. Derivation The page enumerates all 6 orders, removes duplicates by structure, and gets 5.

GATE CSE 2005 — how many distinct BSTs with 4 distinct keys?

The options were 5, 14, 24 and 35. The answer is 14 = C4.

Use the root split: with 4 keys, the root can take rank 1 to 4, leaving (0,3), (1,2), (2,1) or (3,0) nodes on the left and right. So the count is T(0)T(3) + T(1)T(2) + T(2)T(1) + T(3)T(0) = 5 + 2 + 2 + 5 = 14.

Why 24 is the trap. 4! = 24 is the number of insertion orders. The same overcount as above, and the same fix: count shapes, or divide the orders correctly.

GATE CSE 2008 — which sequences could be a search path for 273?

The tree holds keys in the range 37 to 573, and the four candidate sequences were:

I. 81, 537, 102, 439, 285, 376, 305   II. 52, 97, 121, 195, 242, 381, 472
III. 142, 248, 520, 386, 345, 270, 307   IV. 550, 149, 507, 395, 463, 402, 270

The answer is III only. Read each sequence as bounds. In I, after 285 the search goes left (273 < 285), so everything later must be below 285, and 376 is not. In II, after 381 the search goes left, and 472 is not below 381. In IV, after 395 the search goes left, and 463 is not below 395.

Derivation III survives every step: 273 > 142, > 248, < 520, < 386, < 345, > 270, and 307 lies between 270 and 345. The page re-checks all four sequences by simulation and reports the same verdict.

GATE CSE 2008 — which statement about the same four sequences is TRUE?

The answer was "II is an inorder sequence of some BST where 121 is the root and 52 is a leaf".

II is 52, 97, 121, 195, 242, 381, 472, which is strictly increasing, so it is a valid inorder of some search tree. Any key in the list may be the root: the keys before it become the left subtree and must all be smaller, and the keys after it become the right subtree and must all be larger. Taking 121 as the root splits the list into 52, 97 on the left and 195, 242, 381, 472 on the right, and both parts are increasing, so such a tree exists.

The first key of an inorder list is the leftmost node of the tree. A leftmost node has no left child, and it cannot have a right child either — a right child would be visited after it and would be smaller than everything else, contradicting the order — so it is a leaf. Hence 52 is a leaf.

Why the others fail. I is not increasing, so it is not an inorder. I begins with 81, so it cannot be a preorder with root 439. IV ends with 270, so it cannot be a postorder with root 149 — a postorder ends with its root.

GATE CSE 2016 Set 2 — height of a search tree with 15 nodes

With the convention that a single node has height 0, the minimum is 3 and the maximum is 14.

Maximum: insert in sorted order and every node has one child, giving a chain of 15 nodes and 14 edges. Minimum: a perfect tree of height 3 holds 24 − 1 = 15 nodes exactly, so the bound h ≥ ⌈log2(16)⌉ − 1 = 3 is attained.

Derivation For n = 7 the page enumerates all 5040 insertion orders and finds the smallest height to be 2 and the largest 6, matching ⌊log2 7⌋ and n − 1.

GATE CSE 2015 — the element at the lowest level

Inserting 71, 65, 84, 69, 67, 83 into an empty search tree gives 71 as the root, 65 and 84 as its children, 69 under 65 and 83 under 84, and 67 under 69. The lowest element is 67, at depth 3.

Each insertion is a failing search, so the trace is forced: 65 < 71 goes left; 84 > 71 goes right; 69 > 65 goes right of 65; 67 < 71, > 65, < 69, so left of 69; 83 < 84, so left of 84.

The height of the resulting tree is 3, and the page computes both the tree and its lowest node.

GATE CSE 2024 Set 1 — heapifying a real array

The paper gave the array 82, 101, 90, 11, 111, 75, 33, 131, 44, 93 and asked which option shows the first three elements after heapification. The paper's option list is not reproduced here; what is worth doing is the trace.

Ten elements, so the last internal node is at index 4 (the parent of index 9). Sifting down from index 4 back to 0 gives 11, 44, 33, 82, 93, 75, 90, 131, 101, 111 as a min-heap, using six swaps.

Derivation The page performs the build and checks the result against the heap promise at every parent, so the sequence above is computed, not recalled.

GATE CSE 2024 Set 1 — how many indices can hold the maximum?

A binary min-heap holds 105 distinct elements in an array indexed from 1. The number of possible values of the index of the maximum element is 53.

The maximum must be a leaf: if it had a child, that child would have to be at least as large, contradicting distinctness. With 105 elements indexed from 1, the leaves are the indices from ⌊105/2⌋ + 1 = 53 to 105, which is 53 positions.

The trap. Answering 52 counts the internal nodes instead of the leaves, and answering 105 forgets that the maximum cannot be internal.

The empty tree

The empty tree is a binary tree, has height −1 under the edge convention (and 0 if you count nodes), and has one shape. That is why the Catalan list starts at T(0) = 1 and not at T(1) = 1.

An empty search tree and a one-node tree are different states, and a deletion routine that treats them alike usually crashes on one of them. Test for null before touching the root's children.

A heap of one element, and of two

A one-element heap has one leaf, which is also the root, and the maximum is at index 1. A two-element heap indexed from 1 has leaves at indices 2 and 2 — only one leaf — so the maximum is at index 2 with certainty.

The leaf formula ⌊n/2⌋ + 1 to n must therefore be read as "the leaves", not "a proper subset of the leaves": at n = 2 the range has a single member.

Duplicate keys

The search promise as stated needs distinct keys. With duplicates you must choose a rule — reject, or send equal keys always left or always right — and the rule changes the shape, the inorder list (which becomes non-decreasing rather than increasing) and the count of distinct trees.

GATE states "distinct" when it matters. If it does not, say which rule you are assuming rather than answering as though the keys were distinct.

One child: left or right?

A node with a single child has either a left child or a right child, and those are different trees. This is why preorder plus postorder cannot rebuild a tree: the two-node trees "root 1 with left child 2" and "root 1 with right child 2" have different preorders (1,2 and 1,2 — the same!) and different postorders (2,1 and 2,1 — also the same).

Both traversals are identical and the trees differ, so no algorithm can tell them apart from that pair alone.

Base index 0 against base index 1

Indexed from 0: children 2i+1, 2i+2; parent ⌊(i−1)/2⌋; leaves from ⌊n/2⌋ to n−1. Indexed from 1: children 2i, 2i+1; parent ⌊i/2⌋; leaves from ⌊n/2⌋+1 to n.

Both appear in real GATE questions, and the question always states which. Convert once, at the start, and write the base down next to your working.

Deleting the root

In a search tree with two children the root is replaced by its inorder successor, and the tree keeps its promise. In a heap the root is replaced by the last leaf, and the array shrinks by one.

The two routines are not interchangeable: the search tree must preserve the inorder order, and the heap must preserve the complete shape. Swapping them breaks the structure each is meant to protect.

Misconception 1 — "a search tree searches in log n"

What is true. A search costs the height, and the height of a search tree with n nodes is between ⌊log2 n⌋ and n − 1.

What the promise gives. Nothing about balance. Insert 1, 2, ..., n in order and the tree is a chain, so every search is a walk.

The repair. Answer "log n" only when the question says balanced, AVL, red-black, or complete. Otherwise the answer is "the height", and worst case is n.

Misconception 2 — "checking each parent against its child tests the promise"

What is true. The promise quantifies over whole subtrees, so a key must be inside the range its ancestors allow.

The counterexample. Root 10, left child 5, right child of 5 is 12. Every parent-child pair is ordered correctly, and 12 is in the left subtree of 10, so a search for 12 never finds it.

The repair. Carry a lower and an upper bound down the recursion, or simply check that the inorder list is increasing — which is necessary and, for a tree, also sufficient.

Misconception 3 — "a heap is a sorted array"

What is true. A heap guarantees one comparison per edge: every parent is no larger than its children. It says nothing about siblings.

The counterexample. 1, 3, 2, 7, 4 is a valid min-heap and is not sorted; its inorder walk is 7, 3, 4, 1, 2, which is not increasing.

The repair. A heap gives you the minimum, and gives it in constant time. Everything else costs a scan. That is exactly the trade heapsort exploits.

Misconception 4 — "full, complete and perfect mean the same thing"

Full is about children: 0 or 2. Complete is about filling: every level full except possibly the last, left to right. Perfect is both, and has exactly 2h+1 − 1 nodes.

Two witnesses. The perfect tree of height 2 is full, complete and perfect. A tree where one node at depth 1 has two children and its sibling has none is full and not complete. A complete tree whose last level holds a single node is complete and not full.

The repair. When a question says "complete", it is handing you array indexing and a logarithmic height. When it says "full", it is handing you n0 = n2 + 1.

Misconception 5 — "the number of search trees on n keys is n!"

What is true. There are n! insertion orders and only Cn trees, because many orders give the same tree.

The numbers. 3 keys: 6 orders, 5 trees. 4 keys: 24 orders, 14 trees. 5 keys: 120 orders, 42 trees.

The repair. Count shapes. Fix the shape and there is exactly one way to fill it with sorted keys, which is why the two counts agree.

Misconception 6 — "building a heap costs n log n because there are n insertions"

What is true. Inserting n keys one at a time does cost n log n. The bottom-up build does not insert: it sifts down half the nodes, most of them near the bottom, and the level sum is at most 2n.

The witness. A perfect tree on 15 nodes: 8 leaves move 0 levels, 4 nodes move at most 1, 2 move at most 2, 1 moves at most 3. Total at most 0+4+4+3 = 11, well under 2n = 30.

The repair. Quote the sum over levels, not a per-node worst case. The per-node bound log n is correct and useless here.

Misconception 7 — "the maximum of a min-heap could be anywhere"

What is true. The maximum must be a leaf, because any internal node has a child at least as large, and with distinct keys strictly larger.

What follows. In an n-key heap indexed from 1 the maximum sits somewhere in ⌊n/2⌋+1 to n. That is the count GATE 2024 Set 1 asked for.

The repair. "Anywhere" is too weak and "at the last index" is too strong. It is in the leaves, and finding it still costs a scan of the leaves.

Misconception 8 — "the successor of a node is its right child"

What is true. The successor is the next key in inorder: the leftmost node of the right subtree, or, when there is no right subtree, the lowest ancestor for which the node lies in the left subtree.

Witness. In the tree with root 10 and right child 12 where 12 has a left child 11, the successor of 10 is 11, not 12.

The repair. The successor is defined by the sorted order, not by a pointer. Find it by the inorder position.

Pattern 1 — one traversal in, another out

The shape. You are given one traversal of a search tree and asked for another.

The method. A search tree's inorder is the sorted keys. So you already have two lists: the one given and the sorted one. Rebuild by taking the root from the front of the preorder (or the back of the postorder) and splitting the inorder at it.

The check. Your rebuilt tree's inorder must be increasing and its other traversal must match the given list. Both are cheap to verify by hand.

Pattern 2 — is this sequence possible?

The shape. Could this be a search path, a preorder, an inorder, a heap array?

The method. For a search path, carry bounds. For an inorder, test sortedness. For a preorder, rebuild and compare. For a heap array, test every parent against its children.

The check. One counterexample settles it. Find the first position where the promise breaks and name the pair.

Pattern 3 — count the structures

The shape. How many trees, how many orders, how many indices, how many ways to fill.

The method. Split at the root for trees (Catalan). Use rank for indices (leaves are the last ⌈n/2⌉). Use 2k for orders that produce a chain. Use 1 when the shape and the keys are both fixed.

The check. Compute the small case by hand. For 3 keys the answer is 5, and that anchors every larger case.

Pattern 4 — cost from the height

The shape. The complexity of a search, an insertion, a deletion, a build.

The method. For a search tree, the cost is the height, and the height is only guaranteed logarithmic when the question says balanced or complete. For a heap, the height is guaranteed logarithmic because the shape is complete.

The check. Ask what the worst input is. For a search tree it is the sorted one, which gives n. For a heap there is no bad input, which is the point.

Traps that recur across years

The word "worst case". It turns log n into n for a search tree, and it turns "average" into a claim you must justify.

The word "distinct". It is what makes the maximum of a min-heap strictly a leaf, and what makes the count of trees Catalan.

The stated base index. Indexed from 0 or 1 changes every formula. Read it before writing arithmetic.

The stated height convention. "The height of a tree with a single node is 0" is a gift; without it, say which convention you used.

Closely confused pairs, side by side

Heap against sorted array. A heap gives the minimum in O(1) and a search in O(n). A sorted array gives a search in O(log n) and the minimum in O(1) but an insertion in O(n).

Search tree against heap. The search tree orders left against right; the heap orders parent against children and ignores left against right.

Height against depth. Depth is per node, measured from the root. Height is per tree (or per subtree), measured to the deepest leaf.

Complete against full. Complete is about where the last level ends; full is about how many children each node has.

What is not covered, and why

AVL, red-black and splay trees are class C for this lesson: balancing is not named in Section 4, and the search-tree property taught here is what they preserve. A separate lesson will cover rotations.

B and B+ trees are class A but belong to the database indexing unit, where they are taught with the same node-and-pointer reasoning at a higher branching factor. Fibonacci heaps and binomial heaps are class D for this exam.

MCQEasyOriginal GATE-style

A binary tree has 9 nodes, of which 4 have exactly one child. How many leaves does it have?

  1. 4
  2. 5
  3. 6
  4. Cannot be determined

Answer: C — 6

Use n0 = n2 + 1 and n0 + n1 + n2 = 9 with n1 = 4. Substituting n2 = n0 − 1 gives 2n0 + 3 = 9, so n0 = 6.

A is the number of two-child nodes plus one, read off the wrong variable. B forgets that the one-child nodes still consume nodes. D would be right for a general tree, not a binary one.

The page checks n0 = n2 + 1 by enumeration on every binary tree with up to 7 nodes, so the identity is not taken on trust.

NATEasyOriginal GATE-style

A min-heap holds 100 distinct keys in an array indexed from 0. At how many indices could the maximum key sit?

Answer: 50

Indexed from 0, the leaves are the indices from ⌊n/2⌋ to n − 1, which for n = 100 is 50 to 99: exactly 50 indices.

Common wrong answers. 51 counts the boundary twice. 100 forgets that the maximum cannot be internal. 49 uses ⌊n/2⌋ + 1, which is the base-1 formula.

The page computes the leaf range for both base indices and checks it against a direct scan of every parent-child pair.

MSQMediumOriginal GATE-style

A binary tree T with distinct keys is stored with left and right children. Which of these statements are TRUE?

  1. If every node's left child is smaller and right child is larger, T is a binary search tree.
  2. If the inorder traversal of T is increasing, T is a binary search tree.
  3. If T is a binary search tree, every key in the left subtree of a node is smaller than the key at that node.
  4. If T is a binary search tree, its postorder traversal is increasing.

Answer: B and C

B is true: an increasing inorder forces every key in a left subtree below its node and every key in a right subtree above it, which is the promise. C is the promise itself, stated for one node; it holds at every node of a search tree.

A is the parent-only trap. Root 10, left child 5, and 12 as the right child of 5: every parent-child pair is ordered correctly, and 12 sits in the left subtree of 10, so the tree is not a search tree.

D is false twice over: a postorder ends with the root, which is the median key, and the rest of the order is not increasing either.

MCQMediumOriginal GATE-style

How many distinct binary search trees can be built from the four keys 1, 2, 3, 4?

  1. 8
  2. 14
  3. 24
  4. 42

Answer: B — 14

C4 = (1/5)·C(8,4) = 70/5 = 14. By the root split: T(0)T(3) + T(1)T(2) + T(2)T(1) + T(3)T(0) = 5+2+2+5 = 14.

C is 4!, the number of insertion orders, which overcounts because different orders give the same tree. D is C5, the count for five keys. A is 23, the count for a different question entirely.

This is GATE CSE 2005 in substance; the option list here is reconstructed, so it is labelled original practice rather than a reproduction.

NATMediumOriginal GATE-style

The keys 40, 20, 60, 10, 30, 50, 70 are inserted into an empty binary search tree in that order. What is the height of the resulting tree, with the height of a single node taken as 0?

Answer: 2

40 is the root; 20 and 60 are its children; 10, 30 go under 20 and 50, 70 under 60. That is a perfect tree of height 2 with 7 nodes.

Common wrong answer: 3. That counts the levels (three of them) rather than the edges. The convention in the question decides, and it said edges.

MCQHardOriginal GATE-style

Which one of these arrays, indexed from 0, is a valid min-heap?

  1. 2, 1, 3, 4, 5, 6
  2. 1, 4, 3, 2, 5, 6
  3. 3, 1, 2, 4, 5, 6
  4. 1, 3, 2, 4, 6, 5

Answer: D — 1, 3, 2, 4, 6, 5

Test every index that has a child. In D: 1 ≤ 3 and 1 ≤ 2; 3 ≤ 4 and 3 ≤ 6; 2 ≤ 5. Every parent is no larger than both children, so D is a min-heap.

A fails at the root: 2 > 1. B fails at index 1: 4 has children 2 and 5, and 4 > 2. C fails at the root: 3 > 1.

Note what is not required: the array need not be sorted, and siblings need not be in order. D has 3 > 2 at indices 1 and 2 and is still a heap, which is the whole difference between the heap promise and the search promise.

MCQHardOriginal GATE-style

A binary search tree T is built by inserting the keys 50, 30, 70, 20, 40, 60, 80. The key 50 is then deleted by the successor rule. Which key now sits at the root?

  1. 30
  2. 40
  3. 60
  4. 70

Answer: C — 60

The inorder successor of 50 is the smallest key larger than 50, which is 60 (the leftmost node of the right subtree). It is copied into the root's position and removed from its old place, which had no left child.

B is the predecessor's neighbour and belongs to the left subtree, so putting it at the root would place 40 above 30 and 20 and break the promise. A is the root of the left subtree. D is the root of the right subtree, which is larger than the successor.

The page deletes every key of several trees by the successor rule and re-checks the whole tree against the bounds test afterwards.

NATHardOriginal GATE-style

A max-heap is built from the 7 keys 1 to 7 by the bottom-up build. What is the maximum number of swaps any single sift-down performs during the build?

Answer: 1

A perfect tree on 7 nodes has height 2. The bottom-up build starts at index 2 (0-based), the last internal node. The nodes at height 1 can move at most one level, and the root can move at most two — but with 7 distinct keys the root of the built heap is the maximum, which ends at the root, so it moves 0 times here. The deepest single sift is 1.

Careful. The bound per node is the node's height, so the worst single sift in a general 7-node array can be 2. This question asks about the build of 1..7 in a max-heap, where the answer is 1; read what the question fixes.

The page runs the build on every permutation of 1..7 and reports the largest single sift it observes.

MCQHardOriginal GATE-style

A max-heap H holds 15 distinct keys in an array indexed from 0. Which of the following is TRUE?

  1. The largest key is at index 0, and the second largest is at index 1 or index 2.
  2. The largest key is at index 14.
  3. The inorder traversal of H is decreasing.
  4. Searching H for an arbitrary key costs O(log n).

Answer: A

In a max-heap the root is the largest key. Every other key is a descendant of the root, and the children of the root are indices 1 and 2, so the second largest must be one of them: it is larger than everything below it, and everything below it is below one of those two.

B confuses the heap with a sorted array. Index 14 is a leaf, so it holds one of the smaller keys. C confuses inorder with the heap promise: the inorder walk of 3, 1, 2 is 1, 3, 2. D is the search-tree promise, which a heap does not make; finding an arbitrary key costs O(n).

The page checks the second-largest claim by constructing heaps from many permutations and confirming that the runner-up always lands at index 1 or 2.

Revision sheet — definitions and formulas

Depth of a node: edges from the root; root is 0.
Height of a tree: largest depth; single node is 0.
Full: every node has 0 or 2 children.
Complete: all levels full but possibly the last, which fills left to right.
Perfect: 2h+1 − 1 nodes, all levels full.

Leaves identity: n0 = n2 + 1.
Node bound: height h holds at most 2h+1 − 1 nodes.
Shape count: Cn = (1/(n+1))·C(2n, n), with C0 = 1.
Search trees on n distinct keys: also Cn.

Traversals: pre (root, L, R), in (L, root, R), post (L, R, root), level (by depth, left to right).
Inorder of a search tree: sorted.
Rebuild from: (pre, in) or (post, in); never (pre, post) alone.

Heap, base 0: children 2i+1, 2i+2; parent ⌊(i−1)/2⌋; leaves ⌊n/2⌋ … n−1.
Heap, base 1: children 2i, 2i+1; parent ⌊i/2⌋; leaves ⌊n/2⌋+1 … n.
Heap height: ⌊log2 n⌋.
Build: O(n). Insert / remove-min: O(log n). Heapsort: O(n log n), in place, not stable.

The five decision procedures

  1. Is this tree a search tree? Walk down with a lower and an upper bound, or check that the inorder list is increasing.
  2. Could this be a search path? Carry bounds; each left turn lowers the upper bound, each right turn raises the lower bound.
  3. Rebuild a tree. Root from the front of the preorder or the back of the postorder, split the inorder at it, recurse on the two parts.
  4. Is this array a heap? For every index i with children, test parent against both children. Nothing else is needed.
  5. Which index can hold the extreme? The minimum is index 0 (or 1). The maximum is somewhere in the leaf range.

Six traps, in the order they cost marks

  1. Answering log n for an unbalanced search tree.
  2. Validating a search tree parent by parent.
  3. Calling a heap array sorted, or binary-searching a heap.
  4. Using n! where Catalan is needed.
  5. Mixing base-0 and base-1 heap indices.
  6. Counting levels where the question asked for edges.
