Topic and objective

TOPIC: Sorting algorithms and the comparison lower bound — what a sort must promise, the quadratic family, the n log n wall and why it exists, merge sort, quicksort, heapsort, counting and radix sort, stability, and in-place behaviour.

LEARNING OBJECTIVE: Given a sorting algorithm, an input arrangement and a question about comparisons, time, extra memory or stability, produce the right number and say which case it belongs to. Given a claim that sorting cannot beat n log n, say whether it is true of comparison sorts, of all sorts, or of neither. Given a new algorithm, place it in the master table from its structure rather than from memory.

I read this topic as two skills: counting what an algorithm does on a named input, and knowing which of five different questions a problem is asking. Searching by comparison already has its own lesson (Binary Search and Its Variants), and hashing is the third word of the same syllabus line but is a separate lesson — this one is sorting only.

GATE relevance

Verified fact Class A — explicitly in the syllabus.

Section 5 of the official GATE 2027 CS syllabus (IIT Madras, CS_GATE2027_Syllabus.pdf) opens with: "Searching, sorting, hashing." Sorting is the second of the three words, and it is the first sentence of the Algorithms section.

Section 4 (Programming and Data Structures) also names "binary heaps", which is where heapsort comes from, and Section 5's next sentence — "Asymptotic worst case time and space complexity" — is the language every sorting question is phrased in.

Class A means a question here is inside the declared boundary. It does not mean one is guaranteed in GATE 2027, and it says nothing about marks. The previous-year questions quoted in this lesson are observations about old papers, not a forecast.

Prerequisites

Five published lessons carry the machinery this one uses:

  • Asymptotic Complexity and Recurrences — the five notations, the growth ladder, and the master theorem with its gap. Scene 4's n log n and scene 6's build cost are applications of it.
  • Trees, Binary Search Trees and Heaps — the complete-tree shape, the array indices 2i+1 and 2i+2, and sift-up and sift-down. Heapsort is that heap, emptied.
  • Recurrence Relations — T(n) = 2T(n/2) + n solved, which is merge sort's cost.
  • Arrays, Stacks and Queues — index arithmetic, in-place swapping, and why a stack of recursive calls is memory.
  • Counting and Combinatorics — n! and the logarithm of a product, which is the whole of the lower-bound argument.

The only extra mathematics is one fact: log₂(n!) grows like n log₂ n. If that is unfamiliar, scene 3 derives it and the page checks it numerically.

What you should be able to do afterwards

Answer any sorting question in this order: what is being counted?, which input arrangement?, which implementation?, is it a comparison sort?

The most expensive mistake in this topic is answering a comparisons question with a time-complexity table. Selection sort makes n(n−1)/2 comparisons on every input and Theta(n²) time on every input — those agree. Insertion sort makes n−1 comparisons on a sorted input, which is linear, and still has a quadratic worst case. One algorithm, several true statements, and the question picks one.

Level 1 — Intuition: sorting a hand of cards

You already know insertion sort. You are dealt cards one at a time. You hold the cards in your left hand in order and slide each new card into place from the right end. If the new card is the largest so far, you look at one card and stop. If it is the smallest, you slide past all of them.

And you already know the wall. Suppose you may only learn a card's rank by comparing two cards. Then every question you ask is a yes-or-no answer, and after k questions you can distinguish at most 2k different hands. There are n! possible hands, so you need 2k ≥ n!, that is k ≥ log₂(n!). That is the entire lower bound, and you can derive it at a card table.

Educational interpretation The card picture is exact for comparison sorting and misleading for counting sort, where you glance at the card's printed value without comparing it to anything. That distinction is the point of scene 7.

Level 2 — The formal specification of a sort

Let the input be a sequence a[0..n-1] of keys drawn from a set with a total order ≤. A sorting algorithm returns a sequence b[0..n-1] such that both of these hold:

b is a permutation of a there is a bijection from the positions of a to the positions of b that preserves the key — the multiset of keys is unchanged
b[0] ≤ b[1] ≤ … ≤ b[n-1] every neighbouring pair in the output is in order — for a total order this is equivalent to "every pair is in order"

Two further properties are defined only because questions ask about them:

stable if two input records have equal keys, their relative order in the output is the same as in the input
in place the algorithm uses O(1) auxiliary cells — cells beyond the input array — so the extra memory does not grow with n

Note what "in place" does not say: it says nothing about the recursion stack. Quicksort is called in place and still uses O(log n) stack in the good case, O(n) in the bad one. Say which memory you mean.

Level 3 — Visual understanding: the decision tree

Take three distinct keys a, b, c. Any comparison sort starts by asking one question, say "is a < b?". Depending on the answer it asks a second question, and so on until it knows the order. Draw a dot for each question and a branch for each answer:

  • the root is the first comparison;
  • each internal node is a comparison, and has exactly two children, because a comparison has two answers;
  • each leaf is a stopping point, and the algorithm prints one permutation there.

A binary tree of height h has at most 2h leaves. There are 3! = 6 orders of three keys, and the algorithm must print a different one at each leaf, so it needs at least 6 leaves. Since 2² = 4 < 6 ≤ 8 = 2³, the height is at least 3. So no comparison sort can order three keys in two comparisons in the worst case, and the page draws exactly that tree.

For n = 8 the same count gives 8! = 40320 > 2¹⁵ = 32768, so at least 16 comparisons are needed. Merge sort's worst case at n = 8 is exactly 17, which the page confirms by trying all 40320 inputs.

Level 5 — Boundaries: where the wall stops applying

The lower bound log₂(n!) is a theorem about a class of algorithms, and it has three hypotheses. Drop any one and the conclusion fails:

  • Only comparisons. The algorithm learns about keys solely from the outcomes of a[i] < a[j]. Counting sort reads a key as an array index, so it is outside the class.
  • Distinct keys. The count is n! only when all keys differ. With many duplicates there are fewer possible outputs and a comparison sort can finish sooner on that input.
  • A worst-case statement. The bound says some input needs that many comparisons. It does not say every input does: on a sorted input insertion sort uses n − 1.

So the correct sentence is: every comparison sort needs Ω(n log n) comparisons in the worst case. The incorrect sentence — sorting cannot be done in less than n log n time — is false, and counting sort on a small range is the counterexample.

Level 4 — Worked example: counting every comparison at n = 8

The page implements all eight algorithms and counts comparisons rather than quoting a table. For n = 8:

  • Selection sort — 28 comparisons on a sorted input, 28 on a reversed one, 28 on a random one. The count is n(n−1)/2 = 28 and depends on n alone.
  • Insertion sort — 7 on a sorted input (one per new key, each stopping immediately), 28 on a reversed one, in between otherwise.
  • Bubble sort with the early exit — 7 on sorted, 28 on reversed. Without the exit, 28 on both, because the pass runs to the end regardless.
  • Merge sort — 12 on a sorted input, 17 on the worst input. Both are found by enumerating all 40320 inputs.
  • Quicksort, last element as pivot — 28 on a sorted input, which is the worst case; the best over all 720 inputs at n = 6 is 8 and the worst is 15.

Read the table by column, not by row: "which algorithm is cheapest on a sorted input" has one answer, "which is cheapest in the worst case" has another.

Level 4 — Worked example: one merge, step by step

Merge L = [7, 10] and R = [8, 19]. Two pointers start at the fronts.

  1. Compare 7 with 8. 7 is smaller, so emit 7 and advance L. Comparisons so far: 1.
  2. Compare 10 with 8. 8 is smaller, so emit 8 and advance R. Comparisons: 2.
  3. Compare 10 with 19. 10 is smaller, so emit 10 and advance L. Comparisons: 3. L is now empty.
  4. The loop ends because one side is exhausted. Append the rest of R: 19. No comparison is spent on it.

Output [7, 8, 10, 19] in 3 comparisons for 4 keys — which is n − 1, the maximum. If instead L had been [7, 10] and R [8, 9], the last element would still cost no comparison, so the count would be 3 again. If one list is entirely below the other, the count is exactly the length of the shorter list, which is the minimum.

Merging lists of sizes 5 and 7 therefore costs at least 5 and at most 11 comparisons. Questions that ask for a minimum and a maximum of a merge are asking for these two numbers.

Level 4 — Worked example: the sorted input, three algorithms

Input [23, 32, 45, 69, 72, 73, 89, 97], already ascending. This is GATE CSE 2021 Set 1, question 9, and the page reproduces the four counts:

  • Insertion sort — 7 comparisons. Each new key is compared once with its left neighbour and stops.
  • Selection sort — 28 comparisons. The scan of the tail is unconditional.
  • Quicksort, last element as pivot — 28 comparisons. Every pivot is the current maximum, so every split is one-sided.
  • Merge sort — 12 comparisons. It never looks at whether the input was ordered.

The answer is insertion sort. The same four algorithms on the reverse of this array would give insertion 28, selection 28, quicksort 28, merge 12 — a different winner, from the same code.

Level 6 — A counterexample to a tempting rule

The tempting rule: "an algorithm with a better worst case is never worse on a particular input."

Counterexample: on the sorted array above, merge sort — worst case Theta(n log n), the best worst case of the four — spends 12 comparisons while insertion sort — worst case Theta(n²) — spends 7. The algorithm with the better guarantee loses on this input, by nearly a factor of two.

Why: a worst-case bound is a statement about the worst input, not about every input. Merge sort's 12 comparisons on this input are consistent with its worst-case bound of n⌈log₂n⌉ − 2^⌈log₂n⌉ + 1 = 17; the bound is an upper limit, not a prediction.

This is why "which algorithm uses the fewest comparisons on this array" and "which has the best worst case" are different questions with different answers, and why a GATE option can be true in one reading and false in the other.

Level 9 — Consolidation: the four numbers to keep

Everything in this topic is one of four quantities, and they are all different:

  • comparisons — a count of a[i] < a[j] evaluations. This is what the lower bound is about.
  • swaps or moves — a count of writes. Selection sort is the winner here with at most n − 1.
  • running time — an order of growth, which usually matches the comparison count but not always: a comparison sort's count and its time can differ by a log factor in some models.
  • auxiliary space — cells beyond the input, not counting the stack unless the question says so.

Name the quantity before you answer. Four of the five most common lost marks in this topic come from naming the wrong one.

Speed

Example 1 — Merge sort, scaled (GATE CSE 2015 Set 3)

"A mergesort algorithm in the worst case takes 30 seconds for an input of size 64. Which of the following most closely approximates the maximum input size of a problem that can be solved in 6 minutes?" Options: 256, 512, 1024, 2048.

Merge sort's worst case is proportional to n log₂ n, so write 30 = c · 64 · 6, giving c = 30/384. Six minutes is 360 seconds, so we need n log₂ n = 360/c = 360 · 384/30 = 4608.

Now test the options: 512 · log₂512 = 512 · 9 = 4608 exactly. So the answer is 512.

Mathematical derivation The page checks that 512 is not merely closest but exact, and that 256 · 8 = 2048 and 1024 · 10 = 10240 fall far from 4608 on either side. The method assumes the same constant c at both sizes, which is what "most closely approximates" licenses.

Example 2 — Optimal merging (GATE CSE 2014 Set 2)

"Suppose P, Q, R, S, T are sorted sequences having lengths 20, 24, 30, 35, 50. They are to be merged into a single sequence by merging together two sequences at a time. The number of comparisons needed in the worst case by the optimal algorithm is ______."

One merge of two sorted lists of sizes m and n costs at most m + n − 1 comparisons. To minimise the total, always merge the two shortest remaining runs — this is the Huffman argument, and an exchange argument shows it is optimal.

  • 20 + 24 → 44, costing 43 comparisons. Runs now 30, 35, 44, 50.
  • 30 + 35 → 65, costing 64. Runs now 44, 50, 65.
  • 44 + 50 → 94, costing 93. Runs now 65, 94.
  • 65 + 94 → 159, costing 158.

Total 43 + 64 + 93 + 158 = 358. Mathematical derivation The page recomputes this by simulation, and the arithmetic is the check: the answer is 358, not the 357 you get if you charge m + n instead of m + n − 1 for one of the merges.

Example 3 — One partition, written out

Partition [3, 1, 4, 1, 5, 9, 2, 6] using the last element 6 as the pivot, Lomuto style: keep an index i at the boundary of the "smaller" region and scan j from left to right.

  • j=0, 3 ≤ 6 → swap into position i=0 (no movement), i becomes 1.
  • j=1, 1 ≤ 6 → swap into i=1 (no movement), i becomes 2.
  • j=2, 4 ≤ 6 → swap into i=2, i becomes 3.
  • j=3, 1 ≤ 6 → swap 1 into i=3, giving [3,1,4,1,5,9,2,6] with the 1 from position 3 moved to 3 (self-swap), i becomes 4.
  • j=4, 5 ≤ 6 → self-swap at i=4, i becomes 5.
  • j=5, 9 > 6 → skip.
  • j=6, 2 ≤ 6 → swap position 6 (value 2) into i=5 (value 9): [3,1,4,1,5,2,9,6], i becomes 6.
  • Finally swap the pivot at position 7 into i=6: [3,1,4,1,5,2,6,9].

The pivot 6 is now at index 6, everything to its left is ≤ 6 and everything to its right is > 6. Seven comparisons were made, one per non-pivot element — that is always n − 1 for a partition of n elements.

Example 4 — Counting sort on a small range

Sort [3, 1, 2, 3, 1, 2], keys in the range 1 to 3, so k = 3.

  • Count: three counters, one per value: value 1 appears 2 times, value 2 appears 2 times, value 3 appears 2 times.
  • Running totals: 2, 4, 6. A running total says how many keys are ≤ that value, so it gives the last position of that value in the output.
  • Place from the right: the last key is 2; its running total is 4, so it goes at index 3 and the total drops to 3. Next key 1 goes at index 1, total 2 → 1. Next 3 at index 5, total 6 → 5. Then 2 at index 2, 1 at index 0, 3 at index 4.

Output [1, 1, 2, 2, 3, 3], and the two 1s kept their original order because we placed from the right. Placing from the left would give the same sorted array but reverse the ties, breaking stability. Cost: n + k = 6 + 3 = 9 cells of work, against log₂(6!) ≈ 9.5 comparisons for the best possible comparison sort at this size.

Example 5 — The GATE 2026 merge-sort item, worked

"Consider an array A = [10, 7, 8, 19, 41, 35, 25, 31]. Suppose the merge sort algorithm is executed on A to sort it in increasing order. The merge sort algorithm will carry out a total of 7 merge operations. A merge operation on sorted left array L and sorted right array R is said to be void if the output of the merge operation is the elements of array L followed by the elements of array R. The number of void merge operations among these 7 merge operations is ______."

Split at the middle: [10,7,8,19] and [41,35,25,31]. Then each half splits again. The seven merges, in the order the recursion performs them:

  • [10] with [7] → 7, 10. Output is R then L, so not void.
  • [8] with [19] → 8, 19. Output is L then R, so void.
  • [7,10] with [8,19] → 7, 8, 10, 19. Interleaved, not void.
  • [41] with [35] → 35, 41. Output is R then L, not void.
  • [25] with [31] → 25, 31. Output is L then R, void.
  • [35,41] with [25,31] → 25, 31, 35, 41. All of R then all of L, not void — the definition names L first.
  • [7,8,10,19] with [25,31,35,41] → 7, 8, 10, 19, 25, 31, 35, 41. All of L then all of R, void.

Mathematical derivation Three void merges. The page computes this by running merge sort on the array and testing each merge's output against the definition, and it reports 7 merges and 3 void ones. Unverified The official answer key for this 2026 item was not consulted; the number above is computed here from the statement as quoted, not copied from a key.

Example 6 — Radix sort's three passes

Sort [170, 45, 75, 90, 802, 24, 2, 66] in base 10. The largest key is 802, which has three digits, so there are three passes.

  • Pass 1, units digit: buckets by 0, 5, 5, 0, 2, 4, 2, 6 → 170, 90, 802, 2, 24, 45, 75, 66.
  • Pass 2, tens digit: reading that order, bucket by 7, 9, 0, 0, 2, 4, 7, 6 → 802, 2, 24, 45, 66, 170, 75, 90.
  • Pass 3, hundreds digit: bucket by 8, 0, 0, 0, 0, 1, 0, 0 → 2, 24, 45, 66, 75, 90, 170, 802.

The page runs exactly this and reports three passes and the sorted result. Note the base: "three passes" comes from three decimal digits, so a question about base 10 and keys below 1000 has three passes, not thirty. Reading the radix as 2 would give ten passes for the same data.

Example 7 — Where stability is the whole point

A hostel list has records (name, marks). You want it ordered by marks, and inside equal marks ordered by name.

The stable route: sort by name first, then sort by marks with a stable sort. The second sort never separates two equal marks that the first sort put in name order, so the result is exactly what you want. Two passes, no comparison function that knows about both fields.

The unstable route: the same two passes with heapsort as the second sort. Inside equal marks the names come back in whatever order heapsort's sift-down happened to leave them — sorted by nothing in particular.

Mathematical derivation The page demonstrates this on twelve tagged records: insertion, merge, counting and radix sort keep the tags of equal keys increasing, while selection sort, quicksort with the last pivot and heapsort do not. That is measured by running each algorithm on records that carry their original index, not asserted from a table.

Example 8 — Reading the master table off a structure

Given an unfamiliar algorithm, place it without memorising: find where the work happens and what it depends on.

  • Split by position, work after the recursion → the cost is the same for every input, so best = average = worst, and the merge needs a second array. That is merge sort's row.
  • Split by value, work before the recursion → the cost depends on how the values fall, so the worst case is quadratic and the average is not. That is quicksort's row.
  • Repeatedly extract the extreme from a heap → n extractions of log n each, all inside the array, and equal keys get rearranged. That is heapsort's row.
  • Read the key as an index → no comparisons, so the lower bound does not apply; the cost is n plus the range or the digit count. That is counting and radix sort.

This is why the table has only seven rows that matter: the rest of the sorting literature is variations on these four structures.

Edge case 1 — n = 0 and n = 1

An empty array and a one-element array are already sorted, and every algorithm must return them unchanged with zero comparisons. Every implementation in this lesson is checked on both.

Where this bites: mergeSort([]) with a midpoint computed as len/2 recurses on two empty halves and must terminate. And quickSortLast([x]) must not partition at all, because lo >= hi already. A question that says "at least one comparison is always needed" is false at n ≤ 1.

Edge case 2 — all keys equal

Input [5, 5, 5, 5]. Insertion sort makes 3 comparisons and no moves. Selection sort makes 6 comparisons. Quicksort with the last pivot makes 6 comparisons and recurses on a side of size 3 — the quadratic worst case again, on an input that is already sorted in the weakest possible sense.

This is the input that shows why a three-way partition (smaller / equal / larger) exists: with many duplicates, a two-way partition puts all the equal keys on one side and gains nothing. The page checks the all-equal input against all eight algorithms.

Edge case 3 — a sorted input is the best case for one algorithm and the worst for another

At n = 32, a sorted input costs insertion sort 31 comparisons and quicksort with the last pivot 496. Both numbers are computed by the page, and 496 = 32 · 31/2.

So the phrase "best case" is meaningless without naming the algorithm, and "on a sorted input" is not a hint that the answer is small. In an exam, first identify which algorithm the option names, then decide what that input does to it.

Edge case 4 — the middle element as pivot is not the median

"Choose the central element" chooses a position. The organ-pipe input — 1, 3, 5, … rising to the middle, then the even numbers falling back — defeats it, costing exactly n²/4 comparisons. The page checks that exact value at n = 24, 48, 96, 192 and 384, and that the ratio to n log₂ n climbs 1.31, 2.15, 3.64, 6.33, 11.18 and never settles.

This is GATE CSE 2014 Set 3's question: with the central element as pivot, the tightest upper bound for the worst case is O(n²), not O(n log n). Any fixed-position rule has an adversarial input, because the adversary knows the rule. Only a random pivot or a true median-finding pivot avoids it.

Edge case 5 — counting sort when the range is huge

Counting sort is O(n + k) where k is the number of distinct possible key values. Sort ten 32-bit integers with it and k is about 4 · 10⁹, so the counter table is four billion cells for ten keys. The "linear" sort is now far worse than anything quadratic.

So "counting sort is linear" always carries the assumption k = O(n). Without it the claim is false, and radix sort — which uses d passes over a small base instead of one pass over the whole range — is the version that survives.

Edge case 6 — merge sort on a nearly sorted input

Take a sorted array with one element moved. Merge sort does exactly the same work as on a random array: the split is by index, and the merge cannot tell that its inputs were almost ordered. At n = 8 it spends 12 to 17 comparisons whatever you hand it.

Insertion sort on the same input spends about 2n comparisons. This is the practical reason libraries use a hybrid — a fast quadratic sort on small or nearly ordered runs, and merge sort for the merge step — and it is the origin of the "adaptive" column in the table.

Misconception 1 — "sorting cannot be faster than n log n"

The belief: n log n is a lower bound on the sorting problem, so every sorting algorithm is at least that slow.

What is true: n log n is a lower bound on comparison sorting. Counting sort on n keys from a range of size O(n) runs in O(n), and the page measures it doing fewer operations than n log₂ n on 200 keys in a range of 100.

The correction: the bound's hypothesis is that the algorithm learns about keys only by comparing them. State the hypothesis before stating the bound. An exam option worded "sorting requires Ω(n log n) comparisons" is true; "sorting requires Ω(n log n) time" is false.

Misconception 2 — "quicksort is O(n log n)"

The belief: quicksort is the fast sort, so its complexity is n log n.

What is true: quicksort's average is Theta(n log n) and its worst case is Theta(n²). At n = 8 with the last element as pivot, a sorted input costs 28 comparisons, which is n(n−1)/2.

The correction: always attach a case. "Quicksort is Theta(n log n) on average, Theta(n²) in the worst case, and Theta(n log n) in the best case" is the complete statement. An option that gives only one of them is not wrong unless the case it names is wrong.

Misconception 3 — "a sorted input is the best case"

The belief: feeding a sort an already sorted array must be cheap.

What is true: it is the best case for insertion sort and for bubble sort with an early exit, and the worst case for quicksort with a first, last or middle fixed pivot. At n = 32 it is 31 comparisons against 496 on the same input.

The correction: "best case" is a property of an algorithm, not of an input. Ask what the algorithm does with the order, not what the order is.

Misconception 4 — "selection sort is the best quadratic sort because it is order-independent"

The belief: a running time that never varies is a virtue, so selection sort is the safest of the simple sorts.

What is true: selection sort's invariance is invariance at Theta(n²), and it makes n(n−1)/2 comparisons on every input including a sorted one. Insertion sort is never worse and is often much better: 7 comparisons against 28 at n = 8 on a sorted input, and the same 28 on a reversed one.

The correction: selection sort wins exactly one column — at most n − 1 swaps, the fewest of any of these algorithms. That is a real advantage when a write is expensive, and it is not the same as being fast.

Misconception 5 — "heapsort is just a heap with a sort bolted on, so it is O(n log n) with extra memory"

The belief: building a heap needs a second array, so heapsort is not in place.

What is true: a complete binary tree can be stored in the array itself, so heapsort needs no second array at all. The page measures it: after heapSortMutate the caller's own array is sorted and nothing was allocated, while merge sort's top-level merge of 32 keys holds 64 auxiliary cells.

The correction: heapsort is the only one of the three n log n sorts that is both guaranteed and in place. It pays with instability and with being non-adaptive — the same cost on a sorted input as on a random one.

Misconception 6 — "bubble sort is quadratic on a sorted input" (and why the key said so)

The belief: that statement is simply false, because bubble sort can stop early.

What is true: it depends on the implementation. With the early-exit flag, a sorted input costs n − 1 comparisons; without it, n(n−1)/2. The page checks both: 7 and 28 at n = 8.

The correction: GATE CSE 2016 Set 2 keyed "bubblesort runs in Theta(n²) on an ascending input" as true, which is the no-early-exit reading. This is not a mistake in the key; it is the key telling you which variant the paper means. When a question is variant-dependent, say which variant you used in your working — and expect the plain textbook loop.

Closely confused pair 1 — the decision tree and the recursion tree

Decision tree: nodes are comparisons, leaves are outputs, and the tree exists to prove a lower bound. It has at least n! leaves, its height is the number of comparisons, and it is a proof object — you never run it.

Recursion tree: nodes are subproblems, each level's total is a cost, and the tree exists to compute an upper bound. Merge sort's has n leaves and log₂ n + 1 levels, and you do run it.

Both are binary trees about sorting, and they answer opposite questions. If the question is "how few comparisons must any algorithm make", it is the decision tree; if it is "how many comparisons does this algorithm make", it is the recursion tree or a direct count.

Closely confused pair 2 — in place and stable

In place is about memory: O(1) auxiliary cells. Stable is about ties: equal keys keep their input order. They are independent, and the four combinations all occur:

  • in place and stable — insertion sort, bubble sort
  • in place and not stable — selection sort, heapsort, quicksort (Lomuto)
  • not in place and stable — merge sort, counting sort, radix sort
  • neither — a naive shuffle-then-insert variant; rare, and usually a bug

A question that offers "stable" and "in place" as two options in one MCQ is asking you to know the table, not to reason. Both properties are measured in this lesson rather than quoted, so the table is trustworthy.

Pattern 1 — the comparison count on a named input

"Which algorithm uses the least number of comparisons to sort this array?" The array is the whole question: read it first. If it is already sorted, the adaptive sort wins; if it is reversed, nothing wins and every count is n(n−1)/2.

Procedure: (1) note whether the input is sorted, reversed, all-equal or random; (2) write each option's count for that arrangement; (3) take the minimum. The counts you need are n−1 and n(n−1)/2 for the simple sorts, and 12 to 17 at n = 8 for merge sort.

Verified instance: GATE CSE 2021 Set 1, question 9 — array 23 32 45 69 72 73 89 97, answer insertion sort with 7 comparisons against 28, 28 and 12.

Pattern 2 — three worst cases in one line

"The worst case running times of Insertion sort, Merge sort and Quick sort, respectively, are:" This is a lookup, and the only trap is the order of the three names in the sentence.

Procedure: write the three rows of the master table in the order the question gives, then match. Insertion Theta(n²), merge Theta(n log n), quick Theta(n²).

Verified instance: GATE CSE 2016 Set 1, question 26 — the keyed option is Theta(n²), Theta(n log n), Theta(n²). The page reproduces the counts at n = 20: 190, 48, 190.

Pattern 3 — the probability a random pivot is bad

"An array of 25 distinct elements is to be sorted using quicksort. Assume the pivot is chosen uniformly at random. The probability that the pivot gets placed in the worst possible location in the first round is ______."

Procedure: the worst location is an end of the partitioned range, because then one side is empty. Among m remaining keys exactly 2 ranks give an end position, so the probability is 2/m. With m = 25 that is 0.08.

Verified instance: GATE CSE 2019, a one-mark NAT — answer 0.08. Note the word "distinct": with duplicates several ranks can tie and the count changes.

Pattern 4 — scaling a measured time

"Merge sort takes 30 seconds for n = 64. What is the largest n solvable in 6 minutes?"

Procedure: write the cost model n log₂ n, form the ratio of the two times, and solve for the new n. Never scale n linearly — a doubling of the time does not double n.

Verified instance: GATE CSE 2015 Set 3, question 40 — 30 s at 64 becomes 360 s at 512, because 64·6 = 384 and 512·9 = 4608 is exactly twelve times larger.

Pattern 5 — MSQ: which statements are true on a given input

"If the input is already in ascending order, which of the following are TRUE? I. Quicksort runs in Theta(n²) II. Bubblesort runs in Theta(n²) III. Mergesort runs in Theta(n) IV. Insertion sort runs in Theta(n)."

Procedure: evaluate each statement against the named input and the named algorithm, one at a time, and write T or F beside it before looking at the options. I is true (last-pivot quicksort), II is true for the plain loop, III is false (merge sort cannot be linear), IV is true.

Verified instance: GATE CSE 2016 Set 2, question 29 — the keyed answer is I and IV only. Statement II is the one that depends on the implementation, and the key's reading is the plain bubble sort without the early exit.

Pattern 6 — optimal merging of several sorted runs

"Sequences of lengths 20, 24, 30, 35, 50 are to be merged two at a time. The number of comparisons in the worst case by the optimal algorithm is ______."

Procedure: this is Huffman coding in disguise. Repeatedly merge the two shortest runs, and charge m + n − 1 comparisons for each merge of sizes m and n. Four merges for five runs.

Verified instance: GATE CSE 2014 Set 2, question 51 — answer 358, from 43 + 64 + 93 + 158. Merging the two longest first would cost more; the exchange argument that the greedy choice is optimal is the same one as for Huffman trees.

Pattern 7 — the tightest bound for a pivot rule

"You implement quicksort by always choosing the central element as pivot. The tightest upper bound for the worst case performance is:" with options O(n²), O(n log n), Theta(n log n), O(n³).

Procedure: ask whether an adversarial input exists. For any fixed position rule it does, and the organ-pipe input costs exactly n²/4. So the answer is O(n²), and the two n log n options are wrong because they claim more than is true.

Verified instance: GATE CSE 2014 Set 3, question 52 — answer O(n²). The page checks the n²/4 cost at five sizes and shows the ratio to n log₂ n climbing without bound, which is exactly what rules out O(n log n).

Pattern 8 — the "least dependent on the input" item, and why it is contested

"Of the following sorting algorithms, which has a running time that is least dependent on the initial ordering of the input?" with options merge sort, insertion sort, selection sort, quicksort.

What the published keys say: merge sort. What a literal reading says: selection sort also has an order-independent running time — Theta(n²) in every case — so two options satisfy the wording, and the key is choosing the one that is order-independent and efficient.

Community observation This exact item appears in solved-paper collections attributed to more than one year and more than one exam, and its ambiguity is discussed openly on question forums. It is included here as a reasoning exercise, not as a verified PYQ: the sources disagree on which paper it belongs to, so no year is claimed. If you meet it, answer merge sort and be ready to say why selection sort is excluded.

NATMediumPYQ — GATE CSE 2019

An array of 25 distinct elements is to be sorted using quicksort. Assume that the pivot element is chosen uniformly at random. The probability that the pivot element gets placed in the worst possible location in the first round of partitioning (rounded off to 2 decimal places) is ______.

Answer: 0.08

After a partition the pivot sits in its final position, and the two sides are split at that position. The split is worst when one side is empty, which happens only when the pivot is the smallest or the largest of the 25 keys — that is, when its rank is 1 or 25.

Two favourable ranks out of 25 equally likely ones gives 2/25 = 0.08.

The trap is answering 1/25: that is the chance of one particular end, and there are two ends. The word distinct is what makes the ranks well defined; with duplicate keys several pivots can produce an empty side and the probability rises.

MCQEasyPYQ — GATE CSE 2016 Set 1

The worst case running times of Insertion sort, Merge sort and Quick sort, respectively, are:

  1. Theta(n log n), Theta(n log n), Theta(n²)
  2. Theta(n²), Theta(n²), Theta(n log n)
  3. Theta(n²), Theta(n log n), Theta(n log n)
  4. Theta(n²), Theta(n log n), Theta(n²)

Answer: D — Theta(n²), Theta(n log n), Theta(n²)

Insertion sort's worst case is a reverse-sorted input, where every key travels to the front: n(n−1)/2 comparisons, Theta(n²). Merge sort splits by position, so its cost is n log n on every input including the worst. Quicksort's worst case is a pivot that splits off nothing, which the sorted input produces with the last-element rule.

A claims insertion sort is n log n, which no quadratic algorithm achieves. B swaps merge and quick. C claims quicksort's worst case is n log n, which randomisation fixes only in expectation.

The page measures all three at n = 20 on adversarial inputs: insertion on a reversed array 190 comparisons, merge on the same array 48, quicksort on a sorted array 190.

MCQEasyPYQ — GATE CSE 2021 Set 1

Consider the array 23 32 45 69 72 73 89 97. Which algorithm uses the least number of comparisons (among the array elements) to sort it in ascending order?

  1. Insertion sort
  2. Merge sort
  3. Selection sort
  4. Quick sort using the last element as pivot

Answer: A — Insertion sort, with 7 comparisons

The array is already ascending. Each of the 7 new keys is compared once with its left neighbour, finds itself in place, and stops: n − 1 = 7 comparisons.

Selection sort scans the whole tail on every pass regardless of order: 28. Quicksort with the last element as pivot finds the maximum as pivot every time, so every split is one-sided: 28. Merge sort never inspects the order and needs 12.

The page computes all four counts on this exact array and reports 7, 12, 28 and 28. The trap is assuming that an "efficient" n log n algorithm must use fewer comparisons than a quadratic one — on this input it uses nearly twice as many.

MCQMediumPYQ — GATE CSE 2015 Set 3

Assume that a mergesort algorithm in the worst case takes 30 seconds for an input of size 64. Which of the following most closely approximates the maximum input size of a problem that can be solved in 6 minutes?

  1. 256
  2. 512
  3. 1024
  4. 2048

Answer: B — 512

Cost is c · n log₂ n. At n = 64, n log₂ n = 64 · 6 = 384, so c = 30/384. Six minutes is 360 seconds, twelve times longer, so the new n log₂ n must be 12 · 384 = 4608.

Check the options: 512 · 9 = 4608 exactly. 256 · 8 = 2048 and 1024 · 10 = 10240 are off by more than a factor of two in either direction.

A is the answer you get by scaling linearly with the log ignored. D is the answer you get by assuming the cost is linear in n. Both are the same mistake: using the wrong model. The page verifies that 512 is exact, not merely nearest.

NATMediumPYQ — GATE CSE 2014 Set 2

Suppose P, Q, R, S, T are sorted sequences having lengths 20, 24, 30, 35, 50 respectively. They are to be merged into a single sequence by merging together two sequences at a time. The number of comparisons that will be needed in the worst case by the optimal algorithm for doing this is ______.

Answer: 358

Merging sorted lists of sizes m and n costs at most m + n − 1 comparisons. To minimise the total, always merge the two shortest remaining runs — the Huffman argument, justified by an exchange argument: any schedule whose first merge is not the two shortest can be improved by swapping in the shorter runs.

20 + 24 → 44 costs 43. Then 30 + 35 → 65 costs 64. Then 44 + 50 → 94 costs 93. Then 65 + 94 → 159 costs 158. Total 43 + 64 + 93 + 158 = 358.

The trap is charging m + n instead of m + n − 1 for a merge, which gives 357 for one of these pairings, or merging in the given order, which costs more. The page simulates the greedy schedule and returns 358.

MSQMediumPYQ — GATE CSE 2016 Set 2

Assume that the algorithms considered here sort the input sequences in ascending order. If the input is already in ascending order, which of the following are TRUE?

I. Quicksort runs in Theta(n²) time
II. Bubblesort runs in Theta(n²) time
III. Mergesort runs in Theta(n) time
IV. Insertion sort runs in Theta(n) time

  1. I and II only
  2. I and III only
  3. II and IV only
  4. I and IV only

Answer: D — I and IV only

I is true: with a first, last or middle fixed pivot, an ascending input makes every split one-sided, so the cost is n(n−1)/2, which is Theta(n²). IV is true: each new key is compared once and stops, so the cost is n − 1, which is Theta(n).

III is false: merge sort splits by index and cannot notice that the halves were ordered, so it stays Theta(n log n) — at n = 20 it spends 40 comparisons where insertion sort spends 19. II is the interesting one: it is true for the plain bubble sort that always runs every pass, and false for the version with the early-exit flag. The key's reading is the plain loop.

The page measures both variants at n = 8: 28 comparisons without the flag, 7 with it. If you assume the adaptive version you will disagree with this key, so state the variant.

MCQMediumOriginal GATE-style

Which of the following sorting algorithms is both stable and in place?

  1. Merge sort
  2. Heapsort
  3. Insertion sort
  4. Quicksort with the Lomuto partition

Answer: C — Insertion sort

Insertion sort moves a key left past strictly larger keys only, so equal keys are never crossed and the order of ties is preserved. It uses O(1) auxiliary cells: one variable for the key being placed.

A is stable but needs Theta(n) extra cells for the merge output. B is in place but not stable — sift-down moves a key past equal keys. D is in place but not stable, because the partition swap ignores equality.

The page does not take this from a table: it runs each algorithm on tagged records with duplicate keys and checks whether the tags of equal keys stay increasing. Insertion, merge, counting and radix pass; selection, quicksort and heapsort fail.

NATHardOriginal GATE-style

Two sorted lists of sizes 5 and 7 are to be merged into one sorted list. What is the minimum number of comparisons between list elements that any correct merge can make in the best case?

Answer: 5

A merge compares the two fronts and emits one element per comparison. If every element of the shorter list is smaller than every element of the longer one, then each comparison emits an element of the shorter list, and after 5 comparisons the shorter list is exhausted — the remaining 7 elements are appended with no further comparison.

So the minimum is the size of the shorter list, 5, and the maximum is m + n − 1 = 11, reached when the two lists interleave so that the last element emitted is the last of one of them.

The trap is answering 11, which is the maximum. A second trap is answering 12 by forgetting the minus one: the final element never needs a comparison because there is nothing left to compare it against. Both numbers matter, and a question that says "at most" wants 11.

MSQHardOriginal GATE-style

Which of the following statements are TRUE?

  1. Every comparison sort needs Omega(n log n) comparisons in the worst case.
  2. Sorting n keys can be done in o(n log n) time if the keys are drawn from a range of size O(n).
  3. A stable sort can never run in o(n log n) comparisons.
  4. Heapsort is Theta(n log n) in the best case as well as the worst.

Answer: A, B and D

A is the decision-tree bound: n! leaves force a height of at least log₂(n!), which is Omega(n log n). Note it says comparison sort — that word is what makes it true.

B is counting sort: O(n + k) with k = O(n) is O(n), which is o(n log n). This is not a contradiction of A, because counting sort does not compare keys, so A's hypothesis fails.

C is false, and B is its counterexample: counting sort is stable (it places from the right) and runs in O(n) when the range is O(n). Stability costs nothing asymptotically.

D is true: heapsort's build is linear and its n extractions are log n each, and neither step looks at the input order, so a sorted input costs the same as any other. The page measures the comparison count at every power of two up to 1024 and finds it always between 0.5 n log₂ n and 4 n log₂ n + 4 n.

NATHardOriginal GATE-style

Merge sort is run on the array [10, 7, 8, 19, 41, 35, 25, 31], splitting at the middle index. Call a merge void if its output is all of the left half followed by all of the right half. How many of the seven merges are void?

Answer: 3

Walk the recursion. [10]|[7] emits 7 then 10 — the right half first, so not void. [8]|[19] emits 8 then 19 — void. [7,10]|[8,19] emits 7, 8, 10, 19 — interleaved, not void. [41]|[35] emits 35 then 41 — not void. [25]|[31] emits 25 then 31 — void. [35,41]|[25,31] emits 25, 31, 35, 41 — all of the right half then all of the left, which the definition does not call void. Finally [7,8,10,19]|[25,31,35,41] emits all of the left then all of the right — void.

Three void merges out of seven. The trap is counting the all-right-then-all-left merge as void as well, which gives 4; the definition is asymmetric and names the left half first. The page runs merge sort on this array and tests each merge's output against the definition.

MCQHardOriginal GATE-style

An array of n keys is sorted with quicksort using the middle index as pivot, with a two-way (Lomuto) partition. Which statement about the worst case is correct?

  1. It is Theta(n log n), because the middle index splits the array evenly
  2. It is Theta(n²), because the organ-pipe input costs exactly n²/4 comparisons
  3. It is Theta(n log n) on average and Theta(n²) only for a sorted input
  4. It cannot exceed O(n log n) because a fixed position is deterministic

Answer: B

The middle index is not the middle value. The organ-pipe array — 1, 3, 5, … up to the middle, then the even numbers falling back — puts the median of the values at the ends and the extremes in the middle, so the middle-index pivot is always extreme and the split is always one-sided.

The page measures the exact cost at n = 24, 48, 96, 192 and 384 and gets exactly n²/4 each time, with the ratio to n log₂ n climbing 1.31 → 2.15 → 3.64 → 6.33 → 11.18. A ratio that grows without bound is precisely what rules out any O(n log n) bound.

A confuses the position with the value. C is wrong because the sorted input is not the only bad input for this rule. D is wrong because being deterministic is exactly what lets an adversary construct the bad input.

MCQMediumOriginal GATE-style

Counting sort is used on 10 integers, each a 32-bit value. Which statement is correct?

  1. It runs in O(n) = O(10), so it is the fastest of all the sorts here
  2. It runs in O(n + k) with k about 4·10⁹, so it is far worse than any quadratic sort here
  3. It cannot sort 32-bit values at all
  4. It runs in O(n log n) because it must scan the counter table

Answer: B

Counting sort's cost is O(n + k) where k is the number of possible key values. For 32-bit keys, k = 2³² ≈ 4.3·10⁹, so the counter table dominates: four billion cells for ten keys.

The claim "counting sort is linear" is really "counting sort is O(n) when k = O(n)". State that assumption or the claim is false.

A drops k entirely. C is false — it sorts them correctly, just slowly. D invents a different cost model: the scan of the table is k, not n log n. On 200 keys in a range of 100 the page measures counting sort at 695 operations against 1529 comparisons for the comparison bound, which is the case where k really is comparable to n.

Definitions to have exact

  • sorted — the output is a permutation of the input and every neighbouring pair is in order. Two promises, not one.
  • stable — equal keys keep their relative input order in the output.
  • in place — O(1) auxiliary cells. Says nothing about the recursion stack.
  • adaptive — the running time changes with the input arrangement.
  • comparison sort — learns about keys only through comparisons. The lower bound applies to exactly this class.
  • decision tree — nodes are comparisons, leaves are outputs, at least n! leaves, height is the comparison count.

Read the definitions in the order they are listed: each one is a hypothesis of the one after it.

Formulas

n(n − 1)/2 the comparison count of selection sort on every input, of insertion sort on a reversed input, and of last-pivot quicksort on a sorted input
n − 1 insertion sort's comparisons on a sorted input; the number of merge operations in merge sort; the maximum comparisons to merge a list of size n
n⌈log₂ n⌉ − 2^⌈log₂ n⌉ + 1 merge sort's worst-case comparison count, exact at n = 4, 5, 6, 7, 8 giving 5, 8, 11, 14, 17
log₂(n!) the lower bound on comparisons for any comparison sort; between (n/2)log₂(n/2) and n log₂ n; the ratio to n log₂ n tends to 1
m + n − 1 the maximum comparisons to merge sorted lists of sizes m and n; the minimum is min(m, n)
2/m with m distinct keys left, the chance a uniformly random pivot lands at an end, giving an empty side

n²/4 is not in this list on purpose: it is the organ-pipe cost for a middle-index pivot, a specific counterexample rather than a general formula.

Traps, in one line each

  • A sorted input is the best case for insertion sort and the worst for last-pivot quicksort. Same input, opposite verdicts.
  • Bubble sort is quadratic on a sorted input without the early exit and linear with it. The key picks one; say which you used.
  • Selection sort wins on swaps (at most n − 1), never on comparisons.
  • The middle index is not the middle value; the organ-pipe input costs a middle pivot exactly n²/4.
  • The n log n wall is about comparisons, so a non-comparison sort is not a counterexample to it.
  • "Counting sort is linear" needs k = O(n). Without it the claim is false.
  • In place says nothing about the recursion stack; quicksort is called in place and still uses O(log n) frames.
  • Merge sort's merge count is n − 1, its comparison count is not.

Eight traps, and seven of them are a case or a hypothesis being dropped. Read the case before the algorithm.

Decision procedure

  1. What is counted? Comparisons, time, swaps, auxiliary memory, or stability.
  2. Which input? Sorted, reversed, all equal, or arbitrary. "Arbitrary" means the worst case.
  3. Which implementation? Early-exit bubble, last-pivot or random quicksort, Lomuto or Hoare, plain or three-way.
  4. Comparison sort? If yes, the n log n wall applies and the row is one of the first six. If no, the wall does not apply and the row is one of the last two.
  5. Look up the cell. By this point no algebra is left to do.

Ask the four questions in this order every time. The order matters because question 2 and question 3 are the two that change the answer most often.

Five-minute revision questions

  1. State both promises of a sort. Which one does a program that prints 1, 2, 3 break?
  2. How many comparisons does selection sort make at n = 100? Does the answer depend on the input?
  3. Why does the decision tree need at least n! leaves, and why does that force log₂(n!) comparisons?
  4. Merge sort at n = 8: how many merges, and what are its best and worst comparison counts?
  5. Which single fact makes a sorted input the worst case for last-pivot quicksort?
  6. Name one sort that is stable but not in place, and one that is in place but not stable.
  7. What exactly does the n log n lower bound assume, and which algorithm violates each assumption?
