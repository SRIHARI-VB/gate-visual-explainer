Topic and objective

TOPIC: Lexical analysis, parsing and syntax-directed translation — the first clause of GATE 2027 Section 7, Compiler Design.

LEARNING OBJECTIVE: Read a line of source as a token stream under the longest-match rule. Compute FIRST and FOLLOW to a fixed point and fill a predictive parsing table from them, reading a cell that holds two productions as the definition of "not LL(1)". Build the canonical LR(0) collection by closure and goto, then apply the three lookahead policies — FOLLOW for SLR, merged cores for LALR, exact lookaheads for canonical LR(1) — and say which grammars each one loses. Read associativity off the recursion side and precedence off the depth of a grammar. Evaluate a syntax-directed definition in reduce order and emit three-address code from the same tree.

I read this topic as one question asked about four objects: what may the parser decide, and how much lookahead does the decision need. The scanner decides with none, LL(1) with one token of the future, LR(0) with none of the future and SLR/LALR/LR(1) with increasing precision about which future. Every definition, table and previous-year item below is that question at a different object.

Prerequisites

  • Regular expressions, DFA and NFA, and the subset construction. A scanner is a DFA, and the longest-match rule is a walk on it. Built in Regular Expressions and Finite Automata.
  • Context-free grammars, derivations, parse trees and ambiguity. Everything after the scanner is a statement about a grammar. Built in Context-Free Grammars and Pushdown Automata.
  • Sets, and closure under a rule applied repeatedly. FIRST and FOLLOW are least fixed points of a monotone rule on finite sets, and the computation is literally "sweep until nothing changes". Built in Sets and Set Operations.
  • Finite automata over item sets. The LR(0) collection is a subset construction on items, so the 2-to-the-n lesson from the theory page is the same construction with a different state type. Built in Regular Expressions and Finite Automata.
  • Recursion, and reading a grammar's shape. Associativity and precedence are read off the recursion, not off the operator. Built in Context-Free Grammars and Pushdown Automata and Recursion.
  • Three-address code and a stack machine. The translation scenes emit code and run it. Built in C Fundamentals.

Nothing about data-flow analysis, register allocation or runtime environments is assumed or taught here; those belong to the back-end clause. Nothing about LR(k) for k above one is assumed.

The five ideas to leave with

  1. The scanner decides with no lookahead beyond the current token, and that limit is what makes it a finite automaton.
  2. FIRST looks forward and is easy; FOLLOW looks at the whole context and is the one that goes wrong. Seed the end marker into the start symbol and nothing else.
  3. A conflict is a cell with two entries, not a cell you could not fill. Filling the cell is a construction; the conflict is a verdict.
  4. The LR(0) automaton is built once and shared. SLR, LALR and LR(1) differ only in what a completed item is allowed to reduce on.
  5. Associativity is the recursion side; precedence is the grammar's depth. Neither is a property of the operator symbol.

Intuition: two readers, one text

Imagine two people reading the same sentence. The first checks that every word is a word — that recieve is not in the dictionary, that a quotation mark is closed. The second checks that the words are in a legal order — that a sentence can have a verb where this one has it. The first reader needs a dictionary and nothing else. The second needs to remember the beginning of the sentence while reading the end.

That is the whole division. The scanner is the dictionary reader: it can be a finite automaton because it never needs to remember anything before the current word. The parser is the grammar reader: it needs a stack, because "is this legal" depends on what is still open. And that is why the two phases are separate, and why the first one is fast.

Level 1 — what each phase is allowed to know

The scanner sees characters and emits tokens. Its one interesting rule is longest match: at each position, take the longest string that is a legal token, then restart. A token is a class plus a lexeme; the class is what the parser reasons about, and the lexeme is kept for the symbol table.

The parser sees tokens and a grammar. It answers one question — is this token sequence derivable from the start symbol — and in answering it builds a derivation, either from the top down (LL) or from the bottom up (LR).

Level 1 — why the boundary sits there

Because the scanner's language is regular and the parser's is not. Balanced brackets, matching if/else, and declared-before-use are all beyond a finite automaton. Putting them in the scanner is not a matter of effort; it is impossible.

The reverse direction is the useful one: everything regular can be pushed down into the scanner, and doing so makes the grammar smaller and the parser table smaller. That is why keywords are handled by the scanner and not by a hundred grammar productions.

Level 2 — the definitions, each symbol in words

Grammar. Four things: a set of terminals (the tokens), a set of nonterminals (the intermediate names), a start symbol, and a set of productions written A → α, read "A may be replaced by α". A derivation is a sequence of such replacements starting at the start symbol. A parse tree is the same derivation drawn as a tree.

FIRST(A) is the set of terminals that can be the first symbol of a string derived from A, together with ε if A can derive the empty string. FOLLOW(A) is the set of terminals that can appear immediately after A in some sentential form, together with the end marker $ if A can be last. Neither is a property of a production; both are properties of the whole grammar.

Level 2 — the parser vocabulary

Handle. A right-hand side sitting on top of a shift-reduce stack at the moment replacing it is the correct next step. It is a production and a position.

Viable prefix. A prefix of a right-sentential form that does not extend past the handle. The stack always holds one.

Item. A production with a dot showing how much of the right side has been read. A → α·β means "α is on the stack and β is still expected".

Conflict. A cell of a parsing table that asks for two different actions. Shift-reduce means shift and reduce compete; reduce-reduce means two productions compete.

Level 2 — the three tables and what differs

All three LR tables are built on the same LR(0) automaton. The only question is which terminals a completed item may reduce on.

LR(0): every terminal. SLR(1): the terminals in FOLLOW of the left side. LALR(1): the lookaheads carried by the item, after merging states that share a core. Canonical LR(1): the lookaheads carried by the item, with no merging.

So the order of strength is LR(0) < SLR(1) < LALR(1) < LR(1), and the state counts are LR(0) = LALR(1) < LR(1).

Level 3 — the visual that carries the mechanism

Three pictures, and the animation draws all three. First, the token stream: a row of boxes, each one a class, with the longest-match decision shown twice so the wrong split is visible next to the right one. Second, the table: a grid of cells, and the only thing that matters is how many productions sit inside a cell. Third, the automaton: a set of boxes each holding items, with arrows for goto — and the reader's eye should go to the dots, because the dot position is the parser state.

What the pictures must not do is imply that the table is computed from the grammar directly. It is computed from FIRST and FOLLOW, which are computed from the grammar by a fixed point. The order of the three pictures is the order of the dependency.

Level 4 — one worked example, in full

Take S → A a | b A c | d c | b d a and A → d. FIRST(A) = {d}. FOLLOW(A) = {a, c}: a from the first production and c from the second.

SLR completes the item A → d· in a state that also holds S → d·c. It reduces on every terminal in FOLLOW(A), and c is one of them, so it reduces — and loses the shift on c.

LALR attaches the lookahead to the item: in that state, A → d· carries only a, because only the first production can put an a after this d. The reduce never competes with the shift, and the conflict is gone.

Level 4 — the same example as a sentence

FOLLOW(A) answers "may an a ever follow an A?" and the answer is yes. LALR answers "may an a follow this A, here?" and the answer is yes as well — but the c that FOLLOW saw comes from a different production and cannot appear here. The gap between the two questions is the entire difference between the two parsers, and it is exactly one word wide: here.

Level 5 — when each construction is licensed

The LL(1) construction is licensed only when the grammar has no left recursion and no common prefixes; otherwise the table conflicts, and left factoring or left-recursion elimination is a preprocessing step, not part of the construction. The LR constructions have no such preprocessing: they handle left recursion natively, which is the practical reason bottom-up parsers are the default in real compilers.

Every LR class is contained in the unambiguous grammars: an ambiguous grammar can never be LR(k) for any k. The converse fails — an unambiguous grammar need not be in any of these classes — and the gap between "unambiguous" and "LR(1)" is where the harder theory lives.

Level 6 — the edge case that decides marks

The nullable start symbol. If the start symbol can derive ε, then ε is in FOLLOW of the start symbol only through the end marker. Leave the end marker out and every nullable production of the start symbol loses its table entry — the grammar then appears to reject the empty input and every input that could have ended there.

The GATE 2012 grammar is exactly this case: S → aAbB | bAaB | ε. Its cell for a holds two productions, and one of them is the empty one, placed there by the FOLLOW branch.

Level 6 — the second edge case

The reduce-count bound. With every right-hand side of length two, a parse of n tokens takes at most n−1 reduces. Add a production whose right side is a single symbol, like A → a, and the bound fails: the page exhibits a grammar where two tokens take three reduces. The bound is a consequence of an identity, and the identity needs the assumption.

Worked example 1 — filling the GATE 2012 table

Grammar. S → aAbB | bAaB | ε, A → S, B → S. Task. Find FIRST and FOLLOW, then the entries for the cells the question marks.

FIRST. Pass one reads only the productions of S: a, b, and ε. Pass two pushes those through A → S and B → S, so FIRST(A) = FIRST(B) = {a, b, ε}. Pass three changes nothing.

FOLLOW. FOLLOW(S) starts as {$}. From aAbB, an a sits before A and a b before B. From bAaB, a b before A and an a before B. So FOLLOW(A) = {a, b}. Since B ends the first production, FOLLOW(B) also gets FOLLOW(S). And A → S and B → S push FOLLOW(A) and FOLLOW(B) back into FOLLOW(S), giving {a, b, $}.

Example 1 — the verdict

The production S → aAbB goes in the cell for a. The production S → ε has FIRST = {ε}, so it goes into every terminal of FOLLOW(S) — which is a, b and $. So the cell for a holds two productions and so does the cell for b.

The grammar is therefore not LL(1). The 2012 question only asked which productions the cells hold, and the answer lists both — that is the point of the question.

Example 1 — the check

The page recomputes FOLLOW a second way: it expands sentential forms by leftmost derivation to a bounded length and records, for every nonterminal occurrence, the terminal immediately after it. That method never uses the fixed-point equations, so agreement between the two is evidence rather than a tautology. Both give FOLLOW(A) = {a, b}.

Worked example 2 — the whole shift-reduce trace

Grammar. S → aSB | d, B → b. Input. aaadbbb. Question (GATE 2020). How many reduce moves?

The parser shifts a, a, a, d. Now d is a complete right-hand side, so it reduces to S. It shifts b, and b is a complete right-hand side, so it reduces to B. Now the stack ends in a S B, which is a complete right-hand side, so it reduces to S. That pattern repeats twice more.

Count the reduces: S → d once, B → b three times, S → aSB three times. Seven. The animation shows all fifteen rows so the pattern is visible rather than memorised.

Example 2 — the invariant on the same trace

Look at the stack column at every row. It never holds a string this grammar could not have produced as a beginning. After two shifts it holds 0 2 2, which is a a — a prefix of a right-sentential form. That is the viable-prefix invariant, and it holds because the automaton was built from the grammar: a state is reachable exactly when its items' prefixes are viable.

Example 2 — why the count is not the point

Seven is the answer, but the transferable fact is the identity: reduces = 1 − tokens + sum of right-hand-side lengths. Here 1 − 7 + (1 + 1 + 3 + 1 + 3 + 1 + 3) = 1 − 7 + 13 = 7. On any grammar whose right sides all have length two, that forces at most n−1 reduces, which is where the familiar bound comes from.

Worked example 3 — SLR against LALR, state by state

Grammar. S → Aa | bAc | dc | bda, A → d. Question (GATE 2025, Set 2). Which class is it in?

The page builds the LR(0) collection — eleven states — and then the three tables on top of it. State 4 holds S → d·c and A → d·. Under SLR, the completed item reduces on FOLLOW(A) = {a, c}, and c is in the state as a shift, so the cell for c holds a shift and a reduce. Under LALR the completed item carries only the lookahead a, so it reduces on a and shifts on c.

SLR: two conflicts, in state 4 on c and in state 7 on a. LALR: none. Canonical LR(1): none. So the grammar is LALR(1) but not SLR(1), and the page reports the counts rather than recalling them.

Example 3 — the same automaton, a different grammar

Take S → CC, C → cC | d. Seven LR(0) states, and canonical LR(1) needs ten — because the two C's in S → CC carry different lookaheads, and the LR(1) construction keeps them in separate states. Merging those states by core gives back exactly seven. That pair, seven and ten, is the cleanest illustration that LALR's state count is the LR(0) count.

Example 3 — where LALR loses

Take S → aEc | aFd | bFc | bEd with E → e and F → e. Canonical LR(1) keeps two states whose items are E → e· with lookahead c and F → e· with lookahead d, and separately the other pairing. Merging them by core puts E → e·{c,d} and F → e·{c,d} in one state, and on c the parser may reduce by either. That is a reduce-reduce conflict, and it is the standard example of an LR(1) grammar that is not LALR(1).

Worked example 4 — a translation scheme evaluated in reduce order

Scheme (GATE 2016, Set 1). S → aA {print 1}, S → a {print 2}, A → Sb {print 3}. Input. aab. Question. What does a bottom-up parser print?

The parser shifts a, then a, then b. The top of the stack is now a, which reduces by S → a and prints 2. The stack becomes a S b, which reduces by A → Sb and prints 3. The stack becomes a A, which reduces by S → aA and prints 1.

Output: 231. The page runs the real parser and reads the order off its trace, so the answer is not a recital.

Example 4 — the same tree as code

For 8*2+3*5 the tree puts both multiplications below the addition. Emitting one temporary per operator in post-order gives t1 = 8 * 2, t2 = 3 * 5, t3 = t1 + t2. Running that on a two-register machine gives 31, and evaluating the expression directly gives 31.

The page checks this on four expressions, including one with brackets, so the agreement is a test rather than an illustration.

Example 4 — the 2022 arithmetic

S → S#T {S.val = S₁.val × T.val}, T → T%R {T.val = T₁.val ÷ R.val}. Because # is left recursive at the S level and % at the T level, % binds tighter and both group left. So 20 # 10 % 5 # 8 % 2 % 2 is (20 × (10÷5)) × ((8÷2)÷2) = 40 × 2 = 80.

The boundary cases that decide marks

Six cases, each one a place where a definition that works on the easy examples stops working. Each is computed by the page, not asserted.

1. The nullable start symbol

If the start symbol derives ε, the end marker is the only thing that puts $ into FOLLOW of the start symbol, and the empty production is placed in cells for a, b and $ at once. Miss the end marker and the empty production vanishes from the table.

Witness: S → aAbB | bAaB | ε. The cell for a holds two productions.

2. The reduce-count bound

"At most n−1 reduces" needs every right-hand side to have at least two symbols. Witness: S → AB, A → a, B → b parses ab with three reduces — the page counts them on the derivation, not on a parser.

All-binary witness for the bound itself: S → SS | aa takes 3 reduces on 4 tokens and 5 on 6.

3. LR(1) without LALR

Merging states with the same core can create a reduce-reduce conflict. Witness: S → aEc | aFd | bFc | bEd, E → e, F → e. Canonical LR(1) is conflict-free; LALR(1) is not.

What merging cannot do is create a shift-reduce conflict — that is the GATE 2008 item, and the page checks the equivalence on six grammars.

4. Ambiguous means not LR, for every k

The dangling-else grammar is ambiguous, and the page counts two parse trees for i b t i b t a e a. No LR table of any lookahead can be conflict-free on it, because a conflict-free table would give one parse and there are two.

5. Unambiguous does not mean LR(1)

There exist unambiguous context-free grammars with no conflict-free LR(k) table for any k, and deterministic context-free languages are a proper subclass of the context-free languages. This lesson does not construct one; it only records that "unambiguous" is necessary and not sufficient, so an argument that stops at "it is unambiguous" is incomplete.

6. Left recursion is not ambiguity

A left-recursive grammar is fine for LR and fatal for LL. S → S + T | T is left recursive and unambiguous, and its SLR table has no conflict; its LL(1) table cannot be built at all.

Conversely the dangling-else grammar is right recursive and ambiguous. The two properties are independent, and exam distractors swap them.

The one that is not a boundary but a definition

A token count. Whitespace produces no token; a two-character operator produces one; a keyword is one token of its own class, not an identifier that happens to spell if. On the sample line the page emits twelve tokens from twenty-six characters, and the class counts are computed, not read off a list.

Five beliefs that cost marks

Each is stated as a learner would state it, then corrected with the smallest counterexample or the sharpest distinction.

1. "More lookahead means more states, so LALR has fewer states than SLR"

No. LALR and SLR are built on the same LR(0) automaton, so their state counts are identical by construction — eleven and eleven on the 2025 grammar, seven and seven on S → CC.

What LALR adds is not states but precision inside each state: an exact lookahead per item instead of a global FOLLOW set.

2. "The parser reduces when the stack matches a right-hand side"

Matching is necessary and not sufficient. The stack may match several right-hand sides; the handle is the one whose replacement keeps the parse on a rightmost derivation read backwards.

That is why the automaton exists at all: it records, per state, which completed items are actually possible.

3. "Precedence and associativity are properties of the operator"

They are properties of the grammar. In one and the same grammar the page exhibits * left associative and + right associative — because T → T*U recurs on the left and P → Q+P recurs on the right.

An ambiguous grammar like E → E+E | E*E | id has neither, and the parser is given both by a table.

4. "A cell I cannot fill is the conflict"

A conflict is a cell holding two productions. An empty cell is just an error entry, and it appears legitimately in every correct LL(1) table — for instance M[S, b] on the GATE 2010 grammar, where S has no production that can start with b.

5. "FOLLOW is computed from FIRST, so it is the same kind of thing"

FOLLOW is not derivable from FIRST alone; it needs the whole context and a backward-closed rule. The page therefore computes it twice by two unrelated methods — the fixed-point equations, and a bounded expansion of sentential forms — and compares. Agreement is evidence; a single method is only a claim.

Closely confused pair 1: grammar class against language class

"Is this grammar LL(1)?" is a question about a grammar. "Is this language deterministic context-free?" is a question about a language. A language can be parsed by an LR(1) parser while the particular grammar you were handed is not LR(1).

So "not SLR(1)" never means "not context-free", and "ambiguous grammar" never means "ambiguous language".

Closely confused pair 2: LL against LR

LL builds a leftmost derivation top-down and must decide a production before seeing its body. LR builds a rightmost derivation in reverse bottom-up and decides after seeing the body.

Consequence: LR handles left recursion natively and LL does not; every LL(1) grammar is LR(1) and not conversely. The GATE 2010 grammar happens to be both, which is why that item's answer is "both" rather than "LR(1) only".

The five shapes this clause is asked in

Every previous-year item I could verify in this clause falls into one of these. The procedure for each is short, and the marks come from doing it in the right order.

Shape 1 — fill or read a table cell

"The entries M[S, a] and M[S′, $] respectively are…" The work is FIRST and FOLLOW, then the two-branch rule. Read the options as production sets and check whether each production's FIRST or nullable-FOLLOW places it there.

Trap: the cell may legitimately hold two productions, and the correct option may say so.

Shape 2 — classify a grammar

"The grammar is LL(1) / SLR(1) / LALR(1) / LR(1)…" Build the LR(0) automaton once, then test the rungs from the cheapest up. The first rung that conflicts tells you the answer.

Trap: options often pair a class with a wrong reason ("not LL(1) because left recursive" on a right-recursive grammar).

Shape 3 — count states or items

"The number of items in GOTO(I₀, <) is…" Build the closure, apply goto, count items — including the ones added by closure, which is where the count goes wrong.

On the 2022 grammar, GOTO(closure(I₀), +) holds five items. The page computes it.

Shape 4 — trace a translation

"What does this scheme print / evaluate to?" Reduce order for bottom-up, and the recursion side decides the grouping. Write the reductions in order before evaluating anything.

Trap: subscripted nonterminals mean "the instance on the right-hand side", not new symbols.

Shape 5 — a true/false statement cluster

"Which of the following statements is/are TRUE?" These test the ladder, the state counts, and what each parser is for. The three recurring facts: every LL(1) grammar is LR(1); LALR has the LR(0) state count; merging cannot create a shift-reduce conflict.

Trap: a statement that is true of languages offered as if it were about grammars.

The order that never changes

Augment → FIRST and FOLLOW → LL(1) table → LR(0) automaton → add lookaheads one rung at a time. Five steps. Every question in this clause is one of those steps with a number attached, and doing them out of order is the most common way to lose a mark you could have had.

Q1 (original practice, MCQ). How many tokens does the scanner emit for a1 <= b*c, with longest match and no whitespace sensitivity?

(A) 4   (B) 5   (C) 6   (D) 7

(B) 5. a1, <=, b, *, c. Longest match makes <= one token; the identifier and the number classes each consume a whole run.

Why not 6: that counts < and = separately, which longest match forbids. Why not 4: that misses the *.

Q2 (original practice, MCQ). Is S → aSb | ε LL(1)?

(A) Yes   (B) No, because it is left recursive   (C) No, because M[S, b] holds two productions   (D) No, because the grammar is ambiguous

(A) Yes. FIRST(S) = {a, ε} and FOLLOW(S) = {b, $}. S → aSb goes in the cell for a; S → ε goes in the cells for b and $. One entry per cell.

The distractor C is the interesting one: the empty production does go in M[S, b], but only one production does, because no production of S starts with b.

Q3 (original practice, NAT). How many states are in the canonical LR(0) collection for S → CC, C → cC | d?

7. The page builds them: I0 = {S′→·S, S→·CC, C→·cC, C→·d}, and the collection closes at seven. Canonical LR(1) on the same grammar needs ten, and merging those ten by core gives the same seven back.

Q4 (original practice, MSQ). Which are TRUE?

(a) Every LL(1) grammar is LR(1). (b) Every LR(1) grammar is LALR(1). (c) LALR(1) has the same number of states as SLR(1) for the same grammar. (d) Merging LR(1) states by core can create a shift-reduce conflict.

(a) and (c).

(b) is false: S → aEc | aFd | bFc | bEd with E → e, F → e is LR(1) and not LALR(1), because merging produces a reduce-reduce conflict.

(d) is false: merging can only create reduce-reduce conflicts. A shift-reduce conflict in a merged state was already present in the states being merged, since they share a core. This is the GATE 2008 result, checked here on six grammars.

Q5 (adapted from GATE 2019). For S → Aa, A → BD, B → b | ε, D → d | ε, how many terminals are in FOLLOW(B)?

2 — namely a and d. d because D can begin with d, and a because D can vanish, so whatever follows A follows B. The page computes it and gets {a, d}.

Q6 (adapted from GATE 2014, Set 2). In S → T*P, T → U | T*U, P → Q+P | Q, Q → id, U → id, which is TRUE?

(A) both left associative   (B) both right associative   (C) + left, * right   (D) * left, + right

(D). T → T*U recurs on the left, so * groups left; P → Q+P recurs on the right, so + groups right. The page builds both trees from the grammar and they lean opposite ways.

Q7 (adapted from GATE 2022). With S → S#T {S.val = S₁.val × T.val}, T → T%R {T.val = T₁.val ÷ R.val}, R → id, the value of 20 # 10 % 5 # 8 % 2 % 2 is ______.

80. % binds tighter and both operators group left, so it is (20 × (10÷5)) × ((8÷2)÷2) = 40 × 2.

Q8 (original practice, MCQ). On the grammar S → ACB, A → aA | ε, C → cC | ε, B → bB | b, the SLR(1) parser built on the LR(0) automaton has how many conflicts?

(A) 0   (B) 1   (C) 5   (D) cannot be built

(A) 0. The same automaton under LR(0) has five shift-reduce conflicts, and SLR removes all five by restricting each reduce to FOLLOW of its left side. This is the sharpest illustration in the lesson that a conflict count belongs to a parser, not to a grammar.

Q9 (original practice, NAT). For S → SS | aa, what is the number of reduce moves to parse the four-token input a a a a?

3. Every right-hand side has length two, so n−1 = 3. The page confirms it by counting internal nodes on the derivation: S → SS, then S → aa twice.

What to do if you got several wrong

Nearly every error in this clause is one of four: a FOLLOW set missing the end marker, a conflict counted as a cell rather than as entries inside a cell, associativity read off the operator, or a state count quoted without naming the parser. Check those four before re-deriving anything.

Revision sheet

Definitions, formulas, the decision procedure and the traps, in the order you would use them.

Definitions in one line each

Token — a class plus a lexeme. Longest match — take the longest legal token, then restart.

FIRST(A) — terminals that can begin a string from A, plus ε if A can vanish. FOLLOW(A) — terminals that can come immediately after A, plus $ if A can be last.

Handle — a right-hand side on top of the stack at the moment replacing it is correct. Viable prefix — a prefix of a right-sentential form that stops at the handle.

Item — a production with a dot. Conflict — a table cell holding two actions.

The three tables, and the two numbers

Same LR(0) automaton. Reduce policy: everything (LR(0)), FOLLOW (SLR), merged core lookaheads (LALR), exact lookaheads (LR(1)).

States: LR(0) = LALR < LR(1).

Strength: LR(0) < SLR(1) < LALR(1) < LR(1) < all unambiguous grammars.

The decision procedure

1. Augment the grammar. 2. FIRST and FOLLOW to a fixed point. 3. LL(1) table; count productions per cell. 4. LR(0) collection by closure and goto. 5. Add lookaheads one rung at a time and count conflicts.

Every step's output is an input to the next. Doing 5 before 4 is the usual way to lose time.

The four slips

Missing $ in FOLLOW of the start symbol. Reading associativity off the operator instead of the recursion side. Assuming LALR has more states than SLR. Counting cells instead of the productions inside a cell.

And a fifth, quieter one: quoting a conflict count without naming the parser.

Quick revision questions

Is S → aSb | ε LL(1)? Yes — FIRST is {a, ε}, FOLLOW is {b, $}, one entry per cell.

Can merging LR(1) states create a shift-reduce conflict? No, only reduce-reduce.

Does LALR ever have more states than SLR? No — both are the LR(0) count.

Is a left-recursive grammar ambiguous? Not necessarily — S → S+T | T is left recursive and unambiguous.

What does a cell with two productions mean? The grammar is not LL(1).

What was not verified

The claim that LALR(1) has a shift-reduce conflict exactly when canonical LR(1) does is a theorem from the literature; the page checks it on six grammars and does not prove it. The claim that canonical LR(1) parses every deterministic context-free language is cited, not proved. The 2026 Set 2 answer of five LR(0) shift-reduce conflicts is the number this page computed on its own automaton; one archive agrees, and no second independent archive was found.
