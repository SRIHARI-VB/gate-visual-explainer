Topic and objective

TOPIC: Sequencing in C. Precedence and associativity decide how an expression is grouped; they do not decide the order in which its parts are computed. This page teaches the second question: value computations against side effects, the places the standard calls sequence points, the rule about an unsequenced side effect on a scalar object, and the expressions that therefore have no answer.

LEARNING OBJECTIVE: Given any C expression, decide in five steps whether its value is fixed, whether only its order is free, or whether its behaviour is undefined — and state which, with the reason. Rewrite each undefined form into a defined one. Name the operators that carry a sequence point and the one comma that does not.

I read the request as the sequencing rules of the C language as the standard states them, not as a general lecture on operator precedence, which the C fundamentals lesson already owns. Precedence appears here only as the thing that is not the answer.

Prerequisites

  • C fundamentals — types, operators, precedence and associativity, i++ against ++i.
  • Reading a small expression as a tree: which operator takes which operand.
  • The idea of a variable as a named box whose contents can be read and written.
  • No compiler and no packet of hardware is needed. Every count on this page is computed when the page loads.

Five ideas, one line each

  • Grouping is not scheduling. Precedence fixes the tree; the standard leaves the order open.
  • An evaluation is two parts. A value computation, and sometimes a side effect — a store.
  • Barriers are few and named. The call, &&, ||, the comma operator, ?:, and the end of a statement.
  • One rule decides everything. Two unsequenced accesses to one scalar, one of them a write, is undefined.
  • A computable answer proves nothing. i = i++ + 1 has one answer on every ordering and is still undefined.

Intuition first: two cooks, one shopping list

Two cooks are told to "add the flour and add the sugar". The instruction is unambiguous about what to add; it says nothing about which cook moves first. If they use separate bowls, any order works and the cake is the same. If they both reach into the same bowl at the same moment — one adding flour while the other reads how much is there — the result depends on who moved first, and the recipe no longer describes what comes out.

Educational interpretation The bowls are variables. Separate bowls explain why f() + g() is safe with no order fixed. One shared bowl explains why i++ + i++ is not: the second cook reads a quantity the first cook is in the middle of changing.

Vocabulary, every term in words

Value computation — working out a value: reading a variable, or computing a result from operands.

Side effect — a change to the state of the program: storing into a variable, or calling a function that does.

Sequenced before — a relation between two evaluations: the first finishes, including its side effects, before the second begins.

Unsequenced — neither is sequenced before the other, so they may happen in any order, and may even interleave.

Indeterminately sequenced — one happens entirely before the other, but the standard does not say which. Function calls are like this.

Sequence point — a place in the program where a barrier is placed.

Full expression — an expression that is not part of a larger one: up to the semicolon, or the controlling condition.

The rule, stated exactly

From the C17 standard, 6.5 paragraph 2, in the standard's own words:

If a side effect on a scalar object is unsequenced relative to either a different side effect on the same scalar object or a value computation using the value of the same scalar object, the behavior is undefined.

The same paragraph adds a second sentence that closes the last loophole: if there are several allowable orderings of the subexpressions, the behaviour is undefined if such an unsequenced side effect occurs in any of them.

Verified fact Quoted from the C17 working draft (N2176), 6.5p2, the same text the published ISO/IEC 9899:2018 carries.

The eight places a sequence point sits

Grouped from the standard's Annex C summary. The first five are the ones a question turns on, because they are the only barriers available inside one expression.

1after the function designator and the arguments, before the call — 6.5.2.2p10
2after the left operand of && — 6.5.13p3
3after the left operand of || — 6.5.14p3
4after the left operand of the comma operator — 6.5.17p2
5after the first operand of ?: — 6.5.15p4
6after a full expression, before the next full expression — 6.8p4
7at the end of a full declarator — Annex C
8before a library function returns — Annex C

Educational interpretation Annex C also lists the conversion specifiers of formatted input and output, and the calls to a comparison function made by qsort and bsearch. They are left out of the eight above because they never decide an expression question, and a list of eleven is harder to remember than a list of eight.

Example 1 — i++ + i++ with i equal to 5, enumerated in full

Write the four events. rA and wA belong to the left operand, rB and wB to the right. The only constraints are that each read precedes its own store.

1rA wA rB wBreads 5 and 6, sum 11
2rA rB wA wBreads 5 and 5, sum 10
3rA rB wB wAreads 5 and 5, sum 10
4rB rA wA wBreads 5 and 5, sum 10
5rB rA wB wAreads 5 and 5, sum 10
6rB wB rA wAreads 5 and 6, sum 11

Six orderings, two answers, and three pairs of events that are unsequenced: rA against wB, wA against rB, and wA against wB. Because one of those pairs is a store against a store, the statement is undefined — so neither 10 nor 11 is the answer. The page generates this table when it loads; the numbers here are the same computation.

Example 2 — the one that looks safe

int i = 5; i = i++ + 1;

Two stores to i: the store inside i++, and the store from the assignment. The assignment's store is sequenced after the value computations of both sides — but the store inside i++ is a side effect, not a value computation, so nothing orders the two stores.

Both orderings leave i equal to 6. That is the trap: the value is the same in every ordering, and the behaviour is still undefined, so no compiler is obliged to produce it.

Defined rewrite: i = i + 1;

Example 3 — the index and the increment

int a[10]; int i = 5; a[i] = i++;

The store inside i++ is unsequenced with the read of i used as the index. The enumeration gives index 5 or index 6, so the element written is not determined by the source text.

Defined rewrites: a[i] = i + 1; i++; or i++; a[i - 1] = i; — both say which element and when.

Example 4 — two arguments, one variable

void f(int x, int y); int i = 5; f(i++, i);

There is a sequence point after the arguments and before the call, but none between the arguments. The two argument expressions are unsequenced, and one of them writes i while the other reads it, so this is undefined — not merely unspecified. The three orderings give the pairs (5,5), (5,5) and (5,6): two distinct pairs, and no rule that picks one.

Defined rewrite: int t = i++; f(t, i); — the increment is now a separate full expression, and the arguments read variables that nothing else in the call writes.

Example 5 — buying a barrier

int i = 5; int x = (i++, i);

Here the comma is the operator: it has a sequence point after its left operand. So the store from i++ completes before i is read on the right. One ordering, one answer, 6, and the statement is defined.

The parentheses are load-bearing. Written f(i++, i) the same characters are an argument separator, with no barrier at all.

Example 6 — the guard that works

if (i < n && a[i] == x)

&& has a sequence point after its left operand, so i < n is finished — value and side effects — before a[i] is looked at. The guard protects the index.

Swap the operands, a[i] == x && i < n, and the read of a[i] happens first. The guard still runs, but too late to protect anything. Nothing in the language saves a guard written on the wrong side.

Where the rule stops applying, and where it bites hardest

The rule is about a scalar object — one number, one pointer, one structure member. Most of the mistakes in this topic come from applying it too widely or too narrowly. These are the boundaries.

Two reads never conflict

x = a + a; reads a twice with no barrier between the reads, and it is perfectly defined. A conflict needs at least one write.

This is the commonest false alarm: students mark every repeated variable as suspicious. Only a store makes a pair dangerous.

a[i] and a[j] are different objects

An array is not one scalar object; its elements are separate scalar objects. a[i] = a[j] with i different from j writes one object and reads another, so there is no conflict.

But i itself is one object, which is why a[i] = i++ is undefined: the conflict is on i, not on a.

One statement is one segment

i++; x = i; is defined: the semicolon is a sequence point. i++, x = i as one expression statement is not — unless the comma is the operator, in which case it is a barrier and it is defined.

The distinction is the comma's role, not the presence of the character.

The call barrier sits after the arguments

A sequence point exists after the function designator and all the arguments, before the call. It does not sit between two arguments.

So f(i++, i) is undefined, while f(i++, (i, i)) is not — the inner comma is the operator.

Library calls that write

scanf("%d %d", &i, &i) is fine, and the standard says so: there is a sequence point after the action of each conversion specifier. The same rule makes printf with %n ordered against its own conversions.

But printf("%d %d", i++, i++) is undefined: the conversions are ordered, the argument expressions are not, and both write i.

The loop that is safe by accident

for (i = 0; i < n; i++) a[i] = i; is defined: the increment is one full expression in the for header, and each loop body is another.

The same loop written a[i++] = i inside the body is undefined for exactly the reason in Example 3 — and it is the kind of "cleanup" an optimiser may compile away.

What undefined does not mean

Undefined behaviour is not "a value you cannot know". The standard imposes no requirement at all, so an implementation may produce the value you expected, a different value, a trap, or nothing — and it may do so differently on the next run of the same binary, because the freedom belongs to the compiler, not to the input.

Community observation Discussions of this topic often report that mainstream compilers "usually" print the naive answer. That is an observation about practice, not a rule: the same reports note that the printed value changes with optimisation level. Nothing in the standard makes the naive answer available.

Six slips, each with a counterexample

Each slip is written as the sentence a student says, followed by the case that shows it is wrong, followed by what is true instead.

Slip 1 — "left to right associativity means left to right execution"

Counterexample: f() + g() + h() is grouped (f() + g()) + h(), and the call to h() may run first.

True instead: associativity is a statement about the shape of the tree, not about time. The standard fixes the tree and leaves the schedule open.

Slip 2 — "unspecified order means undefined behaviour"

Counterexample: f() + g() where the two functions touch nothing shared. The order is unspecified and the program is a correct program.

True instead: unspecified means two or more possibilities, and every one of them is correct. Undefined means no possibility is promised.

Slip 3 — "a comma is a comma"

Counterexample: f(i++, i) is undefined, while (i++, i) is defined and has one answer.

True instead: the comma between arguments is punctuation with no barrier; the comma operator carries a sequence point after its left operand.

Slip 4 — "I ran it, so that is the answer"

Counterexample: i = i++ + 1 prints 6 on every ordering and is undefined, so a compiler may legally remove the statement or print anything.

True instead: an observed output is a fact about one compiler and one set of options. A specification is a fact about the language.

Slip 5 — "a call evaluates its arguments in order"

Counterexample: f(i++, i) yields the pairs (5,5) and (5,6) depending on which argument is evaluated first.

True instead: the barrier is after all the arguments, not between them. Order across arguments is unspecified at best, undefined when one of them writes.

Slip 6 — "an array is one object"

Counterexample: a[i] = a[j] with i different from j is defined: two different elements, one read and one write.

True instead: the rule counts scalar objects. Elements are separate objects; the index variable is one object, which is why a[i] = i++ fails.

The closely confused pair, side by side

Unspecifiedtwo or more possibilities, all correct — f() + g(), one answer, two orderings
Undefinedno requirement at all — f(i++, i), two answers, three orderings
Indeterminately sequencedone finishes before the other, but which one is not stated — two calls that share nothing
Unsequencedmay overlap — two operands of one operator, which is where the rule bites

Only the last line is dangerous, and only when a store is involved. The first three are properties of the language that a correct program may rely on; the fourth is the one to design out.

How the topic is tested, and the procedure that answers it

A question on this material never needs a compiler. It needs the barriers, and a count of what happens between them. The five steps below answer every shape on this page.

Step 1. Find the full expression: up to the semicolon, or the controlling condition of if, while, for or switch.
Step 2. Mark the barriers inside it: the call, &&, ||, the comma operator, ?:.
Step 3. Within each segment, list every access to each variable, and mark which accesses are writes.
Step 4. If two accesses to one scalar are unsequenced and at least one is a write, stop: the answer is that the behaviour is undefined.
Step 5. Otherwise the value is fixed. The only freedom left is the order of calls that share nothing.

Educational interpretation This is a decision procedure, not a theorem about the exam. It works because the standard's rule is local: a conflict is decided by one pair of evaluations inside one segment.

Shape 1 — a count with no side effect

"What does this print?" where every operand only reads: a chain of +, *, comparisons, or two calls that touch nothing shared.

How to answer: steps 1 to 3 find no write, step 4 does not fire, and the arithmetic of step 5 is ordinary. The order of the calls is free and does not matter.

Shape 2 — a count with a guard

"How many times is a[i] read?" with && or || in the condition. Short-circuiting is a consequence of the barrier, not a separate rule.

How to answer: step 2 puts a barrier after the left operand, so the right side is not evaluated at all when the left side settles the answer. Count the evaluations, not the characters.

Shape 3 — the verdict question

"Is the behaviour of this statement defined?" — the shape that rewards the rule. Any expression with two unsequenced accesses to one variable, one of them a store, is the answer.

How to answer: run steps 3 and 4 only. Do not compute a number first; the number is not part of the answer, and computing it is how the trap is sprung.

The trap that catches the most marks

A question that asks for a number, where the correct response is that no number is defined. If the options include a value that "looks right" and no option says the behaviour is undefined, the question has a broken premise.

MCQOriginal practice

With int i = 5; consider the statement i = i++ + 1;. Which statement is correct?

  1. It stores 6 in i, and the behaviour is defined.
  2. It stores 6 in i on both possible orderings, and the behaviour is undefined.
  3. It stores 7 in i, because i++ is 5 and the increment adds one more.
  4. It stores 5 in i, because the assignment happens first.

Answer: B

The two stores — the one inside i++ and the one from the assignment — are unsequenced, so the behaviour is undefined. The page enumerates both orderings and both give 6, which is exactly why the item is worth asking: one answer does not make a statement defined.

Why A appears. It reads the output as the specification. Why C appears. It counts the increment twice. Why D appears. It assumes the assignment is sequenced before the right side, when the standard sequences it after the value computations of both operands.

NATOriginal practice

With int i = 5; the expression i++ + i++ has how many distinct sums over all allowable orderings of its evaluations?

Answer: 2

Six orderings are allowable, and they produce the sums 10 and 11: four orderings give 10, two give 11. The number of orderings is 6 and the number of distinct answers is 2 — the question asks for the second.

The shortcut, and its assumption. Reading both operands as 5 and answering 10 assumes the two reads happen before either store. That is one ordering out of six, and nothing in the standard prefers it.

MSQOriginal practice

Which of these carries a sequence point? Select all that apply.

  1. The end of the left operand of &&.
  2. Between two arguments of a function call.
  3. The end of the left operand of the comma operator.
  4. The end of a full expression, before the next one.

Answer: A, C, D

The call's barrier comes after all the arguments and before the call — not between two of them. That is the distinction the whole topic turns on: f(i++, i) is undefined, and (i++, i) is defined.

Why B is the distractor. The comma character looks identical in both positions; only its role differs.

MCQOriginal practice

int a[10]; int i = 5; a[i] = i++; — which is true?

  1. Defined, because a and i are different objects.
  2. Undefined, because the store to i is unsequenced with the read of i used as the index.
  3. Defined, and it always writes a[5].
  4. Undefined, because an array is a scalar object.

Answer: B

The conflict is on i, not on a: one access writes i, the other reads it, and nothing orders them. The enumeration gives index 5 or index 6.

Why A appears. It is right that a and i are different objects, and wrong about which object conflicts. Why D appears. An array is not one scalar object; that is the mistake of Slip 6.

MCQOriginal practice

void f(int, int); and int i = 5;. The call f(i++, i) is:

  1. defined, and passes (5, 6).
  2. defined, and passes (5, 5).
  3. undefined, because the arguments are unsequenced and one writes what the other reads.
  4. unspecified but defined, because the order of arguments is unspecified.

Answer: C

Unspecified order alone would be harmless. The write makes it undefined, and both (5,5) and (5,6) are reachable, so neither A nor B is the answer.

Why D appears. It stops at the first true fact — the order is unspecified — and misses that a write inside one of the arguments turns unspecified into undefined.

NATOriginal practice

int i = 5; int x = (i++, i); — the value stored in x is ______.

Answer: 6

The comma operator has a sequence point after its left operand, so the store from i++ completes before the right operand reads i. One ordering, one answer, defined.

The edge case. Drop the parentheses and write f(i++, i): the same characters are now a separator, the barrier is gone, and the call is undefined. Parentheses change the meaning of the comma, not the arithmetic.

MSQOriginal practice

Which of these statements have defined behaviour? Select all that apply.

  1. i = i + 1;
  2. i++ + i++;
  3. (i = 3) + (i = 4);
  4. i++; x = i;

Answer: A, D

i = i + 1 has one store and one read, sequenced by the assignment rule. i++; x = i; is two statements, and the semicolon is a sequence point between them.

Why C appears. It has one answer, 7, on every ordering — and it is still undefined, because the two stores to i are unsequenced. One answer is not a definition.

Definitions, in one line each

Side effecta change of state: storing into an object, or calling a function that does
Sequenced beforethe first finishes, side effects included, before the second begins
Unsequencedneither before the other; may interleave
Indeterminately sequencedone before the other, but the standard does not say which
Full expressionan expression that is not part of another

The rule, in one line

Two unsequenced accesses to one scalar object, at least one of them a store: undefined.

It fires if any allowable ordering has such a pair, so a single legal ordering is enough to condemn the statement.

The barriers

Inside one expression: the call (after its arguments), &&, ||, the comma operator, ?:. Between statements: every full expression boundary.

Not a barrier: the comma that separates arguments, and anything inside a single operator's operands.

The three verdicts

One answer, fixed ordernothing written — x = i + 1
One answer, free ordernothing shared — f() + g()
Several or no answera write in the gap — f(i++, i), i++ + i++

The four rewrites

i++ + i++a = i; b = i; i += 2;
a[i] = i++a[i] = i + 1; i++;
f(i++, i)t = i++; f(t, i);
i = i++ + 1i = i + 1;

Every rewrite works by the same move: make each store its own full expression, or put a comma operator between the store and the read.

Four quick checks, answers withheld

1Is x = a + a defined? Why?
2How many distinct answers does i++ + ++i have with i equal to 5?
3Why is i < n && a[i] == x safe and a[i] == x && i < n not?
4Is printf("%d %d", i++, i++) defined? What about scanf("%d %d", &i, &i)?

Answers: (1) yes, two reads never conflict; (2) two — 11 and 12, over six orderings; (3) the barrier sits after the left operand, so the guard must be written first; (4) the first is undefined, the second is defined because there is a sequence point after each conversion specifier.
