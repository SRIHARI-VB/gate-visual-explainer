Topic and objective

TOPIC: File input and output in C — the stream and its four fields, the six fopen modes, the return value of every call that can fail, the file position, and the two rules that decide what a program is even allowed to do (append writes at the end; an update stream needs a positioning call between directions).

LEARNING OBJECTIVE: Given a small C program that opens a file and a description of the file's contents, say what the program writes, how many bytes it writes, and where the position ends up — or say that the program is undefined and therefore has no answer. State for each of the six mode strings whether the open succeeds on an existing file and on a missing one, what happens to the old content, and where the position starts. Read fgetc, fgets, fscanf, fread and fclose as functions that return a count or a signal, and use that count as the only reliable error test.

I read this topic as the part of Section 4's "Programming in C" that no lesson in this repository owned. The existing C fundamentals page covers types, operators and control flow; Strings covers the null terminator; Dynamic memory covers the heap. This page owns the library's file functions, which is where a program stops talking to itself and starts talking to a disk.

Prerequisites

  • C fundamentals — declarations, the difference between a value and a pointer, and the if statement. Everything here is a pointer plus a call.
  • Pointers in C — a FILE * is a pointer, and passing it to a function does not copy the stream.
  • Strings and the null terminator — fgets writes a terminator, and the count of characters is one less than the count of bytes.
  • Functions, scope and the preprocessor — #include <stdio.h>, and why the declaration has to be in scope.
  • Helpful, not required: bitwise operators, for the byte value 255 in the counterexample.

The six ideas, in one line each

  • A FILE * is a handle, not a file: it carries a position, a buffer, an end flag and an error flag.
  • The mode decides three things before your first call: whether the open succeeds, what happens to the old bytes, and where the position starts.
  • Every call that can fail returns a signal, and the signal is a count or a null pointer, never an exception.
  • fgetc returns an int because all 256 byte values are legal data and EOF had to be outside them.
  • Append ignores the position; r+ honours it. Same three statements, one different byte.
  • An update stream needs a positioning call between a write and a read, and between a read and a write. Without it the program has no defined output.

1. Intuition — the counter, the tray and the drawer

Think of a library reading room. You ask at the desk for a book, and the librarian hands you a numbered ticket. The ticket is not the book. It is what you show to ask for the next page, and it is what the librarian updates every time you take a page. FILE * is that ticket. Educational interpretation

Now add a tray. When you write something, the librarian does not walk to the shelf for each page: the pages go into a tray, and the tray is carried to the shelf when it is full or when you say you are finished. That tray is the buffer, and it is why a program can report a successful write that has not reached the disk yet.

Two marks on the ticket matter. One says where you are in the book. The other says whether the last request failed, and why it failed — you ran out of pages, or the book was withdrawn. Those are two different marks, and confusing them is the single most common file-I/O mistake: asking "have we reached the end?" before asking for a page.

2. Formal definitions

Stream. A FILE object is a record of an open file: a file position indicator, a buffer, an end-of-file indicator and an error indicator. FILE * is a pointer to that record.

fopen(name, mode). Returns a pointer to a new stream, or a null pointer on failure. The mode is one of r, w, a, each optionally followed or preceded by b and optionally with one +. Any other string makes the behaviour undefined.

EOF. A negative integer constant, conventionally −1, returned by input functions to report that no value was produced. It is outside the range 0 to 255, which is exactly what makes it usable as a failure signal.

feof and ferror. Report the state of the stream as left by the most recent operation, not the state of the file.

Position. A long offset from the start of the file, read with ftell and set with fseek(stream, offset, origin) where the origin is SEEK_SET, SEEK_CUR or SEEK_END.

3. Visual understanding — what the drawing has to show

The mode table cannot be drawn as prose. So the animation runs the six strings against a simulated four-byte file and a simulated empty directory, and prints the four facts the run produced.

The second thing the drawing must show is that a loop bug is a count, not a warning. So the canvas draws the same three-byte file twice, once read into an int and once into a char, and prints 3 and 1. A picture of a loop would teach the syntax; a count teaches the failure.

4. The four moves every file question needs

  1. Open. Which mode, and does it succeed on the file described?
  2. Position. Where does the mode put it, and what does each call do to it?
  3. Count. What does the call return, and is the return a count of characters, items or elements?
  4. Legality. Does the sequence obey the append rule and the update-stream rule? If not, stop: the program has no answer.

5. Boundaries — when each rule applies

Append. In a, ab, a+ and ab+, data is written at the end of the file regardless of the position. The position still moves, and ftell still reports it.

Update streams. With a +, output cannot be followed by input without an intervening fflush, fseek, fsetpos or rewind, and input cannot be followed by output without an intervening fseek, fsetpos or rewind, unless the input operation met the end of file.

Text streams. Only a zero offset, or an offset produced by ftell, is portable for fseek. On a binary stream any offset is defined.

Buffering. A stream from fopen is fully buffered unless the file is an interactive device. Bytes written are in the buffer until it fills, or until fflush or fclose.

6. Edge cases — the four that decide questions

  • An empty file is not a failed open. The open succeeds, the first read returns EOF and sets the end flag.
  • A byte of value 255. Held in a signed char, it is −1, which is EOF. The loop stops one byte into the file.
  • fgets at the end of a line. With a buffer of four on "hello" and a newline, the first call returns three characters, not four, because the terminator needs a slot.
  • A failed fgets. The buffer is untouched, so printing it prints the previous line again.

7. GATE application — what the reasoning demands

A file question in the exam is almost never about remembering a function name. It is one of four shapes: a mode question (which open succeeds, what survives), a count question (how many bytes or characters), a position question (what ftell reports), or a legality question (is this sequence defined at all). The fourth shape is the one that separates a candidate who has memorised the table from one who has read the rule, because its correct answer is "no output can be predicted".

Worked examples — every number below is computed on this page

Two running files throughout: a text file holding GATE (four bytes) and a binary file holding the bytes 97, 255, 98. The first answers mode and count questions; the second answers the char-versus-int question, because 255 is the one byte value that collides with EOF in a signed char.

Example 1 — the mode table, run rather than quoted

file "GATE" = 4 bytes

  1. fopen("f","r") — opens, size stays 4, position 0, read only.
  2. fopen("f","w") — opens, size becomes 0, position 0, write only.
  3. fopen("f","a") — opens, size stays 4, position 4, write only.
  4. fopen("f","r+") — opens, size 4, position 0, both directions.
  5. fopen("f","w+") — opens, size 0, both directions.
  6. fopen("f","a+") — opens, size 4, reads from 0, writes at 4.

On a name that does not exist, r and r+ fail and the other four create the file. The size column is the whole difference between w and a.

Example 2 — one byte of value 255, two loops

file: 97, 255, 98   ('a', 0xFF, 'b')

  1. int c; while ((c=fgetc(fp))!=EOF) — reads 97, 255, 98, then fails. 3 bytes.
  2. char c; same loop — 255 narrowed to a signed char is −1, which equals EOF. 1 byte.
  3. EOF is −1, outside 0 to 255, so it can never collide with data in an int.
  4. Whether plain char is signed is implementation-defined, so the second answer is a fact about a platform, not about C.

This is the counterexample that makes the rule memorable: the danger is not a rare character, it is the one byte value that is also the failure signal.

Example 3 — the end-of-file loop that runs once too often

file: "abc" (3 bytes)

The wrong loop tests feof before reading:

while (!feof(fp)) { c = fgetc(fp); putchar(c); }

  1. Iteration 1: feof is 0, read 'a'.
  2. Iteration 2: feof is 0, read 'b'.
  3. Iteration 3: feof is 0, read 'c' — the last byte. feof is still 0, because the read succeeded.
  4. Iteration 4: feof is 0, the read fails and returns −1, and only now is feof set. putchar((char)−1) writes one byte of value 255.

Four iterations on a three-byte file, and one junk byte. The correct loop reads into an int and stops on the read's own return value: three iterations, no junk.

Example 4 — fgets with a buffer of four

file: "hello\n" (6 bytes), n = 4

  1. Call 1 returns hel plus a terminator: 3 characters, because n − 1 = 3.
  2. Call 2 continues: lo plus the newline, plus a terminator. The newline is kept.
  3. Call 3 returns NULL, and the buffer is untouched.
  4. A loop of while (!feof(fp)) { fgets(buf,16,fp); printf("%s",buf); } on a two-line file makes 2 successful reads and 3 prints.

The duplicate is not a duplicated read. It is a print of a string nobody read, because a failed fgets leaves the buffer exactly as it was.

Example 5 — counting bytes written

for (i = 1; i <= 10; i++) fprintf(fp, "%d\n", i);

  1. Digits: nine single-digit numbers (1 to 9) plus two digits for 10 = 11.
  2. Newlines: 10.
  3. Total: 21 bytes, confirmed by writing the bytes out and measuring the simulated file.

The return value of each fprintf is the number of characters that conversion produced, so the loop's own returns sum to the same 21.

Example 6 — the same three statements in two modes

fopen("t.txt", MODE); fseek(fp,0,SEEK_SET); fputc('X',fp);
t.txt before: "abc"

  1. Mode "a": opened at 4? no — at 3, the end. Sought to 0. Position after the write is 4, and the file is abcX.
  2. Mode "r+": opened at 0, sought to 0, position after the write is 1, and the file is Xbc.
  3. The write in "a" ignored the seek entirely, because the mode says writes go to the end.

Same statements, same seek, one different byte. This is the pair that a mode question is really testing.

The four boundary cases

  • An empty file. The open succeeds with size 0; the first read returns EOF and sets the end flag. There is no null pointer anywhere in this story.
  • A missing file. r and r+ return a null pointer, create nothing, and set no end flag, because there is no stream to hold one.
  • A byte of value 255. Legal data, and the one value that collides with EOF after a narrowing conversion to a signed char.
  • A buffer of size 1. fgets(buf, 1, fp) can store only the terminator, so it reads nothing and returns an empty string, not NULL, for as long as there is input left.

Where the standard says "implementation-defined"

These are the places a well-posed question avoids, and where an answer depends on the platform rather than the language:

  • Whether plain char is signed — this decides the 255 counterexample.
  • The initial read position of a+; the common libraries start it at 0.
  • An fseek offset in a text stream that is not 0 and not from ftell.
  • The file size after seeking past the end and writing — a hole is created, and its size is not fixed by C.
  • Whether errno is set by a failing fopen; POSIX requires it, C alone does not.
  • fflush on an input stream: undefined in C, a discard of read-ahead on POSIX.

Closely confused pairs

EOF versus feof. EOF is the value an input call returns when it produced nothing. feof is a query about the last operation. After reading the final byte, the call returned data and feof is 0; after the next call, the call returned EOF and feof is nonzero. One is a value, the other is a report.

fflush versus fclose. fflush pushes the buffer out and leaves the stream open and usable. fclose flushes and then releases the stream, after which any use is undefined.

w versus a. Both write. w destroys the old content at the moment of the open; a keeps it and puts every write after it.

fseek versus rewind. rewind is a seek to the start and clears the error indicator; a bare fseek to the start clears the end indicator but not the error one.

The one legality case that matters most

FILE *fp = fopen("t.txt", "r+");
int c = fgetc(fp); /* input */
fputc('Z', fp); /* output, with no positioning call */

This is not "the write goes at position 1" and it is not "the write overwrites the byte just read". It is undefined: the standard requires an intervening fseek, fsetpos or rewind before output can follow input on an update stream. Adding fseek(fp, 0, SEEK_SET); makes the program defined, and then the write lands at 0.

So the correct answer to a question that shows this code and asks for the output is that there is no output to compute — and that is a stronger answer than any particular guess.

Misconception 1 — "a failed fopen gives an empty stream"

Wrong. It returns a null pointer. There is no stream: no position, no buffer, no flags. An empty file is the different case where the stream exists and the first read reports the end.

The test that separates them: compare the pointer with NULL for the first, and check the first read's return value for the second.

Misconception 2 — "feof tells me whether I am at the end"

Wrong, in the sense that matters. feof reports the last operation. After the read that returned the last byte it is still 0, and it becomes nonzero only when a read fails.

Counterexample: the three-byte file read by while (!feof(fp)) makes four iterations, not three, and writes one byte of value 255.

Misconception 3 — "char is fine for fgetc, because a character is a character"

Wrong. fgetc returns an int precisely because 256 byte values are all legal data and the failure signal had to sit outside them.

Counterexample: the file 97, 255, 98 read into a signed char stops after one byte, because 255 narrowed is −1, which is EOF.

Misconception 4 — "fseek then write always writes there"

Wrong in append mode. In a and its variants the write goes to the end regardless of the position. The position still moves; the write ignores it.

Counterexample: abc, opened "a", seek to 0, write X, gives abcX — while the same calls in "r+" give Xbc.

Misconception 5 — "if fprintf succeeded, the data is on the disk"

Wrong. The bytes go into the buffer. A count reported by fprintf is a count of characters formatted, not of bytes written to the disk.

Counterexample: five characters written to a "w" stream leave the file empty until fflush or fclose. That is why a crash can lose output the program already reported.

Misconception 6 — "mixing reads and writes is always allowed on r+"

Wrong. The two directions share one buffer, so a positioning call is required between them. Without it the program is undefined, not merely surprising.

The fix is one line: fseek, fsetpos or rewind between the read and the write — and fflush is also allowed when the order is output then input.

Five question shapes, and the procedure for each

No previous-year item is quoted on this page, because one with a verifiable year, set and question number was not located for this run. What follows is the shape of the question and the procedure that answers it, which is what transfers to an unseen paper.

Pattern 1 — which mode opens

Shape. A file exists or does not; a mode string is given; which of the options is true?

Procedure. Read the first letter first: r needs the file, w empties it, a keeps it. Then read the +: it adds a direction and changes nothing about existence. Then read the b: it changes nothing except newline handling and seek offsets.

The trap. Options that differ only in whether the old content survives. Answer that column first and most options fall away.

Pattern 2 — how many bytes

Shape. A loop of fprintf or fputc; how large is the file, or how many characters are written?

Procedure. Count characters, not calls: digits, separators, newlines. Then check the mode — in a the old bytes are still there and must be added; in w they are gone.

Check. The ten numbers 1 to 10 with a newline each give 11 digits and 10 newlines, so 21.

Pattern 3 — what the loop prints

Shape. A read loop, a small file, and four options that differ in length or in the last item.

Procedure. Simulate the loop on paper, one iteration per line, and mark at each step: the value returned, the position, and the two flags. Stop when the read fails, not when you think the file ends.

Check. A three-byte file under while(!feof) gives four iterations; the same file under a read-and-test loop gives three.

Pattern 4 — where the position is

Shape. Some reads, one fseek, then ftell, or a read after the seek.

Procedure. Start at the position the mode set. Add one per byte read. Apply the seek as base + offset with the base taken from the origin. A successful seek clears the end flag, which is what makes the next read work.

Check. On eleven bytes, five reads put the position at 5; fseek(−3, SEEK_END) puts it at 8.

Pattern 5 — is this program even defined?

Shape. Read then write, or write then read, on a + stream, or a use of a pointer that may be null.

Procedure. Check the pointer first. Then check the interleaving: input then output needs a positioning call; output then input needs fflush or a positioning call. If either is missing, the answer is "undefined", and a paper that offers a definite output has made an error.

Why it matters. This is the one shape where the correct answer is a statement about the language rather than a number, and it is the shape most often answered by guessing.

MCQOriginal practice question

A file f.txt exists and holds the four bytes GATE. A program runs

FILE *fp = fopen("f.txt", "w");
fclose(fp);

What is the size of f.txt afterwards?

(A) 4   (B) 0   (C) undefined, because nothing was written   (D) 1

Answer: B

w truncates the file at the moment of the open, before any write happens. The size column of the mode table shows 4 before and 0 after.

Why A is wrong. It assumes the old bytes survive an open in write mode. They do not.

The distinction being tested. w destroys; a keeps. Nothing else in the mode string changes that.

MCQOriginal practice question

Which one of the following calls returns a null pointer when the named file does not exist?

(A) fopen("x","a")   (B) fopen("x","w+")   (C) fopen("x","r+")   (D) fopen("x","a+")

Answer: C

Only the r family requires the file to exist. r+ is still the r family, so it fails on a missing file and creates nothing.

Why B is wrong. w+ creates the file and empties it; the plus adds reading, and does not add an existence requirement.

The trap. Reading the plus sign as "the safe, general mode". It is not safer; it is the same family with one more direction.

NATOriginal practice question

A text file is created by

for (i = 1; i <= 10; i++) fprintf(fp, "%d\n", i);

How many bytes does the file hold? (Assume one byte per character, no translation.)

Answer: 21

Digits: 1 to 9 contribute 9, and 10 contributes 2, so 11. Newlines: 10. Total 21.

Why 20 is wrong. It counts ten numbers as ten characters and forgets that 10 has two digits.

The trap. Counting calls instead of characters. The count is what the file holds, not how many times the function ran.

NATOriginal practice question

A binary file holds 11 bytes. The stream is at position 0. The program executes

fseek(fp, -3, SEEK_END);

What does ftell(fp) report?

Answer: 8

SEEK_END puts the base at 11, and the offset is −3, so the position is 8. The three bytes at 8, 9 and 10 are the last three of the file.

Why 3 is wrong. It reads the offset as an absolute position and ignores the origin.

The assumption being used. The stream is binary. On a text stream this offset is implementation-defined unless it came from ftell.

MCQOriginal practice question

t.txt holds abc. The program runs

fp = fopen("t.txt", "a");
fseek(fp, 0, SEEK_SET);
fputc('X', fp);
fclose(fp);

What does t.txt hold afterwards?

(A) Xbc   (B) abcX   (C) X   (D) undefined

Answer: B

In an append mode the write goes to the end of the file regardless of the position, so X lands after abc.

Why A is wrong. It is what the same three statements do in "r+", where the position is honoured. That is the pair this question tests.

Why D is wrong. Seeking and writing in an append stream is perfectly defined; only the + interleaving rule can make a program undefined here.

MSQOriginal practice question

Which of the following statements are TRUE?

(A) After a read that returns the last byte of a file, feof returns nonzero.
(B) fgets stores at most n−1 characters plus a terminating zero.
(C) fclose returns EOF if the flush failed.
(D) fseek on a stream opened "r" can clear the end-of-file indicator.

Answer: B, C, D

B. The size argument includes the terminator's slot, so the characters stored are at most n−1.

C. A successful close returns 0; a failed flush makes it return EOF, and that is the last report the library gives.

D. A successful fseek clears the end-of-file indicator, which is why the next read can succeed.

Why A is false. That read succeeded, so the indicator is still 0; only a read that fails sets it. This is the whole content of the four-iteration example.

MCQOriginal practice question

A binary file holds exactly three bytes: 97, 255, 98. The program is

char c;
while ((c = fgetc(fp)) != EOF)
    putchar(c);

On a platform where plain char is signed, how many times does the body of the loop run?

(A) 0   (B) 1   (C) 2   (D) 3

Answer: B

The first byte, 97, is stored as 'a' and is not EOF, so the body runs once. The second byte, 255, narrowed to a signed char, is −1, which compares equal to EOF, so the loop stops.

Why D is wrong. It is the answer for int c, where all three bytes are distinguishable from EOF.

The assumption in the question. Signed char. Where char is unsigned the answer is D, which is why the platform is stated — the C standard does not fix it.

MCQOriginal practice question

A file holds the text hello followed by a newline. The program is

char buf[4];
fgets(buf, 4, fp); /* call 1 */
fgets(buf, 4, fp); /* call 2 */

What does buf hold after call 2?

(A) hell   (B) o\n   (C) lo\n   (D) llo

Answer: C

Call 1 stores h, e, l and a zero — three characters, because n−1 = 3. Call 2 continues from there: l, o, the newline, and a zero.

Why A is wrong. It uses all four slots for characters and leaves no room for the terminator.

The trap. The newline is kept. A question that offers lo without the newline is testing exactly that.

MCQOriginal practice question

t.txt holds abc. The program is

fp = fopen("t.txt", "r+");
c = fgetc(fp);
fputc('Z', fp);
fclose(fp);

Which one of the following is TRUE?

(A) t.txt becomes Zbc
(B) t.txt becomes aZc
(C) The program is undefined, because no positioning call separates the read from the write
(D) t.txt becomes abcZ

Answer: C

On an update stream, input cannot be followed by output without an intervening fseek, fsetpos or rewind, unless the input met the end of file. Here it did not, so the program is undefined.

Why B is wrong. It is the plausible guess — the position is 1 after one read — and it is exactly what the standard refuses to promise.

The fix. Insert fseek(fp, 0, SEEK_SET); and the answer becomes Zbc, which is option A.

NATOriginal practice question

A text file holds the eight characters 12 34 x. The program executes

int a, b, c, n;
n = fscanf(fp, "%d %d %d", &a, &b, &c);

What value does n hold?

Answer: 2

The first two conversions read 12 and 34. The third meets the letter x, which is not an integer, so it fails and the call returns the number of items assigned: 2.

Why 3 is wrong. It assumes every conversion succeeds. A conversion that fails does not assign, and does not consume the offending character.

The trap. The position is left on the x, so a second fscanf with the same format fails again — a loop that ignores the count does not terminate.

One-screen revision sheet

open → position → count → legality → close

The six modes

r   existing only, read, pos 0
w   truncates or creates, write, pos 0
a   creates if missing, write, pos end
r+  existing only, both, pos 0
w+  truncates or creates, both, pos 0
a+  creates if missing, read from 0, write at end

The five return values

fopen    a pointer, or NULL
fgetc    an int 0..255, or EOF (−1)
fgets    the buffer, or NULL
fscanf   items assigned
fread     elements read
fclose   0, or EOF

The three positions

SEEK_SET  from the start
SEEK_CUR  from the current position
SEEK_END  from the end (negative counts back)

ftell → the offset as a long
rewind → seek to 0 and clear the error flag

The two rules that make a program legal

Append. In a and its variants, writes go to the end whatever the position is.

Update. On a + stream, output then input needs fflush or a positioning call; input then output needs a positioning call, unless the input met the end of file.

The traps, ranked by how often they cost marks

  1. Testing feof before a read, and printing the buffer anyway.
  2. Storing fgetc in a char.
  3. Assuming a failed fopen gives an empty stream.
  4. Forgetting that w destroys the old content at the open.
  5. Reading then writing on r+ with no positioning call.
  6. Counting bytes when fread counts elements.
  7. Forgetting that fgets keeps the newline.

Language behaviour

cppreference, fopen — the six mode strings, the table of what each does to an existing and a missing file, the append rule ("data is written to the end of the file regardless of the current position"), the b and x flags, and the update-stream interleaving rule. Used for the mode table and for the legality checks.

cppreference, fgetc — the return value as an unsigned char converted to int, and EOF on failure, with the end indicator set only when the failure was end of file.

cppreference, feof — the note that the function reports the state left by the most recent I/O operation, so that after a read returning the last byte it still returns zero. ISO/IEC 9899 clause 7.21.5.3 is the primary text behind the interleaving rule; the standard itself was not downloaded for this run, and the wording quoted here is cppreference's summary of it.

Where the standard leaves a choice

Six behaviours are marked implementation-defined or undefined on this page rather than answered: whether plain char is signed; the initial read position in a+; a fseek offset in a text stream that did not come from ftell; the file size after seeking past the end and writing; whether errno is set by a failing fopen; and fflush on an input stream. Each is labelled where it appears, so that a learner can tell a fact about C from a fact about one library.
