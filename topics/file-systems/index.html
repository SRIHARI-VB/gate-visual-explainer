Topic and objective

TOPIC: File systems — the file, the directory and the inode; allocation by contiguous run, by linked chain, by file allocation table and by indexed pointers; free-space management with bitmaps and lists; path resolution and directory operations; hard and symbolic links; and the space arithmetic that every question in this topic reduces to. This is the clause "File systems" of Section 8 of the official GATE 2027 CS syllabus.

LEARNING OBJECTIVE: Given a configuration — block size, address width, number of direct and indirect pointers, disk size, pointer width — compute the maximum file size, the size of the allocation or free-space table, the number of blocks a file occupies, the bytes wasted in its last block, and the number of disk accesses an operation costs; and say which of two allocation schemes can leave external fragmentation and why.

I read this topic as three tables and one count. A name is in a directory, the metadata and block pointers are in an inode, and the bytes are in data blocks. Every question asks either how big one of those tables is, or how many of them must be read. The animation draws the three tables and prints its arithmetic on the canvas.

Prerequisites

  • Powers of two and unit conversion. 210 = 1 K, 220 = 1 M, 230 = 1 G, and the difference between a million bytes and a mebibyte. The whole topic is one division and one ceiling.
  • Paging arithmetic. A block is to a disk what a page is to memory, and "offset bits" behaves the same way. Built in Memory Management and Virtual Memory.
  • Disk geometry and access time. Seek, rotation and transfer are named here only where a file-system question needs them. The scheduling policies are their own lesson. Built in Memory Hierarchy and Cache for the cache side.
  • Trees, only as a shape. An inode's indirect pointers form a tree whose depth is the level of indirection. Built in Trees, Binary Search Trees and Heaps; B and B+ trees are the indexing lesson, not this one.

Nothing from concurrency is assumed. Where a claim depends on an assumption — that the inode is not cached, that a directory lookup is one block — the assumption is stated in the scene and again in the Edge cases tab.

The five ideas to leave with

  1. A file is three things in three places: a name in a directory, metadata and pointers in an inode, bytes in blocks. Every question reads one of those and counts the cost.
  2. Allocation schemes differ only in what the inode holds — a start and a length, one pointer, or many pointers. That single difference sets fragmentation and access cost.
  3. An inode's maximum file size is the sum of its pointer terms: direct, then single, then double, each multiplied by the fan-out of the level above. Pointers per block is block size divided by address size.
  4. Space arithmetic is three subtractions: the tail of the last block, the pointer stored inside each block, and the table the scheme needs. Every one of them is a division and a ceiling.
  5. Deleting a name frees nothing until the link count reaches zero. A hard link adds a name to an inode; a symbolic link adds an inode holding a path.

Intuition: a coat check with three ledgers

A coat check does not remember your coat by where it hangs. It hands you a numbered tag, keeps one ledger that maps your tag to a slot number, and hangs the coat in whatever slot is free. Rename the tag and the coat does not move. Lose the tag and the coat is still there but you cannot ask for it.

A file system is that coat check with one extra ledger. The directory maps a name to an inode number. The inode maps that number to the metadata and to the slots. The disk itself is the rack, a numbered array of slots called blocks. Nothing in the design requires the slots of one coat to be adjacent, which is why a file can grow without moving and why a fragmented rack still works.

Educational interpretation The analogy fixes two things: the name is not the data, and the ledger is what makes scattered storage workable. It does not fix what happens when the rack runs out of tags — that is the inode-table limit, which is a separate and easily forgotten failure.

Definition: the file

A file is a named, contiguous logical sequence of bytes, stored on secondary storage and manipulated as a unit. Its attributes — name, identifier, type, location, size, protection, owner, timestamps — are metadata. Its operations are create, open, read, write, reposition, delete, truncate and append.

Two access methods matter. Sequential access reads in order, which is all a tape can do. Direct access reads block k without reading 1 to k − 1, which needs the allocation scheme to keep an index.

Verified fact The file-and-attributes vocabulary, the access methods and the directory operations are the standard presentation in the operating-systems texts listed in the Sources tab; the syllabus clause itself is the three words "File systems".

Definition: inode, directory, block

An inode (index node) is a fixed-size record holding one file's metadata and its block pointers. It is identified by an integer, the inode number, unique within one volume.

A directory is itself a file whose contents are entries of the form (name, inode number). A block is the unit of disk allocation: the smallest amount of space that can be given to a file.

The distinction that decides most questions: in the classic layout the directory stores only the name and the inode number. The block pointers are in the inode. So a directory lookup and an inode read are two separate accesses.

Assumptions this lesson works under

  • The inode is not cached unless a question says so. Then opening a file costs a directory read, an inode read and a data read.
  • A directory entry is found in one block read; a linear list may need a scan, which is counted separately and named as a scan.
  • One disk access is one block read or one block write. Seek and rotation are not added unless the question gives them.
  • Indirect blocks hold block numbers only, never file data.

The one distinction to fix now

A file name and a file identifier are different. Two names can point at one inode — that is a hard link — and one name can point at an inode whose content is another name — that is a symbolic link. Once those two sentences are clear, the whole links scene is bookkeeping.

Mathematical derivation If two directory entries hold the same inode number, the inode must record how many entries point at it, or it cannot know when to free its blocks. That integer is the link count, and it is forced by the design rather than added to it.

Definition: allocation, formally

Let a file have n blocks of B bytes. An allocation scheme is a rule that assigns each of the n logical block numbers 0 … n − 1 to a physical block number, together with a data structure that stores the assignment.

Contiguous: the rule is physical = start + k. The structure is the pair (start, length). Consequence: n consecutive blocks must be free, so free space can be plentiful and still unusable — external fragmentation.

Linked: the rule is "block k is named inside block k − 1". The structure is the first and last block numbers in the inode. Consequence: any free block will do, and reaching block k costs k pointer follows.

File allocation table: the same rule, but every next-pointer is collected into one table with one entry per disk block. The chain is unchanged; where it is stored is not.

Indexed: the rule is "the k-th entry of the index block holds block k". The structure is one index block, or a tree of them when one is not enough. Consequence: any free block will do, and block k costs one extra read.

Definition: free-space management

A bitmap (bit vector) has one bit per disk block: 1 for free, 0 for allocated. Its size depends only on the number of blocks, never on how many are free.

A free list chains the free blocks themselves, storing free block numbers inside free blocks. Its size depends on how many blocks are free.

Grouping batches many free numbers into each list block; counting stores (first free block, run length) per entry. Both are the same division with a different number of entries per block.

Definition: the inode's pointer tree

Let p = ⌊B / a⌋ be the number of block addresses that fit in one block, where B is the block size and a the address width. With d direct, s single-indirect, D double-indirect and T triple-indirect pointers, the number of data blocks reachable is

blocks = d + s·p + D·p² + T·p³

and the maximum file size is that count times B. Every symbol is a count of pointers except p, which is the fan-out of one level.

Definition: links and mounting

A hard link is a directory entry naming an existing inode. It increments the inode's link count and adds no data. A symbolic link is a file whose content is a path; it has its own inode and leaves the target's link count unchanged.

Mounting makes the root of one file system reachable through a directory of another, so one path can span several volumes. The root directory of a volume must sit at a fixed, known location, because it must be found before any path can be resolved.

Worked examples, page 1 of 2 — size and space

Every number below is produced by the model in this lesson and re-checked on load. Where a step is a definition rather than a calculation, the step says so.

Example 1 — the largest file an inode can address (GATE 2019)

12 direct, one single-indirect and one double-indirect pointer; 4 KB blocks; 32-bit block addresses.

1. Fan-out. One block holds 4,096 / 4 = 1,024 block addresses. That number is p.

2. Direct. 12 pointers reach 12 blocks.

3. Single indirect. One pointer reaches an index block of 1,024 addresses, so 1,024 blocks.

4. Double indirect. One pointer reaches an index block of 1,024 addresses, each of which reaches an index block of 1,024, so 1,024 × 1,024 = 1,048,576 blocks.

5. Total. 12 + 1,024 + 1,048,576 = 1,049,612 blocks × 4,096 B = 4,299,210,752 B = 4.00395 GB.

6. Round. To one decimal place, 4.0 GB.

Mathematical derivation The double-indirect term is 99.9 per cent of the answer; the direct and single terms move the second decimal place only.

Example 2 — the same question with small blocks (GATE 2012)

8 direct, one indirect and one doubly indirect pointer; 128-byte blocks; 8-byte addresses; a 300 GB disk.

1. Fan-out. 128 / 8 = 16 addresses per block.

2. Blocks. 8 + 16 + 256 = 280 blocks.

3. Bytes. 280 × 128 = 35,840 B = 35 KB.

4. Why the disk size is a distractor. The inode structure limits the file, not the disk: a 300 GB volume with this inode still caps a file at 35 KB. That is why "dependent on the size of the disk" is wrong.

Trap 280 is the block count. The option list contains both a block-flavoured and a byte-flavoured distractor; only one is a size.

Example 3 — what a FAT costs the disk (GATE 2014 Set 2)

100 × 106 bytes of disk, 103-byte blocks, 4 bytes per FAT entry.

1. Blocks. 100,000,000 / 1,000 = 100,000 blocks.

2. Table. One entry per block × 4 B = 400,000 B, which is 400 blocks of the same disk.

3. Data. 100,000,000 − 400,000 = 99,600,000 B.

4. Answer in millions. 99.6.

Mathematical derivation The table and the data are two parts of one disk, so they must add back to the whole. Checking that addition catches the common slip of answering 100.

Example 4 — a pointer inside every block (GATE 2025 Set 1)

512 MB disk, 64 KB blocks, 4-byte next-pointer in each data block, file of 1 MB.

1. Usable capacity. 65,536 − 4 = 65,532 B per block.

2. Blocks needed. 1,048,576 / 65,532 = 16.0009, so 17 blocks. Sixteen blocks hold 1,048,512 B — 64 bytes short.

3. Waste. The seventeenth block holds 64 B of data, so 65,532 − 64 = 65,468 B of usable space are unused.

Trap Subtracting the 64 bytes from 65,536 gives 65,472 and subtracts from the whole block rather than the usable part. The pointer is not available for data, so it cannot be part of the waste.

Worked examples, page 2 of 2 — accesses and tables

Two counting questions and two table-size questions. The counting ones are decided by the scheme; the table ones by a division and a ceiling.

Example 5 — one insertion, two schemes (GATE 2022)

File systems A (contiguous) and B (linked), each holding 100 blocks. Insert a block after the 50th; its data is already in memory; the control blocks are in memory.

1. Contiguous, reads. Blocks 51 to 100 must move, so 50 reads.

2. Contiguous, writes. Those 50 blocks are rewritten, plus the new block: 51 writes. nA = 101.

3. Linked, reads. Walk to block 50: 50 reads.

4. Linked, writes. Write the new block, and rewrite block 50's pointer: 2 writes. nB = 52.

5. Sum. 101 + 52 = 153.

Mathematical derivation Nothing in the count depends on block size or disk geometry; only on which blocks must be touched.

Example 6 — how many blocks a free list needs (GATE 2026 Set 2)

16 GB disk, 2 KB blocks, 32-bit block numbers, a 4-byte pointer to the next list block in each list block.

1. Blocks. 234 / 211 = 223 = 8,388,608.

2. Entries per list block. (2,048 − 4) / 4 = 511.

3. Divide. 8,388,608 / 511 = 16,416.06.

4. Ceiling. 16,417 list blocks. Check: 511 × 16,416 = 8,388,576, which is 32 numbers short.

Mathematical derivation The 32 leftover numbers need a block of their own, and a block cannot be split, so only a ceiling is correct.

Example 7 — the size of a bitmap (original practice, not a PYQ)

A 1 TB disk with 4 KB blocks and one bit per block.

1. Blocks. 240 / 212 = 228 = 268,435,456.

2. Bits. One per block, so 228 bits.

3. Bytes. 228 / 8 = 225 = 33,554,432 B = 32 MB.

4. In blocks. 33,554,432 / 4,096 = 8,192 blocks.

Mathematical derivation A bitmap costs one bit per block, so its size as a fraction of the disk is fixed by the block size alone: 1 / (8 × 4,096), which is about 0.003 per cent.

Example 8 — six reads for one path (original practice, not a PYQ)

Open /usr/lib/libc.so with nothing cached, one block per directory lookup.

1. Read the root directory block and find usr: 1 read.

2. Read usr's inode, then the usr directory, and find lib: 2 reads.

3. Read lib's inode, then the lib directory, and find libc.so: 2 reads.

4. Read libc.so's inode: 1 read.

5. Total. 1 + 2 + 2 + 1 = 6, before any data block.

Educational interpretation The count depends on the assumption that each lookup is one block. A question that gives a directory layout and asks for a count is asking you to state that assumption and then add.

Counterexample: "a bigger disk allows a bigger file"

GATE 2012 gives a 300 GB disk and an inode with 8 direct, one indirect and one doubly indirect pointer, with 128-byte blocks and 8-byte addresses. The answer is 35 KB.

Mathematical derivation The maximum file size is bounded by the pointer structure, not the disk. 8 + 16 + 256 = 280 blocks × 128 B = 35,840 B. The disk size is in the question to test exactly this.

Counterexample: "free space is the only limit on new files"

A volume formatted with 1,000,000 inodes of 128 bytes spends about 122 MB on its inode table and can never hold more than a million files, however much data space is free. Creating the million-and-first file fails with no space, although gigabytes are free.

Mathematical derivation The inode array is allocated at format time and cannot grow, so the file count is capped by a constant chosen before any file existed.

Boundary: the smallest file still costs a whole block

A 1-byte file occupies one 4 KB block, so 4,095 bytes are wasted — 99.98 per cent. Under indexed allocation it may also cost an index block, doubling the waste.

This is why "no external fragmentation" does not mean "no waste", and why the 2017 answer (linked and indexed only) is about external fragmentation specifically.

Boundary: the triple indirect dominates (GATE 2004)

10 direct, one single, one double and one triple indirect pointer; 1 KB blocks; 4-byte addresses. Fan-out is 256.

The triple term is 256³ blocks × 1 KB = 234 bytes. The direct and single terms together are 272,384 B, which is 0.0016 per cent of the total.

Mathematical derivation At three levels the deepest term is 224 times the shallowest, so a maximum-size question with a triple indirect is decided by that term alone.

The word "necessarily" (GATE 2021 Set 1)

In a linear-list directory, create and rename must scan the whole list because both must prove a name is unused. Delete and open stop when they find the entry, so they do not necessarily scan it all — they may, but need not.

A multiple-select question with "necessarily" is asking about the worst case that is forced, not the worst case that is possible.

Boundary: a symbolic link can dangle, and costs a lookup

A symbolic link stores a path, so deleting the target leaves a link that fails only when followed. Following it also costs an extra inode read, which is why a path full of symbolic links is measurably slower to resolve.

A hard link cannot dangle: the inode exists as long as any name points at it. It also cannot cross a file system, because inode numbers are unique only within one volume.

Boundary: 511, not 512

A 2 KB list block divided by 4-byte numbers is 512 — but the next-list-block pointer consumes one entry, so 511 numbers fit. On the 2026 configuration that is 16,417 blocks instead of 16,384.

Mathematical derivation Any structure that stores its own continuation inside itself loses one slot to that continuation. The same subtraction appears in linked allocation, where each data block loses 4 bytes.

What is deliberately not covered here

Disk scheduling (FCFS, SSTF, SCAN, C-SCAN, LOOK) is a separate coverage-tracker entry and its own lesson; this one counts accesses but does not order them. Journaling, copy-on-write, log-structured file systems, RAID and network file systems are outside the syllabus clause. Sparse files and extents are named in the Misconceptions tab only, because the clause does not reach them.

"The file name is the file"

Why it tempts: you open files by name, so the name feels like the identity.

Minimal counterexample: two directory entries holding the same inode number are two names for one file. Renaming one changes nothing about the other's content; deleting one frees nothing.

Correct rule: the inode is the identity. The name is an entry in a directory that maps to it, and the link count records how many entries do.

"Indexed allocation removes fragmentation"

Why it tempts: the GATE 2017 answer says indexed avoids external fragmentation, which is true.

Minimal counterexample: a 1-byte file under indexed allocation occupies one data block and one index block — 8 KB for 1 byte, which is 99.99 per cent waste.

Correct rule: it removes external fragmentation. Internal waste in the last block, and the index block itself, remain. Name which kind you mean.

"A larger block is better"

Why it tempts: larger blocks mean fewer seeks and longer transfers, so throughput rises.

Minimal counterexample: a volume of 1-byte files with 64 KB blocks wastes almost the entire disk, and its FAT grows with the block count only if blocks are small — so the two effects pull in opposite directions.

Correct rule: block size trades throughput against space. There is no single optimum without knowing the file-size mix.

"Deleting a file frees its space"

Why it tempts: deleting is the operation you use to reclaim space.

Minimal counterexample: with two hard links, deleting one drops the count to 1 and frees nothing. Free space appears only when the second name goes.

Correct rule: the inode is freed at link count zero, not at first unlink. An open file can also outlive its last name.

"Indirect pointers point at data"

Why it tempts: the inode's pointer array holds block numbers, and data blocks also hold block numbers in linked allocation.

Minimal counterexample: in the 2019 configuration, a 50 KB file fits in the 12 direct blocks and reads no indirect block at all. Its size does not change because indirect pointers exist.

Correct rule: an indirect block holds addresses only. The tree above the data is paid for only when the file is large enough to need it.

"Block count and file size are the same answer"

Why it tempts: the arithmetic produces a block count first, and it is the number you just wrote down.

Minimal counterexample: GATE 2012: 280 blocks, 35 KB. The distractor list contains 280 and 280 Kbytes-shaped options; the size is 35,840 B.

Correct rule: write the unit into the working line — "280 blocks × 128 B" — before dividing, and the slip cannot survive.

Four question shapes, and the reasoning each demands

The archives tag file-system items to 2004, 2012, 2014 Set 2, 2017 Set 2, 2019, 2021 Set 1, 2022, 2025 Set 1 and 2026 Set 2. Read as a group, they ask four things: how big a table is, how many blocks a file needs, how many accesses an operation costs, and which scheme has which property. The first three are arithmetic with one ceiling; the fourth is a definition.

Shape 1 — maximum file size from an inode

Reasoning: fan-out = block ÷ address; then direct + single·p + double·p² (+ triple·p³); then × block size.

Common wrong approach: adding the indirect blocks themselves, or writing p² as 2p.

Check: the deepest term present should be 99 per cent or more of the total. If it is not, you have mis-levelled something.

Shape 2 — table size (FAT, bitmap, free list)

Reasoning: count the blocks, then multiply by the entry width, or divide by the entries per block. Subtract the link if the structure stores its own continuation.

Common wrong approach: forgetting that the table lives on the same disk, so the largest file is disk minus table.

Check: table plus data must add back to the whole disk.

Shape 3 — accesses for one operation

Reasoning: list the blocks that must be read and the blocks that must be written. Shifted blocks cost a read and a write each. Walked blocks cost a read each. The new block costs one write.

Common wrong approach: counting a read of data the question already put in memory.

Check: every access you counted should correspond to a block you could point at on a diagram.

Shape 4 — a property question (MCQ/MSQ)

Reasoning: go back to the definition. External fragmentation means free space in the wrong shape; a full scan means proving absence; a hard link means the same inode.

Common wrong approach: answering from the reputation of a scheme rather than its definition.

Check: if your answer would change when the word "necessarily" is added or removed, you are answering a different question.

The decision procedure in one line

Convert everything to blocks, write the fan-out, and then ask whether the question wants a size (multiply), a count (divide and take a ceiling), or a cost (list the reads and writes). Almost every wrong answer in this topic is one of those three operations applied to the wrong quantity.

NATMediumPYQ — GATE CSE 2019

The index node (inode) of a Unix-like file system has 12 direct, one single-indirect and one double-indirect pointer. The disk block size is 4 kB and the disk block address is 32 bits long. The maximum possible file size, rounded off to one decimal place, is ______ GB.

Answer: 4.0

One block holds 4,096 / 4 = 1,024 addresses. Blocks = 12 + 1,024 + 1,048,576 = 1,049,612. Bytes = 1,049,612 × 4,096 = 4,299,210,752 = 4.00395 GB, which rounds to 4.0.

Both archives consulted give 4 (some accept 4.0 to 4.1). The double-indirect term is 99.9 per cent of the total, so an error there moves the answer in gigabytes; an error in the direct term does not.

MCQEasyPYQ — GATE CSE 2017 Set 2, Q8

In a file allocation system, which of the following allocation scheme(s) can be used if no external fragmentation is allowed? I. Contiguous II. Linked III. Indexed

Answer: II and III only

Contiguous needs one unbroken run, so free space can be too small to use while being plentiful: that is external fragmentation. Linked and indexed take any free block, so they never leave an unusable hole.

Neither surviving scheme is waste-free: both waste the tail of the last block, and indexed also spends an index block per file.

NATMediumPYQ — GATE CSE 2014 Set 2, Q20

A FAT-based file system is being used and the total overhead of each entry in the FAT is 4 bytes. Given a 100 × 106-byte disk on which the file system is stored and a data block size of 103 bytes, the maximum size of a file that can be stored on this disk, in units of 106 bytes, is ______.

Answer: 99.6

Blocks = 100,000. FAT = 100,000 × 4 = 400,000 B = 400 blocks. Data space = 100,000,000 − 400,000 = 99,600,000 B = 99.6 × 106 bytes.

The archives record the accepted range as about 99.55 to 99.65, which is a rounding window around 99.6. Answering 100 omits the table from the same disk.

NATHardPYQ — GATE CSE 2022, Q63

Two file systems A and B use contiguous and linked allocation respectively. A file of 100 blocks is stored in both. A new block, whose data is already in memory, is inserted between the 50th and 51st block. Free blocks exist at the end of the file and the file control blocks are in memory. If A needs nA and B needs nB disk accesses, then nA + nB is ______.

Answer: 153

Contiguous: blocks 51–100 are read and rewritten (50 reads, 50 writes) and the new block is written once, so nA = 101. Linked: walk to block 50 (50 reads), write the new block, patch block 50's pointer (2 writes), so nB = 52. Sum 153.

The 50th block's rewrite is the pointer patch, and the new block's data is not read because the question puts it in memory. Dropping either write gives 151 or 152.

NATHardPYQ — GATE CSE 2025 Set 1, Q51

A disk of size 512 M bytes is divided into blocks of 64 K bytes. A file is stored using linked allocation, and each data block reserves 4 bytes to store the pointer to the next data block; the last block's link part holds a NULL pointer, also of 4 bytes. A file of 1 M bytes is stored. Assume 1 K = 210 and 1 M = 220. The space wasted due to internal fragmentation, in bytes, is ______.

Answer: 65468

Usable data per block = 65,536 − 4 = 65,532 B. 1,048,576 / 65,532 = 16.0009, so 17 blocks. Sixteen blocks hold 1,048,512 B, leaving 64 B for the seventeenth. Unused usable space = 65,532 − 64 = 65,468 B.

The trap is subtracting from 65,536 instead of 65,532, which gives 65,472, or forgetting that a seventeenth block is needed at all. The published key and this recomputation agree on 65,468.

MSQMediumPYQ — GATE CSE 2021 Set 1, Q15

Consider a linear-list-based directory implementation in a file system. Each directory is a list of nodes, and each node contains the file name along with the file metadata, such as the list of pointers to the data blocks. For a given directory foo, which of the following operations will necessarily require a full scan of foo for successful completion?

(a) Creation of a new file in foo   (b) Deletion of an existing file from foo   (c) Renaming of an existing file in foo   (d) Opening an existing file in foo

Answer: (a) and (c)

Creation must prove that no entry with that name already exists, so it must see every entry. Renaming must prove the new name is unused, so it also scans fully.

Deletion and opening stop when the name is found; they may scan a lot but need not scan everything, and "necessarily" excludes them. Note that this question's directory node stores the block pointers in the directory itself, which is a variant of the classic layout — the answer does not depend on that detail.

NATMediumPYQ — GATE CSE 2026 Set 2, Q53

To keep track of free blocks, a file system uses a linked list. The disk size is 16 GB, the block size is 2 KB, and block numbers are 32 bits long. A single 4-byte pointer in each list block points to the next list block. The number of blocks required to hold the free disk block numbers is ______.

Answer: 16417

Blocks = 234 / 211 = 8,388,608. Entries per list block = (2,048 − 4) / 4 = 511. 8,388,608 / 511 = 16,416.06, so 16,417 blocks.

Two archives list this as 2026 Set 2 Q53; the wording above follows them and the answer is recomputed here rather than copied. Using 512 entries gives exactly 16,384, and that is the slip: 512 numbers per block would fit the 8,388,608 block numbers exactly, but the block also spends 4 bytes on the pointer to the next list block, so only 511 fit.

NATMediumOriginal practice

A file system uses an inode with 10 direct pointers and one triple-indirect pointer only. Blocks are 4 KB and block addresses are 4 bytes. What is the maximum file size in GB? (Original practice question, not a previous-year question.)

Answer: 4096 GB

Fan-out = 4,096 / 4 = 1,024. The triple term reaches 1,0243 = 230 blocks, which is 230 × 212 B = 242 B = 4,096 GB.

The 10 direct pointers add 40 KB, which is invisible at this scale — that is the point of the question. If you reached 242 GB you multiplied by the block size twice; if you reached 1,024 GB you stopped at the block count.

MCQMediumOriginal practice

A file of 10,000 bytes is stored on a volume with 4 KB blocks under indexed allocation, where the inode has enough direct pointers that no indirect block is needed. How many bytes are wasted inside allocated blocks? (Original practice question, not a previous-year question.)

Answer: 2,288 bytes

ceil(10,000 / 4,096) = 3 blocks = 12,288 B allocated. 12,288 − 10,000 = 2,288 B wasted.

The distractor to avoid is 1,904, which is what you get by using floor(10,000 / 4,096) = 2 blocks. The third block is needed for the remaining 1,808 bytes. This is internal fragmentation, not external.

NATHardOriginal practice

A volume has 1 TB of data space, 4 KB blocks, and a bitmap with one bit per block. The bitmap itself is stored in blocks of the same size. How many blocks does the bitmap occupy? (Original practice question, not a previous-year question.)

Answer: 8192

Blocks = 240 / 212 = 228. Bits = 228, bytes = 225 = 33,554,432. Blocks = 225 / 212 = 213 = 8,192.

The answer is a power of two because both the disk and the block are. Note the self-reference: the bitmap occupies blocks that it must also describe, which is why a real volume reserves its metadata area first and then bitmaps the rest.

The revision sheet

Everything on this tab is a definition, a formula or a number that was computed in this lesson. Nothing here is a claim about which question will appear.

Formulas

blocks = ceil(size / B)

p = B / a

max blocks = d + s·p + D·p² + T·p³

internal waste = blocks·B − size

bitmap bytes = blocks / 8

list entries = (B − link) / number width

list blocks = ceil(free blocks / entries)

Every symbol: B block size, a address width, p pointers per block, d/s/D/T counts of direct, single, double and triple indirect pointers.

Definitions in one line each

  • Inode — fixed-size record of one file's metadata and block pointers.
  • Directory — a file of (name, inode number) entries.
  • Contiguous allocation — physical = start + k; external fragmentation.
  • Linked allocation — the next block number is stored in the block; no random access.
  • FAT — the same chain, collected into one table with an entry per disk block.
  • Indexed allocation — one index block holds every block number; the tree extends it.
  • Bitmap — one bit per block, size independent of how many are free.
  • Hard link — a second name for one inode; raises the link count.
  • Symbolic link — a file holding a path; own inode; can dangle.
  • Mounting — grafting a volume's root onto a directory of another volume.

The five traps

  1. Answering a block count where a size is asked (280 against 35 KB).
  2. Forgetting the pointer stored inside each data block (65,532, not 65,536).
  3. Using 512 entries per list block instead of 511.
  4. Missing the word "necessarily" in a directory-scan question.
  5. Assuming that deleting one of two hard links frees space.

Three sentences that answer most questions

The name is not the file; the inode is. Free space in the wrong shape is external fragmentation, and space inside your own last block is internal.

The scheme decides the access count, the configuration decides the size, and the ceiling decides the table.
