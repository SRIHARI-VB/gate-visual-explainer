Topic and objective

TOPIC: Bit-fields in C — the declarator form type name : width, the allocation unit the fields live in, the packing rule, the two kinds of unnamed field, the range a width gives, and the six properties the standard deliberately leaves to the implementation.

LEARNING OBJECTIVE: Given a struct whose members are bit-fields, compute its sizeof and say which bit each named field occupies, or state that the answer is not determined by the standard. Distinguish an unnamed field of width four from a zero-width field, and say what each does to the unit. Read the same bits as signed and as unsigned and know which reading a given declaration asks for. And name the four constructs a bit-field refuses, with the one reason they all fail.

GATE RELEVANCE: Class A — Section 4 of the GATE 2027 CS syllabus names “Programming in C”, and a bit-field is a declarator form of that language, not an application of it. Two honest qualifications, because this topic is where it is easiest to overclaim. First, the words “bit-field” are not printed in the syllabus; the classification rests on the named language. Second, no previous-year GATE item on bit-fields specifically was located in the papers and archives searched for this lesson, so every question on the Practice tab is labelled original practice and none is presented as a previous-year question. What GATE has asked, verifiably and repeatedly, is the size of a struct — and bit-fields are a struct-sizing question with one more rule in it. The sibling lesson on structures recomputes those items.

PREREQUISITES: the layout rules for an ordinary struct — member sizes, alignment, and the trailing round-up (Structures, unions and enumerations); the integer types and their widths (C fundamentals); and two’s complement, for reading a signed field (Number representation). Bitwise operators are not required: a bit-field is read by assignment, not by a mask, though the mask reading is the same idea and is linked at the end.

Prerequisites, precisely

Must already be comfortable with:

  • A struct is one block, and its size is the sum of its members plus the padding the alignment rules force, rounded up to the largest member alignment.
  • An int is 4 bytes and 32 bits on the platform this lesson uses, and is aligned to 4.
  • Two’s complement: in a signed field of width w, the top bit is worth −2w−1, not +2w−1.
  • Modular arithmetic on w bits: there are 2w patterns, and adding one to the largest wraps to zero.
  • What an lvalue is, since the whole “no address” section is about lvalues that cannot have one.

Helpful, not required: having met sizeof on an ordinary struct, since the questions here are the same question with one extra rule.

Approximate learning time: 35–50 minutes with the animation, or 10 minutes for the Revision tab alone. The figure is an estimate, not a measurement.

The five ideas

  1. A bit-field is a run of bits in a unit, not a small int. The unit is the size of the declared type, and the field is a window into it. That is why a field can start mid-byte, and why it has no address.
  2. Pack in order; start a new unit when the field does not fit. The test is width against the bits remaining, not width against the unit size. The bits left behind are lost.
  3. Width zero and unnamed-with-width are different instructions. Width zero ends the unit; an unnamed width consumes bits inside it. One token apart, one whole unit apart.
  4. The width sets the range, the declared type sets the reading. Three bits hold eight patterns: 0 to 7 unsigned, −4 to 3 signed. Six and −2 are the same three bits.
  5. Six properties are open, so a size question must name the platform. Order within the unit, straddling, plain-int signedness, other types, atomic types and unit alignment are not fixed by the standard.

Intuition: a form with ruled boxes

Think of a paper form with one wide row of thirty-two small boxes. Most of the questions on the form need a number from 0 to 59, which is at most six boxes. If every question got a whole row of its own, the form would be twelve rows long and mostly empty. A bit-field is the instruction “this question gets six boxes of this row, starting where the last one stopped”.

Two things follow immediately, and both matter later. First, a question with six boxes is not a question with its own row: you cannot point at it and say “it starts here”, because it may start in the middle of a row. Second, how the boxes are numbered and which end you start from is the form designer’s choice — the language fixes that a question gets its boxes, not which end they are counted from.

Educational interpretation The form is exact about packing and silent about order, which is precisely the split the standard makes: packing a following field into adjacent bits is required, and the direction is implementation-defined.

Formal definition

A struct or union member may be declared to consist of a specified number of bits. That member is a bit-field, and its width follows a colon.

struct S { unsigned int kind : 3; };
0 ≤ width ≤ bits in the declared type

Read: the width is an integer constant expression. It may not exceed the number of bits in an object of the type that would apply if the colon and the width were removed. A width of zero is allowed only when the declaration has no name.

type ∈ { _Bool, signed int, unsigned int } ∪ { any other type the implementation allows }

Read: three types are required to work, plus whatever else the implementation chooses to allow. char and long bit-fields are extensions, not standard C.

no address, no array, no sizeof of a field

Read: the unary & may not take a bit-field, so there are no pointers to or arrays of bit-fields, and a field cannot be the operand of sizeof.

Verified fact The three constraints and the prohibition on taking an address are clause 6.7.2.1 of the C standard, read in the annotated reproduction listed on the Sources tab and cross-checked against cppreference’s page for the same feature.

Derivation 1 — the size is a whole number of units

A bit-field lives inside an allocation unit: an addressable storage object large enough to hold it, whose size is that of the declared type. For an unsigned int field that is 4 bytes, or 32 bits. The struct is then a sequence of such units, plus any ordinary members.

So the total size is never the sum of the widths divided by eight. It is the number of units used, times the unit size, rounded up to the alignment of the whole struct. Three fields of 5, 6 and 6 bits use 17 of 32 bits, which is one unit, which is four bytes — not three.

sizeof = units used × unit size, rounded to the struct alignment

Read: the rounding is at the unit, not at the byte. Adding widths and dividing by 8 answers a question nobody asked, and it is the commonest wrong method on this topic.

Derivation Checked in code on every declaration the page draws: the size is always a multiple of the unit size, and the used, padding and unused bits always add up to the size in bits. Both checks are reported in the model-checks panel.

Derivation 2 — the fit test, and what it costs

The standard requires that a bit-field which immediately follows another and has enough space left be packed into adjacent bits of the same unit. It does not require that a field which does not fit be split across two units: whether it starts a new unit or straddles is implementation-defined.

The model this lesson computes takes the non-straddling choice, which is what GCC does on x86-64. The test at each step is therefore: does width exceed the bits remaining in the current unit? If it does, move to the next unit boundary first, then place it.

fits(unit, width) ⇔ width ≤ 32 − (bits used in unit)

Read: the comparison is against the bits left, not against 32. A twenty-bit field in a unit with twelve bits free does not fit, even though twenty is less than thirty-two.

The cost of the non-straddling choice is visible and should be said out loud: the bits left behind are not reused. Two twenty-bit fields occupy two units and waste twenty-four bits.

Derivation Enumerated in code over all 961 pairs of widths from 1 to 31: every size lies between the bit-count floor and two units, and no pair produces overlapping bits.

Derivation 3 — the zero-width field

The standard has one special case: a bit-field member with a width of zero indicates that no further bit-field is to be packed into the unit in which the previous bit-field, if any, was placed. It takes no bits itself; it moves the boundary.

unsigned : 0 — end this unit here; the next field starts a new one unsigned : 4 — place four bits of padding inside this unit

Read: the first ends the unit and the second fills part of it. They differ by one character in the source and by an entire unit in the layout.

The worked consequence: unsigned b1:5, b2:6, b3:15; uses 26 bits and is one unit, four bytes. Insert :0 after b1 and the same three fields need two units, eight bytes, and every field after the zero moves.

Derivation Both declarations are laid out in code; the check confirms the four-byte difference comes from the zero-width field alone, and that b2 starts at bit 32 with it and bit 5 without it.

Derivation 4 — the width is the range

A width of w gives exactly 2w patterns, and a bit-field is interpreted as a signed or unsigned integer type consisting of that many bits. So the range is fixed by the width and the reading is fixed by the declared type.

unsigned w-bit field: 0 .. 2w − 1 signed w-bit field: −2w−1 .. 2w−1 − 1

Read: for w = 3 those are 0 to 7, and −4 to 3. Eight patterns either way; only the interpretation of the top bit differs.

A store into an unsigned field keeps the value modulo 2w: storing 9 in a three-bit field reads back 1, and incrementing 7 gives 0. That is defined behaviour, not overflow, because an unsigned field has a defined modular result.

Derivation Every in-range value for every width from 1 to 12 survives a store and a read, checked in code; and raw 110 read as a three-bit signed field is −2.

Derivation 5 — why there is no address

A byte address designates a byte. A field of three bits may begin at bit 5 of a byte and end at bit 7 of the same byte, or begin at bit 30 and end at bit 0 of the next unit. In the first case no address designates it because it is not a whole object; in the second, no address designates it because it is not contiguous in the address space.

The standard states the consequence directly: the unary address-of operator cannot be applied to a bit-field, so there are no pointers to or arrays of bit-field objects. Everything else follows: no scanf into a field, no offsetof on one, no sizeof of one.

Verified fact Clause 6.7.2.1 footnote on the address-of operator, and clause 6.5.3.2 on what the operand of & may be. cppreference states the same prohibition and adds that calling offsetof on a bit-field is undefined behaviour.

Derivation 6 — the same declaration, two compilers

Take struct { unsigned a:28, b:8; }. Twenty-eight bits are placed in the unit, four remain, and eight do not fit in four. A non-straddling compiler starts b at bit 32. A straddling compiler puts b at bits 28 to 35, crossing the boundary, and the struct may be the same size with entirely different bit positions.

So the size alone is not enough to answer “which bits does b occupy”, and the bit positions alone are not enough to answer “what is sizeof”. A question must pin down the compiler for either, and this is why the lesson states its model in one sentence and tests it against published sizes.

Derivation The page computes the non-straddling layout for this declaration and reports b starting at bit 32, not 28.

Example 7 — the four refusals

&s.a
constraint violation: & may not take a bit-field
sizeof s.a
not allowed: sizeof needs an object or a type
unsigned f:3 arr[4]
no arrays of bit-fields exist
offsetof(struct S, a)
undefined behaviour
scanf("%d", &s.a)
cannot work: it needs an address

Each line is a different symptom of one fact. A field may start mid-byte, so no byte address designates it. Copying the field into an int first and taking the address of the copy is the working alternative.

Verified fact The first, third and fourth are stated in clause 6.7.2.1 and in cppreference’s page on bit-fields; the offsetof case is named there as undefined behaviour.

1. A width equal to the type width

unsigned int a : 32 is legal: the constraint is width ≤ 32, not width < 32. A width of 33 is a constraint violation and no object exists to size. So the boundary case is allowed and the one past it is not.

Verified fact The constraint reads “shall not exceed the number of bits in an object of the type”, so equality is inside it. The model rejects 33 and accepts 32.

2. A named zero-width field

unsigned int a : 0; is a constraint violation, because the standard says that if the width is zero the declaration shall have no declarator. There is no object for the name to refer to. The model reports exactly this error.

Derivation Checked in code: the declaration produces one error and no layout.

3. The field that does not fit, but almost does

A twenty-eight-bit field leaves four bits free. An eight-bit field does not fit, even though eight is much less than thirty-two. The fit test is against the bits remaining, so the answer is a new unit and four wasted bits.

Derivation Computed: the second field starts at bit 32 in the non-straddling model.

4. Padding is not zero

An unnamed field of width four has no defined value. Assigning the whole struct copies the members; what happens to the padding bits is not something the standard promises, so two structs with equal members need not be equal byte for byte. Comparing a bit-field struct with memcmp is therefore unreliable.

Derivation The page’s bit map shows those bits owned by (pad) and by nothing else; no member can be read from them.

5. “Adding the widths gives the size” fails on the first example

The counterexample is the smallest one available: unsigned b1:5, :11, b2:6, b3:2; has widths summing to 24 bits, which is 3 bytes, and its size is 4. Nothing exotic is involved: no ordinary members, no unions, one unit. The method fails because the object is a unit.

Derivation Both numbers are computed; the disagreement is a property of the model, not an accident of one declaration.

6. “A field of width w holds values up to 2w” fails at the boundary

A three-bit field holds 0 to 7, so 8 is the first value that does not fit, and it is stored as 0. The tempting statement “it holds up to eight” is off by one in the direction that matters, because 8 wraps to 0 rather than saturating or failing.

Derivation Computed: store 8 in a three-bit field reads back 0; store 9 reads back 1.

7. Two readings of the same bits, and no way to tell from the value

A signed three-bit field and an unsigned three-bit field holding pattern 110 are indistinguishable from the bits: one is 6 and the other is −2. If a question prints the field and does not say which type, the answer for pattern 110 is not determined. This is the closest-confused pair in the topic, and the difference is one keyword in the declaration.

Derivation Computed for all eight patterns: the two readings agree on 000 to 011 and differ on 100 to 111.

8. Mixing bit-field types

A struct that declares an unsigned int field and then an unsigned char field is outside this lesson’s model: whether they share a unit, and how the smaller type’s unit aligns, is implementation-defined and differs between compilers. The model covers int, signed int and unsigned int fields, and says so rather than guessing.

Verified fact Clause 6.7.2.1 permits any implementation-defined type and leaves the unit’s alignment unspecified, which is what makes mixed-width field types unpredictable.

Misconception 1 — “a bit-field is a small int”

Why it is wrong: an int has an address, a size, and a whole object of its own. A bit-field has none of the three. &s.a does not compile, sizeof s.a does not compile, and the field may begin in the middle of a byte.

What to hold instead: a bit-field is a named window into an allocation unit. Everything that follows — no pointer, no array, no scanf, no offsetof — comes from that one sentence.

Verified fact The prohibition on taking the address is in clause 6.7.2.1 and in clause 6.5.3.2’s list of permitted operands.

Misconception 2 — “sizeof is the widths added up and divided by eight”

Why it is wrong: the object is a whole number of allocation units. Widths of 5, 11, 6 and 2 sum to 24 bits, and the answer is 4 bytes, not 3. The same method also fails the other way on a struct with a :0, where the widths sum to 26 and the answer is 8.

What to hold instead: count the units the declaration touches, multiply by the unit size, then round to the struct alignment.

Derivation Both cases are computed; the page reports 4 and 8 for the two declarations.

Misconception 3 — “:0 is the same as an unnamed field of some width”

Why it is wrong: they do opposite things. unsigned : 4 consumes four bits of the current unit and the next field continues after them. unsigned : 0 consumes nothing and ends the unit, so the next field starts at the next boundary.

What to hold instead: a nonzero unnamed width is padding; a zero width is a boundary. The second is the only way to force a new unit without inserting a full member.

Derivation The mixed struct on the Examples tab places clock at bit 8 after four bits of padding, and flag at bit 32 after a zero.

Misconception 4 — “a three-bit field holds up to 8”

Why it is wrong: three bits give eight patterns, numbered 0 to 7. The value 8 does not fit, and storing it keeps 8 modulo 8, which is 0. So the field never holds 8, and it silently holds 0 instead.

What to hold instead: a w-bit unsigned field holds 0 to 2w − 1, and a store is a reduction modulo 2w. Check the maximum value the data can take before choosing the width.

Derivation Computed: store 8 reads 0, store 9 reads 1, and incrementing 7 gives 0.

Misconception 5 — “the first field is in the first byte”

Why it is wrong: the first field is in the low-order bits of the unit, which is the first byte only if the compiler packs from the low end and the machine is little-endian. On a big-endian target of the same compiler, the first field is in the last byte of the unit.

What to hold instead: the field is in the unit, and where inside the unit is implementation-defined. Only the struct’s first byte address is fixed.

Verified fact Clause 6.7.2.1: the order of allocation of bit-fields within a unit is implementation-defined.

Misconception 6 — “the size is fixed by the standard”

Why it is wrong: four of the six open properties change the size. Straddling can save a unit, a different plain-int signedness changes the range but not the size, and a compiler that permits char bit-fields may place them in one-byte units.

What to hold instead: a size question names a platform or it has several right answers. The two published sizes for the same three fields differ by a whole unit between GCC and MSVC on some declarations.

Community observation The GCC-and-MSVC difference for a zero-width field between char and int fields is documented in a public defect report discussion, and is reported rather than measured here.

Misconception 7 — “bit-fields are portable if I use unsigned int”

Why it is wrong: using unsigned int fixes the signedness question and the unit size, and leaves the order inside the unit, the straddling choice, the unit alignment, and whether the compiler honours the widths at all. A struct written to match a network header is not portable across compilers without a packing attribute.

What to hold instead: bit-fields are portable for values (read and write through the member) and not for bytes (memcpy, file formats, network order). Use masks and shifts when the byte layout matters.

Educational interpretation This is the practical rule the standard’s own division implies; the bitwise operators lesson builds the portable alternative.

Misconception 8 — “the compiler will warn me if the value does not fit”

Why it is wrong: assigning an out-of-range value to a bit-field is not a constraint violation for an unsigned field; it is a defined reduction. For a signed field the result is implementation-defined. Neither is a required diagnostic, so nothing is printed and the value quietly changes.

What to hold instead: the range check is yours. If the data can exceed 2w − 1, the width is wrong, and no compiler is obliged to tell you.

Derivation Computed for every width from 1 to 12: a store keeps the value modulo 2w, with no error path in the model.

Pattern A — “what is sizeof” on a struct of bit-fields

The commonest form, and the one this topic is really about. You are given a declaration and a platform (or a platform statement is implied by the paper’s conventions), and asked for the size. The work is: unit size, pack in order, count the units, round.

Where marks are lost: adding the widths and dividing by 8. It is quick, it looks like arithmetic, and it is wrong whenever the declaration touches more than one unit or leaves a partial unit.

Pattern B — the effect of one token

Two declarations differing by a :0, by a member’s order, or by one width, and a question about the difference in size. This form tests whether you know which token does what. The zero-width field is the favourite, because it changes the size by a whole unit and moves every later field.

Shortcut, with its assumption: a :0 costs one unit of waste, so the size goes up by one unit. The assumption is that the unit had bits free; if the previous field filled the unit exactly, the zero changes nothing.

Pattern C — what a field holds after an out-of-range store

A three-bit field, a value of 9, and a print. For an unsigned field the answer is 9 mod 8 = 1. For a signed field of the same width the answer is implementation-defined, so the question has to name the compiler or be unanswerable.

Where marks are lost: answering 9 because 9 is what was assigned, or answering −7 by applying two’s complement to the wrong width.

Pattern D — which construct is illegal

Four lines, one of which does not compile: &s.a, sizeof s.a, an array of fields, offsetof on a field. All four fail for the same reason, so recognising the reason answers all four at once.

Shortcut, with its assumption: if the operand is a bit-field and the operator needs an address, it is the illegal one. The assumption is that you can tell a field from an ordinary member, which the colon does.

Pattern E — “what does this print” where the answer is “it depends”

A declaration with a plain int field, a value whose top bit is set, and four numeric options. The correct reasoning is that the signedness of a plain int field is implementation-defined, so on the stated platform the answer follows that platform’s choice and on an unstated platform there is none.

Where marks are lost: assuming int means signed int, which is what it means everywhere else in C and not inside a bit-field declaration.

The five-step reading procedure

  1. Find the colon. A member without one is an ordinary member and takes its whole type.
  2. Read the declared type. It fixes the unit size and, with the width, the range.
  3. Pack in declaration order into the low-order bits. A field that does not fit starts a new unit, in this model.
  4. Handle the unnamed forms: width zero ends the unit, nonzero width only consumes bits.
  5. Round the total to the unit size, then to the struct alignment.

This procedure is the procedure scene twelve animates. It is a reading checklist, not a proof of the standard’s rules, and it holds only under the model stated on the Build-up tab.

Answer: 4. Twenty bits fit inside one 32-bit unit, so one unit is touched and a unit is 4 bytes.

The wrong method gives 20/8 = 2.5, which is not even an integer, and a student who rounds it up to 3 has answered a question about a bit string rather than about a struct. The page computes 4 for this declaration, which is the size a reported run prints for it.

MCQOriginal practice

What is the difference between unsigned : 4 and unsigned : 0 in a struct?

(A) nothing, both are padding   (B) the first consumes four bits of the current unit, the second ends the unit   (C) the first ends the unit, the second consumes four bits   (D) the second is a constraint violation

Answer: (B). A nonzero unnamed width is padding placed inside the unit; a zero width takes no bits and moves the next field to the next unit boundary.

(A) is the misconception the scene refutes: the two differ by an entire unit in the layout. (C) is (B) with the two halves swapped, which is the pair most often confused. (D) confuses this with the named zero-width form, which is a violation; an unnamed zero width is the legal and intended case.

NATOriginal practice

struct S { unsigned b1:5, :0, b2:6, b3:15; }; — how many bytes is sizeof(struct S)?

Answer: 8. b1 occupies bits 0 to 4 of unit 1, the zero ends that unit, and b2 and b3 take 21 bits of unit 2. Two units, so 8 bytes.

Delete the :0 and the same three fields fit in one unit of 26 bits, giving 4. The page computes both and the check confirms the four-byte difference comes from the zero-width field alone.

MCQOriginal practice

struct S { unsigned a:3; } s; s.a = 9; — what does printf("%u", s.a) print, given a is declared unsigned?

(A) 9   (B) 1   (C) 0   (D) implementation-defined

Answer: (B) 1. A three-bit unsigned field keeps the value modulo 8, and 9 mod 8 is 1.

(A) is what was assigned, which is not what is stored. (C) is what storing 8 would give. (D) is the trap of this question: for an unsigned field the result is defined, and only for a signed field — or a plain int field — does implementation-defined enter. Reading the keyword carefully is the whole question.

MSQOriginal practice

Which of the following are true of a bit-field member a of a struct? Select all that apply.

(A) &s.a is a constraint violation   (B) sizeof s.a is not allowed   (C) offsetof(struct S, a) has a defined value   (D) an array of bit-fields cannot be declared

Answer: (A), (B) and (D). All three follow from the field having no address.

(C) is the false statement, and it is the one people mark true: offsetof is defined in terms of the address of a member, so calling it on a bit-field is undefined behaviour rather than a value. The three true options are three symptoms of one cause, which is why they are asked together.

NATOriginal practice

struct S { unsigned a:20, b:20; }; — how many bits of the object belong to no field at all?

Answer: 24. a takes bits 0 to 19 of unit 1; b needs 20 bits, only 12 remain, so b starts unit 2 at bit 32 and takes bits 32 to 51. The object is 64 bits and the fields own 40 of them.

Twelve bits at the top of unit 1 and twelve at the top of unit 2 are lost. A straddling compiler would use some of them, which is exactly why the question must state the model.

MCQOriginal practice

A struct holds unsigned light:1, toast:1; followed by int count;. Where does count begin?

(A) offset 2   (B) offset 1   (C) offset 4   (D) offset 8

Answer: (C) offset 4. The two one-bit fields occupy a four-byte unit, and an ordinary member starts a new location after that unit; four-byte alignment also demands offset 4.

(A) treats the fields as two one-byte members, which ignores the unit. (B) is the same error with the two bits packed into one byte. (D) would need a second unit before the int, which nothing here asks for. Both the unit rule and the alignment rule point at 4, which is why the wrong options are plausible.

NATOriginal practice

struct S { unsigned a:4; unsigned :4; unsigned b:2; unsigned :0; unsigned c:1; }; — what is sizeof(struct S) in bytes?

Answer: 8. Unit 1 holds a at bits 0 to 3, four bits of padding at 4 to 7, and b at 8 and 9. The zero ends that unit. c starts unit 2 at bit 32. Two units, so 8 bytes.

The trap is answering 4: the fields themselves need only seven bits, and without the :0 the struct would indeed be 4 bytes. The padding field is what makes b land at bit 8 rather than bit 4, and the zero is what costs the second unit.

Formulas, each with its condition

type name : width

width is an integer constant expression, 0 ≤ width ≤ the bits of the declared type. Width 0 only with no name.

sizeof = units touched × unit size, rounded to struct alignment

Not the widths divided by 8. A unit is the size of the declared type: 4 bytes for int, signed int and unsigned int here.

fits ⇔ width ≤ bits remaining in the unit

Otherwise a new unit starts, in the non-straddling model. The bits left behind are lost.

unsigned : 0 ends the unit; unsigned : w (w > 0) consumes w bits inside it

The zero takes no bits and moves the boundary. The nonzero width is padding placed in the unit.

unsigned w-bit: 0 .. 2w−1; signed w-bit: −2w−1 .. 2w−1−1

A store is a reduction modulo 2w. For a plain int field the signedness is implementation-defined.

no &field, no sizeof field, no array of fields, no offsetof field

One cause: a field may start mid-byte, so no byte address designates it.

The decision procedure

  1. Find the colon. No colon means an ordinary member with its whole type.
  2. Read the declared type: it fixes the unit size and, with the width, the range.
  3. Pack in order into the low-order bits; a field that does not fit starts a new unit.
  4. Apply the unnamed rules: zero ends the unit, nonzero consumes bits.
  5. Round to the unit, then to the struct alignment.
  6. If the question asks for bit positions or for a signed value, check that it named the compiler.

A reading procedure for exam questions. It is not a proof, and it is valid only under the model stated on the Build-up tab.

Traps, each with its defusing example

  • Widths divided by 8: 24 bits is not 3 bytes; the struct is 4.
  • :0 read as padding: it ends the unit and costs 4 bytes here.
  • Padding read as ending the unit: :4 keeps the unit and places the next field after it.
  • 3 bits holding 8: it holds 0 to 7, and 8 stores as 0.
  • Plain int field read as signed: its signedness is implementation-defined.
  • Bit positions without a compiler: the standard does not fix the order or the straddling.
  • &s.a as a workaround: it is a constraint violation, not a warning.
  • memcmp on a bit-field struct: padding bits have no defined value.

Every one of these is refuted on the Misconceptions or Edge cases tab with the smallest example that breaks it.

Six questions to test yourself, answers below

1. Is unsigned int a : 32; legal?
2. Is unsigned int a : 0; legal?
3. How many bytes is struct { unsigned a:5, b:6, c:6; }?

4. A three-bit signed field holds 110. What does it read?
5. Does unsigned : 4 end the unit?
6. What does sizeof s.a do?

Answers. 1. Yes: the constraint is width ≤ 32, and 33 is the first illegal width. 2. No: a zero width may not be given a name. 3. Four: 17 bits fit in one unit. 4. −2, because the top bit is the sign in a signed three-bit field. 5. No — it consumes four bits of the current unit; only a zero width ends the unit. 6. It does not compile: sizeof takes an object or a type, and a bit-field is neither.

Answers 3 and 4 are computed by the page’s own model; the rest are the constraints restated.

  • ISO/IEC 9899, clause 6.7.2.1 (structure and union specifiers) — the width constraint, the permitted types, the packing requirement, the implementation-defined order and straddling, the unnamed and zero-width fields, and the footnote that the address-of operator cannot be applied to a bit-field. Read as clause text reproduced in an annotated form rather than from a purchased copy of the standard.
  • “The New C Standard”, annotation of 6.7.2.1 — a sentence-by-sentence reproduction of the clause, which is the source of the exact wording paraphrased on the Build-up tab.

Textbook-level and community material
