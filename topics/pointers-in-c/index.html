Topic and objective

TOPIC: Pointers in C — addresses, dereferencing, pointer arithmetic, and the array relationship, at the depth GATE CSE asks them.

LEARNING OBJECTIVE: Given a short C program that uses pointers, predict its output or its addresses by reasoning from three rules — scaled arithmetic, array decay with its three exceptions, and sizeof reporting the object rather than the target — and recognise the cases where the standard defines no answer at all.

I read "pointers in C programming" as the C language mechanics, not as data structures built on pointers. Linked lists, trees and BSTs get their own lessons and are linked from here.

GATE relevance

Verified fact Class B — a prerequisite for a syllabus topic.

The official GATE 2027 CS syllabus (IIT Madras), Section 4, reads in full: "Programming in C. Recursion. Arrays, stacks, queues, linked lists, trees, binary search trees, binary heaps, graphs."

The word "pointer" is not printed. Pointers are still examinable: they are the mechanism behind arrays, linked lists, trees and BSTs, and unavoidable inside "Programming in C". So class B, not A — and not a guarantee of appearance.

Prerequisites

  • Variables, types and assignment in C.
  • Functions and parameters — what "pass by value" means.
  • Arrays: declaration, indexing from 0, and that elements are contiguous.
  • Nothing about pointers is assumed. This lesson starts from a byte.

The five ideas

  1. An address and a value are different things.
  2. &x gives an address; *p gives the object at an address.
  3. p + k moves k elements, scaled by sizeof(*p).
  4. An array name decays to &a[0] except under sizeof and &.
  5. sizeof answers about the object you named, never about what a pointer points at.

Intuition first: a locker number, not the locker

A railway cloakroom gives you a numbered token. The token is not your luggage and it is not the shelf — it is a small object whose whole content is where your luggage is. Hand the token to the clerk and the clerk can fetch the luggage, put something else inside it, or tell you it is empty.

Educational interpretation The token is the pointer, the number written on it is the address, the luggage is the pointed-to object, and the shelf slot is the memory the object occupies. The analogy breaks in one useful place: a real token is a physical object of a fixed size, and so is a pointer — but the luggage behind it can be one byte or a thousand, and the token tells you nothing about which.

Formal definition 1 — object and address

Memory is a sequence of bytes, and each byte has a number: its address. A region of storage that holds a value of some type is an object. The address of an object is the address of its first byte.

Verified fact This is why sizeof matters at all: an int object spans several bytes, and the address names only the first one.

Formal definition 2 — pointer

A pointer is a variable whose value is an address. If the address is of an object of type T, the pointer has type T *, read "pointer to T".

Read a declaration from the name outward: in int *p, start at p, step left to the * — p is a pointer — then step to int — to an int.

Formal definition 3 — the two operators

& (unary) takes an object and yields its address. * (unary, in an expression) takes a pointer and yields the object it points at.

Derivation The two are inverse where both are defined: &*p is p, and *&x is x. The caveat is "where defined" — if p holds no valid address, &*p is already undefined behaviour.

Formal definition 4 — the decay rule

An expression of array type, in most contexts, is converted to a pointer to its first element. So for int a[5], the expression a becomes a value of type int * equal to &a[0].

Verified fact There are exactly three exceptions, where no conversion happens:

  1. The array is the operand of sizeof — so sizeof(a) is the whole block.
  2. The array is the operand of unary & — so &a has type int (*)[5], a pointer to the whole array.
  3. A string literal used to initialise a char array, as in char t[] = "GATE";.

Example 1 — reading an address off a base

int a[6] = {10,20,30,40,50,60}; with a at 2000, sizeof(int)=4. Let int *p = a + 2; Find *(p+3) - *p and p - a.

  1. p = a + 2 scaled: 2000 + 2×4 = 2008, which is &a[2]
  2. *p is a[2] = 30 dereference the address p holds
  3. p + 3 is 2008 + 12 = 2020 = &a[5] again scaled by 4
  4. *(p+3) = 60 the object at 2020
  5. Answer: 60 − 30 = 30; and p - a = 2 pointer difference counts elements, not bytes: (2008−2000)/4

Example 2 — *(p+2) is not *p+2

With int a[5]={10,20,30,40,50}; int *p=a;

  1. *(p+2) add first, then dereference: address 1008 → value 30
  2. *p+2 dereference first, then add to the value: 10 + 2 = 12

The brackets are not decoration. Unary * binds tighter than the outer +, so it applies to p before the addition happens.

Example 3 — a two-dimensional offset

int m[3][4] at 2000, row-major, sizeof(int)=4. Where is m[2][1]?

  1. Row length is 4 elements C stores every element of row 0, then row 1, and so on
  2. Elements before it: 2 rows × 4 + 1 = 9 row 0 and row 1 fully, then one more
  3. Byte offset: 9 × 4 = 36 scale by the element size
  4. Address = 2000 + 36 = 2036 formula: base + (i×C + j)×sizeof(T)

Example 4 — why a swap needs pointers

void bad(int x, int y){int t=x; x=y; y=t;} does not swap the caller's variables.

  1. Parameters are new objects C passes by value; the arguments are copied
  2. bad swaps the copies the caller's objects are untouched
  3. void ok(int *a, int *b){int t=*a; *a=*b; *b=t;} the parameters are still copies — copies of the addresses
  4. *a = *b writes through the address the object written is the caller's
  5. Call as ok(&x, &y) you must pass the addresses, not the objects

One past the end is legal to form

For int a[5], the pointer a + 5 may be computed and compared. It is the address just after the last element.

Dereferencing it is undefined. The rule exists so that loops can write p != a + 5 as a stopping test.

Arithmetic outside the array is undefined

int *q = &a[-1]; or a + 6 — even without a dereference — is not covered by the standard. It may compute, or it may not.

The 1-based-array trick you sometimes see in old code is exactly this violation.

Pointer subtraction needs a common array

p2 - p1 is defined only when both point into the same array (or one past it). Subtracting pointers into two different objects has no defined value.

== and != are safer: they may compare any two pointers of compatible type.

int *p[5] is not int (*p)[5]

[] binds tighter than *. So int *p[5] is an array of five pointers; int (*p)[5] is one pointer to an array of five ints.

With 8-byte pointers: sizeof gives 40 for the first and 8 for the second.

A 2-D array is not int **

Decay is not recursive. int m[3][4] decays to int (*)[4], a pointer to a row — not to a pointer.

So the parameter must be int m[][4]. The column count cannot be omitted, because it is needed to index.

void * arithmetic is not standard C

You cannot dereference a void * — the compiler does not know the element size. C99 does not define arithmetic on it either.

GCC allows it as an extension, treating it as char *. A question relying on that is relying on a compiler, not on C.

String literals are not writable

char *s = "GATE"; points at a shared, non-modifiable array. s[0] = 'L'; is undefined behaviour.

char s[] = "GATE"; is a different declaration: it copies five chars into your own writable array.

An uninitialised pointer is not NULL

int *p; holds an indeterminate value. It is not zero, and testing it against NULL tells you nothing.

Only int *p = NULL; — or any explicit assignment — makes it safe to compare.

The distinction that resolves most of these

Ask two separate questions: is this pointer value well defined? and is the object it designates alive and of the right type? Forming a valid address and having a live object there are independent. Most "it prints something anyway" answers fail the second question while passing the first.

Misconception 1 — "an array is a pointer"

1. The belief. "Arrays and pointers are the same thing; int a[5] is just a constant int *."

2. Why it seems right. int *p = a; compiles with no &, a[i] and p[i] give the same answers, and both can be passed to the same function.

3. Why it is wrong. An array is a block of objects; a pointer is one object holding an address. The array name converts to a pointer in most expressions, but the objects themselves are different, and the conversion has exceptions.

4. Minimal counterexample.

int a[5]; int *p = a;
sizeof(a)   /* 20 */
sizeof(p)   /*  8 */
a = p;      /* error: not assignable */

5. Correct rule. An array expression decays to a pointer to its first element, except as the operand of sizeof, as the operand of &, or as a string literal initialising a char array.

6. Question that exposes it. Practice Q6 and Q11.  7. Visual. Animation scene 5 shows the decay as an explicit conversion applied to an array object, and scene 6 shows the two sizeof answers side by side.

Misconception 2 — "p + 1 moves one byte"

1. The belief. "Addresses are byte numbers, so adding 1 to an address adds 1."

2. Why it seems right. The address is a byte number, and +1 looks like ordinary integer addition.

3. Why it is wrong. Pointer arithmetic is defined in units of the pointed-to type. The compiler multiplies by sizeof(*p) before it adds. That is what makes p+1 land on the next element instead of inside the current one.

4. Minimal counterexample.

int *p;  /* 4-byte ints */
p + 1;   /* address + 4 */

char *q;
q + 1;   /* address + 1 */

5. Correct rule. addr(p + k) = addr(p) + k × sizeof(*p), and p2 - p1 counts elements, not bytes.

6. Question that exposes it. Practice Q4 and Q12.  7. Visual. Animation scene 4 puts an int * row above a char * row starting at the same address, so the two jump distances are directly comparable.

Misconception 3 — "sizeof tells me the array length"

1. The belief. "I can write n = sizeof(arr)/sizeof(arr[0]) anywhere the array is available, including inside the function that receives it."

2. Why it seems right. It works perfectly in the function that declares the array, which is where most people first try it.

3. Why it is wrong. Inside the callee there is no array — only a pointer. The division becomes 8/4 = 2 regardless of the real length.

4. Minimal counterexample.

void f(int arr[10]){
  sizeof(arr);      /* 8, not 40 */
}
int a[10];
f(a);               /* fine; f cannot
                       see the 10 */

5. Correct rule. sizeof reports the type of the expression. A parameter declared int arr[10] has type int *. Pass the length as a second argument.

6. Question that exposes it. Practice Q7.  7. Visual. Animation scene 6, third panel: the same call, seen from inside.

Misconception 4 — "*p++ increments the value"

1. The belief. "The star applies to everything after it, so *p++ means ++(*p)."

2. Why it seems right. Unary * is written first, and reading left to right suggests it takes p++ as a unit — but people often assume the reverse grouping too.

3. Why it is wrong. Postfix ++ binds tighter than unary *. So the operand of * is p++, not p, and the pointer moves while the cell is untouched.

4. Minimal counterexample.

int b[4]={1,2,3,4}; int *p=b;
int v = *p++;   /* v=1, p now &b[1],
                   b[0] still 1 */
(*p)++;         /* now b[1] is 3 */

5. Correct rule. *p++ = *(p++): read, then move. (*p)++: change the cell, leave the pointer.

6. Question that exposes it. Practice Q8 and Q9.  7. Visual. Animation scene 7 animates all four forms against the same array.

Misconception 5 — "a dangling pointer is a null pointer"

1. The belief. "Once the variable dies the pointer becomes NULL, or holds garbage I can detect."

2. Why it seems right. Both are described as "pointers that do not point at anything", and both are taught as things to avoid.

3. Why it is wrong. The pointer keeps the exact address it held. Nothing clears it, so a NULL test passes. The object at that address has ceased to exist, which is a different failure.

4. Minimal counterexample.

int *f(void){
  int y = 5;
  return &y;   /* frame dies */
}
int *q = f();
/* q != NULL, and *q is UB */

5. Correct rule. Dereferencing a pointer to an object whose lifetime has ended is undefined behaviour. free() creates the same situation.

6. Question that exposes it. Practice Q10.  7. Visual. Animation scene 9 lets the frame disappear while the arrow stays.

Two question shapes, almost every time

Shape 1 — trace an output. A short program with an array, a pointer or two, and a printf. You are asked what it prints. Everything needed is the scaling rule plus the */++ grouping.

Shape 2 — decide a property. "Which of these statements is/are true", or a sizeof value, or whether an expression is legal. Here the traps are type-level: decay, sizeof, and pointer-to-array versus array-of-pointers.

A — Direct definition

Reasoning: recall the definition of decay or of pointer arithmetic, then apply it literally.

Common wrong approach: answering from a remembered slogan ("arrays are pointers") rather than the definition, which has exceptions.

B — Property verification

Reasoning: compute the type of the expression, then check what operations that type permits.

Common wrong approach: assuming a construct compiles because a similar-looking one does.

C — Calculation

Reasoning: base + offset, with the offset computed in elements and then multiplied by the element size.

Common wrong approach: forgetting the multiplier, or using the row count where the row length belongs.

E — Counterexample reasoning

Reasoning: to refute a universal claim, produce the smallest program where it fails. int a[5]; sizeof(a) refutes "an array is a pointer".

Common wrong approach: trying to prove the claim true by finding examples where it holds.

G — Misconception trap

Reasoning: notice which belief the distractor encodes, and check it against the definition.

Common wrong approach: choosing the option that matches the intuitive (byte-wise) reading of pointer arithmetic.

H — Multi-step reasoning

Reasoning: track two things at once — the pointer's position and the array's contents — one statement at a time.

Common wrong approach: tracking only the printed value and losing the pointer's new position.

The one habit that fixes most of these

Before evaluating anything, write down two columns: the type of every expression, and the value. Most pointer questions are decided in the type column — int versus int * versus int (*)[5] — before any arithmetic happens. If the types are right, the arithmetic is usually one multiplication.

MCQBasicOriginal GATE-style

With int a[5] = {10,20,30,40,50}; and int *p = a + 1;, what is the value of *(p + 2)?

  1. 30
  2. 40
  3. 50
  4. 20

Answer: B — 40

p points at a[1]. p + 2 moves two elements on, to a[3], which holds 40.

Common wrong answer: A (30). That is *(a + 2) — you forgot that p did not start at a[0]. Concept tested: scaled arithmetic from an arbitrary start.

NATBasicOriginal GATE-style

Given int a[10]; with sizeof(int) = 4, what is the value of the expression sizeof(a) / sizeof(a[0])? Answer as an integer.

Answer: 10

sizeof(a) is 40 (the whole array, because a is not decayed here) and sizeof(a[0]) is 4. 40/4 = 10.

Concept: this idiom works only where the array is still an array. Inside a function it would give 2 on this machine, for any length.

MCQBasicOriginal GATE-style

On a machine where sizeof(pointer) = 8, what is sizeof(s) for char *s = "GATE";?

  1. 4
  2. 5
  3. 8
  4. 9

Answer: C — 8

s is a pointer variable. Its size is the size of an address, not the size of the five characters it points at.

Common wrong answer: B (5). That is sizeof("GATE"), or sizeof of a char[5] array — a different declaration.

NATApplicationOriginal GATE-style

int m[3][4] begins at byte address 2000, stored row-major, with sizeof(int) = 4. What is the address of m[2][1]?

Answer: 2036

Offset in elements = 2×4 + 1 = 9. Byte offset = 9×4 = 36. Address = 2000 + 36 = 2036.

Common wrong answer: 2024. That comes from using 3 (the row count) as the multiplier instead of 4 (the row length).

MCQApplicationOriginal GATE-style

What does this print?

int x = 5;
int *p = &x;
int **pp = &p;
**pp = 9;
printf("%d", x);
  1. 5
  2. 9
  3. the address of x
  4. undefined

Answer: B — 9

**pp follows pp → p → x and designates x itself. Assigning to it writes into x.

Common wrong answer: A. It assumes **pp = 9 only changes a copy. Dereferencing produces the object, not a copy of its value.

MCQApplicationOriginal GATE-style

With sizeof(pointer) = 8, what does this function print when called as f(a) for int a[10];?

void f(int arr[10]){
  printf("%zu", sizeof(arr));
}
  1. 4
  2. 8
  3. 40
  4. 10

Answer: B — 8

The parameter int arr[10] is adjusted to int *. The 10 in the brackets is documentation, not a type.

Common wrong answer: C (40). Correct for sizeof(a) in the caller, wrong for sizeof(arr) in the callee. This is the classic pairing in GATE questions.

MSQConceptualOriginal GATE-style

For int a[10]; int *p = a; with sizeof(int) = 4, which statements are true? (One or more may be correct.)

  1. a[i] and *(a + i) are the same expression.
  2. sizeof(a) equals sizeof(&a[0]).
  3. &a + 1 and a + 10 hold the same address.
  4. a = p; is a legal assignment.

Answer: A and C

A: subscripting is defined as *(a + i). C: &a is a pointer to the whole 40-byte array, so &a + 1 is base + 40; a + 10 is also base + 40.

Why B fails: 40 versus 8. Why D fails: an array name is not a modifiable lvalue. Note that equal addresses in C do not mean equal types.

MSQConceptualOriginal GATE-style

Which of the following are undefined behaviour in C? (One or more may be correct.)

  1. Dereferencing a null pointer.
  2. Returning the address of a local variable from a function.
  3. Computing a + 5 for int a[5]; without dereferencing it.
  4. Dereferencing a + 5 for int a[5];.

Answer: A, B and D

A and D are dereferences of an address where no object lives. B creates a pointer to an object whose lifetime has ended; the dereference that follows is undefined.

Why C is not the answer: forming the one-past-the-end address is explicitly allowed. It exists so that a loop can test p != a + 5. This distinction is the point of the question.

MCQConceptualOriginal GATE-style

With sizeof(pointer) = 8 and sizeof(int) = 4, what is sizeof(int *p[5])?

  1. 8
  2. 20
  3. 40
  4. a syntax error

Answer: C — 40

[] binds tighter than *, so int *p[5] is an array of five int *. Five pointers of 8 bytes = 40.

Common wrong answer: A (8). That is int (*p)[5], one pointer to an array of five ints. The brackets move the meaning entirely.

NATTrickyOriginal GATE-style

After these statements, what is the value of p - a?

int a[5] = {1,2,3,4,5};
int *p = a;
int v = *p++;

Answer: 1

*p++ is *(p++): the value read is a[0] = 1, and then p advances one element. So p - a = 1.

Common wrong answer: 0. That reads *p++ as "increment the value, pointer stays". Brackets are the whole question.

MCQTrickyOriginal GATE-style

What does this print?

int a[4] = {1,2,3,4};
int *p = a;
(*p)++;
printf("%d %ld", a[0], (long)(p - a));
  1. 1 0
  2. 2 0
  3. 2 1
  4. 1 1

Answer: B — 2 0

The brackets force *p to be evaluated first, so the increment lands on a[0], which becomes 2. p never moves.

Common wrong answer: C (2 1). That is what *p++ would have done — the pointer would move and a[0] would stay 1.

NATTrickyOriginal GATE-style

With int a[5] at base address 1000 and sizeof(int) = 4, what is the value of

(char *)(&a + 1) - (char *)(a + 1) ?

Answer: 16

&a + 1 = 1000 + 20 = 1020 (it moves by the whole array). a + 1 = 1000 + 4 = 1004 (it moves by one element). The casts make the subtraction count bytes: 1020 − 1004 = 16.

Common wrong answer: 20 or 4. Each comes from applying only one of the two scales. Note that without the casts the subtraction would be between different pointer types.

Definitions, one line each

Address
The number of a byte; an object's address is its first byte's.
Pointer
A variable whose value is an address; type T * if it addresses a T.
&x
The address of the object x.
*p
The object at the address p holds — an object, not a copy.
Decay
An array expression becomes a pointer to its first element, except under sizeof, under &, or as a string-literal initialiser.
Dangling pointer
Holds a valid address whose object's lifetime has ended.

Formulas and their conditions

addr(a[i]) = base(a) + i × sizeof(T) T is the element type; i starts at 0.
addr(p + k) = addr(p) + k × sizeof(*p) The single scaling rule. k counts elements.
p2 - p1 = element count Only when both point into the same array (or one past its end).
addr(m[i][j]) = base + (i × C + j) × sizeof(T) C is the row length. Row-major, as C always stores.
a[i] ≡ *(a + i) ≡ i[a] The definition, not a trick. Legal because addition commutes.

Decision procedure for an output question

  1. Write down every declaration and the type it gives each name.
  2. Draw the array as cells with addresses, if there is one.
  3. Take the statements one at a time; after each, note the pointer's position and the array's contents.
  4. For any * and ++ combination, apply postfix first, then the star.
  5. Before committing to an answer, check for undefined behaviour: null, dangling, out of range, wrong type.

Traps, each with the counterexample that defuses it

"Arrays are pointers"
sizeof(a)=20, sizeof(p)=8.
"p+1 is one byte"
int* moves 4, char* moves 1.
"sizeof gives the length"
Inside f(int arr[10]), sizeof(arr) is 8.
"&a and a behave the same"
&a+1 jumps 20 bytes, a+1 jumps 4.
"*p++ increments the value"
It moves the pointer; (*p)++ changes the cell.
"Dangling means NULL"
It keeps the old address; a NULL test passes.

Quick revision questions

  1. What are the three exceptions to array decay?
  2. int a[7]; — what is sizeof(a)/sizeof(a[0])?
  3. char *s = "hi"; — is s[0]='H' allowed?
  4. int *p = a + 4; for int a[5] — may you compute it? May you dereference it?
  5. What type is &a for int a[5]?
  6. int **pp — how many dereferences to reach an int?
  7. Which binds tighter: postfix ++ or unary *?
  8. Does p2 - p1 give bytes or elements?
Answers
  1. Operand of sizeof; operand of unary &; a string literal initialising a char array.
  2. 7 (28/4 on this convention).
  3. No — string literals are not modifiable; that is undefined behaviour.
  4. Yes to computing (one past the end is allowed); no to dereferencing.
  5. int (*)[5] — a pointer to the whole array.
  6. Two.
  7. Postfix ++.
  8. Elements.
