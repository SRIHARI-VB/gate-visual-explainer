Topic and objective

TOPIC: The IPv6 address and the IPv6 base header — the 128-bit address as eight groups of sixteen bits, the five rules that decide its written form, the prefix arithmetic, the fixed forty-octet header, and the three IPv4 fields that were removed.

LEARNING OBJECTIVE: Write any 128-bit address in RFC 5952 canonical form and expand any legal form back to eight groups, including the two cases that decide marks (a single zero group is never compressed, and a tie between two zero runs goes to the first). Count the addresses in a prefix, subtract the one address a subnet reserves, and say why it is one and not two. Recite the eight header fields with their widths, check that they sum to 320 bits, and compute Payload Length and the resulting wire size for a packet with extension headers. Walk a Next Header chain. Build a modified EUI-64 interface identifier from a MAC address and a link-local address from that.

GATE RELEVANCE: Class C — a useful extension beyond the 2027 syllabus wording, with verified previous-paper evidence. The GATE 2027 CS syllabus, Section 10, names IPv4 and does not name IPv6; GATE CSE 2018 Question 13 did examine the IPv6 Next Header field, and the address arithmetic transfers directly to the CIDR questions the syllabus does name. The reasoning behind the class is set out in full in the second card.

PREREQUISITES: a prefix and its length, and the count $$2^{32-n}$$ for an IPv4 prefix (IP fragmentation, CIDR and NAT); the IPv4 header as a set of named fields; the idea of a 48-bit MAC address (Error detection, MAC and Ethernet); binary and hexadecimal place value, and powers of two.

Prerequisites, precisely

Must already be comfortable with:

  • A prefix of length $$n$$ and the count $$2^{32-n}$$ of IPv4 addresses it holds.
  • Hexadecimal: one hex digit is four bits, so four digits are sixteen bits.
  • That a MAC address is 48 bits, written as six octets.
  • Powers of two up to $$2^{10}$$, and the fact that $$2^{a+b} = 2^a \times 2^b$$.

Helpful, not required: having seen an IPv6 address written with a double colon, so that the third scene has something to correct.

Approximate learning time: 45–60 minutes with the animation, or 12 minutes for the Revision tab alone. The figure is an estimate, not a measurement.

The five ideas

  1. The address is eight groups of sixteen bits. Everything else is a way of writing those eight numbers down.
  2. Reading is generous and writing is strict. Any legal form expands to eight groups; exactly one form is canonical, and RFC 5952 fixes it.
  3. A single zero group is never compressed, and a tie goes to the first run. Those two rules are where the marks are lost.
  4. The header is a fixed forty octets. Eight fields, 320 bits, no header-length field, no checksum, no options, no router fragmentation.
  5. Payload Length is not Total Length. It counts what follows the base header, extension headers included, and the base header not at all.

Legend: green marks a value the page’s model computed and checked; amber marks a trap or a clause; red would mark a failing check, and none is failing on this page.

Intuition: a building with more floors

An IPv4 address is a short street address. There are only so many of them, and every new building has to reuse somebody’s number. An IPv6 address is the same idea with a much longer plot number, plus a rule that the last half of the number is the flat and the first half is the street.

The written form is the part that surprises people. Because the number is long, it is written in hex, and because it is mostly zeros, the zeros are allowed to collapse into a double colon. Collapsing is where the ambiguity lives, so the collapse has exactly five rules and no more.

Educational interpretation The analogy is exact about the split — prefix says where, interface ID says which — and loose about the writing, which has no counterpart in a postal address.

Formal definitions

An IPv6 address is a 128-bit value. It is written as eight groups of sixteen bits each, separated by colons, each group written as one to four hexadecimal digits.

A prefix of length $$n$$ is the first $$n$$ bits of an address, written after a slash. The remaining $$128-n$$ bits are the interface ID.

The base header is the fixed forty-octet header at the start of every IPv6 packet: eight fields, no options, no checksum.

address = 8 groups × 16 bits = 128 bits    header = 320 bits = 40 octets

Both lines are arithmetic, and both are checked by the page: the eight groups are the address, and the eight header fields sum to 320 bits, which is forty octets. Neither number is a convention you have to memorise.

Mathematical derivation A group holds sixteen bits because four hex digits hold four bits each. Four times four is sixteen, and eight times sixteen is one hundred and twenty-eight.

Level 1–2: the eight groups, and why hex

Binary would need 128 characters per address. Decimal would need 39 digits and still not align to anything. Hex gives four bits per character, so a group is four characters and the whole address is thirty-two — and a group boundary is also a natural place to break a routing decision.

So the address is read as eight independent sixteen-bit numbers. Converting one group is ordinary place value: 0202 is $$0\times16^3 + 2\times16^2 + 0\times16 + 2 = 514$$, which in binary is 0000 0010 0000 0010.

Mathematical derivation Each hex digit stands for four bits, so a group of four digits stands for sixteen. That is the whole reason a group is four characters and not five.

Level 3: the five rules of the written form

RFC 5952 fixes one canonical form. Applied in order:

  • Rule 1. Leading zeros inside a group are suppressed. 0db8 becomes db8, and 0000 becomes 0.
  • Rule 2. The digits a to f are lowercase.
  • Rule 3. The double colon appears at most once, because it stands for one or more groups of zeros.
  • Rule 4. The longest run of zero groups is the one compressed, and compression must be used to its maximum.
  • Rule 5. If two runs tie for longest, the first is compressed.

Two consequences that the rules imply and that people miss: a run of one zero group is never compressed, and a double colon may not be used where it would have to stand for no group at all.

Verified fact All five are quoted from RFC 5952, sections 4.1 to 4.3, whose own worked example for the tie rule is the address used in this lesson: 2001:db8:0:0:1:0:0:1 becomes 2001:db8::1:0:0:1.

Level 3: expansion is a count, not a guess

To read an address back, count the groups on each side of the double colon and let it stand for whatever makes eight. In 2001:db8::1 there are two groups before and one after, so the colon stands for five groups of zeros.

The test that decides whether a string is an address is therefore a single sentence: after expansion, are there exactly eight groups? Every malformed input fails that test, and nothing else needs checking.

Verified fact RFC 4291 says the double colon stands for one or more groups of 16 bits of zeros and can appear only once in an address. Both halves of that sentence are used by the parser on this page, and both are checked.

Level 4: prefix arithmetic, and the one reserved address

A prefix of length $$n$$ leaves $$128-n$$ bits, so it holds $$2^{128-n}$$ addresses. A $$/64$$ holds $$2^{64}$$, a $$/48$$ holds $$2^{80}$$, and a $$/48$$ therefore contains $$2^{16} = 65{,}536$$ subnets of size $$/64$$.

One address per subnet is reserved: the interface ID of all zeros is the subnet-router anycast address, which every router on that subnet must answer for. So a $$/64$$ has $$2^{64}-1$$ usable interface IDs, and there is no broadcast address, so no second reservation is needed.

usable in a $$/64$$: $$2^{64} - 1 = 18{,}446{,}744{,}073{,}709{,}551{,}615$$

The subtraction is one, not two. IPv4 subtracts two because it reserves a network address and a broadcast address; IPv6 reserves the anycast address and has no broadcast address to reserve.

Verified fact The subnet-router anycast address is predefined in RFC 4291 section 2.6.1, and all routers are required to support it for the subnets they are attached to.

Level 4: the header, field by field

Eight fields, in order: Version 4 bits; Traffic Class 8; Flow Label 20; Payload Length 16; Next Header 8; Hop Limit 8; Source Address 128; Destination Address 128. The sum is 320 bits, which is forty octets.

Three meanings that carry marks: Version is always 6; Hop Limit counts hops, not seconds; Payload Length counts the octets after this header, including every extension header, and excludes the forty octets of the base header itself.

Verified fact All eight widths and all three meanings are stated in RFC 8200 section 3, which is the current IPv6 specification (July 2017).

Level 5: what was removed, and the condition that removed it

Three fields are gone, and each removal has a stated replacement:

  • Header checksum. Gone. The link layer checks each hop and the transport layer checks the ends.
  • Options, and with them the header-length field. Moved into extension headers, so the base header can be fixed.
  • Identification, flags and fragment offset. Routers no longer fragment; only the source does, through a Fragment header, and a router that cannot forward sends ICMPv6 Packet Too Big (type 2).

The condition attached to the third: every IPv6 link must carry at least 1280 octets, so a source can always send something that fits.

Verified fact The 1280-octet minimum link MTU is RFC 8200 section 5; the Packet Too Big message with type 2 is RFC 4443 section 3.2, and it is the message path MTU discovery depends on.

Example 1 — write the canonical form

Given 2001:0DB8:0000:0000:0001:0000:0000:0001, write the RFC 5952 form.

  1. Suppress leading zeros. 2001:db8:0:0:1:0:0:1. 0db8 becomes db8, and each 0000 becomes 0.
  2. Lowercase. The D and B of DB8 become d and b. Already done in step 1 here; it matters when the input is uppercase.
  3. Find the zero runs. Groups 2 and 3 are zero, and groups 5 and 6 are zero. Two runs, each two groups long.
  4. Break the tie. The first run wins. RFC 5952 section 4.2.3: on equal length, shorten the first sequence.

Answer: 2001:db8::1:0:0:1 — seventeen characters, and the page’s model produces it and checks it.

2001:db8:0:0:1::1 expands to the same eight groups and is not canonical. If the question says canonical, only the first is right; if it says a valid representation, both are.

Example 2 — expand, and decide validity

Given fe80::202:b3ff:fe1e:8329, expand it and say what kind of address it is.

  1. Count. One group before the colon, four after. So the colon stands for $$8-5 = 3$$ groups of zeros.
  2. Expand. fe80:0000:0000:0000:0202:b3ff:fe1e:8329. Eight groups, so the string is a legal address.
  3. Read the prefix. The first ten bits are 1111 1110 10. That is fe80::/10, the link-local prefix.

Answer: a link-local address. Routers must not forward it off the link it was made on, which is what makes it useful for autoconfiguration and useless for reaching anything else.

Notice the interface ID: 0202:b3ff:fe1e:8329 has FF FE in the middle and a 02 in the first octet. That is a modified EUI-64 identifier built from a MAC address, which is Example 5.

Example 3 — the packet arithmetic

Given an IPv6 packet carrying an 8-octet Routing header and a 1000-octet UDP datagram. Find Payload Length and the size on the wire.

  1. Payload is everything after the base header: the Routing header plus the UDP datagram. $$8 + 1000 = 1008$$.
  2. Base header is not in the payload, and is 40 octets. It is fixed, so no length field is needed for it.
  3. On the wire the packet is $$40 + 1008 = 1048$$ octets. IPv4 would have written 1048 in Total Length, for the same packet.

Answer: Payload Length 1008; 1048 octets on the wire.

The off-by-forty error is the commonest slip: 1008 is the answer to “what does the field say”, and 1048 is the answer to “how big is the packet”. Read which one was asked.

Example 4 — count a prefix

Given the allocation 2001:db8:abcd::/48. How many /64 subnets does it contain, and how many usable interface IDs does one of them have?

  1. Subnet bits. The allocation fixes 48 bits and a /64 fixes 64, so the subnet field is $$64-48 = 16$$ bits. $$2^{16} = 65{,}536$$.
  2. Addresses in one /64. $$128-64 = 64$$ bits remain, so $$2^{64}$$ addresses. That is 18,446,744,073,709,551,616.
  3. Subtract the reserved one. The all-zero interface ID is the subnet-router anycast address. $$2^{64}-1$$ usable, and no broadcast address to subtract.

Answer: 65,536 subnets; 18,446,744,073,709,551,615 usable interface IDs each.

The allocation itself holds $$2^{80}$$ addresses, so a /48 is not a small thing. That is why the first three groups are enough to route on.

Example 5 — build a link-local address

Given the MAC address 00:1a:2b:3c:4d:5e, build the modified EUI-64 interface ID and the link-local address.

  1. Insert FF FE between the third and fourth octets: 00:1a:2b:ff:fe:3c:4d:5e. Six octets become eight, which is sixty-four bits.
  2. Flip the universal/local bit, which is the 0x02 bit of the first octet: 00 becomes 02, giving 02:1a:2b:ff:fe:3c:4d:5e. RFC 4291 Appendix A inverts it so a locally administered identifier can be hand-written as 0:0:0:1 rather than 0200:0:0:1.
  3. Group the octets in pairs: 021a:2bff:fe3c:4d5e. Two octets per group, which is what a group is.
  4. Prefix it with fe80::/64 and write the canonical form: fe80::21a:2bff:fe3c:4d5e. The leading zero of 021a is suppressed.

Answer: fe80::21a:2bff:fe3c:4d5e. Every step is computed by the page and compared with the example in RFC 4291 Appendix A.

The final compressed form suppresses the zero in 021a. That is rule 1, not a mistake: the interface ID is still sixteen bits per group.

Counterexample — why an example is not a rule

Most addresses you will see compress a run of three or four zero groups, so it is tempting to conclude that any zero group can be collapsed. Here is the smallest counterexample:

2001:0db8:0000:0001:0001:0001:0001:0001

Its canonical form is 2001:db8:0:1:1:1:1:1. The single zero group stays a 0. Written as 2001:db8::1:1:1:1:1 it is not canonical, and RFC 5952 section 4.2.2 forbids it explicitly.

The reason is not stylistic. A double colon must stand for one or more groups, so writing one zero group with it is a wasted opportunity at best, and at worst it invites a reader to expand it as two groups, which changes the address.

Mathematical derivation The compression rule is defined on the run length: a run of length $$k\ge 2$$ saves $$k-1$$ characters, and a run of length 1 saves none. So the rule that compresses only runs of at least two is the rule that saves the most characters.

The double colon at the end

2001:db8:: is legal: two groups then six of zeros, and the trailing colon compresses the run. But 2001:db8:1:2:3:4:5:6:: is not legal, because eight groups are already present and the colon would have to stand for zero groups.

The page’s parser refuses exactly this, and the refusal is in the model checks under “:: standing for no group at all”.

Zero runs at both ends

::1 is the loopback address: seven zero groups and a one. :: alone is the unspecified address: eight zero groups, and it is never a valid destination. Both compress a run at the boundary, which is why the formatter must treat the ends like any other run.

The model formats both from eight integers and checks them against the independent table, so the boundary case is exercised rather than assumed.

The IPv4-mapped address

An address in ::ffff:0:0/96 embeds an IPv4 address in its low 32 bits. RFC 5952 section 5 recommends mixed notation for exactly these well-known prefixes, so ::ffff:c000:0201 is written ::ffff:192.0.2.1.

This is the one place where dotted decimal appears inside an IPv6 address, and the page computes both forms and checks them.

A /127 is legal

A /127 holds two addresses and is used on point-to-point links. It is not “the same as IPv4’s /30”: IPv4 needs two of its four for network and broadcast, IPv6 needs neither of those two reservations on a /127 in the same way, and the subnet-router anycast matters only where a router is expected to answer.

The general rule still holds: subtract the anycast address where a router is present on the subnet, and check whether the question asked for addresses or usable interface IDs.

Jumbograms, and Payload Length zero

Payload Length is 16 bits, so it stops at 65,535. A larger payload is signalled by setting the field to 0 and carrying the real length in the Jumbo Payload option of the hop-by-hop header. A zero with no such option means a zero-length payload, which is a legal but useless packet.

So a zero in that field is ambiguous until you have read the hop-by-hop header — the only field in the base header whose meaning depends on another header.

Next Header 59

The value 59 means there is no next header at all. A packet can therefore end at an extension header with nothing behind it, which is legal and is how some control traffic is sent.

This is the value most often forgotten in a list, and it is the reason the chain is described as ending either at a transport header or at 59.

An extension header is part of the payload

RFC 8200 says explicitly that extension headers count towards Payload Length. So a packet with a 24-octet Routing header and 100 octets of TCP data has Payload Length 124, not 100.

If you forget this, every packet with an extension header is short by the size of that header, and the error is invisible unless you add the pieces up.

The EUI-64 errata

RFC 4291 Appendix A inserts 0xFF and 0xFE. Its own errata note records that an earlier version of the text said 0xFF twice, and explains that 0xFF 0xFE is the pair used when starting from a MAC-48.

Worth knowing because a page that quotes the old text will produce a different interface ID from the one every operating system produces.

Link-local addresses do not leave the link

A router must not forward a packet whose source or destination is link-local. So fe80::/10 is the address a host uses to talk to its neighbours before it has anything routable.

This is why a host can have several addresses at once: one link-local, and one or more global ones per prefix it has been told about.

The minimum MTU is a requirement, not a default

Every link must carry 1280 octets. That is what lets a source fragment once, at the start, and know the pieces will fit anywhere. A link that cannot carry 1280 must fragment below IPv6, at the link layer.

So 1280 is the number to use when a question says “the source does not know the path MTU”, and 1500 is the number to use when it says “Ethernet”.

Misconception 1 — “Payload Length counts the whole packet”

  1. The belief. Payload Length is IPv6’s name for Total Length, so a 1048-octet packet says 1048.
  2. Why it seems right. Both fields sit in the second word of the header, both are 16 bits, and both describe size.
  3. Why it is wrong. Payload Length counts what follows the base header. The base header is fixed at 40 octets and is therefore never counted.
  4. Minimal counterexample. An empty payload with no extension header is a valid packet of 40 octets on the wire, and its Payload Length is 0. If the field counted the packet, it would say 40.
  5. Correct rule. Field value plus 40 is the wire size, when no jumbo option is in play. Extension headers are inside the field.

Misconception 2 — “Any zero group can be compressed”

  1. The belief. The double colon is shorthand for zeros, so a single zero group can be written as a double colon too.
  2. Why it seems right. Most real addresses have long runs of zeros, so the pattern “zero means colon colon” is what a learner actually sees.
  3. Why it is wrong. The double colon stands for one or more groups. Using it for one group is forbidden by RFC 5952 section 4.2.2 and saves no characters.
  4. Minimal counterexample. 2001:0db8:0000:0001:0001:0001:0001:0001 is written 2001:db8:0:1:1:1:1:1. The zero stays.
  5. Correct rule. Compress the longest run, and only a run of at least two.

Misconception 3 — “A subnet reserves two addresses”

  1. The belief. A $$/64$$ has $$2^{64}-2$$ usable addresses, because IPv4 subtracts a network address and a broadcast address.
  2. Why it seems right. That is exactly what every IPv4 subnetting question does, and it is a habit that transfers badly.
  3. Why it is wrong. IPv6 has no broadcast address, so there is nothing to reserve for one. The single reservation is the subnet-router anycast address.
  4. Minimal counterexample. RFC 4291 section 2.6.1 defines one required anycast address per subnet, and no broadcast address anywhere in the architecture.
  5. Correct rule. Subtract one, and only when the question asks for usable interface IDs rather than addresses.

Misconception 4 — “The header checksum was removed because it was wrong”

  1. The belief. IPv6 dropped the checksum because checksums are unreliable, or because the transport layer does it better.
  2. Why it seems right. The usual one-line explanation is “the link layer already checks”, which sounds like a claim about correctness.
  3. Why it is wrong. It was removed because it cost every router a recomputation, since Hop Limit changes at each hop. The check was correct; it was expensive and largely redundant.
  4. Minimal counterexample. TCP and UDP checksums cover a pseudo-header that includes the addresses, so end-to-end integrity was already checked without the header field.
  5. Correct rule. No header checksum in IPv6; the UDP checksum becomes mandatory, which is the compensating change.

Misconception 5 — “Routers still fragment, just less often”

  1. The belief. IPv6 routers fragment only when they must, so fragmentation is rarer but still possible in transit.
  2. Why it seems right. The Fragment header exists, so fragmentation plainly exists.
  3. Why it is wrong. The Fragment header is used by the source. A router that cannot forward a packet discards it and returns ICMPv6 Packet Too Big (type 2).
  4. Minimal counterexample. RFC 8200 section 4.5 says fragmentation in IPv6 is performed only by source nodes, not by routers along the delivery path.
  5. Correct rule. Source fragments, router reports. Path MTU discovery is the mechanism that makes that workable.

Misconception 6 — “Anycast is a separate address type”

  1. The belief. IPv6 has four address types — unicast, multicast, anycast and broadcast — and each has its own prefix.
  2. Why it seems right. The list of types is usually taught as a list of four, and IPv4 does have a distinct class for multicast.
  3. Why it is wrong. Anycast addresses are taken from the unicast space and are syntactically indistinguishable from unicast; and there is no broadcast type at all.
  4. Minimal counterexample. RFC 4291 section 2.4 gives five rows in its type table and says anycast addresses are not syntactically distinguishable from unicast addresses.
  5. Correct rule. Three types exist in the type table — unicast, multicast, anycast-as-a-use — and the all-nodes group ff02::1 does the job broadcast used to do.

What a question on this topic actually asks

Across the papers this page could verify, an IPv6 item has one of four shapes, and three of them are arithmetic rather than recall:

  • A field width. “The IPv6 Next Header field is how many bits?” One remembered number, and one distractor that is the neighbouring field.
  • A canonical form. “Which of these is a valid / the canonical representation of …?” Decided by the count of groups and the two tie rules.
  • A count in a prefix. “How many addresses / subnets / usable interface IDs?” Decided by $$2^{128-n}$$ and by subtracting the right number.
  • A header or payload size. “What does Payload Length say, and how big is the packet?” Two different questions that share one packet.

Community observation Question indexes tag IPv6 items as field-width and comparison items far more often than as address-planning items. That is a catalogue’s tagging, not an official distribution, and it is not a forecast for 2027.

The procedure, in the order that avoids the trap

  1. Name the object. Is the question about the address, the prefix, the header, or the payload? The four have four different arithmetics.
  2. Expand before you compare. Two addresses that look different may be the same eight groups. Write both as eight groups and compare those.
  3. Check the count of groups. Any validity question is decided by whether the expansion lands on eight.
  4. Apply the two tie rules last. Longest run first, then first run on a tie, and never a single zero group.
  5. For a size question, add 40. Field value plus 40 gives the wire size; the wire size minus 40 gives the field. Say which one was asked.
  6. For a count question, subtract one. The subnet-router anycast address, and not two, because there is no broadcast address.

Steps 2 and 3 are the two that turn a guess into an answer, and both are mechanical: they need no memory of IPv6 trivia, only the eight-group rule.

I. 48
Q. Ethernet MAC address
II. 8
R. IPv6 Next Header
III. 32
S. TCP header’s sequence number

An item that is not a GATE CSE previous-year question

A question circulates as “GATE CSE 2013, Question 56”: “IPv6 does not support which of the following addressing modes?” with options unicast, multicast, broadcast and anycast, and the answer broadcast.

Community observation At least two indexes attribute it to GATE CSE 2013. A solved previous-year compilation attributes the same question, with the same question number, to ISRO CSE 2013. On the available evidence this page treats it as an ISRO question, not a GATE CSE one, and does not count it as a GATE previous-year question.

The fact it tests is nonetheless true and worth carrying: IPv6 has no broadcast address. The all-nodes group ff02::1 is a multicast address, and multicast is the mechanism that replaced broadcast.

This is the same trap in a different costume: a question is a GATE previous-year question only if it is printed in a GATE paper. An index labelling it GATE does not make it one.

MCQ original

Q1 — the canonical form

Which one of the following is the RFC 5952 canonical representation of 2001:0db8:0000:0000:0001:0000:0000:0001?

(a) 2001:db8:0:0:1:0:0:1   (b) 2001:db8::1:0:0:1   (c) 2001:db8:0:0:1::1   (d) 2001:db8::1::1

Answer: (b)

Two runs of two zero groups tie, and the first is compressed. The page’s formatter produces exactly this string, and the model checks it against an independent computation.

(a) compresses nothing. (c) compresses the second run, which is legal to read but not canonical. (d) uses the double colon twice, which RFC 4291 forbids outright.

Trap: (c) is the attractive wrong answer, because both runs are the same length and only the tie rule separates them.

Q2 — which statements hold

Select every true statement about the IPv6 base header.

(a) It is forty octets and has no header-length field.
(b) It contains a header checksum covering the header only.
(c) Payload Length counts the extension headers and not the base header.
(d) Hop Limit is decremented once per hop.
(e) A router may fragment a packet that is too large for the next link.

Answer: (a), (c) and (d)

(a) holds: eight fields summing to 320 bits, so the length is fixed and no field records it. (c) holds: RFC 8200 counts extension headers as payload. (d) holds: each forwarding node decrements it by one.

(b) fails: there is no header checksum in IPv6 at all. (e) fails: only the source fragments; a router discards the packet and sends ICMPv6 Packet Too Big, type 2.

(b) is the closest to true-sounding, because IPv4’s checksum covers the header only. (e) is the one that stays in people’s heads from IPv4.

Q3 — the payload field

An IPv6 packet carries a 24-octet Routing header and 500 octets of TCP data, with no other extension headers. The value in its Payload Length field is ______ octets.

Answer: 524

Payload = extension header + transport data = $$24 + 500 = 524$$. The base header’s 40 octets are not in the field, and the extension header’s 24 are.

The packet on the wire is $$40 + 524 = 564$$ octets, which is a different number and the answer to a different question.

Common wrong answers: 500 (forgetting the extension header) and 564 (counting the base header). Both are errors of exactly one term.

MCQ original

Q4 — the closely confused pair

Which statement distinguishes Payload Length from IPv4’s Total Length correctly?

(a) They are the same field under two names.
(b) Payload Length excludes the base header; Total Length includes the IPv4 header.
(c) Payload Length is 16 bits; Total Length is 32 bits.
(d) Payload Length excludes extension headers; Total Length includes options.

Answer: (b)

For one packet of 1048 octets, IPv4 writes 1048 and IPv6 writes 1008. The difference is exactly the header, and it is 40 because the IPv6 header is fixed.

(a) is false. (c) is false: both are 16 bits. (d) is false and is the interesting distractor — IPv6 counts extension headers inside Payload Length, while IPv4 counts its options inside Total Length, so the two behave the same way there.

This is the distinction the lesson calls the off-by-forty error, and it is the one that survives into real packet captures.

Q5 — count the subnets

An organisation is allocated 2001:db8:1234::/48 and splits it into /64 subnets. The number of /64 subnets it can create is ______.

Answer: 65536

The subnet field is $$64 - 48 = 16$$ bits, so $$2^{16} = 65{,}536$$. The page computes this with exact integer powers rather than floating point.

Each of those subnets then holds $$2^{64}$$ addresses, of which $$2^{64}-1$$ are usable interface IDs.

Common wrong answer: 256, which is the IPv4 habit of assuming an 8-bit subnet field. In IPv6 the field is whatever the two prefix lengths leave.

Q6 — the interface ID

A host with MAC address 00:1a:2b:3c:4d:5e forms a modified EUI-64 interface identifier. Its first two octets are:

(a) 00:1a   (b) 02:1a   (c) ff:fe   (d) 01:1a

Answer: (b), 02:1a

The universal/local bit is the 0x02 bit of the first octet. 00 exclusive-ored with 02 is 02, and the second octet is untouched, so the identifier begins 021a:2bff:fe3c:4d5e.

(a) is the unmodified MAC. (c) is the pair inserted in the middle, which lands at octets three and four, not one and two. (d) flips the low bit instead of the universal/local bit.

The whole construction is checked against RFC 4291 Appendix A’s own example, which uses this exact MAC address.

MSQ original

Q7 — valid against canonical

Select every string that is a valid IPv6 address, whether or not it is canonical.

(a) 2001:db8:0:0:1::1
(b) 2001:db8::1::2
(c) ::
(d) 2001:db8:1:2:3:4:5:6:7
(e) fe80::

Answer: (a), (c) and (e)

(a) expands to eight groups and is legal, though not canonical. (c) is the unspecified address: eight zero groups. (e) is a link-local prefix with an all-zero interface ID, which is legal as a string.

(b) uses the double colon twice, so it cannot be expanded. (d) has nine groups and no double colon, so it cannot be reduced to eight.

This is the distinction the lesson keeps returning to: validity is a count, canonical form is a separate and stricter question.

Q8 — the header sum

Ignoring any extension headers, how many bits of an IPv6 packet are spent on the source and destination addresses together?

Answer: 256

Two addresses of 128 bits each. They are 80 per cent of the 320-bit header, which is why the other six fields fit in two 32-bit words.

The remaining 64 bits are Version 4, Traffic Class 8, Flow Label 20, Payload Length 16, Next Header 8 and Hop Limit 8.

A useful sanity check on any remembered field width: the eight fields must sum to 320. A wrong width almost always breaks that sum.

The compression procedure in one place

  1. Suppress leading zeros in every group.
  2. Lowercase every a to f.
  3. Find every run of two or more zero groups.
  4. Compress the longest run, and the first one if two tie.
  5. Use the double colon once, never for a single zero group, never where it would stand for nothing.

To read one back: count the groups, let the colon absorb the difference to eight, and refuse anything that does not land on eight.

Next Header values, and the order

Values: 0 hop-by-hop · 43 routing · 44 fragment · 50 ESP · 51 AH · 59 no next header · 60 destination options · 6 TCP · 17 UDP · 58 ICMPv6.

Order: base header, hop-by-hop, destination options, routing, fragment, AH, ESP, destination options again, upper layer.

ICMPv6 types: 1 destination unreachable · 2 packet too big · 3 time exceeded · 128 and 129 echo · 133 router solicitation · 134 router advertisement · 135 neighbour solicitation · 136 neighbour advertisement.

Type 2 is the one to remember: it is what replaces router fragmentation.

Six sentences to carry into the exam

  1. The address is eight groups of sixteen bits, and the written form is a choice among legal spellings.
  2. A single zero group is never compressed, and a tie between two runs goes to the first.
  3. Validity is a count to eight; canonical form is a separate, stricter question.
  4. The header is fixed at forty octets with eight fields summing to 320 bits, no checksum and no options.
  5. Payload Length excludes the base header and includes extension headers, so field plus 40 is the wire size.
  6. A subnet reserves one address, not two, because there is no broadcast address in IPv6.

If a question turns on anything else — a prefix’s size, a chain’s order, an interface ID — it is one of the procedures on this tab applied to the numbers in the question.

  • RFC 8200, Internet Protocol, Version 6 (IPv6) Specification Read this run. Supports: the eight header fields and their widths, the payload-length definition including extension headers, the hop-limit meaning and the note that packet lifetime is not required, the statement that fragmentation is performed only by source nodes, the 1280-octet minimum link MTU, and the prescribed order of extension headers.
  • RFC 4291, IP Version 6 Addressing Architecture Read this run. Supports: the type table with its binary prefixes, the double colon appearing only once, the requirement that interface IDs be 64 bits for unicast addresses not beginning 000, the link-local fe80::/10 format, the subnet-router anycast address in section 2.6.1, and Appendix A’s modified EUI-64 construction with the inverted universal/local bit.
  • RFC 5952, A Recommendation for IPv6 Address Text Representation Read this run. Supports: all five canonical-form rules, the prohibition on compressing a single zero group, the longest-run and first-run tie rules, and the mixed-notation recommendation for well-known prefixes that embed an IPv4 address.
  • RFC 4443, ICMPv6 Supports: the message type numbers, and Packet Too Big (type 2) as the message a router sends when a packet is larger than the outgoing link MTU.
  • RFC 8201, Path MTU Discovery for IPv6 Supports: why Packet Too Big exists, and the rule that a node must not lower its path-MTU estimate below the 1280-octet minimum.
