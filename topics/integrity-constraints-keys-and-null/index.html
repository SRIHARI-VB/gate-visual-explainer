Topic and objective

TOPIC: Integrity constraints in the relational model — the key constraints, the foreign key and its referential actions, and what each one does when the value involved is NULL. This is the item "Integrity constraints" in Section 9 of the official GATE 2027 CS syllabus.

LEARNING OBJECTIVE: Given a schema and one write, decide whether the engine accepts it, without running it. Count which candidate rows NOT NULL, UNIQUE, PRIMARY KEY and CHECK accept when NULL is one of the candidates. Read a foreign key as a promise in one direction only, and say what MATCH SIMPLE, MATCH FULL and MATCH PARTIAL do to a composite key that contains a null. Trace an ON DELETE action to its full closure, in rounds, including a cascade that stops because the referencing action was SET NULL. Separate what a declaration enforces from what a functional-dependency proof shows, and say which constraints may be deferred to COMMIT.

I read this topic as one question in four costumes: does this write keep every declared predicate non-FALSE? A key answers it for a column set, a CHECK answers it for a row, a foreign key answers it across two tables, and an action answers it for the rows that the write touches indirectly. The whole lesson is that one predicate, and the reason NULL keeps deciding the answer is that UNKNOWN is not FALSE.

Prerequisites

  • Relations, tuples and attributes. A relation is a set of tuples over a schema; a constraint is a predicate on an instance. Built in Relational algebra, tuple calculus and SQL.
  • Relational algebra. Projection and set difference, because referential integrity is one subtraction. Also in that lesson.
  • Functional dependencies and candidate keys. A candidate key is a minimal superkey, which is what a key constraint declares. Built in Functional dependencies and normal forms.
  • Three-valued logic and NULL. NULL means "no value", comparisons with it yield UNKNOWN, and a WHERE clause keeps only TRUE. Built in the SQL lesson; this page uses it but does not re-teach it, and re-derives only the parts a constraint needs.
  • Sets and subsets. Counting superkeys means counting subsets that are closed upward. Built in Sets and set operations.

No prior knowledge of triggers, assertions or of any particular DBMS product is assumed. PostgreSQL is named only where the standard leaves a choice to the implementation, and that naming is labelled as a product fact each time.

Ten scenes, each one argument:

  1. The gate. A write entering a check, and two exits: applied, refused. The four families of constraint beside it.
  2. The key ladder. One three-row relation with five superkeys, two candidate keys and one primary key, drawn as nested claims.
  3. Three verdicts on one NULL. A 3 × 3 table of NOT NULL, UNIQUE and PRIMARY KEY against the candidates NULL, 1, 2, with the counts printed.
  4. Three-valued CHECK. The same three candidates through a > 5, then through NOT (a > 5), with the single surviving row identified.
  5. Match types. Nine composite candidates against a one-row parent, with SIMPLE, FULL and PARTIAL verdicts counted side by side.
  6. Five actions. NO ACTION, RESTRICT, CASCADE, SET NULL, SET DEFAULT, each with what happens to the child and when it is checked.
  7. Closure in rounds. The 2005 table, deleted row by deleted row, until the closure is three tuples.
  8. SET NULL stops the chain. The 2017 Set 2 tables, the one updated row, and the zero that follows.
  9. Four operations. Insert and delete, on parent and child, with the enumeration count behind each verdict.
  10. Declared against provable. What a key enforces, what needs a trigger, and where a deferred check fires.

The five ideas to leave with

  1. A constraint is satisfied when its predicate is not FALSE. UNKNOWN satisfies it, and that single sentence decides every NULL question in this topic.
  2. PRIMARY KEY = UNIQUE + NOT NULL. UNIQUE alone accepts many NULLs, because two nulls are never equal; the standard leaves that choice to the implementation.
  3. A foreign key is a one-directional promise: every non-null child key must exist in the parent. The parent need not be referenced by anything.
  4. The action, not the data, decides a cascade question. CASCADE and SET NULL differ in whether a child row dies or merely changes, and a SET NULL stops the chain that a CASCADE would continue.
  5. Only child-insert and parent-delete can orphan a row. Parent-insert and child-delete cannot, and that asymmetry is the whole content of the "which operation violates" question.

Intuition: a doorman with a written list of rules

Picture a club with one door and a doorman holding a short list. The list says: every member needs a number nobody else has; every member needs a name; the sponsor you name must already be inside. Those rules are written once, at the door, and the doorman applies them to everybody who arrives — he does not care which travel agent sent them. That is what a schema-level constraint is: a rule attached to the table, not to the program that writes to it.

Now the part that makes the topic interesting. A blank line on the form is not the same as a wrong answer. The doorman has a third response to a blank: "I cannot tell whether this breaks a rule, so I will let it through." That third response is UNKNOWN, and it is why a rule like "the number must be positive" never stops a missing number, and why a rule like "numbers must be distinct" never stops two blanks. The whole lesson is about which of the doorman's rules treat a blank as a failure and which treat it as none of their business.

Level 1 — Intuition, in one sentence each

  • Constraint. A predicate written in the schema that every write must leave not-FALSE.
  • Superkey. A set of columns whose values never repeat in the table.
  • Candidate key. A superkey with nothing to spare.
  • Primary key. The candidate key the schema picks, and the only one that also forbids NULL.
  • Foreign key. A set of child columns whose non-null values must appear as a key in the parent.
  • Referential action. What happens to the child when the parent's key is deleted or changed.
  • Deferred check. A constraint whose test is postponed to the end of the transaction.

Level 2 — Formal definitions

Verified fact An integrity constraint is a Boolean condition that the database must satisfy at all times; the DBMS rejects any statement that would leave it unsatisfied. SQL states constraints as part of the schema, in CREATE TABLE or ALTER TABLE.

Verified fact A superkey of a relation schema is a set of attributes such that no two tuples agree on all of them. A candidate key is a superkey no proper subset of which is a superkey. The primary key is one chosen candidate key; the others are alternate keys.

Verified fact A foreign key is a set of attributes in the referencing (child) relation whose values must either be null or match the values of a declared key in the referenced (parent) relation. The referenced columns must carry a PRIMARY KEY or UNIQUE constraint.

Mathematical derivation The definition of PRIMARY KEY as a constraint follows from those two: uniqueness gives "no two tuples agree", and the not-null requirement removes the tuple that would agree with nothing. Formally, PRIMARY KEY = UNIQUE ∧ NOT NULL, and the page checks this inequality in code: the number of candidates a primary key accepts is never larger than the number a unique constraint accepts.

Level 5 — the boundary conditions, stated up front

Three boundaries decide most of the marks. First, the satisfaction rule is "not FALSE", not "TRUE": a CHECK whose expression is UNKNOWN passes, so a CHECK cannot be used to forbid NULL. Second, the treatment of nulls in a UNIQUE constraint is left by the SQL standard to the implementation; PostgreSQL's default is that nulls are distinct, SQL Server's documented behaviour is that multiple nulls are duplicates, so a question that does not name an engine is answered under the default its source states. Third, a referential action is not a constraint: it is a repair the engine performs when a constraint would otherwise be violated, and it runs as part of the data-changing statement even when the constraint itself is deferred.

Level 3 and 4 — why the foreign key target has to be unique

A foreign key is a promise about existence, so the promise needs a unique referent. Suppose course.dept referenced department.name and department allowed two rows named "CSE". A course row saying "CSE" would then point at two departments at once, and "which department owns this course" would have no answer — the reference would not identify anything.

That is the argument, and it is a derivation rather than a rule to memorise: a reference resolves a value to a row, and a value that names two rows resolves to neither. It also explains a fact that surprises people: the target does not have to be the primary key. Any UNIQUE constraint will do, because uniqueness is the only property the reference needs. A table may therefore have several columns that other tables point at, and a table may point at itself — a manager column referring to the employee key in the same row set.

Why a CHECK cannot forbid NULL

Verified fact PostgreSQL's manual, on CREATE TABLE, states the rule directly: a CHECK "specifies an expression producing a Boolean result which new or updated rows must satisfy ... Expressions evaluating to TRUE or UNKNOWN succeed. Should any row ... produce a FALSE result, an error exception is raised."

Mathematical derivation A comparison with NULL yields UNKNOWN. So for a row where the column is NULL, x > 0 is UNKNOWN, and UNKNOWN is not FALSE, so the row is accepted. The same holds for the negated test, so declaring both CHECK (x > 0) and CHECK (NOT (x > 0)) still admits the null row: the two constraints are a contradiction only over TRUE and FALSE, and UNKNOWN sits outside both. The page evaluates all three candidates through both checks and finds exactly one survivor, the NULL row.

Why UNIQUE lets a second NULL in

Verified fact PostgreSQL's manual: "In general, a unique constraint is violated if there is more than one row in the table where the values of all of the columns included in the constraint are equal. By default, two null values are not considered equal in this comparison. That means even in the presence of a unique constraint it is possible to store duplicate rows that contain a null value in at least one of the constrained columns."

Verified fact The same page adds that the default null treatment "is implementation-defined according to the SQL standard", and that PostgreSQL 15 added the clause NULLS NOT DISTINCT to reverse it.

Mathematical derivation The constraint tests equality, and NULL = NULL is UNKNOWN rather than TRUE, so the test never fires between two nulls. That is the whole mechanism: UNIQUE is not "the column has no repeated value", it is "no two rows are equal on this column set", and two nulls are not equal.

Scene 5 uses the nine ordered pairs from {NULL, 1, 2}² against a parent holding (1, 1), so there are nine candidates and three match rules.

A count without its instance is meaningless, and a count that was not computed is a guess. Both are avoided here: the animation prints the instance on the canvas beside the number, and the number comes from the same function that the model checks re-verify by enumeration.

Level 6 and 7 — where the exam actually bites

Two of the four previous-year items on this page are closure counts: a delete is performed and the question asks how many further rows must go. The other two are definitional: which statement about foreign keys is true, and which algebra expression must be empty when referential integrity holds. The closure questions are the ones that separate a careful candidate, because a cascade is transitive and a set-null is not.

The procedure that always works is a round-based fixpoint. Round one: take the key values that the statement removed. Round two: find every child row that references one of those values, and apply the declared action. A CASCADE adds new key values to the set, so the process repeats. A SET NULL changes a child row without removing its key, so it adds nothing. Stop when a round adds nothing. The 2005 question needs three rounds and the 2017 question needs one, and the difference between the answers 3 and 0 is entirely that difference.

The referential actions, precisely

Verified fact PostgreSQL's CREATE TABLE page defines five actions. NO ACTION: "Produce an error if the deletion or update would create a foreign key constraint violation. If the constraint is deferred, this error will be produced at constraint check time if there still exist any referencing rows. This is the default action." RESTRICT: "Produce an error if a row to be deleted or updated matches a row in the referencing table. This prevents the action even if the state after the action would not violate the foreign key constraint."

Verified fact CASCADE deletes the referencing rows, or writes the new key values into them. SET NULL sets the referencing columns to null. SET DEFAULT sets them to their defaults, and "there must be a row in the referenced table matching the default values, if they are not null, or the operation will fail."

Verified fact On deferral the same page says: "Only UNIQUE, PRIMARY KEY, EXCLUDE, and REFERENCES (foreign key) constraints accept this clause. NOT NULL and CHECK constraints are not deferrable", and "Referential actions are executed as part of the data changing command, even if the constraint is deferred."

The match types, precisely

Verified fact From the same page: "There are three match types: MATCH FULL, MATCH PARTIAL, and MATCH SIMPLE (which is the default). MATCH FULL will not allow one column of a multicolumn foreign key to be null unless all foreign key columns are null; if they are all null, the row is not required to have a match in the referenced table. MATCH SIMPLE allows any of the foreign key columns to be null; if any of them are null, the row is not required to have a match in the referenced table. MATCH PARTIAL is not yet implemented."

Community observation A database Stack Exchange answer quotes the standard's definitions, which add the third case: under MATCH PARTIAL, if at least one referencing column is non-null, the row passes only if a referenced row matches every non-null referencing column. This page models that definition so the three counts can be compared, and labels it as the standard's rule, not as PostgreSQL behaviour.

What a constraint is not

A constraint is not a query: it cannot return rows, and a CHECK may not read another row of the same table, let alone another table. It is not a trigger: it has no body and no ordering. It is not a type: a domain check on a type applies everywhere that type is used, while a CHECK applies to one column or one table. And it is not a proof: a schema can enforce every key it declares and still permit an instance that violates a functional dependency nobody declared. That last distinction is the one that links this topic to normalisation, and it is why a BCNF schema is not automatically a checked one.

Worked examples — every decision written down

Each example states the schema, the instance and the write, then shows the check that decides it. The numbers are the ones the page computed; the animation draws the same values from the same model.

Example 1 — GATE CSE 2005, the cascade closure

Verified fact The question gives one table with attributes A and C, "A is the primary key and C is the foreign key referencing A with on-delete cascade", holding (2,4), (3,4), (4,3), (5,2), (7,2), (9,5), (6,4). The tuple (2,4) is deleted and the question asks for the set of tuples that must additionally be deleted.

1. Delete (2,4). The key value 2 has gone.

2. Round 1: rows whose C is 2 — (5,2) and (7,2). Keys 5 and 7 have now gone.

3. Round 2: rows whose C is 5 — (9,5). Rows whose C is 7 — none.

4. Round 3: rows whose C is 9 — none. The closure is closed.

Answer: (5,2), (7,2) and (9,5) — three tuples, option C. Option B is the answer after one round only, which is the trap: a cascade is transitive.

Example 2 — GATE CSE 2017 Set 2 Q19, the cascade that never fires

Verified fact T1(P,Q) holds (2,2), (3,8), (7,3), (5,8), (6,9), (8,5), (9,8); T2(R,S) holds (2,2), (8,3), (3,2), (9,7), (5,7), (7,2). In T1, P is the key and Q references T2.R with on-delete cascade. In T2, R is the key and S references T1.P with on-delete set NULL. Delete (3,8) from T1; how many additional records must be deleted from T1?

1. T1's key value 3 has gone. T2's row (8,3) references it through S.

2. The action on T2.S is SET NULL, so that row becomes (8, NULL). It is updated, not deleted.

3. No row of T2 was deleted, so the cascade from T1.Q to T2.R has nothing to fire on.

4. Nothing propagates back into T1.

Answer: 0, which is the official key. The whole question is the difference between a delete and an update: had T2.S been declared CASCADE, the chain would have continued.

Example 3 — the three verdicts on one NULL

Table holds a = 1 and a = NULL. Candidates are NULL, 1 and 2.

NOT NULL: NULL refused, 1 accepted, 2 accepted — 2 of 3.

UNIQUE: NULL accepted (it is not equal to the existing NULL), 1 refused (it equals the existing 1), 2 accepted — 2 of 3.

PRIMARY KEY: NULL refused (not-null half), 1 refused (unique half), 2 accepted — 1 of 3.

Reading: the primary key accepts strictly fewer rows than either half, which is the inequality the page checks in code. With UNIQUE NULLS NOT DISTINCT the unique constraint would also accept only 1 of 3.

Example 4 — a CHECK that does not do what it says

A column is declared price numeric CHECK (price > 0), and the insert supplies price = NULL.

NULL > 0 is UNKNOWN. The constraint is satisfied when the expression is TRUE or UNKNOWN, so the row is accepted. The table now holds a product with no price, and the check that was supposed to prevent that did nothing.

Fix: price numeric NOT NULL CHECK (price > 0). Two constraints, because they forbid two different things: one forbids a missing value and the other forbids a bad value. Adding CHECK (NOT (price > 0)) instead would not help — it is UNKNOWN on the same row.

Example 5 — nine candidates, three match rules

Parent P(x, y) holds one row, (1,1). The child's key is the pair (x, y). Candidates are the nine ordered pairs from {NULL, 1, 2}².

MATCH SIMPLE accepts 6: every pair with at least one null (five of them), plus (1,1). The three non-null pairs that are not (1,1) fail.

MATCH FULL accepts 2: (NULL, NULL) and (1,1). A mixed pair such as (1, NULL) fails, because FULL allows only all-null or all-match.

MATCH PARTIAL accepts 4: the all-null pair, (1,1), and the two pairs that match on their non-null column — (1, NULL) matches on x, (NULL, 1) matches on y. (NULL, 2) fails because no parent row has y = 2. The page checks that both FULL and PARTIAL are subsets of SIMPLE, which is the sanity condition these definitions must satisfy.

Example 6 — GATE CSE 2004 Q13, referential integrity as a subtraction

Verified fact Let R1(A, B, C) and R2(D, E) have primary keys A and D, and let C be a foreign key in R1 referring to R2. Suppose the instances r1 and r2 satisfy that constraint. Which expression must be empty?

The promise is: every value of C either is null or appears in D. Relational algebra has no nulls, so under that reading every value of C appears in D, and therefore the projection of C onto r1 minus the projection of D onto r2 is empty.

Answer: Π_C(r1) − Π_D(r2), which is option 2 (B). The reverse subtraction is not empty in general: a parent key need not be referenced by anything, so Π_D(r2) − Π_C(r1) can be non-empty. Option 3 is not empty either, since it pairs a row with unrelated rows; option 4 is a join that returns matched rows, not an empty relation.

Example 7 — a circular pair, and why deferral exists

Two tables reference each other: dept(head int REFERENCES emp) and emp(dept int REFERENCES dept). Inserting the first row of either table violates the other's key, whichever order you choose, because the row it needs does not exist yet.

1. Declare both foreign keys DEFERRABLE INITIALLY DEFERRED.

2. Insert the department with a null head, insert the employee with the department, then update the department's head.

3. Both checks run at COMMIT, when both rows exist, and both pass.

Reading: deferral changes when the error appears, not whether it appears. Leave the employee's department pointing at nothing and the COMMIT fails. Note also that the referential actions themselves are not deferred: they run with the statement.

Example 8 — a composite key, a composite reference, and one null

Enrolment is keyed by (sid, cid), and both columns are foreign keys. Suppose instead that a single foreign key references course(dept, number) as a pair, and a row is inserted with dept = 'CSE' and number = NULL.

Under MATCH SIMPLE, the null in one column excuses the whole reference: the row is accepted even though the pair ('CSE', NULL) matches nothing. Under MATCH FULL the same row is refused, because one column is null and the other is not.

Reading: this is the case where the default is the dangerous choice. If both columns are required, declare them NOT NULL; that forbids the mixed row outright and makes the match type irrelevant.

Boundaries, and what each one changes

Each card names a condition the rule assumes, then shows the smallest case where the condition fails and what the answer becomes. None of these is a curiosity: the first is why a UNIQUE question must name its engine, and the last is why a CHECK cannot express a rule that spans rows.

An empty parent table

With no rows in the parent, the only child values that can be inserted are nulls. Under MATCH SIMPLE a null child key passes, so the child table can be filled entirely with nulls while the parent is empty.

That is not a bug in the constraint; it is the definition of a reference that only applies to non-null values. A schema that needs a mandatory reference must say NOT NULL, and then the empty parent blocks every insert.

A foreign key that points at UNIQUE, not at the primary key

The target of a foreign key may be any column set carrying a PRIMARY KEY or UNIQUE constraint. On the relation used in this lesson, {A} and {B, C} are both candidate keys, so a child may reference either.

What is not allowed is a reference to a column set that is only indexed. A unique index also satisfies the requirement in PostgreSQL, but the guarantee is the same one: the reference must resolve to at most one row.

A self-referencing foreign key

Verified fact GATE CSE 2021 Set 2 Q6 offers "a foreign key in a relation scheme R cannot be used to refer to tuples of R", and the key is that this is false: employee(eid, mid) with mid referencing eid is the standard example.

The same question's first statement, that a scheme can have at most one foreign key, is also false. A table may carry as many foreign keys as it has references to make, and a self-reference is one of them.

SET DEFAULT with no matching default row

Verified fact PostgreSQL: for SET DEFAULT, "there must be a row in the referenced table matching the default values, if they are not null, or the operation will fail."

So a delete that was expected to succeed can fail because a repair it triggered was impossible. This is the one action whose failure is caused by a value nobody wrote in the statement being deleted.

Deferral does not defer the repair

Verified fact "Referential actions are executed as part of the data changing command, even if the constraint is deferred."

So deferring a foreign key postpones the error for a still-dangling reference; it does not postpone the cascade, the set-null or the set-default. A question that mixes the two is testing exactly this sentence.

A CHECK that tries to read another row

Verified fact PostgreSQL states plainly that it does not support CHECK constraints that reference table data other than the new or updated row, and warns that such a constraint "may appear to work in simple tests" without being guaranteed.

A rule such as "a student's total credits equals the sum of the courses passed" is therefore not a CHECK. The standard's tool is an assertion; where the engine lacks assertions, a trigger is the route, and the rule is then no longer declarative.

Six beliefs that cost marks, each with its counterexample

Each card states the belief as a candidate would hold it, gives the smallest instance that refutes it, and names what to say instead.

1. "A CHECK prevents NULL"

Belief: CHECK (price > 0) means every price is positive, so a missing price cannot be stored.

Counterexample: insert price = NULL. The expression is UNKNOWN, and a CHECK is satisfied by TRUE or UNKNOWN, so the row is accepted.

Say instead: a CHECK forbids values for which it is FALSE. It forbids a missing value only if you also declare NOT NULL.

2. "UNIQUE means at most one NULL"

Belief: a unique column can hold one null, because two nulls would be duplicates.

Counterexample: PostgreSQL's default treats two nulls as distinct, so any number of rows may hold NULL in a UNIQUE column. SQL Server's documented behaviour is the opposite, which is why the standard leaves it to the implementation.

Say instead: UNIQUE tests equality; two nulls are not equal; the default null treatment is implementation-defined and PostgreSQL 15 added NULLS NOT DISTINCT to reverse it.

3. "A composite primary key may contain a null in one column"

Belief: only the whole key has to be unique, so one column of a two-column primary key may be null as long as the other differs.

Counterexample: a primary key is UNIQUE plus NOT NULL applied to every column of the key. A row with a null in any key column is refused, and in PostgreSQL a primary key column is declared NOT NULL implicitly.

Say instead: uniqueness is about the tuple of key values; non-nullness is about each column. The second half is the one that catches people.

4. "CASCADE and SET NULL both remove rows"

Belief: any referential action that fires on a delete removes the child rows, so a chain continues either way.

Counterexample: GATE CSE 2017 Set 2 Q19. The referencing action is SET NULL, so the child row survives with a null key, no deletion happens in the second table, and the cascade back into the first table never fires. The answer is 0.

Say instead: CASCADE deletes; SET NULL and SET DEFAULT update. Only a deletion can continue a cascade.

5. "A foreign key must reference the primary key"

Belief: REFERENCES only accepts the target table's primary key.

Counterexample: any UNIQUE constraint works, and omitting the target column list is what defaults to the primary key. A table with two candidate keys can be referenced through either.

Say instead: the target must be unique, and the primary key is only the default choice. The reference needs uniqueness, not primacy.

6. "Referential integrity means every parent is referenced"

Belief: the constraint is a two-way correspondence, so a department with no employees violates it.

Counterexample: the promise runs from child to parent only. GATE CSE 2004 Q13 turns on exactly this asymmetry: Π_C(r1) − Π_D(r2) must be empty, while Π_D(r2) − Π_C(r1) need not be.

Say instead: every non-null child value must exist in the parent; a parent value need not be used. That is why the subtraction goes one way.

Five question shapes, and the procedure that answers all of them

Each pattern names what the paper gives, what it asks, and the one decision that resolves it. The previous-year items are listed with year and paper; nothing here is presented as an official question without them.

Pattern A — closure counting

Given: a table or two, the keys, and the referential action on each foreign key. Asked: how many further rows are deleted.

Decision: run rounds. Take the keys the statement removed; find child rows referencing them; apply the action; a CASCADE adds keys and the process repeats, while SET NULL and SET DEFAULT add nothing.

Seen in: GATE CSE 2005 (answer 3) and GATE CSE 2017 Set 2 Q19 (answer 0).

Pattern B — which operation can violate

Given: two relations, a foreign key from one to the other, and four operations. Asked: which can violate referential integrity.

Decision: only child-insert and parent-delete can orphan a row. Parent-insert adds a key; child-delete removes a reference. The page verifies this by enumerating every legal instance over a two-value domain and applying each operation.

Note: this shape appears in several papers and in ISRO and other recruitment tests. Where the year and paper cannot be confirmed for a GATE item, this page does not label one.

Pattern C — the algebra of a promise

Given: two schemas with a foreign key, and the statement that the instances satisfy it. Asked: which relational-algebra expression must be empty.

Decision: translate the promise into a subtraction and keep the direction: child keys minus parent keys. Then check the other options for the reverse direction, a theta-join that pairs unrelated rows, or a join that returns matches.

Seen in: GATE CSE 2004 Q13 (option 2).

Pattern D — statement pairs about keys

Given: two statements about the relational model. Asked: which combination is correct.

Decision: try to build a schema that makes each statement false. "At most one foreign key" fails on an enrolment table with two; "cannot refer to itself" fails on a manager column.

Seen in: GATE CSE 2021 Set 2 Q6 (both false).

Pattern E — NULL against a constraint

Given: a constraint and a row containing NULL. Asked: whether the row is accepted, or which pairs of queries agree.

Decision: evaluate the predicate to TRUE, FALSE or UNKNOWN, then apply the acceptance rule of that constraint: CHECK wants not-FALSE, NOT NULL wants non-null, UNIQUE wants no equality, PRIMARY KEY wants both.

Where: the three-valued logic itself is built in Relational algebra, tuple calculus and SQL; this page applies it to constraints.

The five-step procedure

  1. Name the constraint kind in the question: key, reference, row check, or general.
  2. Write its acceptance rule before looking at the data: not-FALSE, non-null, no-equality, or existence.
  3. Fix the instance and, if NULL is involved, evaluate to three values rather than two.
  4. Apply the write and, for a reference, follow the action in rounds until nothing changes.
  5. Check the result against the constraint itself: does the surviving instance satisfy it? The page runs that check on both of its closure answers.

The five traps

  • Stopping a cascade after one round: 2005 becomes 2 instead of 3.
  • Counting a SET NULL as a deletion: 2017 becomes non-zero.
  • Reading UNKNOWN as FALSE, which turns an accepted null row into a refused one.
  • Reversing the subtraction in the algebra pattern, which makes a parent-only key look like a violation.
  • Answering what a well-designed schema would do instead of what the stated constraint does.

MCQGATE CSE 2021 Set 2 Q6

Consider the following statements S1 and S2 about the relational data model:

S1: A relation scheme can have at most one foreign key.
S2: A foreign key in a relation scheme R cannot be used to refer to tuples of R.

Which one of the following choices is correct?

  1. Both S1 and S2 are true
  2. S1 is true and S2 is false
  3. S1 is false and S2 is true
  4. Both S1 and S2 are false

Answer: D — both S1 and S2 are false

S1 is false. An enrolment scheme (sid, cid, marks) has sid referencing student and cid referencing course: two foreign keys in one scheme. Nothing in the model limits the count.

S2 is false. employee(eid, mid) with mid referencing eid of the same relation is a self-reference, and it is a standard design.

What it tests. That "foreign key" is a reference, not a role reserved for other tables. Both statements are the kind of plausible-sounding restriction that a candidate invents under time pressure.

MCQGATE CSE 2004 Q13

Let R1(A, B, C) and R2(D, E) be two relation schemas, with primary keys A and D respectively, and let C be a foreign key in R1 referring to R2. Suppose there is no violation of the referential integrity constraint in the instances r1 and r2. Which of the following relational algebra expressions would necessarily produce an empty relation?

  1. ΠD(r2) − ΠC(r1)
  2. ΠC(r1) − ΠD(r2)
  3. ΠD(r1 ⋈C ≠ D r2)
  4. ΠC(r1 ⋈C = D r2)

Answer: option 2 — ΠC(r1) − ΠD(r2) is empty

Referential integrity says every value of C appears in D. Relational algebra has no nulls, so every value of C is in the projection of D, and the subtraction leaves nothing.

Why the others are not necessarily empty. Option 1 reverses the subtraction: a parent key need not be referenced, so D can contain values no child uses. Option 3 pairs rows of r1 with rows of r2 whose C and D differ, which normally returns rows. Option 4 is a join and returns matched rows, which is the opposite of empty unless the child table is empty.

Trap. Option 3 looks like a violation test, and a candidate who reasons "C ≠ D cannot hold when C is a foreign key" forgets that the comparison is between a child row and every unrelated parent row.

NATGATE CSE 2005 (2-mark)

A table has two attributes A and C, where A is the primary key and C is the foreign key referencing A with on-delete cascade. Its rows are (2,4), (3,4), (4,3), (5,2), (7,2), (9,5), (6,4).

The number of tuples that must be additionally deleted to preserve referential integrity when the tuple (2,4) is deleted is ______.

Answer: 3

Round 1: C = 2 gives (5,2) and (7,2). Round 2: C = 5 gives (9,5); C = 7 gives nothing. Round 3: C = 9 gives nothing. The closure is three tuples: (5,2), (7,2), (9,5).

Why 2 appears. Stopping after one round gives (5,2) and (7,2) only, which is option B of the original question. The cascade is transitive, so the second round is compulsory.

Edge case. If C had been declared on-delete set NULL, the answer would be 0: the two rows would have C set to null instead of being removed. The action decides the number.

NATGATE CSE 2017 Set 2 Q19

T1(P,Q) holds (2,2), (3,8), (7,3), (5,8), (6,9), (8,5), (9,8). T2(R,S) holds (2,2), (8,3), (3,2), (9,7), (5,7), (7,2). In T1, P is the primary key and Q is the foreign key referencing R in T2 with on-delete cascade and on-update cascade. In T2, R is the primary key and S is the foreign key referencing P in T1 with on-delete set NULL and on-update cascade.

In order to delete record ⟨3, 8⟩ from table T1, the number of additional records that need to be deleted from table T1 is ______.

Answer: 0

Deleting ⟨3, 8⟩ removes P = 3. The only T2 row referencing it is ⟨8, 3⟩, and the action on T2.S is SET NULL, so that row becomes ⟨8, NULL⟩. It is updated, not deleted.

Because no T2 row is deleted, the cascade from T1.Q to T2.R never fires, and no further T1 row is removed. The official key is 0.

Why 2 appears. A candidate who treats SET NULL as a delete deletes ⟨8, 3⟩ from T2, then cascades to the T1 rows with Q = 8 — ⟨3, 8⟩ and ⟨5, 8⟩ — and reports one additional row.

MSQOriginal practice

A column is declared q int CHECK (q > 5), with no other constraint. Which of the following statements are TRUE?

  1. A row with q = NULL is accepted
  2. A row with q = 5 is refused
  3. Adding CHECK (NOT (q > 5)) as well would make q = NULL refused
  4. A row with q = 9 is accepted

Answer: A, B and D

A CHECK is satisfied when the expression is TRUE or UNKNOWN. For q = NULL the comparison is UNKNOWN, so the row is accepted (A). For q = 5 the comparison is FALSE, so the row is refused (B). For q = 9 it is TRUE, so accepted (D).

Why C fails. NOT (q > 5) is also UNKNOWN when q is NULL, so the second constraint is satisfied as well. Both checks accept the null row, so the pair still does not exclude it. The page computes this: exactly one candidate survives both checks, and it is the null.

What it tests. That "satisfied" means "not FALSE", and that a contradiction in two-valued logic is not a contradiction over three values.

NATOriginal practice

A table already holds the rows a = 1 and a = NULL. Under the default null treatment, how many of the three candidate values NULL, 1, 2 are accepted by a UNIQUE constraint on a?

Answer: 2

NULL is accepted, because two nulls are not equal and so never collide. 1 is refused, because it equals the existing 1. 2 is accepted. That is 2 of 3.

Why 1 appears. A candidate who believes a unique column may hold only one null refuses the NULL candidate and counts 1.

Edge case. With UNIQUE NULLS NOT DISTINCT the null would collide with the existing null and the answer would be 1. The clause, not the data, changes the count.

MCQOriginal practice

A child table has a two-column foreign key (x, y) referencing a parent whose only row is (1, 1). A row is inserted with x = 1 and y = NULL. Which statement is correct?

  1. It is refused under both MATCH SIMPLE and MATCH FULL
  2. It is accepted under MATCH SIMPLE and refused under MATCH FULL
  3. It is accepted under both
  4. It is refused under MATCH SIMPLE and accepted under MATCH FULL

Answer: B

MATCH SIMPLE, the default, excuses the row as soon as any referencing column is null, so the reference is not checked at all. MATCH FULL allows only all-null or all-match, and this row is mixed, so it is refused.

Why D is the popular wrong answer. The names suggest that SIMPLE is the stricter of the two. The page's model checks the opposite: every pair accepted under FULL is also accepted under SIMPLE, and the counts are 2 against 6 out of 9.

Edge case. Declaring x and y NOT NULL refuses this row under either match type, which is usually the intent.

MSQOriginal practice

Relations R(a) and S(d) satisfy the foreign key S.d → R.a. Which of the following operations can introduce a violation of that constraint?

  1. Insert a tuple into R
  2. Insert a tuple into S
  3. Delete a tuple from R
  4. Delete a tuple from S

Answer: B and C

Inserting into the child can supply a value the parent does not have. Deleting from the parent can remove a value the child is using.

Why A and D cannot. Inserting into the parent only adds a key, so it can only make more references legal. Deleting from the child only removes a reference, so it can only make fewer references exist. The page confirms this by enumeration: over every legal instance on a two-value domain, parent-insert and child-delete introduce zero violations, while the other two do.

Edge case. Deleting from the child is safe for this constraint but may break a constraint on a table that references S — the safety is local to one foreign key.

One screen to revise from

The acceptance rule of each constraint, its behaviour on NULL, whether it can be deferred, and the one fact that decides a question about it.

The constraint table

constraint acceptance rule a NULL row deferrable
NOT NULLthe value is presentrefusedno
UNIQUEno two rows equal on the columnsaccepted; two nulls are not equalyes
PRIMARY KEYUNIQUE and NOT NULLrefusedyes
CHECKthe expression is not FALSEaccepted when UNKNOWNno
FOREIGN KEYnon-null child key exists in the parentaccepted under MATCH SIMPLEyes

The closure procedure, in four lines

  1. Collect the key values the statement removed.
  2. Find every child row referencing one of them.
  3. Apply the action: CASCADE adds keys and repeats; SET NULL and SET DEFAULT stop; NO ACTION and RESTRICT raise an error.
  4. Stop when a round adds nothing. Count the rows, not the rounds.

The four operations

Insert into parent: cannot orphan. Insert into child: can orphan. Delete from parent: can orphan. Delete from child: cannot orphan. Updates follow the same split — a child key set to a missing value, or a parent key changed to a new value, can orphan.

Numbers this page computed

  • Superkeys of the three-row relation: 5 of 7 non-empty subsets; candidate keys: 2.
  • Accepted of three candidates: NOT NULL 2, UNIQUE 2, PRIMARY KEY 1, CHECK (a > 5) 1.
  • Composite match counts out of 9: SIMPLE 6, FULL 2, PARTIAL 4.
  • GATE CSE 2005 closure: 3 additional tuples, in 3 rounds.
  • GATE CSE 2017 Set 2: 0 additional T1 rows, 1 T2 row updated to NULL.

The four sentences worth memorising

  • Satisfied means not FALSE, so UNKNOWN passes.
  • PRIMARY KEY is UNIQUE plus NOT NULL, and one per table.
  • A cascade fires on a deletion; SET NULL is an update and stops the chain.
  • Only child-insert and parent-delete can orphan a row.

What the research did not cover

No database engine was run in the build environment, so no output on this page is quoted from a live server; every semantic claim is either the SQL standard's (via the sources above) or PostgreSQL's documented behaviour, and each is labelled. No textbook edition was consulted, so no page or section number is quoted. The SQL standard itself was not read directly: the CHECK rule, the match types and the referential actions are taken from PostgreSQL's documentation of them, which is why the two places where the standard leaves a choice to the implementation are called out rather than glossed. No search was made for GATE 2027 sample papers, because none exists at the time of writing. Finally, the MATCH PARTIAL counts on this page model the standard's definition so that the three rules can be compared; they are not a claim about what PostgreSQL will do, since it does not implement that rule.
