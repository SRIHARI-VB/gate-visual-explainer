Topic and objective

TOPIC: Type checking and type systems — the semantic-analysis phase that decides whether every operation in a program is applied to values it can accept, and the type algebra that decision rests on.

LEARNING OBJECTIVE: Say where the checker sits and what it consumes and produces; build the type expression for a declaration; decide type equality two ways, structurally and by name, and say which one C uses and where; separate static from strong; read a typing rule and find the node where no rule fires; count which pairs are assignable under strict and under coercing rules; resolve an overloaded call; and explain why one mistake should produce one message and not four.

I read the topic as one question asked at every node — are these operands of a kind this operation accepts — plus the type algebra that makes the question answerable. The page computes every number it shows and reports how many of its own checks passed.

GATE relevance

Verified fact Class A, through the phrase the syllabus uses. The GATE CS syllabus names type checking as part of the analysis phase, and every standard compiler-design syllabus that follows it (NPTEL's Compiler Design course, the IIT and university course outlines) lists "type checking" as a week or a module of its own, next to syntax-directed translation and before runtime environments.

Verified fact The phase fact has been asked at least twice on CSE papers twenty years apart: GATE CSE 2018, Q8 ("type checking is done before parsing" is the false statement) and GATE CSE 2021 Set 1, Q36 (what one SDT for declarations can type-check).

Verified fact GATE CSE 2026 Set 1 carried an MSQ comparing two SDDs for declarations. Class A means a question is inside the boundary, not that one is guaranteed. No marks distribution is claimed for 2027.

Prerequisites

  • Lexical analysis, parsing and syntax-directed translation — attributes, S-attributed and L-attributed definitions, evaluation order. This lesson assumes all of it.
  • C fundamentals — declarations, integer and floating types, the assignment conversion rules.
  • Sets and relations — equivalence and partition, which is exactly what type equivalence is.

Approximate learning time: 50 to 70 minutes, including the practice set. That figure is an estimate, not a measurement.

The five ideas

  1. One question per node: are these operands acceptable to this operator?
  2. A type expression is a tree of constructors; the array length and the field names are part of it.
  3. Structural equivalence ignores the record tag; name equivalence is the tag. A typedef adds no type.
  4. Equality is not compatibility. Assignability is one-directional; coercion is the compiler inserting the widening.
  5. One mistake, one message: the error type matches everything so the walk can finish.

Intuition first: a plug that only fits one socket

Every operation in a program is a socket with a shape, and every value is a plug with a shape. Adding two integers is a socket for integers; adding an integer and a string is a plug that does not fit. Nothing about the characters x + b is malformed — a parser is perfectly happy with it. What is missing is a shape that matches.

The type checker is the part of the compiler that holds up each plug against its socket and says yes or no. To do that it needs two things: a written-down shape for every value, which is the type expression, and a rule for every socket, which is the type system.

Educational interpretation The socket is an analogy, not a definition. The definition is in the next card, and it is the one to quote.

Formal definition

Type checking is the activity of ensuring that the operands of an operator are of compatible types, where a compatible type is one that is either legal for the operator or allowed by the language to be implicitly converted to a legal type. That implicit conversion is a coercion.

A type system is a set of rules assigning a type to each expression and statement of the language. A rule has premises above a line and one judgment below it. The judgment is written $$e : T$$ and read "expression e has type T".

Verified fact The first paragraph is the standard wording, used in compiler-course material on type checking; the rule form is the one used throughout Aho, Lam, Sethi and Ullman, Compilers: Principles, Techniques and Tools, chapter 6.

Symbols, in words

  • e : T — "expression e has type T".
  • array(n, T) — an array of n elements, each of type T.
  • pointer(T) — a pointer to something of type T.
  • record((x × int) …) — a record whose field x has type int, and so on.
  • (T1 × T2) → T — a function from parameters T1 and T2 to result T.
  • type_error — the type a failing rule returns; it matches every type.
  • ⊑ — "widens to": int ⊑ float means an int may be used where a float is wanted.
  • typedef — a synonym declaration. It adds a spelling, not a type.

The two asymmetric relations are where marks are lost: a question about assignment is a compatibility question, and an equality test answers a different one.

The conditions each statement carries

Structural equivalence here compares records by field name and field type, in the product form the textbook uses. A language that compares records by field types alone has a different relation, and a question that assumes it must say so. Name equivalence here treats a typedef as a synonym, so it adds no type; a language where every declaration creates a fresh type would count differently. The overload rule needs an exactness test, not just applicability, or every two-candidate call looks resolvable. And "strongly typed" is defined differently by different authors — the guarantee reading is used here, and a question that supplies its own definition overrides it.

Worked example 1 — nine declarations, partitioned twice

Two synonyms of int (Meters, Seconds), three records (point, vec, pt2) and four pointer types (int *, Meters *, struct point *, struct vec *).

  1. Structure. The tag is not compared, so point and vec are one class, and so are the two pointers to them. The synonyms are one class because both are int, and the two int * spellings are one class. Five classes in total.
  2. Name. Every record now stands alone, and every pointer to a record stands alone with it. The synonyms still merge, because a typedef adds no type, and the two int * spellings still merge. Seven classes.
  3. The two counts. Thirty-six unordered pairs. Thirty-four agree, two differ: point / vec and pointp / vecp.
  4. Containment. Every name class sits inside a structural class, never the other way round. Name equivalence refines structural equivalence, and the page checks the containment on all nine.
  5. C. Two structs with the same members and different tags are different types, so C behaves like the name partition on records and like the structural one everywhere else.

Every number above is recomputed by the page: the classes by partition, the pair counts by enumeration, and the containment by testing each class against every structural class.

Worked example 2 — thirteen programs, two modes

A tiny language with int, float, bool, str, arrays, pointers and one function f : (int × float) → bool. The checker is run twice: once allowing widening (coercing) and once allowing only equality (strict).

Accepted both ways: x + 1, p[i], *r, f(1, 2.0). Rejected both ways: x + b (arithmetic on a bool), if x then 1 else 2 (condition not bool), p[y] (subscript is a float), *q (q is not a pointer), f(1) (arity), x = 2.5 (narrowing is not a coercion).

Accepted only when widening is allowed: if b then 1 else 2.0, f(1, 2), y = 2. The two modes therefore disagree on exactly three of the thirteen, and the page reports which three. x = 2.5 stays rejected in both, because float to int is a narrowing and needs a cast.

Worked example 3 — one mistake, four operators above it

Take ((x + z) * 2 - 3) / 4 with x : int and z : bool. Six nodes: the two leaves, and the four operators.

  1. x + z: int plus bool. The premise "both numeric" fails, so the node gets type_error. That is the one real mistake.
  2. (…)*2: the left child is type_error. Under the poison rule type_error matches anything, so no new message; the node passes the error up.
  3. … - 3 and … / 4: the same, so still one message.
  4. Switch the poison off and type_error matches nothing. Now the multiplication, the subtraction and the division each fail in turn, and the compiler prints four messages that all trace back to one mistake.

Computed on the page: 1 message with the poison, 4 without, a difference of exactly 3. This is why type_error is a type and not an exception.

Worked example 4 — three calls against two overloads

Overloads: f(int, float) and f(float, int). A call is applicable when every argument widens to its parameter; among applicable candidates an exact match wins.

  • f(1, 2.0) — the first overload matches exactly. One applicable, one exact: chosen.
  • f(1, 2) — the first needs a widening on argument 2, the second a widening on argument 1. Two applicable, none exact: ambiguous.
  • f(1, b) with b : bool — bool widens to nothing, so neither candidate is applicable: an error, not an ambiguity.

The distinction matters in a question: "no match" and "ambiguous" are different diagnostics, and a language may not break an ambiguity by preferring the first declaration.

Where the rules stop, and what happens there

Each card is a boundary case with the condition it violates or the witness that shows the boundary. Numbers are computed on the Animation tab.

Boundary 1 — accepted, and still wrong at run time

p[5] where p : array(4, int). The indexing rule asks two things: the base is an array, the subscript is an int. Both hold, so the checker accepts and gives the expression type int. The fifth element of a four-element array does not exist.

This is incompleteness, not a bug: the subscript is a value, and a value is not known at compile time. What a static checker guarantees is one-directional — it does not accept programs that always fail, but it does accept some that fail on some inputs.

Boundary 2 — rejected, and would have run

if true then x = 1 else x = "s" with x : int. The branches are int and str, incompatible, so the if-rule fails and the program is rejected. But the condition is the literal true: the else branch is unreachable, so no type error could ever occur.

This is the price of deciding before execution. A checker that looked at reachability would accept more programs and cost more; a checker that does not is conservative. Both facts are computed on the page rather than asserted.

Boundary 3 — a cyclic type

struct node { int info; struct node *next; }. Its type graph has a cycle, so a naive structural comparison never terminates. The standard repair marks each pair already under comparison and treats a repeated pair as provisionally equal.

Two independently built node types are structurally equal and name-equal; a third with the tag other is name-unequal to them. The page runs all three comparisons and checks that the walk ends.

Boundary 4 — the array length

array(10, int) and array(20, int) are different types under both schemes, because the length is one of the two components the comparison must check.

A question that treats them as the same type is treating the length as a run-time property. It is not one in this type system, which is why passing a ten-element array to a parameter declared as twenty elements is a type error and not a bounds error.

Boundary 5 — narrowing is not a coercion

On the widening chain char, short, int, long, float, double, a conversion to the right is a narrowing. x = 2.5 with x : int is rejected in both modes the page runs, because allowing it silently would let a checker accept a program that loses information.

A cast, x = (int) 2.5, is accepted — the checker stops asking, which is exactly why a cast is the hole that makes a statically checked language not strongly typed.

Boundary 6 — bool is not an integer here

In this lesson's toy language bool is its own type: it coerces to nothing and no arithmetic accepts it. That is a design decision, and it is the one most questions assume.

C differs: it has no boolean arithmetic of its own, and its _Bool promotes to int in most expressions. Read the language a question names before answering. Nothing on this page claims C's promotion rules; they belong to the C lessons.

Boundary 7 — what a type checker cannot decide

It cannot decide an index against a length computed at run time, a division by a value that may be zero, a downcast that is safe on this input, or whether an unreachable branch is unreachable in general. Those need either a run-time check or a proof, and a type checker has neither.

This is the honest limit to state in an answer: the type system is a decidable approximation of the property "no operation ever meets a wrong type", and every decidable approximation of a non-trivial property is either sound and incomplete or complete and unsound.

Five beliefs that survive a first reading

Each card states the wrong belief, why it tempts, the smallest witness against it, and the rule to use instead.

M1 — "type checking happens before parsing"

Why it tempts: the type checker is described early in many courses, and declarations appear at the top of a file, so it feels like a first pass.

Witness: the checker's input is a syntax tree. There is no tree before the parser runs.

Correct rule: lexical, then syntax, then semantic analysis, of which type checking is part. Verified fact GATE CSE 2018, Q8 marks the "before parsing" statement as the false one.

M2 — "static and strong are the same word"

Why it tempts: most languages people meet first are both.

Witness: C is statically checked and not strongly typed — a union or an unchecked cast lets a value of one type be read as another. Python is dynamically checked and catches the same misuse.

Correct rule: "when is it checked" and "is every error caught" are two questions with four answers.

M3 — "a typedef creates a new type"

Why it tempts: the declaration looks like a definition, and it does introduce a name.

Witness: on this page Meters and Seconds are one class under both schemes, and int * and Meters * are one class too.

Correct rule: a synonym adds a spelling. A record, union or class declaration is what adds a type.

M4 — "structural equivalence ignores field names"

Why it tempts: the sentence "same structure" is usually stated without saying what counts as structure.

Witness: record((x × int)) and record((u × int)) are not structurally equal here, because the product carries the label.

Correct rule: state which form you are using. The tag is skipped; the field name is not, in the standard product form.

M5 — "a type error is reported at every node it touches"

Why it tempts: each operator really does fail if you test it in isolation.

Witness: the same six-node tree gives 4 messages without the poison and 1 with it.

Correct rule: the lowest failing node is the mistake; everything above it is a consequence. The error type matches everything so the walk can continue and find the other independent mistakes.

M6 — "ambiguous and no-match overloads are the same failure"

Why it tempts: both produce a compile error.

Witness: f(1, 2) has two applicable candidates and is ambiguous; f(1, b) has none and is a no-match.

Correct rule: applicability first, exactness second. An ambiguity may not be broken by declaration order.

Six shapes this topic takes on a paper

Each card names the category, the reasoning it demands, and the wrong approach that produces a plausible option. Historical frequency is an observation about past papers, not a prediction for 2027.

P1 — the phase question

Shape: which phase reports this error, or which statement about the phases is false.

Reasoning: map the error to the information it needs. A malformed token is lexical; a bad derivation is syntactic; a name that is not declared, or a type that does not fit, is semantic.

Wrong approach: deciding by where the error text appears in the source. Declarations at the top of a file have nothing to do with the phase order.

P2 — what an SDD or SDT can check

Shape: a printed definition, and a question about what it can or cannot type-check.

Reasoning: trace one attribute assignment at a time and ask whether the information needed is available at that point. If an identifier's type is set to a constant regardless of its declaration, the scheme cannot distinguish two types.

Wrong approach: judging by the grammar. The grammar is identical for a scheme that checks and one that does not; the difference is in the semantic rules.

P3 — S-attributed against L-attributed, for a declaration

Shape: which of the two definitions is S-attributed, or which attributes each uses.

Reasoning: a synthesized attribute is computed from children only; an inherited one takes a value from the parent or a left sibling. A definition that passes a type down a list uses an inherited attribute and is therefore not S-attributed.

Wrong approach: assuming a left-recursive grammar is S-attributed. Left recursion makes an S-attributed definition easy; it does not make it automatic.

P4 — type equivalence and what C does

Shape: are these two declarations the same type, under structural or name equivalence.

Reasoning: write both type expressions, compare constructors, sizes and components, then ask whether the record tags differ. In C, records are nominal and everything else is structural.

Wrong approach: answering by the field lists alone, which merges two different structs.

P5 — assignability and coercion counts

Shape: how many of the assignments in a list are legal, or which one needs a cast.

Reasoning: decide the direction. Widening is silent, narrowing needs a cast, and a non-numeric type converts to nothing. Count with the rule written down, not by intuition about "compatible".

Wrong approach: treating compatible as symmetric, which makes float to int as legal as int to float.

P6 — the count of messages, or the number of errors

Shape: how many type errors a compiler reports for a given program.

Reasoning: count the lowest failing nodes, then check whether the failures are independent. Two independent mistakes in different subtrees give two messages; one mistake under four operators gives one.

Wrong approach: counting every node whose type ends up as error, which counts consequences as mistakes.

The four-step procedure, in the order to use it

First, build the type expression for every declaration and write it down. Second, walk the tree bottom-up applying one rule per node, and mark the lowest failing nodes. Third, check the statement rules separately — scope, arity, parameter and result types. Fourth, keep equality and compatibility apart, and state which one the question is asking. If a question is about C specifically, apply C's rule: structural except for struct and union.

The page's thirteen programs and its two partitions are the worked instances of these four steps; nothing in the procedure needs the animation.

Practice set

Nine questions: two reproduce verified past-paper items, seven are original practice written for this lesson. Answers are hidden until you reveal them one at a time; the mock-test switch hides them all and reveals them together.

Q1 PYQ — GATE CSE 2018, Q8 MCQ

Which one of the following statements is FALSE?

(A) Context-free grammar can be used to specify both lexical and syntax rules.   (B) Type checking is done before parsing.   (C) High-level language programs can be translated to different intermediate representations.   (D) Arguments to a function can be passed using the program stack.

Answer: B

Type checking is part of semantic analysis, and semantic analysis consumes the parse tree, so it cannot precede parsing. (A) is true because every regular language is context-free, so one CFG can describe tokens and phrases. (C) and (D) are standard.

The trap is that (B) is not merely imprecise: it is the intended false statement, and the official key confirms it. A learner who thinks "declarations are checked early, so maybe before parsing" picks (A) or (C) instead.

Q2 PYQ — GATE CSE 2021 Set 1, Q36 MCQ

A grammar admits a series of declarations followed by expressions, with semantic actions: D → int ID {record ID.lexeme as int}, D → bool ID {record as bool}, E → E1 + E2 {check E1.type = E2.type = int; E.type := int}, E → !E1 {check E1.type = bool; E.type := bool}, E → ID {set E.type := int}. Which choice is correct?

(A) The actions type-check any syntactically correct program. (B) They type-check syntactically correct integer declarations and integer expressions. (C) They type-check syntactically correct boolean declarations and boolean expressions. (D) The actions lead to an infinite loop.

Answer: B

The rule E → ID assigns type int to every identifier expression, whatever was declared. So a boolean variable used as an operand of ! looks like an int and the check E1.type = bool fails even for a correct program; and b + 1 with b boolean is not caught either. The integer half works, because there the constant int is the right answer.

A fails on the boolean cases. C fails because the identifier rule never yields bool, so no boolean expression can be validated. D is unrelated: the actions terminate.

The general lesson: an SDT can only check what its semantic rules carry. If the identifier rule discards the declared type, no later rule can recover it.

Q3 Original practice MCQ

With struct point {int x, y;} and struct vec {int x, y;}, which statement is true under structural equivalence with records written as products of field name and field type?

(A) the two types are equivalent, and the tags are irrelevant   (B) the two types are not equivalent, because the tags differ   (C) they are equivalent only if the fields are renamed   (D) they are equivalent only in C

Answer: A

Both type expressions are record((x × int) × (y × int)). The record name is not part of that expression, so the two are structurally equal — the page computes this and places them in one class.

B describes name equivalence, which is the other scheme. C inverts the rule: renaming a field breaks structural equality here. D is false: C is the language that treats records nominally, so C would say these are different.

Watch the wording: "structurally equivalent" and "the same type in C" have different answers for this pair.

Q4 Original practice MCQ

Which one of these is a coercion and not a cast?

(A) int i = (int) 3.7;   (B) float f = 3;   (C) int *p = (int *) q;   (D) char c = (char) 300;

Answer: B

int widens to float, so the compiler inserts the conversion itself and the source says nothing. That is a coercion.

A and D narrow, and both are written by the programmer, so both are casts. C reinterprets a pointer and is also written out.

The distinction is not "which one is safe" but "who wrote the conversion". A cast is the programmer taking responsibility, which is why the type checker stops asking after it.

Q5 Original practice MSQ

A language has types int, float, bool and the widening rule int ⊑ float only. Which statements are true?

(A) exactly 4 of the 9 ordered pairs over the three types are assignable   (B) float is assignable to int   (C) bool is assignable to int   (D) the assignable relation is not symmetric

Answer: A and D

The legal pairs are int→int, int→float, float→float and bool→bool: four. The page enumerates all nine and reports 4, against 3 under strict equality only.

B is a narrowing and needs a cast. C is false because bool is not numeric here, so it widens to nothing.

D is true because int→float is legal and float→int is not: assignability is one-directional, and that is the single most useful fact about it.

Q6 Original practice NAT

A checker reports one message per failing node and uses a type_error that matches every type. The expression ((a + b) * 2 - 3) / 4 has a : int and b : bool. How many messages does it report?

Answer: 1

Only a + b fails. The three operators above it receive a type_error operand, which matches anything, so they produce no new message.

Without the poison the same tree reports 4, and the page computes both numbers on the Animation tab. If a question says the checker reports every node whose type is error, answer 4; read which rule the question states.

Q7 Original practice MCQ

A program is rejected by the type checker although it would have executed without a type error. Which term describes this?

(A) the checker is unsound   (B) the checker is incomplete   (C) the language is not strongly typed   (D) the program is not well typed

Answer: B

Rejecting a program that cannot go wrong is incompleteness: the checker fails to accept something it could have. The witness on this page is the unreachable else branch with an incompatible type.

A is the opposite failure: accepting a program that does go wrong, which is the p[5] witness. C is about guarantees across the language, not about one program. D is circular: "not well typed" means rejected by the rules, which is what we are explaining.

Keeping these two words in the right order is worth a mark on its own: sound means never accepts a bad program; complete means never rejects a good one.

Q8 Original practice MCQ

Overloads f(int, float) and f(float, int) exist. What does the call f(1, 2) do under the rule "applicable first, then exact"?

(A) calls the first overload   (B) calls the second overload   (C) is ambiguous and rejected   (D) is rejected because no overload applies

Answer: C

Both candidates apply: the first needs int→float on argument 2, the second needs int→float on argument 1. Neither is an exact match, so no rule chooses between them.

A and B would require breaking the tie by declaration order, which is not a rule. D confuses ambiguity with no-match; the no-match case is f(1, b) with a boolean argument.

The page resolves all three calls and prints how many candidates were applicable for each.

Q9 Original practice NAT

Nine declarations: two synonyms of int, three distinct records, and four pointer types — int *, Meters *, struct point *, struct vec *, where point and vec have identical fields. How many equivalence classes does structural equivalence give over the nine?

Answer: 5

{Meters, Seconds}, {point, vec}, {pt2}, {int *, Meters *}, {struct point *, struct vec *}. The tag is not compared, so each record merges with its lookalike, and each pointer follows its pointee.

Name equivalence would give 7 on the same nine, because the records and their pointers stop merging. If the question says "name", the answer changes; that is the whole difference between the two schemes.

One screen

The phase fact, the two equivalences, the three relations, the poison rule and the two failures of a static checker. Everything else is an instance of one of these.

Facts to keep

  • Type checking is semantic analysis: after parsing, before intermediate code.
  • A type expression is a tree: base type, or array, pointer, record, function.
  • Structural: tag ignored, field name compared. Name: tag compared.
  • A typedef adds a spelling, not a type.
  • C: structural, except struct and union, where the tag is the identity.
  • Static asks when; strong asks whether every error is caught.
  • Widening may be coerced; narrowing needs a cast.
  • type_error matches everything, so one mistake gives one message.

Numbers this page computed

  • sizes: array(10,int) 2, pointer(char) 2, a two-field record 3, a two-parameter function 4
  • nine declarations: 5 structural classes, 7 name classes
  • 36 unordered pairs: 34 agree, 2 differ
  • assignable: 3 of 9 strictly, 4 of 9 with widening
  • thirteen programs: 3 verdicts change between strict and coercing
  • one mistake: 1 message with the poison, 4 without
  • p[5] on a four-element array: accepted, out of bounds

Traps

  • "Before parsing" is the false statement, not a near miss.
  • Compatible is not symmetric.
  • Counting declarations as types over-counts a typedef.
  • Renaming a field breaks structural equality.
  • Ambiguous is not the same as no-match.
  • An accepted program can still fail; a rejected one can still be fine.

What the answer must state

  • which equivalence scheme you used
  • which relation the question asks: identical, assignable or coercible
  • whether the question's language is C or the toy language of this page
  • which definition of "strongly typed" you are applying

Where this connects

Backwards, to lexical analysis, parsing and syntax-directed translation: the checker is an SDD, and the attribute machinery is that lesson's. Sideways, to C fundamentals, which owns C's actual conversion rules, and to runtime environments, which consume the types to size each slot in an activation record. Forwards, to code generation, where the type decides which machine operation is emitted and how wide it is. The relations themselves are the relations of discrete mathematics: type equivalence is an equivalence relation, and its classes are a partition.

University of Western Ontario CS447, type equivalence — the two schemes stated as trees, the recursive-type problem and the marking repair, and the statement that C uses structural equivalence except for records, where it uses name equivalence.

Compilers-course notes on type checking — the definition used verbatim in the Build-up tab: type checking is ensuring the operands of an operator are of compatible types, and a coercion is the implicit conversion that makes one compatible.

Community material

GATE question archives — used to locate the 2018, 2021 and 2026 items and to read the option text. Where two archives disagree on a question number, the lesson says so rather than choosing one.

Community observation The "static equals strong" conflation and the "typedef creates a type" miscount are both reported repeatedly in discussion of this topic. That is an observation about what learners ask, not a measured claim.

What the page computes for itself

Nothing on the canvas is copied. The page implements type expressions and their sizes, structural equivalence with a cycle repair, name equivalence, the two partitions and their pair count, the widening relation, assignability under two rules, overload resolution, and a syntax-directed checker over thirteen programs in two modes. It then re-verifies each computed value against its definition: 40 checks, all of which must pass before the lesson is published.

What could not be confirmed

The 1998 item ("type checking is normally done during ...") is quoted from a question archive; the 1998 paper itself was not opened for this lesson, so treat its exact wording as reported rather than transcribed.

The 2026 Set 1 declaration question appears under two different question numbers in two archives. Only the year and the set are asserted.

No claim is made about how many marks this topic will carry in GATE CSE 2027, and no historical weightage is asserted. The toy language of this lesson is not C: its bool is not numeric, its widening chain is declared rather than inherited, and C's actual integer promotions belong to the C lessons.
