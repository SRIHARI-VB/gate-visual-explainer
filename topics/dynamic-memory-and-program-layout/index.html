Topic and objective

TOPIC: Dynamic memory in C — malloc, calloc, realloc and free — together with the layout of a running program that gives those bytes a home. This is part of Programming in C, Section 4 of GATE 2027.

LEARNING OBJECTIVE: Say where an object lives and how long it lives, for every object in a C program. Read a heap allocation as a chunk with a header rather than as a bare run of bytes, and compute what an allocator actually gives you for a given request. State exactly what malloc, calloc and realloc put in the bytes they return, and what free does and does not do. Trace the three outcomes of realloc and name the one rule that survives all three. Count the copies made by a doubling growth policy and prove the total is below 2n. Recognise the four classic heap faults, and separate what the C standard guarantees from what one implementation happens to do.

I read this topic as one question asked in four costumes: who owns these bytes, how long do they live, what is in them, and what happens when the owner lets go. Almost every exam question here is one of those four, and almost every lost mark comes from treating a pointer as if it were the block.

  • sizeof and size_t. sizeof yields an unsigned size_t and does not evaluate its operand, which is why sizeof *p is safe even when p is uninitialised. Also in Pointers in C.
  • Integer widths and unsigned arithmetic. Why a product can wrap, and why unsigned wraps are defined while signed overflow is not. Built in C fundamentals.
  • Scope and storage duration. The difference between a name being visible and an object existing. Built in Functions, scope and the preprocessor.
  • Structs and their size. A list node is a struct, and its size decides the stride of an array of nodes. Built in Structures, unions and enums.

The five ideas to leave with

  1. Storage duration is a lifetime, not a place. The place is an implementation's way of implementing the lifetime.
  2. An allocation gives you at least the bytes you asked for, uninitialised and suitably aligned. Everything else about it is implementation detail.
  3. The pointer is yours; the block is borrowed. Copying a pointer copies nothing, and freeing one copy tells the other copies nothing.
  4. realloc may move the block, and it invalidates the pointer you passed whatever it does. Only its return value is safe to use.
  5. Amortised is not per-operation. Doubling makes a sequence of n appends linear in total, while a single append can still cost O(n).

Intuition: a warehouse with a counter, and a rule about who owns what

Picture a warehouse. Most of the shelves are already booked: some hold the program's own instructions, some hold the globals that were given a value, some hold the globals that were not and are therefore all zero, and one tall rack at the back is reserved for whatever a function needs while it is running. That rack is the stack, and it is booked and released automatically as functions are entered and left.

Then there is the floor in the middle: the heap. Nobody books it in advance. You walk up to the counter, say "eight bytes, please", and the clerk hands you a numbered slip. The slip is a pointer. Three things are worth noticing. The clerk never gives you exactly eight bytes — there is a label on every crate, and the crate is rounded up so the next one starts on a tidy boundary. The clerk does not clean the crate, so whatever the last tenant left is still inside. And the slip is yours; the crate is the warehouse's. Hand the slip back and the crate returns to the pool, but your slip still has the old number written on it, which is exactly how a dangling pointer is born.

Level 1 — Intuition, in one sentence each

  • Storage duration. How long an object exists, from one of four kinds: automatic, static, allocated, thread.
  • Segment. The region of the process image where a duration is implemented.
  • malloc. Ask for n bytes; get at least n, uninitialised, or NULL.
  • calloc. Ask for num objects of size bytes; get them zeroed.
  • realloc. Ask for a different size for a block you own; get a new pointer, or NULL.
  • free. Give a block back; get nothing, and change nothing you can see.
  • Chunk. The allocator's real unit: a header plus the bytes you asked for, rounded up.
  • Leak. A block that is still allocated and no longer reachable.

Level 2 — Formal definitions

Verified fact C17 names four storage durations. Automatic: storage is allocated when the block is entered and deallocated when it is left. Static: the storage lasts the entire execution, and the value is initialised once, before main. Allocated: allocated and deallocated on request by the allocation functions. Thread: the lifetime of one thread.

Verified fact void *malloc(size_t size) allocates size bytes of uninitialised storage and returns a pointer suitably aligned for any object type with fundamental alignment, or a null pointer on failure.

Verified fact void *calloc(size_t num, size_t size) allocates num × size bytes and initialises every byte to zero. void *realloc(void *ptr, size_t new_size) reallocates a block, keeping its contents up to the lesser of the old and new sizes. void free(void *ptr) deallocates, and does nothing if ptr is null.

Level 3 — The structure the animation computes

Two computations carry this whole topic, and both are done in code on the page before anything is drawn.

Chunk arithmetic (glibc, x86-64). Every allocation is a chunk with one 8-byte size word in front of the bytes you get. Chunks are multiples of 16, and never smaller than 32. So:

request2size(req) = max(32, (req + 8 + 15) & ~15) and usable(req) = request2size(req) − 8.

The page evaluates that for fourteen requests and checks four properties of the result: every chunk is a multiple of 16, no chunk is below 32, usable is never less than the request, and the chunk never shrinks as the request grows. Ask for 1 byte and you get 32 with 24 usable; ask for 25 and you get 48 with 40 usable; ask for 1000 and you get 1008 with exactly 1000 usable.

Growth arithmetic. Appending to a dynamic array that doubles when full copies the old capacity at each growth: 0, 1, 2, 4, 8, and so on. The page runs that simulation for every n from 1 to 1024 and checks that the total equals 2^ceil(log2 n) − 1 in every case, and that it is always below 2n.

Level 4 — Worked example: sixteen appends

Start with capacity 0. Push items one at a time; when the array is full, double the capacity and copy everything across.

Growths happen before items 1, 2, 3, 5, 9 and 17 — that is, when the index equals the capacity. The copies made are the old capacities: 0, then 1, then 2, then 4, then 8.

Total for 16 items: 15 copies. The final capacity is 16, and 1 + 2 + 4 + 8 = 15 = 16 − 1.

For 17 items: 31 copies, because the seventeenth push triggers one more doubling from 16 and copies all 16.

Growing by exactly one instead would copy 0 + 1 + 2 + … + 15 = 120 elements for the same 16 items. That is the difference between quadratic and linear, and it is a factor of eight already at n = 16.

Level 4 — Worked example: the three realloc outcomes

Take p = malloc(8 * sizeof(int)), so 32 bytes of data, then realloc(p, 16 * sizeof(int)).

Grew in place. The address stays 0x1000, nothing is copied, and the 32 new bytes are undefined. The standard still invalidates p: use the returned pointer.

Moved. A new block at 0x2000, a copy of min(32, 64) = 32 bytes, and the old block freed. p now dangles.

Failed. The return value is NULL, the old block is untouched and still yours, and p = realloc(p, n) has just thrown away the only handle to it. Write t = realloc(p, n); if (t) p = t;.

Level 5 — Boundaries: where the standard stops

The C standard fixes the promises, not the machinery. It promises at least n bytes, suitably aligned, uninitialised, and NULL on failure. It says nothing about where the bytes are, how much padding surrounds them, what free leaves in them, or which of two equal-sized holes is reused. Everything in this lesson that is not one of those promises is labelled as one implementation's behaviour, and the animation prints the label next to the number.

This is why a question that asks "which segment" or "how many bytes does malloc(1) really give you" is asking about an implementation, while a question that asks "what may you read after malloc" is asking about the language. Answer the second kind from the standard and the first kind only after the platform has been stated.

Level 6 — The counterexample that matters

Here is a program that prints a plausible number and is wrong.

int *p = malloc(sizeof(p));
for (int i = 0; i < 10; i++) p[i] = i;
printf("%d\n", p[9]);

sizeof(p) is the size of a pointer, 8, and ten ints need 40. The loop writes 32 bytes past the end of the block.

What it breaks: the belief that a program which prints the right answer is correct. Writing past an allocation is undefined behaviour, and undefined behaviour is allowed to look exactly like success — until the heap metadata it overwrote is used by the next malloc or free.

Level 6 — Closely confused: a leak and a dangling pointer

Leak: p = malloc(5); p = NULL; — the block still exists and nothing can reach it. You have lost the block.

Dangling: q = p; free(p); q->value = 5; — you still hold an address, and the block behind it is gone. You have lost the block, not the address.

Why they get merged: both start with a valid pointer and end with a bug. The difference is which one is left over. In the first, the address is gone and the memory is not; in the second, the address is present and the memory is not. GATE CSE 2000 Q1.12 is built entirely on that distinction.

Level 7 — How it is examined

Four shapes recur. A matching question asks you to name the fault in each line. A what is wrong with these functions question asks you to separate a dead stack address, an uninitialised pointer and a live heap block. A linked-list question gives a malloc loop and asks what the traversal does when the last next was never set. A count question asks how many bytes or how many copies, which is the doubling arithmetic or the chunk arithmetic.

None of these needs the bin structure or the page tables. All of them need the four questions in the overview answered precisely.

GATE CSE 2000 Q1.12 — match the fault

X: m = malloc(5); m = NULL;   Y: free(n); n->value = 5;   Z: char *p; *p = 'a';
1: using dangling pointers   2: using uninitialised pointers   3: lost memory

X is lost memory. The block exists and no pointer names it. Nothing can free it, so it is lost for the life of the process.

Y is dangling. free(n) ends the block and leaves n holding the old address, so n->value writes through a pointer to nothing.

Z is uninitialised. p was never given an address, so *p = 'a' writes to whatever the indeterminate bytes of p happen to denote.

Answer: X–3, Y–1, Z–2 (option D). The tempting wrong answer puts X with dangling, which is exactly the confusion this lesson separates.

GATE CSE 2001 Q2.18 — three functions

P1 returns &x for a local x. P2 writes *px = 10 before px is given an address. P3 calls malloc, writes through it, and returns it.

P1 fails on every run. The stack frame dies at return, so the address it hands back is dead the moment it is handed back.

P2 fails on every run. The first statement dereferences an indeterminate pointer, which is undefined behaviour before any question of lifetime arises.

P3 is fine. The block has allocated duration: it survives the return, and its owner is the caller, who must free it.

Answer: only P1 and P2 (option C). The word "likely" is doing the work: P3 is only wrong if malloc returns NULL, which is rare, while P1 and P2 are wrong always.

GATE CSE 2021 Set 2 Q35 — the list that walks off its end

The program allocates a head node with value = 0, then in a loop allocates three more nodes and links them, but never sets the next field of the last one. The printing loop then does head = head->next; printf(... head->value).

The list is four nodes long. boxE->next = boxN links each new node in, so the structure is 0 → 1 → 2 → 3, and the last node's next holds whatever malloc left there.

The traversal reads past the end. After printing node 3, head = head->next loads the uninitialised value and the next head->value dereferences it.

Answer: it dereferences an uninitialised pointer that may result in a run-time error (option D). Note the wording: may. The garbage value might by luck be a readable address, so the standard does not promise a crash — it promises nothing at all.

Three computations, done in full

These are the arithmetic shapes a count question takes. Every figure below is produced by the same functions the animation uses.

Example 1 — how many bytes does the allocator really give?

On glibc x86-64, with request2size(req) = max(32, (req + 23) & ~15):

malloc(1) → chunk 32, usable 24.
malloc(16) → chunk 32, usable 24.
malloc(24) → chunk 32, usable 24.
malloc(25) → chunk 48, usable 40.
malloc(40) → chunk 48, usable 40.
malloc(41) → chunk 64, usable 56.

So a hundred allocations of 24 bytes consume 3200 bytes, not 2400, and every one of them is 16-aligned. The page checks that usable ≥ request for all fourteen rows it computes, which is the property that makes the formula safe to use.

Example 2 — copies under a doubling policy

Capacity starts at 0 and doubles when full.

n = 1 → 0 copies, 1 reallocation
n = 4 → 3 copies
n = 9 → 15 copies
n = 16 → 15 copies
n = 17 → 31 copies
n = 100 → 127 copies
n = 1024 → 1023 copies

The pattern is 2^ceil(log2 n) − 1: at 1024 the total is 1023, which is n − 1, and the ratio copies/n falls towards 1 as n grows. Growth by one would need 1024 × 1023 / 2 = 523,776 copies for the same result.

Example 3 — 96 free bytes and a request that still fails

Six chunks of 32 bytes occupy 192 contiguous bytes. Free the second, fourth and sixth: three holes of 32, and 96 bytes free in total. Now ask for 40 bytes.

request2size(40) = 48, so the allocator needs a 48-byte chunk. Total free 96 ≥ 48, so by the total it should fit. Largest hole 32 < 48, so in one piece it does not.

The allocator takes fresh memory from the top of the heap and 96 bytes sit unused. This is external fragmentation, and the lesson is that an allocation consults the largest hole, never the sum of the holes. C cannot fix it by compaction, because it hands out real addresses that the program is allowed to keep.

Boundaries, and what each one breaks

Each card names a condition the rules above assume, then shows the smallest case where the condition fails and what the answer becomes. Several of these are questions in their own right, because the edge case is the exam item.

malloc(0) is not an error and not a guarantee

If the size is zero the behaviour is implementation-defined: a null pointer may come back, or a non-null pointer that must not be dereferenced and must still be passed to free.

What it breaks: if (!p) error(); as a test for "zero bytes requested". A zero-size request that returns a pointer is not a failure, and a zero-size request that returns NULL is not a failure either. Neither tells you anything about the machine's memory.

malloc can fail, and the check is not optional

On failure it returns a null pointer. A program that writes through the result without testing it is correct only as long as the allocation succeeds.

What it breaks: every one-liner of the form p = malloc(n); p[0] = 0;. On a machine where n is large or the address space is exhausted, the second statement dereferences NULL. On Linux this usually terminates the process; on other systems it may not.

realloc(p, 0) is implementation-defined

Before C23 the behaviour of a zero new size was implementation-defined — a null pointer may be returned, in which case the old block may or may not have been freed — and C23 made it undefined.

What it breaks: using realloc(p, 0) as "free and null out". Use free(p); p = NULL;, which has one meaning on every implementation and every version of the standard.

free(NULL) is defined; everything else is not

free(NULL) does nothing at all. But free of a pointer that was not returned by an allocation function, of a pointer into the middle of a block, or of a block already freed, is undefined behaviour.

What it breaks: free(p + 1) as a way to release "from here on", and free on the address of a local variable or of a static array. The allocator needs the exact value it returned, because that is where its header sits.

realloc invalidates the old pointer even when nothing moved

The standard says the original pointer is invalidated and any access to it is undefined behaviour, even if the reallocation was in place.

What it breaks: keeping p and using it after q = realloc(p, n) because "the address looked the same". The address is not the contract; the returned pointer is.

Static objects are zeroed; automatic and allocated ones are not

A file-scope int z; and a block-scope static int s; are both zero-initialised before main, once. A block-scope int x; and a fresh malloc block are indeterminate.

What it breaks: generalising from "globals start at zero" to "memory starts at zero". The zeroing is a property of static storage duration, not of memory. It is also why a static local is the cheapest place to put a flag that must survive between calls.

The multiplication can wrap before malloc is even called

On a 32-bit size_t, n = 2^30 and sizeof(int) = 4 give a product of exactly 2^32, which is 0 modulo 2^32. malloc receives 0.

What it breaks: the belief that malloc(n * sizeof *p) is the safe idiom. It is the safe spelling, not a safe computation. Test n > SIZE_MAX / sizeof *p first — a division, which cannot overflow — or use calloc, which is required to return NULL when the product cannot be represented.

A string needs one more byte than its length

strlen("hello") is 5. The array holding it needs 6, because the terminator is a byte too, and strcpy writes all six.

What it breaks: malloc(strlen(s)), which is one byte short on every input. The idiom is malloc(strlen(s) + 1), and the + 1 is not defensive style — it is the terminator.

Seven beliefs that produce the wrong option

Each card states the wrong belief, why it is tempting, the smallest case that refutes it, and the rule that replaces it. The refutations are computed on this page, not asserted.

1. "malloc(n) gives me n bytes"

Why it tempts: it is how every textbook introduces the function, and it is true of the guarantee.

Minimal counterexample: glibc gives 24 usable bytes for malloc(1) and a 32-byte chunk for malloc(24). The number you asked for and the number you got are different numbers.

The rule: at least n bytes are yours by the standard; the allocator rounds up, and the rounding is implementation detail. Write code that needs only n.

2. "malloc zeroes the memory"

Why it tempts: a fresh block from the operating system often is zero, because the kernel zeroes new pages, so the first few allocations look clean.

Minimal counterexample: allocate, write 1..8, free, allocate the same size again. The second block frequently still holds 1..8.

The rule: malloc leaves storage uninitialised; calloc zeroes every byte. If you need zeros, ask for them.

3. "free sets the pointer to NULL"

Why it tempts: it would be a lovely design, and some languages do exactly that.

Minimal counterexample: free(p); printf("%p", (void*)p); prints the old address. free receives a copy of the value and cannot change your variable.

The rule: free(p); p = NULL; is a discipline you write. It protects p and does nothing for any other pointer to the same block.

4. "realloc returns the same pointer, so I can keep using p"

Why it tempts: growing in place is the common case for small growth, and the address really does come back unchanged.

Minimal counterexample: a block with a live neighbour cannot grow, so realloc moves it. Now p is dangling and q is the block.

The rule: the standard invalidates the old pointer in every outcome. Only the returned value may be used, and it must be tested for NULL.

5. "A leak and a dangling pointer are the same bug"

Why it tempts: both end with a pointer that is no longer useful, and both appear in the same 2000 question.

Minimal counterexample: p = NULL after malloc loses the block and keeps no address; free(p) and then *q keeps an address and loses the block.

The rule: a leak loses the handle; a dangling pointer loses the object. Name which one is missing before you name the fault.

6. "Doubling means every append is O(1)"

Why it tempts: the word amortised gets dropped, and the conclusion survives without it.

Minimal counterexample: the push that takes the count from 1024 to 1025 copies 1024 elements. That single operation is linear.

The rule: n appends cost O(n) in total, so O(1) on average; one append can cost O(n). A question about the worst case of one operation has a different answer from a question about the sequence.

7. "The heap is one contiguous block after the stack"

Why it tempts: the textbook picture draws five tidy bands, and the picture is a reasonable first approximation.

Minimal counterexample: the five bands are a linker and loader convention, not a C rule; a large malloc may be served by a separate mmap region far from the heap's start.

The rule: the segment order is an implementation fact to be cited as such. What the standard fixes is the storage duration, not the address.

How the topic is asked, and the procedure that answers it

Four question shapes cover every item this lesson has seen. The procedure below is ordered so that each step can be done on the rough sheet in under a minute.

The procedure, in five steps

1. Name the duration of every object mentioned: automatic, static, allocated. That alone answers most segment questions.

2. For each pointer, ask where it came from and whether the block behind it still exists at the point of use.

3. For each allocation, ask what was initialised — nothing for malloc, all bytes for calloc.

4. For each realloc, keep only its return value and test it for NULL before overwriting the old pointer.

5. For each count, decide which arithmetic applies: chunk rounding for bytes, the doubling series for copies, the largest hole for fragmentation.

Five traps in the wording

  • "likely to cause problems" — the word likely excludes the fault that needs malloc to fail. GATE 2001 Q2.18 turns on it.
  • "may result in a run-time error" — correct for undefined behaviour, because a crash is not promised. GATE 2021 Set 2 Q35 uses it.
  • "uninitialized pointer" — an uninitialised pointer is not an uninitialised block. One is a bad address, the other is bad contents.
  • "ignoring alignment" or a missing platform — the size question has no single answer until the ABI is fixed.
  • "amortised" against "worst case" — the same structure, two different answers.

MCQGATE CSE 2000 Q1.12

The most appropriate matching for the following pairs is:

X: m = malloc(5); m = NULL; 1: using dangling pointers
Y: free(n); n -> value = 5; 2: using uninitialized pointers
Z: char *p; *p = 'a'; 3: lost memory

  1. X–1, Y–3, Z–2
  2. X–2, Y–1, Z–3
  3. X–3, Y–2, Z–1
  4. X–3, Y–1, Z–2

Answer: D — X–3, Y–1, Z–2

X loses the only pointer to a live block, so the block is lost memory. Y frees the block and then writes through the pointer that used to name it, which is a dangling pointer. Z writes through a pointer that was never given an address, which is an uninitialised pointer.

Why the others fail. Option A calls X dangling; the block was never freed, so nothing dangles — the address is simply gone. Option C swaps the last two, which requires reading n->value as uninitialised rather than dangling. Option B starts from the same misreading of X.

The distinction being tested. Dangling means the object is gone and the pointer remains. Lost memory means the pointer is gone and the object remains. Both are faults; they are not the same fault.

MCQGATE CSE 2001 Q2.18

Consider three functions. [P1] declares a local int x = 10 and returns &x. [P2] declares int *px, executes *px = 10, and returns px. [P3] declares int *px, executes px = (int *) malloc(sizeof(int)), then *px = 10, and returns px.

Which of the above are likely to cause problems with pointers?

  1. Only P3
  2. Only P1 and P3
  3. Only P1 and P2
  4. P1, P2 and P3

Answer: C — only P1 and P2

P1 returns the address of an automatic object, whose storage ends when the function returns. P2 dereferences a pointer whose value is indeterminate, which is undefined behaviour before lifetime even matters. P3 returns a block of allocated storage, which survives the return and belongs to the caller.

Why D is tempting. If malloc returns NULL, P3 does dereference a null pointer. The question asks what is likely, and that failure needs the allocator to run out of memory, which is rare — while P1 and P2 fail on every run. D is the answer a careful reader might prefer in real code, and C is the answer the paper intends.

What P3 still owes you. The caller must free the block, and production code must test the NULL return. Neither makes P3 a fault in the sense the question asks about.

MCQGATE CSE 2021 Set 2 Q35

An ANSI C program allocates a head node with value = 0, then in a loop for index = 1..3 allocates another node, sets boxE->next = boxN, sets boxN->value = index and advances boxE = boxN. A second loop for index = 0..3 prints head->value, advances head = head->next, and prints again.

Which statement about the program is correct?

  1. Upon execution, the program creates a linked list of five nodes
  2. Upon execution, the program goes into an infinite loop
  3. It has a missing return which will be reported as an error by the compiler
  4. It dereferences an uninitialized pointer that may result in a run-time error

Answer: D — it dereferences an uninitialised pointer that may result in a run-time error

Four nodes are created, not five, and the last node's next is never assigned, so it holds whatever malloc left in those bytes. The traversal reaches that node, prints its value, loads the uninitialised next, and dereferences it.

Why the others fail. A miscounts the nodes: one before the loop plus three inside it. B describes a cycle, which would need the last next to point back into the list; an indeterminate value does not do that. C is wrong twice over — main without a return is legal in C99 and later and returns 0.

The wording to notice. "May result in" is exact. The garbage value might be a readable address, so the standard does not promise a crash; it promises that nothing is guaranteed.

MSQGATE CSE 2021 Set 1

Which of the following standard C library functions will always invoke a system call when executed from a single-threaded process in a UNIX/Linux operating system?

  1. strlen
  2. malloc
  3. exit
  4. sleep

Answer: C and D — exit and sleep

strlen walks bytes in user space and never enters the kernel. malloc usually serves the request from memory it already holds and calls sbrk or mmap only when its region is exhausted, so it does not always make a system call. exit must terminate the process and sleep must block it, and both need the kernel to do that.

Why B is the interesting wrong answer. The first allocation in a process often does cause a system call, which makes the pattern look universal. The question says always, and one allocation served from the free list breaks it.

Cross-topic note. This is the bridge between this lesson and System calls: the allocator is a library that sometimes acts as a client of the kernel.

Original practice questions

Written for this page, in GATE style, with the arithmetic taken from the same model the animation uses. They are not previous-year questions and are not labelled as such.

NATOriginal practice

A dynamic array starts empty and doubles its capacity whenever it is full, copying all existing elements to the new block. How many element copies are performed in total while appending 20 elements, one at a time?

Answer: 31

The growths happen before items 1, 2, 3, 5, 9 and 17. The copies made are the old capacities: 0 + 1 + 2 + 4 + 8 + 16 = 31. Equivalently, 2^ceil(log2 20) − 1 = 32 − 1 = 31.

Common wrong answers. 20 comes from assuming each append copies one element. 32 comes from using the final capacity instead of the sum. 36 comes from counting the copies after the twentieth push as well, but no doubling happens there because the capacity is already 32.

Edge case. At exactly 16 elements the total is 15, not 31, because the capacity of 16 is reached without a further copy. Powers of two are where the total is exactly n − 1.

NATOriginal practice

On glibc for x86-64, chunks are rounded up to a multiple of 16 bytes and are never smaller than 32 bytes, and the allocator keeps one 8-byte size word in front of the bytes it returns. How many bytes may a program safely use after malloc(20) under this allocator?

Answer: 24

request2size(20) = max(32, (20 + 8 + 15) rounded down to a multiple of 16) = max(32, 32) = 32. Usable is the chunk minus the 8-byte header, so 24.

Common wrong answers. 20 is what was requested, not what the chunk provides. 32 is the chunk including the header. 40 is the next chunk size up and belongs to a request of 25 to 40.

What the question is really testing. That the answer depends on the allocator being named. Without "on glibc for x86-64" the question has no answer, and a paper that asks it without that clause is asking about a specific implementation.

MCQOriginal practice

Consider t = realloc(p, bigger); where p was returned by an earlier malloc and bigger exceeds the current block. Which statement is true?

  1. If the call succeeds, p and t are interchangeable
  2. If the call fails, p has been freed and must not be used
  3. If the call fails, t is NULL and p is still a valid block
  4. The bytes beyond the old size are zero-filled when the block grows

Answer: C

On failure the function returns NULL and does not free the old block, so p remains valid and must still be freed by you. On success, the old pointer is invalidated even when the block grew in place, which rules out A.

Why B is the trap. It is the behaviour of the p = realloc(p, n) one-liner, not of realloc. The leak comes from overwriting p, not from the function freeing anything.

Why D is wrong. Only calloc zeroes. A grown tail is undefined, whether the block moved or not.

MSQOriginal practice

Which of the following statements are true of a conforming C implementation?

  1. free(NULL) has no effect
  2. Every byte returned by calloc is zero
  3. Every byte returned by malloc is zero
  4. malloc(0) always returns NULL

Answer: A and B

free accepts the null pointer and does nothing with it, which is specified. calloc initialises every byte of the storage it returns to zero, which is also specified.

Why C fails. malloc allocates uninitialised storage. The bytes may happen to be zero and nothing promises it.

Why D fails. A zero size is implementation-defined: a null pointer may be returned, or a non-null pointer that must not be dereferenced and must still be freed.

Related distinction. calloc zeroes bytes. The standard does not promise that all-bits-zero is 0.0 or a null pointer, though it is on every common platform.

MCQOriginal practice

A heap region holds six 32-byte chunks. The chunks at positions 2, 4 and 6 are freed. A request then arrives for 40 bytes of data. Assuming no other free memory, what happens and why?

  1. The request is served from the free space, because 96 ≥ 40
  2. The request fails, because no chunk is free
  3. The request takes new memory, because the largest free chunk is 32 and 48 are needed
  4. The request is served after the allocator compacts the region

Answer: C

96 bytes are free in three separate 32-byte holes. request2size(40) is 48, and no single hole is 48, so the allocation cannot be satisfied in place and the region grows. That is external fragmentation.

Why A is the trap. It uses the total instead of the largest hole. An allocation needs one contiguous run.

Why D is impossible in C. Compaction moves objects, and C hands out real addresses that the program may store anywhere — in a pointer, in an integer, in a file. A collector that moves objects cannot be added to C without changing the language.

One-screen revision sheet

Everything on this page, compressed to what you would write on the rough sheet in the first minute of the paper. Say which allocator and which platform before you quote a byte count.

The four functions, in one line each

  • malloc(n): at least n bytes, uninitialised, aligned, or NULL.
  • calloc(k, s): k × s bytes, every byte zero, or NULL.
  • realloc(p, n): a new block keeping min(old, new); old pointer invalid; NULL on failure with the old block intact.
  • free(p): returns the chunk; nothing if p is NULL; undefined if p is not a returned value or was already freed.

Two formulas

Chunk: request2size(req) = max(32, (req + 23) & ~15), and usable = chunk − 8.

Copies under doubling: 2^ceil(log2 n) − 1, always below 2n, equal to n − 1 when n is a power of two.

Six traps, six answers

  • Reading a fresh block? It is uninitialised; only calloc zeroes.
  • Freeing and then using? Undefined, and allowed to look like it worked.
  • p = realloc(p, n)? Leaks on failure; use a temporary.
  • Growing in place? The old pointer is still invalid.
  • Totalling free bytes? The largest hole is what an allocation needs.
  • Multiplying before allocating? Test n > SIZE_MAX / sizeof *p first.

Two sentences to carry into the next topic

A list node is allocated, linked and freed, so Linked lists is this lesson applied once per node — and the 2021 item shows what happens when the last next is left uninitialised. And the heap is the only region whose size the program decides at run time, which is why the operating system's memory-management lesson begins exactly where this one stops: with a request for pages.
