Topic and objective

TOPIC: Functions, scope, lifetime and the preprocessor, at the depth GATE CSE asks them inside "Programming in C".

LEARNING OBJECTIVE: Given a short C program that uses functions, static, extern or a #define, decide three things without running it: which object each name refers to, whether that object still exists at the moment it is read, and exactly what text the preprocessor produced — then state the output, or say that the standard defines none.

I read this topic as the four mechanisms that decide an answer: the function call and its prototype, scope, storage duration and linkage, and the preprocessor. Recursion, pointers, arrays and structures each have their own lesson and are linked from here rather than repeated.

GATE relevance

Verified fact Class A — explicitly in the syllabus.

Section 4 of the official GATE 2027 CS syllabus (IIT Madras) opens with the words "Programming in C." Functions, scope and the preprocessor are part of that phrase, not an extension of it.

Class A does not mean "guaranteed to appear". It means a question on it is inside the declared boundary. The previous-year questions quoted in this lesson are recorded as an observation about past papers, never as a forecast.

What you should be able to do afterwards

Read a function-and-macro program and answer three questions in order: which object?, does it still exist?, what text did the preprocessor make?

Most wrong answers in this topic come from answering the second question with the first one's answer — treating a name's scope as if it were the object's lifetime.

Level 1 — Intuition: the workshop, the shelf and the paste-up

A function call is a workbench. Every time you call the function, a fresh bench is set up, the arguments are copied onto it, the body works on those copies, and the bench is cleared when you leave. The caller's own tools are untouched on the caller's bench.

A static local is a drawer bolted to the workshop wall rather than to the bench. The name on the drawer is only readable from inside that one function, but the drawer is not cleared when the bench is.

The preprocessor is a paste-up artist who works before the compiler arrives. It has no idea what int means. It replaces words with other words, pastes files into files, and deletes whole regions when asked. Every macro surprise in this lesson is that artist being perfectly obedient.

Level 2 — Formal: the four definitions

Declaration. Introduces a name and its type. Definition. A declaration that also allocates storage or supplies a body. A prototype is a function declaration that specifies every parameter type.

Scope. The region of program text in which a name is visible: block, function (labels only), file, or function prototype.

Storage duration. How long the object exists: automatic (block entry to block exit), static (the whole run, initialised once before main), thread, or allocated (malloc to free).

Linkage. Whether the same name in another translation unit denotes this object: no linkage, internal, or external.

Verified fact — these four are separate properties. The standard's storage-class table fixes them jointly, which is why one keyword can change three answers at once. Cppreference's Storage-class specifiers (C) reproduces the table.

Level 3 — The call, step by step

A call to a function with a prototype in scope runs in this order:

  1. Evaluate each argument the argument expression is evaluated once, in the caller
  2. Convert it to the parameter's type "as if by assignment"; this is where a double becomes an int
  3. Create a new object for each parameter automatic storage duration, one per call, one per recursion level
  4. Run the body the body sees only those new objects
  5. Convert the returned value to the declared return type a double returned from an int function is truncated
  6. Destroy the parameters any pointer to them is now dangling

Without a prototype, step 2 is replaced by the default argument promotions, and a mismatch after promotion is undefined behaviour.

Level 4 — The distinction the whole topic turns on

Scope answers "can this line see the name?" Storage duration answers "does the object exist right now?"

These are independent, and all four combinations are real:

  • local name, automatic lifetime — an ordinary local variable
  • local name, static lifetime — a static local, the exam favourite
  • file name, static lifetime — a global or a file-scope static
  • file name, no object at all — an extern declaration that nothing defines

Level 5 — Worked: which object does x mean?

int x = 100;              /* file scope, static duration */
int main(void) {
  int x = 1;              /* block scope, hides the global */
  {
    int x = 2;            /* hides both */
    printf("%d ", x);     /* 2 */
  }
  printf("%d ", x);       /* 1 — the inner block has ended */
  return 0;
}

Three objects, one spelling. The lookup rule is mechanical: start in the innermost enclosing block, move outward, stop at the first match. There is no ambiguity and no diagnostic.

After the inner block closes, its object is destroyed and the outer x is visible again. The global x is never printed here — it is shadowed for the whole of main.

Level 6 — Worked: the static counter, three ways

int a(void){ int n = 0;  n++; return n; }   /* 1 1 1 */
int b(void){ static int n = 0; n++; return n; } /* 1 2 3 */
int c(void){ static int n;  n++; return n; }    /* 1 2 3 */

a makes a new n on every call, so the answer never changes. b initialises once, so the value accumulates. c omits the initialiser entirely — and because static objects are zero-initialised before main, it behaves exactly like b.

Derivation The third line is the one people misread. "No initialiser" does not mean "no initial value" for a static object; it means "the default, which is zero".

Level 7 — Worked: expanding a macro by hand

Given #define SQR(x) (x*x) and b = 4:

  1. Replace the parameter token SQR(b+2) → (b+2*b+2) — the argument's three tokens go in, no parentheses added
  2. Substitute the values (4+2*4+2)
  3. Apply precedence multiplication first: 2*4 = 8
  4. Left to right at the additive level 4+8+2 = 14

With #define SQR(x) ((x)*(x)) the expansion is ((b+2)*(b+2)), which is 36. The page computes both, rather than trusting this paragraph.

Level 8 — Boundaries: when each rule applies

The prototype rule applies when the called function's type includes a prototype. A call through a K&R-style declaration such as int f(); gets default argument promotions instead.

The static-local rule applies to any block-scope object declared static. It does not reset, ever, including across recursion levels — all levels share one object.

The macro rule applies to every macro, including a fully parenthesised one. Parentheses fix precedence; they never fix double evaluation.

The one-definition rule applies to names with external linkage. Two static definitions in two files are two different objects, and the linker is happy.

Example 1 — a static local in a loop header

Verified fact GATE CSE 2019, Programming in C. Numbering note: the archive at gateoverflow records this as Question 27; another aggregator indexes it as Set 1 Q37. The question text is identical.

int r() { static int num = 7; return num--; }
int main() {
  for (r(); r(); r())
    printf("%d", r());
}
  1. Init r() returns 7, num becomes 6 — the value is thrown away
  2. Condition r() returns 6, num becomes 5; 6 is non-zero, so the body runs
  3. Body r() returns 5, num becomes 4; prints 5
  4. Update r() returns 4, num becomes 3
  5. Condition r() returns 3, num becomes 2; body runs again
  6. Body r() returns 2, num becomes 1; prints 2
  7. Update, then condition update returns 1 (num 0); condition returns 0 (num −1) and is false

Output 52. The page's own model simulates all eight calls and compares the joined digits to the string "52".

Example 2 — the swap that does nothing

void swap(int a, int b){ int t = a; a = b; b = t; }
int main(void){
  int x = 1, y = 2;
  swap(x, y);
  printf("%d %d", x, y);   /* 1 2 */
}

Four objects exist during the call: x and y in main, and a and b in swap. The body swaps a and b and then those two are destroyed.

The repair is to pass addresses and dereference:

void swap(int *a, int *b){ int t = *a; *a = *b; *b = t; }
/* call: swap(&x, &y);   now prints 2 1 */

The pointers are still copies — but they point at the caller's objects, so writing through them reaches the originals. Copying the address is what makes the write visible.

Example 3 — the array that arrives as a pointer

void show(int a[10]){
  printf("%zu %zu\n", sizeof(a), sizeof(a[0]));  /* 8 4 on LP64 */
}
int main(void){
  int v[10];
  printf("%zu\n", sizeof(v));                    /* 40 */
  show(v);
}

A parameter declared int a[10] has its type adjusted to int *a. The 10 is discarded entirely; it is documentation, not a check.

Derivation So sizeof(a) is the size of a pointer, and sizeof(a)/sizeof(a[0]) gives 2 on a 64-bit machine — not 10, and not a compile error. The count must be passed as a second parameter.

Example 4 — reading a macro expansion

Three macros, one argument b = 4:

macro bodySQR(b+2) expands tovalue
x*xb+2*b+214
(x*x)(b+2*b+2)14
((x)*(x))((b+2)*(b+2))36

Row two is the trap worth noticing: outer parentheses around the body change nothing here, because the damage is inside — between the parameter and the operator.

You need parentheses around each parameter and around the body. The page evaluates all three expansions with its own arithmetic parser and checks the values 14, 14 and 36.

Example 5 — auto against static in two functions

int g;                       /* 0, static duration */
void f(void){
  static int s = 10;
  int a = 10;
  s++; a++;
  printf("%d %d ", s, a);
}
int main(void){ f(); f(); printf("%d", g); }

First call prints 11 11. Second call prints 12 11 — s kept its value, a was rebuilt.

Then g prints 0, because an object with static storage duration is zero-initialised before main. Had g been declared inside a function without static, reading it would have been undefined behaviour rather than zero.

Example 6 — identifying the storage class from a trace

A function is called three times and prints 1 1 1. Which declaration of n is consistent?

A:  int n = 0;
B:  static int n = 0;
C:  static int n;
D:  register int n = 0;

Answer: A or D. Both have automatic storage duration, so both rebuild n on every call.

B and C both give 1 2 3. They are not distinguishable from the output at all, because a static object without an initialiser is zero-initialised. If an option list offers only one of B and C, that is the answer; if it offers both, the question is broken — which is worth recognising in a mock test.

Example 7 — an include guard, before and after

/* shape.h, no guard */
struct point { int x, y; };
/* main.c */
#include "shape.h"
#include "shape.h"      /* error: redefinition of 'struct point' */
/* shape.h, guarded */
#ifndef SHAPE_H
#define SHAPE_H
struct point { int x, y; };
#endif

The preprocessor pastes the file twice either way. With the guard, the second paste finds SHAPE_H already defined, so #ifndef is false and the whole block is skipped.

The page models this as a counter: definitions of point equal 2 without a guard and 1 with one.

Example 8 — static at file scope, seen by the linker

/* a.c */                    /* b.c */
static int counter;          static int counter;
void bump(void){ counter++; } void bump2(void){ counter++; }

Two objects, both called counter, both private to their own file. The linker never compares them, so there is no conflict.

Remove static from both and the link fails with a multiple-definition error on counter. Keep static on only one and it still fails, because the other is external.

The page counts definitions per symbol and reports the link verdict for each of the four combinations.

Counterexample: "a static local resets on each call"

int f(void){ static int n = 0; n++; return n; }
/* f() f() f()  ->  1 2 3, not 1 1 1 */

The initialiser = 0 is executed once, before main begins — not each time control reaches the declaration. Reaching the declaration again does nothing at all.

The property violated: static storage duration means initialisation happens once for the whole run.

Counterexample: "parentheses make a macro safe"

#define SQR(x) ((x)*(x))
int i = 5;
printf("%d %d", SQR(i++), i);   /* 30 and 7 */

Fully parenthesised, and still wrong. The argument i++ appears twice in the expansion, so it is evaluated twice: 5 then 6, product 30, and i ends at 7.

The property violated: a macro substitutes text, so an argument with a side effect is duplicated. No bracketing can prevent that.

Counterexample: "injective-looking sizes prove the array arrived"

void f(int a[10]){ printf("%zu", sizeof a); }  /* 8, not 40 */

The 10 in the parameter looks like a guarantee. It is not even retained: the parameter's type is adjusted to int * before the body is compiled.

The property violated: an array-typed parameter is adjusted to a pointer, so all size information is lost at the call boundary.

Trap: the missing prototype still compiles

/* no prototype for g */
int main(void){ g(3.7); return 0; }   /* int g(int); */
int g(int x){ return x; }

In C99 and later this is a constraint violation and a conforming compiler must diagnose it — but many compilers accept it with only a warning, and pre-C99 code was allowed to.

If it is accepted, the argument 3.7 is a double and is not promoted (only float is), while the parameter is int. The behaviour is undefined. Do not answer "3".

Trap: static inside a recursive function

void count(int n){
  static int d = 1;
  printf("%d ", d);
  d++;
  if (n > 1) count(n - 1);
  printf("%d ", d);
}

All recursion levels share one d, because it is one object with static duration — not one per frame. So the second print of the deepest call and every unwinding call print the same final value.

For count(3) the first three prints are 1, 2, 3 and the last three are all 4. Compare this with an ordinary local, which would give a different number at every level. The Pointers in C and C Fundamentals lessons cover the frame behaviour.

Trap: extern is a declaration, not a definition

extern int total;            /* declares; allocates nothing */
int main(void){ return total; }   /* link error: undefined reference */

With no initialiser and no earlier definition, extern int total; only promises that total exists somewhere. If no translation unit defines it, the program compiles and fails to link.

At file scope, plain int total; is a tentative definition and does allocate. The single word extern is the whole difference between a program that links and one that does not.

Misconception 1 — "scope and lifetime are the same thing"

Why it tempts: for an ordinary local variable they coincide exactly — the name is visible and the object exists over the same region of text. The two only come apart when you add static, and that is the case exams choose.

Minimal counterexample: static int n; inside a function. The name is visible only in that function (block scope), yet the object exists for the entire program (static duration).

Correct rule: scope is a property of the name and is decided by where the declaration sits. Storage duration is a property of the object and is decided by the storage class and by file versus block position. Ask the two questions separately, in that order.

Misconception 2 — "a function can change its arguments"

Why it tempts: in many languages a parameter is a reference, and even in C, passing a pointer does let you change the caller's object. It is easy to generalise from the pointer case to all cases.

Minimal counterexample: Example 2's swap(int a, int b). It compiles, runs, swaps its own copies, and leaves x and y untouched.

Correct rule: C passes by value, always. What a pointer parameter copies is the address, and writing through a copied address reaches the original object. No copy, no effect on the caller.

Misconception 3 — "a macro is a small function"

Why it tempts: the call syntax is identical, and for a simple argument such as SQR(4) the answer is identical too. The difference only shows with a compound or side-effecting argument.

Minimal counterexample: SQR(b+2) with body (x*x) gives 14, while a function would give 36. And SQR(i++) gives 30 and leaves i at 7.

Correct rule: a macro is token substitution performed before compilation. There is no call, no argument evaluation, no type checking and no scope. Parentheses fix grouping; they never fix duplication.

Misconception 4 — "uninitialised means zero"

Why it tempts: it is true for globals and for every static object, which are the ones that appear in traces. Students carry the rule across to locals.

Minimal counterexample: int x; printf("%d", x); inside main reads an object with automatic storage duration and indeterminate value. That is undefined behaviour, and a printed 0 is luck.

Correct rule: objects with static storage duration are zero-initialised before main; objects with automatic duration are not initialised at all. The dividing line is the storage class, not whether the variable looks important.

Misconception 5 — "declaration and definition are opposites"

Why it tempts: textbooks often write "a declaration introduces a name, a definition allocates storage", which reads like a partition.

Minimal counterexample: int f(void){ return 1; } is a definition and it is also a declaration — the compiler learns the name and the type from it.

Correct rule: every definition is a declaration; not every declaration is a definition. The useful question is "does this line allocate storage or supply a body?"

Misconception 6 — "two files cannot both use the name counter"

Why it tempts: the one-definition rule is usually taught as "one definition per name", which sounds like a global namespace.

Minimal counterexample: Example 8 — static int counter; in both a.c and b.c links cleanly.

Correct rule: the rule is one external definition per name. Internal linkage makes each static name a different object, so two files may each have one.

Pattern 1 — trace a static counter through a control structure

A function with a static local is called from several places in one statement — most often from all three parts of a for header. You are asked for the printed output.

Reasoning it demands: write the call order explicitly (init, condition, body, update, condition, …) and give each call the next value in sequence. Do not reason about the loop and the function separately.

Common wrong approach: counting only the body's calls. The header's calls consume values too — in the 2019 question, six of the eight calls are bookkeeping. See Example 1 for the full trace.

Pattern 2 — two variables, one spelling

A local in main and a local or static in a called function share a name, and the question asks for an expression involving both.

Reasoning it demands: resolve every occurrence of the name by the innermost-block rule, and keep a separate column per object. The 2023 question needs three columns: main's x, main's y, and funcp's static x.

Common wrong approach: one column. Once the two x are merged, every later number is wrong, and the wrong numbers are usually among the options.

Pattern 3 — swap the storage class, ask for the new output

The question gives a program, then says "if Line 1 is replaced by auto int a = 1; and Line 2 by register int a = 2;, what is the output?" This is the 2012 format.

Reasoning it demands: change the duration and nothing else. auto and register both mean automatic, so both variables are rebuilt on each call. Re-trace from scratch — do not adjust the old trace.

Common wrong approach: assuming register behaves like static because it is also an unusual keyword. It has automatic duration; the only extra rule is that its address cannot be taken.

Pattern 4 — expand a macro and evaluate

A #define with an under-parenthesised body is applied to a compound argument, and the output is asked for. A second flavour adds a side-effecting argument.

Reasoning it demands: write the expansion on paper, token for token, then evaluate with C precedence. Never evaluate the argument first and then apply the macro as if it were a function.

Common wrong approach: computing the "intended" value. If you find yourself answering 36 for SQR(b+2) with body (x*x), you have silently replaced the macro with a function.

A four-line procedure for any question in this topic

  1. List the objects one line per declaration; mark each as automatic or static, and note its scope
  2. Resolve each name occurrence innermost block outward; a name is not an object
  3. Expand every macro before evaluating token for token; count how many times each argument text appears
  4. Check for undefined behaviour before computing uninitialised automatic read, mismatched prototype, or a duplicated side effect are all verdicts, not numbers

Step 4 is the one that turns a wrong number into a right answer.

MCQModerateGATE CSE 2023, Q35

The integer value printed by this ANSI-C program is ______.

#include <stdio.h>
int funcp(){
    static int x = 1;
    x++;
    return x;
}
int main(){
    int x, y;
    x = funcp();
    y = funcp() + x;
    printf("%d\n", (x + y));
    return 0;
}
  1. 5
  2. 6
  3. 7
  4. 8

Answer: C — 7

First call: static x goes 1 → 2, returns 2, so main's x is 2. Second call: the same static object goes 2 → 3, returns 3. Then y = 3 + 2 = 5, and x + y = 2 + 5 = 7.

Common wrong answer: 8. That comes from treating the two x as one variable, so the second call appears to increment main's x. 6 comes from forgetting that the static initialiser runs only once.

The page's model runs this program and checks the printed value is 7.

MCQHardGATE CSE 2012, Q49

What output is generated if Line 1 becomes auto int a = 1; and Line 2 becomes register int a = 2;?

int a, b, c = 0;
void prtFun(void);
main() {
  static int a = 1;      /* Line 1 */
  prtFun(); a += 1; prtFun();
  printf("\n %d %d ", a, b);
}
void prtFun(void) {
  static int a = 2;      /* Line 2 */
  int b = 1;
  a += ++b;
  printf("\n %d %d ", a, b);
}
  1. 4 2 · 4 2 · 2 0
  2. 3 1 · 4 1 · 4 2
  3. 4 2 · 6 2 · 2 0
  4. 4 2 · 4 2 · 3 1

Answer: A — 4 2 · 4 2 · 2 0

With auto and register, both a variables have automatic duration, so each call rebuilds prtFun's a at 2. Each call: b becomes 2, a becomes 4, prints 4 2. In main, a is 1 then 2, and b is the global b, still 0.

Option C is the answer to the unreplaced program, where prtFun's a is static and keeps its value — that is the companion question Q48. Option B comes from treating register as if it preserved its value. Option D misreads the global b, which is never written.

The page's model simulates both versions of the program.

MCQBasicOriginal GATE-style

With int b = 4; what does this print?

#define SQR(x) (x*x)
...
printf("%d", SQR(b+2));
  1. 14
  2. 18
  3. 36
  4. 20

Answer: A — 14

The expansion is (b+2*b+2) = 4+2*4+2. Multiplication first gives 4+8+2 = 14.

Common wrong answer: 36. That is what a real function with the same body would return, and it is what the author intended. 18 comes from grouping as (4+2)*(4+2)/2 — a made-up regrouping with no rule behind it.

MSQModerateOriginal GATE-style

Which of the following are true of a block-scope object declared static int n; inside a function f?

  1. Its name is visible only inside f.
  2. It is initialised to 0 before main begins.
  3. A second call to f re-runs the declaration's initialisation.
  4. Recursive calls to f each get their own copy of it.

Answer: A, B

A — scope is block scope; static changes the duration, not the scope. B — static storage duration means zero-initialisation before main, so an omitted initialiser still gives 0.

C is false — the initialisation happens once for the whole run. D is false — all recursion levels share the single object, which is exactly why the recursive counter in Edge cases prints 4 three times.

This is the closest pair in the topic: scope is per name and does not change; duration is per object and does change. C and D each confuse one with the other.

NATBasicOriginal GATE-style

What is printed?

int f(void){ static int n = 0; return ++n; }
int main(void){
  int i, s = 0;
  for (i = 0; i < 4; i++) s += f();
  printf("%d", s);
  return 0;
}

Answer as an integer.

Answer: 10

f returns 1, 2, 3, 4 on its four calls, and s accumulates them: 1+2+3+4 = 10.

Common wrong answer: 4. That is the last return value, not the sum. 7 comes from starting the counter at 1 and running three times, which drops the first call. The page's model iterates this and checks the total is 10.

NATModerateOriginal GATE-style

On a machine with 4-byte int and 8-byte pointers, what does this print?

void g(int a[10]){
  printf("%zu", sizeof(a) / sizeof(a[0]));
}
int main(void){ int v[10]; g(v); return 0; }

Answer as an integer.

Answer: 2

The parameter int a[10] is adjusted to int *a, so sizeof(a) is 8 and sizeof(a[0]) is 4. The quotient is 2.

Common wrong answer: 10. That reads the 10 in the parameter list as a guarantee. It is discarded by the type adjustment before the body is compiled. 40 would be sizeof(v) in the caller, where v is still an array.

MSQHardOriginal GATE-style

Which of these have undefined behaviour in standard C?

  1. int x; printf("%d", x); inside main
  2. #define SQR(x) ((x)*(x)) then SQR(i++) with int i = 5;
  3. Calling int g(int) as g(3.7) with no prototype in scope
  4. Reading a static local inside f after an earlier call to f returned

Answer: A, B, C

A — an automatic object is not initialised, so its value is indeterminate. B — the expansion contains two unsequenced modifications of i. C — 3.7 is a double and is not subject to the default argument promotions, so the argument type does not match the parameter.

D is defined. The object has static storage duration, so it outlives the call that created it; its name is out of scope in the caller, but reading it inside f is entirely valid. This is the option people mark by mistake, because "the function returned" sounds like "the object is gone".

Notice that B is undefined even though the macro is correctly parenthesised — the two classic macro defects are independent.

MCQHardOriginal GATE-style

What happens here, with a conforming implementation?

#include <assert.h>
#define NDEBUG
int main(void){ assert(1 == 2); return 0; }
  1. The assertion is checked and the program aborts.
  2. The assertion is compiled out, because NDEBUG is defined.
  3. It is undefined behaviour to define NDEBUG after including the header.
  4. It does not compile, because assert is not a function.

Answer: A — it aborts

The standard ties the effect of NDEBUG to the moment <assert.h> is included. It was not defined then, so assert was defined as the real checking macro, and defining NDEBUG afterwards changes nothing.

B is the whole trap: the definition looks like it should work, and in a build system it usually does, because -DNDEBUG is on the compiler command line and therefore in effect before every include. C is false — it is legal, merely ineffective. D is false — assert is a macro that expands to an expression, not a function call.

Four questions, in order

  1. Which object? resolve the name innermost block outward
  2. Does it exist? automatic dies at block exit; static lives for the run
  3. What text did the preprocessor make? expand token for token; count each argument's appearances
  4. Is it defined at all? uninitialised automatic read, mismatched prototype, duplicated side effect

Answer them in this order every time. Skipping step 4 is how a wrong number gets chosen over a right verdict.

Macro checklist

Write the expansion before you compute. Then check:

  • Parentheses around each parameter and around the whole body — both, or precedence bites.
  • How many times does each parameter appear in the body? That many evaluations, if the argument has a side effect.
  • #x stringifies; a##b pastes tokens. Neither expands its argument first.
  • #include pastes a file; a guard stops the second paste.
  • NDEBUG is tested where <assert.h> is included.

Six sentences to keep

A definition is a declaration; the reverse is not true. C passes by value, always — a pointer parameter copies an address. Scope is per name, duration is per object. static at block scope keeps the value and the local name. A macro substitutes text, so parentheses fix grouping and nothing fixes duplication. Objects with static duration start at zero; automatic ones start at whatever was there.

If you can say those six without looking, the practice set is a check rather than a lesson.

Version and platform notes

The lesson assumes C99 or later, which is what GATE machines use. Two answers depend on it:

  • A call with no prototype in scope is a constraint violation from C99 onward, so a conforming compiler must diagnose it. Pre-C99 code was allowed to compile it silently.
  • Two unsequenced modifications of one object became undefined behaviour with C99's sequence-point wording; before that it was unspecified.

Standard and reference treatments

  • cppreference — Storage-class specifiers (C) Supports the four storage classes and their duration and linkage, the defaults when no specifier is given, that a static object's value is initialised only once prior to main, that automatic storage is allocated on block entry and released on exit with a fresh allocation per recursion level, and that register forbids taking the address.
  • cppreference — Implicit conversions (C) Supports the call rule "converted as if by assignment" for a function with a prototype, and the default argument promotions — integer promotion plus float to double — for a call without a prototype and for trailing variadic arguments.
  • cppreference — Function declarations (C) Supports declaration against definition, the prototype's role in checking argument types, and the adjustment of an array-typed parameter to a pointer.
  • cppreference — Macro replacement (C) Supports that macro arguments are fully expanded before substitution unless the parameter is an operand of # or ##, and the behaviour of the stringification and token-pasting operators used in the Revision tab.
  • cppreference — #include (C) Supports #include being textual inclusion, and the difference between the quoted and angle-bracket search paths.
  • cppreference — assert (C) Supports that if NDEBUG is defined when <assert.h> is included, assert expands to nothing — which is the whole of practice question 8.
  • cppreference — extern and linkage (C) Supports extern being a declaration without a definition when it has no initialiser, and the internal linkage that file-scope static gives.
