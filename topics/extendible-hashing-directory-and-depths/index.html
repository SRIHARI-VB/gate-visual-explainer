Topic and objective

TOPIC: Extendible hashing — the hashed index that replaces a fixed bucket count with a directory of 2d pointers. The two depths (global d and local d′), the split, the doubling, the buddy merge and the halving.

LEARNING OBJECTIVE: Given a key and a structure, find its directory entry from the low d bits, say whether an overflow splits a bucket alone or doubles the directory first, and say why. Compute the four numbers that questions ask for — pointers per bucket, maximum records, minimum global depth, directory size. Trace an insertion sequence by hand and check the four defining properties afterwards. State what the structure guarantees about a lookup, and name the query it cannot answer.

I read this topic as one promise and two depths: a lookup costs one block read because the directory is resident, and every structural decision follows from comparing d with d′. Every number on this page — the 8 entries and 6 buckets of the ten-record trace, the 3 doublings and 5 splits, the 4-of-4 copied pairs, the 64 entries for 5 skewed keys, the 20160 insertion orders checked — is computed at load by the lesson’s own model and re-checked against the definition it claims.

Prerequisites

This lesson needs one idea from the disk and one from ordinary hashing. Neither is assumed.

  • Secondary storage — a block is the unit of transfer, and a block read is the unit of cost.
  • Hashing — a hash function, a home bucket, a collision, a load factor. That lesson is about hashing inside main memory; this one is about hashing on disk.
  • File organisation and indexing — heap, sequential and hashed files, and the B+ tree this lesson is measured against.
  • Asymptotic complexity — why "one block read regardless of size" is the claim worth paying for.

Approximate learning time: 75 minutes, of which about 25 is the animation.

Five ideas, and the rest follows

  1. A fixed bucket count overflows as the file grows, and the chain that absorbs the overflow is what makes the lookup cost grow.
  2. A directory of 2d pointers, indexed by the low d bits of the hash, makes the bucket reachable in one probe. The global depth d is the number of bits it reads.
  3. Each bucket records how many bits it actually needed: the local depth d′, never larger than d. A bucket at d′ is reached by exactly 2d−d′ entries, and all of them agree on its low d′ bits.
  4. On overflow, compare the two depths. d′ < d: split and repoint, no new entry. d′ = d: double the directory first, then split.
  5. Deletion reverses it — merge with the split image when the records fit, then halve the directory when every local depth has fallen below it. The cost of all this is a directory that can grow large when the hash is skewed, and no range query.

Intuition: a hotel that adds corridors instead of rebuilding

A hotel has a fixed number of rooms. When a floor is full, guests are put in a corridor and the receptionist keeps a note: room 3, then the corridor. Every extra guest makes that note longer, and finding a guest at the end of the corridor takes longer than finding one in a room.

The other hotel keeps a signboard at reception: one line per room, saying which floor to go to. When a floor is full, it does not build a corridor — it splits that floor into two and rewrites only the signboard lines that pointed at it. If the signboard has no spare line to give, it reprints the whole board at double the size, which costs a photocopy and nothing else.

Educational interpretation The analogy maps: room = bucket, corridor = overflow chain, signboard = directory, one line = one pointer, reprinting at double size = doubling. It stops mapping at the split, which redistributes guests by one bit of their booking number — something a hotel cannot do.

The formal objects, every symbol in words

Hash value — h(k), a bit string computed from the key. The structure reads only its low-order bits.

Directory — an array of 2d pointers to buckets. Entry number i is chosen as i = h(k) AND (2d − 1), that is, the last d bits of h(k) read as a number.

Global depth d — the number of low-order bits the directory reads. It is a property of the directory, and it equals the largest local depth in the structure.

Bucket — one disk block holding up to capacity records, plus a header field holding its local depth d′: the number of low-order bits that were actually needed to separate the records in it.

$$\text{pointers reaching one bucket} \;=\; 2^{\,d-d'}$$ A bucket whose local depth is d′ is pointed at by 2 to the power (d minus d′) directory entries, and every one of those entries agrees with the bucket on its low d′ bits.

Split image (or buddy) — the bucket that shares every bit of a bucket except bit d′−1. Splitting creates a pair of split images; merging rejoins them.

The one decision, and the two cases it has

Every structural change in the structure comes from one question, asked when a record does not fit in the bucket it hashed to. Nothing else causes a split or a doubling.

the overflowing bucket what happens why cost
d′ < d split only the bucket already has 2d−d′ ≥ 2 pointers, so a spare one exists for the new bucket 1 bucket read, 1 write, and the pointers that reached it rewritten
d′ = d double, then split the bucket has exactly 20 = 1 pointer, so a second pointer has to be created, and a new entry means a longer directory one copy of the pointer array, then the same split

The comparison is made on the bucket as it stands, before anything is moved. Reading it after a split is the commonest procedural error, because after the split the local depth has already changed.

The assumptions under all of it

Three assumptions are load-bearing, and each has a named failure.

  • The directory fits in main memory. Then an equality lookup is one block read. If it does not, the lookup is two: one for the directory page, one for the bucket.
  • The hash spreads keys uniformly over the low bits. When it does not, one bucket keeps overflowing and the directory doubles for nothing — the skew scene computes 64 entries for 5 records.
  • Keys differ somewhere in their bits. Two records with the same full hash value cannot be separated by any number of bits; implementations keep an overflow chain for duplicates.

Verified fact Ramakrishnan and Gehrke state the first and third directly: "If directory fits in memory, equality search answered with one disk access; else two… Multiple entries with same hash value cause problems!"

What the one-read promise does not cover

A hash index answers one key equals one value. It does not answer a range, a prefix, or an ordered scan, because the hash deliberately scatters neighbours in value across unrelated buckets.

This page measures it: 20 records in 12 buckets, and the eight consecutive keys 5 to 12 land in 8 different buckets. A B+ tree reads one leaf and then walks the leaf chain. So "which index" is never a question with one answer — it is a question about the query shape.

Example 1 — ten records, computed end to end

Capacity 2 records per bucket, hash h(k) = k so that a key is its own bit string, and the insertion order 16, 4, 6, 22, 24, 10, 31, 7, 9, 20.

1. 16 arrives at depth 0: one entry, one bucket, room for two. 16, 4 in the bucket

2. 6 overflows it: d′ = d = 0, so double to depth 1, then split on bit 0. 6 has bit 0 = 0, so it goes to the low half, which still holds two others and overflows again

3. the same bucket is still over capacity, so d′ = d = 1 again: double to depth 2, split on bit 1. 16 and 4 differ at bit 1, and are now separated

4. 22 arrives, entry 10 = 2, joins 6. no change

5. 24 arrives, entry 00 = 0, holds 16: full but fits. no change

6. 24 needs a third: d′ = d = 2, double to depth 3, split on bit 2. 16 and 24 differ at bit 2 (24 has 1)

7. 10 arrives, entry 010 = 2, overflows, and now d′ = 2 < d = 3, so split only. this is Example 2

8. 31 joins 7 at entry 011. fits

9. 9 arrives at entry 001, overflows a bucket at d′ = 1 < 3, split only. a second split with no doubling

10. 20 joins 4 at entry 100. fits

Final state, computed: global depth 3, 8 entries, 6 buckets, 10 records, 10 of 12 slots used, from 3 doublings and 5 splits, with local depths 2, 2, 3, 3, 3, 3. The two buckets at d′ = 2 are each shared by two entries.

Example 2 — the split that does not double

State before: depth 3, 8 entries, 5 buckets. Insert 10. Its low three bits are 010, so the entry is 2, and that bucket holds 6 and 22 — three records where two fit.

1. Compare: the bucket’s d′ is 2, the global depth is 3. d′ < d, so this is the split-only case

2. The split bit is bit number d′ = 2, which is the 4s bit.

3. 6 = 0110 has bit 2 = 1. 10 = 1010 has bit 2 = 0. 22 = 10110 has bit 2 = 1. so 10 stays, 6 and 22 move

4. Both halves take d′ = 3. The old bucket had 23−2 = 2 pointers; each half now has 23−3 = 1.

5. Entries stay 8, global depth stays 3, buckets go from 5 to 6.

The check that catches a slip: 10 & 7 = 2, and the bucket it now sits in must have d′ = 3, so that bucket’s single entry is 2 and it must contain only keys with low three bits 010. It contains 10 alone. Mathematical derivation

Example 3 — the split that doubles first

State before: depth 2, 4 entries, buckets A(16, 4 at d′ = 2), B(6, 22 at d′ = 2), C(10 at d′ = 2), D(24 at d′ = 2) — every bucket at the global depth, so every bucket has exactly one pointer.

1. Insert 24: its low two bits are 00, so entry 0, which holds 16 and 4. Three records, capacity 2.

2. Compare: d′ = 2 and d = 2. equal, so the directory must double

3. Copy the array: entry i + 4 becomes entry i, for i = 0 to 3. 4 of 4 pairs identical, checked

4. Global depth becomes 3. Now the overflowing bucket has two pointers, at 000 and 100.

5. Split on bit 2: 4 = 100 has bit 2 = 1, 16 = 10000 has bit 2 = 0, 24 = 11000 has bit 2 = 0. 4 moves, 16 and 24 stay

6. The halves take d′ = 3. Entry 000 reaches the bucket holding 16 and 24; entry 100 reaches the bucket holding 4.

Depth 2 → 3, entries 4 → 8, buckets 4 → 5. The doubling came first and the split came second; doing them in the other order leaves the new bucket with no pointer.

Example 4 — the four counts, worked

Each line is computed by the page’s model, and each is a question that has actually been asked in this shape.

a. A bucket at d′ = 2 in a directory at d = 4: 24−2 = 4 entries reach it. count of entries, not of records

b. Most records at d = 4, capacity 3: 24 × 3 = 48. a ceiling, reached only if every bucket is full and no two share an entry

c. 100 records at capacity 8: ⌈100/8⌉ = 13 buckets at least, so the smallest d with 2d ≥ 13 is 4, giving 16 entries and a ceiling of 128 records.

d. Directory at d = 20 with 4-byte pointers: 220 × 4 = 4194304 bytes = 4 MiB. about two million records at capacity 2

e. 1000 records at capacity 10: ⌈1000/10⌉ = 100, so d = 7, 128 entries, ceiling 1280.

Line (c) and line (e) are floors and line (b) is a ceiling. They meet only for a perfectly uniform hash: the bound is necessary, not sufficient, which is exactly what the skew scene shows.

Example 5 — a deletion sequence with both answers

Start from the finished ten-record structure: depth 3, 8 entries, 6 buckets. Delete 20, then 24, then 22, then 16 and 4.

1. Delete 20. Its bucket held 4 and 20, so it now holds 4. Its split image holds 16 and 24. Combined 1 + 2 = 3 > capacity 2. merge refused, still 6 buckets

2. Delete 24. Now 1 + 1 = 2, which fits, and both have d′ = 3. merge accepted, d′ falls to 2, 5 buckets

3. Delete 22. Its bucket held 6 and 22, now 6 alone at d′ = 3; its image holds 10 at d′ = 3; combined 2 fits. merge, d′ 3 → 2

4. Every local depth is now below the global depth 3, so entry i and entry i + 4 agree for all i. halve: d 3 → 2, entries 8 → 4, 4 buckets

5. Delete 16, then 4. The last deletion merges again. 3 buckets at depth 2, 5 records

Deleting the remaining records returns the structure to one bucket at depth 0. The page checks that round trip over all 720 insertion orders of six keys.

Example 6 — the skew, measured

Five keys, capacity 2: 1, 17, 33, 49, 65. Every one is congruent to 1 modulo 16, so every one ends in 0001.

1. 1 arrives, then 17: two records, one bucket, fits at depth 0.

2. 33 arrives: d′ = d = 0, double to 1, split on bit 0. Both 1 and 17 have bit 0 = 1, so both move and the new bucket is still over capacity. the split achieved nothing

3. The same thing happens at bits 1, 2 and 3: 1, 17, 33 and 49 agree on all four low bits.

4. The directory doubles six times, reaching depth 6.

5. Final state, computed: 64 directory entries, 7 buckets, 5 records.

This is the honest worst case: the directory can grow to roughly one entry per record. The algorithm is not wrong; its assumption — that the hash spreads keys over the low bits — has failed. The engineering answer is a small overflow allowance with doubling on a threshold.

Edge case 1 — the initial state is depth 0, not depth 1

At the start there is one directory entry and one bucket, and both depths are 0. The first overflow therefore has d′ = d = 0 and doubles immediately, to a two-entry directory. The first split of any structure is always preceded by a doubling.

Consequence for counting: "after k splits the directory has doubled k times" is false. In the ten-record trace, 5 splits produced only 3 doublings, because two of the splits found a bucket at d′ < d.

Edge case 2 — a bucket at d′ = d has exactly one pointer

2d−d = 20 = 1. Such a bucket cannot be split without a new entry, which is precisely why the doubling case exists. A bucket at d′ < d always has at least two pointers, so it can always be split without touching the array.

The test that settles a question: count the pointers reaching the overflowing bucket. One pointer means the directory must grow; more than one means it must not.

Edge case 3 — a split can immediately overflow again

If every record in the bucket has the same bit at position d′, the split sends all of them to one half and that half is over capacity again. The loop repeats: another doubling, another bit. In the ten-record trace this happened to the very first bucket, which doubled twice while inserting a single key.

So one insert can cause more than one doubling, and the skew example is the extreme case: six doublings for five keys. A question that says "one insertion caused a split" is not the same as "one insertion caused one doubling".

Edge case 4 — duplicates cannot be separated

Two records whose full hash values are identical agree on every bit the directory could ever read. No number of doublings separates them, so the bucket overflows for ever.

This is the one documented exception to "no overflow chain": real implementations chain duplicates, and the structure gives up on separating them. Ramakrishnan and Gehrke state it as a comment on the scheme rather than a defect in an implementation.

Edge case 5 — deleting to empty

Deletion must be able to undo everything. If the last record goes and the merges and halvings are correct, the structure returns to exactly its initial state: one bucket, one entry, both depths 0. If it does not, the deletion path is wrong somewhere.

This page checks that over all 720 insertion orders of six keys from six: insert all six, delete all six, and require depth 0, one bucket, zero records, and no invariant violation at any intermediate step.

Edge case 6 — which end are the bits read from?

The original paper (Fagin, Nievergelt, Pippenger and Strong, 1979) uses the first d bits of the hash value and calls them a prefix. Ramakrishnan and Gehrke, and most database texts, use the last d bits, because then doubling is a single copy of the array.

Both are internally consistent, and the depths, the split rule and the counts are identical. Only the entry numbers differ. A question that gives a binary hash usually says which end; if it does not, say which convention you are using and stay inside it.

Edge case 7 — the merge needs both conditions, and here is what each one stops

Condition A: the same local depth on both sides. Buckets that disagree on d′ are not split images of each other — one of them spans more of the directory — so merging them would leave a pointer array that no longer matches the buckets. Condition B: the combined records fit in one bucket. Without it, the merge creates an overflowing bucket, and the structure would have to split it again immediately.

Worked boundary: in the deletion trace, deleting 20 leaves one record against a split image holding two. 1 + 2 = 3 > 2, so condition B refuses and the structure keeps 6 buckets. Deleting 24 next leaves 1 + 1 = 2, so the merge goes through and the local depth falls from 3 to 2. The two deletions differ only in the count.

“A bucket overflow always doubles the directory”

Wrong. It doubles only when d′ = d. When d′ < d the bucket already has at least two pointers, so the split repoints them and the array is untouched.

In the ten-record trace: 5 splits, 3 doublings. Two of the splits were free of any directory work.

“The directory has 2d entries, so there are 2d buckets”

Wrong. 2d is an upper bound. Buckets at d′ < d are pointed at by several entries each, which is the entire saving the scheme makes.

Computed here: the finished trace has 8 entries and 6 buckets; 20 records at depth 4 fill 12 of 16 entries. A question that asks for the bucket count needs the sequence traced.

“Global depth is the number of records per bucket”

Wrong, and this one costs marks. Global depth is a number of bits, not a count of anything stored. The capacity is a separate parameter of the block: how many records fit in one disk block.

The three quantities are independent: capacity comes from the block size and record size, d from the data distribution, and d′ from what one bucket happened to need.

“Extendible hashing has no overflow, ever”

Almost, and the exception matters. It has no overflow for distinct hash values, because it can always read another bit. Records with identical full hash values cannot be separated at all.

The other honest qualification is skew: the directory can grow to about one entry per record, so the space saved in the buckets can reappear in the directory.

“A hash index is faster, so use it for everything”

Wrong for ranges. Eight consecutive keys touch eight different buckets here. A B+ tree reads one leaf and walks the chain, and it also answers ORDER BY, MIN, MAX and prefix matches.

A database offers both because the choice is about the query, not about which structure is better.

“Deleting a record always shrinks the directory”

Wrong. Two separate events must happen first: the bucket must merge with its split image, and then every local depth must be below the global depth. A single deletion usually does neither.

In the trace, deleting 20 changed no bucket count at all; deleting 24 merged; only deleting 22 made the halving possible.

The two pairs that get confused, side by side

pairthe distinctionwhat tells them apart
d vs d′ d is one number for the whole directory; d′ is one number per bucket and is never larger ask “how many pointers reach this bucket?” — 2d−d′ uses both
extendible vs linear extendible splits the bucket that overflowed and needs a directory; linear splits the next bucket in a fixed order and needs none does the structure have a pointer array, and is the split order round-robin?
split vs doubling the split redistributes records and is always needed; the doubling only creates a pointer and may not be needed compare d′ with d before moving anything

A fourth pair worth keeping apart: directory entries (2d) and block reads (1, or 2 if the directory is on disk). The first is a size, the second is a cost.

The six question shapes this topic produces

1. Read a structure. Given the directory and the depths, name the bucket for a key, or the keys in a bucket. write the low d bits, then read the entry

2. Count the pointers. “How many directory entries point to a bucket at d′ = 2 in a depth-4 directory?” 2d−d′

3. Trace one insert. Given the state, say what happens and give the new depth. compare the two depths first

4. Bound a size. Maximum records, minimum depth, directory bytes. three different formulas

5. Choose an index. Given a query shape, say hash or B+ tree and why. equality against range

6. Compare schemes. Static against extendible against linear, on cost and on structure. a table, not a ranking

The procedure, in the order that avoids a second pass

1. Write the key in binary. every later step reads bits, not decimals

2. Read the low d bits as the entry number. and note which end the question uses

3. Follow that entry to its bucket. If the key is there, the lookup is done.

4. If the bucket has room, insert and stop. most inserts end here

5. If it is full, compare d′ with d before moving anything. equal → double then split; smaller → split only

6. Redistribute on bit d′, then increment both local depths.

7. Recheck: entries = 2d, d = max d′, each bucket reached by 2d−d′ entries, no bucket over capacity.

Where the marks are actually lost

  • Comparing the depths after the split instead of before — the local depth has already changed, so the answer inverts.
  • Splitting on bit d instead of bit d′. One bit too high and the records do not separate at all.
  • Reporting 2d as the number of buckets. It is the number of entries, and an upper bound on the buckets.
  • Reading the bits from the wrong end, or mixing the two conventions inside one calculation.
  • Forgetting that one insert can double more than once, when the records share the bit being examined.
  • Merging on the record count alone, without checking that both buckets have the same local depth.
  • Calling the directory halving automatic after any deletion; it needs every local depth below d.

MCQ original

Q1 — pointers to one bucket

In an extendible hash structure the global depth is 4 and one bucket has local depth 2. How many directory entries point to that bucket?

(a) 2  (b) 4  (c) 8  (d) 16

(b) 4. The count is 2d−d′ = 24−2 = 4.

(a) is d′ itself, the commonest slip: local depth is a number of bits, not a number of pointers. (c) is 2d′, and (d) is the whole directory.

Sanity check: four entries agreeing on the low two bits is 24−2 = 4 combinations of the two remaining bits. It must be a power of two, and it must divide the directory size.

NAT original

Q2 — the smallest directory that can hold 100 records

Each bucket holds 8 records. What is the minimum global depth of a directory able to hold 100 records?

4. At least ⌈100/8⌉ = 13 buckets are needed. The smallest d with 2d ≥ 13 is 4, giving 16 entries and a ceiling of 128 records.

The two wrong answers are 3 (8 entries, 64 records, too few) and 7 (which is the answer for 100 buckets, not 100 records).

This is a floor, and it assumes a uniform hash. Skew can force a larger directory for the same record count, which is why the question says “minimum”.

MCQ original

Q3 — when does the directory double?

A bucket overflows. The directory must double when, before the split:

(a) the bucket holds more than the capacity (b) d′ < d (c) d′ = d (d) the number of buckets reaches 2d

(c). Equality means the bucket has exactly 20 = 1 pointer, so a new entry has to be created for the second bucket.

(a) is what caused the overflow, not what decides the response. (b) is the case that does not double: a spare pointer already exists. (d) describes a consequence, not a condition — and after a doubling the bucket count is still below 2d because buckets share entries.

The comparison must be made on the bucket as it stands. After the split both halves have d′ = d + 1, so re-reading the depths gives the wrong answer.

NAT original

Q4 — the ceiling on records

A directory has global depth 4 and each bucket holds 3 records. What is the largest number of records the structure can hold?

48. At most 24 = 16 buckets, each holding 3, so 16 × 3 = 48.

The tempting wrong answer is 12 (which is 4 × 3, reading the depth as a bucket count) or 24 (using 8 buckets, the depth-3 count).

This is a ceiling and it needs every bucket distinct and full. In practice buckets share entries, so the real count is lower — the trace here holds 10 records in 8 entries at capacity 2, against a ceiling of 16.

MCQ original

Q5 — trace one insert

A structure has global depth 2 with 4 entries, and every bucket has local depth 2. Inserting a key whose bucket is full leaves the global depth at:

(a) 1  (b) 2  (c) 3  (d) 4

(c) 3. Every bucket is at d′ = d = 2, so the overflowing bucket has one pointer. The directory doubles to 8 entries and depth 3, and then the split runs.

(b) is the trap for anyone who assumes a split never touches the directory. (a) is impossible: depth never falls on an insert. (d) would need two doublings, which happens only if the split leaves all records in one half — possible when the keys share the new bit, but not implied here.

“Every bucket has local depth 2” is the whole question. With one bucket at d′ = 1 the answer would be 2, because that bucket could split without the directory growing.

MSQ original

Q6 — which statements hold

For extendible hashing with the directory held in main memory, which of these are true?

(A) an equality lookup costs one block read (B) a range query is answered by following a chain of buckets (C) there is no overflow chain for distinct hash values (D) the number of buckets equals 2d

A and C. A: the directory entry is computed arithmetically, so only the bucket is read. C: as long as two records differ in some bit, another bit can be read, so no chain is needed.

B is false: there is no leaf chain, because the buckets are not in key order. That is the B+ tree. D is false: 2d is an upper bound, and buckets at d′ < d are shared.

C needs its qualification to be exactly right: distinct hash values. Records with identical full hash values cannot be separated by any number of bits, and those do chain.

MCQ original

Q7 — when the directory can halve

After a deletion, the directory can be halved when:

(a) the deleted bucket becomes empty (b) the bucket merges with its split image (c) every local depth is strictly less than the global depth (d) the number of records falls below 2d

(c). Halving needs entry i and entry i + 2d−1 to agree for every i, and that is exactly the condition that no bucket sits at d′ = d.

(a) and (b) are necessary steps, not the condition: a bucket can merge and the directory still cannot halve, because some other bucket is still at d′ = d. (d) confuses a count of records with a count of bits.

In the deletion trace, deleting 24 merged a pair and left depth 3; only after deleting 22 did the last bucket at d′ = 3 drop to 2, and then the halving to depth 2 became possible.

NAT original

Q8 — directory size in bytes

A directory has global depth 10 and each pointer is 4 bytes. What is the size of the directory in bytes?

4096. 210 = 1024 entries, and 1024 × 4 = 4096 bytes, which is 4 KiB.

The wrong answers are 10240 (multiplying the depth by something) and 2048 (using a two-byte pointer, or halving the entries by mistake).

Carry the pattern forward: depth 20 at four bytes is 4 MiB, which is why the resident-directory assumption usually holds even for a file of millions of records.

Definitions, one line each

  • Directory — an array of 2d pointers to buckets, addressed by the low d bits of h(k).
  • Global depth d — the number of low-order hash bits the directory reads; equal to the largest local depth.
  • Local depth d′ — the number of low-order bits a particular bucket needed; at most d.
  • Pointers per bucket — 2d−d′, all agreeing on the bucket’s low d′ bits.
  • Split — redistribute a bucket’s records on bit d′; both halves take d′ + 1.
  • Doubling — replace the array by two copies of itself; entry i + 2d becomes entry i, and d rises by one.
  • Split image (buddy) — the bucket that agrees with another on every bit except d′ − 1.
  • Merge — rejoin two split images when their local depths match and their records fit in one bucket.
  • Halving — drop the second half of the array when every local depth is below d.

The formulas, and the one condition each needs

  • Entry for key k: h(k) AND (2d − 1) — the low d bits, unless the question says prefix.
  • Pointers to a bucket: 2d−d′ — needs d and d′ at the same instant, before any split.
  • Maximum records: 2d × capacity — a ceiling, needing distinct buckets and full buckets.
  • Minimum depth: smallest d with 2d ≥ ⌈N / capacity⌉ — a floor, assuming a uniform hash.
  • Directory bytes: 2d × pointer width — no condition.
  • Equality lookup: 1 block read, or 2 if the directory is on disk — the condition is residency.
  • Range lookup: no guarantee at all; a range can touch every bucket.

Decision procedure for an exam question

1. Write the key in binary. bits, not decimals, from here on

2. Take the low d bits as the entry, unless a prefix convention is stated. note which end, and stay in it

3. Read the bucket and its d′. the two depths are the whole decision

4. Full? Compare d′ with d. Equal → double, then split. Smaller → split only.

5. Split on bit d′; both halves take d′ + 1; repoint the entries that reached it.

6. Recheck four things: entries = 2d, d = max d′, pointers = 2d−d′, no bucket over capacity.

7. Answer the quantity asked for. depth, entries, buckets and reads are four different numbers

Traps, each with the case that defuses it

  • Doubling on every overflow — 5 splits, 3 doublings in the trace.
  • Buckets = 2d — 8 entries, 6 buckets; 16 entries, 12 buckets.
  • Local depth as a pointer count — 2d−d′, so d′ = 2 at d = 4 gives 4.
  • Comparing the depths after the split — after it, both halves are at d′ + 1.
  • Splitting on bit d instead of d′ — the records do not separate.
  • “No overflow ever” — duplicate hash values cannot be separated.
  • “Ranges work too” — eight consecutive keys, eight buckets.
  • Halving after any deletion — needs every d′ below d.

The one-screen summary

A fixed bucket count overflows as the file grows, and the overflow chain is what makes the lookup cost grow with it. Extendible hashing adds a directory of 2d pointers indexed by the low d bits of the hash, so a bucket is found in one probe and the only disk access is the bucket itself. Each bucket records the number of bits it actually needed, its local depth d′, and that single number explains everything else: a bucket at d′ is reached by 2d−d′ entries, all agreeing on its low bits; an overflow with d′ < d splits and repoints; an overflow with d′ = d doubles the array first, because the bucket has only one pointer. Doubling is a copy — entry i + 2d becomes entry i — and that is the only reason the index is taken from the low end. Deletion reverses all of it: merge split images whose records fit and whose depths match, then halve the array once every local depth has fallen below the global depth. The price is a directory that can grow to about one entry per record when the hash is skewed, and the total absence of range queries, which is the B+ tree’s job. When a question asks for a number, decide first whether it wants a depth, an entry count, a bucket count or a block count — they are four different answers and only one of them is 2d.
